Cloud & AWS Core: The Complete Guide

Understand cloud computing from first principles and master the core AWS services every DevOps engineer uses daily — compute, networking, storage, databases, security, and cost — with diagrams and hands-on CLI.

📖 How to read this guide

Concepts are cloud-general but examples use AWS (the market leader; Azure/GCP have direct equivalents). Each topic: what it is, why it exists, the CLI, and ★ best practice. This underpins the Terraform, Kubernetes/EKS, and CI/CD guides.

1. What is the Cloud?

The cloud is renting computing resources — servers, storage, databases, networking — on demand over the internet, instead of buying and running your own hardware.

Cloud = electricity, not a generator

You don't build a power plant to run your toaster — you plug into the grid and pay for what you use. The cloud is the same for computing: instead of buying servers (a generator), you rent capacity from AWS/Azure/GCP (the grid) and pay only for what you consume. Need 100 servers for an hour? Rent them, then give them back. That elasticity is the whole point.

BenefitWhat it means
ElasticScale up for a traffic spike, down when it passes — in minutes
Pay-as-you-goNo huge upfront hardware cost; pay per hour/second/request
GlobalDeploy near your users worldwide in minutes
Managed servicesLet the provider run the databases, queues, and clusters for you
Why the cloud exists — the problem it solves

Before the cloud, launching a product meant buying servers months ahead, guessing peak demand, racking hardware in a data center, and eating the cost whether or not customers showed up. Over-provision and you burned money on idle machines; under-provision and you fell over on launch day. Capacity was a slow, capital-intensive bet made before you had any real usage data. The cloud converts that upfront capital expense (CapEx) into a pay-per-use operating expense (OpEx), and shrinks provisioning from months to seconds — so you can experiment cheaply, fail cheaply, and scale only when real demand appears.

Under the hood, the magic is virtualization and multi-tenancy. AWS runs enormous fleets of physical servers in its data centers. A hypervisor (AWS's is called Nitro) slices each physical machine into many isolated virtual machines that different customers use simultaneously — none can see the others. Because AWS aggregates demand from millions of customers, the statistical peaks average out: your spike happens while someone else is quiet, so AWS keeps utilization high and passes economies of scale to you. When you "launch a server," you're really asking a control plane to carve a slice out of a machine that already exists and is already powered on.

Prove elasticity: create and destroy real capacity in seconds
$ aws ec2 run-instances --image-id ami-0abc123 --instance-type t3.micro \
    --count 1 --query 'Instances[0].InstanceId' --output text
i-0a1b2c3d4e5f67890

$ aws ec2 describe-instances --instance-ids i-0a1b2c3d4e5f67890 \
    --query 'Reservations[0].Instances[0].State.Name' --output text
running

$ aws ec2 terminate-instances --instance-ids i-0a1b2c3d4e5f67890 \
    --query 'TerminatingInstances[0].CurrentState.Name' --output text
shutting-down

Those three commands — a server born and returned in under a minute, billed only for the seconds it ran — capture the entire economic shift. Buying that same box physically would take weeks and thousands of dollars.

Common mistake: "the cloud is always cheaper"

Pay-per-use is only cheap when you actually turn things off. A server you forget to terminate bills 24×7 forever; a dev environment left running over a weekend costs the same as one serving customers. The classic "$5,000 surprise" is a beefy instance or an idle RDS database that ran for a month unnoticed. Cloud rewards elasticity and punishes "set it and forget it." Tag resources, set budgets, and shut down what you're not using (§14).

Mental model: a hotel, not a house

Owning servers is buying a house — huge upfront cost, you maintain everything, and empty rooms still cost you. The cloud is a hotel: check in when you need a room, pay per night, get a bigger suite or more rooms instantly, and check out when you're done. The catch is the same as a real hotel — if you never check out, the meter keeps running.

2. IaaS / PaaS / SaaS

Cloud services come at different levels of abstraction — how much the provider manages versus you.

Why three models exist — the trade you're making

Every abstraction level is the same bargain: you give up control to gain leverage. With IaaS (raw VMs) you control the OS, kernel, and every package — but you also own patching, scaling, and 3am pages. With PaaS you hand the runtime and OS to the provider and just ship code — faster, but you accept their versions, limits, and lock-in. With SaaS you own nothing but your data and config. The models exist because different workloads sit at different points on the "how much do I want to operate?" curve. There is no "best" level — only the right level for a given problem and team size.

Under the hood there's no hard technical boundary — each higher level is built on the one below. AWS Elastic Beanstalk (PaaS) is literally EC2 instances (IaaS) plus an Auto Scaling Group, a load balancer, and a deployment agent that AWS wires up and manages for you. RDS (PaaS) is a managed process running on EC2-class hardware with automated backups and failover bolted on. When you "move up" a level, you're not using different hardware — you're delegating the operational glue to AWS's automation instead of writing it yourself.

Same app, two levels of abstraction
# IaaS path: you own the whole stack on a bare VM
$ aws ec2 run-instances --image-id ami-0abc123 --instance-type t3.small ...
# → then YOU install nginx, the runtime, deploy code, configure logrotate,
#   patch the OS monthly, set up the load balancer, wire up autoscaling...

# PaaS path: AWS owns everything below your code
$ aws elasticbeanstalk create-application --application-name myapp
$ eb create myapp-prod --instance-type t3.small
# → AWS provisions EC2 + ALB + ASG + health checks + rolling deploys for you.
#   You only ever touch application code and a config file.

Common mistakes: paying twice and quiet lock-in

Billing: PaaS/SaaS pricing hides the IaaS underneath — a "managed" service still bills you for the instances, storage, and data transfer it runs on, plus a premium. Teams get surprised when a "simple" managed service costs 2-3× the raw compute. Lock-in: the higher you go, the harder it is to leave — SaaS and proprietary PaaS (e.g., DynamoDB, Beanstalk configs) tie you to one vendor's APIs. That's often a fine trade, but make it deliberately, not by accident.

Mental model: pizza-as-a-service

Making pizza at home = on-prem (you buy the oven, dough, everything). Take-and-bake = IaaS (they supply ingredients, you provide the oven and bake it). Pizza delivery = PaaS (they cook it, you provide the table and drinks). Dining out = SaaS (you just show up and eat). Same pizza in the end — the only question is how much of the work you want to do yourself versus pay someone else to handle.

3. The Shared Responsibility Model

Security in the cloud is split: the provider secures the cloud itself; you secure what you put in it.

The most misunderstood security concept

AWS secures the infrastructure (data centers, hardware, hypervisor). You are responsible for your data, IAM permissions, network config, patching your instances, and encryption. "The cloud is secure" does not mean "your setup is secure." Most breaches are misconfigurations on the customer side (public S3 buckets, over-broad IAM) — not AWS failing.

Why the split exists — and why the line moves

The model exists because a single party can't secure both ends: AWS can't know that your S3 bucket should be private, and you can't audit AWS's physical data-center access. So responsibility is split at the boundary each party actually controls. Crucially, the line moves with the service model (§2): on EC2 (IaaS) you patch the guest OS; on RDS (PaaS) AWS patches the OS and database engine but you still own users, passwords, network placement, and encryption settings; on S3 (SaaS-like) AWS runs everything but you own bucket policies and access. The higher-level the service, the more AWS covers — but there is always a customer slice, and it's always the data and access controls.

How it works in practice: AWS calls its half "security of the cloud" and yours "security in the cloud." AWS proves its half through third-party audits and compliance attestations (SOC 2, ISO 27001, PCI DSS) that you can download from AWS Artifact — you inherit those controls. Your half is enforced by the tools in §12: IAM policies, security groups, KMS encryption, and CloudTrail auditing. Nothing automatically makes your slice secure; the defaults are safe-ish but you must actively configure least privilege, encryption, and network isolation.

Auditing YOUR half — find the misconfigurations attackers look for
# Is any S3 bucket publicly readable? (the #1 breach cause)
$ aws s3api get-public-access-block --bucket my-bucket
An error occurred (NoSuchPublicAccessBlockConfiguration) ...
# ^ NO block configured = danger. A safe bucket returns:
{
  "PublicAccessBlockConfiguration": {
    "BlockPublicAcls": true,
    "IgnorePublicAcls": true,
    "BlockPublicPolicy": true,
    "RestrictPublicBuckets": true
  }
}

# Any security group open to the whole internet on SSH/RDP?
$ aws ec2 describe-security-groups \
    --filters Name=ip-permission.cidr,Values='0.0.0.0/0' \
    --query 'SecurityGroups[].GroupId' --output text
sg-0badc0ffee   # <- investigate: is 0.0.0.0/0 really intended here?
Common mistakes: assuming AWS "has it covered"

Security: teams assume encryption, backups, and access control are automatic. They are not — an unencrypted EBS volume, a public snapshot, an over-broad "Action":"*" IAM policy, or a security group open to 0.0.0.0/0 are all firmly in your half. Billing surprise adjacent: AWS's DDoS protection (Shield Standard) is free, but application-layer protection (WAF, Shield Advanced) is your responsibility and costs extra — assuming you're protected when you aren't is both a security and a cost trap after an attack.

Mental model: renting an apartment

The building owner (AWS) secures the foundation, exterior walls, and front-door lock system. But you decide whether to actually lock your own apartment door, who gets a copy of your key, and whether you leave your valuables on the balcony. If you prop your door open and get robbed, the building was still "secure" — you just didn't do your part. That's the shared responsibility model.

4. Regions & Availability Zones

AWS is organized into geographic Regions, each containing multiple isolated Availability Zones (AZs) — the foundation of high availability.

Always design for multi-AZ

Run at least two AZs for anything that matters. Load balancers, RDS, and Kubernetes worker nodes should all span AZs. It's the single cheapest, highest-impact availability decision you'll make.

Why this hierarchy exists — failure domains

The Region/AZ split exists to give you independent failure domains. A single data center can lose power, flood, or catch fire; a whole region can suffer a rare large-scale outage. AZs are physically separate data centers (miles apart, independent power, cooling, and networking) but joined by fast, low-latency private links — so you get fault isolation and the ability to run one system across several. Regions are hundreds of miles apart for true disaster isolation and to satisfy data-residency laws (EU data must stay in EU regions, etc.). Placing copies of your app in multiple AZs means one data center dying is a non-event; placing them in multiple regions protects against the once-in-a-decade regional failure.

How it works under the hood: AZs within a region are connected by redundant, dedicated fiber with single-digit-millisecond latency, which is why synchronous replication (like RDS Multi-AZ) works across AZs but not across regions (too far, too slow). Each AZ maps to one or more physical data centers, and — importantly — AWS shuffles which physical AZ your account's us-east-1a points to, so two customers' "us-east-1a" may be different buildings. That prevents everyone from piling into the same "first" AZ. Cross-region data transfer, by contrast, traverses the public-ish AWS backbone and is billed per gigabyte — a frequent source of surprise costs.

List regions and the AZs available to your account
$ aws ec2 describe-regions --query 'Regions[].RegionName' --output text

The ZoneId (e.g. use1-az4) is the physical identifier that's stable across accounts — use it, not the friendly name, when you need two accounts to land in the same real data center.

Common mistakes: single-AZ prod and cross-region egress bills

Availability: the classic outage is running everything in one AZ (or an RDS instance with Multi-AZ turned off) — when that data center blips, you're fully down, and no amount of "the cloud is reliable" saves you. Billing: data transfer between AZs and especially between regions is charged per GB and adds up fast for chatty apps or cross-region replication. Region pitfalls: us-east-1 is AWS's oldest, largest region — new features land there first, but it also has the most historical outages and some global services (IAM, CloudFront, Route 53) are anchored to it. Don't assume a resource is global; most are region-scoped, and a resource created in one region is invisible from another.

Mental model: a company with offices in several cities

A Region is a city (New York, London, Mumbai). Availability Zones are separate office buildings within that city, on different power grids and blocks — if one building loses power, staff in the other buildings keep working. Putting all your staff in one building is risky; spreading them across buildings in one city survives a local outage; opening offices in multiple cities survives a citywide disaster. That's exactly the multi-AZ vs multi-region trade-off.

Mental model: renting an apartment

The landlord (AWS) secures the building — locks on the front door, structural walls, the fire-suppression system. You (the customer) secure your own apartment — you decide who gets a key, whether you leave a window open, and what valuables you leave lying around. "Living in a secure building" doesn't help if you prop your own door open. Most cloud breaches are propped-open doors, not the building failing.

5. Accounts, IAM & the CLI

IAM (Identity and Access Management) controls who can do what. Get this right and most cloud security follows.

IAM conceptWhat it is
UserA person or app with long-term credentials (avoid for apps)
RoleA set of permissions that can be assumed temporarily (preferred for apps & services)
PolicyA JSON document listing allowed/denied actions on resources
GroupA collection of users sharing policies
Configure the CLI & basic calls
aws configure                 # set access key, region, output format
aws sts get-caller-identity   # who am I? (verify credentials)
aws ec2 describe-instances --region us-east-1
aws s3 ls
IAM golden rules
  • Least privilege — grant only what's needed, nothing more.
  • Roles, not long-lived keys — apps/EC2/EKS assume roles; CI uses OIDC (see CI/CD guide).
  • MFA on humans, especially the root account — then lock root away.
  • Multi-account via AWS Organizations — separate prod/dev/security accounts to limit blast radius.
Why IAM exists — the problem it solves

An AWS account can create resources that cost real money and hold real data. Without fine-grained control, everyone would share one all-powerful "root" login — one leaked password and an attacker owns everything, and you'd have no record of who did what. IAM solves three problems at once: authentication (proving who you are), authorization (deciding what you may do), and auditability (recording it, via CloudTrail). It lets you give a build server permission to write to exactly one S3 bucket and nothing else, give a developer read-only access to logs, and guarantee the intern can't delete the production database — all enforced by AWS on every single API call.

How it works under the hood: every AWS action is an API call, and every call carries a signed identity. Before AWS executes it, the IAM engine evaluates all applicable policies and answers one question — allow or deny (see the full evaluation logic in §18). The key insight is roles vs users: a user has long-lived access keys (a password that never expires until you rotate it); a role has no permanent credentials — instead an entity assumes it and receives temporary keys that expire in minutes to hours via the STS (Security Token Service). When an EC2 instance needs S3 access, it doesn't store a key — it assumes an "instance profile" role and AWS injects short-lived credentials automatically. Nothing to leak, nothing to rotate.

Roles in action — assume a role and get temporary credentials
# Who am I right now?
$ aws sts get-caller-identity
{
  "UserId": "AIDAEXAMPLE",
  "Account": "123456789012",
  "Arn": "arn:aws:iam::123456789012:user/dev-sandeep"
}

# Assume a more-privileged role for a specific task (temporary!)
$ aws sts assume-role \
    --role-arn arn:aws:iam::123456789012:role/deploy-role \
    --role-session-name my-deploy
{
  "Credentials": {
    "AccessKeyId": "ASIA...",
    "SecretAccessKey": "wJal...",
    "SessionToken": "FQoGZ...",
    "Expiration": "2026-09-27T13:32:00Z"   <- expires in 1 hour, then useless
  },
  "AssumedRoleUser": { "Arn": "arn:aws:sts::123456789012:assumed-role/deploy-role/my-deploy" }
}
Common mistakes: long-lived keys and wildcard policies

Security: the two most damaging IAM mistakes are (1) committing access keys to Git — bots scan public repos and start mining crypto on your account within minutes, producing five-figure bills; and (2) attaching AdministratorAccess or "Action":"*","Resource":"*" "just to make it work" — that key is now a master key to your whole account. Also: using the root user for daily work (it can bypass most restrictions — lock it away with MFA and never use it), and forgetting to enable MFA on humans. If keys leak, rotate them immediately and check CloudTrail for what they touched.

Mental model: a hotel with keycards, not a master key

A user with long-lived keys is like giving someone a permanent master key — if it's copied, you're in trouble forever. A role is like the front desk issuing a keycard that only opens your room and only works until checkout. Apps and servers should always get temporary keycards (assume a role), never the master key. Least privilege just means: the keycard opens the fewest doors needed to do the job — housekeeping doesn't get into the safe.

Why roles beat access keys

A user carries long-lived credentials that leak, get committed to Git, and rarely rotate. A role is an identity that is assumed — the caller (an EC2 instance, a Lambda, another account) receives short-lived credentials from STS that auto-expire in minutes to hours. Nothing to store, nothing to leak, nothing to rotate. This is why EC2 uses an instance profile and Lambda uses an execution role instead of embedded keys. The golden rule: humans and services should assume roles; long-term access keys are a last resort.

Mental model: a hotel

An IAM user is a permanent staff badge. A role is a guest keycard from the front desk — it works only for your room, only until checkout, then it's dead. A policy is the list printed on the card: "opens room 412 and the gym, not the manager's office." And the hotel's rule is simple — if any list says "never open the safe room," that "no" beats every "yes" (explicit Deny always wins).

6. EC2 — Virtual Servers

EC2 (Elastic Compute Cloud) gives you virtual machines on demand — the classic "server in the cloud."

Launch & manage an instance
aws ec2 run-instances --image-id ami-0abc123 --instance-type t3.micro \
  --key-name mykey --security-group-ids sg-123 --subnet-id subnet-123
aws ec2 describe-instances --filters "Name=instance-state-name,Values=running"
aws ec2 stop-instances --instance-ids i-0abc123

Don't hand-launch prod servers

Define EC2 in Terraform, configure with Ansible or a baked AMI, and run them behind an Auto Scaling Group. Manually-launched "pet" servers become undocumented liabilities.

Why EC2 exists — and how it actually boots

EC2 exists to give you a full operating system you control — root access, any software, any kernel tweak — without owning hardware. It's the escape hatch for anything that doesn't fit a managed service: legacy apps, custom networking, GPU workloads, or software with weird install requirements. Under the hood, launching an instance means AWS's control plane picks a physical host with spare capacity, the Nitro hypervisor carves out your vCPUs and memory, attaches an EBS volume (a network-attached virtual disk) built from your chosen AMI (a disk image/snapshot), plugs in a virtual network card (ENI) inside your VPC subnet, and boots it. An instance type like t3.micro just names a fixed recipe of vCPU + RAM + network capacity (§22 covers the families).

Two under-the-hood details matter constantly. First, user data: a script you pass at launch that runs once on first boot — this is how instances self-configure (install packages, pull code) without you SSHing in. Second, instance metadata (IMDS): every instance can query http://169.254.169.254 to learn its own ID, region, and — critically — fetch the temporary credentials for its attached IAM role. That's the mechanism behind "roles, not keys" from §5.

A realistic launch: self-configuring instance + verify it
$ aws ec2 run-instances --image-id ami-0abc123 --instance-type t3.micro \
    --key-name mykey --security-group-ids sg-123 --subnet-id subnet-123 \
    --iam-instance-profile Name=web-role \
    --user-data 'file://bootstrap.sh' \
    --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=web-1},{Key=env,Value=prod}]' \
    --query 'Instances[0].InstanceId' --output text
i-0d1e2f3a4b5c6d7e8

$ aws ec2 describe-instances --instance-ids i-0d1e2f3a4b5c6d7e8 \
    --query 'Reservations[0].Instances[0].{State:State.Name,IP:PrivateIpAddress,Type:InstanceType}'
{
  "State": "running",
  "IP": "10.0.1.53",
  "Type": "t3.micro"
}

The bootstrap.sh user-data script runs automatically on that first boot — no manual login needed. Prefer SSM Session Manager over SSH for shell access (no open port 22, full audit trail).

Common mistakes: stop ≠ terminate, and the t-family CPU-credit trap

Billing: (1) A stopped instance costs nothing for compute but you still pay for its EBS volume and any Elastic IP — "I stopped it, why am I billed?" (2) The cheap burstable t3/t4g family runs on CPU credits; a steadily busy workload exhausts credits and either throttles hard or (with "unlimited" mode) silently bills extra — great for spiky dev, bad for sustained load. (3) Forgetting to terminate a big instance over a weekend. Security: a security group with SSH open to 0.0.0.0/0, or baking secrets into the AMI/user-data (user-data is readable by anything on the instance via IMDS). Set --metadata-options HttpTokens=required to enforce IMDSv2 and block SSRF credential theft.

Mental model: renting a bare computer in someone else's building

EC2 is renting an empty PC in AWS's data center — it comes with a chosen amount of CPU and RAM, a blank-ish hard drive (the AMI is the pre-installed OS image), and a network cable into your private network (the VPC). You get the keyboard (root access) and can install anything. "Stopping" it is like putting the PC to sleep — you stop paying for electricity (compute) but still pay rent on the hard drive (EBS). "Terminating" throws the PC away entirely. The maintenance burden — patching, scaling, replacing it when it dies — is the price of that full control.

7. Containers, Lambda & Serverless

EC2 isn't the only way to run code. Modern AWS gives you containers and serverless — often better fits.

Serverless ≠ no servers

"Serverless" means you don't think about servers — the provider runs, scales, and patches them invisibly. With Lambda you upload a function; it runs on demand, scales to thousands of copies automatically, and you pay per millisecond of execution. Idle costs nothing. Great for APIs, event processing, and glue between services.

Why these options exist — matching the unit of deployment to the work

EC2 makes you manage a whole VM even if your code is a 50-line function that runs twice a day — you pay 24×7 and patch an OS for almost no work. The compute spectrum exists to shrink both the unit you deploy and the ops you own. Containers (ECS/EKS) package your app with its dependencies so it runs identically everywhere and starts in seconds. Fargate removes even the container hosts — you declare CPU/memory per task and AWS finds the hardware. Lambda goes furthest: the unit is a single function, it scales from zero to thousands of parallel copies automatically, and idle costs nothing. Each step trades control and flexibility for less operational burden.

How Lambda works under the hood: your code sits packaged (zip or container image) doing nothing until an event arrives — an HTTP request via API Gateway, a new S3 object, an SQS message, a schedule. On that trigger AWS spins up a tiny isolated micro-VM (Firecracker), loads your code, and runs the handler. The first invocation on a fresh micro-VM pays a cold start (the runtime and your init code load — tens to hundreds of ms). AWS keeps the environment warm for a while to reuse it, but under a traffic spike it launches many environments in parallel — that's how it scales. You're billed for GB-seconds: memory allocated × milliseconds run, rounded to the ms.

Deploy and invoke a Lambda; see per-request billing
$ zip function.zip index.py
$ aws lambda create-function --function-name hello \
    --runtime python3.12 --handler index.handler \
    --zip-file fileb://function.zip \
    --role arn:aws:iam::123456789012:role/lambda-basic --memory-size 128 --timeout 10
{ "FunctionName": "hello", "State": "Active", "MemorySize": 128 }

$ aws lambda invoke --function-name hello --payload '{"name":"world"}' out.json
{ "StatusCode": 200, "ExecutedVersion": "$LATEST" }
$ cat out.json
{"message": "hello world"}

Common mistakes: the scaling-cost paradox and hidden VM under "no servers"

Billing: Lambda is nearly free when idle but can be more expensive than an always-on instance under sustained heavy traffic — past a steady load threshold, a right-sized EC2/Fargate task is cheaper. Also, a runaway loop or recursive trigger (Lambda writes to S3 which triggers the same Lambda) can fan out to thousands of concurrent executions and rack up cost fast — set reserved concurrency limits. Ops gotchas: Lambda's default account concurrency is ~1,000 — a spike can throttle other functions; a slow downstream database gets hammered by sudden parallelism (buffer with SQS); and "serverless" still runs on servers you can't SSH into, so debugging is via logs and traces (X-Ray), not a shell.

Mental model: taxi vs owning a car

An EC2 instance is owning a car — it sits in your driveway (and you pay for it) whether you drive or not, and you handle the oil changes. Lambda is calling a taxi — one appears only when you need a ride, you pay just for that trip, and a hundred taxis show up if a hundred people need rides at once. Perfect for occasional trips; but if you commute constantly, owning the car (a steady server) ends up cheaper. Containers/Fargate sit in between — like a rental you keep for the busy season.

8. Load Balancing & Auto Scaling

Distribute traffic across healthy instances and add/remove capacity automatically with demand.

Why LB + ASG exist — two different problems

They solve two problems people often conflate. A load balancer solves distribution and health: it gives clients one stable address, spreads requests across many backends, and stops sending traffic to any instance that fails its health check — so a dying server drops out silently instead of serving errors. An Auto Scaling Group solves capacity and self-healing: it keeps a target number of instances running, launches replacements when one dies or fails health checks, and adds/removes instances as demand changes. Together they turn a fixed set of fragile "pet" servers into an elastic, self-repairing fleet of interchangeable "cattle." AWS offers three LB types: ALB (Layer 7, HTTP/HTTPS, path/host routing — the default for web apps), NLB (Layer 4, TCP/UDP, extreme throughput/low latency), and the legacy CLB.

How scaling actually works: the ASG has a launch template (the recipe: AMI, instance type, user-data, security groups) and min/desired/max counts. A scaling policy watches a CloudWatch metric — the modern approach is target tracking: you say "keep average CPU at 50%" and AWS does the math to add or remove instances to hold that target, like a thermostat. Health checks come from two sources: the EC2 status check (is the VM alive?) and, better, the ELB health check (does the app actually respond 200 on /health?). When the LB marks a target unhealthy, the ASG can terminate and replace it. New instances register with the LB's target group only after passing health checks, so traffic never hits a half-booted server.

Target-tracking autoscaling: "keep CPU near 50%"
# Create the ASG from a launch template, spanning multiple AZs
$ aws autoscaling create-auto-scaling-group --auto-scaling-group-name web-asg \
    --launch-template LaunchTemplateName=web-lt,Version='$Latest' \
    --min-size 2 --max-size 10 --desired-capacity 2 \
    --vpc-zone-identifier "subnet-aaa,subnet-bbb,subnet-ccc" \
    --target-group-arns arn:aws:elasticloadbalancing:...:targetgroup/web/abc123 \

Common mistakes: bad health checks and flapping

Availability: the most common failure is a too-shallow health check — pointing it at / which returns 200 even when the database is down, so the LB keeps routing to broken instances; give it a real /health that checks dependencies. Conversely, a too-aggressive check (short interval, low threshold) plus a slow boot causes flapping: instances get killed before they finish starting, so set a sensible health-check-grace-period. Cost/behavior: a max-size set too high means a traffic spike (or a retry storm) can scale you to a huge, expensive fleet; scaling thresholds that are too twitchy cause thrash (launch/terminate churn). Statefulness: autoscaling assumes instances are disposable — if your app stores session state locally, users get logged out when their instance is replaced. Externalize sessions (ElastiCache/DynamoDB).

Mental model: a restaurant host + on-call staff

The load balancer is the host at the door — they seat each guest at a table that's free and staffed, and never seat anyone at a table where the waiter just quit (failed health check). The Auto Scaling Group is the manager who calls in more waiters when a rush hits and sends them home when it's quiet — and instantly replaces any waiter who walks out. You, the owner, just set the rules ("keep tables ~50% full per waiter") and the system staffs itself.

9. VPC — Your Private Network

A Virtual Private Cloud is your isolated network in AWS: subnets, routing, and firewalls. It's the foundation everything else sits in.

The standard secure layout

Public subnets hold only load balancers and NAT gateways. App servers and databases live in private subnets with no direct inbound internet access. Databases sit in their own subnets reachable only from the app tier. This layered design is the cloud version of the network segmentation in the Linux networking and Docker networking sections.

Why a VPC exists — isolation on shared hardware

Your instances run on physical hosts shared with other AWS customers. A VPC is the software-defined network that guarantees your traffic is completely isolated from everyone else's — as if you had your own private data-center network, but conjured in seconds. It exists so you can control exactly what can talk to what: which tiers are reachable from the internet, which are internal-only, and which paths traffic may take. Without it, "just put it in the cloud" would mean every instance is exposed and flat — the opposite of secure. The VPC is the canvas; subnets, route tables, gateways, and firewalls are how you draw the security boundaries.

How the pieces fit under the hood: a VPC owns a private IP range (a CIDR block like 10.0.0.0/16 = 65,536 addresses). You carve that into subnets, each pinned to one AZ. What makes a subnet "public" isn't a flag — it's that its route table has a route 0.0.0.0/0 → Internet Gateway. A "private" subnet's default route instead points at a NAT Gateway (for outbound-only) or has no internet route at all. Traffic is then filtered by two firewalls at different layers: Security Groups are stateful and attach to instances/ENIs (if you allow a request out, the reply is automatically allowed back — you only write allow rules); NACLs are stateless and attach to subnets (you must allow both directions explicitly, and they support deny rules). The rule of thumb: use security groups for almost everything; reach for NACLs only for coarse subnet-wide blocks.

$ aws ec2 create-subnet --vpc-id vpc-0a1b2c3d --cidr-block 10.0.11.0/24 \
    --availability-zone us-east-1a --query 'Subnet.SubnetId' --output text

Common mistakes: the two expensive/insecure classics

Security: the #1 mistake is putting app servers or (worse) databases in a public subnet with a security group open to 0.0.0.0/0 on SSH (22), RDP (3389), or the database port — bots find these in minutes. Keep app/DB tiers in private subnets; expose only the load balancer. Also, overlapping CIDR ranges between VPCs make future peering impossible — plan address space up front. Billing: NAT Gateways are a top surprise on bills — they charge an hourly fee plus per-GB for all data flowing through them. A private subnet pulling large amounts from S3 through NAT can cost real money; route S3/DynamoDB traffic through a free Gateway VPC Endpoint instead (see §19). Running one NAT per AZ is HA but multiplies the hourly cost.

Mental model: an office building with security

The VPC is your company's floor in a shared building. Subnets are rooms. The lobby (public subnet) is the only room with a door to the street (Internet Gateway) — that's where reception (the load balancer) sits. The back offices (private subnets) have no street door; staff there can still order lunch out through a controlled service exit (NAT Gateway) but nobody off the street can walk in. Security groups are the guards checking each person at each office door; route tables are the hallway signs deciding which corridors lead where.

Mental model: an office building with a lobby

The VPC is your office building. The public subnet is the lobby — visitors can walk in from the street (the Internet Gateway is the front door). The private subnet is the back offices — no street entrance at all, so nobody outside can reach them directly. When a back-office worker needs to order supplies (an OS update), they send a request out through the mailroom (the NAT Gateway), which can send mail out but never lets strangers walk back in.

S3 basics

aws s3 cp ./file.txt s3://my-bucket/

# Block public access + enable encryption + versioning at creation (best practice)
Public S3 buckets = the classic breach

By default keep Block Public Access ON. A bucket accidentally made public has leaked countless companies' data. Enable default encryption and versioning; use bucket policies + IAM for access, and pre-signed URLs for temporary sharing — never "make it public."

Why three storage types — they're fundamentally different shapes

These aren't three flavors of the same thing; they're three different abstractions for three different needs. EBS is block storage — a raw virtual hard disk attached to one EC2 instance, which formats it with a filesystem. Use it when a program needs a normal disk (a database's data files, an OS boot volume). EFS is a network filesystem (NFS) — one shared folder that many instances can mount and read/write simultaneously. Use it when a fleet needs shared files. S3 is object storage — not a disk and not a filesystem, but a flat key→blob store you access over HTTPS APIs, with effectively unlimited capacity and 11-nines durability. Use it for anything you'd treat as a whole file: uploads, backups, logs, static assets, data lakes, Terraform state.

How S3 works under the hood — and why it's so durable: there are no folders. A bucket is a flat namespace; the "path" logs/2026/app.log is just a key string (the console fakes folders by splitting on /). When you upload an object, S3 automatically replicates it across multiple devices in multiple AZs within the region before acknowledging the write — that redundancy is where "eleven nines" (99.999999999%) durability comes from. Access is governed by a layered model: Block Public Access (account/bucket master switch), bucket policies (resource-based, JSON), IAM policies (identity-based), and legacy ACLs. A request is allowed only if the combined evaluation permits it — and an explicit deny or Block Public Access overrides everything.

Create a bucket the safe way, then verify it's locked down
$ aws s3api create-bucket --bucket acme-app-uploads --region us-east-1
$ aws s3api put-public-access-block --bucket acme-app-uploads \
    --public-access-block-configuration \
    BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true
$ aws s3api put-bucket-encryption --bucket acme-app-uploads \
    --server-side-encryption-configuration \
    '{"Rules":[{"ApplyServerSideEncryptionByDefault":{"SSEAlgorithm":"aws:kms"}}]}'
$ aws s3api put-bucket-versioning --bucket acme-app-uploads \
    --versioning-configuration Status=Enabled

# Share a file temporarily WITHOUT making the bucket public — pre-signed URL
$ aws s3 presign s3://acme-app-uploads/report.pdf --expires-in 3600
https://acme-app-uploads.s3.amazonaws.com/report.pdf?X-Amz-Expires=3600&X-Amz-Signature=...
# ^ this link works for exactly 1 hour, then 403s. No public bucket needed.
Common mistakes: sharing an EBS volume, and silent S3 cost creep

Architecture: a very common misunderstanding is trying to attach one EBS volume to many instances for shared files — EBS is single-attach (io2 multi-attach is a narrow exception); use EFS for shared file access or S3 for objects. Another: putting data that needs shell/filesystem access into S3 (it's an API, not a mount). Billing: S3 charges for storage and per-request and data transfer out (egress) — a chatty app doing millions of tiny GETs, or serving downloads directly from S3 to the internet, can cost far more than expected; put CloudFront in front to cut egress. Un-deleted old object versions and incomplete multipart uploads silently accumulate storage cost — add a lifecycle rule (§23) to expire them. Security: the eternal one — a bucket policy or ACL that makes objects world-readable "just to test."

Mental model: hard drive vs shared drive vs valet parking

EBS is the hard drive inside one computer — only that computer uses it. EFS is a shared network drive the whole office maps as Z:\ — everyone reads and writes the same files. S3 is valet parking for files: you hand over a file and get a ticket (the key); to get it back you show the ticket. You never see the "disk," you can store an unlimited number of items, and it's copied to several garages so it's never lost — but you can't run a program directly off it like a disk.

Managed databases save you nights

RDS handles backups, patching, replication, and multi-AZ failover for you. Enabling Multi-AZ means a standby in another AZ takes over automatically if the primary fails. Running your own database on EC2 means you own all of that — rarely worth it.

Why managed databases exist — and how failover works

Databases are the hardest thing to operate: backups you can actually restore, point-in-time recovery, minor-version patching, replication, and — the scary one — automatic failover when the primary dies at 3am. Getting these right on a self-run database is a specialist job. RDS/Aurora/DynamoDB exist to make AWS do that undifferentiated heavy lifting so you focus on your schema and queries. Under the hood, RDS Multi-AZ keeps a hot standby replica in a second AZ, synchronously replicated. Your app connects to a DNS endpoint, not an IP. If the primary fails, RDS promotes the standby and repoints the endpoint to it — your app reconnects to the same hostname and keeps working, usually within 60-120 seconds, no manual intervention. Aurora goes further: it decouples compute from a shared storage layer that keeps 6 copies across 3 AZs, so failover is faster and you can add up to 15 read replicas cheaply.

The deeper split is SQL vs NoSQL. RDS/Aurora are relational: rigid schemas, JOINs, transactions, and you scale reads with replicas but writes are limited to one primary (vertical scaling). DynamoDB is a different beast — a serverless key-value/document store that scales horizontally to any throughput by partitioning data across many nodes based on your partition key. That's why it delivers single-digit-millisecond latency at massive scale but can't do arbitrary JOINs or ad-hoc queries — you must design around your access patterns up front (see §24).

Common mistakes: the always-on billing trap and DynamoDB hot partitions

Billing: RDS is the classic quiet money-drain — unlike EC2, a stopped RDS instance auto-starts again after 7 days, and you pay for allocated storage, provisioned IOPS, backups beyond the free allotment, and Multi-AZ doubles the instance cost. A forgotten dev database on a large instance class is a common $100s/month surprise. Right-size and stop/delete idle databases. Security: setting --publicly-accessible plus a wide security group exposes your database to the internet — keep databases in private subnets, reachable only from the app tier. Never hardcode the DB password; use --manage-master-user-password (Secrets Manager) or Parameter Store. DynamoDB: a poorly chosen partition key (e.g. keying everything on today's date) funnels all traffic to one partition — a "hot partition" that throttles while the rest of the table sits idle; and on-demand billing mode can be far pricier than provisioned for steady, predictable load.

Mental model: filing cabinet vs valet coat-check

A relational database (RDS) is a well-organized filing cabinet with labeled drawers and cross-references — you can ask complex questions ("all orders by customers in Texas last March") because everything is related and indexed, but one cabinet can only be so big and one clerk files at a time. DynamoDB is a giant coat-check with thousands of clerks: hand over a ticket (the key) and you get your item back in milliseconds no matter how many people are in line — infinitely scalable — but you must know your ticket number; you can't ask the coat-check "find me all the red coats." Managed (RDS) means AWS is the building staff who back up the cabinets and swap in a spare clerk the instant one faints.

Why these services exist — defense in depth

No single control stops every attack, so cloud security is layered: control identity (IAM, §5), protect data at rest (KMS), keep secrets out of code (Secrets Manager), detect threats (GuardDuty), block malicious web traffic (WAF/Shield), and record everything for forensics (CloudTrail). Each service closes a different gap, and they reinforce each other — if one layer fails, the next limits the damage. The reason they're separate managed services is that each is genuinely hard: running a highly available key-management HSM, or building ML threat detection over billions of log events, is not something you want to build yourself.

How the key ones work under the hood: KMS uses envelope encryption — your data is encrypted with a fast per-object data key, and that data key is itself encrypted by a master key (KMS key) that never leaves AWS's hardware security modules. Services like S3, EBS, and RDS call KMS transparently, and every use is logged in CloudTrail (so you can prove who decrypted what). Secrets Manager stores credentials encrypted with KMS and can rotate them automatically (e.g., change a DB password and update it everywhere on a schedule). CloudTrail records every API call in the account — the "who did what, when, from where" ledger that turns an incident from a mystery into a timeline. GuardDuty continuously analyzes CloudTrail, VPC flow logs, and DNS logs with ML to flag things like credential exfiltration or crypto-mining, with zero agents to install.

Mental model: locks, a keymaster, a safe, and CCTV

CloudWatch vs Prometheus/Grafana

CloudWatch is the zero-setup default and integrates with every AWS service. Many teams also run the Prometheus/Grafana stack (see the Observability guide) for richer querying and Kubernetes-native monitoring, feeding CloudWatch metrics in via exporters. Use CloudWatch for AWS-service health and alarms; use Prometheus for deep application/K8s metrics.

Why observability exists — you can't fix what you can't see

A distributed cloud system has no single machine to look at — requests hop across load balancers, containers, queues, and databases spread over AZs. When something is slow or broken, "SSH in and check" doesn't scale. Observability exists to answer, from the outside, three questions: is it broken? (metrics/alarms), what exactly happened? (logs), and where in the chain? (traces). CloudWatch is the built-in answer because every AWS service already emits metrics and logs into it automatically — an ALB reports request counts and 5xx rates, RDS reports CPU and connections, Lambda reports duration and errors — with nothing to install. That zero-friction, everything-integrated property is exactly why it's the default even for teams that also run Prometheus.

How it works under the hood: CloudWatch is a time-series metrics store plus a log store plus an alarm engine. Metrics are organized by namespace (e.g. AWS/EC2), metric name (CPUUtilization), and dimensions (which instance). AWS pushes standard metrics free at 5-minute granularity (1-minute "detailed monitoring" costs extra); your app can push custom metrics via the API. Logs flow into log groups, and Logs Insights lets you run a purpose-built query language over them. An alarm watches one metric against a threshold over N periods and, when breached, fires an action — almost always publishing to an SNS topic that fans out to PagerDuty/email/Slack or triggers an autoscaling action. This is the same alarm→action machinery that drives target-tracking autoscaling in §8.

Common mistakes: the surprise log bill and alerting on the wrong thing

Billing: CloudWatch is a genuine top-5 bill surprise. Log ingestion is charged per GB — a chatty app at DEBUG level, or dumping full request/response bodies, can cost more than the servers producing the logs. Set log retention (logs default to never expire and pile up forever), sample verbose logs, and watch custom metrics and high-cardinality dimensions (each unique combination is a separate paid metric). Alerting: the classic mistake is paging on causes like raw CPU — high CPU may be fine — instead of symptoms users feel (error rate, latency, queue depth). Cause-based alarms create noise and alert fatigue; symptom/SLO-based alarms page only when it actually matters (see the SRE SLO section).

Mental model: a car dashboard vs a mechanic's diagnostic port

Metrics are your dashboard gauges — speed, fuel, temperature — a constant at-a-glance health read. Alarms are the warning lights that flash when a gauge crosses a red line so you don't have to stare at them. Logs are the detailed trip log — every event, timestamped — that you read after a warning light to find out what actually went wrong. Traces are following one specific passenger's whole journey across multiple connecting buses to see exactly where they got stuck. CloudWatch is the dashboard that comes built into the AWS "car" for free; Prometheus/Grafana is an aftermarket dashboard some drivers add for richer gauges.

14. Cost Management (FinOps)

Cloud bills grow silently. A DevOps engineer keeps spend proportional to value.

Cost control checklist
  • Tag everything (owner, env, cost-center) so you can attribute spend.
  • Set budgets & alerts (AWS Budgets) so surprises page you early.
  • Right-size — most instances are over-provisioned; use Compute Optimizer.
  • Buy Savings Plans for steady baseline; Spot for interruptible work.
  • Delete waste — unattached EBS volumes, old snapshots, idle load balancers, forgotten NAT gateways (surprisingly pricey).
  • Use Cost Explorer monthly to find the top movers.
The silent bill-killers

NAT Gateways (hourly + per-GB), inter-AZ/egress data transfer, idle RDS instances, and unattached Elastic IPs quietly add up. Data transfer especially surprises people — architect to keep chatty traffic within one AZ where sensible.

Why FinOps exists — the incentive flip

On-prem, spending is front-loaded and gated: buying a server needs a purchase order and sign-off, so cost is controlled by scarcity. In the cloud, any engineer can spin up expensive resources in seconds with a single API call, and the bill only arrives weeks later. That decouples the person causing cost from the person seeing it, so waste accumulates invisibly. FinOps (cloud financial operations) exists to close that loop — to make cost visible, attributable, and owned by the teams that generate it, in near-real-time, so engineering and finance speak the same language. It's not about spending less for its own sake; it's about keeping spend proportional to the value delivered.

How AWS billing works under the hood, and why the levers exist: almost everything is billed on usage dimensions — instance-seconds, GB-months of storage, GB of data transferred, number of API requests — summed across the account and itemized in the Cost and Usage Report. Three mechanisms give you control. Tags (like env=prod, team=payments) attach to resources and flow into the billing data, so once activated as cost-allocation tags you can slice the bill by team or service in Cost Explorer. Commitment discounts (Savings Plans / Reserved Instances) trade a 1- or 3-year usage promise for up to ~72% off — because AWS can plan capacity when you commit. Spot sells spare capacity at up to ~90% off but AWS can reclaim it with two minutes' notice. Matching each workload to the right pricing model is where most savings live.

15. The Well-Architected Framework

AWS's Well-Architected Framework is six pillars to evaluate any cloud design against. Lead engineers use it as a review checklist.

Why the framework exists — turning "good architecture" into a checklist

"Is this a good design?" is a dangerously subjective question — two smart engineers can disagree, and important concerns (a missing backup, an over-broad IAM role, a cost bomb) slip through because nobody explicitly checked. The Well-Architected Framework exists to make that review systematic and repeatable: it distills the patterns AWS has seen succeed and fail across millions of workloads into six pillars of concrete questions, so a review becomes a documented checklist instead of an opinion. Its most important idea is that the pillars trade off against each other — more reliability (multi-region) costs more money; more security (extra approval gates) can slow operations. The framework doesn't tell you to max out every pillar; it makes you choose deliberately where to trade, and write down why.

How it's used in practice: it's not just a poster — AWS ships the free Well-Architected Tool in the console. You define a "workload," answer the pillar questions, and it produces a list of identified risks (High/Medium) with links to remediation guidance, which you track over time. Big organizations run this per major workload quarterly, and the pillars map directly onto the AWS features taught elsewhere in this guide: Reliability → Multi-AZ (§4) and Auto Scaling (§8); Security → IAM (§5, §18) and the security blocks (§12); Cost → FinOps (§14); Operational Excellence → IaC and observability (§13, §33). §31 walks through turning each pillar into concrete actions.

Common mistakes: treating it as one-time or all-or-nothing

  • Scope with conditions (source IP, MFA, tags) and resource ARNs — avoid "Resource": "*".

Why the "explicit deny wins" model exists

The evaluation logic looks fiddly but it's designed around one goal: a guardrail must be unbreakable from below. If Allows and Denies were simply summed or the "last one wins," a team member could grant themselves permissions their org tried to forbid. By making any explicit Deny override every Allow, and defaulting to deny when no Allow exists, AWS guarantees that a Deny placed high up (an SCP on the account, a permissions boundary on the role) can never be undone by a more permissive policy lower down. That's what lets a security team hand developers freedom to write their own IAM policies while knowing certain actions (leave the region, disable CloudTrail, touch prod) remain impossible. The model trades a little intuitiveness for an ironclad guarantee.

How a request is actually evaluated, step by step: when you call an API, AWS gathers every policy that applies — identity policies on your user/role, any resource policy (e.g. the S3 bucket policy), the permissions boundary, any session policy, and the SCPs on your account/OU. It then runs the funnel: (1) is there an explicit Deny anywhere? → denied, full stop. (2) Do the SCPs allow it? (3) Does the permissions boundary allow it? (4) Does an identity or resource policy explicitly Allow it? Only if it survives all gates is the request permitted; a missing Allow anywhere means implicit deny. This is why "I added the permission but it still fails" is almost always an SCP or boundary Deny higher up, or a resource policy (bucket policy) that wasn't updated.

Common mistakes: wildcards, confused deputy, and the SCP surprise

Security: the cardinal sins are "Action":"*" and "Resource":"*" ("it works now, I'll tighten it later" — you never do), and trusting a role from "AWS":"*" in the trust policy, which lets any AWS account assume it (the "confused deputy" problem — always scope trust to a specific principal + an ExternalId for third parties). Debugging trap: spending an hour adding Allows when an SCP or permissions boundary is silently Denying — check those first with the simulator. Resource policies: forgetting that S3/KMS/SQS have their own policies — cross-account access needs an Allow on both the identity side and the resource side. Least privilege drift: permissions granted "temporarily" that outlive their need; use Access Advisor last-used data to prune.

Mental model: a nightclub with a bouncer and a permanent ban list

Getting into the club is IAM evaluation. First the bouncer checks the permanent ban list (explicit Deny / SCP) — if you're on it, no wristband, no VIP pass, nothing gets you in. If you're not banned, you still need to be on the guest list for the room you want (an explicit Allow); not being on the list means you don't get in (implicit deny). The owner (security team) writes the ban list so that no matter how many guest-list invites a promoter (a developer) hands out, banned actions stay banned. That's why "I'm on the guest list but still can't get in" almost always means you're quietly on the ban list somewhere.

Connecting VPCs, accounts, and on-premises networks securely is core cloud-networking work. Three tools cover most needs.

PrivateLinkExpose one service privatelyConsume a service without exposing whole networks
VPN / Direct ConnectOn-prem ↔ AWSHybrid connectivity (VPN = internet, DX = dedicated line)
VPC endpoints save money & improve security

By default, traffic from a private subnet to S3/DynamoDB goes out via the (costly) NAT gateway. A Gateway VPC Endpoint routes it privately over the AWS backbone — free for S3/DynamoDB, and it never touches the internet. Interface Endpoints (PrivateLink) do the same for most other services. Use them to cut NAT costs and reduce exposure.

Why these tools exist — the N×N mesh problem

The moment you have more than one VPC (and serious orgs have dozens across many accounts), you need them to talk — app VPC to shared-services VPC, every VPC to on-prem. The naive answer, VPC Peering, connects two VPCs directly, but it has two fatal limits at scale: it's non-transitive (if A peers with B and B peers with C, A still can't reach C — traffic won't hop through B), and connecting N VPCs fully needs N×(N−1)/2 peerings — 10 VPCs = 45 links to manage, each with its own route entries. That combinatorial mess is exactly why Transit Gateway exists: a central router where each VPC connects once, and TGW handles transit between all of them and on-prem. PrivateLink solves a different problem — exposing one specific service to consumers without joining whole networks together.

How they differ under the hood: Peering is a direct, private route between two VPCs' route tables — no bandwidth bottleneck, no extra hop, but no transit. Transit Gateway is a managed regional router; each VPC attaches to it and TGW route tables decide who can reach whom (you can even segment — e.g. dev VPCs can't route to prod). It scales to thousands of attachments and connects VPN/Direct Connect for hybrid. PrivateLink works at a finer grain: a provider puts a service behind a Network Load Balancer and publishes an endpoint service; consumers create an interface endpoint (an ENI with a private IP in their own subnet) that tunnels to just that service. The consumer never gets network reachability to the provider's VPC — only to the one exposed service, over private IPs. That's also how AWS itself exposes services like Secrets Manager privately.

Common mistakes: overlapping CIDRs, and TGW/endpoint cost surprises

Networking: the #1 killer is overlapping CIDR blocks — if two VPCs both use 10.0.0.0/16 you cannot peer or attach them to TGW (routing is ambiguous); plan a non-overlapping IP scheme org-wide before you build. Also expecting peering to be transitive (it isn't) and forgetting that both sides need route-table entries and security-group rules. Billing: Transit Gateway charges per attachment per hour plus per-GB of data processed — cheap for a few VPCs, but it adds up, and it can be more expensive than peering for a small, static topology. Interface endpoints (PrivateLink) also bill per-hour per-AZ plus per-GB, so creating an endpoint for every service in every AZ silently multiplies cost — but Gateway endpoints (S3, DynamoDB only) are free and almost always worth it purely to cut NAT charges.

Mental model: direct phone lines vs a switchboard vs a service window

Peering is running a private phone line between two offices — great for two, but wiring every office to every other office becomes a spaghetti nightmare, and office A can't reach C just because both know B. Transit Gateway is a central switchboard: every office plugs in one line to the operator, who connects any office to any other (and to headquarters/on-prem). PrivateLink is a single service window in a wall — the payroll department exposes just "submit timesheet here," and other teams use that window without getting the keys to walk around payroll's whole office.

18. Route 53 & DNS

DNS is how names become addresses — and Route 53 adds powerful routing policies that make it a traffic-management and failover tool, not just a name server.

DNS = the internet's phone book, with a brain

DNS turns app.example.com into an IP address, like looking up a name to get a phone number. Route 53 adds intelligence: it can hand different callers different numbers based on where they are (geo), which line is fastest (latency), or which is still working (failover health checks). That makes DNS a first-class tool for global routing and disaster recovery.

Why Route 53 is more than a name server

Plain DNS answers one question — "what IP is example.com?" — and that's essential because humans and code use names, not IPs, and because IPs change (autoscaling replaces instances, failover swaps regions) but the name stays stable. Route 53 exists because in the cloud the answer to that question should be dynamic: the best IP depends on who's asking, from where, and what's currently healthy. By making DNS routing-aware, AWS turns the name-resolution step — which every request already performs first — into a global traffic-control point. That's powerful because it works for any protocol and requires no change to clients: they just do a normal DNS lookup and get steered to the right place. The "53" is the DNS port.

How the routing policies work under the hood: Route 53 hosts your hosted zone (the authoritative records for your domain) on a globally distributed fleet of name servers. When a resolver asks for a record, Route 53 doesn't just return a static value — it evaluates the record's policy at query time. Latency-based routing uses AWS's own measured latency maps to return the region with the lowest latency to that resolver. Failover routing pairs a primary and secondary record with a health check — Route 53 continuously probes an endpoint (e.g. https://app/health) from multiple locations, and if it goes unhealthy, stops returning the primary and serves the secondary. Weighted splits answers by ratio (90/10) for canary releases. The catch that bites everyone: TTL (time-to-live) tells resolvers how long to cache the answer — so failover isn't instant, it's bounded by the TTL you set.

Common mistakes: long TTLs, forgotten domain renewal, and the "propagation" myth

Availability: setting a long TTL (e.g. 3600s) on records you might need to fail over means clients keep hitting the dead endpoint for up to an hour after failover — use short TTLs (30–60s) on anything DR-critical. Health checks that probe / instead of a real dependency-aware /health won't detect a broken app (same trap as ALB checks in §8). Billing/ops: forgetting to auto-renew a registered domain has taken companies fully offline; each hosted zone and health check has a small monthly charge, and huge numbers of them add up. Misconception: "DNS propagation" delays are really just caching — resolvers hold the old answer until its TTL expires; there's no mysterious global sync, so pre-lowering TTL before a planned change is the fix.

Mental model: a smart receptionist for a chain of stores

Regular DNS is a phone book: one name, one number. Route 53 is a smart receptionist who, when you ask for "the store," checks where you're calling from and sends you to the nearest branch (latency/geo), and — crucially — if that branch's phone is dead (failed health check), quietly gives you the next branch's number instead. The one quirk: the receptionist tells you "this number's good for the next 60 seconds" (TTL), so if a branch closes right after you called, you might dial the dead number until your 60 seconds are up. Set a short expiry on numbers that might change.

19. CloudFront & Edge

A CDN caches your content at edge locations worldwide so users get fast responses from nearby, and your origin is shielded from load and attacks.

Why a CDN exists — physics and load

Two hard problems drive CDNs. First, the speed of light is fixed: a user in Tokyo hitting a server in Virginia pays ~150ms round-trip per request no matter how fast your server is — and a page makes dozens of requests. You can't make light faster, but you can move a copy of the content closer to the user. Second, your origin is a bottleneck and a target: every request that reaches it costs compute, bandwidth, and money, and a traffic surge (or a DDoS) can overwhelm it. A CDN like CloudFront solves both by caching content at ~600 edge locations worldwide: users get served from a nearby edge (fast), and the origin only sees the small fraction of requests that miss the cache (protected and cheap). It also terminates TLS at the edge and, with WAF/Shield, absorbs attacks far from your origin.

How caching decisions work under the hood: when a request hits an edge, CloudFront computes a cache key (normally the URL path, plus any headers/query strings/cookies you tell it to include) and checks if a fresh copy exists at that edge. A hit is served immediately. A miss is forwarded to the origin (S3, an ALB, or any HTTP server); CloudFront stores the response according to its TTL — driven by the origin's Cache-Control/Expires headers or your CloudFront settings — and serves it to the user. Subsequent nearby users get hits until the TTL expires. To push out an update immediately you either version the filename (app.a1b2c3.js — best) or issue an invalidation. For logic at the edge, CloudFront Functions (lightweight, viewer request/response) and Lambda@Edge (heavier, full runtime) let you rewrite URLs, add security headers, or do auth without a round-trip to the origin.

Common mistakes: caching the wrong things and the invalidation bill

Correctness: the two opposite traps are (1) caching dynamic/personalized content — if your cache key ignores the auth cookie, user A can be served user B's cached account page (a real data-leak); mark private responses no-store or include the right headers in the cache key; and (2) caching so aggressively you can't push updates — deploys "don't take effect." The clean fix is filename versioning, not constant invalidations. Billing: CloudFront invalidations are free only for the first 1,000 paths/month — scripts that invalidate /* on every deploy rack up charges; and while edge egress is cheaper than raw S3/EC2 egress, a low cache-hit ratio (badly tuned cache key) means most requests still hit the origin, so you pay the origin egress and get none of the speed benefit. Security: forgetting to lock the origin (e.g. Origin Access Control on S3) lets users bypass CloudFront/WAF and hit the origin directly.

Mental model: local corner shops stocking a warehouse's goods

Your origin is a single central warehouse; the edge locations are corner shops in every neighborhood. Instead of everyone driving across the country to the warehouse (slow, and the warehouse gets mobbed), the corner shop keeps copies of the popular items — you pop next door (fast). Only when the shop is out of something does it order from the warehouse (a cache miss). The catch: if you change a product, the shops keep selling the old stock until their "sell-by" date (TTL) — so to force an update you either give the new product a new label (versioned filename) or tell every shop to bin the old one (an invalidation).

Why so many families and volume types exist

How instance naming and placement work under the hood: an instance name like m6g.large decodes as family (m = general purpose) + generation (6) + attributes (g = Graviton/ARM) + size (large). On storage, the crucial distinction is that EBS is network-attached — it survives instance stop/termination and can be detached and reattached — while instance store is a physical disk on the host: blazing fast but ephemeral, wiped the moment the instance stops or moves.

Why storage classes exist — data gets cold

Multi-AZ vs read replicas — don't confuse them

Multi-AZ keeps a synchronous standby in another AZ purely for availability: your app talks to one DNS endpoint, and if the primary dies, AWS promotes the standby and re-points that endpoint automatically — no data loss, no code change. Read replicas are asynchronous copies for scaling reads: you send SELECTs to them to offload the primary, accepting slight replication lag. They solve different problems and are often used together.

22. RDS, Aurora & DynamoDB Deep

Choosing and running the right database is one of the highest-impact architecture decisions. Here's how the managed options differ at depth.

DynamoDB is not "just NoSQL RDS"

DynamoDB requires single-table design thinking — you model around your access patterns, not normalized entities, choosing partition/sort keys carefully. A poor key choice creates "hot partitions" that throttle. It's brilliant at scale but demands a genuinely different design mindset than SQL. Don't pick it just to "avoid SQL."

Why the deep differences matter — the write bottleneck

The single most important architectural fact: relational databases scale reads easily but writes hardly at all. RDS/Aurora serve all writes through one primary node — you scale reads by adding replicas, but to handle more writes you must buy a bigger primary (vertical scaling), and there's a ceiling. That's fine for the vast majority of apps. DynamoDB exists for the workloads that blow past that ceiling: by hashing every item's partition key and spreading data across many storage nodes, it scales writes horizontally and near-infinitely, holding single-digit-millisecond latency at any scale. The price is that you lose ad-hoc queries and JOINs — you can only efficiently fetch data by keys you designed for in advance. Aurora is the clever middle ground: it keeps the relational model and SQL, but re-architects storage as a shared, auto-replicating layer across 3 AZs, so failover is seconds (not minutes) and you can add up to 15 read replicas that share that storage.

How each handles failure and scale under the hood: RDS Multi-AZ keeps a synchronous standby; failover repoints the DNS endpoint (60–120s). Aurora stores 6 copies of your data across 3 AZs and only needs 4 to write / 3 to read, so it tolerates losing a whole AZ transparently; replicas read from the same storage, so they're near-zero lag. DynamoDB automatically replicates across 3 AZs, and you choose a capacity mode: provisioned (you set read/write capacity units, cheapest for steady load) or on-demand (pay per request, auto-scales, best for spiky/unknown load). You extend query flexibility with secondary indexes (GSIs) — but each is essentially another copy of the table with its own key and cost. DynamoDB Streams emit a change log you can trigger Lambdas from, which is the backbone of event-driven serverless (§25).

Common mistakes: scan-everything, hot partitions, and the RDS scaling wall

DynamoDB: the killer anti-patterns are (1) using Scan instead of Query — Scan reads the whole table (slow and expensive at scale); design keys so you always Query. (2) A low-cardinality partition key (status = "active", or today's date) funnels traffic to one partition — a hot partition that throttles while capacity sits idle elsewhere. (3) Treating it like SQL and trying to normalize into many tables with JOINs — you can't JOIN; denormalize into access-pattern-shaped items. Billing: on-demand mode is convenient but can cost several times more than provisioned+autoscaling for steady traffic; and every GSI duplicates write cost. RDS/Aurora: the surprise is hitting the write ceiling — read replicas don't help write-heavy loads; and Multi-AZ doubles instance cost. Forgetting deletion-protection and taking no tested restore is how companies lose data permanently.

Mental model: one expert accountant vs a warehouse of order-pickers

RDS/Aurora is one brilliant accountant with a cross-referenced ledger — ask any complex question ("total revenue from repeat customers in Q3") and they'll work it out, because everything's related. But there's only one of them writing in the ledger, so if a thousand transactions pour in at once, they become the bottleneck; you can hire assistants to read copies (replicas), but only one person writes. DynamoDB is a giant warehouse of thousands of order-pickers, each responsible for a numbered aisle (partition key). Give any picker an item number and they fetch it in milliseconds no matter how busy the warehouse — infinite throughput — but you can't ask them "find all blue items across every aisle"; you must know the aisle. Design your aisles (keys) up front, or one poor picker gets mobbed while the rest stand idle (hot partition).

The hot-partition trap

DynamoDB scales by spreading items across partitions using the partition key's hash. If most traffic targets a few key values — say status = "active" or a single tenant — that partition gets hammered while others idle, and you get throttled even though total table capacity looks fine. Design high-cardinality keys (user IDs, order IDs) and, when needed, add a suffix to spread writes. This is the #1 DynamoDB performance mistake.

23. Serverless Architecture Deep

Beyond "Lambda runs functions" — real serverless systems compose functions, queues, APIs, and state machines, and require you to design around cold starts, concurrency, and event sources.

Serverless gotchas to design for
  • Cold starts — first invocation is slower; use provisioned concurrency for latency-critical paths.
  • Concurrency limits — Lambda scales fast; protect downstream databases with reserved concurrency or SQS buffering.
  • Statelessness — store state in DynamoDB/S3, not in the function.
  • Orchestration — use Step Functions for multi-step workflows instead of chaining Lambdas manually.
Why compose services instead of one big app

The serverless philosophy is to assemble small, single-purpose managed pieces (functions, queues, buses, state machines) that each scale and fail independently, rather than run one monolith on a server you babysit. Why? Because in event-driven systems the work is bursty and uneven — a flood of uploads, then quiet — and different steps need different scaling. If the "validate" step and the "process video" step were in one process, the slow step would block the fast one and you'd size the whole thing for the worst case. By splitting them across a queue, each side scales to its own load, a failure in one doesn't take down the other, and you pay only for the work each actually does. The trade is distributed-systems complexity: you now reason about retries, ordering, idempotency, and partial failure — which is exactly what the patterns below manage.

How the hard parts work under the hood: cold starts happen because a request with no warm environment must spin up a fresh Firecracker micro-VM and run your init code — mitigate latency-critical paths with provisioned concurrency (pre-warmed environments). Concurrency is Lambda's superpower and its footgun: it launches one environment per simultaneous request, so a spike to 5,000 concurrent requests means 5,000 parallel executions — which will happily open 5,000 connections and flatten a database that can handle 200. You defend downstream systems by putting an SQS queue in front (it buffers the spike; workers drain it at a controlled rate) and by setting reserved concurrency caps. Because any invocation can fail or be retried, functions must be idempotent (processing the same event twice is safe). For multi-step flows, Step Functions is a managed state machine that handles the sequencing, retries, and error branches so you don't hand-code a fragile chain of Lambdas calling Lambdas.

Protect a database from a Lambda spike, and orchestrate with Step Functions
# Cap a function so a traffic spike can't open unlimited DB connections
$ aws lambda put-function-concurrency --function-name db-writer \
    --reserved-concurrent-executions 50
{ "ReservedConcurrentExecutions": 50 }   # never more than 50 in parallel

# Pre-warm a latency-critical function to avoid cold starts
$ aws lambda put-provisioned-concurrency-config --function-name checkout-api \
    --qualifier LIVE --provisioned-concurrent-executions 10

# Run a multi-step workflow as a managed state machine (retries/branches built in)
$ aws stepfunctions start-execution \
    --state-machine-arn arn:aws:states:us-east-1:123456789012:stateMachine:order-flow \
    --input '{"orderId":"o-42"}' --query 'executionArn' --output text
arn:aws:states:us-east-1:123456789012:execution:order-flow:o-42-run1
Common mistakes: recursion bombs, connection exhaustion, and the always-on cost flip

Billing/blast radius: the scariest serverless bug is a recursive trigger — a Lambda writes to the S3 bucket (or SQS) that triggers itself — which fans out to thousands of concurrent executions in seconds, racking up cost and downstream damage; always separate input and output buckets and set reserved concurrency. Downstream overload: pointing a highly concurrent Lambda straight at RDS exhausts its connection pool — buffer with SQS or use RDS Proxy. Correctness: assuming an event fires exactly once — most sources are at-least-once, so non-idempotent handlers double-charge cards or double-insert rows. Cost: serverless is cheapest when spiky/idle; for a steadily busy API, per-request Lambda pricing can exceed a small always-on Fargate task — measure before assuming it's cheaper. Ops: no DLQ on your queues/functions means a single poison message silently blocks or drops work.

Mental model: a restaurant with a ticket rail

Orders (events) come in at the counter (API Gateway). Instead of one cook doing everything for each order start-to-finish, the order is written on a ticket and clipped to a rail (the SQS queue). Cooks (worker Lambdas) grab tickets as they're free — during a rush you add cooks, when it's quiet they go home, and if one cook drops a ticket it goes back on the rail for someone else (retry). The rail stops a sudden rush of 100 orders from overwhelming the kitchen all at once — they queue up and get worked through at a sustainable pace. A ticket nobody can ever complete (a poison message) gets moved to a "problem" spike (dead-letter queue) so it doesn't jam the rail forever.

Mental model: a vending machine vs a running kitchen

A traditional server is a kitchen you keep staffed 24/7 whether anyone orders or not. Serverless is a vending machine: it sits idle costing nothing, springs to life the instant someone presses a button (a request), serves it, and goes back to sleep. You pay only for the presses, and if a thousand people press at once, a thousand machines appear instantly.

24. SQS, SNS & EventBridge

AWS's messaging trio decouples services. Knowing which to use is a common design decision (and complements the Kafka guide).

The classic fan-out pattern

SNS → multiple SQS queues is the canonical AWS decoupling pattern: one event is published once to SNS, which fans it out to several SQS queues, each feeding an independent consumer. Add a dead-letter queue to every SQS queue to capture messages that repeatedly fail, so a poison message never blocks the queue.

Why decoupling exists — don't let services call each other directly

If service A calls service B directly (synchronously), they're welded together: if B is slow, A is slow; if B is down, A fails; if B can't keep up with a spike, requests are lost. Messaging exists to break that rigid coupling by putting an intermediary between them, which buys three things: buffering (a queue absorbs a spike so a slow consumer catches up instead of dropping work), resilience (B can be down for maintenance and messages simply wait), and fan-out (one event can notify many independent consumers without the producer knowing they exist). The three services exist because they solve different coupling problems: SQS decouples load (point-to-point buffering), SNS decouples who listens (one-to-many push), and EventBridge decouples routing logic (content-based rules and third-party integration).

How they differ under the hood: SQS is a pull-based queue — consumers poll for messages, each message is delivered to one consumer, hidden by a visibility timeout while processed, and deleted on success or redriven to a dead-letter queue after N failures. Standard queues are at-least-once/best-effort-order; FIFO queues guarantee exactly-once and ordering at lower throughput. SNS is push-based pub/sub — publish once to a topic, and every subscriber (SQS queues, Lambdas, HTTP endpoints, email) gets its own copy; senders and receivers never know each other. EventBridge is a smart event bus — events carry a JSON body, and rules match on their content (e.g. "orders over $1000") to route them to targets, and it natively ingests events from AWS services and many SaaS products. Kinesis is different again: an ordered, replayable stream (like Kafka) where multiple consumers each read the whole ordered log at their own pace.

Wire SNS fan-out to an SQS queue with a dead-letter queue

$ aws sqs create-queue --queue-name email-worker \
    --query QueueUrl --output text

$ aws sns subscribe --topic-arn arn:aws:sns:...:order-events \
    --protocol sqs --notification-endpoint arn:aws:sqs:...:email-worker

# One publish fans out to every subscribed queue/Lambda/email:
$ aws sns publish --topic-arn arn:aws:sns:...:order-events \
    --message '{"orderId":"o-42","total":1299}' --query MessageId --output text
9a1c...  # delivered to email-worker AND any other subscriber, independently

# EventBridge rule: route only big orders to a fraud-check target
$ aws events put-rule --name big-orders \
    --event-pattern '{"detail":{"total":[{"numeric":[">",1000]}]}}'
Common mistakes: no DLQ, visibility-timeout bugs, and picking the wrong tool

Reliability: the top mistake is no dead-letter queue — one un-processable "poison" message gets retried forever, blocking (FIFO) or endlessly reprocessing (standard) and never clearing; always attach a DLQ with a sane maxReceiveCount. Second: a visibility timeout shorter than processing time — the message reappears and a second consumer processes it in parallel (duplicate work / double charges), so consumers must be idempotent and the timeout must exceed worst-case processing. Design: using SNS when you needed durable buffering (SNS won't hold messages for an offline consumer — subscribe an SQS queue to it), or reaching for Kinesis/Kafka when a simple SQS queue would do (streaming adds real operational complexity). Billing: SQS bills per request, so tight polling loops with short/no long-polling waste money — enable long polling; and fan-out to many queues multiplies request counts.

Mental model: a to-do inbox, a group text, and a smart mailroom

SQS is a shared to-do inbox: tasks pile up and whoever's free grabs the next one — exactly one person does each task, and tasks wait patiently if everyone's busy. SNS is a group text blast: you send one message and everyone subscribed gets their own copy instantly — great for "this happened, whoever cares, react." EventBridge is a smart mailroom clerk who reads each incoming letter and, based on its contents, forwards it to the right department ("complaints go to support, big orders go to the VIP desk"). The classic combo — one group text (SNS) that drops a copy into several to-do inboxes (SQS) — lets one event kick off several independent teams without the sender knowing or caring who they are.

Why SNS + SQS together

SNS is push pub/sub: one publish fans out to N subscribers instantly, but if a subscriber is down the message is gone. SQS is a durable pull queue: messages wait until a worker pulls them, with retries and a dead-letter queue for failures. The classic fan-out pattern subscribes an SQS queue to each SNS topic — so every consumer gets its own durable buffer. One order event can trigger billing, shipping, and analytics independently, and a slow analytics worker never blocks shipping.

25. Multi-Account & Organizations

Serious AWS usage means many accounts, not one. Separation limits blast radius, simplifies billing, and enforces guardrails centrally.

Why separate accounts beat one big account
  • Blast radius — a mistake or breach in dev can't touch prod.
  • Billing clarity — per-account/team cost attribution.
  • Guardrails — SCPs enforce policy no IAM user can override.
  • Quota isolation — one team can't exhaust another's limits.

Use IAM Identity Center (SSO) for humans to assume roles across accounts, and Control Tower or Terraform to provision new accounts consistently.

Why the account is the strongest boundary in AWS

Inside one account, IAM can separate teams — but it's soft: a mistake in a policy, a wildcard, or a compromised admin can reach everything, and one team's runaway workload can exhaust a service quota (which are per-account) that another team needs. The AWS account is a far harder wall: resources in account A are simply invisible to account B unless you deliberately grant cross-account access, quotas are per-account, and billing is per-account. So the multi-account model uses accounts as the unit of isolation — prod in its own account, dev in another, security tooling in a locked-down third. Organizations exists to make managing many accounts sane: it groups them into OUs, consolidates billing, and — most importantly — lets you apply Service Control Policies (SCPs) that set an unbreakable permission ceiling across whole OUs, something no in-account IAM policy can achieve.

How SCPs and cross-account access work under the hood: an SCP is not itself a grant — it's a filter on the maximum permissions any principal in an account may have. Even a full account administrator cannot exceed the SCP; if the SCP denies ec2:* outside approved regions, no one in that account can launch there, period (this is the "explicit deny wins" rule from §18 applied org-wide). For humans, IAM Identity Center (SSO) replaces per-account users: people authenticate once against your identity provider and are handed temporary credentials for a role in whichever account they're permitted — zero long-lived keys sprawled across accounts. New accounts are vended consistently by Control Tower (a managed, best-practice landing zone) or by Terraform/the Landing Zone Accelerator, so every account is born with logging, guardrails, and baseline security already wired in (§30).

Mental model: separate apartments in one building, not one giant loft

Running everything in one AWS account is a giant open-plan loft — one spilled coffee (a bad script) can ruin everyone's work, and there's no real privacy between teams. Multi-account is giving each team its own locked apartment in the same building: a fire in dev's kitchen can't burn prod's apartment, each has its own utility meter (billing), and one tenant hogging the water (quotas) doesn't drain the others. Organizations is the building management; SCPs are building rules even the tenants' own house rules can't override ("no open flames anywhere"); and SSO is the front-desk that issues you a temporary keycard to exactly the apartments you're allowed into.

One account per environment, not one big account

Separate accounts give hard blast-radius isolation: a mistake or breach in Dev can't touch Prod, and billing is naturally split per account. Use AWS Organizations to group accounts into OUs, Service Control Policies (SCPs) as organization-wide guardrails (e.g., "deny leaving approved regions"), and a dedicated Log Archive and Audit account so security telemetry lives outside the accounts it monitors. Control Tower automates this baseline.

26. Disaster Recovery Strategies

DR is about surviving a region-level failure. There's a spectrum from cheap-and-slow to expensive-and-instant — pick based on your RTO/RPO.

RTO vs RPO in one line

RTO = how long you can be down (recovery time). RPO = how much data you can afford to lose (recovery point). "RTO 1 hour, RPO 5 min" means: back up at least every 5 minutes, and be able to restore within an hour. These two numbers drive which DR strategy (and how much money) you need.

Why a spectrum exists — DR is a cost/speed dial, not a checkbox

Recovering instantly from a regional disaster requires running a full duplicate of your system in a second region at all times — which roughly doubles your infrastructure bill. Recovering cheaply means keeping only backups and rebuilding on demand — which can take hours. Neither is "right"; the right answer depends entirely on what an hour of downtime actually costs your business. A bank's trading system loses millions per minute (spend on active-active); an internal reporting tool can be down for a morning (nightly backups are fine). The four strategies exist to give you a dial between those extremes, and the two numbers that set the dial are RTO (tolerable downtime) and RPO (tolerable data loss). You pick the cheapest strategy that still meets both.

How each strategy works under the hood: Backup & Restore keeps snapshots/AMIs (ideally replicated cross-region) and rebuilds everything from scratch in a disaster — cheapest, RTO in hours. Pilot Light keeps the critical core alive and current in the DR region — typically the database, kept warm by cross-region read replication — while everything else (app servers) sits as ready-to-launch templates you scale up on failover. Warm Standby runs a scaled-down but fully working copy in the DR region continuously; on disaster you just scale it up and flip traffic — RTO in minutes. Multi-Site Active/Active runs full capacity in both regions serving live traffic simultaneously, usually steered by Route 53 latency or weighted routing — a regional loss is nearly invisible (RTO ≈ 0) but you pay for two of everything and must solve the hard problem of cross-region data consistency. In all cases, infrastructure-as-code (§35) is what makes the DR region reproducible — you deploy the same Terraform to both regions.

Common mistakes: untested DR, forgotten dependencies, and paying for gold-plated recovery you don't need

The cardinal sin: a DR plan that has never been tested is not a DR plan — restores fail on missing IAM roles, wrong region AMIs, un-replicated secrets, or a runbook nobody has rehearsed. Run regular game days that actually fail over. Hidden dependencies: teams replicate the database but forget secrets, DNS records, certificates, container images (ECR), or the S3 buckets the app reads — the DR region comes up but the app can't function. Global-service assumption: forgetting that some things (a Route 53 config, an ACM cert in the wrong region) are region-pinned. Cost: the opposite mistake — building active-active for a system whose downtime costs little — is a Well-Architected Cost failure (§15); match spend to the business impact of downtime. RPO reality: asynchronous cross-region replication has lag, so your true RPO is "however far behind the replica is," not zero — measure it.

Mental model: how you'd survive your house burning down

Backup & Restore = you keep photos of your belongings in the cloud; after a fire you re-buy everything — cheap to maintain, but you're camping for weeks (long RTO). Pilot Light = you keep a small storage unit with the essentials (bed, clothes) ready to move into fast. Warm Standby = you rent a small furnished second apartment, already livable, that you can upgrade quickly. Active/Active = you actually live across two fully-equipped homes at once, so if one burns you barely notice — but you're paying two full rents. RTO/RPO are just "how long can I be homeless?" and "how much of my stuff can I lose?" — and the honest, dangerous mistake everyone makes is never actually testing that the spare key to the backup place still works.

Mental model: spare tyre vs second car

Backup & restore is a repair kit in the boot — cheapest, but you're stuck on the roadside for hours. Pilot light is a spare tyre — a bit of prep gets you moving again fairly soon. Warm standby is a small backup car in the garage, engine warm — swap over in minutes. Multi-site active is driving two cars in convoy — if one breaks down you don't even slow, but you're paying for two cars all the time. RTO is how long you're stranded; RPO is how far back your last map update was.

Landing-zone checklist (the day-one baseline)

Why a landing zone exists — you can't retrofit a foundation

The tempting path is to open one AWS account, start building, and "sort out security later." The problem is that account structure, logging, identity, and guardrails are foundational — everything else depends on them, so retrofitting them later means migrating live workloads across accounts, re-issuing credentials, and re-plumbing networks under production load. It's the cloud equivalent of trying to add a basement to a house that's already built. A landing zone exists to do that foundational work once, up front, as code, so every workload you create afterwards inherits multi-account isolation, centralized audit logging, SSO-based access, threat detection, and unbreakable guardrails for free — without anyone remembering to configure them. It converts "did someone remember to turn on CloudTrail in this account?" from a hope into a guarantee.

How it works under the hood: a landing zone is the concrete implementation of the multi-account model (§27) plus the security baseline (§12). The management account holds Organizations and billing only; a dedicated log-archive account receives an organization CloudTrail + Config aggregation from every other account into an immutable, access-restricted bucket (so even an attacker who compromises a workload account can't erase the evidence — the logs live somewhere they can't reach). SCPs on each OU enforce guardrails top-down. IAM Identity Center federates human access. AWS Control Tower is AWS's opinionated automation that stands all of this up and continuously detects drift (an account falling out of compliance), while the Landing Zone Accelerator or Terraform give the same result as version-controlled code you own. New accounts are vended through an Account Factory so they're born compliant.

Common mistakes: workloads in the management account, and click-ops drift

Security: the most dangerous mistake is running workloads (or storing data) in the management account — it's exempt from SCPs and holds the keys to the whole org, so a breach there is catastrophic; keep it empty except Organizations/billing. Second: a log-archive bucket that isn't actually locked down (no bucket policy denying deletes, no MFA-delete) — if an attacker can wipe the audit logs, you're blind. Third: ClickOps drift — setting the baseline up by hand means new accounts get created without it and existing ones silently drift out of compliance; use Control Tower's drift detection or Config conformance packs, and vend accounts as code. Guardrail lockout: an over-broad SCP applied org-wide can break every account at once — roll SCPs out to a sandbox OU first (§27). Cost: Control Tower, Config recorders, and org CloudTrail have ongoing per-account costs — real and worth it, but budget for them rather than being surprised.

30. ECS vs EKS vs Fargate — Choosing & Using

Running containers on AWS has three main paths. Picking correctly saves months of complexity; here's the decision and the hands-on basics of each.

Run a container service on ECS + Fargate (no servers to manage)

docker tag myapp:1.0 <acct>.dkr.ecr.us-east-1.amazonaws.com/myapp:1.0
docker push <acct>.dkr.ecr.us-east-1.amazonaws.com/myapp:1.0

# 2. Register a task definition (Fargate launch type) and run it as a service
aws ecs create-cluster --cluster-name prod
aws ecs register-task-definition --cli-input-json file://taskdef.json
aws ecs create-service --cluster prod --service-name myapp \
  --task-definition myapp --desired-count 3 --launch-type FARGATE \
  --network-configuration "awsvpcConfiguration={subnets=[subnet-abc],securityGroups=[sg-abc]}"
# ECS keeps 3 tasks running across AZs, replaces unhealthy ones, integrates with ALB
The honest decision guide

Choose ECS + Fargate if you want the simplest path and you're all-in on AWS — most teams are happiest here. Choose EKS if you need Kubernetes' portability/ecosystem, already have K8s skills, or run multi-cloud — but budget for the extra operational complexity (see the whole Kubernetes guide). Use Fargate under either when you'd rather not manage EC2 nodes; use EC2 nodes when you need GPUs, special instance types, or the lowest cost at steady scale.

Why three options — orchestration vs compute are separate choices

The confusion clears the moment you realize you're making two independent decisions, not one. Decision 1 — which orchestrator schedules your containers, restarts them when they die, and wires them to load balancers? That's ECS (AWS's own, simple, deeply integrated) vs EKS (managed Kubernetes — portable and huge ecosystem, but more to learn and operate). Decision 2 — who runs the servers the containers land on? That's EC2 nodes (you manage a fleet — cheapest at steady scale, needed for GPUs/special hardware) vs Fargate (serverless — you declare CPU/memory per task and AWS finds the capacity; no nodes to patch or scale). They combine freely: ECS-on-Fargate, ECS-on-EC2, EKS-on-Fargate, EKS-on-EC2. The options exist because "run containers" spans a team writing its first Dockerfile and a platform team running a multi-cloud Kubernetes estate — no single product fits both.

How the pieces work under the hood: on ECS, a task definition (image, CPU/memory, ports, env, IAM task role) is the unit; a service keeps N tasks running across AZs, replaces unhealthy ones, and registers them with an ALB target group — the same self-healing loop as an ASG (§8) but at the container level. On EKS, AWS runs the Kubernetes control plane (the API server and etcd) for you at a flat hourly fee, and you supply worker capacity as either managed EC2 node groups or Fargate; you then use standard Kubernetes objects (Deployments, Services, Ingress). With Fargate, each task/pod runs in its own micro-VM with no shared host — great isolation and zero node management, but you can't SSH to a node, run privileged DaemonSets, or use GPUs, and per-vCPU it costs more than well-utilized EC2. Images for all paths live in ECR, and tasks assume IAM task roles for least-privilege AWS access (the container-level version of instance profiles from §6).

Common mistakes: EKS when you didn't need it, and Fargate cost/limits

Complexity: the most expensive mistake is choosing EKS for its résumé value when a five-person team just needs to run a few services — you inherit the entire Kubernetes operational surface (upgrades, add-ons, RBAC, networking CNI, an ecosystem that changes constantly) for benefits you won't use; ECS+Fargate would have shipped in a fraction of the time. Billing: EKS charges a per-cluster hourly fee for the control plane on top of compute — running many small clusters multiplies that; and Fargate's convenience premium means at high, steady utilization a right-sized EC2 node fleet is meaningfully cheaper (measure the crossover). Fargate limits bite late: no GPUs, no privileged containers, no host-level DaemonSets (so some monitoring/security agents need a sidecar pattern), and larger task sizes cost more per hour than an equivalently packed EC2 host. Security: forgetting task/pod IAM roles and instead baking AWS keys into the image (same anti-pattern as §6).

Mental model: catering — chosen menu vs full kitchen, staffed vs self-run

Running containers is catering an event. Orchestrator is your menu system: ECS is a caterer's fixed, easy package — pick dishes, they handle the rest; EKS is running a full professional kitchen — infinitely flexible and industry-standard, but you must know how to run a kitchen. Most first-timers are happiest with the easy package and hired staff (ECS + Fargate); a big catering company with unusual needs runs its own kitchen and crew (EKS on EC2).

Why the three pillars — and why tracing is the hard one

§13 introduced CloudWatch; this section is the hands-on toolkit for the three pillars of observability — metrics, logs, and traces — because each answers a question the others can't. Metrics (cheap, aggregated numbers over time) answer "is something wrong right now, and is it trending?" — but they can't tell you why. Logs (detailed per-event records) answer "what exactly happened in this component?" — but in a system of dozens of services, they don't show how a single user request flowed across them. That's the gap distributed tracing (X-Ray/OpenTelemetry) fills: it stitches together every hop of one request — API Gateway → Lambda → DynamoDB → downstream API — into a single timeline, so you can see which service ate the 800ms. Tracing exists because in distributed systems the slow part is rarely where you'd guess, and no amount of per-service logs reconstructs the cross-service journey.

How it works under the hood: metrics and logs flow into CloudWatch automatically for AWS services, and your app pushes custom ones via the API/agent. Tracing works by context propagation: the first service generates a trace ID and passes it in headers to every downstream call; each service records a span (its slice of work, with timing) tagged with that trace ID; the backend (X-Ray or Tempo) reassembles all spans sharing an ID into one waterfall. The modern, vendor-neutral way to emit all three signals is OpenTelemetry (OTel) — you instrument once with OTel SDKs/agent and export to X-Ray, CloudWatch, or a Prometheus/Grafana/Tempo stack without changing app code. On EKS, teams commonly run Amazon Managed Prometheus (AMP) scraping pod metrics + Managed Grafana for dashboards, while CloudWatch covers the AWS-service layer beneath.

Common mistakes: the log bill, alerting on causes, and no correlation IDs

Billing (recurring surprise): CloudWatch log ingestion and storage and high-cardinality custom metrics are a top-5 bill line — DEBUG-level logging in prod, dumping full payloads, or a unique metric dimension per user ID can cost more than the compute; set log retention, sample verbose logs, and keep dimension cardinality low. Mental model: a hospital monitor, the chart, and following one patient

The bill killers, ranked

In real bills the top surprises are usually: 1) over-provisioned instances/RDS (right-size — often 30-50% off), 2) data transfer & NAT Gateway egress (architect to keep traffic in-AZ, use VPC endpoints), 3) idle/orphaned resources (unattached EBS, old snapshots, idle load balancers, forgotten dev environments), 4) no commitment discounts on steady load (Savings Plans). Attack them in that order.

Why a playbook, and why the order matters

§14 gave the FinOps principles; this is the runbook you execute when a bill needs cutting — and the order is deliberate because doing it wrong wastes effort or locks in mistakes. You See first because you cannot optimize what you can't measure, and guessing at the culprit is how people spend a week shaving 3% off the wrong service. You Right-size second because it's the biggest, risk-free win — most resources are provisioned "to be safe" and run at a fraction of capacity. You Commit (Savings Plans/RIs) third, and only after right-sizing, because committing to a 1–3 year discount on an oversized instance locks in the waste — you'd be paying a discounted rate for capacity you didn't need. You Clean up orphans last (or continuously) because it's pure deletion of things nothing uses. Then you set guardrails so it doesn't creep back.

How the savings mechanisms actually work: right-sizing uses Compute Optimizer, which reads weeks of real CloudWatch utilization to recommend a smaller/newer instance at equal performance — often a newer generation or Graviton (§22) that's cheaper and faster. Savings Plans give you a discount (up to ~72%) in exchange for committing to a steady dollars-per-hour of compute for 1 or 3 years; because they apply to a spend commitment rather than a specific instance type, they're more flexible than old Reserved Instances and survive you changing instance families. Spot sells spare capacity at up to ~90% off with a 2-minute reclaim warning — perfect for fault-tolerant, interruptible work (batch, CI, stateless workers) but never for a stateful primary. Cost Anomaly Detection uses ML to learn your normal spend pattern and alerts on deviations, catching a runaway before the monthly invoice.

Common mistakes: committing before right-sizing, and cutting the wrong thing

Ordering: the classic blunder is buying Savings Plans/RIs first — you lock a 1–3 year commitment to oversized capacity, then right-size and discover you're committed to compute you no longer use (and can't easily unwind). Always right-size then commit, and commit only to your proven baseline, not your peak. Over-commitment: a 3-year RI for a workload you'll retire in 6 months is money burned; prefer flexible Savings Plans and shorter terms until usage is stable. Cutting value: "optimizing" by deleting backups, disabling Multi-AZ, or shrinking prod below what it needs trades a small saving for a large risk — that's a reliability failure, not a cost win. No guardrail: finishing the cleanup but not setting a Budget + Anomaly Detection, so spend silently creeps back and you re-run the whole exercise next quarter. Spot misuse: putting a stateful database or a single-instance service on Spot — the 2-minute reclaim will take it down.

Mental model: cutting a household budget the smart way

To cut spending you first read the bank statement to see where money actually goes (See) — you don't guess. Then you downgrade the plans you barely use — the giant cable package you watch 10% of (right-size). Then, on the things you'll definitely keep, you sign a cheaper annual contract for a discount (commit) — but only after downgrading, or you'd be locking in a year of the oversized plan. Finally you cancel the zombie subscriptions you forgot about (clean up orphans) and set a spending alert so it doesn't creep back. The killer mistake is signing the annual contract before downgrading — now you're committed to paying for channels you were about to cut.

Tying it together: here's a realistic, minimal Terraform that provisions a production-shaped setup — the kind of thing you'd actually start from. (Full Terraform depth is in the Terraform guide.)

A production-shaped stack in Terraform (excerpt)
terraform {
  backend "s3" {                      # remote state + locking (never local for teams)
    bucket = "acme-tfstate"
    key    = "prod/app/terraform.tfstate"
    region = "us-east-1"
    dynamodb_table = "tf-locks"
    encrypt = true
  }
}

# Reuse the battle-tested community VPC module instead of hand-rolling
module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "5.5.0"
  name    = "prod"
  cidr    = "10.0.0.0/16"
  azs             = ["us-east-1a", "us-east-1b", "us-east-1c"]
  private_subnets = ["10.0.1.0/24", "10.0.2.0/24", "10.0.3.0/24"]
  public_subnets  = ["10.0.101.0/24", "10.0.102.0/24", "10.0.103.0/24"]
  enable_nat_gateway = true
  single_nat_gateway = false          # one NAT per AZ = HA (cost tradeoff)
}

resource "aws_db_instance" "main" {
  engine            = "postgres"
  instance_class    = "db.t3.medium"
  multi_az          = true            # standby in another AZ
  storage_encrypted = true
  backup_retention_period = 14
  deletion_protection     = true      # can't be accidentally destroyed
  db_subnet_group_name    = module.vpc.database_subnet_group
}
Why this shape is "production"
  • Remote, locked, encrypted state — safe for a team.
  • Multi-AZ everything — subnets, NAT, RDS standby.
  • Reuses a vetted module — don't hand-roll a VPC.
  • Encryption + backups + deletion protection on the database.
  • Runs through CI with OIDC — no static keys, plan on PR, gated apply.
Why IaC — the problem with clicking in the console

Every section so far showed aws ... commands to create things imperatively. That's fine for learning and one-offs, but it doesn't scale to a real environment for three reasons. Reproducibility: a console-clicked or hand-scripted environment can't be recreated identically — the DR region (§28), the staging copy, and prod inevitably drift apart, and "it works in staging" stops meaning anything. Auditability: nobody can answer "who changed this security group and why?" — there's no diff, no review, no history. Safety: a typo in a live command executes immediately with no preview. Infrastructure as Code solves all three: your infrastructure is a declarative description in version control, so it's peer-reviewed like code, diffable, reproducible in any account/region by re-running it, and previewable before it touches anything. It turns infrastructure from a pile of manual actions into a versioned, testable artifact.

How Terraform works under the hood: you declare the desired end state (this VPC, this RDS with these settings); Terraform compares that to a state file — its record of what it currently manages — and computes the minimal set of API calls to reconcile reality with your declaration. terraform plan shows that diff before applying (create/change/destroy), which is the safety net a raw CLI command lacks. The state file is why the backend "s3" block matters: for a team it must live in remote, shared, locked storage (S3 + a DynamoDB lock table) so two engineers can't apply simultaneously and corrupt it. Modules (like the community VPC module in the excerpt) are reusable, battle-tested building blocks — you don't hand-roll a VPC's dozen interlocking resources. In CI, the pipeline authenticates via OIDC (a short-lived token, no static keys — §5), runs plan on the pull request for review, and only applys after approval.

    }

Common mistakes: local state, unreviewed destroys, and secrets in code

State: the disasters are (1) local state on one laptop for a team — lose the file or two people apply at once and the state (Terraform's map of reality) corrupts, orphaning or duplicating resources; always use a remote, locked backend. (2) Ignoring the plan and applying a change that quietly says 1 to destroy — a renamed resource or changed immutable attribute can replace (destroy + recreate) your production database; read every destroy in the plan. Security: hardcoding passwords/keys in .tf files (they're plaintext in Git and in the state file) — pass secrets via Secrets Manager/variables, and treat the state file as sensitive (it can contain secrets). Cost: the excerpt's single_nat_gateway = false is one NAT per AZ — correct for HA but 3× the NAT hourly cost (§9); make that trade-off consciously per environment (one NAT is fine for dev). Drift: making a "quick fix" in the console after Terraform owns a resource — now code and reality disagree and the next apply may revert your fix or fail.

Mental model: a blueprint vs building by hand each time

Clicking in the AWS console is building a house by hand, room by room, from memory — the second house never quite matches the first, and nobody can tell what changed or why. Terraform is an architectural blueprint: you write down exactly what the building should be, and a contractor builds it identically every time, in any city (region/account). Before any construction, the contractor shows you a marked-up plan — "I'll add these 42 things, tear down nothing" — so you approve before a wall moves. Change the blueprint, and it figures out the minimal renovation. The one rule: everyone must work from the same master blueprint kept in one safe place (remote state), or two contractors renovate the same room at once and chaos follows.

34. Real-World Scenarios

Advanced understanding is knowing which services combine to solve a real problem. Here are common architectures a DevOps engineer is asked to build.

Scenario: a scalable web application

The reference 3-tier web app

Route 53 (DNS) → CloudFront (CDN + WAF) → ALB (load balancer, multi-AZ) → ECS Fargate / EKS (app tier, autoscaling, private subnets) → RDS Multi-AZ (database) + ElastiCache (cache) + S3 (static/uploads). Secrets in Secrets Manager, images in ECR, logs/metrics in CloudWatch, everything defined in Terraform and deployed via CI/CD. This single pattern covers the majority of web workloads.

Scenario: event-driven / serverless processing

The serverless pipeline

API Gateway → Lambda (validate) → SQS (buffer) → Lambda workers (process, auto-scale to load) → DynamoDB (store) → EventBridge (fan out events to other systems). Add a dead-letter queue for poison messages and Step Functions for multi-step workflows. Pay only per request, scale to zero when idle — ideal for spiky or asynchronous work.

Scenario: disaster recovery for a critical system

Warm-standby DR (see §28 and SRE DR)

Primary region runs full-scale. A second region runs a scaled-down copy kept current by RDS cross-region read replica + S3 cross-region replication, with infra defined once in Terraform and deployed to both. Route 53 health-check failover flips traffic to the standby if the primary fails. Test the failover with regular game days — an untested DR plan is not a DR plan.

This is what "advanced" really means

Advanced cloud skill isn't memorizing every service — it's knowing which handful to combine for a given requirement, how they fail, and what they cost. The scenarios above are the patterns you'll build over and over. Master these, the landing zone, Well-Architected reviews, and the cost/observability playbooks, and you're operating at the level the roadmaps call "lead."

Why scenarios beat a service list — architecture is composition

You could memorize all 200+ AWS services and still be unable to build anything, because the skill that matters is composition: knowing which small set of services snaps together to meet a real requirement, and — just as important — how the seams between them fail. These three scenarios exist because they cover the overwhelming majority of what teams actually build (a request/response web app, an asynchronous processing pipeline, and surviving a disaster), and each is really a recap that ties the earlier sections into a working whole: the web app uses DNS (§20), CDN (§21), load balancing (§8), containers (§32), databases (§11/§24), and secrets (§12); the serverless pipeline uses the messaging (§26) and serverless (§25) patterns; the DR scenario applies §28. Learning them as patterns means the next novel requirement is "which pattern is this a variation of?" rather than "where do I even start?"

How to reason about a new requirement, concretely: start from the traffic shape. Is it synchronous request/response where a user waits for an answer? → the 3-tier web pattern (edge → LB → stateless app tier → managed data tier), sized for steady load. Is it asynchronous work that can be queued and processed later? → the event-driven serverless pattern (API → queue → workers → store), which scales to zero and absorbs spikes. Then layer the cross-cutting concerns every pattern needs: state goes in managed stores (RDS/DynamoDB/S3), never on the compute; secrets in Secrets Manager; identity via IAM roles, not keys; observability (§33) and cost guardrails (§34) from day one; and everything as code (§35) so it's reproducible in a DR region. The scenarios differ mainly in that first traffic-shape decision — the surrounding hygiene is identical.

Common mistakes: over-engineering, wrong pattern, and skipping the hygiene

Over-engineering: reaching for the full 3-tier + multi-region + EKS pattern for an internal tool with 20 users — the reference architectures are a menu, not a mandate; scale the pattern to the actual requirement (a single small instance or a Lambda may be plenty). Wrong traffic shape: forcing async work (video processing, report generation) into a synchronous request that then times out at the ALB/API Gateway — queue it (§26) instead; conversely, putting a low-latency user-facing API behind a queue adds needless delay. Skipping hygiene: building the happy path and omitting the cross-cutting concerns — no dead-letter queue (poison messages jam the pipeline), state stored on the compute (lost on autoscale/replace), secrets baked into images, no budget or alarms — these are exactly what turn a demo into a 3am incident. Untested DR: drawing the warm-standby diagram but never running a game day (§28) — an untested DR plan is decoration.

Mental model: recipes, not a pantry inventory

A great cook isn't someone who can name every ingredient in the pantry — it's someone who knows a handful of reliable recipes and which one fits the occasion. These scenarios are those recipes: "customer-facing website" → the 3-tier dish; "process a flood of uploads" → the queue-and-workers dish; "survive the kitchen catching fire" → the DR dish. Once you know the recipes, a new request is just "which recipe is this, and what do I swap?" — you're no longer staring at 200 ingredients wondering where to begin. And every good recipe includes the same basics (season it, don't leave the stove on) — the secrets, identity, monitoring, and cost guardrails you add to every build.

35. Best Practices — the checklist

Production cloud checklist
  • Multi-AZ for anything that matters; multi-region for DR/critical.
  • Least-privilege IAM; roles + OIDC, MFA on humans, root locked away.
  • Private subnets for app/DB; only LBs/NAT in public subnets.
  • Everything as code (Terraform) — no click-ops in prod.
  • Encrypt at rest (KMS) and in transit (TLS); block public S3.
  • CloudTrail + GuardDuty on; centralize logs.
  • Tag + budget + right-size for cost control.
  • Automate everything through CI/CD with OIDC auth.

36. Troubleshooting Playbook

"Access Denied" on an API call

IAM. Check the identity (aws sts get-caller-identity) and its policies. Decode the message, or use the IAM Policy Simulator. Remember explicit Deny always wins, and check resource policies (S3 bucket policy) too.

Can't SSH / connect to an instance

Check: security group allows your IP on the port; instance is in a public subnet with a route to the Internet Gateway (or use SSM Session Manager — no SSH needed); the instance is healthy.

App in a private subnet can't reach the internet

Private subnets need a NAT Gateway in a public subnet and a route to it for outbound traffic. Inbound stays blocked (that's the point).

Surprisingly high bill

Open Cost Explorer, group by service and tag. Usual culprits: data transfer, NAT gateways, idle RDS/instances, orphaned EBS/EIP. Set an AWS Budget alert so it never surprises you again.
