Ansible: The Complete Guide

Automate server configuration, application deployment, and orchestration with simple, agentless YAML — from your first playbook to reusable roles, vaults, and CI-driven automation.

📖 How to read this guide

Each concept: what it is, why it exists, the YAML, and ★ best practice. Ansible pairs naturally with the Terraform guide (which provisions the servers Ansible then configures) and builds on the Linux guide.

1. What is Ansible?

Ansible automates repetitive IT tasks — configuring servers, installing software, deploying apps — by describing the desired state in YAML and running it across many machines at once.

Ansible = a to-do list your servers follow

Instead of SSH-ing into 50 servers and typing the same commands 50 times, you write the steps down once in a playbook and Ansible runs them on all 50 in parallel. And it's smart: if a step is already done (package already installed), it skips it. So you can run it again and again safely.

Why Ansible exists

Before configuration management, servers were configured by hand or by fragile bash scripts that assumed a clean starting state. That approach doesn't survive contact with reality: servers drift apart ("snowflake" servers), a script that worked on a fresh box breaks when re-run on a half-configured one, and nobody can say with confidence what state any given machine is in. Ansible exists to replace imperative "run these commands" thinking with declarative "here is the state I want" thinking. You describe the end result; Ansible figures out whether each step is already satisfied and only changes what needs changing.

It was designed to be radically simple to adopt compared to earlier tools (Puppet, Chef) that require an agent daemon and a central server. Ansible needs neither — which is why a single engineer can start managing a fleet in an afternoon.

How it works under the hood

When you run a playbook, the control node (your laptop or CI runner, the only machine with Ansible installed) reads your YAML, resolves the inventory into a concrete host list, and for each task connects to each managed host over SSH. It then copies a small, self-contained Python module file to a temporary directory on the target, executes it with the task's arguments, captures the JSON the module prints to stdout, and deletes the temp file. Nothing stays behind — there is no running agent. The module itself contains the logic to check current state and decide whether a change is needed.

Declarative desired state, not a script

A task like "package nginx is present" is a goal, not a command. Ansible asks the target "is nginx installed?" and installs it only if not. Contrast a bash script that blindly runs apt install nginx every time. This distinction — state vs. commands — is the mental foundation for everything else in this guide.

A worked example: one command against your whole fleet
# Report the uptime of every host, in parallel
ansible all -i inventory.ini -m command -a "uptime"
Output
web-1 | CHANGED | rc=0 >>
 12:30:01 up 5 days,  3:14,  0 users,  load average: 0.02, 0.05, 0.01
web-2 | CHANGED | rc=0 >>
 12:30:01 up 5 days,  3:11,  0 users,  load average: 0.00, 0.01, 0.00
db-1  | CHANGED | rc=0 >>
 12:30:01 up 9 days,  8:42,  0 users,  load average: 0.10, 0.08, 0.09

That single line did what would otherwise be three SSH logins and three manually-typed commands — and it would scale identically to 300 hosts.

Common early misconceptions

Ansible is push-based and stateless — it does not keep a database of your infrastructure the way Terraform keeps state. It also is not a monitoring or scheduling system by itself; it runs when you run it (AWX/cron adds scheduling, see §28). And "agentless" doesn't mean "requirement-less": managed Linux hosts still need Python and reachable SSH.

Recipe vs. errand list

Think of a shell script as an errand list: "buy milk, buy eggs" — run it twice and you buy milk twice. An Ansible playbook is a recipe for what the fridge should contain: "there should be milk and eggs." Run it twice and the second time it looks in the fridge, sees they're already there, and does nothing. Same desired outcome, no waste, no harm.

2. How Ansible Works — Agentless over SSH

Ansible's killer feature: no agent to install on the machines you manage. It connects over plain SSH (or WinRM for Windows) and runs small modules, then removes them.

Why agentless matters

Agent-based tools (Puppet, Chef, Salt in its classic mode) require you to install a daemon on every managed machine, keep it patched, open a port for it, and run a central master server it phones home to. That is a lot of moving parts to secure and maintain — and a bootstrapping problem (how do you install the agent on a brand-new box?). Ansible sidesteps all of it by riding on infrastructure you already have and trust: SSH. If you can SSH to a box, you can manage it. There is no new attack surface, no agent version skew, and no "the agent died so the host stopped reporting" failure mode.

The task execution lifecycle, step by step

For each task on each host, Ansible does roughly this:

  1. Connect — opens an SSH session (reusing an existing one if ControlPersist is enabled).
  2. Assemble the module — on the control node, Ansible bundles the module's Python code plus your task arguments into a single executable payload.
  3. Ship it — copies that payload into a temp dir under the remote user's home (e.g. ~/.ansible/tmp/).
  4. Execute — runs the payload with the remote Python interpreter, escalating with become (sudo) if requested.
  5. Collect — the module prints a JSON result (changed, failed, plus any data) to stdout, which Ansible parses.
  6. Clean up — deletes the temp files. Nothing persists on the target.
Pipelining removes round-trips

Normally steps 3–4 mean multiple SSH operations per task (copy file, then execute). With pipelining = true (in ansible.cfg), Ansible pipes the module straight into the remote Python process over the existing SSH connection, eliminating the separate copy step. This can cut playbook time dramatically — see §22. It requires that the remote sudoers file does not force requiretty.

Watch the connection happen with -vvv
ansible web-1 -i inventory.ini -m ping -vvv
Abbreviated output — note the SSH command and temp dir
ESTABLISH SSH CONNECTION FOR USER: ubuntu
SSH: EXEC ssh -o ControlMaster=auto -o ControlPersist=60s ... 10.0.1.11
<10.0.1.11> PUT /tmp/ansible-local-.../ping.py TO /home/ubuntu/.ansible/tmp/ansible-tmp-.../AnsiballZ_ping.py
<10.0.1.11> EXEC /bin/sh -c 'python3 .../AnsiballZ_ping.py && sleep 0'
web-1 | SUCCESS => {
    "changed": false,
    "ping": "pong"
}

You can see the whole lifecycle: it establishes SSH, PUTs the module into a temp dir, EXECs it with remote Python, and the module replies with JSON. The ping module deliberately reports changed: false because checking reachability changes nothing.

Gotchas: Python, host keys, and WinRM

Because modules run in remote Python, the target must have a Python interpreter — set ansible_python_interpreter if it lives somewhere non-standard (e.g. /usr/bin/python3 on minimal images). The first SSH connection may block on host-key verification; pre-seed known_hosts or set host_key_checking deliberately. Windows hosts don't use SSH-by-default modules — they connect over WinRM and run PowerShell modules instead.

A traveling contractor with a toolbox

Imagine a contractor who owns no permanent office in your building. Each time there's a job, they knock on the door (SSH), bring exactly the one tool they need for that task (the module), do the work, take the tool back, and leave — no locker, no stored equipment, no rent. That's agentless: the intelligence lives on the control node and visits only when needed.

3. Install & First Command

Install & ping your fleet
python3 -m pip install --user ansible
ansible --version

# "ping" all hosts (checks SSH + Python, does NOT ICMP ping)
ansible all -i inventory.ini -m ping

Why the install is so light — and what actually gets installed

You only install Ansible on the control node. The PyPI package ansible is a "batteries-included" bundle: it pulls in ansible-core (the engine: ansible, ansible-playbook, ansible-galaxy CLIs and the SSH connection machinery) plus a large set of community collections. If you want a minimal footprint — common in CI images — install just ansible-core and add only the collections you need via requirements.yml. Managed nodes get nothing installed; they only need SSH access and a Python interpreter.

Prefer a pinned virtualenv, not a global install

Ansible is just Python. Installing it into a dedicated virtualenv (or pinning it in requirements.txt) means every engineer and every CI run uses the same version, so "works on my machine" doesn't turn into "the pipeline behaves differently." Pin both ansible-core and your collections.

Reproducible install into a virtualenv
python3 -m venv .venv && source .venv/bin/activate
pip install "ansible-core==2.16.*"          # pin the engine
ansible-galaxy collection install -r requirements.yml   # pin collections
ansible --version
Output — confirm config file, python, and paths
ansible [core 2.16.6]
  config file = /home/you/project/ansible.cfg
  configured module search path = ['/home/you/.ansible/plugins/modules', ...]
  ansible python module location = /home/you/project/.venv/lib/python3.11/site-packages/ansible
  executable location = /home/you/project/.venv/bin/ansible
  python version = 3.11.4

The config file line tells you which ansible.cfg is in effect — invaluable when a setting isn't taking effect because a different config is being loaded.

The ping module is not ICMP ping

The most common beginner surprise: -m ping does not send an ICMP packet. It SSHes in, runs a tiny Python module, and expects "pong" back — so it actually verifies the whole management path (SSH auth and a working remote Python), which is exactly what you want to test first. A host that answers a network ping can still fail Ansible's ping if SSH or Python is broken.

Install the remote control, not the TVs

Setting up Ansible is like buying one universal remote (the control node). You don't install anything into the TVs (your servers) — the remote just needs line-of-sight (SSH) to talk to them. Buy one good remote, keep its firmware version pinned, and it drives the whole living room.

4. Inventory — Your Fleet

The inventory lists the machines Ansible manages, organized into groups you can target.

inventory.ini
[web]
web-1 ansible_host=10.0.1.11
web-2 ansible_host=10.0.1.12

[db]
db-1 ansible_host=10.0.2.11

[production:children]   # a group of groups
web
db

[all:vars]
ansible_user=ubuntu
ansible_ssh_private_key_file=~/.ssh/id_ed25519
Dynamic inventory for the cloud

In the cloud, servers come and go. Instead of a static file, use a dynamic inventory plugin (e.g., aws_ec2) that queries your cloud provider live and groups hosts by tags — so a newly-provisioned instance is automatically manageable.

Why the inventory is the center of gravity

Every Ansible run answers two questions: what to do (the playbook) and where to do it (the inventory). The inventory is your source of truth for the fleet's topology. Groups ([web], [db]) are how you target subsets, and groups-of-groups ([production:children]) let you compose them — run against production and you hit every web and db host at once. This is what lets one playbook serve staging and prod: same tasks, different inventory.

How host and group variables attach to hosts

Inventory isn't just a host list — it's also where variables live. Ansible looks for host_vars/<hostname>.yml and group_vars/<groupname>.yml directories next to your inventory and merges them onto matching hosts automatically. When a host belongs to several groups, their variables merge; if two groups define the same variable, the one with higher group priority (or, by default, the last-loaded alphabetically) wins. The special group all applies to every host, so group_vars/all.yml is the place for fleet-wide defaults.

Recommended layout: vars beside the inventory
inventories/
  prod/
    hosts.ini
    group_vars/
      all.yml          # fleet-wide defaults
      web.yml          # vars for the [web] group
    host_vars/
      db-1.yml         # vars for just db-1
Verify what Ansible actually sees
# Render the whole inventory as a tree of groups and hosts
ansible-inventory -i inventory.ini --graph

# Dump the fully-merged variables for one host (great for debugging precedence)
ansible-inventory -i inventory.ini --host web-1
--graph output
@all:
  |--@production:
  |  |--@web:
  |  |  |--web-1
  |  |  |--web-2
  |  |--@db:
  |  |  |--db-1
  |  |--@ungrouped:

Always run ansible-inventory --graph before a big playbook — it confirms your groups resolved the way you think, before you accidentally target the wrong hosts.

Common inventory mistakes

1. Targeting all by accident: forgetting --limit and running a destructive play against every host. 2. INI vs YAML confusion: INI inventories put host vars inline (web-1 ansible_host=10.0.1.11), while YAML inventories nest them — mixing syntaxes silently drops variables. 3. Duplicate hostnames across groups are fine (same host, merged vars) but the same name pointing at different ansible_host values is a bug. 4. Putting secrets in the inventory file — use Vault (§13) instead.

A seating chart for your servers

The inventory is like a classroom seating chart with named groups: "the front row," "the window seats," "everyone." When the teacher says "front row, hand in your homework," they don't need to name each student. You point Ansible at a group name and it knows exactly which machines that means — and each seat can have sticky notes (variables) attached.

5. Ad-hoc Commands & Modules

For quick one-off tasks, run a single module across hosts without writing a playbook.

Ad-hoc examples
ansible web -m apt -a "name=nginx state=present" --become   # install nginx on [web]
ansible all -m service -a "name=nginx state=restarted" --become
ansible all -m shell -a "df -h"                              # run a shell command
ansible db  -m copy -a "src=./my.cnf dest=/etc/mysql/my.cnf" --become
Modules are the verbs

Ansible ships thousands of modules — apt, yum, service, copy, template, user, git, docker_container, cloud modules, and more. Each is idempotent: it describes a desired state, not a command to blindly run. Always prefer a module over shell/command.

Why ad-hoc commands exist alongside playbooks

Not everything deserves a saved file. Ad-hoc commands are for investigation and one-offs: "is nginx running everywhere?", "how much disk is free on the db tier?", "restart this service on one host right now." They use the exact same modules and inventory as playbooks, so what you learn ad-hoc transfers directly. The rule of thumb: if you'll run it more than once, or it changes state you care about, promote it to a playbook so it's version-controlled and repeatable.

How a module call resolves under the hood

ansible web -m apt -a "name=nginx state=present" breaks down as: web is the host pattern (resolved via inventory), -m apt selects the module, and -a passes its arguments. Ansible ships the apt module's Python to each host in the web group, runs it, and the module itself queries dpkg to see whether nginx is installed before deciding to act. That's why the same command is safe to run repeatedly — the idempotency logic lives inside the module, not in your command.

Worked example: check state, then converge it
# 1) Investigate — is nginx installed anywhere? (read-only)
ansible web -i inventory.ini -m command -a "dpkg -l nginx" 

# 2) Converge — make sure it's present (idempotent)
ansible web -i inventory.ini -m apt -a "name=nginx state=present" --become
Second run shows idempotency in action
# First converge:
web-1 | CHANGED => { "changed": true, ... }     # installed it
# Run the SAME command again:
web-1 | SUCCESS => { "changed": false, ... }    # already present, did nothing

The color/keyword tells the story: CHANGED (yellow) means Ansible altered the host; SUCCESS/ok (green) means reality already matched the goal. A well-behaved fleet trends toward all-green on repeat runs.

shell vs command vs a real module

The command module runs a binary directly (no shell), so |, >, &&, and environment expansion do not work. The shell module runs through /bin/sh, so those do work — but it's a security and idempotency risk. Both report changed every single time because they can't know whether they changed anything. Prefer a purpose-built module (apt, copy, service) that understands state. Only drop to command/shell when no module exists — and then guard it (see §7 and §21).

A quick phone call vs. a written procedure

An ad-hoc command is like phoning one team and saying "hey, restart the printer." A playbook is the written, approved procedure you file away and hand to anyone. Same action, but one is a spur-of-the-moment ask and the other is documented and repeatable. Use the phone call to poke around; write the procedure for anything that matters.

6. Playbooks

A playbook is a YAML file of plays; each play maps a group of hosts to a list of tasks.

webserver.yml
---
- name: Configure web servers
  hosts: web
  become: true                 # run tasks with sudo
  vars:
    nginx_port: 80
  tasks:
    - name: Install nginx
      ansible.builtin.apt:
        name: nginx
        state: present
        update_cache: true

    - name: Deploy site config
      ansible.builtin.template:
        src: nginx.conf.j2
        dest: /etc/nginx/sites-available/default
      notify: Restart nginx        # triggers a handler (only if changed)

    - name: Ensure nginx is running & enabled
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: true

  handlers:
    - name: Restart nginx
      ansible.builtin.service:
        name: nginx
        state: restarted
Run it
ansible-playbook -i inventory.ini webserver.yml
ansible-playbook -i inventory.ini webserver.yml --check --diff   # dry-run + show changes
ansible-playbook -i inventory.ini webserver.yml --limit web-1    # one host
ansible-playbook -i inventory.ini webserver.yml --tags config    # only tagged tasks

Why playbooks are the heart of Ansible

An ad-hoc command does one thing on one target set. Real work is a sequence: install the package, drop the config, ensure the service is running, and only restart if the config changed. A playbook captures that whole ordered workflow in one version-controlled file, with names on every step so the run log doubles as documentation. Because it's declarative and idempotent, it's both the deploy tool and the source of truth for "what should this server look like."

How a playbook is structured and executed

A playbook is a list of plays. Each play binds a hosts: pattern to a list of tasks:, plus optional vars:, handlers:, and roles:. Execution order is deliberate and top-down: by default Ansible runs task 1 on all targeted hosts, waits for them, then task 2 on all hosts, and so on (the linear strategy, §19). This lockstep is what makes ordered rollouts and "gate on all hosts passing this step" possible. At the very start of a play, unless you disable it, Ansible runs an implicit fact-gathering step (§8) so ansible_facts is populated before your tasks reference it.

Always use fully-qualified module names

Write ansible.builtin.apt, not just apt. The FQCN (fully-qualified collection name) makes it unambiguous which collection provides the module, protects you from name collisions when you install community collections, and is the modern, lint-clean style. Short names still work for built-ins but are discouraged in shared code.

What a run looks like — the PLAY RECAP is the summary that matters
PLAY [Configure web servers] ***************************************

TASK [Gathering Facts] *********************************************
ok: [web-1]
ok: [web-2]

TASK [Install nginx] ***********************************************
changed: [web-1]
ok: [web-2]                # web-2 already had it

TASK [Deploy site config] ******************************************
changed: [web-1]
changed: [web-2]

RUNNING HANDLER [Restart nginx] ************************************
changed: [web-1]
changed: [web-2]

PLAY RECAP *********************************************************
web-1 : ok=4  changed=3  unreachable=0  failed=0  skipped=0
web-2 : ok=4  changed=2  unreachable=0  failed=0  skipped=0

Read the PLAY RECAP bottom-up when triaging: unreachable means SSH/connectivity, failed means a task errored, and a healthy re-run should show changed=0 everywhere (proof of idempotency).

--check --diff is your seatbelt

--check is a dry run: modules report what they would change without touching anything. Add --diff to see the actual before/after of files and templates. Run this against production before every real apply. Note the caveat: tasks whose result depends on an earlier task's real change (e.g. a command that only runs after a package install) may report inaccurately in check mode — use check_mode: false on read-only tasks that must always execute.

Playbook gotchas

YAML indentation is significant — a misaligned - silently changes structure; run ansible-playbook --syntax-check and ansible-lint. become: true is per-play or per-task — forgetting it gives "permission denied" on privileged tasks. Order matters — put "install" before "configure" before "start." And tasks without name: produce unreadable logs; name everything.

A checklist a whole team runs in lockstep

A play is like a preflight checklist read aloud to a row of pilots at once: "everyone, check fuel… now everyone, check flaps…" The captain doesn't move to the next item until every pilot has done the current one. That's why the order is dependable and why one failing pilot is easy to spot — the checklist stops and tells you exactly who and where.

7. Idempotency — the Core Idea

The most important concept in Ansible: running the same playbook twice should produce the same result, changing nothing the second time.

shell/command break idempotency

Raw shell commands run every time and report "changed" always. If you must use them, guard with creates=/removes= or a when:/changed_when: condition. Reach for a real module first — it handles idempotency for you.

Why idempotency is the whole point

Without idempotency, re-running automation is dangerous — you might install twice, append a line twice, or restart a service that was fine. That fear leads teams to run automation once and then never again, which is how servers drift. Idempotency flips this: because a re-run is guaranteed safe, you can run the playbook on a schedule (or on every deploy) to continuously enforce the desired state. Drift gets corrected automatically. This is the difference between "a script I ran once" and "the definition of what this server is."

How idempotency is actually implemented

There is no magic in the engine — idempotency lives inside each module. A module follows a check-then-act pattern:

  1. Read current state: the apt module asks dpkg "is nginx installed?"; the copy module computes the checksum of the destination file; the user module reads /etc/passwd.
  2. Compare to desired state: the arguments you passed (state: present, a source file's checksum, a UID).
  3. Act only on a diff: if they already match, return changed: false and do nothing; otherwise make the change and return changed: true.

The engine aggregates those changed booleans into the changed=N count you see in the recap, and uses them to decide whether to fire handlers. So "idempotent" is a property the module author guarantees — which is exactly why command/shell, which can't inspect arbitrary side effects, can't guarantee it.

Making a necessary shell command idempotent
- name: Extract app bundle (only if not already extracted)
  ansible.builtin.command: tar xzf /tmp/app.tar.gz -C /opt/app
  args:
    creates: /opt/app/VERSION      # skip entirely if this file already exists

- name: Run a report and decide "changed" ourselves
  ansible.builtin.command: /opt/generate-report.sh
  register: report
  changed_when: "'wrote' in report.stdout"   # only 'changed' if it actually wrote
  failed_when: report.rc not in [0, 2]        # rc=2 is an acceptable warning here
Result: honest change reporting on re-run
# First run:  changed: [web-1]   (VERSION didn't exist, tar ran)
# Second run: ok: [web-1]        (creates: matched, task skipped)
The "always changed" trap and its fixes

A task that reports changed on every run breaks handler logic (it fires restarts needlessly) and hides real changes in the noise. Culprits are almost always command/shell. Fixes, in order of preference: (1) switch to a real module; (2) add creates:/removes: guards; (3) set an explicit changed_when: based on the command's output or return code. Never leave a shell task reporting a blind changed.

A thermostat, not a light switch

A light switch is imperative: flip it and the state toggles — flip it twice and you're back where you started, which is not what you wanted. A thermostat is idempotent: you set it to 21°C and it does whatever is needed to reach and hold that temperature. Set it to 21 again and nothing happens — you're already there. Ansible modules are thermostats: you declare the target and re-declaring it is harmless.

8. Variables & Facts

Variables parameterize playbooks; facts are data Ansible auto-discovers about each host (OS, IP, memory).

group_vars & using facts
# group_vars/web.yml  — variables for all hosts in [web]
nginx_worker_processes: 4
app_version: "1.4.2"

# In a task, reference variables and gathered facts:
- name: Show OS family and memory
  ansible.builtin.debug:
    msg: "{{ ansible_facts['distribution'] }} with {{ ansible_facts['memtotal_mb'] }} MB"
Variable precedence

Ansible has many variable sources with a strict precedence (roughly: command-line -e > task vars > block vars > role vars > host_vars > group_vars > role defaults). When a value surprises you, precedence is usually why. Keep it simple: defaults in roles, overrides in group_vars/host_vars.

Why variables and facts exist

The same playbook must work across dev, staging, and prod, across Debian and RHEL, across 1 GB and 64 GB boxes. Hard-coding values would mean a separate playbook per environment — an unmaintainable fork. Variables let one playbook adapt by injecting different values per host or group. Facts go further: they let the playbook discover the host's reality at runtime (OS family, IP, CPU count, mounted disks) and adapt itself, so you don't have to enumerate every host's specifics by hand.

How fact gathering works

At the start of each play (unless gather_facts: false), Ansible runs the setup module on every host. It collects hundreds of data points and returns them as the ansible_facts dictionary — ansible_facts['distribution'], ['default_ipv4']['address'], ['memtotal_mb'], and so on. This is just another module ship-and-run over SSH, which is why it costs time on large fleets (mitigate with fact caching, §22). You can see everything it gathers with the setup module directly.

Inspect the facts of a host
ansible web-1 -i inventory.ini -m setup                    # dump all facts
ansible web-1 -i inventory.ini -m setup -a "filter=ansible_distribution*"
Filtered output
web-1 | SUCCESS => {
    "ansible_facts": {
        "ansible_distribution": "Ubuntu",
        "ansible_distribution_major_version": "22",
        "ansible_distribution_version": "22.04"
    }
}

How precedence resolves in practice

When the same variable name is set in multiple places, Ansible does not merge scalar values — the highest-precedence source wins outright. From lowest to highest, the sources you'll touch daily are: role defaults/ → inventory group_vars → inventory host_vars → play vars: → role vars/ → block/task vars: → --extra-vars (-e, always wins). The practical discipline: put overridable baselines in role defaults/, environment values in group_vars/, host-specific tweaks in host_vars/, and reserve -e for emergencies and CI-injected values.

Precedence demonstrated + a safe default
# roles/app/defaults/main.yml
app_port: 8080                 # lowest precedence — a sensible baseline

# group_vars/prod.yml
app_port: 80                   # prod overrides the default

# task-level (wins over both) or override at runtime:
- ansible.builtin.debug:
    msg: "listening on {{ app_port }}"
# ansible-playbook site.yml -e app_port=9090   # -e beats everything
Trace where a value actually came from
ansible-inventory -i inventories/prod --host web-1   # shows merged vars
ansible-playbook site.yml -e app_port=9090 --check   # confirm the override wins
Variable and fact gotchas

Undefined variables error at use time — protect optional ones with {{ x | default('...') }}. Precedence surprises come from setting the same name in two layers; consolidate. gather_facts: false means ansible_facts is empty — a task referencing a fact then fails cryptically. YAML type coercion: unquoted version: 1.10 becomes the float 1.1; quote version strings. And a bare {{ var }} at the start of a YAML value must be quoted or YAML treats it as a dict.

Mad-libs with auto-filled blanks

A playbook is a mad-libs sheet with blanks like {{ app_port }}. Variables are the words you write in the blanks. Facts are blanks that fill themselves in by looking at the actual server ("this box has 4 CPUs, so write 4"). Precedence is the rule for what happens when two people wrote in the same blank: the person with the most authority (the -e flag) wins.

9. Templates (Jinja2)

Generate config files dynamically per host using the Jinja2 templating engine.

templates/nginx.conf.j2
worker_processes {{ nginx_worker_processes }};
server {
    listen {{ nginx_port }};
    server_name {{ ansible_facts['fqdn'] }};
    {% for backend in app_backends %}
    upstream_server {{ backend }};
    {% endfor %}
}

Why templating beats copying static files

Config files differ per host — a worker count tied to CPU cores, a server_name equal to each host's FQDN, a backend list that varies by environment. Shipping a static file per host would mean maintaining dozens of near-identical files. A template is one file with placeholders that Ansible fills in per host using that host's variables and facts. One source, infinite correct outputs.

How the template module works under the hood

The template module renders the .j2 file on the control node using Jinja2, substituting variables and evaluating loops/conditionals, to produce the final text. It then behaves exactly like copy: it checksums the rendered result against the file already on the target and writes only if they differ — so templating is fully idempotent. Because rendering happens control-side, the target never needs Jinja2 or your variables; it just receives the finished file. This also drives handlers: the task reports changed only when the rendered output actually differs, so a "restart on config change" handler fires precisely when the config truly changed.

The task that renders it — with validation and backup
- name: Render nginx config
  ansible.builtin.template:
    src: nginx.conf.j2
    dest: /etc/nginx/nginx.conf
    owner: root
    group: root
    mode: "0644"
    backup: true                 # keep a timestamped copy of the old file
    validate: "nginx -t -c %s"   # abort if the rendered config is invalid
  notify: Restart nginx
Preview the exact change before applying
ansible-playbook site.yml --check --diff
--diff shows the rendered before/after
TASK [Render nginx config] *****************************************
--- before: /etc/nginx/nginx.conf
+++ after:  /etc/nginx/nginx.conf
@@ -1,3 +1,3 @@
-worker_processes 2;
+worker_processes 4;
 server {
     listen 80;
changed: [web-1]
validate: prevents shipping a broken config

The validate parameter runs a checker on the freshly-rendered file (with %s as its path) before installing it. If the check fails, the task fails and the old file is left untouched. This is how you avoid the classic outage where a templated typo takes down every web server at once. Pair it with backup: true for a fast manual rollback path.

Template gotchas

Whitespace: Jinja control blocks ({% ... %}) leave blank lines behind — use {%- ... -%} to trim, or set trim_blocks/lstrip_blocks. Undefined variables render as errors (or worse, empty strings under some settings) — default them. Escaping: if the target file itself uses {{ }} syntax (e.g. another templating system), wrap it in {% raw %}...{% endraw %}. And never template a file whose literal {{ you didn't intend to render.

A form letter with a mail-merge

A template is a form letter: "Dear ⟨name⟩, your order ⟨number⟩ ships to ⟨city⟩." The mail-merge (Jinja2) runs it once per recipient, filling the blanks from a spreadsheet (your variables and facts). Everyone gets a letter that reads as if it were written just for them — but you only wrote and maintain the one form.

10. Handlers, Loops & Conditionals

Loops, when, and handlers
- name: Install multiple packages
  ansible.builtin.apt: { name: "{{ item }}", state: present }
  loop: [nginx, git, curl, htop]

- name: Only on Debian family
  ansible.builtin.apt: { name: nginx, state: present }
  when: ansible_facts['os_family'] == "Debian"

- name: Deploy config
  ansible.builtin.template: { src: app.j2, dest: /etc/app.conf }
  notify: reload app            # handler runs ONCE at end, only if this changed
Handlers run once, at the end, only on change

A handler is a task triggered by notify. Even if ten tasks notify "restart nginx," it restarts once, after all tasks, and only if something actually changed. This is how you avoid needless service restarts.

Why these three constructs exist

Loops exist because you constantly repeat the same task over a list — ten packages, five users, three config files. Without loops you'd copy-paste a task ten times. Conditionals (when:) exist because one playbook runs across heterogeneous hosts — a Debian apt task must be skipped on RHEL. Handlers exist to solve the "restart only if something changed, and only once" problem elegantly, decoupling what changed from the reaction to the change.

How handlers, loops, and conditionals are evaluated

Handlers are queued, not run inline: when a task reports changed and has a notify, Ansible adds the named handler to a per-play notification set (a set, so duplicates collapse to one). Handlers run at the end of the play, in the order the handlers are defined (not the order notified). If a task fails mid-play, pending handlers don't run unless you --force-handlers. Loops run the task body once per item, and the task's changed/failed is aggregated across iterations. when: is a raw Jinja2 expression evaluated per host — if false, the task shows skipping and never ships a module.

Worked example combining all three, with flush_handlers
- hosts: web
  become: true
  tasks:
    - name: Install packages (loop)
      ansible.builtin.apt:
        name: "{{ item }}"
        state: present
      loop:
        - nginx
        - git
        - curl

    - name: Deploy vhost only for the prod environment (conditional)
      ansible.builtin.template:
        src: vhost.conf.j2
        dest: /etc/nginx/conf.d/app.conf
      when: env == "prod"
      notify: Restart nginx

    - name: Force pending handlers to run NOW, before the smoke test
      ansible.builtin.meta: flush_handlers

    - name: Smoke test (only meaningful after the restart happened)
      ansible.builtin.uri:
        url: "http://localhost/health"
        status_code: 200

  handlers:
    - name: Restart nginx
      ansible.builtin.service:
        name: nginx
        state: restarted
Run showing skip, single handler fire, and loop
TASK [Install packages (loop)] *************************************
changed: [web-1] => (item=nginx)
ok:      [web-1] => (item=git)
ok:      [web-1] => (item=curl)

TASK [Deploy vhost only for the prod environment] ******************
skipping: [web-2]        # web-2 is env=staging
changed:  [web-1]

RUNNING HANDLER [Restart nginx] ************************************
changed: [web-1]         # fired ONCE, only on web-1 which changed
meta: flush_handlers when order matters

Handlers normally wait until the play's end — but sometimes you must restart the service before a later task (like a health check) runs. meta: flush_handlers forces all pending handlers to run immediately at that point. Use it to sequence "change config → restart → verify" correctly within one play.

Loop and conditional gotchas

Old with_items is superseded by loop: — prefer loop. Looping a package module is slow if it installs one at a time; many modules (like apt) accept a list directly (name: "{{ list }}") and do it in one transaction — much faster. when with a bare variable should not be wrapped in {{ }} (it's already an expression). Handlers silently don't run if the notifying task didn't report changed, or if the play failed earlier — this confuses newcomers who expect an unconditional restart.

Sticky notes on the fridge

A handler is a sticky note: every time you finish a chore that dirties a pan, you slap a "wash the pan" note on the fridge. It doesn't matter if you cooked three dishes — there's one note, and you wash the pan once, at the end. If you cooked nothing that dirtied it, there's no note and you don't wash a clean pan. Loops are "do this chore for each item on the shopping list," and when: is "only do this chore if it's actually a weekday."

11. Roles — Reusable Structure

A role packages tasks, handlers, templates, variables, and defaults into a standard directory layout — the module/package of Ansible.

Create & use a role
ansible-galaxy role init roles/nginx     # scaffold the directory structure

# playbook using the role:
# - hosts: web
#   become: true
#   roles:
#     - nginx
#     - { role: app, app_version: "1.4.2" }
Put sane values in defaults/

Role defaults/main.yml has the lowest precedence, so consumers can easily override them. Ship every role with working defaults so it runs out of the box, and document the variables in the role's README.

Why roles exist

A single big playbook works until it doesn't: it grows to hundreds of lines, tasks and templates and vars tangle together, and you can't reuse "the nginx setup" in another project without copy-pasting. Roles are Ansible's answer to modularity — the equivalent of a library or package. A role bundles everything one concern needs (its tasks, handlers, templates, files, defaults, and metadata) into a conventional directory layout, so it can be dropped into any playbook, shared on Galaxy, versioned, and tested (with Molecule, §26) in isolation.

How role loading works — convention over configuration

When a play lists roles: [nginx], Ansible looks in roles/nginx/ and auto-loads by filename convention, no wiring required: tasks/main.yml becomes the role's tasks, handlers/main.yml its handlers, defaults/main.yml and vars/main.yml its variables, templates/ and files/ its assets (referenced by bare filename, since the role search path knows to look there), and meta/main.yml its dependencies on other roles. Roles listed under roles: run before the play's tasks:; to control ordering precisely, use import_role/include_role inside tasks: instead.

Scaffold and inspect a role
ansible-galaxy role init roles/nginx
find roles/nginx -maxdepth 2 -type f
Generated structure
roles/nginx/defaults/main.yml     # overridable variables (lowest precedence)
roles/nginx/vars/main.yml         # internal vars (high precedence)
roles/nginx/tasks/main.yml        # the work
roles/nginx/handlers/main.yml     # restart/reload handlers
roles/nginx/templates/            # *.j2 files
roles/nginx/files/                # static files to copy
roles/nginx/meta/main.yml         # role deps + Galaxy metadata
roles/nginx/README.md
tasks/main.yml + a play consuming the role with overrides
# roles/nginx/tasks/main.yml
- name: Install nginx
  ansible.builtin.apt: { name: nginx, state: present }
- name: Configure
  ansible.builtin.template:
    src: nginx.conf.j2            # found automatically in templates/
    dest: /etc/nginx/nginx.conf
  notify: Restart nginx           # handler lives in handlers/main.yml

# site.yml — thin playbook, roles do the work
- hosts: web
  become: true
  roles:
    - role: nginx
      vars:
        nginx_worker_processes: 8   # override a default for this play
Keep playbooks thin, roles fat

A mature Ansible codebase has short playbooks that mostly just map host groups to a list of roles. All logic lives in reusable, independently-testable roles. One role = one responsibility (nginx, postgres, the app). This is the single biggest structural improvement most teams make.

Role gotchas

vars/ vs defaults/: vars/main.yml has high precedence and is hard to override — put only true constants there; put anything a user might tune in defaults/. Referencing files by full path defeats the role search path — use bare filenames so the role stays relocatable. Hidden coupling: a role that reads a variable it doesn't declare in defaults/ will mysteriously fail when used elsewhere — document and default every input. roles: ordering vs tasks: confuses people; use import_role in tasks when you need a role to run at a specific point.

IKEA furniture kits

A role is a flat-pack furniture kit: one box with all the parts (tasks), the screws (templates/files), and an instruction sheet with sensible defaults. You don't need to know how the shelf is built — you just say "add the BILLY bookcase" and optionally tweak "make it white." Your playbook becomes a short shopping list of kits, and anyone can grab the same kit for their own room.

12. Ansible Galaxy & Collections

Don't reinvent common roles. Galaxy is the public hub; Collections bundle modules, roles, and plugins together.

Install shared content
ansible-galaxy collection install community.docker amazon.aws
ansible-galaxy role install geerlingguy.nginx
# requirements.yml pins versions for reproducibility (commit this):
#   collections: [ { name: amazon.aws, version: "7.0.0" } ]
ansible-galaxy install -r requirements.yml

Why Galaxy and Collections exist

Most infrastructure problems are not unique — thousands of teams install nginx, configure PostgreSQL, or manage AWS resources. Rewriting that from scratch is wasted effort and bugs. Galaxy is the shared marketplace of community roles and collections so you can stand on others' work. Collections exist because the old model (everything bundled into Ansible core) couldn't scale: modules were tied to Ansible's slow release cycle. Splitting content into independently-versioned collections lets the AWS modules ship on their own schedule, decoupled from ansible-core.

How collections are namespaced and resolved

A collection has a two-part name: namespace.name (e.g. amazon.aws, community.docker). Inside it live modules, roles, and plugins referenced by fully-qualified name — amazon.aws.ec2_instance. Ansible searches installed collections in ~/.ansible/collections and any paths in collections_paths. This namespacing is why FQCNs matter: community.docker.docker_container and a hypothetical mycorp.docker.docker_container can coexist with no collision. Roles installed from Galaxy (the older, standalone kind) land in ~/.ansible/roles and are referenced by their Galaxy name.

requirements.yml — pin everything, commit it
---
collections:
  - name: amazon.aws
    version: "7.0.0"          # exact pin for reproducibility
  - name: community.docker
    version: ">=3.4.0,<4.0.0" # allow patches, block breaking majors
roles:
  - name: geerlingguy.nginx
    version: "3.1.4"
Install pinned content and verify
ansible-galaxy install -r requirements.yml
ansible-galaxy collection list        # show installed collections + versions
ansible-doc amazon.aws.ec2_instance   # read a module's docs offline
collection list
# /home/you/.ansible/collections/ansible_collections
Collection        Version
----------------- -------
amazon.aws        7.0.0
community.docker  3.4.11
Pin versions and vet community content

Unpinned Galaxy content means a fresh CI checkout can silently pull a new major version and break your pipeline. Always pin in a committed requirements.yml. Before adopting a community role, check its maintenance status, stars, and open issues — you're inheriting its bugs and its security posture. For regulated environments, mirror trusted content into a private Automation Hub rather than pulling from the public Galaxy at runtime.

Galaxy gotchas

Roles ≠ collections: ansible-galaxy role install and ansible-galaxy collection install use different paths and syntaxes; a single requirements.yml can list both under roles: and collections:. Short module names may resolve to the wrong collection once multiple are installed — use FQCNs. Community quality varies wildly — a five-year-stale role may not support your OS. And installing without pinning is the top cause of "it worked yesterday" pipeline failures.

An app store for automation

Galaxy is an app store; collections are the apps (bundles of features), and roles are simpler single-purpose apps. Instead of coding a nginx installer yourself, you "download the app" someone already polished. And just like phone apps, you pin the version — you don't want an app to auto-update to a version that suddenly breaks your workflow the morning of a deploy.

13. Ansible Vault — Secrets

Store passwords, keys, and certs encrypted inside your repo, decrypted only at runtime.

Encrypt secrets
ansible-vault create secrets.yml          # create new encrypted file
ansible-vault edit secrets.yml            # edit it
ansible-vault encrypt_string 's3cr3t' --name db_password   # inline encrypted var
ansible-playbook site.yml --ask-vault-pass                 # prompt for the key
ansible-playbook site.yml --vault-password-file ~/.vault   # or read from a file
Vault protects at rest, not from your CI logs

Vault encrypts files in Git, but a careless debug task can print the decrypted value into pipeline logs. Use no_log: true on tasks that handle secrets. For dynamic secrets, integrate HashiCorp Vault or your cloud secrets manager instead of static vaulted files.

Why Ansible Vault exists

Automation needs secrets — DB passwords, API keys, TLS private keys, join tokens. But your playbooks live in Git, and plaintext secrets in Git are a breach waiting to happen (they persist in history forever, get cloned onto every laptop, and leak in CI). Vault lets you keep secrets in the same repo, next to the code that uses them, but encrypted at rest with AES-256. You get the convenience of everything-in-one-place without the exposure. The tradeoff versus a dedicated secrets manager: Vault secrets are static and rotate only when you re-encrypt them.

How Vault encryption and runtime decryption work

Vault encrypts a file's contents with AES-256 using a key derived from your vault password; an encrypted file starts with the header $ANSIBLE_VAULT;1.1;AES256 followed by the ciphertext as hex. At runtime you supply the password (--ask-vault-pass or --vault-password-file), Ansible decrypts the file in memory only, and the plaintext never touches disk on the control node or the target. You can encrypt whole files (like group_vars/prod/vault.yml) or just individual values inline with encrypt_string. Multiple keys are supported via vault IDs, so prod and dev secrets can use different passwords.

Encrypt a single value and see the ciphertext
ansible-vault encrypt_string 'S3cr3tP@ss' --name db_password
Paste this straight into a vars file
db_password: !vault |
          $ANSIBLE_VAULT;1.1;AES256
          66386439653236336462...<hex ciphertext>...3462
          3961393832...
Use it safely — note no_log
- name: Configure DB connection (secret must not leak to logs)
  ansible.builtin.template:
    src: db.conf.j2               # references {{ db_password }}
    dest: /etc/app/db.conf
    mode: "0600"
  no_log: true                    # suppress task output entirely
Run with the vault key, and set up vault IDs per env
ansible-playbook site.yml --vault-password-file ~/.vault_prod
# Multiple environments with distinct keys:
ansible-playbook site.yml \
  --vault-id dev@~/.vault_dev \
  --vault-id prod@prompt
Keep the vault password out of the repo

Encrypting secrets is pointless if the password sits next to them. Store the vault password file outside the repo (e.g. ~/.vault_prod, chmod 600), inject it in CI via a masked secret variable, and rotate it if anyone leaves the team. Separate keys per environment via vault IDs so a leaked dev key can't decrypt prod. For anything requiring rotation or auditing, graduate to HashiCorp Vault or a cloud secrets manager and pull secrets at runtime via a lookup.

Vault gotchas

Leaking via debug/loops: the biggest risk isn't the file, it's a task printing the decrypted value — add no_log: true. Merge conflicts on encrypted files are unresolvable (it's ciphertext) — encrypt values inline or keep vaulted files small and single-owner. Lost password = lost secrets, permanently — back up the key securely. git diff is useless on vaulted files; review the plaintext before encrypting. And check-mode/diff can still reveal secrets for templated files unless the task uses no_log.

A locked diary in your backpack

Vault is a locked diary you carry in the same backpack as your notebooks (the repo). Anyone who grabs the backpack sees a locked book, not your secrets. You open it only when you need it, using a key you keep separately — not tucked inside the same backpack. And if you shout the secret out loud after opening it (a debug task), the lock didn't help — that's why you stay quiet with no_log.

PatternWhat / why
Rolling updatesserial: 2 updates hosts in small batches for zero-downtime deploys
Delegationdelegate_to: localhost runs a task somewhere else (e.g., pull a host out of a load balancer before updating it)
Blocks + rescueblock/rescue/always = try/catch/finally for error handling

Zero-downtime rolling update
- hosts: web
  serial: 2                        # 2 hosts at a time
  tasks:
    - name: Remove from load balancer
      community.aws.elb_target: { state: absent, target: "{{ inventory_hostname }}" }
      delegate_to: localhost
    - name: Deploy new version
      ansible.builtin.apt: { name: "myapp={{ app_version }}", state: present }
    - name: Add back to load balancer
      community.aws.elb_target: { state: present, target: "{{ inventory_hostname }}" }
      delegate_to: localhost

Why these patterns exist

Basic playbooks assume a happy path: all hosts, all at once, everything succeeds. Production breaks those assumptions. You can't restart every web server simultaneously (that's an outage) — hence rolling updates with serial. You can't take a host out of rotation from the host itself while it's serving traffic — hence delegation. Long-running tasks would block the whole play — hence async. These patterns are how you go from "works in a demo" to "safe on a live fleet."

How serial, delegation, and async work under the hood

serial changes the play's batching: instead of running all tasks across all hosts, Ansible splits the host list into batches (e.g. 2 hosts, or 25%) and runs the entire play on batch 1 before starting batch 2 — so a failure in the first batch halts the rollout before it spreads. delegate_to runs a task's module on a different host than the one being configured, while keeping that host's variables (inventory_hostname still refers to the target) — perfect for "call the load balancer's API from localhost on behalf of this host." async + poll launches the module in the background on the target and returns a job ID; with poll: 0 it's fire-and-forget, and you check status later with the async_status module.

Async fire-and-forget + block/rescue rollback
- hosts: batch
  serial: "20%"                    # 20% of hosts per wave
  max_fail_percentage: 10          # abort the whole rollout if >10% fail
  tasks:
    - name: Kick off a long migration without blocking
      ansible.builtin.command: /opt/migrate.sh
      async: 3600                  # allow up to 1h
      poll: 0                      # don't wait — fire and forget
      register: migration

    - name: Do other work while it runs...
      ansible.builtin.debug: { msg: "migration launched as {{ migration.ansible_job_id }}" }

    - name: Now wait for it, checking every 15s
      ansible.builtin.async_status:
        jid: "{{ migration.ansible_job_id }}"
      register: job
      until: job.finished
      retries: 240
      delay: 15
Rolling batches visible in the recap
PLAY [batch] *******************  (hosts 1-2 of 10)
...
PLAY [batch] *******************  (hosts 3-4 of 10)
...    # each wave completes fully before the next starts
run_once for cluster-wide singletons

Some actions should happen exactly once across the whole batch, not per host — running a DB schema migration, or registering a deployment marker. Combine run_once: true with delegate_to so a single designated host performs it while the fact is available to all. This prevents the classic "10 hosts each ran the migration" disaster.

Pattern gotchas

serial resets fact scope per batch — facts gathered in a later batch aren't available to an earlier one. Delegation confuses variable context: inventory_hostname is still the target, but ansible_host/facts may reflect the delegate; use delegate_facts deliberately. Async without async_status leaves you blind to failures — a fire-and-forget task that dies is silently ignored unless you poll it. And max_fail_percentage is per-batch, evaluated after each wave.

Renovating a hotel one floor at a time

You don't shut the whole hotel to renovate (that's an outage). You do it floor by floor (serial): move guests off floor 3, renovate, move them back, then start floor 4. If a floor's renovation goes badly wrong, you stop before touching the rest (max_fail_percentage). Telling the front desk to reroute guests is done from the lobby, not from inside the room being painted (delegate_to). And a long paint job can dry overnight while you work elsewhere (async).

15. Ansible in CI/CD

Lint + run in a pipeline
# Lint every change (catches bad practices, not just syntax)
ansible-lint site.yml
# Dry-run against staging on PR, real run on merge:
ansible-playbook -i inventories/staging site.yml --check --diff
ansible-playbook -i inventories/prod    site.yml --vault-password-file "$VAULT_FILE"
Test with Molecule

Molecule spins up a container/VM, applies your role, and asserts the result — then checks idempotency by running twice and confirming zero changes on the second pass. Run it in CI so roles are proven before they touch real servers.

Why run Ansible from CI/CD at all

Running ansible-playbook from an engineer's laptop has three problems: it's unaudited (who ran what, when?), it's unreproducible (their laptop has a different Ansible version and stray local vars), and it's a bottleneck (only people with the vault password and SSH keys can deploy). Moving execution into a pipeline makes every change go through the same reviewed, version-controlled path: lint → dry-run → approval → apply, with logs and identity attached. The playbook becomes the deploy mechanism and the audit record.

How the pipeline stages map to Ansible features

A solid pipeline layers Ansible's own safety features into gates: syntax-check (--syntax-check) catches YAML/structure errors instantly; ansible-lint catches anti-patterns (bare command, missing names, deprecated syntax) that syntax-check misses; Molecule proves roles converge and are idempotent in a throwaway container; check-mode against staging (--check --diff) previews real changes on a PR without applying them; and only on merge does the pipeline run the real apply, reading the vault password from a masked CI secret. Idempotency is what makes re-running on every merge safe.

.gitlab-ci.yml — a staged Ansible pipeline
stages: [lint, test, dry-run, deploy]

lint:
  stage: lint
  script:
    - ansible-playbook site.yml --syntax-check
    - ansible-lint site.yml

molecule:
  stage: test
  script:
    - cd roles/nginx && molecule test    # converge + idempotence + verify

staging-plan:
  stage: dry-run
  script:
    - ansible-playbook -i inventories/staging site.yml --check --diff
  rules: [ { if: '$CI_PIPELINE_SOURCE == "merge_request_event"' } ]

prod-deploy:
  stage: deploy
  script:
    - echo "$VAULT_PASS" > .vault && chmod 600 .vault
    - ansible-playbook -i inventories/prod site.yml --vault-password-file .vault
  when: manual                               # require a human to click deploy
  rules: [ { if: '$CI_COMMIT_BRANCH == "main"' } ]
ansible-lint catching a real problem
site.yml:14: [command-instead-of-module] Use the 'service' module instead of 'command'
site.yml:22: [risky-file-permissions] File permissions unset or incorrect
Failed: 2 failure(s) — pipeline stops before deploy
Gate prod behind check-mode and a manual approval

The strongest, cheapest safety net: run --check --diff against staging on every merge request so reviewers see the exact diff, then require a when: manual click to apply to prod. This mirrors Terraform's plan/apply discipline. Inject the vault password from a masked CI variable, never commit it, and scope SSH keys to the CI runner only.

CI/CD gotchas

Secrets in logs: a failing task can echo secrets into the pipeline log — combine no_log with CI log masking. Non-deterministic runs: unpinned collections make CI diverge from local — pin in requirements.yml. Check-mode false positives: tasks depending on earlier real changes may report inaccurately in --check; mark read-only tasks check_mode: false. And host-key prompts hang non-interactive runners — pre-seed known_hosts or set the policy explicitly.

An assembly line with quality gates

Doing deploys from your laptop is like a chef tasting and shipping food straight from a home kitchen — no records, no second opinion. A CI pipeline is a restaurant line: the dish passes an inspector (lint), a test kitchen (Molecule), a "show the manager the plan" gate (check-mode on staging), and only then, with a manager's nod (manual approval), does it go out to customers (prod). Every plate is logged.

16. Ansible + Terraform — Better Together

A common, powerful pairing: Terraform builds the infrastructure, Ansible configures it.

In a container world, configuration shifts left

With Docker/Kubernetes, most "configuration" moves into the image build and Kubernetes manifests, so Ansible's role shrinks to bootstrapping nodes, managing non-containerized systems, and orchestration. It remains invaluable for the many workloads that aren't containerized.

Let each tool own its half — don't blur the boundary

The clean split is: Terraform owns what exists (VMs, VPCs, load balancers, DNS) and Ansible owns what's on it (packages, config files, services). Resist the temptation to shell out to Ansible from Terraform's provisioner "local-exec" for anything non-trivial — it couples the two lifecycles and makes terraform apply fail for configuration reasons. Instead, let Terraform tag instances, and let Ansible's dynamic inventory discover them on its own run. Two commands, two responsibilities, cleanly composable in CI.

Builders vs. movers

Terraform is the construction crew that pours the foundation and puts up the walls — it makes the house exist. Ansible is the moving crew that comes afterward to install the appliances, hang the pictures, and set the thermostat — it makes the house livable. You wouldn't ask the bricklayers to also arrange your furniture; each crew does the job it's good at, in order.

17. Execution Strategies & Forks

By default Ansible runs each task on all hosts before moving to the next task (the linear strategy). How it parallelizes and orders work is tunable — critical for large fleets and rolling deploys.

Strategy, forks, serial & throttle
- hosts: web
  strategy: free            # or linear (default), or host_pinned
  serial: "25%"             # roll out to 25% of hosts at a time
  tasks:
    - name: Heavy task, but cap concurrency
      ansible.builtin.command: /opt/migrate.sh
      throttle: 2           # never run this task on more than 2 hosts at once

# Global parallelism (ansible.cfg): how many hosts in parallel
# [defaults]
# forks = 50               # default is only 5 — raise it for big fleets
The default forks = 5 is the #1 speed limiter

Out of the box Ansible touches only 5 hosts at a time. On a 200-host fleet that's painfully slow. Raise forks (50–100 is common) in ansible.cfg — bounded by the control node's CPU/RAM and target SSH capacity. Combine with serial for safe, batched rollouts.

Why strategies and forks are tunable

The default lockstep-with-5-forks behavior is a safe, conservative choice for small fleets, but it's the wrong default for two opposite extremes. For large fleets you want more parallelism (raise forks) and often don't care about cross-host ordering (the free strategy). For sensitive rollouts you want less blast radius and strict ordering (serial batches on the linear strategy). Ansible exposes these knobs because "how fast and in what order" is a policy decision that differs per playbook, not something the engine can guess.

How strategy, forks, serial, and throttle interact

These four operate at different layers and compose:

  • forks (global, in ansible.cfg) — the size of the worker pool on the control node; the maximum number of hosts touched in parallel at any instant.
  • strategy (per play) — how those workers advance: linear keeps all hosts on the same task (barrier after each task); free lets each host sprint through all tasks independently; host_pinned keeps a host on one worker to reduce reconnects.
  • serial (per play) — batches the host list; the whole play completes on a batch before the next batch starts (independent of, and layered on top of, the strategy).
  • throttle (per task) — caps concurrency for one specific task below the global fork count, for tasks that hammer a shared resource (a license server, a shared DB).
Measure the impact of forks with the timer callback
# Slow: default 5 forks on 40 hosts
time ansible all -i inv -m ping
# Fast: bump forks for this run
time ANSIBLE_FORKS=50 ansible all -i inv -m ping
Difference is dramatic on wide fleets
# forks=5  : real  0m22.5s   (8 waves of 5)
# forks=50 : real  0m3.1s    (all 40 in one wave)
linear vs free — pick by whether ordering matters

Use linear (the default) whenever cross-host coordination matters: rolling updates, "don't start task N until all hosts finished task N-1," or gating on a health check. Use free for embarrassingly-parallel, independent work (patch 500 unrelated hosts as fast as possible) where one slow host shouldn't hold up the rest. free can finish far sooner but gives up any guarantee about relative ordering across hosts.

Execution gotchas

Cranking forks too high can exhaust control-node memory/CPU or trip target MaxStartups/SSH rate limits — scale up gradually and watch both ends. free + handlers is subtle: handler timing is no longer synchronized across hosts. serial multiplies runtime (each batch pays full play overhead) — balance safety against speed. And throttle only limits one task, not the play, so a shared resource can still be overwhelmed by another unthrottled task.

A group tour vs. a scavenger hunt

linear is a guided group tour: everyone stays together and the guide won't move to the next room until the whole group has seen this one. free is a scavenger hunt: each person races ahead at their own pace and finishes when they finish. forks is how many people you let into the museum at once, and serial is admitting the crowd in small groups so the museum never gets dangerously packed.

18. Advanced Jinja2 & Filters

Jinja2 is Ansible's expression engine. Filters transform data inline; tests check conditions; lookups pull external data. This is where dynamic playbooks come alive.

Filters, tests, and defaults
# Filters (piped transforms)
{{ users | map(attribute='name') | join(', ') }}      # extract & join
{{ config | to_nice_yaml }}                            # pretty YAML
{{ password | password_hash('sha512') }}              # hash a secret
{{ mylist | select('match', '^web') | list }}         # regex filter
{{ some_var | default('fallback') }}                   # safe default
{{ item | ternary('enabled', 'disabled') }}            # bool -> string

# Tests (in when:)
when: ansible_distribution_version is version('20.04', '>=')
when: my_var is defined and my_var is not none

# Lookups (pull external data at runtime)
{{ lookup('env', 'HOME') }}
{{ lookup('file', '/etc/hostname') }}
{{ lookup('aws_secret', 'prod/db/password') }}
Filters = an assembly line for data

A Jinja2 filter pipeline is like a factory line: raw data enters on the left, and each | is a station that transforms it — extract a field, filter rows, join into a string, hash it. By the time it reaches the right end, you've shaped raw variables into exactly the value a task needs, without writing procedural code.

Why Jinja2 is central to Ansible

Ansible's YAML is declarative and deliberately not a programming language — there are no for loops or if statements in the YAML itself. Jinja2 is the escape hatch that provides just enough computation to make playbooks dynamic without turning them into code: shape data with filters, branch with tests, and pull in external values with lookups. This keeps the structure declarative while letting values be computed. Almost every {{ }} you write is Jinja2, so mastering filters is the difference between rigid and adaptable playbooks.

How filters, tests, and lookups differ mechanically

Filters (value | filter) transform data and are evaluated on the control node during templating — they're pure functions of their input. Tests (value is test) return a boolean and are used in when: and conditionals. Lookups (lookup('plugin', args)) reach outside the playbook to fetch data at runtime — a file, an environment variable, a secrets manager — and, importantly, they run on the control node, not the target, which matters for security and for what paths/credentials are available. Filters and tests are stateless transforms; lookups have side effects (I/O).

A realistic data-shaping example
vars:
  servers:
    - { name: web-1, env: prod, cpu: 4 }
    - { name: web-2, env: prod, cpu: 8 }
    - { name: dev-1, env: dev,  cpu: 2 }

tasks:
  - name: Build a comma list of prod hostnames only
    ansible.builtin.debug:
      msg: >-
        {{ servers | selectattr('env','equalto','prod')
                   | map(attribute='name') | join(', ') }}

  - name: Total CPUs across all servers
    ansible.builtin.debug:
      msg: "{{ servers | map(attribute='cpu') | sum }}"

  - name: Safe default when an optional var is missing
    ansible.builtin.debug:
      msg: "{{ feature_flag | default(false) | ternary('on','off') }}"
Rendered results
ok: [localhost] => { "msg": "web-1, web-2" }
ok: [localhost] => { "msg": "14" }
ok: [localhost] => { "msg": "off" }
Debug complex expressions before embedding them

A gnarly filter chain that fails inside a template gives a cryptic error. Prototype it in a standalone debug task first (as above) until the output is exactly right, then drop it into the real template. For truly hairy logic, ansible-console lets you evaluate expressions interactively against a host.

Jinja2 gotchas

default(omit) vs default(''): use | default(omit) to drop an optional module argument entirely rather than passing an empty string. Type surprises: everything from the CLI arrives as a string — "3" > "20" is true lexically; cast with | int. Lookups run control-side, so lookup('file', ...) reads a file on your machine, not the target (use the slurp module for target files). Chained filters short-circuit on undefined unless you default early. And whitespace control ({%- -%}) is needed to keep rendered files clean.

A spreadsheet formula bar

Think of Jinja2 as the formula bar in a spreadsheet. The cells (variables) hold raw data; the formula (= FILTER(range) | JOIN(...)) turns them into the value you actually want to display, live, without you retyping it. Tests are the IF() that returns true/false, and lookups are like a formula that pulls a live value from another workbook.

19. Error Handling & Blocks

Production automation must handle failure gracefully. Ansible provides block/rescue/always (try/catch/finally), plus fine control over what counts as failure.

block / rescue / always + failure control
- name: Safe deployment with rollback
  block:
    - name: Deploy new version
      ansible.builtin.command: /opt/deploy.sh {{ version }}
  rescue:
    - name: Roll back on any failure
      ansible.builtin.command: /opt/deploy.sh {{ previous_version }}
    - name: Alert
      ansible.builtin.debug: { msg: "Deploy failed, rolled back" }
  always:
    - name: Always re-enable monitoring
      ansible.builtin.command: /opt/monitoring.sh enable

# Control what "failure" means:
- ansible.builtin.command: /opt/check.sh
  register: result
  failed_when: "'ERROR' in result.stdout"     # custom failure condition
  changed_when: result.rc == 2                 # custom "changed" condition
  ignore_errors: true                          # continue even if it fails
Design for partial failure

In a fleet, some hosts will fail mid-run. Use max_fail_percentage to abort a rollout if too many fail, any_errors_fatal: true to stop everything on first error when correctness demands it, and rescue blocks to leave systems in a known-good state. Never leave a host half-configured.

Why explicit error handling is non-negotiable

By default a failed task removes that host from the play and continues on the others — which is sometimes fine and sometimes catastrophic. If a deploy fails halfway, the host is now in a broken, half-configured state serving traffic. Error handling exists so you can decide, per situation, what "failure" means, whether to retry, whether to roll back, and whether one host's failure should stop the entire fleet. It's the difference between "the run errored" and "the run errored and left everything safe."

How Ansible decides success, failure, and change

Every task result carries flags the engine acts on: failed, changed, rc, stdout. By default a nonzero return code means failure. You override this with failed_when (a Jinja expression that redefines failure — e.g. treat rc=2 as OK, or fail on a string in stdout) and changed_when (redefine what counts as a change, crucial for making shell tasks honest). register captures the whole result dict for later tasks to inspect. block/rescue/always mirrors try/catch/finally: a failure anywhere in block jumps to rescue (where ansible_failed_task and ansible_failed_result are available), and always runs no matter what. retries/until loops a task until a condition holds.

Retry-until, then block/rescue with real diagnostics
- hosts: web
  any_errors_fatal: true          # one host failing aborts the whole play
  tasks:
    - name: Wait for the app port to come up (retry)
      ansible.builtin.wait_for:
        port: 8080
        timeout: 5
      register: portcheck
      retries: 12
      delay: 5
      until: portcheck is succeeded

    - name: Deploy with automatic rollback
      block:
        - name: Pull new release
          ansible.builtin.command: /opt/deploy.sh {{ version }}
        - name: Health check
          ansible.builtin.uri: { url: "http://localhost:8080/health", status_code: 200 }
      rescue:
        - name: Show why it failed
          ansible.builtin.debug:
            msg: "Failed task: {{ ansible_failed_task.name }} — {{ ansible_failed_result.msg | default('n/a') }}"
        - name: Roll back
          ansible.builtin.command: /opt/deploy.sh {{ previous_version }}
      always:
        - name: Re-enable monitoring no matter what
          ansible.builtin.command: /opt/monitoring.sh enable
Rescue path firing on a failed health check
TASK [Health check] ***********************************************
fatal: [web-1]: FAILED! => {"status": 503, "msg": "Status code was 503"}

TASK [Show why it failed] *****************************************
ok: [web-1] => { "msg": "Failed task: Health check — Status code was 503" }

TASK [Roll back] **************************************************
changed: [web-1]

TASK [Re-enable monitoring no matter what] ************************
changed: [web-1]
ignore_errors is a blunt instrument — prefer failed_when

ignore_errors: true swallows all failures including ones you didn't anticipate, hiding real problems. When you only want to tolerate a specific non-fatal outcome, use failed_when with a precise condition instead. Reserve ignore_errors for genuinely best-effort tasks, and always register the result so a later task can react.

Error-handling gotchas

Handlers don't run after a failure unless you pass --force-handlers — a host can fail with its restart handler never firing. rescue that itself fails aborts hard. changed_when: false is the right fix for read-only shell tasks that shouldn't ever report changed. any_errors_fatal vs max_fail_percentage: the former stops on the first failure, the latter tolerates a threshold — don't set both carelessly. And until loops still fail after exhausting retries, so wrap them if you need graceful handling.

A trapeze act with a safety net

block is the trapeze trick you're attempting. rescue is the safety net — if the acrobat slips, the net catches them and puts them safely back on the platform (rollback). always is the stagehand who turns the house lights back on whether the trick succeeded or failed. retries/until is the acrobat re-attempting the catch a few times before giving up. You plan the net before the show, not after someone falls.

20. Performance Tuning

Slow playbooks kill productivity. A handful of settings can turn a 20-minute run into 2 minutes.

SettingEffect
forks = 50More hosts in parallel (biggest single win)

A fast ansible.cfg
[defaults]
forks = 50
gathering = smart
fact_caching = jsonfile
fact_caching_connection = /tmp/ansible_facts
[ssh_connection]
pipelining = true
ssh_args = -o ControlMaster=auto -o ControlPersist=60s

Why Ansible playbooks get slow

Ansible's simplicity has a cost: every task is a round-trip over SSH, and by default it only talks to 5 hosts at a time. On a big fleet with a long playbook, that's thousands of serialized SSH operations. The slowness isn't the modules doing work — it's the connection overhead (opening SSH, copying the module, waiting) repeated over and over, plus fact-gathering on every play. Nearly all tuning targets one of two things: do more in parallel, or do fewer/cheaper round-trips.

How each lever reduces overhead

  • forks attacks serialization — more hosts in flight at once (the single biggest win on wide fleets).
  • pipelining attacks per-task round-trips — it pipes the module into the remote Python over the existing connection, removing the separate "copy file then execute" step (can cut task time 2–3×).
  • ControlPersist attacks reconnection — it keeps the SSH socket open between tasks so you pay the TCP/auth handshake once, not per task.
  • Fact caching attacks the setup tax — gathered facts are stored (jsonfile/redis) and reused across runs, so you skip re-gathering on every play.
  • gather_facts: false skips fact-gathering entirely when a play doesn't reference any facts.
Profile first — you can't optimize what you don't measure

  ansible-playbook -i inv site.yml

Here fact-gathering (18s) and one package task (12s) dominate — so enabling fact caching and pipelining, and raising forks, will help far more than micro-optimizing the 1-second tasks. Always profile before tuning.

The high-leverage trio

For most fleets, three changes deliver 80% of the speedup: (1) forks = 50, (2) pipelining = true, (3) ControlPersist=60s. Add fact caching if you gather facts and run frequently. Verify each change with the timer callback so you know it actually helped rather than assuming.

Performance gotchas

Pipelining needs no requiretty in sudoers or it errors — check target defaults. Over-high forks can exhaust control-node RAM or hit SSH server limits (MaxSessions, MaxStartups). Stale fact cache can make a play act on outdated facts after hardware changes — set a sensible TTL. Looping single-package installs is a classic slow spot — pass the whole list to the package module instead. And free strategy speeds runs but sacrifices ordering — don't use it where sequencing matters.

Checkout lines at a store

A slow playbook is a store with one open register (forks=5) serving a huge queue. Open more registers (raise forks) and the line moves in parallel. Keep each customer's lane open between items instead of re-scanning their loyalty card every time (ControlPersist). Skip re-asking regulars for their whole life story every visit (fact caching). And profile first — count where the line actually backs up before rearranging the store.

21. Dynamic Inventory Deep Dive

Static inventory files don't work when servers autoscale. Dynamic inventory plugins query the source of truth (cloud API, CMDB) live and group hosts automatically.

aws_ec2 dynamic inventory (inventory.aws_ec2.yml)
plugin: amazon.aws.aws_ec2
regions: [us-east-1]
keyed_groups:
  - key: tags.Environment       # creates groups like tag_Environment_prod
    prefix: env
  - key: tags.Role
    prefix: role
filters:
  instance-state-name: running
compose:
  ansible_host: private_ip_address
# use it: ansible-inventory -i inventory.aws_ec2.yml --graph

Why dynamic inventory is essential in the cloud

A static hosts.ini assumes the fleet is fixed and you know every IP. The cloud breaks both assumptions: autoscaling groups create and destroy instances continuously, IPs are ephemeral, and nobody hand-maintains a list of 200 machines that changes hourly. Dynamic inventory makes the cloud itself the source of truth — Ansible asks the provider "what exists right now?" at the start of every run, so a machine that autoscaled into existence five minutes ago is instantly manageable, and one that was terminated simply disappears from the inventory. No file edits, no drift between the list and reality.

How an inventory plugin resolves hosts at runtime

An inventory plugin (configured by a YAML file ending in a recognized suffix like .aws_ec2.yml) runs when Ansible starts. It authenticates to the source API, queries for resources matching your filters, and then builds the inventory dynamically: keyed_groups auto-creates groups from attributes (every instance tagged Environment=prod lands in a env_prod group), compose sets host variables from instance attributes (e.g. ansible_host = the private IP), and groups can define conditional group membership. The result is the same host/group/variable structure a static file would produce — just computed live instead of typed by hand. Caching (cache: true) avoids hammering the API on rapid successive runs.

Tags become your inventory — so tag deliberately

With dynamic inventory, your cloud tagging strategy is your inventory design. Standardize tags like Environment, Role, and App across all instances, and keyed_groups will hand you clean, automatic groups (env_prod, role_web). Enforce the tags at provisioning time (in Terraform) so no instance is ever untargetable.

Dynamic inventory gotchas

Credentials & permissions: the plugin needs read access to the cloud API (an IAM role/keys) — missing perms yield a silently empty inventory. Plugin must be enabled in ansible.cfg under [inventory] enable_plugins. The file must end with the right suffix (*.aws_ec2.yml) and start with plugin: or Ansible treats it as a static file. Stale cache can hide brand-new instances — disable caching for deploy pipelines that must see the latest. And public vs private IP: set compose: ansible_host to the address you can actually reach.

A live guest list vs. a printed one

A static inventory is a guest list printed last week — useless when people keep arriving and leaving. Dynamic inventory is a doorman with a live headcount: every time the party needs a decision, he looks around the room and reports exactly who's here right now, sorted into groups by the badges (tags) they're wearing. New arrivals are counted automatically; people who left are simply no longer on the list.

22. Custom Modules & Plugins

When no existing module fits, write your own. Modules are the "verbs"; plugins extend Ansible's core behavior (lookups, filters, callbacks, connections).

A minimal custom module (Python) — library/my_check.py
#!/usr/bin/python
from ansible.module_utils.basic import AnsibleModule

def main():
    module = AnsibleModule(argument_spec=dict(
        path=dict(type='str', required=True),
    ))
    import os
    exists = os.path.exists(module.params['path'])
    # modules communicate via JSON on stdout; changed= drives idempotency
    module.exit_json(changed=False, exists=exists)

if __name__ == '__main__':
    main()

The profile_tasks callback shows how long each task took (find your slow spots); timer shows total runtime. Community callbacks can post results to Slack or write JSON logs. Enable in ansible.cfg: callbacks_enabled = profile_tasks, timer.

Why write custom modules and plugins

Ansible ships thousands of modules, but your organization has systems no public module knows about — an internal API, a bespoke appliance, a proprietary database. You could shell out to a CLI with the command module, but you'd lose idempotency, check-mode support, and clean error reporting. A custom module lets that internal system be a first-class Ansible citizen: idempotent, describable in YAML, supporting --check, and returning structured data. Plugins extend a different axis — not "new things to do" but "new ways Ansible itself behaves" (how it connects, how it templates, how it reports).

How a module communicates with the engine

A module is just a program Ansible ships to the target and runs. The contract is entirely over stdin/stdout as JSON: Ansible passes the task arguments in, and the module must print a JSON result and exit. AnsibleModule (from module_utils.basic) handles the boilerplate — parsing arguments against an argument_spec (with types, required, defaults, and validation), supporting check mode, and providing exit_json(changed=..., ...) and fail_json(msg=...). The critical field is changed: the module itself must implement the check-then-act pattern and report whether it actually changed anything — that's what makes your module idempotent and what drives handler notifications.

An idempotent, check-mode-aware module — library/manage_flag.py
#!/usr/bin/python
from ansible.module_utils.basic import AnsibleModule
import os

def main():
    module = AnsibleModule(
        argument_spec=dict(
            path=dict(type='str', required=True),
            state=dict(type='str', default='present',
                       choices=['present', 'absent']),
        ),
        supports_check_mode=True,          # honor --check
    )
    path = module.params['path']
    want_present = module.params['state'] == 'present'
    exists = os.path.exists(path)

    # check-then-act: only "change" if reality differs from desired state
    changed = (want_present and not exists) or (not want_present and exists)

    if changed and not module.check_mode:
        if want_present:
            open(path, 'a').close()        # create the flag file
        else:
            os.remove(path)                # remove it

    module.exit_json(changed=changed, path=path, state=module.params['state'])

if __name__ == '__main__':
    main()

Support check mode and return structured data

A production-grade custom module declares supports_check_mode=True and skips side effects when module.check_mode is set, so it works with --check --diff like built-ins. It validates inputs via argument_spec (never trust raw params), reports an accurate changed, fails with a clear fail_json(msg=...), and returns useful data other tasks can register. Add a DOCUMENTATION/EXAMPLES block so ansible-doc works.

Custom module gotchas

Blindly reporting changed=True defeats the whole point — implement real state checking. Printing anything but the final JSON to stdout corrupts the result parsing (debug to stderr or via the module's return data). Runs in remote Python, so any third-party library it imports must exist on the target, not just the control node. Prefer a module over a plugin unless you're truly changing Ansible's behavior — new lookups/filters/callbacks are for extending the engine, not for doing configuration work.

Teaching a robot a new chore

Built-in modules are chores the robot already knows ("install a package," "copy a file"). A custom module teaches it a brand-new chore for your household's quirky appliance. The key lesson you must include: "before you act, check whether it's already done." A well-taught robot glances first and only acts if needed — so telling it twice is harmless. Plugins, by contrast, don't teach new chores; they change how the robot gets around the house or writes its report.

Why package your own collections

Once you have more than a handful of roles and custom modules, copy-pasting them between repos creates drift: three teams end up with three slightly-different "nginx" roles and no way to ship a fix to all of them. Packaging your reusable automation as an internal, versioned collection solves this the way a private library solves code reuse. Version with SemVer and gate releases with tests

Treat a collection like any published library: SemVer the version, keep a CHANGELOG, run ansible-lint and Molecule (§26) in CI on every change, and only publish a new version when tests pass. Host it on a private Automation Hub so builds don't depend on the public internet, and pin exact versions in consumers' requirements.yml so an internal release never surprises a downstream pipeline.

Collection-building gotchas

Forgetting to bump version means build overwrites the same tarball and caches serve stale content. Breaking changes on a minor bump violate SemVer and break consumers who allowed >= ranges. Missing DOCUMENTATION blocks leave ansible-doc empty. Wrong namespace/name in galaxy.yml makes FQCN references fail confusingly. And bundling untested roles just distributes bugs faster — test before you publish.

Shipping your recipes as a published cookbook

Your team's roles and modules are handwritten recipe cards passed around the kitchen — some copies have errors, nobody knows which is current. A collection is publishing them as a proper cookbook with an edition number (version). When you fix a recipe, you release a new edition; other kitchens choose when to buy it. Everyone cooks from the same tested, numbered book instead of a drawer of conflicting index cards.

24. Testing Roles with Molecule

Untested roles break in production. Molecule spins up a real container/VM, applies your role, verifies the result, and — crucially — checks idempotency.

Molecule workflow
pip install molecule molecule-plugins[docker]
cd roles/nginx
molecule init scenario                # scaffold molecule/default/
molecule test                         # full sequence: create→converge→idempotence→verify→destroy
molecule converge                     # just apply (fast dev loop)
molecule login                        # shell into the test container to debug

Why role testing needs Molecule specifically

You can eyeball a role and think it works, but three things routinely break silently: it fails on a different OS than you developed on, it isn't actually idempotent (reports changes on the second run), and a refactor quietly breaks a previously-working path. Manual testing on a real server is slow, pollutes that server, and doesn't get run consistently. Molecule turns role testing into a repeatable, automated pipeline that spins up a clean, disposable environment every time — so tests are reproducible and can run in CI on every commit, catching regressions before they reach real hosts.

How the Molecule test sequence works

molecule test runs a fixed lifecycle, and each phase checks something specific:

  1. create — provisions a fresh container/VM from a clean image (the driver, usually Docker).
  2. converge — runs a small playbook that applies your role to that instance. This proves the role runs.
  3. idempotence — runs converge again and fails the test if the second run reports any changed. This is the phase you can't easily do by hand and the reason Molecule exists.
  4. verify — runs assertions (Ansible assert tasks, or Testinfra) to check the resulting state: the service is running, the config contains the right line, the port is open.
  5. destroy — tears the instance down, leaving no residue.
molecule/default/verify.yml — assert the end state
- name: Verify nginx role produced the right state
  hosts: all
  tasks:
    - name: nginx service is running and enabled
      ansible.builtin.service_facts:
    - ansible.builtin.assert:
        that:
          - "'nginx.service' in ansible_facts.services"
          - "ansible_facts.services['nginx.service'].state == 'running'"

    - name: config contains the tuned worker count
      ansible.builtin.command: grep -q "worker_processes 4" /etc/nginx/nginx.conf
      changed_when: false
The idempotence phase catching a non-idempotent role
--> Scenario: 'default'
--> Action: 'converge'   ... changed=3   ok
--> Action: 'idempotence'
    Idempotence test failed because of the following tasks:
    * [instance] => Deploy config      # reported changed on the 2nd run!
--> ERROR: Idempotence test failed.

That failure is Molecule earning its keep: a command task with no changed_when reported changed on the second pass, so the role isn't truly idempotent — a bug you'd never notice by running it once.

Fast dev loop: converge then login

Don't run the full molecule test on every edit — it destroys and recreates the container each time. While developing, use molecule converge to re-apply the role to the existing instance (fast), and molecule login to shell in and inspect what actually happened. Run the full test sequence (which includes destroy/recreate and idempotence) before you commit and in CI.

Molecule gotchas

Containers ≠ full VMs: systemd, kernel modules, and some services behave differently in a container — test on an image close to production, or use a VM driver for systemd-heavy roles. Skipping the idempotence phase (or molecule converge only) defeats the main benefit. Verify with assertions, not just "it didn't error" — a role can converge cleanly yet produce the wrong config. And test the OSes you actually run by defining multiple platforms in molecule.yml, not just your laptop's distro.

A crash-test lab for your role

Molecule is a crash-test facility for cars (your role). It builds a fresh test car (create), drives it (converge), then drives the same car again to prove the second drive changes nothing new (idempotence), inspects the dashboard against a checklist (verify), and finally scraps the test car so the next test starts fresh (destroy). You'd never ship a car design tested only once in your driveway — you run it through the lab, repeatedly and automatically.

25. Network & Cloud Automation

Ansible isn't just for servers — it manages network devices (Cisco, Juniper, Arista) and orchestrates cloud resources through provider collections.

Network device + cloud orchestration
# Configure a Cisco switch (agentless, over SSH/API)
- hosts: switches
  gather_facts: false
  tasks:
    - cisco.ios.ios_config:
        lines: ["vlan 100", "name web-tier"]

# Orchestrate AWS (Ansible can provision too, though Terraform is preferred for that)
- hosts: localhost
  tasks:
    - amazon.aws.ec2_instance:
        name: web-1
        instance_type: t3.micro
        image_id: ami-0abc123
        tags: { Environment: prod }
Provision vs configure — the right tool

For provisioning cloud infra, Terraform is usually the better choice (state, plan, drift detection). Ansible shines at configuring what runs on those resources and at network device automation where it's a leader. Many teams use both: Terraform builds, Ansible configures (see §16).

Why Ansible reaches beyond servers

The same agentless model that makes Ansible great for servers makes it uniquely suited to network gear: you can't install an agent on a Cisco switch or a firewall, but you can reach its SSH/API. Before automation, network changes were typed by hand into each device's CLI — error-prone, unauditable, and impossible to do consistently across a hundred switches. Ansible brings the same "declare the desired config, apply it everywhere, keep it in Git" discipline to network and cloud resources that it brings to servers. It became a leader in network automation precisely because it needs nothing installed on the device.

How network and cloud modules differ from server modules

Two important mechanical differences. Network modules use special connection types — network_cli (drives the device's CLI over SSH) or httpapi/netconf (drives its API) instead of the normal SSH-and-ship-Python model, because network OSes don't have a general-purpose Python you can run modules on. You typically set gather_facts: false and run the play against the device from the control node. Cloud modules mostly run on localhost (or a bastion) and call the provider's API — the "managed host" is the cloud API endpoint, not a server. Both are still idempotent: the module reads current device/cloud state and only pushes changes that are needed.

Network config with the right connection + idempotency
- name: Manage switch VLANs
  hosts: switches
  gather_facts: false
  connection: ansible.netcommon.network_cli    # CLI over SSH, not module-shipping
  vars:
    ansible_network_os: cisco.ios.ios
  tasks:
    - name: Ensure VLAN 100 exists (idempotent — no change if already present)
      cisco.ios.ios_vlans:
        config:
          - name: web-tier
            vlan_id: 100
        state: merged

    - name: Save running-config to startup-config
      cisco.ios.ios_command:
        commands: ["write memory"]
Run it and confirm idempotency
ansible-playbook -i network.ini switch-vlans.yml
ansible-playbook -i network.ini switch-vlans.yml   # second run
Second run makes no changes
PLAY RECAP ********************************************************
sw-core-1 : ok=2  changed=0  unreachable=0  failed=0
# VLAN 100 already existed -> the module recognized it and changed nothing
Use the resource modules and merged/replaced states

Modern network collections provide resource modules (like ios_vlans, ios_interfaces) that model config as structured data with explicit states: merged (add/update), replaced (make this section exactly match), overridden (make the whole config match), deleted. Prefer these over raw ios_command — they're idempotent and let you manage config declaratively instead of sending blind CLI lines.

Network/cloud gotchas

Wrong connection type is the #1 error: forgetting connection: network_cli/ansible_network_os makes Ansible try to ship Python to a switch and fail. gather_facts: true on network devices errors (no remote Python) — set it false. Raw ios_command is not idempotent — it re-sends lines every run; use resource modules. Cloud API rate limits and credentials bite when running on localhost — throttle and scope IAM. And "config applied" ≠ "config saved" — many devices need an explicit save (write memory) to survive reboot.

One universal remote for the whole building

Servers, switches, firewalls, and cloud accounts all speak different "languages," but Ansible is a universal remote that knows the right buttons for each. It doesn't need to install anything inside the TV, the thermostat, or the garage door — it just needs to reach each one and speak its protocol (SSH CLI for switches, API calls for the cloud). You describe the setting you want once, and it presses the correct buttons on every device.

26. AWX / Ansible Automation Platform

Running playbooks from laptops doesn't scale or audit. AWX (open source) and Ansible Automation Platform (Red Hat's supported product) add a web UI, RBAC, scheduling, secrets, and an API.

FeatureWhy it matters
Web UI + RBACNon-experts can run approved jobs safely; who-ran-what is audited
Job templatesParameterized, reusable runs with surveys
SchedulingRun playbooks on a cron (patching windows, compliance)
Credential vaultCentral, encrypted secrets — not on anyone's laptop
REST API + webhooksTrigger automation from CI/CD or events
WorkflowsChain job templates with branching/approval gates
Graduate from CLI to a control plane

Ad-hoc CLI runs are fine for learning and small teams. Once multiple people, environments, and schedules are involved, move to AWX/AAP so automation is centralized, audited, access-controlled, and API-driven — the same maturity jump as going from laptop terraform apply to CI-driven applies.

Why a control plane replaces laptop runs

Running playbooks from laptops fails in predictable ways as a team grows: SSH keys and vault passwords get copied onto every engineer's machine (a security liability), there's no record of who ran what against prod, everyone's laptop has slightly different Ansible versions and local vars (non-reproducible), and only "the Ansible people" can deploy (a bottleneck). AWX (the open-source upstream) and Ansible Automation Platform (Red Hat's supported edition) solve this by making a server the single place automation runs — with a UI, an API, centralized credentials, role-based access control, and a full audit trail.

How AWX executes jobs

AWX ties together four concepts. A project syncs your playbooks from Git. An inventory is static or dynamically synced from the cloud. Credentials (SSH keys, vault passwords, cloud tokens) are stored encrypted in AWX and injected into runs at execution time — so they never live on a laptop. A job template binds a playbook + inventory + credentials + variables into a runnable, parameterized unit; running it launches a job inside an isolated execution environment (a container image with pinned Ansible and collections), streams live output to the UI, and records the result. Workflows chain job templates with success/failure branching and approval gates. Everything is also exposed over a REST API, so CI systems and webhooks can trigger jobs programmatically.

Launch a job template via the AWX REST API
# Trigger a deploy from CI/CD without SSH keys on the runner
curl -s -X POST \
  -H "Authorization: Bearer $AWX_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"extra_vars": {"app_version": "1.4.2"}, "limit": "role_web"}' \
  https://awx.example.com/api/v2/job_templates/42/launch/
AWX returns a job id you can poll for status
{ "job": 137, "status": "pending",
  "url": "/api/v2/jobs/137/" }
# GET /api/v2/jobs/137/  -> status transitions to running, then successful/failed
Store credentials in AWX, not on runners

The biggest security win of AWX/AAP is centralized credential management: SSH keys, vault passwords, and cloud tokens live encrypted in the platform and are injected into jobs at runtime, scoped by RBAC. CI runners and engineers trigger jobs by reference (a job template id + a token) and never handle the secrets themselves. Combine with surveys for safe, parameterized self-service and with schedules for unattended patching windows.

AWX/AAP gotchas

AWX is the unsupported upstream — fast-moving and self-managed; production shops that need support run Red Hat AAP. Execution environments must include your collections — a job fails if the EE image lacks a collection your playbook imports (build a custom EE with ansible-builder). RBAC misconfiguration can let the wrong team run prod jobs — scope organizations, teams, and job-template permissions deliberately. And project sync must be triggered (or set to auto-update) or AWX runs stale playbooks from its last sync.

An air-traffic control tower for automation

Running from laptops is like every pilot taking off whenever they feel like it, with no log and their own private runway. AWX is the control tower: one authority that holds the keys, schedules the flights, records every takeoff, and lets approved people request a flight through a form (job template) without ever touching the cockpit controls directly. Same planes (playbooks), but now coordinated, logged, and safe.

27. Best Practices — the checklist

Production Ansible checklist
  • Prefer real modules over shell/command; keep everything idempotent.
  • Structure everything as roles; keep playbooks thin.
  • Encrypt all secrets with Vault; add no_log: true on sensitive tasks.
  • Pin collection/role versions in requirements.yml.
  • ansible-lint + --check --diff in CI; test roles with Molecule.
  • Use serial + LB delegation for zero-downtime rolling updates.
  • Name every task clearly — names are your logs and documentation.
  • Separate inventories per environment (staging/prod).

Why these practices matter, not just what they are

Each checklist item exists because a real failure taught the community a lesson. Modules over shell preserves idempotency and check-mode; a fleet of shell tasks can't be safely re-run or dry-run. Thin playbooks, fat roles is how automation stays reusable and testable as it grows past one project. Vault + no_log keeps secrets out of both Git and CI logs — leaking either is a breach. Pinning versions is what makes a run today reproduce next month. Lint + check-mode + Molecule catch mistakes before they touch production. Serial + LB delegation turns a risky big-bang deploy into a safe, reversible rollout. Named tasks turn opaque logs into readable audit trails. Per-environment inventories prevent the worst incident of all: running a staging change against prod.

A production project layout tying the practices together
ansible.cfg                 # forks, pipelining, ControlPersist (perf)
requirements.yml            # pinned collections + roles (reproducible)
inventories/
  staging/hosts.ini
  prod/hosts.ini            # separate per environment
group_vars/
  all/vault.yml             # encrypted secrets
site.yml                    # thin: maps host groups -> roles
roles/
  nginx/{tasks,handlers,templates,defaults,molecule}/   # tested role
.gitlab-ci.yml              # lint -> molecule -> check-mode -> manual apply
Adopt incrementally — don't boil the ocean

You don't need every practice on day one. A pragmatic order: (1) get everything into Git and name your tasks; (2) replace shell tasks with real modules for idempotency; (3) refactor into roles; (4) add Vault for secrets; (5) add lint + check-mode to CI; (6) add Molecule tests; (7) move execution to AWX. Each step pays off on its own, so you can stop and stabilize at any point.

A pilot's preflight checklist

These best practices are a preflight checklist. Each item looks minor, but every one was added to the list because skipping it once caused a crash somewhere. Experienced pilots don't skip items because they're experienced — they run the list because they know how the accidents happen. Treat your Ansible checklist the same way.

28. Troubleshooting Playbook

"UNREACHABLE" / SSH failures

Check connectivity and auth: ansible host -m ping -vvv. Verify ansible_user, the SSH key, and that the host is in the inventory. First connection may need host-key acceptance.

"changed" every run on a shell task

The task isn't idempotent. Add creates=/removes=, a when: guard, or changed_when: — or switch to a proper module.

Variable has an unexpected value

It's variable precedence. Run with -e to force, or trace with a debug task. Consolidate where the var is defined (defaults vs group_vars).

"Missing sudo password"

Add --ask-become-pass (or -K), or configure passwordless sudo for the ansible user on managed nodes.

Why a systematic debugging method beats guessing

Ansible failures usually come from one of a few layers — connectivity, privilege, variables, or idempotency — and each has a distinct signature in the output. Guessing wastes time; reading the failure signature points you straight at the layer. The two highest-value tools are verbosity (-v through -vvvv, which progressively reveals the SSH command, the module arguments, and the raw JSON result) and debug (to print a variable's actual value at the moment of failure). Almost every mystery resolves once you can see the exact command Ansible ran and the exact value a variable held.

A debugging toolkit for the common failure layers
# Connectivity layer: see the actual SSH invocation and auth
ansible host -m ping -vvvv

# Variable layer: print what a var really resolves to, and where vars came from
ansible-playbook site.yml -e debug_var=app_port --tags never   # or add a debug task
ansible-inventory -i inventories/prod --host web-1

# Structure layer: validate before running
ansible-playbook site.yml --syntax-check
ansible-lint site.yml

# Idempotency layer: run twice; the second run should be changed=0
ansible-playbook site.yml && ansible-playbook site.yml

# Step through interactively, or start at a specific task
ansible-playbook site.yml --step
ansible-playbook site.yml --start-at-task "Deploy site config"
Drop-in debug task to inspect state mid-play
- name: Show a variable and a registered result
  ansible.builtin.debug:
    var: app_port

- name: Fail loudly with context if a precondition isn't met
  ansible.builtin.assert:
    that: app_port | int > 0
    fail_msg: "app_port resolved to '{{ app_port }}' — check group_vars precedence"
Read the failure output bottom-up, then raise verbosity

The most useful line is usually the fatal: message and the msg/stderr in the JSON right above the recap. If that's not enough, re-run the single failing host with --limit host -vvv to see the exact remote command and its raw output. Escalate verbosity only as needed — -vvvv is noisy but shows the full connection plumbing when nothing else explains an UNREACHABLE.

Debugging gotchas

Verbose output can leak secrets — avoid -vvvv on tasks handling vaulted data, and keep no_log on. --check can mislead for tasks that depend on earlier real changes — a "failure" in check-mode may be a false alarm. An empty/odd variable is almost always precedence (§8) — trace it with ansible-inventory --host rather than guessing. And UNREACHABLE ≠ failed: it means Ansible never got in (SSH/DNS/key), so debug the connection, not the task.

A doctor's differential diagnosis

Troubleshooting Ansible is like a doctor narrowing down symptoms. "UNREACHABLE" is like "the patient never showed up" — check the door (SSH), not the treatment. "Changed every run" is a chronic condition (non-idempotent shell). "Wrong variable value" is a lab-result mix-up (precedence). You don't prescribe randomly; you read the symptom, order the right test (-vvv, debug, ansible-inventory), and treat the actual cause.
