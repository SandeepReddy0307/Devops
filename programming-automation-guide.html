Programming & Automation for DevOps

DevOps is automation, and automation is code. Learn the three languages that matter most — Bash for glue, Python for automation, Go for tools — plus the engineering practices that make your scripts production-grade.

📖 How to read this guide

Each concept: what it is, why it matters for DevOps, real code, and ★ best practice. This builds on the Linux guide (where Bash lives) and powers everything in Ansible, Terraform, and CI/CD.

1. Why DevOps Engineers Code

The line between "ops" and "software engineer" has vanished. Modern infrastructure is code, pipelines are code, and the difference between a good and a great DevOps engineer is often the ability to automate anything.

If you do it twice, script it

The DevOps mindset: any task you do manually more than a couple of times is a candidate for automation. Manually checking 20 servers? Write a script. Copying files the same way each release? Automate it. Coding turns hours of error-prone clicking into a reliable command you run in seconds — and it documents the process at the same time. This is the core skill that scales you.

Why this discipline exists. Manual operations don't just waste time — they drift. Two engineers doing "the same" deploy by hand will do it slightly differently, and those small differences are where outages hide. Code makes the process deterministic: the same inputs produce the same actions every time. It also turns tribal knowledge ("ask Priya, she knows how to restart the cache") into a reviewable, versioned artifact that survives people leaving the team.

How it pays off under the hood. Automation compounds. A script you write once runs thousands of times, so a five-minute investment saves hundreds of hours across a team. More importantly, code is auditable: every change goes through version control and review, so when something breaks you can see exactly what changed and roll it back. Manual work leaves no such trail.

The toil-vs-engineering tradeoff

Google's SRE book frames this as a budget: time spent on toil (repetitive manual work) is time not spent on engineering (building things that reduce future toil). If more than ~50% of your week is toil, you're falling behind — the fix is almost always to write code that eliminates the repetitive part.

Worked example: the same task, manual vs scripted
# Manual: SSH into each of 3 hosts, run uptime, eyeball the result — every morning.
# Scripted: one command, consistent output, ready to schedule on cron.
for host in web-1 web-2 db-1; do
  echo "== $host =="
  ssh "$host" 'uptime; df -h / | tail -1'
done
Output
== web-1 ==
 09:14:02 up 42 days,  3:11,  load average: 0.14, 0.09, 0.05
/dev/root        49G   18G   31G  37% /
== web-2 ==
 09:14:03 up 42 days,  3:10,  load average: 0.22, 0.18, 0.11
/dev/root        49G   21G   28G  43% /
== db-1 ==
 09:14:04 up 88 days,  1:02,  load average: 0.51, 0.44, 0.40
/dev/root        99G   77G   22G  78% /
Common mistakes when you start automating
  • Automating a broken process. If the manual steps are wrong, the script just makes them wrong faster. Fix the process first, then encode it.
  • No dry-run / no logging. An unattended script that acts silently is scary. Add a --dry-run mode and log what it does.
  • One-off scripts on a laptop. If it's not in version control, it doesn't exist — it'll be lost or drift out of sync.
Mental model

Think of yourself as a manager delegating to a very literal, very fast intern (the computer). Anything you can describe as precise steps, you can hand off. Your job shifts from doing the task to describing it well enough that the machine does it reliably forever.

2. Choosing a Language

Three languages cover almost all DevOps work. Knowing when to reach for each is half the skill.

LanguageSweet spotReach for it when
BashGluing commands togetherShort scripts, wrapping CLI tools, quick automation (<100 lines)
PythonSerious automation & toolingLogic, APIs, cloud SDKs, data processing, anything beyond simple glue
GoFast, distributable toolsCLI tools, controllers, high-performance daemons (K8s/Docker are Go)
The rule of thumb

Start in Bash. When it exceeds ~50-100 lines, has real logic, or needs error handling and data structures, rewrite in Python. When you need a single compiled binary, high performance, or you're building cloud-native tooling, use Go. Most DevOps engineers are strongest in Python, competent in Bash, and reach for Go for tools.

Why three languages, not one. Each sits at a different point on the tradeoff between speed of writing and robustness of running. Bash is instant to write but has no real data structures and fails in surprising ways at scale. Python trades a little startup cost for real types, libraries, and error handling. Go trades slower development (you must compile, handle every error explicitly) for a fast, dependency-free binary. You pick based on how long the code will live and who runs it.

How the runtime differences drive the choice. Bash shells out to other programs for everything — it's a coordinator, not a computer. Python runs on an interpreter that's preinstalled almost everywhere, so no build step, but the target machine needs Python and your dependencies. Go compiles ahead-of-time to native machine code with the runtime baked in, so the artifact is a single file that needs nothing installed — which is exactly why you download kubectl as one binary, not a pile of scripts.

Worked example: the same idea, escalating in complexity
# Bash — perfect for a 5-line glue task:
kubectl get pods -o name | wc -l

# But add retries, JSON parsing, and Slack alerts, and Bash gets ugly fast.
# That is your signal: the task has outgrown glue and wants Python.
The same task once it has real logic
import subprocess, json
out = subprocess.run(["kubectl", "get", "pods", "-o", "json"],
                     capture_output=True, text=True, check=True)
pods = json.loads(out.stdout)["items"]
not_ready = [p["metadata"]["name"] for p in pods
             if p["status"]["phase"] != "Running"]
print(f"{len(not_ready)} pods not running: {not_ready}")
Output
2 pods not running: ['api-7d9f-crash', 'worker-55b-pending']
Common mistakes when choosing
  • Staying in Bash too long. A 400-line Bash script juggling arrays and JSON is a maintenance nightmare — the sunk-cost trap. Rewrite earlier than feels comfortable.
  • Reaching for Go too early. A quick internal script doesn't need a compile step and a repo. Go shines for tools other people run, not throwaways.
  • Ignoring the audience. If ops folks must edit it, a readable Python script beats a clever Go binary they can't change.
Mental model

Bash is a duct-tape — great for quickly joining two things. Python is a power drill — the general-purpose tool you'll use most. Go is a machined part — more effort to make, but rock-solid and shippable. Match the tool to how long the thing needs to last and who has to use it.

3. Bash for Automation

Bash is the glue of Linux. It excels at stringing commands together, but it's easy to write fragile scripts — so structure matters (deep patterns are in the Linux scripting section).

Bash essentials for DevOps
#!/usr/bin/env bash
set -Eeuo pipefail                # fail fast, fail loud

# Variables & command substitution
REGION="${AWS_REGION:-us-east-1}"        # default if unset
COUNT=$(kubectl get pods --no-headers | wc -l)

# Loop over command output safely
while IFS= read -r pod; do
  echo "Checking $pod"
done < <(kubectl get pods -o name)

# Conditionals
if kubectl get deploy myapp &>/dev/null; then
  echo "exists"
else
  echo "missing"; exit 1
fi

Why Bash exists. Bash isn't really a programming language — it's a command orchestrator. Its whole reason for being is to launch other programs, wire their input and output together with pipes, and react to their exit codes. That's why on Linux everything is a small program (ls, grep, awk, kubectl) and Bash is the glue that composes them into workflows.

How command substitution and process substitution work. $(...) runs a command in a subshell, captures its stdout, strips trailing newlines, and pastes the text in place. Process substitution <(...) is different: it runs the command and hands your loop a file descriptor (like /dev/fd/63) to read from. That matters because piping into a while loop (cmd | while read) runs the loop in a subshell, so variables you set inside are lost. Using while read ... < <(cmd) keeps the loop in the current shell, so your variables survive.

Why IFS= read -r is the safe reading idiom

IFS= stops the shell from trimming leading/trailing whitespace and splitting on it, so lines with spaces stay intact. -r stops backslashes from being interpreted as escapes. Together they mean "give me the line exactly as it is." Skip them and filenames with spaces or backslashes silently corrupt.

Worked example: variable scope pitfall vs the fix
#!/usr/bin/env bash
count=0
# WRONG: the pipe runs the loop in a subshell — count resets to 0 after.
printf 'a\nb\nc\n' | while IFS= read -r x; do count=$((count+1)); done
echo "piped count = $count"

# RIGHT: process substitution keeps the loop in this shell.
count=0
while IFS= read -r x; do count=$((count+1)); done < <(printf 'a\nb\nc\n')
echo "procsub count = $count"
Output
piped count = 0
procsub count = 3
Common Bash mistakes
  • Unquoted variables. rm $file with file="my report.txt" deletes two files. Always rm "$file".
  • Parsing ls. for f in $(ls) breaks on spaces and newlines. Use globs (for f in *) or find -print0.
  • Piping into while. Loses variables set inside the loop (subshell scope), as shown above.
Mental model

Bash is a conveyor belt in a factory. Each station is a separate machine (a program); the belt (pipes) carries text between them; and you (the script) decide the order and check whether each machine reported success. Bash itself doesn't do the manufacturing — it moves parts between machines.

4. Robust Bash Patterns

Production-grade script skeleton
#!/usr/bin/env bash
set -Eeuo pipefail
trap 'echo "Error on line $LINENO" >&2' ERR
trap 'rm -f "${TMP:-}"' EXIT          # always clean up

log() { printf '%s [%s] %s\n' "$(date +%FT%T)" "$1" "${*:2}"; }

main() {
  [[ $# -ge 1 ]] || { echo "usage: $0 <env>"; exit 1; }
  local env="$1"
  TMP="$(mktemp)"
  log INFO "deploying to $env"
  # ... work ...
}
main "$@"
Always: strict mode + ShellCheck

Begin every script with set -Eeuo pipefail and lint with shellcheck. These two habits eliminate the vast majority of shell bugs (unset variables, silent failures, word-splitting). Quote all variables ("$var"). When a Bash script starts needing arrays of structured data or complex logic, that's your signal to switch to Python.

Why strict mode exists and what each flag actually changes. By default Bash is dangerously forgiving — it keeps running after errors, treats typo'd variables as empty strings, and only reports the exit code of the last command in a pipeline. Strict mode flips those defaults so failures surface immediately instead of silently producing wrong results:

  • set -e — exit the moment any command returns non-zero, instead of blindly continuing.
  • set -u — treat use of an unset variable as an error, catching typos like $HOEM.
  • set -o pipefail — a pipeline fails if any stage fails, not just the last one. Without it, false | true "succeeds."
  • set -E — make ERR traps fire inside functions and subshells too, so your error handler actually runs.

How trap works. A trap registers a command to run when a signal or pseudo-signal fires. trap ... ERR runs on any error (great for logging the failing line via $LINENO); trap ... EXIT runs no matter how the script ends — success, error, or Ctrl-C — which makes it the reliable place to clean up temp files. Because EXIT always fires, cleanup can't be skipped by an early exit.

Worked example: strict mode catching a bug that would otherwise pass silently
#!/usr/bin/env bash
set -Eeuo pipefail
trap 'echo "FAILED at line $LINENO" >&2' ERR

# Typo: variable is DEPLOY_ENV but we reference DEPLOY_ENVIRONMENT
DEPLOY_ENV="staging"
echo "Deploying to $DEPLOY_ENVIRONMENT"     # -u turns this into a hard error
echo "this line never runs"
Output
./deploy.sh: line 7: DEPLOY_ENVIRONMENT: unbound variable
FAILED at line 7

Without set -u, that same script would print Deploying to (empty) and merrily continue — deploying to nowhere. Strict mode converted a silent logic bug into a loud, line-numbered failure.

set -e has sharp edges — know them

set -e does not trigger for commands in an if condition, in &&/|| chains, or when negated with !. And a function whose last command "fails" as part of a test can mask errors. When you deliberately allow a command to fail, be explicit: cmd || true. Don't assume set -e catches 100% of failures — it catches the common ones.

Mental model

Default Bash is a car with no dashboard warning lights — it'll keep driving with the engine on fire. Strict mode installs the warning lights and an automatic stop; trap EXIT is the seatbelt that always engages when the ride ends, cleaning up after you no matter what happened.

5. Python Fundamentals

Python is the lingua franca of DevOps automation — readable, batteries-included, and with libraries for every cloud and tool. If you learn one language deeply, make it Python.

Python building blocks
#!/usr/bin/env python3
import sys

# Data structures
servers = ["web-1", "web-2", "db-1"]           # list
config = {"region": "us-east-1", "count": 3}    # dict
unique = {"a", "b", "a"}                          # set -> {"a", "b"}

# Comprehensions (Pythonic transforms)
web_servers = [s for s in servers if s.startswith("web")]
port_map = {name: 8000 + i for i, name in enumerate(servers)}

# Functions with type hints (self-documenting)
def scale(service: str, replicas: int = 1) -> bool:
    if replicas < 0:
        raise ValueError("replicas must be >= 0")
    print(f"Scaling {service} to {replicas}")
    return True

if __name__ == "__main__":
    scale("api", int(sys.argv[1]) if len(sys.argv) > 1 else 1)
Why Python for automation

Python reads almost like English, so scripts are easy to write and maintain (you'll re-read them at 3 a.m. during an incident). It has a library for everything — talk to AWS, Kubernetes, databases, APIs — and it's installed nearly everywhere. That combination is why it dominates DevOps automation.

f-strings are the readable way to build output

f"Scaling {service} to {replicas}" embeds expressions directly in the string, which is far clearer than +-concatenation or %-formatting for log lines and messages. Add = for quick debugging — f"{replicas=}" prints replicas=3. One caveat: never f-string user input straight into a shell command or SQL query; that's how injection bugs start (use the list form / parameterized queries shown later).

Why the built-in data structures matter. Bash only really has strings and arrays; Python gives you the right shape for each job. A list is ordered and allows duplicates (a sequence of servers). A dict maps keys to values in O(1) lookups (config, JSON responses) — it's the workhorse of DevOps code because every API returns dict-shaped data. A set stores unique items and does fast membership tests and set math (required - present = "what's missing"), which is perfect for tag/permission audits.

How comprehensions and type hints work under the hood. A comprehension is just a tight, optimized loop that builds a collection — [s for s in servers if ...] compiles to bytecode that's typically faster than an explicit for+append loop and, more importantly, reads as a single "transform this into that" thought. Type hints (replicas: int) are not enforced at runtime — Python ignores them when executing. They're metadata that tools like mypy read to catch type errors before you run, and that editors use for autocomplete. They're documentation the machine can check.

Worked example: set math for a real audit
required = {"Owner", "Environment", "CostCenter"}
present  = {"Owner", "CostCenter"}          # tags actually on a resource

missing = required - present                 # set difference
extra   = present - required
print(f"missing tags: {sorted(missing)}")
print(f"compliant: {required <= present}")   # subset test
Output
missing tags: ['Environment']
compliant: False
Common Python beginner gotchas
  • Mutable default arguments. def f(items=[]) reuses the same list across calls. Use items=None then items = items or [].
  • Modifying a list while iterating it. Skips elements. Iterate a copy (for x in list(items):) or build a new list.
  • Assuming type hints validate. They don't at runtime — you still need real checks (like the ValueError above) for untrusted input.
  • Confusing == and is. == compares values; is compares identity. Use is only for None.
Mental model

Picture data structures as containers on a shelf: a list is a numbered row of boxes, a dict is a labelled filing cabinet, a set is a bag that automatically throws out duplicates. Choosing the right container makes the rest of the code obvious — most "hard" scripting problems are really just "I picked the wrong container."

6. Python for DevOps

The standard library and a few key packages cover most automation tasks: running commands, handling files, parsing config, and calling APIs.

Running commands, files & config
import subprocess, json, os
from pathlib import Path

# Run a command safely (list form avoids shell-injection)
result = subprocess.run(
    ["kubectl", "get", "pods", "-o", "json"],
    capture_output=True, text=True, check=True,
)
pods = json.loads(result.stdout)
running = [p["metadata"]["name"]
           for p in pods["items"]
           if p["status"]["phase"] == "Running"]

# Files the modern way (pathlib)
config_dir = Path("/etc/myapp")
for cfg in config_dir.glob("*.yaml"):
    print(cfg.read_text())

# Environment variables with defaults
db_host = os.environ.get("DB_HOST", "localhost")
Never use shell=True with untrusted input

subprocess.run("rm " + user_input, shell=True) is a command-injection hole — if user_input is "x; rm -rf /", disaster. Always pass commands as a list (["rm", user_input]) so arguments can't be interpreted as shell syntax. Same principle as parameterized SQL queries.

How the list form actually prevents injection. When you pass a list, Python calls the OS execve() family directly — the program name and each argument are handed over as separate array elements, and no shell is ever involved. There's no parser looking for ;, |, $(), or &&, so those characters are just literal bytes in an argument. With shell=True, Python instead runs /bin/sh -c "your whole string", and the shell does interpret those metacharacters — that's the door attackers walk through. The list form doesn't "escape" dangerous input; it removes the interpreter that made it dangerous.

Why pathlib over string paths. Path objects handle separators, joining (/ operator), globbing, and existence checks portably and readably, instead of fragile string concatenation like dir + "/" + name that breaks on edge cases. And check=True on subprocess.run raises CalledProcessError on a non-zero exit — the Python equivalent of Bash's set -e — so a failing command can't be silently ignored.

Worked example: safe vs unsafe, demonstrated
import subprocess

user_input = "myfile.txt; echo PWNED"   # attacker-controlled

# UNSAFE: the shell runs the injected 'echo PWNED'
subprocess.run(f"wc -l {user_input}", shell=True)

# SAFE: the whole thing is treated as ONE filename argument
subprocess.run(["wc", "-l", user_input])
Output
# Unsafe form:
wc: myfile.txt: No such file or directory
PWNED                                  ← injected command executed!

# Safe form (no injection — the ';' is part of the filename):
wc: 'myfile.txt; echo PWNED': No such file or directory
Common subprocess/file gotchas
  • Forgetting check=True. Without it a failed command returns quietly; you read empty output and carry on.
  • Forgetting text=True. You get raw bytes and comparisons/joins mysteriously fail.
  • Reaching for shell=True just to use a pipe. Chain two subprocess calls or use Python instead of invoking the shell.
  • Building paths with +. Use Path(a) / b to avoid double/missing slashes.
Mental model

The list form is like handing a cashier a labelled shopping list where "milk; free money" is one item name — they'll just look for a product with that exact name and fail. shell=True is like reading the list aloud to someone who acts on every sentence — the semicolon becomes a new instruction. Remove the middleman who interprets, and injection can't happen.

7. APIs, Cloud SDKs & Automation

Most DevOps automation is calling APIs — clouds, Kubernetes, monitoring, chat. Python has first-class SDKs for all of them.

Calling APIs & cloud SDKs
import requests               # HTTP APIs
import boto3                  # AWS SDK

# Generic REST API call with error handling
resp = requests.get("https://api.example.com/health", timeout=5)
resp.raise_for_status()       # raise on 4xx/5xx
data = resp.json()

# AWS: list running EC2 instances
ec2 = boto3.client("ec2", region_name="us-east-1")
for r in ec2.describe_instances()["Reservations"]:
    for inst in r["Instances"]:
        if inst["State"]["Name"] == "running":
            print(inst["InstanceId"], inst.get("PrivateIpAddress"))

# Kubernetes API (kubernetes package)
from kubernetes import client, config
config.load_kube_config()
v1 = client.CoreV1Api()
for pod in v1.list_pod_for_all_namespaces().items:
    print(pod.metadata.namespace, pod.metadata.name)
Key libraries to know

requests (HTTP), boto3 (AWS), google-cloud-*/azure-* (other clouds), kubernetes (K8s API), PyYAML (config), click/typer (building CLIs), rich (nice terminal output), jinja2 (templating). These cover the vast majority of automation you'll write.

Why SDKs beat hand-rolled HTTP. You could call AWS with raw requests, but you'd have to implement AWS Signature V4 request signing, pagination, retries with exponential backoff, and endpoint resolution yourself. boto3 does all of that for you and reads credentials from a standard chain (env vars → shared config → IAM role), so the same code runs on your laptop and inside a pod with no changes. That credential chain is why you rarely hardcode keys.

How raise_for_status() and timeouts protect you. An HTTP 500 is still a "successful" HTTP round-trip as far as the network is concerned — requests won't raise on its own. resp.raise_for_status() inspects the status code and raises HTTPError for 4xx/5xx, converting a silent bad response into an exception you can catch. And always pass timeout=: without it a hung server makes your automation hang forever, which in a cron job means a stuck process that never alerts anyone.

Pagination is the #1 cloud-API surprise

Cloud APIs return results in pages (often 50–1000 items). ec2.describe_instances() may only give you the first page. Use paginators — for page in ec2.get_paginator("describe_instances").paginate(): ... — or you'll silently miss resources and "pass" an audit that's actually incomplete.

Worked example: robust API call with retry and pagination
import time, requests, boto3

def get_json(url, retries=3):
    for attempt in range(1, retries + 1):
        try:
            r = requests.get(url, timeout=5)
            r.raise_for_status()
            return r.json()
        except requests.RequestException as e:
            if attempt == retries:
                raise
            wait = 2 ** attempt            # exponential backoff: 2s, 4s...
            print(f"attempt {attempt} failed ({e}); retrying in {wait}s")
            time.sleep(wait)

ec2 = boto3.client("ec2", region_name="us-east-1")
count = 0
for page in ec2.get_paginator("describe_instances").paginate():
    for r in page["Reservations"]:
        count += len(r["Instances"])
print(f"total instances across ALL pages: {count}")
Output
attempt 1 failed (HTTPSConnectionPool... Read timed out); retrying in 2s
total instances across all pages: 137
Common API/SDK mistakes
  • No timeout. One hung endpoint hangs the whole job forever.
  • Skipping pagination. You process page 1 and think you're done — silently wrong.
  • Not checking status. Treating a 500 body as valid data.
  • Hardcoding credentials. Let the SDK's credential chain / IAM role supply them; keys in code leak into git.
Mental model

An SDK is a professional translator between you and a foreign bureaucracy (the cloud). It knows the required stamps (signing), that answers come in numbered folders (pagination), and that you should ask again politely if the office is busy (retries). Talking raw HTTP is doing all that paperwork by hand.

8. Packaging & Virtual Environments

Dependency isolation prevents "works on my machine" — each project gets its own isolated set of packages.

Virtual envs & modern tooling
# Classic: venv + pip
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

# Modern all-in-one (fast): uv or poetry
uv venv && uv pip install -r requirements.txt
# poetry add requests boto3   # manages deps + lockfile + packaging

# Pin dependencies for reproducibility (commit the lockfile!)
pip freeze > requirements.txt
Always isolate & pin

Never pip install into system Python — you'll create conflicts. Use a virtual environment per project and pin versions (a lockfile) so everyone and every CI run gets identical dependencies. For distribution, containerize the tool (see the Docker Python section) so it runs anywhere.

Why isolation is necessary. Python installs packages into a shared site-packages directory. Project A needs requests==2.28, project B needs requests==2.31 — installed globally, the second install overwrites the first and silently breaks A. Worse, the OS itself uses the system Python for its own tools, so sudo pip install can brick system utilities. Isolation gives each project its own private package set so they can't collide.

How a virtualenv actually works. It's surprisingly simple: python -m venv .venv creates a folder with its own bin/python (a symlink or copy of the interpreter) and an empty site-packages. source .venv/bin/activate just prepends .venv/bin to your PATH and sets VIRTUAL_ENV, so typing python or pip resolves to the venv's copies first. Those interpreters are configured to look in the venv's site-packages, not the system one. There's no magic sandbox — it's PATH manipulation plus a per-env package directory. That's why "activating" is optional if you call .venv/bin/python directly.

Why pinning and lockfiles matter. requests in requirements.txt means "newest at install time" — so a build that worked Monday breaks Wednesday when a dependency ships a bad release. A lockfile records the exact version (and hash) of every direct and transitive dependency, so every machine and every CI run resolves the identical tree. That's the difference between reproducible and "works on my machine."

Worked example: proving isolation
python3 -m venv .venv
source .venv/bin/activate
which python          # -> /home/me/proj/.venv/bin/python  (not /usr/bin)
pip install requests==2.31.0
pip freeze > requirements.txt
deactivate
which python          # -> /usr/bin/python  (back to system, requests gone)
Output
/home/me/proj/.venv/bin/python
Successfully installed requests-2.31.0 ...
/usr/bin/python
Common packaging mistakes
  • sudo pip install. Pollutes system Python and can break OS tools. Never do this.
  • Not committing the lockfile. Then "pinning" pins nothing — CI still floats to newer versions.
  • Committing the .venv/ folder. It's machine-specific and huge; add it to .gitignore and recreate from the lockfile.
  • Wrong interpreter. ModuleNotFoundError usually means the venv isn't active — check which python.
Mental model

A virtualenv is a project's own kitchen with its own pantry. The system Python is the building's shared kitchen — if everyone dumps their ingredients there, recipes clash. Give each project its own kitchen, and write down the exact brands you used (the lockfile) so anyone can recreate the dish identically.

9. Go for DevOps Tools

Go is the language of cloud-native infrastructure — Docker, Kubernetes, Terraform, and Prometheus are all written in it. It compiles to a single static binary, making tools trivial to distribute.

A simple Go CLI tool
package main

import (
	"fmt"
	"net/http"
	"os"
	"time"
)

func main() {
	if len(os.Args) < 2 {
		fmt.Println("usage: healthcheck <url>")
		os.Exit(1)
	}
	url := os.Args[1]
	client := http.Client{Timeout: 5 * time.Second}
	resp, err := client.Get(url)
	if err != nil {
		fmt.Printf("DOWN: %v\n", err)
		os.Exit(1)
	}
	defer resp.Body.Close()
	fmt.Printf("%s -> %d\n", url, resp.StatusCode)
}
// go build -o healthcheck .   → one static binary, no runtime needed
Why infrastructure tools are written in Go

Go compiles to a single self-contained binary — no interpreter, no dependencies to install. Copy it to any Linux machine and it just runs. It's also fast and has built-in concurrency. That's why you can curl down kubectl or terraform as one file. If you're building a tool for others to run, Go's distribution story is unbeatable.

Why the single-binary property exists. Go links everything the program needs — including its runtime and garbage collector — directly into the output file (static linking). There's no separate .so to find, no interpreter version to match, no pip install on the target. Cross-compiling is a one-liner (GOOS=linux GOARCH=arm64 go build), so from a Mac you can produce a Linux ARM binary for a Raspberry Pi. That portability is the whole reason cloud-native tooling standardized on Go.

How Go's explicit error handling shapes the code. Go has no exceptions for ordinary failures; functions return an error value as their last result, and you check it right where it happens (if err != nil). It's verbose, but it means every failure is handled at the point it occurs — you can't accidentally let an error propagate silently the way an unhandled exception might. The defer resp.Body.Close() pattern schedules cleanup to run when the function returns, guaranteeing resources are released even on an early return.

Worked example: build once, run anywhere

Common Go beginner mistakes
  • Ignoring the error. Assigning resp, _ := client.Get(url) and using resp — it may be nil and panic. Always check err.
  • Forgetting defer resp.Body.Close(). Leaks connections; long-running tools eventually run out of sockets.
  • Unused imports/vars fail to compile. Go is strict on purpose — delete them, don't fight it.
  • Expecting Python-speed development. Go trades quick iteration for a compile step and explicitness; that's the deal you accept for the binary.
Mental model

A Python script is a recipe card — useless without a kitchen (interpreter + ingredients) already set up on the target machine. A Go binary is a vending machine: self-contained, plug it in anywhere and it works. You do more assembly up front, but then it runs with zero setup.

10. Concurrency & CLI Tools

Go's goroutines make concurrent work (checking many servers at once) simple — a common need in ops tooling.

Concurrent health checks with goroutines
package main

import (
	"fmt"
	"net/http"
	"sync"
)

func check(url string, wg *sync.WaitGroup, results chan<- string) {
	defer wg.Done()
	resp, err := http.Get(url)
	if err != nil {
		results <- fmt.Sprintf("%s DOWN", url)
		return
	}
	results <- fmt.Sprintf("%s %d", url, resp.StatusCode)
}

func main() {
	urls := []string{"https://a.com", "https://b.com", "https://c.com"}
	var wg sync.WaitGroup
	results := make(chan string, len(urls))
	for _, u := range urls {
		wg.Add(1)
		go check(u, &wg, results)   // run concurrently
	}
	wg.Wait(); close(results)
	for r := range results { fmt.Println(r) }
}
Building real CLIs in Go

Use Cobra (the framework behind kubectl, gh, and most cloud CLIs) for commands, flags, and help text, plus Viper for config. This is how you build professional, distributable DevOps tools. For quick scripts, though, Python is faster to write — reach for Go when performance or single-binary distribution matters.

Why goroutines exist and how they schedule. Checking 500 servers one at a time is dominated by waiting on the network — the CPU sits idle. A goroutine is an extremely cheap unit of concurrent work (starts at ~2KB of stack, versus ~1MB for an OS thread), so you can launch thousands. Go's runtime multiplexes them onto a small pool of real OS threads with its own scheduler (the "M:N" model): when a goroutine blocks on I/O, the scheduler parks it and runs another on that thread, so the CPU stays busy. You get the throughput of async I/O with code that reads like plain sequential functions.

How channels and WaitGroup coordinate safely. A channel is a typed, thread-safe pipe: one goroutine sends (results <- x), another receives (<-results), and the runtime handles the locking so you don't share memory unsafely. A WaitGroup is a counter — Add(1) per goroutine, Done() when each finishes, and Wait() blocks until the count hits zero. Together they express "fan out this work, then collect all the answers." The buffered channel (make(chan string, len(urls))) has room for every result so senders never block waiting for a reader.

Why order to close and drain matters

You must wg.Wait() then close(results) then range over the channel. Close too early and a still-running goroutine panics sending on a closed channel. Range over an unclosed channel and the loop blocks forever waiting for more values. This ordering is the classic fan-out/fan-in shape.

Worked example: bounding concurrency with a semaphore channel
package main

import ("fmt"; "sync")

func main() {
	urls := []string{"a", "b", "c", "d", "e"}
	sem := make(chan struct{}, 2)   // at most 2 in flight at once
	var wg sync.WaitGroup
	for _, u := range urls {
		wg.Add(1)
		go func(u string) {
			defer wg.Done()
			sem <- struct{}{}         // acquire a slot (blocks if 2 busy)
			defer func() { <-sem }()  // release the slot
			fmt.Printf("checking %s\n", u)
		}(u)
	}
	wg.Wait()
}
Output (only 2 run at a time; order varies)
checking a
checking b
checking c
checking d
checking e
Common concurrency mistakes
  • Loop-variable capture. In older Go, go func(){ use(u) }() without passing u as an argument captures the same variable — every goroutine sees the last value. Pass it in: go func(u string){...}(u).
  • Unbounded fan-out. Launching 10,000 goroutines that each open a socket can exhaust file descriptors. Bound it with a semaphore channel (above).
  • Deadlock from wrong close order. Closing the channel before goroutines finish, or never closing it before ranging.
  • Data races. Multiple goroutines writing a shared map/slice without a channel or mutex — run go test -race to catch these.
Mental model

Goroutines are like sending out a team of couriers all at once instead of one at a time. The WaitGroup is the dispatcher ticking off each courier as they return; the channel is the inbox where they drop their deliveries. You wait until everyone's back, then read the inbox — instead of standing at the door for each courier in turn.

11. Version Control & Code Structure

Your automation code deserves the same discipline as application code — it is production code. (Deep Git coverage in the Git guide.)

Treat scripts as real software
  • Version control everything — no scripts living only on someone's laptop.
  • Code review automation via pull requests — a bad script can break production faster than app code.
  • Structure — functions/modules, a clear entry point, a README explaining usage.
  • Config separate from code — env vars/config files, not hardcoded values.
  • No secrets in code — pull from a secrets manager (see Security/Vault).

Why automation code deserves the same rigor as app code. A bug in a web app might show a wrong page; a bug in a deploy script can delete the production database across every region in seconds. Automation has higher blast radius than the app it manages, yet it's often written casually. Version control gives you the same safety net app developers rely on: history, blame, review, and instant rollback. When an incident starts with "what changed?", git log is the answer.

How structure keeps scripts maintainable. A pile of top-level statements is fine at 20 lines and unreadable at 200. Breaking work into small functions with a single responsibility, guarding the entry point (if __name__ == "__main__": so the file can be both imported and run), and separating configuration from logic means the next person — often future-you — can understand and safely change one piece without re-reading everything. Config-out-of-code also means the same script runs across dev/staging/prod by changing an env var, not by editing and re-committing.

Worked example: unstructured vs structured
# BEFORE: everything at top level, config hardcoded, can't test or reuse
import boto3
ec2 = boto3.client("ec2", region_name="us-east-1")   # hardcoded region
for r in ec2.describe_instances()["Reservations"]:
    for i in r["Instances"]:
        print(i["InstanceId"])

# AFTER: testable function, config from env, guarded entry point
import os, boto3

def list_instances(region: str) -> list[str]:
    ec2 = boto3.client("ec2", region_name=region)
    return [i["InstanceId"]
            for r in ec2.describe_instances()["Reservations"]
            for i in r["Instances"]]

if __name__ == "__main__":
    region = os.environ.get("AWS_REGION", "us-east-1")
    print("\n".join(list_instances(region)))
Mental model

Treat every script as a small product with users (your team and future-you), not a sticky note. The sticky note gets lost and only you can read it; the product is in version control, reviewed, documented, and safe for anyone to pick up. The extra minutes of structure buy you hours you won't spend debugging at 3 a.m.

Make automation idempotent

A well-structured script should be safe to run twice. Idempotent means running it again produces the same end state rather than piling up duplicates or erroring — "create if missing, update if present" instead of blind "create." This is what lets CI retry a flaky step, or an operator re-run a deploy after a timeout, without fear. It's the same principle Terraform and Ansible are built on, applied to your own scripts.

12. Testing Your Code

Automation that breaks silently is worse than no automation — it can do damage at scale. Tests catch regressions before they hit production.

A Python unit test (pytest)
# test_deploy.py
from deploy import scale

def test_scale_valid():
    assert scale("api", 3) is True

def test_scale_rejects_negative():
    import pytest
    with pytest.raises(ValueError):
        scale("api", -1)
# run: pytest -v
The testing pyramid applies to automation too

Many fast unit tests (individual functions), fewer integration tests (does it actually talk to the API/tool correctly?), and a few end-to-end tests. For infra code, also test in a throwaway environment (see Terraform's testing section and Ansible's Molecule). Run tests in CI on every change.

Why test automation you can't easily test against real infra. You can't spin up real production EC2 to test a "delete idle volumes" script — that's the point of the script. The trick is separating logic (which volume is idle?) from side effects (actually calling AWS). You unit-test the logic in isolation with fake data, and reserve slow, real-infra checks for a disposable sandbox. This is why the earlier examples put decision-making in small pure functions.

How mocking works under the hood. A mock is a stand-in object that records how it's called and returns whatever you tell it — no real network involved. MagicMock() auto-creates attributes and methods on demand, so ec2.describe_instances.return_value = {...} makes your function believe it got a real AWS response. Your test then asserts on the function's output, and can even assert the function called AWS with the right arguments (mock.assert_called_with(...)). The function under test can't tell the difference — that's what makes the test fast and deterministic.

Worked example: run the tests and see the report
# deploy.py
def scale(service: str, replicas: int) -> bool:
    if replicas < 0:
        raise ValueError("replicas must be >= 0")
    return True

# test_deploy.py
import pytest
from deploy import scale

def test_scale_valid():
    assert scale("api", 3) is True

def test_scale_rejects_negative():
    with pytest.raises(ValueError):
        scale("api", -1)
$ pytest -v
test_deploy.py::test_scale_valid PASSED                    [ 50%]
test_deploy.py::test_scale_rejects_negative PASSED         [100%]

======================== 2 passed in 0.01s ========================
Common testing mistakes
  • Testing against real infra by accident. A test that hits real AWS is slow, flaky, and can cost money or delete things. Mock the side effects.
  • Only testing the happy path. The negative/error cases (bad input, API failure) are exactly where automation causes damage — test those.
  • Asserting on log text. Brittle. Assert on return values and raised exceptions instead.
  • No tests in CI. Tests that don't run on every change rot silently. Wire pytest/go test into the pipeline.
Mental model

Mocking is a flight simulator for your code: you fly it through engine failures and storms (API errors, bad data) safely on the ground, so you're confident before it flies the real plane (production). Tests are the pre-flight checklist that runs automatically every time you change anything.

13. Linting, Formatting & Types

Automated code quality tools catch bugs and enforce consistency so humans review logic, not style.

Pythonblack, ruff formatruff, pylintmypy (type hints)
Gogofmt (built-in)go vet, golangci-lintcompiler (static)
Bashshfmtshellcheck—
Automate quality with pre-commit + CI

Run formatters and linters automatically via the pre-commit framework and in CI. Type hints + mypy in Python catch a whole class of bugs before runtime (passing the wrong type). Treat lint warnings as errors in CI so quality never regresses — the same discipline the whole hub teaches.

Why formatters and linters are different tools. A formatter (black, gofmt) only rewrites layout — spacing, line breaks, quotes — never behavior, so it's safe to run automatically. A linter (ruff, go vet) analyzes the code for likely bugs and smells: unused variables, shadowed names, comparing with == where you meant is. Formatting ends the pointless "tabs vs spaces" debate in review; linting catches real defects before they run.

How static type checking works. mypy reads your type hints and simulates the flow of types through the program without executing it. If a function is annotated to return list[str] but a caller passes the result where an int is expected, mypy flags it — the same class of error Go catches at compile time. Because it's static, it finds bugs on code paths your tests never exercised, like an error branch that only runs during an outage.

Worked example: a bug mypy catches that tests might miss
def replicas_for(env: str) -> int:
    return {"prod": 5, "staging": 2}.get(env)   # .get returns int | None!

def scale(n: int) -> None:
    print("scaling to", n * 2)

scale(replicas_for("dev"))    # env not in dict -> None -> None*2 explodes
$ mypy app.py
app.py:2: error: Incompatible return value type
    (got "int | None", expected "int")  [return-value]
app.py:7: error: Argument 1 to "scale" has incompatible type
    "int | None"; expected "int"  [arg-type]
Found 2 errors in 1 file (checked 1 source file)

Runtime would crash with TypeError: unsupported operand type(s) for *: 'NoneType' and 'int' — only if the "dev" path ever ran. mypy finds it before you ship.

Common quality-tooling mistakes
  • Bikeshedding style in review. Let the formatter decide; humans review logic, not commas.
  • Linters as warnings only. Warnings get ignored. Make them fail CI so they get fixed.
  • Type hints that lie. Annotating -> int when you sometimes return None defeats the checker. Be honest (int | None).
  • Running tools only locally. Someone always forgets — enforce in pre-commit and CI.
Mental model

The formatter is spell-check and auto-layout for code; the linter is grammar-check that flags confusing sentences; the type checker is a proofreader who notices you promised a number but delivered "maybe a number." All three run automatically so the human reviewer can focus on whether the idea is right.

14. Error Handling & Logging

Automation runs unattended, often at 3 a.m. Good error handling and logging are what let you understand what happened when you weren't watching.

Proper error handling & structured logging
import logging, sys

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)s %(message)s",
)
log = logging.getLogger(__name__)

def deploy(service: str) -> None:
    try:
        log.info("Deploying %s", service)
        # ... risky work ...
    except ConnectionError as e:
        log.error("Network failure deploying %s: %s", service, e)
        raise                       # re-raise; don't swallow silently
    except Exception:
        log.exception("Unexpected error")   # logs full traceback
        sys.exit(1)
    finally:
        log.info("Deploy attempt finished")
Never silently swallow errors

An empty except: pass is how automation "succeeds" while actually failing — the worst outcome, because you trust a broken process. Always log the error, and either handle it meaningfully or re-raise/exit non-zero so the caller (and CI) knows it failed. Exit codes matter: 0 = success, non-zero = failure. Scripts that always exit 0 break pipelines silently.

Why exit codes are the contract with everything above you. Cron, CI runners, Kubernetes, and shell && chains all judge success purely by the exit code — 0 means "worked," anything else means "failed." They never read your logs. So a script that catches an error, prints a sad message, and still exits 0 tells the whole system "all good," and the pipeline goes green on a broken deploy. Returning non-zero (sys.exit(1), or letting an exception propagate) is how you make failure visible to the machines that act on it.

How logging beats print, and why log.exception matters. The logging module adds a timestamp, severity level, and source, and can route output to files, stdout, or a log aggregator — with a single line you can raise or lower verbosity everywhere. Crucially, log.exception(...) (called inside an except) captures the full traceback, not just your message, so at 3 a.m. you see the exact line and call chain that failed instead of a vague "something broke." print gives you none of that structure and can't be filtered by level.

Catch narrow, re-raise broad

Handle the specific exceptions you can actually recover from (retry a ConnectionError), and let unexpected ones propagate so they're loud. A bare except Exception is acceptable only at the top level, where you log the traceback and exit non-zero — never to quietly continue.

Worked example: swallowed vs surfaced failure
import sys, logging
logging.basicConfig(format="%(levelname)s %(message)s")
log = logging.getLogger("deploy")

def risky():
    raise ConnectionError("registry unreachable")

# BAD: pipeline goes GREEN on a failed deploy
try:
    risky()
except Exception:
    pass
print("exit code:", 0)   # lies

# GOOD: log the traceback and fail loudly
def main() -> int:
    try:
        risky()
    except ConnectionError:
        log.exception("deploy failed")
        return 1
    return 0
sys.exit(main())
Output
exit code: 0
ERROR deploy failed
Traceback (most recent call last):
  File "deploy.py", line 15, in main
    risky()
  File "deploy.py", line 6, in risky
    raise ConnectionError("registry unreachable")
ConnectionError: registry unreachable
$ echo $?
1
Common error-handling mistakes
  • except: pass. The classic silent failure — bans itself from every code review.
  • Catching too broadly, too early. Swallows bugs you didn't anticipate. Catch specific types.
  • print instead of logging. No levels, no timestamps, no traceback, can't be aggregated.
  • Always exiting 0. Cron/CI think it worked; the failure is invisible until damage compounds.
Mental model

Think of the exit code as the report you hand your boss: 0 is "done," non-zero is "we have a problem." Logging is the detailed incident notes attached to that report. Swallowing an error is handing in "done" while quietly hiding that the building's on fire — the one thing you must never do in automation.

15. Regex, JSON/YAML & Data Wrangling

DevOps work is full of parsing and transforming text and config. A few tools handle almost all of it.

Parsing & transforming data
import re, json, yaml

# Regex: extract IPs from a log line
ips = re.findall(r"\b(?:\d{1,3}\.){3}\d{1,3}\b", log_line)

# JSON: parse an API response, navigate safely
data = json.loads(api_response)
name = data.get("metadata", {}).get("name", "unknown")

# YAML: read a config file (K8s, CI, Ansible all use YAML)
with open("values.yaml") as f:
    config = yaml.safe_load(f)      # ALWAYS safe_load, never load
The CLI equivalents (jq & yq)
kubectl get pods -o json | jq '.items[].metadata.name'   # query JSON
cat values.yaml | yq '.replicas'                          # query YAML
curl -s api/data | jq '.[] | select(.status=="active")'   # filter
jq and yq are essential

jq (JSON) and yq (YAML) are the Swiss-army knives for wrangling structured data on the command line — parsing API responses, extracting fields, transforming config. Learn jq basics; it appears constantly in scripts and pipelines. For anything beyond one-liners, move to Python's json/yaml for readability.

Why parse structurally, never with regex on JSON/YAML. JSON and YAML are nested, recursive formats — a value can contain objects containing lists containing objects. Regex is a flat pattern matcher with no concept of nesting, so a regex that "works" on today's response silently breaks when a field moves, a value contains a brace, or whitespace changes. A real parser (json.loads, yaml.safe_load, jq) understands the grammar and gives you a navigable data structure that's correct regardless of formatting.

Where regex genuinely belongs, and how it works. Regex is the right tool for unstructured text — log lines, free-form output. A regex compiles to a finite-state machine that scans text left to right; \b anchors word boundaries and \d{1,3} means "1 to 3 digits." Keep patterns simple and anchored; beware catastrophic backtracking, where a pattern with nested quantifiers ((a+)+) on non-matching input can take exponential time and hang your script.

Why safe_load, never yaml.load

Plain yaml.load can construct arbitrary Python objects encoded in the YAML — a malicious config file can execute code on load (a real CVE class). yaml.safe_load only builds basic types (dicts, lists, strings, numbers), so untrusted YAML can't run code. Treat every config file you didn't write as untrusted.

Worked example: parse structurally, transform, re-emit
import json

api_response = '{"items": [{"metadata": {"name": "api"}, "status": {"phase": "Running"}}, {"metadata": {"name": "worker"}, "status": {"phase": "Pending"}}]}'

data = json.loads(api_response)
not_running = [p["metadata"]["name"]
               for p in data["items"]
               if p["status"]["phase"] != "Running"]
print(json.dumps({"not_running": not_running}, indent=2))
Output

  "not_running": [
    "worker"
  ]
}
The jq equivalent for a quick one-liner

  | select(.status.phase != "Running")

Common data-wrangling mistakes
  • Regex-parsing JSON/YAML. Fragile the moment formatting changes. Use a real parser.
  • yaml.load on untrusted input. Remote-code-execution risk — always safe_load.
  • Chained [...] access. data["a"]["b"] throws KeyError if a level is missing; use .get("a", {}).get("b").
  • Greedy/backtracking regex. Can hang on adversarial input; keep patterns anchored and specific.
Mental model

A parser is like handing a document to someone fluent in the language — they understand the structure and can find any field. Regex is like searching for a phrase with Ctrl-F — great for finding a string in prose, hopeless for understanding a nested document. Match the tool to whether the data has real structure.

16. A Real Automation Project — Putting It Together

Concepts click when you build something real. Here's a complete, production-quality automation script that ties together everything in this guide — a tool that audits your cloud for untagged or idle resources and reports to Slack.

Why this example

It's the kind of tool DevOps engineers write constantly: query an API/cloud, apply some logic, and report or act. It uses every good practice — CLI arguments, cloud SDK, error handling, structured logging, a data pipeline, tests, and clean structure. Read it as a template you can adapt to a hundred real tasks.

cloud_auditor.py — a real, well-structured tool
#!/usr/bin/env python3
"""Audit AWS for untagged EC2 instances and idle EBS volumes; report to Slack."""
import argparse, logging, sys
import boto3, requests

logging.basicConfig(level=logging.INFO, format="%(asctime)s %(levelname)s %(message)s")
log = logging.getLogger("auditor")

REQUIRED_TAGS = {"Owner", "Environment", "CostCenter"}

def find_untagged_instances(ec2) -> list[dict]:
    """Return instances missing any required tag."""
    problems = []
    for res in ec2.describe_instances()["Reservations"]:
        for inst in res["Instances"]:
            tags = {t["Key"] for t in inst.get("Tags", [])}
            missing = REQUIRED_TAGS - tags
            if missing:
                problems.append({"id": inst["InstanceId"], "missing": sorted(missing)})
    return problems

def find_idle_volumes(ec2) -> list[str]:
    """Unattached EBS volumes are pure wasted spend."""
    vols = ec2.describe_volumes(Filters=[{"Name": "status", "Values": ["available"]}])
    return [v["VolumeId"] for v in vols["Volumes"]]

def notify_slack(webhook: str, text: str) -> None:
    resp = requests.post(webhook, json={"text": text}, timeout=10)
    resp.raise_for_status()

def main() -> int:
    p = argparse.ArgumentParser(description="Audit AWS resources")
    p.add_argument("--region", default="us-east-1")
    p.add_argument("--slack-webhook", help="post findings here")
    p.add_argument("--dry-run", action="store_true")
    args = p.parse_args()

    try:
        ec2 = boto3.client("ec2", region_name=args.region)
        untagged = find_untagged_instances(ec2)
        idle = find_idle_volumes(ec2)
    except Exception:
        log.exception("audit failed")
        return 1

    report = (f"🔍 Audit ({args.region}): "
              f"{len(untagged)} untagged instances, {len(idle)} idle volumes")
    log.info(report)
    for i in untagged:
        log.info("  %s missing tags: %s", i["id"], ", ".join(i["missing"]))

    if args.slack_webhook and not args.dry_run:
        notify_slack(args.slack_webhook, report)

    # Exit non-zero if problems found — so CI/cron flags it
    return 0 if not (untagged or idle) else 2

if __name__ == "__main__":
    sys.exit(main())

Every good-practice this project demonstrates
  • CLI with argparse — flags, defaults, --dry-run for safety.
  • Cloud SDK (boto3) — real API calls, functions per concern.
  • Structured logging — timestamped, leveled — not print().
  • Error handling — log.exception + non-zero exit so CI/cron notices failures.
  • Type hints — self-documenting, catch bugs with mypy.

Where to run it

Schedule this on a cron / Kubernetes CronJob / EventBridge rule to audit daily, containerize it (Docker Python guide) for portability, give it a read-only IAM role via OIDC, and pipe findings to Slack or a ticket. That's a complete, real, useful DevOps automation — built entirely from this guide's concepts.

Why this architecture holds up in production. The tool cleanly separates three concerns: gathering data (the find_* functions, which only read), deciding (set math on required tags — pure logic), and acting/reporting (notify_slack, exit codes). That separation is what makes it testable (mock the gather step, test the decide step) and safe (--dry-run gates the act step). Every real automation you write will have these same three layers — recognizing them is the skill.

How the exit-code design makes it a pipeline citizen. Returning 0 for clean, 1 for an execution failure, and 2 for "ran fine but found problems" lets the surrounding system react differently to each: a CI gate can fail the build on 2, alert on 1, and pass on 0. Because the logic lives in main() which returns the code and sys.exit(main()) propagates it, the contract with cron/CI is explicit and testable — you could even unit-test that a problem run returns 2.

Why --dry-run is non-negotiable for acting tools

This auditor only reports, but the moment you add "auto-delete idle volumes," a dry-run flag becomes essential: it lets you see exactly what would be deleted before anything is. Ship destructive automation with dry-run defaulted on, and require an explicit flag to actually act — the same philosophy as terraform plan before apply.

Worked example: running it and reacting to the exit code
python cloud_auditor.py --region us-east-1 --dry-run
echo "exit code: $?"

# Use the exit code as a CI/cron gate:
if python cloud_auditor.py --region us-east-1; then
  echo "clean — nothing to do"
else
  code=$?
  [[ $code -eq 2 ]] && echo "compliance issues found — failing the gate"
  [[ $code -eq 1 ]] && echo "the audit itself errored — page on-call"
  exit $code
fi
Output

2025-05-01 09:00:01 INFO   i-0a1b missing tags: CostCenter, Environment
2025-05-01 09:00:01 INFO   i-0c2d missing tags: Owner

Common mistakes scaling a tool like this up
  • Forgetting pagination. As shown in the APIs section, describe_instances pages — wrap it in a paginator or you'll audit only the first page and report "clean" falsely.
  • No dry-run on destructive actions. Adding auto-remediation without a preview is how a tool deletes the wrong resources at scale.
  • Over-broad IAM. A read-only auditor should have a read-only role; don't hand it delete permissions it doesn't need.
  • Swallowing the Slack failure. If notify_slack fails, you still want the non-zero exit — don't let a notification error hide the findings.
Mental model

Every useful DevOps tool is the same sentence: "look at something, decide if it's okay, and tell someone (or fix it)." This project is that sentence written well — gather, decide, report, with a clear pass/fail signal. Once you see that shape, you can build a hundred variations: cost audits, drift detection, backup verification, cert-expiry checks.

17. Best Practices — the checklist

Automation code best practices
  • Right tool: Bash for glue, Python for logic/APIs, Go for distributable tools.
  • Bash: set -Eeuo pipefail + ShellCheck + quote everything.
  • Python: virtual envs, pinned deps, type hints, subprocess lists (never shell=True on input).
  • Version-control & code-review all automation; no laptop-only scripts.
  • Test (pytest/go test), lint, and format automatically in CI + pre-commit.
  • Handle errors explicitly; log with context; use correct exit codes.
  • Config & secrets out of code (env/secrets manager).
  • Containerize tools for portable distribution.

18. Troubleshooting Playbook

Bash script "works interactively but fails in cron/CI"

Different environment — cron has a minimal PATH and no profile. Use absolute paths or set PATH explicitly, don't rely on interactive shell features, and add set -Eeuo pipefail to surface the real error.

Python "ModuleNotFoundError" / wrong version

Not using the right virtual environment, or deps not installed/pinned. Activate the venv, pip install -r requirements.txt, and check which python/python --version. Pin versions to avoid drift.

Script silently does nothing / exits 0 on failure

Errors are being swallowed. Add logging, remove bare except: pass, check exit codes, and in Bash use strict mode. A pipeline step that "passes" but didn't work is worse than a visible failure.

Command injection / weird behavior with special characters

Unquoted variables (Bash) or shell=True (Python) interpreting input as code. Quote all Bash variables; pass Python subprocess args as a list. This is both a bug and a security hole (see AppSec).
