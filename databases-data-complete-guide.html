Databases & Data Engineering: The Complete Guide

Data is the heart of every application. Master how to store, query, scale, and move it — from SQL fundamentals and indexing through NoSQL, replication, sharding, and modern data pipelines.

📖 How to read this guide

Each concept: what it is, why it exists, the SQL/config, and ★ best practice. Complements the Cloud databases section, the Kafka guide (data in motion), and the Docker guide (running databases in containers).

1. Why Data Matters

Applications are mostly about storing and retrieving data correctly, quickly, and safely. The database is often the hardest part to scale and the most catastrophic to lose — so understanding it deeply is essential.

The database is the app's memory

Servers can be thrown away and recreated (they're "cattle"). But the database holds the truth — user accounts, orders, money. Lose a server: shrug. Lose or corrupt the database: potentially fatal. That's why databases get special care: backups, replication, careful schema changes, and the strongest consistency guarantees your use case needs.

Why data outlives everything else

Code is a liability that produces value; data is the value. You can rewrite an entire application in a new language over a weekend and users won't notice — but they will notice instantly if their order history disappears. This asymmetry drives almost every design decision in this guide: we invest disproportionately in protecting, replicating, and correctly modeling data because it is the one component that is genuinely irreplaceable.

How "durability of truth" actually works under the hood. When you commit a change, a well-designed database does not simply overwrite bytes on disk and hope. It first appends a record of the change to a sequential, fsync'd log (the write-ahead log, or WAL) before touching the actual data pages. If power is lost a microsecond later, on restart the database replays that log to reconstruct the committed state. This is why a database can promise "once I said COMMIT succeeded, your data is safe" — the promise is backed by an ordered, flushed log, not by luck.

The cost of getting durability wrong
-- Looks harmless. Runs without a transaction, no backup, on production:
DELETE FROM orders WHERE status = 'pending';
-- Oops: the app writes 'PENDING' (uppercase) for new orders, so this
-- matched a different, much larger set than expected. 2.1M rows gone.
-- Without PITR backups, this data is unrecoverable. The "truth" is lost.
Common mistakes when treating data casually
  • Running destructive statements without a transaction — no BEGIN; means no ROLLBACK; escape hatch.
  • Testing restores never, only backups — you discover the backup was broken at the worst possible moment (covered in §14).
  • Storing derived truth twice without a plan to keep copies in sync — the two copies drift and nobody knows which is right.
Mental model: the database is a bank vault, the app is the teller

Tellers (app servers) come and go, get retrained, get replaced. The vault (the database) holds the actual money. You can lose a teller and open tomorrow; lose the vault's contents and you're finished. So you build the vault with redundant walls (replication), a written ledger of every transaction (the WAL), off-site copies of the ledger (backups), and strict rules about who can change what (constraints and transactions).

2. Database Types Overview

There's no single "best" database — each type is optimized for different data shapes and access patterns. Choosing well is a key architecture decision.

Why so many types exist

Every database makes a bet about how data will be shaped and accessed, and then optimizes ruthlessly for that bet. There is no free lunch: a database tuned for flexible ad-hoc joins (relational) cannot also be the absolute fastest at single-key lookups (key-value), because the very structures that make joins possible add overhead to a simple GET. The proliferation of types is not fashion — it reflects genuinely different physics of storage, indexing, and distribution.

How the type determines the storage engine. A relational database stores rows together in pages and maintains B-tree indexes so it can find and join arbitrary columns. A key-value store like Redis keeps a hash table in RAM — O(1) lookup, but it cannot answer "all users older than 30" without scanning. A wide-column store like Cassandra uses an LSM-tree (log-structured merge tree): writes append to an in-memory table and flush to immutable sorted files, which is why it ingests writes at enormous rates but pays a cost to read (it may check several files). A graph database stores adjacency directly so "friends of friends" is a pointer-hop, not a self-join. The type is the storage engine's worldview.

A decision heuristic

Ask three questions: (1) What is the shape? Highly relational with many entities referencing each other → relational. Self-contained documents → document. Pure lookups → key-value. (2) What is the dominant access pattern? Ad-hoc analytical queries vs one known access path. (3) What is the scale profile? Write-heavy at massive scale often pushes you toward LSM-based stores. Answer these before naming a product.

Common mistakes choosing a type
  • Resume-driven selection — picking a trendy database because it's new, not because your data shape needs it.
  • Using a key-value store as a relational database — reimplementing joins in application code, badly.
  • Ignoring polyglot — forcing one database to serve search, analytics, and OLTP when three purpose-built stores fed by CDC would be simpler and faster.
Mental model: vehicles, not one "best car"

Asking "which database is best?" is like asking "which vehicle is best?" A sports car, a cargo ship, a bicycle, and an ambulance are all "best" — for entirely different jobs. You wouldn't haul freight in a Ferrari or race a container ship. Match the vehicle to the trip; match the database to the data shape and access pattern.

3. The Relational Model & SQL

Relational databases store data in tables (rows & columns) with defined relationships, queried with SQL. They're the default choice for most applications — mature, reliable, and powerful.

Core SQL you must know
-- Query with a join, filter, group, and sort
SELECT u.name, COUNT(o.id) AS orders, SUM(o.total) AS revenue
FROM users u
JOIN orders o ON o.user_id = u.id
WHERE o.created_at >= '2024-01-01'
GROUP BY u.name
HAVING COUNT(o.id) > 5
ORDER BY revenue DESC
LIMIT 10;

-- Modify data safely inside a transaction
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;   -- both succeed or (on ROLLBACK) neither does
Relational = a set of linked spreadsheets

Think of tables as spreadsheets: a users sheet and an orders sheet. Instead of copying the user's details into every order row, each order just stores the user's id — a link. A JOIN follows that link to combine them on demand. This avoids duplication (one source of truth per fact) and is the essence of the relational model.

Why the relational model won

Before relational databases, applications navigated data by following hard-coded pointers between records (the "network" and "hierarchical" models). Changing an access pattern meant rewriting code. In 1970 E. F. Codd proposed something radical: describe what you want, not how to fetch it, and let the database figure out the access path. That separation — declarative queries over a mathematical model of relations (tables) — is why SQL survived fifty years of hardware change. Your SELECT from 1995 still runs, but the engine underneath got a thousand times smarter.

How a JOIN actually executes. A JOIN is not magic — the planner picks one of a few physical algorithms. A nested loop join takes each row from the outer table and probes the inner table (great when the inner side has an index and the outer side is small). A hash join builds an in-memory hash table of the smaller side keyed on the join column, then streams the larger side through it (great for big, unindexed joins). A merge join sorts both sides on the join key and walks them together like a zipper (great when inputs are already sorted). Understanding these three explains almost every plan you'll ever read.

Worked example: the join with a plan
EXPLAIN ANALYZE
SELECT u.name, o.total
FROM users u
JOIN orders o ON o.user_id = u.id
WHERE u.id = 42;
Typical Postgres output
Nested Loop  (cost=0.71..16.76 rows=3 width=40) (actual time=0.021..0.028 rows=3 loops=1)
  ->  Index Scan using users_pkey on users u  (cost=0.28..8.29 rows=1 width=36)
        Index Cond: (id = 42)
  ->  Index Scan using idx_orders_user on orders o  (cost=0.42..8.44 rows=3 width=12)
        Index Cond: (user_id = 42)
Planning Time: 0.140 ms
Execution Time: 0.052 ms

Read it inside-out: Postgres used the primary-key index to find user 42 instantly (one row), then for that one row used the index on orders.user_id to fetch its 3 orders — a nested loop where both sides are index scans. No table was fully read. That's the declarative model paying off: you asked for the answer, the planner found the cheap path.

Common SQL mistakes
  • SELECT * in application code — pulls columns you don't need, defeats covering indexes, and breaks silently when the schema changes.
  • Functions on indexed columns in WHERE — WHERE lower(email) = ? can't use a plain index on email (use a functional/expression index instead).
  • Implicit type casts — comparing an indexed bigint column to a string literal can silently disable the index.
  • Relying on row order without ORDER BY — SQL returns sets; order is undefined unless you ask.
Mental model: you're a customer, the planner is the chef

SQL is ordering off a menu ("I'll have the revenue by top customer") — you describe the dish, not the recipe. The query planner is the chef deciding whether to grill or fry, which ingredients to prep first, and whether to use the fast pantry (an index) or dig through the whole storeroom (a full scan). You can hint and tune, but the chef owns the kitchen.

4. Normalization & Schema Design

Normalization organizes data to eliminate redundancy — each fact stored once. It prevents update anomalies but requires joins; sometimes you deliberately denormalize for read speed.

FormRule (simplified)
1NFAtomic values, no repeating groups
2NFNo partial dependency on part of a composite key
3NFNo non-key column depends on another non-key column
Normalize for writes, denormalize for reads

Start normalized (3NF) — it keeps data correct and is the safe default. Denormalize deliberately and only when read performance demands it (e.g., storing a computed order_count to avoid an expensive join on every page load), accepting that you now must keep the copy in sync. Premature denormalization is a common source of data bugs.

Why normalization exists: the anomalies it prevents

Normalization is not academic tidiness — it exists to eliminate three concrete bugs that plague redundant data. Update anomaly: if a customer's address is copied into every one of their 500 orders, changing the address means 500 updates, and if one is missed the data now contradicts itself. Insertion anomaly: you can't record a new product until someone orders it, because product facts live only in the orders table. Deletion anomaly: deleting the last order for a product also erases the only record that the product existed. Storing each fact exactly once makes all three impossible.

How the normal forms build on each other. Each form removes a specific kind of unwanted dependency. 1NF says a cell holds one atomic value (no comma-separated lists). 2NF removes partial dependencies — in a table keyed by (order_id, product_id), the product's name depends only on product_id, so it doesn't belong here. 3NF removes transitive dependencies — if zip determines city, then city depends on the key only through zip, so city belongs in a zip table. Boyce-Codd (BCNF) tightens 3NF for edge cases with overlapping candidate keys. The mechanical rule of thumb: every non-key column must depend on the key, the whole key, and nothing but the key.

Worked example: denormalizing safely with a trigger-maintained counter
-- Normalized truth: orders reference users.
-- Reads need COUNT(*) per user on every dashboard load — expensive at scale.
-- Denormalize a cached counter, but keep it correct with a trigger:
ALTER TABLE users ADD COLUMN order_count int NOT NULL DEFAULT 0;

CREATE FUNCTION bump_order_count() RETURNS trigger AS $$
BEGIN
  IF (TG_OP = 'INSERT') THEN
    UPDATE users SET order_count = order_count + 1 WHERE id = NEW.user_id;
  ELSIF (TG_OP = 'DELETE') THEN
    UPDATE users SET order_count = order_count - 1 WHERE id = OLD.user_id;
  END IF;
  RETURN NULL;
END; $$ LANGUAGE plpgsql;

CREATE TRIGGER trg_order_count
AFTER INSERT OR DELETE ON orders
FOR EACH ROW EXECUTE FUNCTION bump_order_count();
-- Now the copy stays in sync automatically — denormalization WITH integrity.
Common schema-design mistakes
  • Denormalizing first, measuring never — you inherit sync bugs to solve a performance problem you didn't have.
  • Storing lists in a column (tags = "a,b,c") — violates 1NF, makes querying/indexing miserable; use a join table.
  • Manual counter updates in app code without a transaction — concurrent orders lose increments (lost update); use a trigger or an atomic SET x = x + 1.
  • Over-normalizing tiny reference data — splitting a two-value enum into its own table adds joins for no benefit.
Mental model: one fact, one home

Normalization is just "write each fact down in exactly one place." Your home address lives in your profile, not stapled to every letter you've ever sent. When you move, you update one place and every letter automatically points to the new address. Denormalization is deliberately keeping a sticky note copy for speed — fine, as long as you have a system that updates the sticky note whenever the real record changes.

5. Indexes & Query Performance

Indexes are the single biggest lever on database performance. Without them, the database scans every row; with the right one, it jumps straight to the answer.

Create indexes & read query plans
-- Index the columns you filter/join/sort on
CREATE INDEX idx_orders_user_created ON orders (user_id, created_at);

-- ALWAYS check the plan to see if your index is used
EXPLAIN ANALYZE
SELECT * FROM orders WHERE user_id = 42 ORDER BY created_at DESC;
-- Look for "Index Scan" (good) vs "Seq Scan" (full table scan - bad on big tables)
Indexing rules of thumb
  • Index columns in WHERE, JOIN, and ORDER BY clauses.
  • Composite index order matters — put the most selective / most-filtered column first; it serves queries on leading columns.
  • Don't over-index — each one slows writes and uses space.
  • Use EXPLAIN ANALYZE to confirm indexes are actually used.

Why an index turns O(n) into O(log n)

A table with no index is an unordered pile of rows; finding one means examining every row — O(n), which doubles in cost every time the table doubles. A B-tree index is a sorted, balanced tree. Because it's sorted, at each node the database compares your search key and immediately discards the branches that can't contain it — halving (or better) the remaining search space at every step. To find one row among a billion, a B-tree of order ~hundreds needs only about 4–5 disk reads instead of a billion. That's the whole game: each level of the tree eliminates most of the data, so cost grows with the logarithm of table size, not the size itself.

How it works under the hood. A B-tree keeps keys sorted within fixed-size pages (nodes) and stays balanced — all leaves at the same depth — by splitting a full page in two and pushing a separator key up to the parent when it overflows. Leaf nodes hold the indexed key plus a pointer to the actual row (in Postgres, a heap tuple ID). Because leaves are linked in sorted order, an index also accelerates ORDER BY and range scans (created_at > '2024-01-01'): the engine seeks to the start and walks the linked leaves. A covering index that includes all selected columns lets the query be answered from the index alone — the "Index Only Scan" — never touching the table.

Worked example: composite index and a range scan
CREATE INDEX idx_orders_user_created ON orders (user_id, created_at);

EXPLAIN ANALYZE
SELECT id, total FROM orders
WHERE user_id = 42 AND created_at >= '2024-01-01'
ORDER BY created_at DESC
LIMIT 20;
Output — index used for both filter and sort
Limit  (cost=0.42..12.10 rows=20 width=12) (actual time=0.018..0.031 rows=20 loops=1)
  ->  Index Scan Backward using idx_orders_user_created on orders
        (cost=0.42..58.30 rows=99 width=12) (actual time=0.017..0.027 rows=20 loops=1)
        Index Cond: ((user_id = 42) AND (created_at >= '2024-01-01'))
Planning Time: 0.11 ms
Execution Time: 0.05 ms

The (user_id, created_at) order is deliberate: user_id is the equality filter (leading column), and because the index is already sorted by created_at within each user, Postgres satisfies the ORDER BY ... DESC by scanning the index backward — no separate sort step. Reverse the column order and this query would filter fine but need an extra sort.

Common indexing mistakes & gotchas
  • Missing index on a foreign key / filter column — the number-one cause of the dreaded Seq Scan on a large table.
  • Wrong composite order — an index on (created_at, user_id) is nearly useless for WHERE user_id = ? alone (leading column not filtered).
  • Low-selectivity index — indexing a boolean or a status with 3 values rarely helps; the planner correctly ignores it and you paid write cost for nothing.
  • Over-indexing write-heavy tables — every INSERT/UPDATE must maintain every index; ten indexes can make writes several times slower.
  • Stale statistics — after a big data change, run ANALYZE so the planner's row estimates (and thus its plan choice) are accurate.
Mental model: the index at the back of a book

Finding "mitochondria" by reading a 900-page textbook front to back is a full table scan. Flipping to the alphabetical index, landing on "M," then narrowing to "mi-" and jumping to page 412 is a B-tree lookup: a few quick narrowing steps instead of reading everything. The index costs a few extra pages at the back (space) and must be reprinted if the book changes (write cost) — exactly the tradeoffs a database index makes.

6. Transactions & ACID

A transaction groups operations so they succeed or fail as a unit. ACID is the set of guarantees relational databases provide — the reason you can trust them with money.

PropertyGuarantee
AtomicityAll operations succeed, or none do (no half-done state)
ConsistencyTransactions move the DB from one valid state to another (constraints hold)
IsolationConcurrent transactions don't interfere (as if run one at a time)
DurabilityOnce committed, data survives crashes
Atomicity = the bank transfer guarantee

Transferring £100 = subtract from A, add to B. If the system crashed between those two steps without a transaction, £100 vanishes. Atomicity guarantees both happen or neither does — the money is never lost in limbo. This all-or-nothing property is why financial systems live on ACID databases.

Isolation levels trade safety for speed

From loosest to strictest: Read Uncommitted → Read Committed → Repeatable Read → Serializable. Stricter prevents more anomalies (dirty reads, phantom reads) but reduces concurrency. Most apps use Read Committed (the common default) and reach for stricter only where correctness demands it.

Why transactions exist and how MVCC delivers them

Transactions exist because the real world groups changes: a transfer is two updates, an order is a row plus stock decrements plus a payment record. Without grouping, a crash or a concurrent writer could leave the database in a state that never legally exists — money missing, stock oversold. ACID is the contract that makes such half-states impossible.

How atomicity and durability work: the write-ahead log again. Every change is logged before the data pages are flushed. On COMMIT, the commit record is flushed to durable storage — that flush is the moment the transaction becomes permanent. On ROLLBACK or a crash before commit, the engine uses the log to undo (or simply never applies) the changes. All-or-nothing falls straight out of "the commit record exists, or it doesn't."

How isolation works without locking everything — MVCC. Modern databases (Postgres, MySQL/InnoDB, Oracle) use Multi-Version Concurrency Control: instead of readers and writers blocking each other, every row can have multiple versions tagged with the transaction that created (and later deleted) it. Each transaction sees a consistent snapshot — the set of row versions committed as of its start (or its statement, depending on level). A writer creating a new version doesn't overwrite the old one, so concurrent readers keep seeing the old version until they end. This is why "readers don't block writers and writers don't block readers." The cost: old versions (dead tuples) accumulate and must be reclaimed — Postgres calls this VACUUM.

Worked example: the anomalies each isolation level prevents
-- Two concurrent transactions. Session A reads twice; Session B updates between.
-- Session A:
BEGIN ISOLATION LEVEL READ COMMITTED;
SELECT balance FROM accounts WHERE id = 1;   -- returns 100
--            (Session B commits UPDATE accounts SET balance = 50 WHERE id = 1;)
SELECT balance FROM accounts WHERE id = 1;   -- returns 50  <-- "non-repeatable read"
COMMIT;

-- Re-run Session A under a stricter level:
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT balance FROM accounts WHERE id = 1;   -- returns 100
--            (Session B commits its UPDATE to 50)
SELECT balance FROM accounts WHERE id = 1;   -- STILL returns 100  <-- stable snapshot
COMMIT;
Preventing lost updates with row locks
-- Two users buy the last item concurrently. Naive read-modify-write loses one.
BEGIN;
SELECT stock FROM products WHERE id = 7 FOR UPDATE;  -- locks the row
-- app checks stock > 0, then:
UPDATE products SET stock = stock - 1 WHERE id = 7;
COMMIT;   -- the second buyer waits for this commit, then sees the reduced stock
Common transaction mistakes & gotchas
  • Read-modify-write without a lock or atomic update — classic lost update; two transactions both read 1, both write 0, one decrement vanishes. Use FOR UPDATE or SET x = x - 1.
  • Long-running transactions — they hold snapshots open, block VACUUM, cause bloat, and increase deadlock/lock-wait risk. Keep transactions short.
  • Assuming the default level is Serializable — it usually isn't (Read Committed in Postgres). Phantom reads and write skew are possible; opt into SERIALIZABLE where correctness truly needs it.
  • Doing slow work (HTTP calls, sleeps) inside a transaction — you hold locks the entire time.
Mental model: MVCC is a photograph, not a live feed

When your transaction starts, it takes a photograph of the database. For its whole life it reads from that photo, so nobody editing in the background can smear your picture mid-read. When you commit, your edits are developed into a new photo everyone else will see next. Old photos are kept around until no one is still looking at them — then a janitor (VACUUM) throws them out.

7. Query Optimization

Slow queries are the most common database problem. A systematic approach beats guessing.

The query-tuning workflow
  1. Find slow queries — enable the slow-query log or use pg_stat_statements.
  2. EXPLAIN ANALYZE — read the plan; look for sequential scans on big tables, expensive sorts, nested loops over many rows.
  3. Add/fix indexes — cover the filter/join/sort columns.
  4. Rewrite if needed — avoid SELECT *, pull less data, avoid N+1 queries (fetch in one query, not one-per-row).
  5. Re-measure — confirm the plan improved.
The N+1 query problem

The most common app-level performance killer: fetching a list (1 query), then looping and querying details for each item (N queries). 100 items = 101 queries. Fix by fetching everything in one query (a JOIN or WHERE id IN (...)), or use your ORM's eager-loading. Watch for this in traces — it shows up as many tiny repeated queries.

Why the query planner exists and how it chooses

Because SQL is declarative, one query can be executed many physically-different ways — index scan vs sequential scan, nested-loop vs hash vs merge join, join order A⋈B⋈C vs C⋈A⋈B. The number of candidate plans explodes combinatorially. The cost-based optimizer exists to pick a good one automatically. It estimates the cost (in an abstract unit blending disk pages and CPU) of each candidate using statistics it keeps about your tables: row counts, how many distinct values a column has, histograms of value distribution. From those it estimates selectivity — how many rows a filter will keep — and therefore how much work each plan does. It then searches the plan space and returns the cheapest estimate.

How to read a plan like the planner does. The key numbers in EXPLAIN ANALYZE are the estimated rows versus the actual rows. When they diverge wildly, the planner is working from bad statistics and will make bad choices (e.g., picking a nested loop expecting 3 rows but getting 3 million). The fix is usually ANALYZE (refresh stats) or, for correlated columns, extended statistics — not blindly forcing an index.

Find the slow queries first (Postgres)
-- Enable the extension once, then query cumulative stats:
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

SELECT substr(query,1,60) AS query, calls, mean_exec_time, total_exec_time
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 5;
A planner mis-estimate you can spot and fix
-- BAD plan from stale stats: estimate says 1 row, reality is 480k:
Nested Loop  (cost=0.42..8.9 rows=1 width=..) (actual time=0.03..920.5 rows=480210 loops=1)
  ...
-- After running ANALYZE on the table, the planner switches to a hash join:
Hash Join  (cost=1240..5310 rows=479000 width=..) (actual time=12.1..78.4 rows=480210 loops=1)
Execution Time: 88 ms      -- down from ~950 ms
Common optimization mistakes & gotchas
  • Guessing instead of reading the plan — always EXPLAIN ANALYZE before and after; measure, don't assume.
  • N+1 hidden by an ORM — lazy-loaded relations fire a query per row; enable eager loading / JOIN. This is often invisible until you look at query counts or traces.
  • Adding an index that the planner ignores — usually because the filter isn't selective, stats are stale, or a function/cast on the column disables it.
  • Optimizing the wrong query — a 5 ms query called 2 million times costs more than a 3 s report run once a day. Sort by total time, not per-call time.
  • OFFSET pagination on deep pages — OFFSET 100000 still scans and discards 100k rows; use keyset (seek) pagination on an indexed column instead.
Mental model: a GPS route planner

The optimizer is a GPS. You say "get me to the warehouse" (the result); it considers highways (index scans), back roads (sequential scans), and interchanges (join methods), estimating travel time from its map data (statistics). If the map is out of date (stale stats), it confidently routes you into a traffic jam. ANALYZE is refreshing the map; EXPLAIN is asking it to show the route before you drive.

8. NoSQL Families

NoSQL databases trade some relational features (joins, strict schema) for scale, flexibility, or speed. Each family fits specific patterns.

FamilyModelStrengthsUse for
DocumentJSON-like docs (MongoDB)Flexible schema, nested dataContent, catalogs, evolving schemas
Key-ValueSimple key → value (Redis, DynamoDB)Blazing fast, simpleCaching, sessions, high-scale lookups
Wide-ColumnRows with dynamic columns (Cassandra)Massive write throughput, linear scaleTime-series, IoT, logging at scale
GraphNodes + edges (Neo4j)Relationship traversalSocial networks, recommendations, fraud
NoSQL isn't "no schema" — it's "schema in your code"

Flexible-schema databases don't remove the need for structure — they just move the responsibility from the database to your application. And they require modeling around your access patterns up front (especially DynamoDB/Cassandra). Choosing NoSQL to "avoid database design" backfires; you still design, just differently. Pick NoSQL for a real scale/shape reason, not to avoid SQL.

Why NoSQL emerged and how each family scales

NoSQL databases were born from the operational pain of scaling relational databases horizontally. A single relational primary can be scaled up (bigger box) only so far, and distributing joins and multi-row ACID transactions across many machines is genuinely hard. Web-scale companies traded features they didn't need for a specific workload (rich joins, strict schema) to gain what they did need (linear horizontal scale, flexible documents, or microsecond lookups). Each family makes a different trade.

How document stores work: a document (JSON/BSON) is stored and retrieved as one unit keyed by _id, so fetching a whole entity is a single read with no joins. Secondary indexes on nested fields make queries possible, but the sweet spot is data that's naturally self-contained. How wide-column stores (Cassandra) scale writes: they hash the partition key to place data on a ring of nodes, and use an LSM-tree per node — writes append to a commit log + in-memory memtable and flush to immutable SSTables, so writes never seek and scale linearly with node count. Reads may merge several SSTables (mitigated by bloom filters). How key-value stores are fast: a hash map gives O(1) access; DynamoDB spreads keys across partitions by a hash of the partition key, giving predictable single-digit-millisecond reads at any scale — as long as your access is by that key.

Worked example: modeling for access pattern (DynamoDB single-table)
# Relational instinct: separate users and orders tables, join at read time.
# DynamoDB has no joins — you model for the query "get a user + their orders":
#   PK = USER#42     SK = PROFILE            {name, email}
#   PK = USER#42     SK = ORDER#2024-06-01   {total: 30}
#   PK = USER#42     SK = ORDER#2024-06-09   {total: 12}

# One query returns the profile AND all orders — because they share the partition key:
aws dynamodb query \
  --table-name app \
  --key-condition-expression "PK = :u" \
  --expression-attribute-values '{":u":{"S":"USER#42"}}'
# Single partition read, no join. But "all orders across ALL users this month"
# is now the HARD query — you'd need a secondary index or a scan. You optimize
# for the access patterns you chose up front; the others become expensive.
Common NoSQL mistakes & gotchas
  • Modeling relationally then bolting on NoSQL — designing normalized tables and then discovering there are no joins at query time.
  • Hot partitions — a poorly chosen partition key (e.g., today's date, or a single celebrity user) sends all traffic to one node while the rest sit idle.
  • Unbounded documents — appending to an array inside one MongoDB document forever until it hits the 16 MB limit and rewrites the whole doc on every update.
  • Expecting cross-document transactions everywhere — support varies; don't assume ACID across many partitions/documents.
  • Scans as a habit — a full scan in DynamoDB/Cassandra is the equivalent of a seq scan on a billion rows and can cost real money.
Mental model: pre-plated meals vs a buffet

A relational database is a buffet: raw ingredients laid out normally, and you assemble any dish you want at query time (joins). NoSQL is meal-prep: you decide the meals in advance and store them pre-plated, so serving is instant — but ordering a dish you didn't prep means going back to the kitchen (an expensive scan or a whole new index). Great when you know the menu; painful when requirements change.

9. CAP Theorem & Consistency

In a distributed database, when the network partitions (nodes can't talk), you must choose: stay consistent (reject requests) or stay available (serve possibly-stale data). You can't have both during a partition.

Eventual consistency, explained

"Eventually consistent" means: after a write, different nodes might briefly return old data, but they'll converge to the same value soon. Like a rumor spreading through a crowd — not everyone knows instantly, but eventually everyone does. Fine for a "likes" counter; not fine for an account balance. Knowing which of your data can tolerate this is a key design skill.

Why CAP forces a choice, and how the choice plays out

CAP is really a statement about what happens during a network partition — when nodes that should talk to each other can't. Imagine your data is replicated on nodes in two data centers and the link between them breaks. A write arrives at data center A. You now face an unavoidable fork: (1) accept the write and let A and B diverge — you kept Availability but lost ConsistencyConsistency but lost Availability. There is no third option that both accepts the write and keeps all nodes agreeing, because they physically cannot communicate. That impossibility is the theorem. Since partitions will happen on real networks, P is not optional — so the real decision is C-vs-A during a partition.

How a CP system enforces the choice: it uses a consensus protocol (Raft, Paxos) requiring a quorum — a majority of nodes must acknowledge a write before it commits. On the minority side of a partition, there's no majority, so writes are rejected: correctness preserved, availability sacrificed on that side. How an AP system enforces the choice: Dynamo-style stores accept writes on any reachable replica and record concurrent versions (vector clocks / last-write-wins / CRDTs). When the partition heals, they reconcile — either automatically (CRDTs merge, LWW picks the latest timestamp) or by handing conflicting versions to the application to resolve. Tunable systems (Cassandra) let you dial it per query with R + W > N quorum math.

Worked example: tuning consistency per query (Cassandra)
-- N = 3 replicas. Choose consistency by picking how many must respond.
-- Strong-ish (read-your-writes): W=QUORUM(2) + R=QUORUM(2) > N=3  ->  overlap guaranteed
CONSISTENCY QUORUM;
INSERT INTO balances (id, amount) VALUES (42, 100);  -- waits for 2 of 3 acks

-- High availability, possibly stale: any single replica answers
CONSISTENCY ONE;
SELECT amount FROM balances WHERE id = 42;  -- fast, may see old value during a partition
Common CAP mistakes & gotchas
  • Treating CAP as "pick 2 of 3" permanently — it only bites during a partition; the rest of the time you can have strong consistency and availability. PACELC refines this: else (no partition) you still trade Latency vs Consistency.
  • Assuming eventual consistency is fine everywhere — it's great for likes/view counts, disastrous for balances/inventory without safeguards.
  • Read-your-own-writes surprises — a user updates their profile then sees the old value from an AP replica; route their reads to a node they wrote, or use quorum reads.
  • Ignoring conflict resolution — in AP systems, last-write-wins can silently drop a concurrent update; use CRDTs or app-level merges for data that can't tolerate loss.
Mental model: two clerks and a cut phone line

Two branch clerks share one ledger by phone. The line goes dead (partition). A customer wants to withdraw. The CP clerk says "I can't confirm your balance with head office — come back later" (refuses, stays correct). The AP clerk says "I'll trust my local copy and sort it out later" (serves you, risks double-spend). Neither is wrong — a bank picks CP, a social feed picks AP. The cut line forced the choice.

10. Caching & Redis

Caching stores frequently-accessed data in fast memory to avoid repeatedly hitting the (slower) database. Redis is the ubiquitous choice.

Cache invalidation — the hard part

"There are only two hard things in CS: cache invalidation and naming things." Stale caches serve wrong data. Strategies: set a TTL (expire after N seconds — simple, slightly stale), or invalidate on write (delete/update the cache when the DB changes — fresh, more complex). Also guard against cache stampede (many misses hitting the DB at once when a hot key expires).

Redis, Valkey & the fork you should know about

Redis was the default in-memory store for years. In 2024 Redis changed its license away from open source, and the community (backed by AWS, Google, Oracle and the Linux Foundation) forked the last open version into Valkey — a drop-in, fully open-source replacement that speaks the same protocol and commands. Managed services (AWS ElastiCache, etc.) now offer Valkey, and migrating is typically a low-risk swap. For new work, know both exist: Valkey if you want to stay fully open-source, Redis if you need its newer commercial modules. The caching concepts above apply identically to either.

Why caching works: the latency and locality argument

Caching works because of two facts about real workloads. First, a latency hierarchy: reading from RAM is roughly a hundred times faster than a local SSD and a thousand-plus times faster than a query that touches disk, parses SQL, plans, joins, and serializes. Second, locality: access is rarely uniform — a tiny fraction of keys (the "hot set") gets the overwhelming majority of reads (the 80/20 or Zipf pattern). Put the hot set in RAM and you serve most traffic without ever touching the database, cutting both latency and load dramatically.

How cache-aside works under the hood. On a read the app asks Redis; a hit returns immediately; a miss falls through to the database, and the app writes the result back into Redis with a TTL. On a write the app updates the database and then invalidates (deletes) the cache key so the next read re-populates it fresh. The database remains the source of truth; the cache is a fast, disposable copy. TTL bounds staleness even if an invalidation is missed — a safety net.

Worked example: cache-aside with a TTL (redis-cli)
# 1. Read path — check cache first
GET user:42
(nil)                       # miss

# 2. Miss -> read DB, then store with a 300s TTL
SET user:42 "{\"name\":\"Ada\"}" EX 300
GET user:42
"{\"name\":\"Ada\"}"        # subsequent reads are RAM-speed hits

# 3. Write path — update DB, then invalidate so stale data can't linger
DEL user:42                 # next read re-populates from the fresh DB row
Cache stampede & the dogpile effect

When a very hot key expires, hundreds of concurrent requests all miss at the same instant and slam the database simultaneously — a "stampede" that can take the database down precisely when traffic is highest. Mitigate with a short randomized TTL jitter (so keys don't all expire together), a mutex/lock so only one request rebuilds the value while others wait, or "stale-while-revalidate" (serve the old value while one worker refreshes it).

Common caching mistakes & gotchas
  • No invalidation strategy — updating the DB but not the cache, so users see stale data indefinitely. Every cached fact needs an expiry or an invalidation trigger.
  • Caching then writing (wrong order) — under cache-aside, update the DB then invalidate; invalidating first races with a concurrent read that re-caches the old value.
  • Caching negative results without care — caching "not found" can hide newly-created data (or enable cache penetration where missing keys always bypass the cache).
  • Treating the cache as durable — Redis can evict or restart; never store the only copy of important data in a cache.
  • Unbounded memory — set a maxmemory and an eviction policy (e.g., allkeys-lru) or Redis will OOM.
Mental model: notes on your desk vs the filing cabinet

The database is the filing cabinet across the room — authoritative but slow to walk to. The cache is the sticky notes on your desk for the few things you look at constantly. You glance at the desk first (hit); if it's not there you walk to the cabinet, read it, and jot a note for next time (miss + populate). When a file changes, you throw away the matching sticky note (invalidate) so you don't quote yesterday's number.

11. Search & Time-Series

Some access patterns fit relational tables badly — ranked text search and high-volume timestamped metrics chief among them. Purpose-built engines model these shapes natively and win by orders of magnitude at scale.

Why not just use your main database for everything?

You can bolt search and metrics onto Postgres and it works fine at modest scale. But a search box wants typo-tolerance, synonyms, and relevance ranking; a metrics system wants to ingest millions of points a second and roll them up by time. Those are different jobs with different physics — so past a certain scale you keep the source of truth in your primary database and stream a copy into a specialized engine (polyglot persistence).

TypeToolUse for
Full-text searchElasticsearch, OpenSearchSearch boxes, log analytics, relevance ranking
Time-seriesPrometheus, InfluxDB, TimescaleDBMetrics, IoT, monitoring (see Observability)
Vectorpgvector, Pinecone, MilvusAI/ML embeddings, semantic search
Don't force one database to do everything

Relational databases can do basic search and time-series, but purpose-built tools do it far better at scale. A common pattern: keep the source of truth in Postgres, and stream changes (via CDC/Kafka Connect) into Elasticsearch for search and a time-series DB for metrics. This is polyglot persistence.

Why these need special engines, and how they work

Full-text search exists because LIKE '%term%' can't use a normal B-tree (leading wildcard), can't rank by relevance, and can't handle stemming, typos, or synonyms. Search engines invert the problem with an inverted index: instead of "document → words," they store "word → list of documents containing it," built by an analyzer that lowercases, tokenizes, and stems text ("running" → "run"). A query for "fast running" fetches the posting lists for both terms, intersects/unions them, and ranks results by a relevance score (BM25/TF-IDF) that rewards rare terms and penalizes very long documents. That's why search returns ranked results in milliseconds over millions of documents.

Time-series data has a peculiar shape — append-only, timestamp-ordered, queried by ranges and downsampled aggregates ("avg CPU per 5 min over the last day"). Time-series engines exploit this: they partition by time window, keep data physically sorted by time, and apply heavy columnar compression (delta-of-delta on timestamps, run-length on repeated values) because adjacent points are similar. They also support retention/downsampling policies (keep raw for 7 days, 1-minute rollups for a year). A generic table with a B-tree on timestamp works until volume explodes; then the specialized layout wins by orders of magnitude.

Worked example: Postgres full-text vs a real search engine
-- Postgres can do decent full-text with a GIN index on a tsvector:
ALTER TABLE articles ADD COLUMN ts tsvector
  GENERATED ALWAYS AS (to_tsvector('english', title || ' ' || body)) STORED;
CREATE INDEX idx_articles_ts ON articles USING GIN (ts);

SELECT title, ts_rank(ts, q) AS score
FROM articles, to_tsquery('english', 'fast & running') q
WHERE ts @@ q
ORDER BY score DESC LIMIT 10;
-- Great for moderate scale. Elasticsearch adds typo-tolerance, synonyms,
-- faceting, and horizontal scale you'd otherwise build by hand.
Common search & time-series mistakes
  • Making a search index the source of truth — Elasticsearch is near-real-time and can lose/re-index data; keep the authoritative copy in your primary DB and feed search via CDC.
  • LIKE '%foo%' at scale — a guaranteed sequential scan; use a proper full-text or trigram index.
  • Storing high-cardinality tags as time-series labels — each unique label combination is a separate series; user IDs or request IDs as labels cause a "cardinality explosion" that blows up memory.
  • No retention/downsampling — raw metrics kept forever fill disks; roll up and expire old resolution.
Mental model: index card catalog vs a heart-rate chart

A search engine is a library card catalog flipped inside-out: for every word it lists which books contain it, so you find all books about "sailing" instantly and sorted by how relevant they are. A time-series database is a fitness tracker's chart: an endless ribbon of timestamped readings, stored compressed and read as ranges ("show me the last hour"), never edited, eventually thinned out to save space.

12. Replication

Replication keeps copies of your data on multiple servers — for high availability (survive a server loss) and read scaling (spread reads across replicas).

Replication lag causes "I just saved it but it's gone"

With async replication, a read hitting a replica right after a write to the primary may not see it yet (the change hasn't replicated). Fix: route reads-after-writes to the primary, or use "read your own writes" consistency. This is a classic subtle bug when you add read replicas.

Why replication exists and how the WAL makes it possible

Replication solves two problems at once: survival (if the primary's disk dies, a replica has the data) and read scaling (many replicas share the read load). Both rely on the same mechanism that already gives durability — the write-ahead log.

How WAL streaming works. Recall that every change is first written to the WAL as an ordered sequence of records. Physical (streaming) replication simply ships that same WAL to the replicas over a TCP connection, and each replica replays the records in order onto its own copy of the data files. Because the WAL is an exact, ordered record of every change, replaying it reproduces the primary's state byte-for-byte. The replica keeps a connection open and applies records as they arrive, staying a fraction of a second behind. Synchronous replication makes the primary wait for at least one replica to confirm it has the WAL record before returning COMMIT (zero data loss, higher latency); asynchronous returns immediately (fast, but a crash can lose the last few unshipped records — your RPO). Logical replication decodes the WAL into row-level change events instead, enabling replication between different versions or into other systems (the basis of CDC).

Worked example: measuring replication lag (Postgres)
-- On the primary: how far behind is each replica, in bytes and time?
SELECT client_addr,
       state,
       pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) AS bytes_behind,
       write_lag, flush_lag, replay_lag
FROM pg_stat_replication;

-- On a replica: is it currently in recovery (i.e., a replica) and how stale?
SELECT pg_is_in_recovery(), now() - pg_last_xact_replay_timestamp() AS lag;
Choosing sync vs async per your RPO
# postgresql.conf on the primary — require one replica to confirm (RPO = 0):
synchronous_commit = on
synchronous_standby_names = 'FIRST 1 (replica_a, replica_b)'
# Set to 'off'/'local' for async: lowest write latency, small data-loss window.
Common replication mistakes & gotchas
  • Reading your own writes from a lagging replica — the "I saved it but it vanished" bug; pin post-write reads to the primary.
  • Assuming async failover is lossless — promoting a replica that missed the last WAL records loses those transactions (non-zero RPO). Use sync replication for zero loss.
  • Long-running queries on a replica — they can conflict with WAL replay and either delay replication or get cancelled (hot_standby_feedback / query conflicts).
  • Split-brain on failover — two nodes both think they're primary after a botched promotion; use proper fencing / a coordinator (Patroni, etcd) not manual promotion.
  • Treating replicas as backups — a bad DELETE replicates instantly to every replica. Replicas are for availability; you still need backups (§14).
Mental model: a scribe reading changes aloud

The primary keeps a running diary of every change (the WAL). Replication is a scribe in the next room copying the diary line by line as it's written. Async: the scribe copies at their own pace and is usually a sentence behind. Sync: the author waits for the scribe to say "got it" before starting the next sentence. If the author collapses, the scribe's copy takes over — but only as complete as the last line they managed to copy.

13. Sharding & Partitioning

When one server can't hold or handle all the data, you split it. Partitioning divides a table; sharding spreads data across multiple servers.

Sharding = splitting one huge library into branch libraries

One library can only hold so many books and serve so many visitors. Sharding splits the collection across branches — e.g., books A–M in branch 1, N–Z in branch 2 (by "shard key"). Each branch is smaller and faster. The catch: finding a book now needs the right branch, and asking "how many books total?" means querying every branch (cross-shard queries are expensive). Choose the shard key so most queries hit one shard.

StrategySplit byWatch out for
RangeValue ranges (dates, A-M/N-Z)Hot spots if data is skewed
HashHash of the keyEven spread, but range queries hit all shards
GeographicRegionData residency, cross-region latency
Shard late, and choose the key carefully

Sharding adds major complexity (cross-shard joins/transactions are hard). Exhaust simpler options first: bigger instance, read replicas, caching, archiving old data. When you must shard, pick a shard key that keeps related data together and spreads load evenly — changing it later is extremely painful.

Why sharding, and how the router finds the data

Replication copies the whole dataset to every node — great for reads, useless once the data or the write volume exceeds what one machine can hold or handle. Sharding is the answer: split the data into disjoint pieces (shards) on different machines so each holds a fraction and every machine takes a fraction of the writes. That's the only way to scale writes and total dataset size horizontally.

How routing works. A shard key (e.g., user_id) determines which shard a row lives on. Two common mappings: hash sharding computes hash(key) mod N (or, better, maps the hash onto a consistent-hashing ring so adding a node moves only ~1/N of the data instead of reshuffling everything); and range sharding assigns contiguous key ranges to shards (good for range scans, risky for hot spots). A routing layer (a proxy like Vitess, or client-side logic) hashes/looks up the key and sends the query to exactly that shard. A query with the shard key in its WHERE clause touches one shard — fast. A query without it must scatter-gather: ask every shard and merge results — slow and it gets slower as you add shards. This is why the shard key must match your dominant access pattern.

Worked example: local partitioning (single node) vs true sharding
-- PARTITIONING: one server, one logical table split into physical pieces.
-- The planner prunes irrelevant partitions automatically ("partition pruning").
CREATE TABLE events (id bigint, ts timestamptz, payload jsonb)
  PARTITION BY RANGE (ts);
CREATE TABLE events_2024_06 PARTITION OF events
  FOR VALUES FROM ('2024-06-01') TO ('2024-07-01');

EXPLAIN SELECT * FROM events WHERE ts >= '2024-06-10' AND ts < '2024-06-11';
-- Plan shows only events_2024_06 is scanned; other months are pruned.

-- SHARDING: the SAME idea, but partitions live on DIFFERENT servers, and a
-- router picks the server from the shard key. Cross-shard queries scatter-gather.
Common sharding mistakes & gotchas
  • Bad shard key → hot shard — sharding by country when 70% of users are in one country overloads that shard while others idle.
  • Choosing a key that isn't in your queries — every query becomes a scatter-gather; you scaled hardware but not performance.
  • Cross-shard transactions/joins — no longer a single ACID transaction; you need sagas, two-phase commit, or denormalization. Hard and error-prone.
  • Resharding under load — changing the key or shard count later means migrating live data; consistent hashing and range splits ease it, but it's still a project.
  • Sharding too early — you take on all this complexity before exhausting vertical scaling, replicas, caching, and archiving.
Mental model: many post offices by ZIP code

One post office can't serve a whole country, so mail is split by ZIP code across thousands of branches (shard key = ZIP). Sending a letter to one ZIP goes straight to one branch — fast. But "how many letters are in transit nationwide?" forces you to phone every branch and add up the answers (scatter-gather). Pick a split (ZIP) so most tasks hit one branch, and pray you never have to re-draw all the ZIP boundaries.

14. Backups & Recovery

The database holds irreplaceable data. Backups — and tested restores — are non-negotiable.

Postgres backup basics
pg_dump mydb > backup.sql              # logical backup (portable, slower)
pg_restore -d mydb backup.dump          # restore
# Physical backups + WAL archiving enable Point-In-Time Recovery (PITR):
#   restore to any moment — e.g. "just before the bad DELETE at 14:32"
An untested backup is not a backup

The classic disaster: backups ran for years but were never test-restored — and turn out corrupt or incomplete when you finally need them. Regularly restore to a scratch environment and verify. Also follow the 3-2-1 rule: 3 copies, 2 different media, 1 offsite. Know your RPO (how much data loss is acceptable → backup frequency) and RTO (how fast you must recover → restore method). Ties to the SRE DR section.

Why backups differ from replication, and how PITR works

Replication protects against hardware failure but not against logical failure: a bad DELETE, a buggy migration, or ransomware replicates to every replica in milliseconds. Backups are a point-in-time copy you can roll back to — the only defense against "we destroyed our own data." That's why replicas are not backups.

How Point-In-Time Recovery works — the same WAL, again. PITR combines two things: a periodic base backup (a full physical snapshot of the data files) plus a continuous archive of every WAL segment since. To recover to "just before the bad DELETE at 14:32:07," you restore the most recent base backup taken before that time, then replay the archived WAL forward and tell the database to stop exactly at that timestamp (or transaction ID). Because the WAL is an ordered log of every change, replaying it up to a chosen point reconstructs the database as it existed at that precise instant. Your RPO is bounded by how frequently WAL is archived; your RTO by how long the restore + replay takes.

Enable continuous WAL archiving for PITR (postgresql.conf)
wal_level = replica
archive_mode = on
archive_command = 'test ! -f /archive/%f && cp %p /archive/%f'   # ship each WAL segment
Worked example: recover to just before a mistake
# 1. Restore the latest base backup into a fresh data directory
tar -xzf base_backup_2024-06-10.tar.gz -C /var/lib/pgsql/restore

# 2. Tell Postgres to replay WAL and STOP right before the bad statement
cat > /var/lib/pgsql/restore/recovery.signal <<'EOF'
EOF
# in postgresql.auto.conf:
#   restore_command = 'cp /archive/%f %p'
#   recovery_target_time = '2024-06-10 14:32:06'   # one second before the DELETE
#   recovery_target_action = 'promote'

# 3. Start the server — it replays WAL up to 14:32:06 and comes up clean.
pg_ctl -D /var/lib/pgsql/restore start
Common backup mistakes & gotchas
  • Never test-restoring — the backup is silently broken until the day you need it. Schedule automated restore drills.
  • Backups on the same disk/account/region as the primary — one failure (or one compromised credential) takes out both. 3-2-1: offsite and isolated.
  • No WAL archiving — nightly dumps alone mean up to 24h of data loss; PITR closes the gap to minutes/seconds.
  • Unencrypted or world-readable backups — a backup is a full copy of your data; secure it as strictly as the database.
  • Not measuring RTO — a 2 TB restore might take 8 hours; if your RTO is 1 hour you need a different strategy (hot standby, snapshots).
Mental model: save points in a video game

Replication is playing co-op — if one console dies, your partner still has the live game. But if you both walk into a trap, you're both dead. Backups are save points: PITR is a save point every few seconds, so after a disaster you reload to the exact moment before you stepped on the trap. And an untested backup is a save file you never tried to load — you don't know it's corrupt until it's the only thing standing between you and starting over.

15. Running Databases in Production

Production database checklist
  • High availability — multi-AZ primary + replica with automated failover.
  • Backups + tested PITR; monitor that backups actually run.
  • Connection pooling (PgBouncer) — databases have limited connections; pools prevent exhaustion.
  • Monitor — slow queries, replication lag, connections, disk, cache hit ratio.
  • Safe migrations — additive changes, avoid locking large tables (see below).
  • Prefer managed (RDS/Aurora/Cloud SQL) unless you have a strong reason — see the Cloud DB section.
Schema migrations can lock your table

Some ALTER TABLE operations lock the whole table, freezing your app during the change on a big table. Use tools like gh-ost, pt-online-schema-change, or Postgres' concurrent index builds (CREATE INDEX CONCURRENTLY). Make migrations backward-compatible and multi-step (add column → backfill → switch code → drop old) so deploys stay zero-downtime — connects to the CI/CD deployment strategies.

Why production databases need special care, and how the pieces fit

Everything else in this guide converges here. A production database is a stateful, single-point-of-truth service that cannot simply be restarted or scaled like a stateless web server — so operating it safely means combining availability (replication + failover), recoverability (tested backups + PITR), performance (indexes + query tuning), and safe change management (online migrations). The failure modes are correlated: a bad migration locks a table, connections pile up, the pool exhausts, health checks fail, and an automated failover promotes a replica mid-migration. Understanding why each safeguard exists lets you reason about these chains.

How connection pooling protects the database. Each Postgres connection is a real OS process consuming memory; a few hundred is often the practical ceiling. Modern apps (especially serverless/many-pod deployments) can try to open thousands. A pooler like PgBouncer sits in front and multiplexes many client connections onto a small set of real database connections (transaction pooling hands a backend connection to a client only for the duration of a transaction). This is why "too many connections" is an architecture fix (add a pooler, cap pool sizes), not a "raise the limit" fix.

Worked example: PgBouncer transaction pooling
[databases]
app = host=primary.db.internal port=5432 dbname=app

[pgbouncer]
pool_mode = transaction        ; hand out a backend only per-transaction
max_client_conn = 5000         ; app-facing connections it will accept
default_pool_size = 20         ; actual backend connections per db/user
reserve_pool_size = 5
; 5000 app connections funnel through ~20 real DB connections.
What to watch (the vital signs)
-- Connections in use vs the ceiling:
SELECT count(*), (SELECT setting::int FROM pg_settings WHERE name='max_connections') AS max
FROM pg_stat_activity;

-- Cache hit ratio (want > ~0.99; low means you're disk-bound):
SELECT sum(blks_hit)*1.0 / nullif(sum(blks_hit)+sum(blks_read),0) AS cache_hit_ratio
FROM pg_stat_database;

-- Longest-running queries / possible stuck transactions:
SELECT pid, now()-xact_start AS runtime, state, substr(query,1,50)
FROM pg_stat_activity WHERE state <> 'idle' ORDER BY runtime DESC LIMIT 5;
Common production mistakes & gotchas
  • No connection pooler — the app scales out, opens thousands of connections, and the database falls over under connection overhead alone.
  • Blocking migrations at peak — an ALTER TABLE that rewrites or takes an ACCESS EXCLUSIVE lock during traffic; do it online and off-peak.
  • Adding a NOT NULL column with a volatile default on a huge table — historically rewrote the whole table; add nullable, backfill in batches, then constrain.
  • No monitoring of replication lag / disk / cache hit ratio — you learn about the problem from users, not dashboards.
  • Self-managing without the expertise — for most teams a managed service (RDS/Aurora/Cloud SQL) handles failover, backups, and patching more reliably than a hand-rolled setup.
Mental model: the database is the hospital ICU

Stateless web servers are outpatients — send them home, swap them freely. The production database is the ICU patient wired to monitors: you don't reboot it on a whim, you watch its vitals continuously (connections, lag, disk, cache), you have blood on hand (backups) and a crash cart (failover), and any procedure (migration) is planned, reversible, and done with minimal disruption. Care scales with how irreplaceable the patient is.

16. ETL vs ELT & Data Pipelines

Data engineering moves data from where it's created to where it's analyzed. ETL and ELT are the two dominant patterns for that movement and transformation.

Why the industry flipped from ETL to ELT

The order of the letters encodes an economic assumption. ETL was born when warehouse storage and compute were expensive and rigid: you could not afford to store raw junk, so you cleaned and shaped data on a separate transform server before loading only the polished result. ELT flips this because two things changed: cloud object storage became nearly free, and cloud warehouses (Snowflake, BigQuery) became massively parallel SQL engines. Now it's cheaper and more flexible to load everything raw first and transform inside the warehouse with SQL — you keep the raw source (so you can re-transform when requirements change) and you use the warehouse's horsepower instead of a bespoke transform tier.

How idempotency and incremental loads work. A robust pipeline must survive re-runs (a task fails halfway and retries) without double-counting. The standard techniques: process by a bounded window and overwrite that window's partition (rather than append), or MERGE (upsert) on a natural key so re-processing the same rows is a no-op. Incremental models track a high-water mark (e.g., max(updated_at) already loaded) and only pull rows newer than it. These two ideas — idempotent writes and incremental extraction — are what separate a toy script from a production pipeline.

Worked example: an idempotent incremental ELT step (dbt-style MERGE)
-- Load only new/changed source rows since the last run, then upsert.
MERGE INTO analytics.orders AS tgt
USING (
  SELECT * FROM raw.orders
  WHERE updated_at > (SELECT COALESCE(MAX(updated_at), '1900-01-01')
                     FROM analytics.orders)
) AS src
ON tgt.order_id = src.order_id
WHEN MATCHED THEN UPDATE SET total = src.total, updated_at = src.updated_at
WHEN NOT MATCHED THEN INSERT (order_id, total, updated_at)
                     VALUES (src.order_id, src.total, src.updated_at);
-- Re-running this is safe: already-loaded rows match and update in place.
Common pipeline mistakes & gotchas
  • Non-idempotent appends — a retried task appends the same rows twice and revenue doubles; use overwrite-partition or MERGE.
  • Full reloads every run — reprocessing all history nightly is slow and expensive; track a high-water mark and go incremental.
  • Transforming away the raw data — classic ETL discards the source; when a bug in a transform is found you can't re-derive. ELT keeps raw so you can reprocess.
  • No schema-drift handling — a source adds/renames a column and the pipeline silently drops it or breaks; validate/contract-test the source.
  • Ignoring late-arriving data — events that arrive after their window closes get missed unless you reprocess a lookback window.
Mental model: cook-then-store vs store-then-cook

ETL is prepping and cooking every ingredient before it ever enters your pantry — only finished dishes go in, saving space but throwing away the raw ingredients (and the option to cook something else later). ELT is stocking the pantry with all the raw ingredients cheaply, then cooking whatever dish you need on demand in a very fast kitchen (the warehouse). Because you kept the raw ingredients, when someone asks for a new dish you just cook again — no need to re-shop.

17. Warehouses, Lakes & Lakehouse

Analytical data needs different storage than transactional apps. These are the three dominant architectures for storing data for analysis.

StoreWhat it isBest for
Data WarehouseStructured, optimized for analytical SQL (Snowflake, BigQuery, Redshift)BI dashboards, reporting, structured analytics
Data LakeRaw files of any type in cheap object storage (S3)Storing everything cheaply, ML, unstructured data
LakehouseWarehouse features on top of a lake (Databricks, Delta Lake, Iceberg)Unified — one platform for BI + ML
Warehouse vs lake, plainly

A data warehouse is a well-organized library — everything catalogued and structured, fast to query, but you must organize before storing. A data lake is a giant warehouse where you dump everything raw and cheap, then figure out structure later. A lakehouse tries to give you the lake's cheap flexibility with the warehouse's speed and reliability — the current direction of the industry.

OLTP vs OLAP

OLTP (transactional — Postgres, MySQL) handles many small reads/writes for your app: "get user 42," "insert this order." OLAP (analytical — warehouses) handles few huge queries scanning millions of rows for analysis: "revenue by region last quarter." Don't run heavy analytics on your production OLTP database — it competes with app traffic. Replicate/ETL into an analytical store instead.

Why analytics needs a different engine: rows vs columns

The deep reason OLAP and OLTP use different systems is physical storage layout. OLTP databases are row-stores: all columns of a row sit together, so fetching or updating one whole record is one cheap read — perfect for "get order 12345." OLAP warehouses are column-stores: each column is stored contiguously and separately. An analytical query like "average order total last quarter" reads only the total and created_at columns and skips the other 40 entirely — reading a fraction of the bytes. And because a column holds values of one type, often similar, it compresses spectacularly (dictionary, run-length, delta encoding), so less data moves off disk. That's why a warehouse scans a billion rows for one metric in seconds while doing the same on your OLTP primary would melt it.

How the lakehouse squares the circle. A pure data lake is just files (Parquet) in object storage — cheap and open, but with no transactions, no schema enforcement, and no easy updates/deletes. Lakehouse table formats (Delta Lake, Apache Iceberg, Hudi) add a transaction log on top of those Parquet files: the log records which files make up the current table version, enabling ACID commits, UPDATE/DELETE/MERGE, schema evolution, and "time travel" to a past version — all while the data stays as open columnar files in your own storage. You get the warehouse's reliability with the lake's cost and openness.

Worked example: lakehouse features you can't get from raw files
-- Iceberg/Delta table backed by Parquet in object storage, but transactional:
MERGE INTO lake.dim_customers t USING staging.updates s
  ON t.id = s.id
  WHEN MATCHED THEN UPDATE SET t.email = s.email
  WHEN NOT MATCHED THEN INSERT *;         -- ACID upsert over files

-- "Time travel" — query the table as it existed yesterday (audit / recovery):
SELECT count(*) FROM lake.dim_customers TIMESTAMP AS OF '2024-06-09 00:00:00';

-- Schema evolution without rewriting all data:
ALTER TABLE lake.dim_customers ADD COLUMN loyalty_tier string;
Common warehouse/lake mistakes & gotchas
  • Running BI queries on the OLTP primary — a full-scan report locks buffers and starves app traffic; isolate analytics in a warehouse.
  • Data lake → data swamp — dumping files with no catalog, schema, or governance until nobody can find or trust anything.
  • Many small files — millions of tiny Parquet files cripple query planning; compact them ("optimize"/bin-packing).
  • SELECT * in a column-store — forces reading every column, throwing away the whole point of columnar storage; select only what you need.
  • Treating the warehouse as OLTP — single-row inserts/updates into a columnar warehouse are slow; batch loads and use MERGE.
Mental model: filing by row vs filing by column

OLTP files one folder per customer — everything about that customer in one place, so pulling one customer is instant. OLAP files one drawer per field — all the "order totals" in one drawer, all the "dates" in another. Asking "what's our total revenue?" means opening just the totals drawer and adding it up, ignoring every other drawer. The lakehouse keeps those drawers as cheap open boxes in a warehouse but adds a logbook so edits are safe and you can peek at how the drawers looked last week.

18. Batch vs Streaming

Data pipelines process either in scheduled chunks (batch) or continuously as events arrive (streaming). Modern architectures often use both.

BatchStreaming
ProcessesChunks on a schedule (hourly/daily)Events continuously, in near-real-time
LatencyMinutes to hoursMilliseconds to seconds
ToolsSpark, dbt, scheduled jobsKafka Streams, Flink (see Kafka Streams)
Use forReports, ML training, large aggregationsFraud detection, live dashboards, alerting
The convergence: streaming-first

Older "Lambda architecture" ran batch and streaming in parallel (complex, duplicated logic). Modern "Kappa architecture" treats everything as a stream and derives batch views from it — simpler. Tools like Apache Flink and Kafka Streams enable this. The Kafka guide covers the streaming backbone in depth.

Why the choice exists, and how streaming handles time

The batch-vs-streaming decision is fundamentally about the latency you need versus the simplicity you want. Batch is simpler because it works over a complete, bounded dataset — you know when "all of yesterday's data" has arrived, so aggregations are exact and re-runnable. Streaming is harder because the data is unbounded and never "done": to compute "orders per minute" you must decide when a minute is complete, even though events can arrive late or out of order.

How streaming resolves this: windows, event-time, and watermarks. Stream processors group unbounded events into windows (tumbling 1-minute buckets, sliding, or session windows). Crucially they use event time (when the event actually happened, from its timestamp) rather than processing time (when it reached the engine), because network delays reorder events. To know when a window can be finalized, the engine tracks a watermark — an estimate that "we've probably seen all events up to time T." When the watermark passes a window's end, that window is emitted; events arriving after are "late" and handled by policy (drop, or update the result). This machinery — windows + event-time + watermarks — is what lets a stream produce correct time-based aggregates despite chaos.

Worked example: an event-time tumbling window (Flink SQL)
-- Count orders per 1-minute window using EVENT time, tolerating 10s of lateness.
SELECT
  window_start,
  COUNT(*) AS orders
FROM TABLE(
  TUMBLE(TABLE order_events, DESCRIPTOR(event_ts), INTERVAL '1' MINUTE)
)
GROUP BY window_start;
-- The watermark (declared on event_ts as event_ts - INTERVAL '10' SECOND)
-- decides when each 1-minute bucket is "complete" and safe to emit.
Common batch/streaming mistakes & gotchas
  • Using processing time when you mean event time — a delayed batch of events lands in the wrong minute; metrics wobble and can't be reconciled with source systems.
  • Streaming when batch would do — real-time infrastructure is far more operationally complex; if a daily report suffices, don't build a stream.
  • Ignoring exactly-once semantics — naive stream processors double-count on retry; use the engine's checkpointing + idempotent/transactional sinks.
  • Unbounded state — windows or joins that never expire grow state forever and eventually OOM; set state TTL / bounded windows.
  • Lambda-architecture drift — maintaining separate batch and streaming code paths that slowly compute different answers.
Mental model: mailbox once a day vs a live phone call

Batch is checking your mailbox once a day: everything for the day has arrived, you process the whole stack at once, simple and complete. Streaming is a phone that rings every time something happens: you react instantly, but you must handle calls arriving out of order and decide how long to wait before declaring "that's everyone for this minute" (the watermark). Choose the phone only when waiting for the mail is genuinely too slow.

19. Orchestration & the Modern Data Stack

Data pipelines have many steps with dependencies. Orchestrators schedule them, handle failures/retries, and track lineage.

LayerTools
IngestionFivetran, Airbyte, Kafka Connect
Transformationdbt (SQL transforms + tests + docs)
OrchestrationAirflow, Dagster, Prefect
Warehouse/computeSnowflake, BigQuery, Databricks
BILooker, Metabase, Superset
dbt changed data engineering

dbt lets analysts transform data in the warehouse using just SQL + Jinja, with version control, testing, documentation, and dependency management — bringing software-engineering discipline (the same as this whole learning hub teaches) to analytics. It's the centerpiece of the modern ELT stack.

Why orchestration exists and how a DAG scheduler works

A real pipeline is dozens of interdependent tasks: you can't transform before you extract, can't build the revenue model before both orders and refunds have loaded, and you must retry the flaky API pull without re-running everything downstream. Doing this with cron and shell scripts collapses the moment dependencies or failures appear — cron has no notion of "run B only after A succeeds." Orchestrators exist to model those dependencies explicitly and manage execution, retries, and observability.

How the scheduler works under the hood. You declare tasks and their dependencies as a DAG (directed acyclic graph — no cycles, so there's always a valid execution order). The scheduler computes a topological order and runs each task only once all its upstream dependencies have succeeded, parallelizing independent branches. Each task run has a state (queued → running → success/failed/retrying); on failure it retries per policy (often exponential backoff) and, if still failing, marks downstream tasks blocked rather than running them on bad data. Backfilling re-runs the DAG for a range of past logical dates — which only works correctly if tasks are idempotent (rerunning a date produces the same result), tying straight back to the idempotency principle from §16.

Worked example: dependencies + retries as a DAG (Airflow)
from airflow.decorators import dag, task
from datetime import datetime, timedelta

@dag(schedule="@daily", start_date=datetime(2024,1,1), catchup=True,
     default_args={"retries": 3, "retry_delay": timedelta(minutes=5)})
def revenue_pipeline():
    @task
    def extract_orders(): ...
    @task
    def extract_refunds(): ...
    @task
    def build_revenue(orders, refunds): ...   # runs only after BOTH succeed

    o = extract_orders()
    r = extract_refunds()
    build_revenue(o, r)     # dependency edges inferred -> a DAG

revenue_pipeline()
# extract_orders and extract_refunds run in parallel; build_revenue waits for
# both; any task retries 3x before failing and blocking downstream. catchup=True
# backfills every missed daily run — safe only because tasks are idempotent.
Common orchestration mistakes & gotchas
  • Non-idempotent tasks + backfill — re-running historical dates double-writes; make every task safe to re-run (overwrite/MERGE by logical date).
  • Hidden dependencies — two tasks that secretly share state but have no DAG edge run in the wrong order intermittently; make all dependencies explicit.
  • Giant monolithic tasks — one task that does everything can't be retried granularly and hides where it failed; split into meaningful units.
  • Doing heavy compute in the orchestrator — Airflow schedules work; it shouldn't crunch the data itself. Push compute to the warehouse/Spark and let the orchestrator coordinate.
  • No data-quality gates — pipelines happily load garbage; add tests (dbt tests, expectations) that fail the run before bad data reaches dashboards.
Mental model: a kitchen expediter

An orchestrator is the head chef calling out the order of operations: "sauce and pasta can go at the same time; don't plate until both are done; if the sauce burns, remake just the sauce, don't redo the pasta." It doesn't cook (that's the warehouse/Spark) — it sequences, parallelizes what's independent, retries what fails, and refuses to send out a half-finished plate. A DAG is just that ordered recipe with no step depending on itself.

20. Best Practices — the checklist

Databases & data best practices
  • Choose the right database type for your data shape & access pattern (polyglot is fine).
  • Start normalized; denormalize deliberately for read performance.
  • Index what you query; verify with EXPLAIN ANALYZE; avoid N+1.
  • Use transactions for correctness; pick the right isolation level.
  • HA via multi-AZ + replicas + automated failover; connection pooling.
  • Tested backups + PITR; know your RPO/RTO; 3-2-1 rule.
  • Cache hot reads (with a sane invalidation strategy).
  • Zero-downtime, backward-compatible schema migrations.
  • Separate OLTP (app) from OLAP (analytics); ELT into a warehouse.
  • Prefer managed databases unless you have a strong reason not to.

21. Troubleshooting Playbook

Queries suddenly slow

Check for a missing/unused index (EXPLAIN ANALYZE shows a seq scan), stale statistics (run ANALYZE), a table that grew past a threshold, or lock contention. Also check for a recently-deployed N+1 pattern via traces.

"Too many connections"

The app opened more connections than the DB allows (each is expensive). Add a connection pooler (PgBouncer), lower per-instance pool sizes, and check for connection leaks (connections not being released).

Replica serving stale data

Replication lag. Check lag metrics; route read-after-write to the primary; investigate why the replica is behind (heavy write load, slow network, long-running query on the replica).

Deadlocks

Two transactions each hold a lock the other needs. The DB kills one. Fix by acquiring locks in a consistent order everywhere, keeping transactions short, and reducing their scope.

Disk filling up

Unbounded table growth, un-rotated logs, bloat (Postgres — run VACUUM), or WAL/binlog accumulation. Archive old data, set retention, monitor disk with alerts well before it fills.
