Networking & DNS: The Complete Guide

Every distributed system is networking underneath. Understand it from the ground up — packets, IP, TCP/UDP, routing, DNS, HTTP, TLS, and load balancing — so you can design and debug any system with confidence.

📖 How to read this guide

Each concept: what it is (plain English), why it exists, how it works (with diagrams), and ★ best practice. This underpins the Linux, Cloud/AWS, Kubernetes, and Security guides — networking is the common thread through all of them.

1. Why Networking Matters

Every API call, container-to-container message, database query, and user request travels over a network. When something is "slow" or "can't connect," the answer is usually in the network layer — so networking is a debugging superpower.

Networking = the postal system for computers

When you send a letter, you don't think about the trucks, sorting centers, and routes — but they all must work for it to arrive. Computer networking is the same: your app hands over data, and layers of addressing (IP), delivery guarantees (TCP), and name lookups (DNS) get it to the right machine and back. Learning these layers means when a "letter" gets lost, you know exactly which sorting center to check.

Why this matters in practice. Networking exists because computers are useless in isolation — value comes from them cooperating. Every microservice call, every database read, every page load is a negotiated conversation across shared infrastructure you don't own and can't see. When you understand how that conversation is structured, "the API is flaky" stops being a mystery and becomes a set of measurable, checkable stages: name lookup, connection setup, data transfer, response.

How a request actually flows (the 30-second mental model). Type curl https://api.example.com/users and this happens in order: (1) DNS turns the name into an IP; (2) the OS opens a TCP connection to that IP on port 443 (three-way handshake); (3) TLS negotiates encryption; (4) your HTTP request bytes are sent, wrapped in TCP segments, wrapped in IP packets, wrapped in Ethernet frames, hopping router to router; (5) the server processes it and the reply retraces the path. Every guide section below is one stage of this single flow.

See every stage of one request, timed
curl -w 'dns:%{time_namelookup}s connect:%{time_connect}s tls:%{time_appconnect}s ttfb:%{time_starttransfer}s total:%{time_total}s\n' \
  -o /dev/null -s https://api.example.com/users
output
dns:0.021s connect:0.043s tls:0.121s ttfb:0.198s total:0.205s
Reading that output

Each number is cumulative from the start. Subtract to isolate a stage: TLS handshake here took 0.121 - 0.043 = 0.078s; the server's think time (TTFB minus TLS) took 0.198 - 0.121 = 0.077s. If time_namelookup is high, blame DNS; if time_connect is high, blame the network/routing; if TTFB is high, blame the application or database. One command localizes a "slow site" to a layer.

Common mistakes

Blaming "the network" for what is really slow DNS or a slow backend — always time the stages first. Testing with ping and concluding the service works (ping is L3/ICMP and says nothing about whether port 443 or the app is healthy). Assuming a working local curl means production works — different DNS, firewalls, and routes apply there.

2. The OSI & TCP/IP Models

Networking is organized into layers, each handling one job and talking to the layer above and below. The OSI model has 7 layers; the practical TCP/IP model collapses them into 4.

Use the layers to debug systematically

"Can't reach the service" → check each layer: is the interface up (L1/2, ip link)? Can you route to the IP (L3, ping/traceroute)? Is the port open (L4, nc/ss)? Does the app respond (L7, curl)? Isolating the failing layer turns a vague problem into a specific one.

Why layers exist. The layer model is a contract: each layer only needs to do its one job and talk to its immediate neighbors. That means Ethernet can be replaced by Wi-Fi without changing IP; IP can carry TCP or UDP without caring which; HTTP can run over TCP (HTTP/1.1, HTTP/2) or over QUIC/UDP (HTTP/3) without rewriting the network. This separation is why the internet could evolve for 40 years without a rewrite — you swap one layer's implementation while the others stay put.

How data moves through the layers (encapsulation preview). Going down the stack on the sender, each layer prepends its own header to whatever the layer above handed it: the app produces data → Transport adds a TCP/UDP header (ports, sequence numbers) making a segment → Network adds an IP header (source/dest IP) making a packet → Link adds an Ethernet header + trailer (source/dest MAC, checksum) making a frame. On the receiver, each layer strips its own header and hands the payload up. A layer never inspects the layers above it — a router reads only the IP header and forwards; it neither knows nor cares that it's carrying HTTP.

Map real tools to layers
ip link show          # L1/L2 — is the interface up? MAC address, link state
ip addr show          # L3   — what IP(s) are assigned?
ping 1.1.1.1          # L3   — ICMP reachability (no ports involved)
ss -tlnp              # L4   — which TCP ports are listening
curl -v https://x     # L7   — application request/response
output (ip link show, trimmed)
2: eth0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 ...
    link/ether 02:42:ac:11:00:02 brd ff:ff:ff:ff:ff:ff
Reading that: UP vs LOWER_UP

UP means the interface is administratively enabled; LOWER_UP means the physical link (cable/carrier) is actually present. Seeing UP without LOWER_UP means "the OS turned it on but there's no signal" — a classic L1 problem. mtu 1500 is the max frame payload; mismatched MTUs across a path cause mysterious hangs on large transfers.

The layers = a company shipping department

The app is the person who wrote the letter. Transport is the assistant who numbers the pages so nothing is lost or out of order. Network is the mailroom that writes the destination city on the envelope. Link is the courier who carries it to the next building. Each only does their job and trusts the next — nobody re-reads the letter to deliver it.

Common mistakes

Treating OSI's 7 layers as literal running software — real stacks use the 4-layer TCP/IP model; layers 5–7 are merged into "the application." Debugging top-down when bottom-up is faster (confirm the interface and route before suspecting the app). Forgetting that a router operating at L3 will silently drop frames whose L2 details it can't handle — so "ping works but nothing else" often means an MTU or MSS mismatch two layers down.

3. Packets, Frames & Encapsulation

Data doesn't travel as one blob — it's split into packets, each wrapped with headers from each layer. This wrapping is called encapsulation.

Why encapsulation exists. Splitting data into packets and wrapping each independently means the network can route around failures (each packet can take a different path), share a link fairly (packets from many conversations interleave), and detect corruption per-hop (checksums). If we sent one giant blob, a single lost bit would ruin everything and one big transfer would monopolize the wire.

How the headers stack, byte by byte. Say you send a 100-byte HTTP request. Transport prepends a 20-byte TCP header (source port, dest port 443, sequence number, ACK number, flags, window size) → 120-byte segment. Network prepends a 20-byte IPv4 header (version, TTL, protocol=6 for TCP, source IP, dest IP, header checksum) → 140-byte packet. Link prepends a 14-byte Ethernet header (dest MAC, source MAC, ethertype 0x0800 for IPv4) and appends a 4-byte CRC trailer → 158-byte frame on the wire. At the receiver, each layer removes exactly its own bytes and hands the rest up. This is why real throughput is always less than link speed — headers are overhead on every packet.

Watch encapsulation live with tcpdump
sudo tcpdump -i any -n -v -X -c 1 'tcp port 443 and tcp[tcpflags] & tcp-syn != 0'
output (annotated)
10:15:02.331 IP (tos 0x0, ttl 64, id 44201, proto TCP (6), length 60)   <- IP header
    192.168.1.20.51544 > 93.184.216.34.443: Flags [S], seq 981..., win 64240,   <- TCP header (SYN)
      options [mss 1460,sackOK,TS...,nop,wscale 7], length 0
    0x0000:  4500 003c ac69 4000 4006 ...   <- raw bytes: 45=IPv4+20B header, 06=TCP
    0x0010:  c0a8 0114 5db8 d822 c958 01bb   <- c0a80114 = 192.168.1.20, ...01bb = port 443
Decoding the hex

45 = IP version 4, header length 5×4=20 bytes. 06 in the protocol field = TCP. c0a8 0114 is 192.168.1.20 in hex (192=0xc0, 168=0xa8, 1=0x01, 20=0x14). 01bb = 443. The [S] flag is the SYN — this is literally the first packet of the handshake, captured before any data flows. mss 1460 is the largest TCP payload this host will accept in one segment (1500 MTU − 20 IP − 20 TCP).

Encapsulation = Russian nesting dolls of envelopes

Your message goes in a small envelope labeled with the door number (port). That goes in a bigger envelope labeled with the street address (IP). That goes in a shipping box labeled with the local depot handoff (MAC). Each handler opens only the layer they're responsible for and passes the rest along untouched.

Common mistakes & gotchas

MTU/MSS mismatch: if a packet is larger than a link's MTU and the "don't fragment" bit is set, it's dropped — causing transfers that hang after the handshake succeeds (small packets pass, big ones vanish). This is the classic VPN/tunnel bug; the fix is MSS clamping. Fragmentation: IP can fragment oversized packets, but fragments hurt performance and confuse some firewalls. Assuming packet order: IP makes no ordering guarantee — packets can arrive out of order; TCP reassembles them, UDP does not.

4. IP Addressing & Subnetting

Every device on a network has an IP address — its unique location. Subnetting divides a network into smaller logical segments.

RangeTypeUse
10.0.0.0/8PrivateLarge private networks (clouds love this)
172.16.0.0/12PrivateMedium private networks
192.168.0.0/16PrivateHome/small networks
127.0.0.0/8Loopbacklocalhost (this machine)
Everything elsePublicRoutable on the internet
IP address = a building address; subnet = the neighborhood

An IP like 10.0.3.47 is a specific building. The subnet mask decides how much of that address is the "neighborhood" (network) versus the "house number" (host). Devices in the same neighborhood can talk directly; to reach another neighborhood, traffic goes through a gateway (the router — the neighborhood exit).

Why subnetting exists. Without subnets, every device would have to be on one giant flat network — broadcasts would swamp it, and there'd be no natural security boundary. Subnetting lets you carve address space into segments that map to purpose (web tier, DB tier), location (AZ, office), or trust level, and firewalls/routes then control what crosses between them. It also keeps broadcast domains small so ARP traffic doesn't drown the network.

How a host decides "local or remote." When your machine wants to send to an IP, it ANDs its own IP and the destination IP with its subnet mask. If the resulting network portions match, the destination is on the same subnet → deliver directly via ARP (find its MAC, send the frame). If they differ, the destination is remote → send the frame to the default gateway's MAC instead, and let the router forward it. Example: host 10.0.3.47/24 (mask 255.255.255.0) talking to 10.0.3.90 → both are 10.0.3.x → local. Talking to 10.0.9.5 → different third octet → remote → goes to the gateway.

Inspect addressing and test local vs remote
ip -brief addr                 # concise: interface, state, IP/prefix
ip route get 10.0.3.90         # same subnet? -> delivered directly (dev eth0)
ip route get 8.8.8.8           # remote?     -> goes via the default gateway
ip neigh                       # the ARP table: IP -> MAC for local neighbors
output
$ ip route get 10.0.3.90
10.0.3.90 dev eth0 src 10.0.3.47 uid 1000        <- direct, no gateway = same subnet
$ ip route get 8.8.8.8
8.8.8.8 via 10.0.3.1 dev eth0 src 10.0.3.47 uid 1000   <- "via 10.0.3.1" = through gateway
The tell: "via" or not

If ip route get shows via <ip>, the kernel decided the target is remote and will hand the packet to that gateway. If there's no via, it's directly connected on that subnet. This single command answers "why can't these two hosts talk" faster than any ping — it shows the routing decision itself.

Common mistakes & gotchas

Confusing the network address (10.0.3.0, all-host-bits-zero) and broadcast address (10.0.3.255, all-host-bits-one) with usable host addresses — neither can be assigned to a device. Putting two hosts on overlapping-but-different masks (/24 vs /25) so each thinks the other is remote → one-way connectivity. Forgetting the loopback 127.0.0.1 only ever reaches the same machine — a service bound only to 127.0.0.1 is invisible to the network no matter how open the firewall is.

5. CIDR & Subnet Math

CIDR notation (/24) is how we express subnet size. The number is how many bits are fixed for the network — the rest are available for hosts.

CIDRSubnet maskUsable hostsCommon use
/24255.255.255.0254A typical subnet
/16255.255.0.065,534A whole VPC
/28255.255.255.24014Small subnet (a few servers)
/32255.255.255.2551A single host (firewall rules)
Subnet math quickly
# Hosts in a /N (IPv4): 2^(32-N) minus 2 (network + broadcast)
#   /24 -> 2^8 - 2 = 254
# Use ipcalc to see everything:
ipcalc 10.0.3.0/24
#   Network:   10.0.3.0/24
#   HostMin:   10.0.3.1   HostMax: 10.0.3.254   Broadcast: 10.0.3.255
Plan VPC CIDRs before you build

Pick non-overlapping ranges up front (e.g. prod 10.0.0.0/16, staging 10.1.0.0/16). Overlapping CIDRs make VPC peering and VPN connections impossible without painful re-addressing later. See the Cloud VPC section.

Why CIDR exists. The old "classful" system (Class A/B/C) wasted enormous space — if you needed 300 addresses you had to take a whole Class B (65k) because a Class C (254) was too small. CIDR ("classless") lets the prefix length be any number of bits, so you allocate exactly what you need and can aggregate many small routes into one big advertisement (route summarization), which keeps the internet's routing tables manageable.

How the math works, in binary. The /N means "the first N bits are the network; the remaining 32−N are host bits." A /24 fixes the first 24 bits, leaving 8 host bits → 2⁸ = 256 addresses, minus 2 (network + broadcast) = 254 usable. To split a /24 into two /25s, you borrow one host bit for the network: 10.0.3.0/25 covers .0–.127 and 10.0.3.128/25 covers .128–.255. Each halving of the block adds one to the prefix. The "magic number" for the last significant octet is 256 − maskvalue: a /26 mask is 255.255.255.192, and 256−192=64, so subnets start at .0, .64, .128, .192.

Split and verify subnets
ipcalc -b 10.0.3.0/26          # first /26 block: .0 network, .1-.62 hosts, .63 broadcast
python3 -c 'import ipaddress as i; print(list(i.ip_network("10.0.3.0/24").subnets(new_prefix=26)))'
output
[IPv4Network('10.0.3.0/26'), IPv4Network('10.0.3.64/26'),
 IPv4Network('10.0.3.128/26'), IPv4Network('10.0.3.192/26')]
Fast field arithmetic

Memorize the mask→count table for the last octet: /25=128 addrs, /26=64, /27=32, /28=16, /29=8, /30=4. A /30 gives 4 addresses = 2 usable — exactly right for a point-to-point link between two routers. A /31 (RFC 3021) gives 2 addresses both usable for point-to-point, saving space.

CIDR = how big a plot of land you're fenced off

The /N is the length of your fence in bits. A small number like /8 fences off a huge territory (millions of addresses); a big number like /30 fences off a tiny plot (just 4). More bits fixed = smaller neighborhood.

Common mistakes & gotchas

Cloud providers reserve extra addresses per subnet — AWS reserves 5 (network, VPC router, DNS, future use, broadcast), so a /28 gives you 11 usable, not 14. Off-by-one on broadcast/network when hand-assigning IPs. Choosing a /16 "to be safe" for every subnet and exhausting the VPC's address space. Overlapping CIDRs between environments make peering/VPN impossible — plan the whole address plan on paper first.

6. IPv6

IPv4 ran out of addresses; IPv6 provides an effectively unlimited supply (128-bit addresses). Increasingly required for modern, global systems.

IPv6 essentials
  • Addresses look like 2001:db8::1 (hex, :: compresses zeros).
  • No NAT needed — every device can have a globally-routable address.
  • Dual-stack (run IPv4 + IPv6 together) is the common migration path.
  • Cloud load balancers and CDNs handle IPv6 at the edge even if your backend is IPv4.

Why IPv6 exists. IPv4's 32 bits give ~4.3 billion addresses — fewer than there are phones on Earth. We stretched it with NAT and private ranges, but NAT breaks end-to-end connectivity and adds state/complexity. IPv6's 128 bits give 3.4×10³⁸ addresses — enough that every device can have its own globally-routable address, restoring the internet's original peer-to-peer design without NAT.

How addressing works under the hood. An IPv6 address is 128 bits, written as eight 16-bit hex groups. Rules: leading zeros in a group can be dropped (0db8 → db8), and one run of all-zero groups can be replaced with :: (only once, to stay unambiguous). A typical unicast address splits into a /64 network prefix and a 64-bit interface ID. Hosts can autoconfigure (SLAAC): the router advertises the /64 prefix, and the host generates its own interface ID — no DHCP needed. Every interface also has a link-local address starting fe80:: used for on-link talk (like ARP's role, handled by NDP — Neighbor Discovery Protocol, which replaces ARP).

Work with IPv6
ip -6 addr show                     # your IPv6 addresses (note fe80:: link-local)
ping6 2606:4700:4700::1111          # ping Cloudflare's IPv6 resolver
ip -6 neigh                         # NDP neighbor cache (IPv6's ARP table)
dig AAAA example.com +short         # look up the IPv6 (AAAA) record
curl -6 -sI https://example.com     # force the request over IPv6
output (ip -6 addr, trimmed)
2: eth0: ...
    inet6 2001:db8:85a3::8a2e:370:7334/64 scope global   <- routable, from router's prefix
    inet6 fe80::42:acff:fe11:2/64 scope link             <- link-local, on-wire only
scope global vs scope link

scope global is internet-routable. scope link (fe80::) works only on the local segment and needs a zone index to use (ping6 fe80::1%eth0). If you only have a link-local address and no global one, the router isn't advertising a prefix (no SLAAC/DHCPv6) — that's why you can reach neighbors but not the internet.

Common mistakes & gotchas

Configuring firewall rules only for IPv4 and leaving IPv6 wide open — dual-stack hosts are reachable over both; secure both. Assuming localhost is 127.0.0.1 when the app actually binds to ::1 (IPv6 loopback) first, causing "connection refused" on the v4 address. Forgetting that :: can appear only once in an address. Hardcoding /32 host masks (IPv4 thinking) — single IPv6 hosts are typically /128.

7. NAT & Private Networks

Network Address Translation lets many private devices share one public IP — and is why your laptop's 192.168.x.x can reach the internet.

Why NAT exists. There aren't enough public IPv4 addresses for every device, so NAT lets an entire private network share one (or a few) public IPs. As a side effect it provides a crude firewall: because inbound packets have no existing mapping, unsolicited connections from the internet are dropped — private hosts can initiate outbound but aren't directly reachable inbound.

How NAT rewrites packets (PAT / "NAT overload"). The common form is Port Address Translation. When 10.0.0.5:51000 sends to 93.184.216.34:443, the NAT gateway: (1) rewrites the source to its public IP and a chosen port, e.g. 203.0.113.9:40001; (2) stores a mapping 203.0.113.9:40001 ↔ 10.0.0.5:51000 in its translation table with the destination and a timeout; (3) recomputes the IP/TCP checksums (they cover the addresses/ports) and forwards. When the reply comes back to 203.0.113.9:40001, the gateway looks up the table, rewrites the destination back to 10.0.0.5:51000, and delivers. The port is the key that distinguishes which internal host each conversation belongs to — that's how many hosts share one IP.

See NAT rules and the live translation table (Linux)
sudo iptables -t nat -L -n -v            # show NAT rules (look for MASQUERADE)
sudo nft list ruleset                    # nftables equivalent
sudo conntrack -L                        # live connection-tracking / translation table
curl -s ifconfig.me                      # what public IP does the world see? (post-NAT)
output (conntrack -L, one line)
tcp 6 431999 ESTABLISHED src=10.0.0.5 dst=93.184.216.34 sport=51000 dport=443 \
  src=93.184.216.34 dst=203.0.113.9 sport=443 dport=40001 [ASSURED]
Reading the conntrack entry

The first src/dst pair is the original direction (inside view); the second is the reply direction (outside view). Here internal 10.0.0.5:51000 is presented to the world as 203.0.113.9:40001. 431999 is the seconds until this idle mapping expires. When that timer lapses on a quiet connection, the mapping is dropped and replies stop arriving — the root cause of "long-lived idle connections mysteriously die behind NAT."

NAT = a receptionist with one public phone number

The whole office shares one external number. When you call out, the receptionist notes "extension 12 is talking to the bank" and puts your call on an outside line. When the bank calls back on that line, she knows to transfer it to extension 12. Outsiders can't dial your extension directly — they can only reply to calls you started.

Common mistakes & gotchas

Expecting inbound connections to a NATed host without a port-forward/DNAT rule — they can't work by design. Idle timeouts killing long-lived connections (databases, SSH, websockets); fix with TCP keepalives shorter than the NAT timeout. Protocols that embed IPs in their payload (FTP active mode, SIP) break because NAT rewrites headers, not payload — needs an ALG. Two sites behind NAT with the same private range can't be peered without double-NAT. Losing the real client IP at the app — behind NAT/LB you must read X-Forwarded-For.

8. TCP vs UDP

The two transport protocols make opposite tradeoffs: TCP is reliable but has overhead; UDP is fast but makes no guarantees.

TCPUDP
ConnectionYes (3-way handshake)No (fire and forget)
ReliabilityGuaranteed delivery + orderBest-effort, may drop/reorder
SpeedSlower (acks, retransmits)Faster (no overhead)
Use forWeb, APIs, DB, SSH, emailDNS, video/voice, gaming, metrics

Why two protocols exist. Reliability and speed trade off. TCP guarantees every byte arrives, in order, exactly once — perfect for files, APIs, and databases where a corrupted or missing byte is unacceptable. UDP does none of that; it just fires a datagram and forgets — perfect for voice/video/gaming/DNS where a slightly-late packet is worse than a lost one (you'd rather skip a video frame than pause to re-fetch it).

How TCP guarantees delivery (handshake, sequence numbers, ACKs, windowing). After the SYN/SYN-ACK/ACK handshake establishes agreed starting sequence numbers, every byte is numbered. The receiver ACKs the highest contiguous byte it has (ACK 5001 means "I have everything up to 5000, send 5001 next"). If an ACK doesn't arrive within the retransmission timeout, the sender resends. Flow control uses the receive window: the receiver advertises how much buffer it has free (win 64240), and the sender never has more than that many unacknowledged bytes in flight — this prevents a fast sender from drowning a slow receiver. Congestion control (a separate mechanism: slow-start, then congestion avoidance) probes the network's capacity, shrinking the effective window on packet loss. So throughput ≈ window ÷ round-trip-time — high latency links need big windows (window scaling) to stay fast.

Observe TCP state, windows, and retransmits
ss -ti                                   # per-socket TCP internals: rtt, cwnd, retrans
ss -tan state established                # all established connections + queues
sudo tcpdump -i any -n 'tcp port 443'    # watch SYN/ACK/retransmissions live
nc -u -zv 8.8.8.8 53                      # test a UDP port (DNS) — no handshake
output (ss -ti, one socket)
ESTAB 0 0 10.0.0.5:51000 93.184.216.34:443
     cubic wscale:7,7 rto:204 rtt:3.1/1.5 mss:1460 cwnd:10 ssthresh:64
     bytes_sent:12000 retrans:0/0 rcv_space:64240
Reading the TCP internals

rtt:3.1/1.5 = smoothed round-trip 3.1ms (±1.5). cwnd:10 = congestion window of 10 segments — the sender can have ~10×1460 bytes in flight before waiting for ACKs. retrans:0/0 = no retransmissions (a healthy path); rising retrans means packet loss. rcv_space is the receive window. If cwnd stays tiny and retrans climbs, the network is lossy/congested; if the app is slow to read, the window shrinks and throughput drops even on a clean link.

TCP = registered mail, UDP = a postcard

TCP is registered mail: the recipient signs for each item, and anything not signed for is resent — nothing is lost, but it's slower and chattier. UDP is a postcard: you drop it in the box and hope it arrives. No signature, no resend — but instant and cheap. You'd use registered mail for a contract and a postcard for "having fun, wish you were here."

Common mistakes & gotchas

Blaming bandwidth for slowness that is really the bandwidth-delay product — on a high-latency link, a small window caps throughput no matter how fat the pipe. Leaking sockets in TIME_WAIT by opening a fresh connection per request instead of reusing keep-alives. Assuming UDP "just works" — with no ACKs, you must handle loss/ordering in the app. Firewalls that allow TCP but silently drop UDP, breaking DNS/QUIC. Forgetting TCP keepalives, so dead peers linger as ESTABLISHED for hours.

9. Routing & Switching

Switches move traffic within a network (by MAC address); routers move traffic between networks (by IP address). Together they get a packet from anywhere to anywhere.

Switch = office mailroom; Router = the post office

A switch delivers mail between desks in one office (local network, using MAC addresses). A router sends mail between different offices/cities (across networks, using IP addresses) and knows the routes. Your packet hops router to router across the internet, each one consulting its routing table for the next best hop toward the destination.

Inspect routing on Linux
ip route                 # your routing table (where does traffic go?)
ip route get 8.8.8.8     # which route/interface would reach this IP?
traceroute example.com   # show every router hop to the destination
mtr example.com          # live traceroute + packet loss per hop

Why routing and switching are separate jobs. Within one network, delivery is simple: everyone shares a broadcast domain and can be found by MAC address — that's switching (L2). But you can't put the whole internet on one flat L2 network (broadcasts would melt it, and MAC addresses aren't hierarchical, so there'd be no way to summarize routes). Routing (L3) uses hierarchical IP addresses so a router only needs to know "which direction is that network," not where every individual host lives.

How ARP + routing pick the next hop. When a host sends a packet: (1) it checks its routing table for the most-specific matching route (longest-prefix match); (2) that route says either "directly connected" or "via gateway X"; (3) it now has the next-hop IP, but frames need a MAC — so it consults its ARP cache, and if the MAC is unknown, it broadcasts "who has 10.0.3.1?" and the owner replies with its MAC; (4) it builds a frame with that MAC as destination and sends it. Crucially, the IP addresses stay the same end-to-end, but the MAC addresses are rewritten at every hop — each router swaps in its own MAC as source and the next hop's MAC as destination. Switches, meanwhile, learn which MAC lives on which port by watching source MACs, building a MAC-address table so they forward frames only out the correct port instead of flooding.

Trace a routing decision end to end
ip route                          # the routing table (longest-prefix wins)
ip route get 93.184.216.34        # which route + next-hop + interface is chosen?
ip neigh                          # ARP cache: next-hop IP -> MAC
arping -I eth0 10.0.3.1           # actively resolve the gateway's MAC

How traceroute works (the TTL trick)

Each IP packet has a TTL that every router decrements by 1; at 0 the router discards it and sends back an ICMP "time exceeded." Traceroute exploits this: send with TTL=1 (first router replies), then TTL=2 (second replies), and so on — each reply reveals one hop. A line of * * * means that hop didn't send the ICMP (often filtered), not necessarily that traffic is broken there.

Routing = asking for directions at each town

You don't get one map of the whole country. At each town (router) you ask "which road toward City X?" and drive to the next town, where you ask again. Nobody knows the full route — each just knows the best next road. The town name (IP) stays your goal the whole trip; only the local road you're on (MAC) changes at each town.

Common mistakes & gotchas

Missing or wrong default route → "can reach the local subnet but nothing beyond." Asymmetric routing (reply takes a different path) breaks stateful firewalls that expect to see both directions. A stale ARP entry after a failover (IP moved to new hardware) sends traffic to the old MAC until the cache expires — gratuitous ARP fixes it. Duplicate IPs cause ARP flapping. Overlapping routes: remember longest-prefix wins, so a /32 beats a /24 beats the default.

See what's listening & connected

Why ports exist. One machine (one IP) runs many services at once — web, SSH, database. The IP gets the packet to the machine; the port tells the OS which service should receive it. Without ports you could run only one network service per IP.

How a socket is actually identified. A TCP connection is uniquely keyed by a 4-tuple: (source IP, source port, destination IP, destination port). This is why one server on port 443 can hold thousands of simultaneous connections — each client uses a different source IP/port, so every tuple is unique. Server sockets bind to a well-known port and listen; each accepted connection spawns a new socket sharing the same local port but distinguished by the remote end. Client sockets get an ephemeral port (typically 32768–60999 on Linux) chosen by the OS. Ports 0–1023 are "privileged" — binding them requires root (or a capability), which is why web servers often start as root to grab 80/443 then drop privileges.

The critical difference: 0.0.0.0 vs 127.0.0.1

Send-Q on a LISTEN socket is the accept-queue backlog limit; a full backlog drops new connections.

IP + port = building + apartment number

The IP gets mail to the right building; the port number is the apartment inside. A socket is one specific delivery conversation: your apartment talking to their apartment. Many conversations share the building's front door (the listening port) but each is a distinct pairing of apartments, so they never get mixed up.

Common mistakes & gotchas

Binding to 127.0.0.1 then wondering why remote clients can't connect (bind 0.0.0.0 or a specific interface). Ephemeral port exhaustion under high connection churn — reuse connections, widen the range, or enable tcp_tw_reuse. "Address already in use" on restart because the old socket is in TIME_WAIT — use SO_REUSEADDR. Confusing "port open" (something listening) with "port reachable" (firewall allows it) — nc -zv tests reachability, ss -tlnp tests listening.

11. What is DNS?

DNS (Domain Name System) translates human-friendly names (example.com) into IP addresses (93.184.216.34). It's the internet's distributed phone book, and one of the most common sources of "mysterious" outages.

DNS = contacts app for the internet

You remember "Mom," not her phone number. DNS is the internet's contacts app: you type google.com, and DNS looks up the actual IP address to dial. It's distributed and cached globally so it's fast — but that caching is also why DNS changes "take time to propagate" and why stale cache causes confusing bugs.

"It's always DNS"

An industry in-joke with much truth: a large share of baffling outages trace back to DNS — expired records, wrong TTLs, stale caches, misconfigured resolvers. When something worked yesterday and mysteriously fails today, check DNS early: dig the name, compare against expected, and check TTL/caching.

Why DNS exists. IP addresses change (servers move, scale, fail over) and humans can't memorize them. DNS adds a stable naming layer on top of shifting IPs: you publish api.example.com once, and behind it the actual addresses can change freely. It's also a level of indirection you can exploit — the same name can resolve to different IPs by geography, health, or weighting (covered in Advanced DNS).

How the system is structured. DNS is a distributed hierarchical database. Three roles cooperate: (1) a stub resolver in your OS that just asks a configured server; (2) a recursive resolver (your ISP's, or 8.8.8.8) that does the legwork and caches answers; (3) authoritative servers that hold the real records for a zone. Caching at every level is what makes it fast — most lookups are answered from cache in microseconds and never touch the authoritative servers. That same caching is why changes take time to appear (bounded by the record's TTL).

See what your resolver is and test it
cat /etc/resolv.conf                 # which resolver(s) your OS uses
resolvectl status                    # systemd-resolved: per-link DNS + DNSSEC state
dig example.com                      # full answer incl. which server responded
getent hosts example.com             # resolve the way the OS actually does (respects nsswitch)
output (dig, trimmed)
;; ANSWER SECTION:
example.com.   3389   IN   A   93.184.216.34

;; SERVER: 127.0.0.53#53(127.0.0.53)      <- local systemd-resolved stub
;; Query time: 1 msec                     <- 1ms = served from cache
Why "1 msec" and "3389" matter

A 1ms query time means the answer came from cache, not a full recursive walk (which would be tens of ms). The 3389 is the remaining TTL in seconds — it counts down in cache; when it hits 0 the resolver re-fetches. Seeing a TTL that never changes across repeated digs means you're hitting the authoritative server each time (no caching), which is slow and unusual.

Common mistakes & gotchas

Testing with dig @8.8.8.8 (bypasses your local resolver and /etc/hosts) then wondering why the app resolves differently — the app uses the OS resolver; use getent hosts to match it. Forgetting /etc/hosts overrides DNS entirely, so a stray entry masks the real record. Assuming DNS is TCP — it's UDP by default (falls back to TCP for large responses), so a firewall blocking UDP/53 breaks it. Trusting ping to test DNS — ping caches and won't show the TTL or the answering server the way dig does.

12. Resolution Walkthrough

When you look up a name, a chain of servers cooperates to find the answer. Understanding this chain makes DNS debugging obvious.

Trace resolution yourself
dig www.example.com              # the answer + which server gave it
dig +trace www.example.com       # show the FULL root→TLD→authoritative chain
dig www.example.com @8.8.8.8     # ask a specific resolver (Google's)
dig +short example.com           # just the IP
nslookup example.com             # simpler, cross-platform

Why the hierarchy works this way. No single server could hold or serve all the world's names, and no one organization should control them all. So authority is delegated downward: the root delegates .com to the TLD operator, which delegates example.com to that domain's owner. Each level only knows how to point you one step closer — this makes DNS scalable (load spread across millions of servers) and administratively decentralized (you control your own zone).

How the resolver walks the tree. A recursive resolver starts knowing only the root hints (the 13 root server addresses). To resolve www.example.com: (1) ask a root server "where's .com?" → it returns a referral: the NS records for .com (not the answer, just "go ask these"). (2) Ask a .com TLD server "where's example.com?" → referral to example.com's authoritative nameservers. (3) Ask those "what's www.example.com?" → the authoritative answer (an A record). The resolver caches each step by its TTL, so the next lookup of anything under .com skips the root, and the next www.example.com skips everything. That's why cold lookups are slow and warm ones are instant.

Watch the full walk happen
dig +trace www.example.com         # every referral from root -> TLD -> authoritative
dig NS example.com +short          # who is authoritative for this zone?
dig @a.iana-servers.net www.example.com   # ask the authoritative server directly
output (dig +trace, condensed)
.            518400 IN NS a.root-servers.net.        <- step 0: roots (from hints)
com.          172800 IN NS a.gtld-servers.net.       <- step 1: root referred us to .com
example.com.   172800 IN NS a.iana-servers.net.      <- step 2: .com referred us to the zone
www.example.com. 3600 IN A 93.184.216.34             <- step 3: authoritative ANSWER
Referral vs answer

The first three lines are referrals (NS records: "ask over there"), the last is the authoritative answer (the A record). +trace makes the resolver do each step explicitly and print it — the single best tool for "which level of the hierarchy is broken." If the trace stops at .com, your zone's NS delegation is wrong; if it reaches the authoritative server but the record is wrong, the problem is in your zone file.

Resolution = finding a person via a directory chain

You want to reach someone at a huge company. Reception (root) doesn't know them but says "try the Sales building." Sales reception (TLD) says "try the 4th floor team." The 4th floor assistant (authoritative) finally gives you the desk number (IP). Each step just points you one hop closer, and you remember (cache) the directions so next time you skip straight there.

Common mistakes & gotchas

Lame delegation: the parent's NS records point to a server that isn't actually authoritative — intermittent failures. NS mismatch between the registrar and the zone's own NS records confuses resolvers. Negative caching: an NXDOMAIN is cached too (per the SOA's minimum TTL), so a just-created record can appear "missing" until the negative cache expires. Testing only your local cache and missing that a remote resolver still has the old answer for up to its TTL.

TTL controls caching — and migration speed

Every record has a TTL (time-to-live) telling resolvers how long to cache it. High TTL = fast (fewer lookups) but slow to change. Before migrating a service, lower the TTL (e.g. to 60s) a day ahead so the cutover propagates quickly; raise it again after. Forgetting this is why "I changed DNS but it still points to the old server."

Why so many record types. DNS isn't only name→IP; it's a general lookup system for many kinds of data keyed by name. Mail needs to know which server accepts email (MX); services need to advertise host+port (SRV); email anti-spoofing needs published policy (TXT/SPF/DKIM/DMARC); and aliases let you point one name at another without duplicating IPs (CNAME). Each type answers a different question about a name.

How CNAME, ALIAS, and apex differ. A CNAME says "this name is an alias for that name — go resolve that instead," so the resolver does a second lookup. Crucially, a CNAME can't coexist with other records at the same name, which is why you can't put a CNAME at the zone apex (example.com itself), because the apex must also hold SOA and NS records. Providers solve this with ALIAS/ANAME/flattening records that behave like a CNAME but return the target's A/AAAA directly. MX records carry a priority (lower = preferred) so mail can fail over to backups. SOA holds the zone's serial and timers, including the negative-cache TTL.

Query each record type

dig AAAA example.com +short       # IPv6
dig MX example.com +short         # mail servers (with priorities)
dig TXT example.com +short        # SPF/DKIM/verification strings
dig CNAME www.example.com +short  # is www an alias?
dig SOA example.com +short        # zone serial + timers (incl. negative TTL)
dig ANY example.com               # (often refused now; query types explicitly)

The SOA serial is your change tracker

The 2024051501 serial (date + revision) increments on every zone change; secondary nameservers compare serials to decide whether to re-sync. If you edited a record but the serial didn't bump, secondaries never pick it up — a classic "the change is live on one nameserver but not another" cause. The final field (3600) is how long NXDOMAIN answers are cached.

Record types = different columns in the phone book

One entry for a business can list its street address (A), its PO box (MX for mail), a note saying "we're the real ACME, verified" (TXT), and "also known as" aliases (CNAME). Same name, different kinds of information — you look up the column you actually need.

Common mistakes & gotchas

Putting a CNAME at the apex (breaks the zone) — use an ALIAS/flattening record instead. Chaining CNAMEs deeply adds a lookup per hop and latency. Forgetting SPF/DKIM/DMARC TXT records → your mail lands in spam. Splitting a long TXT record incorrectly (it must be chunked into ≤255-byte strings). A CNAME target that itself doesn't resolve silently breaks the name. Editing the zone but not bumping the SOA serial so secondaries never sync.

14. Advanced DNS & Traffic Routing

Modern DNS is a traffic-management tool: it can route users to the nearest, fastest, or healthiest endpoint. (Covered from the cloud angle in the Route 53 section.)

DNS security: DNSSEC & DoH/DoT

DNSSEC signs DNS records so resolvers can verify they weren't tampered with (prevents cache poisoning). DoH/DoT (DNS over HTTPS/TLS) encrypt DNS queries so they can't be snooped or manipulated in transit. Enable DNSSEC on domains you control, and be aware corporate networks may intercept plain DNS.

Why DNS became a traffic controller. Because it sits at the very start of every connection — before any TCP or TLS — DNS is the earliest point to steer a user. Returning a different IP per user lets you send them to the nearest region (latency), a specific version (canary), or a healthy endpoint (failover) with zero client changes. It's the cheapest, most global load-distribution lever you have.

How the routing policies actually decide. The authoritative server (e.g. Route 53) evaluates the incoming query's metadata and returns a tailored answer: Weighted returns each IP a configured fraction of the time (10% to the new version). Latency/Geo uses the resolver's location (or EDNS Client Subnet, which forwards a truncated client IP) to pick the closest region. Failover ties records to health checks and stops handing out an IP once its endpoint fails checks. Round-robin rotates the record order each response. Because these are just DNS answers, they're still bound by TTL — a failover is only as fast as the record's TTL lets caches expire, which is why failover records use very low TTLs.

Observe DNS-based routing and security

for i in 1 2 3 4; do dig +short api.example.com; done   # see the distribution
dig +dnssec example.com                          # RRSIG present = zone is signed
dig DS example.com +short                        # delegation signer at the parent (DNSSEC chain)
kdig -d @1.1.1.1 +tls example.com                # DoT (DNS over TLS) query
output (repeated dig showing weighting)

203.0.113.10

Why answers seem to "flip"

Different IPs on repeated queries are the routing policy at work, not a bug. But remember a caching resolver holds one answer for the whole TTL, so an individual user sticks to whatever they got until it expires. For fast canary rollback or failover, keep TTLs low (30–60s); for stable records, higher TTLs reduce load. The RRSIG in a +dnssec answer is the cryptographic signature proving the record wasn't tampered with.

Smart DNS = a receptionist who routes callers

Call the same company number and the receptionist decides where to connect you: the nearest branch (geo), whichever agent is free (round-robin), or — if the main office is down — the backup site (failover). Same number, different destination depending on who you are and what's healthy.

Common mistakes & gotchas

Expecting instant failover with a 3600s TTL — caches ignore your health check until the old answer expires. Geo-routing based on resolver location misfires when users use 8.8.8.8 far from home (EDNS Client Subnet mitigates this). Turning on DNSSEC but botching key rollover → the whole zone goes dark (SERVFAIL everywhere). Assuming clients honor TTLs — some apps and JVMs cache DNS forever unless configured otherwise.

15. HTTP/HTTPS & HTTP/2/3

HTTP is the protocol of the web and most APIs. Its versions have evolved to be faster and more efficient — worth understanding for performance work.

VersionKey improvement
HTTP/1.1Persistent connections, but one request at a time per connection (head-of-line blocking)
HTTP/2Multiplexing (many requests over one connection), header compression, server push
HTTP/3Runs over QUIC (UDP) — eliminates TCP head-of-line blocking, faster connection setup
Inspect HTTP
curl -v https://example.com           # full request/response incl. TLS + headers
curl -I https://example.com           # headers only
curl -w "%{time_total}s\n" -o /dev/null -s https://example.com   # timing
curl --http2 -I https://example.com   # check HTTP/2 support
Status codes tell the story

2xx success · 3xx redirect · 4xx client error (400 bad request, 401 unauth, 403 forbidden, 404 not found, 429 rate-limited) · 5xx server error (500 internal, 502 bad gateway, 503 unavailable, 504 timeout). When debugging, the code + response headers usually point straight at the layer that failed.

Why HTTP kept evolving. HTTP/1.1 sends one request at a time per connection, so a slow response blocks everything behind it (head-of-line blocking); browsers hacked around this by opening 6+ parallel connections per host, wasting resources. HTTP/2 fixed the application layer with multiplexing but still rode on a single TCP connection — so one lost packet stalls all streams (TCP-level head-of-line blocking). HTTP/3 moves onto QUIC over UDP, where each stream has independent delivery, so a lost packet only stalls its own stream. Each version removed a bottleneck the previous one exposed.

How multiplexing works under the hood. HTTP/2 splits every message into frames tagged with a stream ID; frames from many concurrent requests interleave over one connection and are reassembled by ID at the other end. Headers are compressed with HPACK (a shared dynamic table so repeated headers like cookie aren't resent in full). HTTP/3 does the same framing but over QUIC, which builds encryption (TLS 1.3) and multiplexing directly into the transport and completes the connection + crypto handshake in as little as one round trip (0-RTT on resumption).

Probe HTTP versions and headers
curl -sI --http2 https://example.com | head -1     # HTTP/2 200 if negotiated
curl -sI --http3 https://example.com | head -1     # needs curl built with HTTP/3
curl -s -o /dev/null -w '%{http_version} %{http_code}\n' https://example.com
curl -s -D - -o /dev/null https://example.com | grep -i -E 'alt-svc|content-encoding|cache-control'
output
$ curl -sI --http2 https://example.com | head -1
HTTP/2 200
$ curl -s -D - -o /dev/null https://example.com | grep -i alt-svc
alt-svc: h3=":443"; ma=86400        <- server advertises HTTP/3 is available on 443
The Alt-Svc header is how HTTP/3 gets used

Clients almost always connect first over HTTP/2 (TCP). The alt-svc: h3=":443" header tells the browser "next time, try HTTP/3 here" — so the upgrade happens on subsequent visits, not the first. If you're testing HTTP/3 and only see HTTP/2, that's expected on the very first connection. content-encoding: gzip/br confirms compression is active — its absence on large text responses is an easy performance win missed.

HTTP versions = lanes on a road

HTTP/1.1 is a one-lane road — one car (request) at a time, and a stalled car blocks everyone. HTTP/2 is a multi-lane road on one bridge — many cars at once, but if the bridge jams (a lost TCP packet) all lanes stop. HTTP/3 gives each lane its own bridge (independent QUIC streams) so one jam doesn't stop the rest.

Common mistakes & gotchas

Still sharding assets across many hostnames "for parallelism" — that hurts HTTP/2, which prefers one connection. Assuming HTTP/2 needs no TLS — browsers only do h2 over HTTPS. Forgetting HTTP/3/QUIC is UDP, so a firewall allowing only TCP/443 silently blocks it (clients quietly fall back). Misreading a 502/504 as the app being down when it's really the reverse proxy failing to reach or waiting on the backend. Ignoring Cache-Control, so a CDN can't cache and every request hits the origin.

16. TLS & Certificates

TLS encrypts HTTP (making it HTTPS) and verifies server identity. (Full cryptographic depth is in the Security PKI/TLS section.)

Debug certificates fast
openssl s_client -connect example.com:443 -servername example.com
echo | openssl s_client -connect example.com:443 2>/dev/null | openssl x509 -noout -dates
curl -vI https://example.com   # shows the TLS handshake + cert chain
The usual TLS failures

Expired cert · incomplete chain (server didn't send the intermediate) · hostname mismatch (cert doesn't cover the domain) · protocol/cipher mismatch (client too old). Automate renewal (Let's Encrypt / cert-manager / ACM) so expiry — the most common cause — never happens.

Why TLS exists. Raw HTTP is plaintext — anyone on the path (Wi-Fi, ISP, proxy) can read or alter it, and you have no proof the server is who it claims. TLS provides three things at once: confidentiality (encryption), integrity (tamper detection), and authentication (the certificate proves the server's identity via a chain of trust up to a CA your system already trusts).

How the handshake works (TLS 1.3). (1) The client sends ClientHello with supported ciphers, a key-share, and the target hostname in the SNI extension (so a server hosting many sites picks the right cert). (2) The server replies ServerHello with its chosen cipher, its key-share, and its certificate chain. (3) Both sides now have the ingredients to derive the same shared secret via Diffie-Hellman — without ever sending it — giving forward secrecy (capturing traffic today can't be decrypted later even if the key leaks). (4) The client verifies the cert chain: does it chain to a trusted root? Is it in date? Does the name match SNI? If all pass, encrypted application data flows — all in a single round trip (TLS 1.2 needed two). Session resumption/0-RTT can skip even that on repeat visits.

Inspect the handshake and chain
openssl s_client -connect example.com:443 -servername example.com </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates
echo | openssl s_client -connect example.com:443 -tls1_3 2>/dev/null | grep -E 'Protocol|Cipher'
curl -sIv https://example.com 2>&1 | grep -E 'SSL connection|subject|issuer|expire'
openssl s_client -connect example.com:443 -showcerts </dev/null 2>/dev/null | grep -c 'BEGIN CERT'
output
subject=CN = example.com
issuer=CN = R3, O = Let's Encrypt, C = US        <- intermediate that signed the leaf
notBefore=Apr  1 00:00:00 2024 GMT
notAfter=Jun 30 23:59:59 2024 GMT                <- expiry: automate renewal before this
# BEGIN CERT count = 2  -> leaf + intermediate sent (good; 1 = missing intermediate)
The certificate-count trick

The server must send the leaf and any intermediates so clients can build the chain to a trusted root. Counting BEGIN CERT blocks tells you instantly: 2+ means the chain is complete; just 1 means a missing intermediate — the classic "works in my browser (which cached the intermediate) but fails in curl/Java/mobile." SNI (-servername) is required on shared hosts, or you'll get the wrong cert.

TLS = a sealed, ID-checked delivery

Before handing over your package, the courier shows ID signed by an authority you trust (the certificate chain), you both agree on a secret lockbox combination without saying it aloud (key exchange), and everything inside is sealed so no one on the route can peek or swap the contents. If the ID is expired, forged, or for the wrong name, you refuse the handoff.

Common mistakes & gotchas

Missing intermediate cert (the #1 "curl fails, browser works"). Expired cert — automate renewal. Hostname/SAN mismatch (modern clients ignore CN and require the name in Subject Alternative Names). Wrong or missing SNI on multi-tenant servers returns the default cert. Clock skew on the client makes valid certs look expired. Terminating TLS at a load balancer but forgetting the backend hop is then plaintext — use end-to-end or a private network. Pinning a cert then rotating it breaks clients.

17. Load Balancing

A load balancer spreads traffic across multiple backend servers, providing scalability and high availability. They operate at Layer 4 (TCP) or Layer 7 (HTTP).

AlgorithmBehavior
Round-robinRotate evenly through backends
Least connectionsSend to the least-busy backend
IP hash / stickySame client → same backend (session affinity)
WeightedBigger servers get more traffic

Why load balancers exist. A single server has a capacity ceiling and is a single point of failure. A load balancer gives you one stable entry point (one IP/DNS name) in front of many interchangeable backends, so you can add capacity by adding servers, survive individual failures, and deploy/patch backends without downtime by draining them one at a time.

How L4 vs L7 balancing differ under the hood. An L4 balancer forwards at the TCP/UDP level — it picks a backend per connection and shuttles bytes without understanding them (fast, protocol-agnostic, can't route by URL). An L7 balancer terminates the connection, reads the HTTP request, and can route by host/path/header, rewrite, retry, and terminate TLS — richer, at slightly higher cost. Both run continuous health checks (e.g. GET /healthz every few seconds) and eject a backend after N consecutive failures, re-adding it when it recovers. Session affinity ("sticky") pins a client to one backend via a cookie or source-IP hash, needed when the app keeps state in memory.

Verify balancing and health checks
for i in $(seq 1 6); do curl -s https://app.example.com/whoami; done   # see different backends
curl -s -o /dev/null -w '%{http_code}\n' https://app.example.com/healthz  # the LB's health probe
curl -sI https://app.example.com | grep -i -E 'set-cookie|server|x-served-by'  # affinity/backend hints
ss -tn state established '( dport = :443 )' | wc -l                     # spread of live conns
nginx: upstream with health-aware balancing
upstream app {
    least_conn;                         # send to the least-busy backend
    server 10.0.1.10:8080 max_fails=3 fail_timeout=10s;
    server 10.0.1.11:8080 max_fails=3 fail_timeout=10s;
    server 10.0.1.12:8080 backup;       # only used if the others are down
}
server { listen 443 ssl; location / { proxy_pass http://app; } }
Watch for uneven distribution

Repeating the whoami call should cycle through backends. If it sticks to one, either affinity is on (a Set-Cookie in the headers) or a keep-alive connection is being reused (each request rides the same connection to the same backend). least_conn beats round-robin when request durations vary a lot, because a couple of slow requests otherwise pile up on one round-robin'd backend.

Load balancer = the host at a busy restaurant

You don't pick a table yourself — the host seats you at whichever section has a free, working table, keeps you away from tables that are "down" (dirty/closed), and spreads guests so no one waiter is swamped. If you're a regular who left your coat at table 4 (session state), they seat you there again (sticky sessions).

Common mistakes & gotchas

A too-shallow health check (just TCP connect, or / returning 200 even when the DB is down) keeps sending traffic to a broken backend — health-check a real dependency-touching endpoint. Sticky sessions defeating even distribution and breaking on backend loss — prefer stateless apps with shared session storage. Losing the client IP at the backend — forward X-Forwarded-For/PROXY protocol. Not draining connections before removing a backend, cutting live requests. Idle-timeout mismatches between LB and backend causing random 502s.

18. CDNs & Proxies

Proxies sit between clients and servers to add caching, security, and routing. CDNs are globally-distributed caching proxies.

TypeSits betweenPurpose
Forward proxyClient → internetEgress control, corporate filtering, caching
Reverse proxyInternet → your serversTLS termination, routing, caching, security (NGINX, Envoy)
CDNUsers → origin, globallyCache content near users; absorb DDoS (see CloudFront)

Why proxies and CDNs exist. A reverse proxy centralizes cross-cutting concerns — TLS termination, routing, caching, compression, rate limiting, auth — so your app servers stay simple and uniform. A CDN extends caching to hundreds of edge locations worldwide so content is served from a few milliseconds away instead of a cross-ocean round trip, which also shields the origin from load and volumetric attacks.

How a CDN decides hit vs miss. Users are steered (via anycast IP or DNS) to the nearest edge PoP. On a request, the edge checks its cache using the URL plus any cache key rules (query strings, headers). On a hit it serves instantly; on a miss it fetches from the origin, stores the response according to Cache-Control/Expires, and serves it — subsequent nearby users get hits. Freshness is governed by max-age; after that the edge revalidates with the origin using ETag/If-None-Match, getting a cheap 304 Not Modified if unchanged. Anycast means one IP is announced from many sites and the network delivers each user to the closest — this is also what lets a CDN absorb DDoS by spreading it across the globe.

Tell a cache hit from a miss
curl -sI https://cdn.example.com/logo.png | grep -i -E 'x-cache|age|cache-control|cf-cache-status'
curl -sI https://cdn.example.com/logo.png | grep -i age   # run twice: Age grows on a cached hit
curl --resolve cdn.example.com:443:1.2.3.4 -sI https://cdn.example.com/  # test a specific edge IP
output
x-cache: Hit from cloudfront          <- served from the edge, origin untouched
age: 137                              <- seconds this object has lived in cache
cache-control: public, max-age=86400  <- edge may keep it up to a day before revalidating
The header that ends "why is my CDN not caching" tickets

x-cache/cf-cache-status shows Hit or Miss; a growing Age confirms a real cached copy. If you always see Miss, the origin is probably sending Cache-Control: no-store/private, or a Set-Cookie is making every response uncacheable, or the cache key includes a varying query string. Fix the origin headers, not the CDN — the CDN only obeys what the origin tells it.

CDN = local corner shops stocking popular items

Instead of everyone driving to the distant central warehouse (origin), popular goods are stocked at the corner shop nearest you (edge). First person to want an item triggers a restock from the warehouse (cache miss); everyone after grabs it locally (cache hit). Perishable goods get a "sell-by" (max-age) after which the shop checks with the warehouse for a fresh one.

Common mistakes & gotchas

Caching personalized/authenticated responses so one user sees another's data — mark them private/no-store and be careful with the cache key. Forgetting to invalidate/purge after a deploy, so users get stale assets — use content hashes in filenames instead. Set-Cookie silently disabling caching. Not forwarding the real client IP (X-Forwarded-For), so logs and rate limits see the proxy. Trusting X-Forwarded-For blindly — it's spoofable unless set by a trusted hop.

The essential networking toolkit — master these and you can diagnose almost anything, layer by layer.

A layered debugging session
ping 8.8.8.8              # L3: is basic connectivity up? (bypasses DNS)

ping example.com          # L3: reachable by name?

Why a layered toolkit. "It doesn't work" is unfalsifiable; a set of layer-specific tools turns it into a sequence of yes/no tests that bisect the problem. Each tool isolates one layer, so instead of guessing you binary-search the stack until exactly one step fails — that failing step is your bug.

How to bisect a failure fast. Go bottom-up and stop at the first failure: (1) ip a/ip link — is the interface up with an IP? (2) ping the gateway then a public IP like 1.1.1.1 — is L3 routing working, independent of DNS? (3) dig the name — does it resolve, and to the expected IP? (4) nc -zv host port — is the port reachable (firewall/listening)? (5) curl -v — does the app answer correctly? The first step that fails localizes everything: ping-by-IP works but ping-by-name doesn't → DNS; port unreachable but host pingable → firewall or service down; app returns 502 → backend problem behind the proxy.

One-shot triage with clear signals
ping -c1 1.1.1.1 && echo L3-OK || echo L3-FAIL     # routing works without DNS?
dig +short example.com | head -1 || echo DNS-FAIL   # resolves?
nc -zv -w3 example.com 443 2>&1                       # port reachable within 3s?
curl -sS -o /dev/null -w 'code:%{http_code} total:%{time_total}s\n' https://example.com
mtr -rwzbc 20 example.com                            # 20-cycle path + loss report
output (mtr, loss localized)
HOST: laptop            Loss%  Snt  Last  Avg  Best  Wrst
  1. 10.0.3.1            0.0%   20   1.1   1.2  0.9   2.0
  4. core-router.isp     0.0%   20   9.8  10.1  9.2  12.0
  5. congested-hop.isp  35.0%   20  88.0  91.3 40.0 210.0   <- loss starts here
  6. example.com         0.0%   20  30.0  31.0 29.0  33.0
Reading mtr: where does loss begin?

Loss that appears at one hop and continues to the destination is real congestion/failure at that hop. Loss that shows at a middle hop but clears by the final hop is usually just that router de-prioritizing its own ICMP replies (harmless) — a very common false alarm. Judge by the destination line and the last hop with sustained loss, not by a single blip mid-path.

Diagnostics = checking the water supply room by room

No water at the tap? Don't guess. Check the street main (ping 1.1.1.1), then the meter (gateway), then the pipe to your house (route), then the valve to that room (port), then the faucet itself (the app). The first place with no water is where the break is — you don't replace the whole plumbing on a hunch.

Common mistakes & gotchas

Concluding a host is down because ping fails — many hosts/firewalls drop ICMP while TCP services work fine; test the actual port. Trusting a single ping (test multiple + latency). Interpreting mid-path ICMP loss as an outage. Running tcpdump without a filter and drowning in packets. Forgetting curl follows redirects only with -L, so a 301 looks like "no content." Testing from your laptop when the failing path is server→server inside the network — run the tools from the affected host.

20. Network Security

Networking and security are inseparable. (Deep coverage in the Security guide.)

Network security essentials
  • Segment networks (subnets/VPCs/VLANs) so a breach can't roam freely.
  • Default-deny firewalls — allow only needed ports/sources.
  • Encrypt in transit (TLS everywhere, mTLS between services).
  • Private subnets for anything not needing public access.
  • DDoS protection + WAF at the edge for public endpoints.
  • Zero Trust — verify every request regardless of network location.

Why network security is layered. No single control is enough — a firewall doesn't stop a stolen credential, and encryption doesn't stop a misconfigured open port. Defense in depth stacks independent controls so an attacker who defeats one still faces the next: segmentation limits blast radius, default-deny firewalls shrink the attack surface, encryption protects data if traffic is captured, and identity checks (Zero Trust) catch attackers who are already "inside."

How the core controls actually work. A stateful firewall tracks connections: it allows return traffic for connections you initiated but blocks unsolicited inbound — the same principle NAT relies on. Segmentation puts tiers in separate subnets/security groups so the web tier can reach the app tier on one port and nothing else — a compromised web box can't scan the database directly. mTLS extends TLS so both ends present certificates, so services authenticate each other, not just the client trusting the server. Zero Trust drops the idea that "inside the network = trusted" and authenticates/authorizes every request regardless of origin.

Audit exposure and firewall state
ss -tlnp                                   # every listening port — is anything unexpectedly open?
sudo nft list ruleset                      # current firewall rules (nftables)
sudo iptables -L -n -v --line-numbers      # rules + hit counters (iptables)
nmap -sT -Pn -p- your.host.example         # what's reachable from OUTSIDE (attacker's view)
ss -tn state established | awk '{print $4}' | sort | uniq -c   # what's actually connected
nftables: default-deny inbound, allow established + specific ports
table inet filter {
  chain input {
    type filter hook input priority 0; policy drop;   # default-deny
    ct state established,related accept                # allow return traffic
    iif "lo" accept                                    # loopback
    tcp dport { 22, 443 } accept                       # only SSH + HTTPS inbound
    ip protocol icmp accept                            # allow ping (optional)
  }
}
Scan from the outside, not the inside

Checking ss -tlnp on the host shows what's listening; running nmap from another machine shows what's actually reachable through the firewall/security group. The gap between them is your real exposure. A service listening on 0.0.0.0 is fine if a default-deny firewall only lets 443 through — but if that firewall is missing, every listening port is internet-facing. Always verify from the attacker's vantage point.

Network security = a building with layered access

The perimeter fence (firewall) keeps most people out. Inside, you still need a badge for each floor (segmentation), sensitive rooms are locked separately (private subnets), conversations happen in soundproof rooms (encryption), and even known employees show ID at each door rather than roaming freely (Zero Trust). One breached door doesn't hand over the whole building.

Common mistakes & gotchas

Security groups/firewalls that are permissive "temporarily" and never tightened (0.0.0.0/0 on port 22 is a magnet). Relying on network location for trust — flat networks let one breach spread everywhere. Terminating TLS at the edge and running plaintext internally on an untrusted network. Opening a port for debugging and forgetting it. Trusting client-supplied headers (X-Forwarded-For) for auth decisions. Logging that captures secrets/tokens in URLs. No egress filtering, so a compromised host can exfiltrate freely.

21. Packet Analysis, Scaling & Storage

A grab-bag of practical infrastructure concepts that come up constantly in real DevOps work (and interviews) — reading packets, defending against floods, scaling directions, and how storage is actually attached.

Packet analysis with Wireshark / tcpdump

When "the app is slow" and metrics don't explain it, capturing the actual packets settles it. tcpdump captures on servers; Wireshark reads and dissects the capture visually.

Capture on a server, analyze anywhere
sudo tcpdump -i any -n port 443 -w capture.pcap    # capture HTTPS traffic to a file
# open capture.pcap in Wireshark and filter, e.g.:
#   http.response.code >= 500        (server errors)
#   tcp.analysis.retransmission      (packet loss / bad network)
#   dns.time > 0.1                   (slow DNS lookups)
tcpdump -i any -n 'tcp[tcpflags] & tcp-syn != 0'   # watch connection attempts
What packets reveal that dashboards don't

Retransmissions = packet loss (bad link or overloaded host). A big gap between the SYN and the response = the server is slow to accept, not the network. TLS handshake taking long = cert/cipher issue. Seeing the raw exchange turns "it's slow somewhere" into "the database's TCP window is full" — the ground truth.

Why capture packets at all. Logs and metrics are the app's opinion of what happened; the packet capture is the ground truth of what actually crossed the wire. When the two disagree — the app logs "sent response" but the client saw nothing — only the capture settles who's lying. It's the court of last resort for network mysteries.

How to capture without drowning. Always narrow with a BPF filter (host/port/flags) at capture time, not after — an unfiltered capture on a busy host fills disk in seconds. Capture to a rotating file, then analyze offline in Wireshark where you can "Follow TCP Stream" to see one conversation reassembled, and use display filters to zero in. The workflow is: capture tightly on the server → copy the .pcap → dissect visually elsewhere.

Targeted capture + read-back
sudo tcpdump -i any -n host 10.0.1.20 and port 5432 -w db.pcap -c 5000   # DB traffic, capped
sudo tcpdump -tttt -n -r db.pcap 'tcp[tcpflags] & (tcp-syn|tcp-fin|tcp-rst) != 0'  # just connection events
sudo tcpdump -i any -n -c 20 'tcp[tcpflags] & tcp-rst != 0'   # who is sending RSTs (abrupt resets)?
output (connection lifecycle)
2024-05-15 10:15:02.331  IP 10.0.1.5.51544 > 10.0.1.20.5432: Flags [S]    <- SYN (open)
2024-05-15 10:15:02.332  IP 10.0.1.20.5432 > 10.0.1.5.51544: Flags [S.]   <- SYN-ACK
2024-05-15 10:15:02.512  IP 10.0.1.20.5432 > 10.0.1.5.51544: Flags [R.]   <- RST 180ms later!
What an RST after a handshake tells you

A connection that completes the handshake then gets an [R] (reset) means the server accepted the TCP connection but the application refused or crashed the session (e.g. max connections reached, auth rejected). That distinguishes a network problem (never gets past SYN) from an app problem (connects then resets) — a distinction dashboards rarely show but a two-line capture makes obvious.

tcpdump = a wiretap on the phone line

Instead of asking each side "what did you say?", you record the actual call. You hear exactly who spoke, when, who hung up first, and whether there was silence (loss) — the objective record, not each party's memory of the conversation.

Common mistakes & gotchas

Capturing with no filter and filling the disk. Forgetting encrypted payloads (HTTPS) show timing/flags but not content — you need TLS keys or capture before/after termination to see the body. Capturing on the wrong interface (-i any when a bridge/veth carries the traffic in containers). Reading only summaries and missing retransmissions — enable tcp.analysis.flags in Wireshark. Leaving a capture running and impacting the host.

DDoS & how to mitigate it

A Distributed Denial of Service attack floods you with traffic from many sources to exhaust your capacity. You can't out-buy every attacker, so you absorb and filter.

Layer of attackExampleDefense
Volumetric (L3/4)UDP/SYN flood saturating bandwidthCloud scrubbing (AWS Shield, Cloudflare), anycast to spread load
Protocol (L3/4)SYN flood exhausting connection tablesSYN cookies, rate limits, stateful firewalls
Application (L7)Flood of expensive HTTP requestsWAF, rate limiting per IP/user, CAPTCHA, caching/CDN
The mitigation mindset

Push defense to the edge (a CDN/scrubbing service absorbs floods before they reach your origin — see §21 and CloudFront), rate-limit at the gateway (see the API gateway guide), cache aggressively so floods hit cache not compute, and autoscale to ride out spikes. You rarely block a DDoS with a single firewall rule — you architect to absorb it.

Why DDoS is hard to "block." The traffic looks legitimate and comes from thousands of sources, so there's no single IP to ban. And volumetric floods can exceed your bandwidth before a packet ever reaches your firewall — you can't filter what already saturated the pipe. The strategy is therefore absorb and distribute, not "block."

How each attack class is defeated. Volumetric floods (raw bandwidth) are absorbed upstream by scrubbing centers and anycast, which spreads one destination IP across dozens of global sites so no single site takes the full load. Protocol attacks (SYN floods that exhaust the connection table) are countered by SYN cookies — the server encodes connection state into the sequence number and keeps no table entry until the handshake completes, so a flood of half-open SYNs costs nothing. Application floods (expensive requests) are stopped by rate limiting per client, caching so the flood hits cache not compute, and a WAF that fingerprints and drops bad requests.

Detect and blunt a flood on the host
ss -s                                       # summary: a huge synrecv count = SYN flood
ss -tn state syn-recv | wc -l               # half-open connections piling up
sudo sysctl -w net.ipv4.tcp_syncookies=1    # enable SYN cookies (usually default on)
sudo tcpdump -i any -n 'tcp[tcpflags] & tcp-syn != 0 and tcp[tcpflags] & tcp-ack = 0' -c 20  # bare SYNs
# crude per-IP rate limit at the edge (nftables):
sudo nft add rule inet filter input tcp dport 443 ct state new limit rate over 50/second drop
output (ss -s during a SYN flood)
TCP:   50213 (estab 42, closed 12, orphaned 0, timewait 10), ports 0
       synrecv 49800                    <- tens of thousands half-open = SYN flood signature
The synrecv tell

A normal server has a handful of synrecv (SYN received, waiting for the final ACK). Tens of thousands means clients are sending SYNs and never completing the handshake — the classic SYN flood. With SYN cookies on, the kernel stops allocating a slot per half-open connection, so the table can't be exhausted; legitimate clients complete normally and attackers' spoofed SYNs cost nothing.

DDoS = a flash mob jamming your front door

Thousands of people crowd your shop entrance so real customers can't get in. You can't fight each one. Instead you open many entrances across the city (anycast/CDN), let a security firm filter the crowd before it reaches you (scrubbing), and stop wasting staff time holding doors for people who never actually enter (SYN cookies).

Common mistakes & gotchas

Trying to block source IPs during a distributed attack — they're too many and often spoofed. Rate-limiting so aggressively you drop real users (tune with real traffic baselines). Assuming your origin firewall helps against volumetric floods — the pipe is already full upstream; you need edge/scrubbing. No caching, so every flood request hits compute. Forgetting UDP-based amplification (DNS/NTP) — filter or rate-limit those services if you run them.

Vertical vs horizontal scaling

Up vs out, plainly

Scale up = replace your laptop with a more powerful one. Easy, but there's a biggest-laptop limit, and if it dies you're down. Scale out = hire more people to share the work. Nearly unlimited and survives one quitting — but the work must be splittable (your app must be stateless, storing session/state in a shared DB or cache, not in local memory). Designing for horizontal scale is why the load balancing and stateless-app patterns matter.

Why the choice matters. Scaling up is the path of least resistance — no code changes — but it hits a hard ceiling (the biggest instance available) and leaves you with a single point of failure. Scaling out has no practical ceiling and survives node loss, but it forces an architectural discipline: the app must be stateless so any node can handle any request. Most systems scale up first for simplicity, then are forced out by the ceiling or availability needs.

How horizontal scaling actually works. Put N identical instances behind a load balancer; the LB spreads requests and health-checks nodes. The catch is state: if a user's session lives in one node's memory, the LB sending their next request elsewhere loses it. The fix is to externalize state — sessions in Redis, data in a shared DB, files in object storage — so instances are interchangeable. Then autoscaling can add/remove nodes based on load (CPU, request rate) and the LB routes only to healthy ones. This is exactly the pattern cloud auto-scaling groups and Kubernetes deployments implement.

Signals that tell you which way to scale
uptime; nproc                              # load average vs core count — CPU-bound? scale up or out
free -h                                    # memory pressure — a single big process may need scale-up
ss -s                                      # connection volume — many clients favor scale-out
# check if the app is stateless (safe to scale out): is session state local or shared?
curl -s https://app.example.com/whoami; curl -s https://app.example.com/whoami   # same node twice?
output
$ uptime
 10:15:02 up 3 days, load average: 7.90, 7.20, 6.80     <- load ~8 on an 8-core box = saturated
$ nproc
8                                                        <- at capacity: add nodes (scale out)
Load average vs core count

A load average near your core count means the CPU is fully used; sustained load above it means work is queuing. If one process can use more cores/RAM, scaling up may suffice; if you're already on a large instance or need fault tolerance, scale out. The whoami test reveals statefulness: if two calls must hit the same node to work, the app isn't ready for horizontal scaling until you externalize its state.

Common mistakes & gotchas

Scaling out a stateful app and getting random logouts/lost carts because sessions live in local memory. Autoscaling on the wrong metric (CPU when the bottleneck is DB connections or memory). Scaling the web tier while the database becomes the new bottleneck — scale the whole path. Forgetting that more nodes multiply DB connections (use pooling). Aggressive scale-in terminating nodes with in-flight requests (drain first). Assuming vertical scaling is free of downtime — resizing often needs a restart.

Storage: RAID, NAS & SAN

TermWhat it isUse
RAIDCombining disks for redundancy/speed (RAID 1 = mirror, RAID 5/6 = parity, RAID 10 = mirror+stripe)Survive a disk failure without data loss / boost throughput
DASDirect-attached storage (a disk in the server)Fastest, but tied to one host (like EBS/instance store)
NASNetwork-attached storage — file-level over the network (NFS/SMB)Shared files across many servers (like EFS)
SANStorage area network — block-level over a dedicated networkHigh-performance shared block storage for databases
How this maps to the cloud

You rarely rack disks now, but the concepts map directly: EBS ≈ network block storage (SAN-like), instance store ≈ DAS, EFS ≈ NAS (shared NFS), and the cloud handles RAID-like redundancy for you inside the service. Knowing the underlying ideas (block vs file, redundancy via mirroring/parity) is why you can pick the right cloud storage in the Cloud guide and Databases guide.

Why these distinctions matter. The core question is block vs file vs object and local vs network. Block storage (DAS/SAN) hands the OS raw blocks it formats itself — fastest, needed for databases. File storage (NAS) serves a shared filesystem over the network — many hosts read/write the same files. Getting this wrong (e.g. trying to share a block volume across hosts like a filesystem) causes corruption, so the categories are practical, not academic.

How RAID redundancy works. RAID combines disks so failures don't lose data or to boost speed. Mirroring (RAID 1) writes identical copies to two disks — survives one failure, halves usable capacity. Striping (RAID 0) splits data across disks for speed — but any disk failure loses everything (no redundancy). Parity (RAID 5/6) stores a computed check block so any one (5) or two (6) failed disks can be reconstructed from the rest — good capacity efficiency, but writes cost extra parity computation. RAID 10 mirrors then stripes for speed and redundancy. NAS speaks file protocols (NFS/SMB) so it's mountable by many hosts; SAN presents block devices over a dedicated fabric (iSCSI/Fibre Channel) for database-grade performance.

Inspect storage on Linux
lsblk                                   # block devices + mounts (the DAS/SAN view)
cat /proc/mdstat                        # software RAID status + which disks are healthy
df -hT                                  # filesystems, types, free space
mount | grep nfs                        # NAS: any NFS mounts? (file-level, network storage)
sudo iscsiadm -m session                # SAN: active iSCSI block sessions
output (/proc/mdstat, a healthy RAID1)
md0 : active raid1 sda1[0] sdb1[1]
      976630464 blocks super 1.2 [2/2] [UU]     <- [2/2] [UU] = both mirror disks present/healthy
Reading [UU] vs [U_]

[2/2] [UU] means both disks of the mirror are up. [2/1] [U_] means one disk failed and the array is running degraded — still serving data, but a second failure now loses everything. That underscore is your cue to replace the disk immediately. This is exactly the redundancy the cloud manages invisibly for you inside EBS/EFS, but the mental model is identical.

RAID/NAS/SAN = how the filing cabinets are arranged

RAID is keeping duplicate copies of documents (or clever checksums) so losing one drawer doesn't lose the file. DAS is a filing cabinet bolted to your desk — fastest, but only you can use it. NAS is a shared cabinet in the hallway everyone can open (file sharing). SAN is a private high-speed cabinet wired directly to a few power users (databases) who need raw speed.

Common mistakes & gotchas

Treating RAID as a backup — it survives disk failure, not deletion, ransomware, or fire; you still need real backups. Mounting a block volume on two hosts simultaneously without a cluster filesystem → corruption. Running a busy database on NFS/NAS and hitting latency/locking issues (use block/SAN). Ignoring a degraded array until the second disk dies. RAID 5 on very large disks — rebuild times are so long a second failure during rebuild is a real risk (prefer RAID 6/10). Assuming NAS gives block semantics — it's file-level.

22. Best Practices — the checklist

Networking best practices
  • Plan non-overlapping CIDR ranges before building.
  • Public subnets only for LBs/NAT; everything else private.
  • Lower DNS TTLs before migrations; use health-checked failover routing.
  • TLS everywhere with automated cert renewal.
  • Load-balance across AZs; health-check backends.
  • Use a CDN for static content and DDoS absorption.
  • Debug systematically by layer (L1→L7).
  • Monitor latency, packet loss, DNS resolution, and cert expiry.

23. Troubleshooting Playbook

"Connection refused"

Something answered but nothing is listening on that port. The service is down or bound to the wrong interface. Check ss -tulpn on the server; verify the app is running and listening on 0.0.0.0 (not just 127.0.0.1).

"Connection timed out"

Nothing answered at all — usually a firewall/security group blocking the port, or wrong IP/route. Check firewall rules, security groups, and that a route exists (traceroute).

Resolves to the wrong/old IP

DNS caching. Check the actual record (dig +short name), compare to expected, and check TTL. Flush local cache. If you just changed it, wait for the old TTL to expire.

Intermittent slowness / packet loss

Run mtr to find which hop drops packets or spikes latency. Could be a saturated link, a bad router, or an overloaded backend. Correlate with the observability metrics.

TLS/certificate errors

openssl s_client to inspect the chain and dates. Usual causes: expired cert, missing intermediate, hostname mismatch. Automate renewal to prevent recurrence.
