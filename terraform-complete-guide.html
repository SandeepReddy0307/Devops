Terraform & Infrastructure as Code: The Complete Guide

Provision and manage cloud infrastructure with code instead of clicking through consoles — from your first resource to production-grade modules, remote state, and automated pipelines.

📖 How to read this guide

Each concept follows the same rhythm: what it is (plain English), why it exists (the problem it solves), the code (real HCL), and ★ best practice. New to the cloud? Skim the Cloud/AWS guide first so the resources here make sense.

1. What is Infrastructure as Code?

Instead of clicking buttons in a cloud console to create servers, networks, and databases, you describe them in text files and let a tool build them for you — repeatably.

IaC = a recipe for your whole data center

Imagine building a house by giving verbal instructions to builders every time — you'd get a slightly different house each time and forget what you asked for. IaC is writing the blueprint down. Hand the same blueprint to the tool and you get an identical house, every time, in minutes. Change the blueprint, and the tool figures out exactly what to add, change, or remove.

Why IaC exists. Before IaC, infrastructure was built by hand: a person logged into a console and clicked through wizards to create servers, networks, and databases. This created three chronic problems. First, irreproducibility — nobody could recreate an environment exactly, so staging never quite matched production and "it works in staging" stopped meaning anything. Second, no audit trail — you couldn't see who changed what, when, or why, and you couldn't review a change before it happened. Third, snowflake servers — each machine accumulated unique manual tweaks until it became too fragile to touch or rebuild. IaC exists to bring the discipline that already tamed application code — version control, code review, testing, repeatable builds — to infrastructure.

How IaC works under the hood

An IaC tool reads your text files, builds an in-memory model of the resources you declared, compares that desired model against a record of what already exists, and emits an ordered set of API calls to close the gap. There are two philosophies for how this happens:

  • Declarative (Terraform, CloudFormation): you describe the end state and the tool computes the difference and the steps. Running it twice is safe — the second run sees nothing to do. This property is called idempotence.
  • Imperative (shell scripts, some Ansible usage): you write the steps. Running twice may do the work twice or error, unless you carefully code every step to be idempotent yourself.

Terraform is declarative, which is why it can show you a plan before touching anything: the plan is the computed difference between desired state and known state.

The same environment, reproduced in minutes
# A teammate joins and needs an identical staging stack.
# Instead of a day of console clicking:
git clone git@github.com:acme/infra.git && cd infra/environments/staging
terraform init
terraform apply        # rebuilds the entire environment from the blueprint
The subtle trap: drift

IaC only helps if the code stays the source of truth. The moment someone edits a resource by hand in the console, reality drifts away from the code. The next apply may try to "correct" that change and undo their fix, or worse, someone's manual patch keeps prod alive while the code says otherwise. The fix is cultural and technical: remove console write access in production so the only path to change is a reviewed code change (covered in depth in §17).

Mental model

Think of IaC as git for your data center. Your infrastructure has a commit history, pull requests, and the ability to roll back. The cloud becomes a rendered output of a repository — not a pile of hand-built machines nobody dares reboot.

2. Why Terraform

Terraform is the most widely-used IaC tool because it's cloud-agnostic (one language for AWS, Azure, GCP, and hundreds of providers) and declarative (you describe the desired end state, not the steps).

ConceptMeaning
DeclarativeYou say what you want ("3 servers"); Terraform figures out how to get there
ProviderA plugin that knows how to talk to a platform (AWS, Kubernetes, GitHub, Cloudflare...)
StateTerraform's record of what it has created, so it knows what to change next time
PlanA preview of exactly what will change before anything happens
Terraform vs OpenTofu

After a 2023 license change, the community forked Terraform into OpenTofu (fully open source, MPL). The commands and HCL are essentially identical (tofu instead of terraform). Everything in this guide applies to both.

Why Terraform won. Every cloud ships its own IaC tool (AWS CloudFormation, Azure ARM/Bicep, Google Deployment Manager), but each speaks only its own cloud. Terraform's bet was a single language and workflow that talks to everything through pluggable providers — so a team using AWS, Cloudflare DNS, GitHub, and Datadog manages all of it with one tool, one state model, and one review process. That portability, plus the declarative plan/apply loop, made it the de-facto standard.

How the provider protocol works under the hood

Terraform Core (the terraform binary) knows nothing about AWS or any cloud. It only understands the graph, the plan/apply lifecycle, and state. Each provider is a separate executable plugin that Terraform launches as a subprocess and talks to over a local gRPC connection. The contract has a few key calls:

  • GetSchema — the provider tells Core which resource types it supports and every attribute's type, whether it's required/optional/computed, and whether changing it forces replacement ("ForceNew").
  • PlanResourceChange — given prior state and desired config, the provider computes what the resource will look like and which attributes are "known after apply."
  • ApplyResourceChange — the provider makes the real cloud API calls and returns the new attribute values, which Core writes into state.

This separation is why Terraform can support hundreds of platforms: the core engine never changes, only the plugins do. When you write hashicorp/aws, Terraform downloads that plugin from the registry during init.

Declaring providers pins the plugins Core downloads
terraform {
  required_providers {
    aws        = { source = "hashicorp/aws",        version = "~> 5.0" }
    cloudflare = { source = "cloudflare/cloudflare", version = "~> 4.0" }
    github     = { source = "integrations/github",   version = "~> 6.0" }
  }
}
# One config, three platforms — this is Terraform's core advantage.
Terraform = a universal remote control

A universal remote works with your TV, soundbar, and streaming box because you snap in a little "code" for each device. Terraform Core is the remote; providers are those device codes. You learn one set of buttons (init/plan/apply) and it drives every cloud you plug in.

Common misconception: "declarative means no ordering"

Declarative describes the end state, but Terraform still figures out ordering itself by building a dependency graph. You don't write the steps — but that doesn't mean order is ignored. It means Terraform derives the order from how resources reference each other (see §9).

3. Install & Your First Config

Install (macOS/Linux) & verify
# macOS
brew install terraform
# or download the binary from developer.hashicorp.com/terraform
terraform version
main.tf — your first resource
terraform {
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 5.0" }
  }
}

provider "aws" {
  region = "us-east-1"
}

resource "aws_s3_bucket" "example" {
  bucket = "my-unique-bucket-name-12345"
  tags   = { Environment = "dev", ManagedBy = "terraform" }
}

Why the terraform { required_providers } block exists. It's a lock on which plugin and version Terraform uses, so every teammate and your CI resolve the identical provider. Without it, Terraform would guess the newest version, and an upstream release could silently change behavior between two people's runs. The ~> 5.0 is a pessimistic constraint: "any 5.x, but not 6.0" — you get bug fixes without surprise breaking changes.

What actually happens when you run this the first time

terraform init reads the required_providers block, downloads the AWS plugin into a hidden .terraform/ directory, and records the exact resolved versions and checksums in .terraform.lock.hcl. That lock file is the provider equivalent of package-lock.json — commit it so builds are reproducible.

First init, plan, apply — with real output
$ terraform init
Initializing provider plugins...
- Finding hashicorp/aws versions matching "~> 5.0"...
- Installing hashicorp/aws v5.60.0...
Terraform has been successfully initialized!

$ terraform plan
Terraform will perform the following actions:
  # aws_s3_bucket.example will be created
  + resource "aws_s3_bucket" "example" {
      + bucket = "my-unique-bucket-name-12345"
      + id     = (known after apply)
      + arn    = (known after apply)
    }
Plan: 1 to add, 0 to change, 0 to destroy.

$ terraform apply -auto-approve
aws_s3_bucket.example: Creating...
aws_s3_bucket.example: Creation complete after 2s [id=my-unique-bucket-name-12345]
Apply complete! Resources: 1 added, 0 changed, 0 destroyed.

Notice (known after apply) — the bucket's id and arn don't exist until AWS creates it, so Terraform marks them unknown during plan and fills them in afterward. This "known after apply" concept is central to how plans handle values that only the cloud can assign.

Common first-timer mistakes
  • Bucket name collisions — S3 bucket names are globally unique across all AWS accounts. my-bucket is long gone; add a random suffix or a company prefix.
  • No credentials — the AWS provider needs credentials (env vars, ~/.aws/credentials, or an assumed role). "No valid credential sources found" means you skipped this.
  • Wrong region — resources land in the region you set; forgetting it (or having a stale AWS_REGION env var) creates things where you didn't expect.
init = unpack the toolbox, apply = build

init is like unpacking the right toolbox for the job (downloading the AWS "tools"). plan is the contractor walking you through exactly what they'll build before lifting a hammer. apply is them actually building it.

4. The Core Workflow — init, plan, apply

Three commands are 90% of daily Terraform. Learn this loop cold.

The daily loop
terraform init          # download providers, set up backend (run once / when providers change)
terraform fmt           # auto-format your .tf files
terraform validate      # check syntax
terraform plan          # preview: what will be added/changed/destroyed?
terraform apply         # execute the plan (asks for confirmation)
terraform destroy       # tear everything down
Always plan before you apply

Read every plan. The summary line — Plan: 2 to add, 1 to change, 0 to destroy — is the most important text in Terraform. A surprise destroy on a database is how outages happen. Save plans in CI (terraform plan -out=tfplan) and apply exactly that reviewed plan.

Why the loop is split into distinct commands. Separating preview (plan) from execution (apply) is the single most important safety property Terraform gives you. Every other benefit — code review of infra changes, gated production deploys, catching an accidental delete — flows from being able to see the exact diff before it happens. Configuration management tools that lack a first-class plan step force you to apply-and-hope.

How plan is actually computed

A plan runs in four internal phases:

  1. Load & evaluate config — parse the .tf files, resolve variables, locals, and expressions into concrete desired values (where known).
  2. Refresh — for every resource already in state, Terraform calls the provider's read API to get its current real-world attributes. This is how drift is detected.
  3. Build the graph & diff — Terraform builds the dependency graph, then walks it asking each provider's PlanResourceChange to compare desired config vs refreshed state. The result is a set of actions: create (+), update in place (~), replace (-/+), or destroy (-).
  4. Render — the diff is printed for you to read.

Crucially, plan makes no changes — it only reads. apply re-runs the plan (or uses a saved one) and then executes the actions in graph order.

Reading the four change symbols in a plan
  + create              # a new resource
  ~ update in-place     # a mutable attribute changes (e.g. a tag)
-/+ destroy and re-create  # a "ForceNew" attribute changed — DANGER
  - destroy             # resource removed from code

# Example of the dangerous one:
  # aws_db_instance.main must be replaced
-/+ resource "aws_db_instance" "main" {
      ~ availability_zone = "us-east-1a" -> "us-east-1b"  # forces replacement
    }
Plan: 1 to add, 0 to change, 1 to destroy.   # a DB replacement = data loss risk!
The -/+ trap and the stale-plan trap

Two classic mistakes: (1) skimming past a -/+ (destroy-and-recreate) on a stateful resource like a database — always read which attribute forces replacement. (2) Running terraform apply without a saved plan in CI, so it computes a fresh plan at apply time. Between review and apply the world may have changed (Time-Of-Check to Time-Of-Use). Always plan -out=tfplan then apply tfplan.

plan is a "diff", apply is a "commit"

If you know git: plan is git diff — it shows what would change, harmlessly. apply is git commit && push — it makes the change real. You'd never push code you didn't diff; never apply infra you didn't plan.

5. HCL & Resources

HashiCorp Configuration Language (HCL) is the declarative language. Its core building block is the resource.

Resource anatomy & referencing
resource "aws_instance" "web" {      # TYPE "aws_instance", NAME "web"
  ami           = "ami-0abc123"
  instance_type = "t3.micro"
  tags = { Name = "web-server" }
}

# Reference another resource's attribute -> creates an implicit dependency
resource "aws_eip" "web_ip" {
  instance = aws_instance.web.id     # <type>.<name>.<attribute>
}

# Data source: read something that ALREADY exists (not managed by you)
data "aws_ami" "ubuntu" {
  most_recent = true
  owners      = ["099720109477"]
  filter { name = "name"  values = ["ubuntu/images/*22.04*"] }
}

Why HCL instead of JSON or YAML. HCL was designed to be both human-friendly to write and machine-friendly to generate. It adds first-class support for expressions, references between resources, comments, and multi-line strings — things raw JSON handles awkwardly. Every HCL file has an exact JSON equivalent (Terraform can read .tf.json), so tools can generate it, but humans get a cleaner surface.

The four top-level block types you'll use daily

BlockWhat it declaresManaged by TF?
resourceSomething Terraform creates and owns (a server, bucket, DNS record)Yes — created, updated, destroyed
dataSomething that already exists, read-only (an existing AMI, VPC, secret)No — only read during plan
providerHow to talk to a platform (region, credentials, alias)N/A — configuration
locals / variable / outputComputed values, inputs, and exported resultsN/A — values

How references create the dependency graph

The line instance = aws_instance.web.id is doing two jobs. It supplies a value, and it tells Terraform "the EIP needs the instance's id, so the instance must be created first." Terraform parses these <type>.<name>.<attribute> references at plan time and turns each into a graph edge. You almost never write ordering explicitly — you express it by referencing. This is the heart of §9.

Resource vs data source — a worked contrast
# DATA: look up the latest Ubuntu AMI AWS already publishes (we don't own it)
data "aws_ami" "ubuntu" {
  most_recent = true
  owners      = ["099720109477"]
  filter { name = "name" values = ["ubuntu/images/*22.04*"] }
}

# RESOURCE: create an instance FROM that looked-up AMI (we own the instance)
resource "aws_instance" "web" {
  ami           = data.aws_ami.ubuntu.id   # reference -> implicit dependency
  instance_type = "t3.micro"
}
The reference produces graph order automatically
$ terraform apply
data.aws_ami.ubuntu: Reading...                    # data sources read first
data.aws_ami.ubuntu: Read complete [id=ami-0abc123]
aws_instance.web: Creating...                      # then the resource that needs it
aws_instance.web: Creation complete [id=i-0def456]
Common gotchas with resources & data sources
  • Renaming the label recreates the resource. Changing "web" to "webserver" makes Terraform think the old one is gone and a new one appeared → destroy + create. Use a moved block (§17) to rename safely.
  • Data sources can hide drift. most_recent = true on an AMI means a new upstream image can silently change your instance's AMI on the next plan, triggering a replacement. Pin to a specific AMI id for stability.
  • Don't manage the same resource twice. A resource and an import both pointing at one real object, or two configs owning the same thing, causes fights and corruption.
resource = "make this", data = "find this"

resource is you telling the tool "build me a house." data is you saying "look up the address of the house next door so I can point my driveway at it" — you're reading something that already exists, not building it.

6. Variables & Outputs

variables.tf / outputs.tf
variable "instance_count" {
  description = "How many web servers"
  type        = number
  default     = 2
  validation {
    condition     = var.instance_count > 0 && var.instance_count <= 10
    error_message = "instance_count must be between 1 and 10."
  }
}

variable "environment" { type = string }

output "web_public_ip" {
  value       = aws_eip.web_ip.public_ip
  description = "Public IP of the web server"
}
Passing variable values
terraform apply -var="environment=prod"           # CLI
terraform apply -var-file="prod.tfvars"           # file
export TF_VAR_environment=prod                     # env var
# Precedence: CLI > *.auto.tfvars > terraform.tfvars > env vars > default

Why variables and outputs exist. They turn a hardcoded config into a reusable one. Variables are a module's parameters — the knobs a caller turns (region, instance size, count). Outputs are its return values — the facts other configs or humans need (an IP, an ARN, a connection string). Together they define the public interface of a module, hiding the messy internals. This input/output contract is exactly what makes modules composable (§10) and layers stackable (§29).

How variable precedence resolves under the hood

When the same variable is set in several places, Terraform picks a winner by a fixed order (highest wins): an explicit -var on the CLI beats -var-file, which beats *.auto.tfvars (loaded automatically, alphabetically), which beats terraform.tfvars, which beats TF_VAR_* environment variables, which beats the default. If nothing sets a variable that has no default, Terraform interactively prompts for it — which will hang a CI job, so always pass values non-interactively in automation.

Types and validation make bad input fail early

Declaring type = number or a full object({...}) means Terraform rejects a wrongly-typed value at plan time with a clear error, instead of passing garbage to the cloud API and getting a cryptic 400 later. validation blocks let you assert business rules ("count between 1 and 10"), and sensitive = true redacts a value from plan/apply output.

Rich types, sensitivity, and locals
variable "db_password" {
  type      = string
  sensitive = true            # redacted in CLI output (still lands in state!)
}

variable "subnets" {
  type = map(object({ cidr = string, az = string }))
  default = {
    a = { cidr = "10.0.1.0/24", az = "us-east-1a" }
    b = { cidr = "10.0.2.0/24", az = "us-east-1b" }
  }
}

# locals = computed, named values reused across the config (not caller inputs)
locals {
  name_prefix = "${var.environment}-web"
  common_tags = { Environment = var.environment, ManagedBy = "terraform" }
}
Reading outputs after apply
$ terraform output
web_public_ip = "54.210.11.22"

$ terraform output -raw web_public_ip   # -raw for piping into scripts
54.210.11.22

$ terraform output -json               # machine-readable, for CI
sensitive hides output, not state

Marking a variable or output sensitive only stops it being printed. The value is still stored in plaintext in the state file. A DB password passed through Terraform is readable by anyone who can read state. This is why state must be encrypted and access-controlled (§7, §16) — sensitivity flags are cosmetic, not cryptographic.

Common variable mistakes
  • Committing *.tfvars with secrets. Values files often hold environment specifics; if they contain secrets, they leak in Git. Keep secrets out and pull them from a secrets manager instead.
  • No type. Untyped variables accept anything and fail deep in an API call. Always declare a type.
  • Overusing variables. Not everything needs to be a variable — hardcode true constants; parameterize only what genuinely varies between callers/environments.
Variables = the form you fill in; outputs = the receipt

A module is like a vending machine. Variables are the buttons you press (which drink, what size). Outputs are the receipt it prints (what you got, where it is). locals are the machine's internal wiring — helpful shorthand nobody outside needs to see.

7. State — the Heart of Terraform

State is Terraform's memory. It maps your code to the real resources it created. Understanding it is the difference between using Terraform and fighting it.

Never commit state to Git, never hand-edit it

The state file (terraform.tfstate) contains resource IDs and often secrets (DB passwords, keys) in plain text. Committing it leaks secrets and causes conflicts. Store it remotely (next section). If you must edit it, use terraform state subcommands — never a text editor.

Why state exists at all. Terraform code says what you want, and the cloud knows what exists, but there's a missing link: which real resource corresponds to which block in my code? The cloud has an instance i-0abc123; your code has aws_instance.web. State is the mapping between them. Without it, on the next run Terraform couldn't tell "update the web server I made" from "make a brand-new web server," and it couldn't know that a resource you deleted from code should now be destroyed.

What state actually is under the hood

The state file is JSON. For each managed resource it stores: the resource address (aws_instance.web), the provider that manages it, the real-world id, a full snapshot of every attribute as of the last apply, and dependency metadata. Terraform uses this snapshot for two things: (1) to know the resource's identity so it can call the right update/delete APIs, and (2) as a performance cache so it doesn't have to re-read every attribute of every resource on every command (though refresh does re-read to catch drift).

A single resource inside terraform.tfstate (abridged)
{
  "resources": [{
    "type": "aws_instance",
    "name": "web",
    "provider": "provider[\"registry.terraform.io/hashicorp/aws\"]",
    "instances": [{
      "attributes": {
        "id": "i-0abc123def456",
        "instance_type": "t3.micro",
        "private_ip": "10.0.1.20",
        "root_block_device": [{ "volume_size": 8 }]
      },
      "dependencies": ["aws_subnet.main"]
    }]
  }]
}
Inspecting state safely (read-only)
terraform state list                    # all resource addresses TF manages
terraform state show aws_instance.web   # full recorded attributes of one
terraform show                          # human-readable view of entire state
The classic state disasters
  • Lost state = "everything is new." Delete or lose the state file and Terraform forgets it ever made anything. The next plan wants to recreate resources that already exist, causing duplicate-name errors or, worse, deleting-and-remaking live infra. Back state up and store it remotely.
  • Two people, one local state. Local state on laptops diverges instantly. Person A applies, person B's copy is now stale and their apply overwrites A's work. This is why teams need remote state + locking (§8).
  • Hand-editing the JSON. One mismatched bracket or wrong id corrupts state and every future plan. Use terraform state subcommands only.
  • Secrets in state. Passwords, private keys, and tokens are stored verbatim. Treat the state file itself as a secret.
State = Terraform's memory / a valet ticket

When you valet-park, you get a ticket that links you to your specific car in the lot. State is that ticket: it links each block in your code to the exact real resource it created. Lose the ticket and the valet (Terraform) can't tell which car is yours — it might hand you a new one or, chaotically, treat someone else's as yours.

8. Remote State & Locking

For any team, state must live in shared remote storage with locking so two people can't apply at once and corrupt it.

S3 backend with DynamoDB locking
terraform {
  backend "s3" {
    bucket         = "mycompany-tfstate"
    key            = "prod/network/terraform.tfstate"
    region         = "us-east-1"
    dynamodb_table = "terraform-locks"   # prevents concurrent applies
    encrypt        = true
  }
}
One state per environment + component

Don't put your whole company in one state file — a mistake there is catastrophic and plans get slow. Split by environment and component (e.g., prod/network, prod/database, staging/app). Smaller state = smaller blast radius, faster plans, and independent team ownership.

Why remote state and locking exist. Local state works for one person on one machine. The moment a team shares infrastructure, local state fails: copies diverge, secrets sit on laptops, and two simultaneous applies race to write the file, corrupting it. A remote backend puts state in shared, durable, encrypted storage (S3, GCS, Azure Blob, Terraform Cloud). A lock ensures only one apply mutates that state at a time.

How state locking works under the hood

Before any operation that could write state (apply, state mv, etc.), Terraform tries to acquire a lock. With the S3 backend, this historically meant writing a lock record into a DynamoDB table with a fixed key; if the record already exists, someone else holds the lock and Terraform refuses to proceed, printing the lock ID, who holds it, and since when. When the operation finishes, Terraform deletes the lock record. DynamoDB's conditional writes make this atomic, so two racing applies can't both win. (Newer Terraform versions also support native S3 lockfiles.)

What a lock conflict looks like
$ terraform apply
╷
│ Error: Error acquiring the state lock
│ Lock Info:
│   ID:        7f3c1a2b-...  
│   Who:       alice@laptop
│   Created:   2026-01-14 09:32:11 UTC
│   Operation: OperationTypeApply
╵
# Someone (alice) is mid-apply. WAIT. Only force-unlock if you're certain
# the holder crashed and no apply is running:
$ terraform force-unlock 7f3c1a2b-...
Migrating existing local state to a remote backend
# After adding the backend "s3" block to your config:
$ terraform init
Initializing the backend...
Do you want to copy existing state to the new backend?
  Terraform detected that the backend type changed from "local" to "s3".
  Enter "yes" to copy: yes
Successfully configured the backend "s3"! Terraform will automatically
use this backend unless the backend configuration changes.
Remote-state gotchas
  • Force-unlocking during a live apply lets a second apply run concurrently — the exact corruption locking prevents. Only force-unlock when you're certain the lock holder crashed.
  • Backend config can't use variables. The backend block is read during init before variables are evaluated, so bucket/key must be literals or passed via -backend-config. This is why tools like Terragrunt (§26) exist to generate it.
  • Forgetting encryption + versioning on the state bucket. Enable encrypt = true, bucket versioning (for recovery), and a strict bucket policy — state holds secrets.
  • Deleting the DynamoDB table / lock backend mid-flight orphans locks. Manage the backend infra (bucket + lock table) in its own tiny bootstrap config.
Locking = the single bathroom key

Picture an office with one bathroom and one physical key. You can't get in while someone else holds the key — you wait. When they come out, they hand the key back. State locking is that key: only one person can be "changing infrastructure" at a time, so two people can't collide inside.

9. Dependencies & the Graph

Terraform builds a dependency graph and provisions resources in the right order automatically — mostly.

Implicit vs explicit dependencies
# Implicit (preferred): referencing an attribute creates the edge
subnet_id = aws_subnet.main.id

# Explicit: when there's a hidden ordering Terraform can't infer
resource "aws_instance" "app" {
  depends_on = [aws_iam_role_policy.app_policy]
}
See the graph

terraform graph | dot -Tsvg > graph.svg renders the dependency DAG — useful for understanding why things apply in a certain order.

Why a graph. Cloud resources have real ordering constraints: a subnet needs its VPC first, an instance needs its subnet, an Elastic IP needs its instance. Rather than make you sequence these by hand, Terraform infers the order from your references and provisions in the correct sequence — and parallelizes everything that has no dependency between them, so large applies finish fast.

How the graph is built and walked under the hood

Terraform constructs a Directed Acyclic Graph (DAG). Every resource, data source, provider, variable, and output becomes a node. Every reference (aws_subnet.main.id) or depends_on becomes a directed edge: "B depends on A." Terraform then does a topological sort — an ordering where every node comes after everything it depends on. During apply it walks the graph, executing nodes as soon as all their dependencies are complete, running independent branches in parallel (default: up to 10 concurrent operations, tunable with -parallelism=N). Because it's acyclic, a cycle (A needs B, B needs A) is an error Terraform refuses to run.

A cycle Terraform will reject
# These reference each other → cycle → error
resource "aws_security_group" "a" {
  ingress { security_groups = [aws_security_group.b.id] }
}
resource "aws_security_group" "b" {
  ingress { security_groups = [aws_security_group.a.id] }
}
# Fix: break the cycle with separate aws_security_group_rule resources.
The error you'll see
$ terraform plan
Error: Cycle: aws_security_group.a, aws_security_group.b
Dependency gotchas
  • Overusing depends_on. It's for hidden dependencies Terraform can't see (e.g., an IAM policy must exist before an instance can use a role, but no attribute is referenced). Sprinkling it everywhere serializes your graph and slows applies. Prefer implicit references.
  • Hidden ordering bugs. If two resources really depend on each other but you never reference the attribute, Terraform may create them in parallel and one fails intermittently. That's the legitimate case for depends_on.
  • depends_on on a module forces the whole module to wait — powerful but blunt; it can serialize far more than intended.
The graph = a recipe's step order

A recipe says "boil water" before "add pasta" before "drain." You don't number every step arbitrarily — the ingredients imply the order (you can't drain pasta you haven't cooked). Terraform reads your "ingredients" (references) and figures out the cooking order itself, doing independent steps (chopping veg while water boils) at the same time.

10. Modules — Reusable Building Blocks

A module is a folder of .tf files you can call with inputs — the function/package of infrastructure. This is how you stop copy-pasting and scale.

Calling a module
module "network" {
  source  = "./modules/vpc"        # local; or a registry/Git URL + version
  # source  = "terraform-aws-modules/vpc/aws"
  # version = "5.5.0"

  cidr_block  = "10.0.0.0/16"
  environment = var.environment
}

# Use the module's outputs
resource "aws_instance" "app" {
  subnet_id = module.network.private_subnet_ids[0]
}
Pin module & provider versions

Always pin versions (version = "5.5.0" or a ~> range) for modules and providers. Unpinned versions mean an upstream release can silently change your infrastructure on the next init. Prefer battle-tested community modules (the terraform-aws-modules collection) over reinventing VPCs.

Why modules exist. Without them you copy-paste the same 200 lines of VPC config into dev, staging, and prod, and they slowly drift apart until each environment is a unique snowflake — the exact problem IaC was meant to kill. A module packages a set of resources behind a clean interface (inputs and outputs) so you define "a VPC" once, get it reviewed and tested once, and instantiate it many times with different parameters. Modules are to infrastructure what functions are to code: the primary tool for DRY, encapsulation, and reuse.

How modules work under the hood

Calling module "network" { source = ... } tells Terraform to load that folder's .tf files as a child scope. During init, Terraform fetches the source (copies a local path, clones a Git ref, or downloads a registry release into .terraform/modules/). The child's variable blocks become the arguments you must/can pass; its output blocks become module.network.<output> in the parent. Internally, every resource gets an address that includes the module path — module.network.aws_vpc.main — and all of a module's resources still live in the same state file as their caller (a module is a code-organization boundary, not a state boundary). Modules can nest, forming a tree, and the whole tree is flattened into one dependency graph.

Inside a module: modules/vpc/ (variables → resources → outputs)
# modules/vpc/variables.tf  — the module's INPUTS (its interface)
variable "cidr_block"  { type = string }
variable "environment" { type = string }

# modules/vpc/main.tf — the encapsulated resources
resource "aws_vpc" "this" {
  cidr_block = var.cidr_block
  tags       = { Name = "${var.environment}-vpc" }
}
resource "aws_subnet" "private" {
  count      = 2
  vpc_id     = aws_vpc.this.id
  cidr_block = cidrsubnet(var.cidr_block, 8, count.index)
}

# modules/vpc/outputs.tf — the module's OUTPUTS (its return values)
output "vpc_id"             { value = aws_vpc.this.id }
output "private_subnet_ids" { value = aws_subnet.private[*].id }
Module resource addresses in state & plan
$ terraform plan
  # module.network.aws_vpc.this will be created
  # module.network.aws_subnet.private[0] will be created
  # module.network.aws_subnet.private[1] will be created
Plan: 3 to add, 0 to change, 0 to destroy.

$ terraform state list
module.network.aws_vpc.this
module.network.aws_subnet.private[0]
module.network.aws_subnet.private[1]
Module gotchas
  • Unpinned source from Git. source = "git::...//modules/vpc" without a ?ref=v1.2.0 tracks the default branch — a teammate's merge silently changes your infra on next init. Always pin a tag.
  • Leaky interfaces. Exposing 40 pass-through variables recreates the copy-paste problem. Expose only what genuinely varies; sane defaults for the rest.
  • Deep nesting. Modules calling modules calling modules become impossible to reason about and slow to plan. Keep the tree shallow (1–2 levels).
  • Renaming/moving a module changes every child resource's address → mass destroy/recreate. Use moved blocks (§17) when refactoring module structure.
  • Provider config inside reusable modules. Best practice is to receive providers from the caller, not declare them, so the module stays portable across regions/accounts (§25).
Module = a LEGO kit with an instruction card

A module is a sealed LEGO kit: the instruction card lists the few choices you make (color, size = the variables), and out comes a finished spaceship (the resources), with a couple of studs exposed to click onto other kits (the outputs). You don't rebuild the spaceship from loose bricks each time — you reuse the kit.

11. count, for_each & Dynamic Blocks

Creating multiple resources
# for_each (preferred) — keyed by a stable identifier, safe to add/remove
resource "aws_iam_user" "team" {
  for_each = toset(["alice", "bob", "carol"])
  name     = each.key
}

# count — indexed; removing a middle item re-indexes the rest (risky)
resource "aws_instance" "web" {
  count         = var.instance_count
  instance_type = "t3.micro"
}
Prefer for_each over count for sets

With count, deleting the middle element shifts all indexes, so Terraform destroys and recreates unrelated resources. for_each keys resources by name, so changes are surgical. Use count only for simple "N identical copies" or conditional creation (count = var.enabled ? 1 : 0).

Why these meta-arguments exist. You rarely want exactly one of something. You want "a bucket per team," "a subnet per availability zone," "a firewall rule per allowed port." Writing each resource by hand is repetitive and error-prone. count and for_each let one block declare many instances driven by data, and dynamic blocks do the same for repeated nested blocks inside a single resource.

How instances are keyed in state — the crux of count vs for_each

This is the single most important thing to understand here. Terraform tracks each generated instance by a key in state:

  • count keys instances by integer position: aws_instance.web[0], [1], [2]. The key is the index.
  • for_each keys instances by a string from the map/set: aws_iam_user.team["alice"], ["bob"]. The key is the identity.

Now remove "bob" from the middle of a count list of three. Everything after him shifts index: what was [2] becomes [1]. Terraform sees [1]'s attributes changed (it was carol, now it's... carol at a new index) and [2] gone — so it destroys and recreates carol even though you only wanted to remove bob. With for_each, removing "bob" only destroys ["bob"]; ["alice"] and ["carol"] keep their keys untouched. This is why for_each is the default choice for any collection of distinct things.

The count re-indexing trap, made concrete
# Before:  count over ["alice","bob","carol"]
aws_iam_user.team[0] = alice
aws_iam_user.team[1] = bob
aws_iam_user.team[2] = carol

# You remove "bob". With COUNT, plan shows:
  ~ aws_iam_user.team[1]  name: "bob"   -> "carol"   # in-place churn
  - aws_iam_user.team[2]  (carol destroyed)          # collateral damage!
Plan: 0 to add, 1 to change, 1 to destroy.

# The SAME change with FOR_EACH:
  - aws_iam_user.team["bob"]  will be destroyed       # only bob, surgical
Plan: 0 to add, 0 to change, 1 to destroy.
The right tool for each job
# for_each over a MAP — best: stable keys AND per-item config
resource "aws_instance" "svc" {
  for_each      = var.services      # map(object)
  instance_type = each.value.size
  tags          = { Name = each.key }
}

# count for CONDITIONAL creation — the one place count shines
resource "aws_cloudwatch_dashboard" "prod_only" {
  count = var.environment == "prod" ? 1 : 0
  # reference it as aws_cloudwatch_dashboard.prod_only[0]
}
More count/for_each gotchas
  • for_each keys must be known at plan time. You can't key for_each off an attribute that's "known after apply" (like a resource id not yet created). Terraform errors with "Invalid for_each argument." Key off inputs/locals instead, or split the apply.
  • for_each needs a set or map, not a list — wrap lists with toset(...). Duplicate values in a list would collide as keys anyway.
  • Switching a resource from count to for_each changes every instance's key ([0] → ["alice"]), so Terraform wants to recreate them all. Use terraform state mv or moved blocks to migrate keys without recreation.
  • Toggling a count = ...?1:0 resource destroys/recreates on every flip — fine for a dashboard, dangerous for a database.
count = numbered lockers, for_each = name-tagged lockers

Numbered lockers (count): remove locker #2 and everyone shuffles down — #3's stuff is now in #2's spot, chaos. Name-tagged lockers (for_each): remove "Bob's locker" and Alice's and Carol's are untouched, because each is tied to a name, not a position. Use names whenever the things are distinct.

12. Managing Environments

dev / staging / prod must be consistent but independent. The dominant pattern: a shared module, one thin directory per environment, separate state.

Directory layout
modules/
  vpc/          # reusable
  app/
environments/
  dev/    main.tf  dev.tfvars     # calls modules, own backend state
  staging/main.tf  staging.tfvars
  prod/   main.tf  prod.tfvars
Terragrunt keeps it DRY

As environments multiply, Terragrunt reduces backend/provider boilerplate and enforces consistent structure. Worth adopting once you have 3+ environments or many components.

Why environment separation matters. Dev, staging, and prod must be structurally identical (so testing in staging is meaningful) yet completely isolated (so a dev experiment can never touch prod, and a prod outage can't cascade to staging). The tension — same shape, separate blast radius — is what all the patterns below solve. Sharing a module gives you sameness; separate directories + separate state give you isolation.

Why "directory per environment" beats the alternatives

Three approaches exist, and the industry converged on the third for good reasons:

ApproachIsolationVerdict
Workspaces (§13)Same code + same backend, different stateWeak — a bad code change hits all envs; only terraform.workspace differs
Branches per envDifferent Git branchesBad — envs drift, merges are scary, promoting a change is a merge conflict
Directory per env + shared moduleSeparate code entrypoint and separate backend/state★ Standard — full isolation, explicit config, easy to reason about
A thin per-environment entrypoint (environments/prod/main.tf)
terraform {
  backend "s3" {
    bucket = "myco-tfstate"
    key    = "prod/app/terraform.tfstate"   # env-specific state key
    region = "us-east-1"
  }
}
module "app" {
  source      = "../../modules/app"         # SAME module every env calls
  environment = "prod"
  cidr_block  = "10.2.0.0/16"               # env-specific inputs
  instance_type = "m5.large"                # prod is bigger
}
Each environment is applied independently
# Promoting a change: apply dev, verify, then staging, then prod —
# each with its own state, from its own directory.
cd environments/dev     && terraform apply -var-file=dev.tfvars
cd ../staging           && terraform apply -var-file=staging.tfvars
cd ../prod              && terraform apply -var-file=prod.tfvars   # gated in CI
Environment gotchas
  • Copy-paste drift between env directories. The whole point of the shared module is that the only differences between envs are the input values. If prod/main.tf and dev/main.tf have diverging resource blocks, you've recreated snowflakes. Keep logic in the module; keep only inputs in the env dirs.
  • Shared state across envs. If two environments write the same state key, they fight. Every environment needs a distinct backend key.
  • Cross-environment references. Prod should never depend on dev's outputs. Keep dependencies within an environment (or via a shared "foundation" layer, §29).
One blueprint, three separate buildings

The module is a house blueprint. Dev, staging, and prod are three houses built from it on three different plots (separate state). They look the same, but renovating one can't collapse the others. You'd never build all three rooms sharing one foundation — a crack anywhere would sink everything.

13. Workspaces

Workspaces let one config have multiple independent states (default, dev, prod).

Workspace commands
terraform workspace new dev
terraform workspace select dev
terraform workspace list
# reference in code: terraform.workspace
Workspaces are not for prod isolation

Workspaces share the same backend and code, so a bad change affects all of them. For real dev/prod separation use separate directories + separate backends (§12). Workspaces suit short-lived, ephemeral copies (per-developer or per-PR environments).

Why workspaces exist. Sometimes you want several parallel copies of the same config that shouldn't share state — a throwaway environment per pull request, or a personal sandbox per developer — without creating a whole new directory and backend for each. Workspaces give one configuration multiple named states cheaply.

How workspaces work under the hood

A workspace is just a separate state file behind the same backend. With the S3 backend, the default workspace stores state at your configured key; every other workspace stores it under env:/<workspace-name>/<key>. The code, the providers, and the backend are identical across workspaces — only the state (and thus the real resources it tracks) differ. Inside your config, terraform.workspace evaluates to the current workspace name, letting you vary a few values (like a name suffix or instance count) per workspace.

Using terraform.workspace to vary sizing
locals {
  # bigger only in a workspace literally named "prod"
  instance_type = terraform.workspace == "prod" ? "m5.large" : "t3.micro"
}
resource "aws_instance" "web" {
  instance_type = local.instance_type
  tags = { Name = "web-${terraform.workspace}" }   # web-pr-123, web-dev...
}
Where each workspace's state lives
$ terraform workspace list
* default
  pr-123
  pr-124

# In the S3 bucket:
#   prod/app/terraform.tfstate               <- default workspace
#   env:/pr-123/prod/app/terraform.tfstate   <- workspace pr-123
#   env:/pr-124/prod/app/terraform.tfstate   <- workspace pr-124
The workspace-for-environments anti-pattern

Using workspaces dev/staging/prod feels tidy but is dangerous: all three run the same code from the same directory, so a bad edit is one terraform apply away from hitting prod, and it's easy to forget which workspace is selected and apply to the wrong one. There's no code-review boundary between environments. Real environments belong in separate directories with separate backends (§12). Reserve workspaces for ephemeral, identical copies.

Workspace gotchas
  • Forgetting which workspace is active — terraform apply hits whatever workspace select last chose. Always check terraform workspace show in scripts/CI.
  • Terraform Cloud workspaces are different — there a "workspace" is a full isolated environment with its own variables, closer to a directory-per-env. Don't conflate CLI workspaces with TFC workspaces.
Workspaces = save slots in a video game

One game (your code), multiple save files (states). Loading a different save gives you a different world, but it's the same game with the same rules. Great for "let me try this on a fresh save." You would not keep your one irreplaceable prod playthrough as just another save slot in the same file — too easy to overwrite the wrong one.

14. Terraform in CI/CD

Manual applies from laptops don't scale and aren't auditable. Run Terraform in a pipeline: plan on PR, apply on merge.

GitHub Actions — plan on PR, apply on merge
jobs:
  plan:
    runs-on: ubuntu-latest
    permissions: { id-token: write, contents: read, pull-requests: write }
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4      # OIDC, no static keys
        with: { role-to-assume: arn:aws:iam::123:role/tf, aws-region: us-east-1 }
      - uses: hashicorp/setup-terraform@v3
      - run: terraform init
      - run: terraform plan -out=tfplan            # post the plan on the PR
  apply:
    if: github.ref == 'refs/heads/main'
    needs: plan
    environment: production                         # requires manual approval
    steps: [ "...", "terraform apply tfplan" ]
The golden CI rules for Terraform
  • Plan on PR so reviewers see infra changes alongside code.
  • Apply the reviewed plan file (-out), not a fresh plan, to avoid TOCTOU surprises.
  • OIDC, never static cloud keys (see the CI/CD guide).
  • Gate prod applies behind manual approval / protected environments.

Why run Terraform in CI/CD at all. Laptop applies are the root of most Terraform incidents: no review of the diff, no audit of who applied what, long-lived cloud admin keys sitting in shell history, and state races when two engineers apply at once. Moving Terraform into a pipeline makes every infra change a reviewed, logged, repeatable event — the same bar you hold application code to. The pipeline becomes the only identity with write access to prod.

How the plan-on-PR / apply-on-merge flow works

The pipeline splits Terraform's two phases across two moments in the Git lifecycle:

  1. On pull request: CI runs fmt, validate, security scans, then terraform plan -out=tfplan. It posts the human-readable plan as a PR comment so reviewers approve the infrastructure diff, not just the code. Nothing is applied.
  2. On merge to main: a gated job applies exactly the saved plan file (terraform apply tfplan). Because it applies the reviewed artifact rather than recomputing, what got approved is what runs — closing the Time-Of-Check-to-Time-Of-Use gap.

Authentication uses OIDC: the CI runner presents a short-lived signed token to the cloud, which exchanges it for temporary credentials scoped to a specific role. No static access keys ever exist to leak.

Passing the reviewed plan artifact between jobs
  plan:
    steps:
      - run: terraform plan -out=tfplan -no-color
      - run: terraform show -no-color tfplan > plan.txt
      - uses: actions/upload-artifact@v4          # save the exact plan
        with: { name: tfplan, path: tfplan }
      # (a separate step comments plan.txt onto the PR)
  apply:
    needs: plan
    if: github.ref == 'refs/heads/main'
    environment: production                        # protected → manual approval
    steps:
      - uses: actions/download-artifact@v4         # get the SAME plan back
        with: { name: tfplan }
      - run: terraform apply -input=false tfplan   # apply the reviewed artifact
The mistakes that make CI Terraform dangerous
  • Auto-apply on merge with no gate. A merged typo becomes a prod change with no human in the loop. Gate prod behind a protected environment / manual approval.
  • Re-planning at apply time. terraform apply (no plan file) recomputes and may apply something never reviewed. Always apply the saved -out plan.
  • Static cloud keys in CI secrets. Long-lived keys leak via logs, forks, or compromised actions. Use OIDC and short-lived credentials.
  • No state lock in CI. Two pipelines applying different branches race. Remote state + locking (§8) is mandatory before you automate.
  • Plans over-privileged. The plan role should ideally be read-only; only the apply role needs write. Splitting them limits blast radius of a compromised PR pipeline.
CI = the change-approval desk for your cloud

Instead of anyone walking into the server room and rewiring things (laptop applies), every change goes to a desk: you submit a request (PR), a reviewer sees exactly what will change (the plan), signs off, and only then does an authorized robot (CI) make the change and log it. If something breaks, there's a paper trail of who approved what.

15. Testing & Validation

ToolPurpose
terraform fmt/validateFormat + syntax; run in pre-commit & CI
tflintLint for provider-specific errors and bad practices
tfsec / Checkov / TrivySecurity scanning (open S3 buckets, unencrypted volumes)
terraform testNative testing framework (.tftest.hcl) for modules
TerratestGo-based real-infra integration tests (apply, assert, destroy)

Why test infrastructure code. A bug in a Terraform module doesn't crash a unit test — it provisions a real, misconfigured, sometimes public, sometimes expensive resource. And a module is reused across every environment, so one defect multiplies. Testing catches the security misconfig, the invalid combination, and the accidental replacement before it reaches prod, and it lets you refactor modules with confidence.

The testing pyramid for Terraform

Layer cheap-and-fast checks under expensive-and-slow ones, running the fast ones on every commit and the slow ones less often:

  • Static (seconds, every commit): fmt, validate, tflint, tfsec/Checkov. No cloud calls — pure config analysis. Catches syntax, style, obvious insecurity.
  • Plan-based / unit (fast): terraform test with command = plan and assert blocks. Verifies your config computes the right values without creating anything.
  • Integration (minutes, real cloud): terraform test with command = apply, or Terratest. Actually provisions in a sandbox account, asserts the resource works, then destroys. Slow and costs money, so run selectively.
Native terraform test — a plan-based assertion (tests/vpc.tftest.hcl)
variables { cidr_block = "10.0.0.0/16", environment = "test" }

run "vpc_cidr_is_correct" {
  command = plan                              # no resources created

  assert {
    condition     = aws_vpc.this.cidr_block == "10.0.0.0/16"
    error_message = "VPC CIDR did not match the input"
  }
}

run "creates_two_subnets" {
  command = apply                             # real apply in a sandbox
  assert {
    condition     = length(aws_subnet.private) == 2
    error_message = "Expected exactly two private subnets"
  }
}
Running the test suite
$ terraform test
tests/vpc.tftest.hcl... in progress
  run "vpc_cidr_is_correct"... pass
  run "creates_two_subnets"... pass          # apply + auto-destroy handled
tests/vpc.tftest.hcl... tearing down
Success! 2 passed, 0 failed.
Testing gotchas
  • Integration tests leak resources on failure. If a test crashes between apply and destroy, it orphans real (billable) infra. Run them in a dedicated sandbox account with automated cleanup/nuke jobs.
  • Testing only the happy path. Also assert that bad inputs are rejected — that your validation blocks and preconditions actually fail. Use expect_failures in terraform test.
  • Confusing static scan pass with correctness. tfsec passing means "no known-bad patterns," not "does what you intended." You still need behavioral tests.
  • Slow integration tests in the PR gate. Keep the PR fast (static + plan tests); run full apply/destroy integration on a schedule or pre-release, not on every push.
Testing = a dress rehearsal before opening night

Static checks are proofreading the script (spelling, grammar). Plan tests are a table read — you check the lines make sense without building the set. Integration tests are the full dress rehearsal on a real stage (a sandbox), performed and then struck, so opening night (prod) has no surprises.

16. Security & Secrets

Secrets in state & code

Never hardcode passwords/keys in .tf files. Pull them at runtime from a secrets manager (AWS Secrets Manager, Vault) via data sources, and remember they still land in the state file — so encrypt state at rest and lock down who can read the state bucket. Scan every plan with tfsec/Checkov in CI.

Reference a secret instead of hardcoding
data "aws_secretsmanager_secret_version" "db" {
  secret_id = "prod/db/password"
}
resource "aws_db_instance" "main" {
  password = data.aws_secretsmanager_secret_version.db.secret_string
}

Why Terraform security is special. Terraform sits at the most privileged point in your stack — it holds credentials able to create and destroy your entire cloud, and its state file accumulates every secret those resources touched. Two attack surfaces dominate: the credentials Terraform runs with (if compromised, an attacker owns your cloud) and the state file (if readable, an attacker harvests every password in plaintext). Everything below reduces those two exposures.

Why secrets end up in state — and what to actually do

When you pass a secret into any resource attribute, the provider returns that resource's full attribute set after apply, and Terraform records it in state verbatim, unencrypted within the JSON. Referencing a secret from Secrets Manager instead of hardcoding it keeps the secret out of your .tf files and Git — a real improvement — but the resolved value still lands in state. There is no way to pass a secret to a resource and keep it out of state. So the defenses are: (1) encrypt state at rest and lock down who can read the state bucket; (2) prefer having the cloud generate/manage the secret so Terraform never sees it (e.g., manage_master_user_password for RDS, which stores it directly in Secrets Manager); (3) rotate anything that did pass through.

Better: let the cloud manage the secret so it never enters state
resource "aws_db_instance" "main" {
  # No password attribute at all — AWS generates & stores it in Secrets Manager.
  manage_master_user_password = true
  username                    = "admin"
  # Terraform state never contains the password; apps read it from Secrets Manager.
}
Proving a secret is sitting in state (why access control matters)
$ terraform state show aws_db_instance.main | grep -i password
    password = "SuperSecret123!"        # plaintext in state — anyone with
                                        # read access to the state bucket sees this
# Mitigations: encrypt=true on the backend, tight S3 bucket policy/IAM,
# bucket versioning off public, and rotation.
Layered Terraform security
  • Least-privilege apply role — the CI apply identity gets only the permissions this stack needs, not cloud admin. Separate read-only plan role from write apply role.
  • Encrypt + lock down state — encrypt = true, strict bucket IAM, no public access; treat state as a secret store.
  • Never hardcode — pull secrets at runtime or let the cloud manage them; keep them out of .tf and .tfvars in Git.
  • Scan every plan — tfsec/Checkov in CI to catch public buckets, open security groups, unencrypted volumes before apply (§27).
  • OIDC over static keys for CI auth (§14).
Classic security mistakes
  • Committing terraform.tfstate or a .tfvars full of secrets to Git. Both leak plaintext secrets into history forever (rotate immediately if it happens).
  • Relying on sensitive = true for protection. It only hides console output; the value is still in state.
  • Giving Terraform a permanent cloud-admin key. Scope it down and make it temporary.
  • Logging plan/apply output containing secrets in CI. Redact and restrict CI log access.
State is a filing cabinet full of copies of your keys

Every time Terraform makes something that needs a password, it quietly files a photocopy of that password in its cabinet (state). Marking a value "sensitive" just means it isn't read aloud in the room — the photocopy is still in the drawer. So the real job is: lock the cabinet (encrypt + restrict access), and where possible let the bank hold the key instead of you (cloud-managed secrets).

17. Drift, Import & Refactoring

Reality diverges from code (someone clicked in the console = drift). And you'll need to bring existing resources under management, or restructure without destroying.

Detect drift, import, and safely refactor
terraform plan                       # a non-empty plan on unchanged code = drift

# Bring an existing resource under Terraform management:
terraform import aws_s3_bucket.legacy my-existing-bucket
# (or use an import block, Terraform 1.5+):
#   import { to = aws_s3_bucket.legacy, id = "my-existing-bucket" }

# Rename/move a resource in state WITHOUT destroy+recreate:
terraform state mv aws_instance.old aws_instance.new
# Or declaratively with a moved block (preferred, reviewable):
#   moved { from = aws_instance.old, to = aws_instance.new }
Use moved blocks, not just state mv

When you rename resources or extract a module, add a moved { } block. It's committed to Git, reviewable, and applied automatically — so teammates and CI refactor state the same way you did, with zero destroy/recreate.

Why these operations exist. Three realities force you off the happy path. (1) Drift: the real world diverges from code because someone clicked in the console or another tool changed a resource. (2) Brownfield: you adopt Terraform on infrastructure that already exists and was built by hand — you must import it into state without recreating it. (3) Refactoring: you rename a resource, split a module, or reorganize — and you need to update state's bookkeeping without destroying and recreating live infrastructure. Each has a purpose-built, safe mechanism.

How import and drift detection work under the hood

Drift is discovered during the refresh phase of a plan: Terraform reads each resource's current attributes from the cloud and compares them to state. If reality differs (an S3 bucket that's now public, a tag someone removed), the plan shows the difference even though your code didn't change. Import works the other direction: given a resource address and a real-world id, Terraform calls the provider's read API for that id, writes the resulting attributes into state, and now "adopts" the resource — but importantly it does not write your .tf file; you must author matching HCL yourself (or use -generate-config-out in modern Terraform). If your HCL doesn't match the imported reality, the very next plan proposes changes to reconcile them.

Adopting existing infra: import block + generated config (Terraform 1.5+)
import {
  to = aws_s3_bucket.legacy
  id = "my-existing-bucket"          # the real-world identifier
}
# Then generate matching HCL automatically:
#   terraform plan -generate-config-out=generated.tf
Import in action, then verifying zero changes
$ terraform plan            # with the import block present
Terraform will perform the following actions:
  # aws_s3_bucket.legacy will be imported
    resource "aws_s3_bucket" "legacy" {
        bucket = "my-existing-bucket"
        id     = "my-existing-bucket"
    }
Plan: 1 to import, 0 to add, 0 to change, 0 to destroy.

$ terraform apply           # after apply, run plan again — the goal:
$ terraform plan
No changes. Your infrastructure matches the configuration.   # HCL matches reality ✓
Refactoring safely: moved block instead of destroy/recreate
# You renamed aws_instance.web -> aws_instance.app_server.
# WITHOUT this block, Terraform destroys "web" and creates "app_server".
moved {
  from = aws_instance.web
  to   = aws_instance.app_server
}
# With it: plan shows a rename in state, 0 to add/destroy.
Drift / import / refactor gotchas
  • Applying without checking drift first can silently revert a colleague's emergency console fix. Read the refresh diff before applying.
  • Importing without writing matching HCL → the next plan wants to change or replace the resource to match your (incomplete) config. Verify you reach "No changes."
  • state mv vs moved block: state mv is a manual, unrecorded action only you ran; teammates and CI don't know. A moved block is committed and self-applies for everyone. Prefer the block.
  • Import doesn't import dependencies. Importing an instance doesn't import its security groups or subnet; you import (or already manage) each resource individually.
  • Deleting a resource block to "stop managing" it destroys it. To stop managing without deleting, use terraform state rm or a removed block (§28).
Import = adopting a stray; moved = updating the address book

Import is adopting a pet that already exists — you register it as yours (state) but you also have to describe it accurately (HCL) or the vet records won't match. moved is when a resource just changes its name/address in your records: the same pet, relabeled, not a new pet bought to replace one you put down (destroy/recreate). Drift is coming home to find someone rearranged your furniture — Terraform notices and asks whether to put it back.

Automated drift detection

Manually running terraform plan to spot drift doesn't scale. Mature teams run a scheduled drift check in CI that alerts when reality no longer matches code — so an out-of-band console change is caught in hours, not discovered during your next deploy.

A scheduled drift-detection job (CI, runs nightly)
# terraform plan -detailed-exitcode returns:
#   0 = no changes (no drift)   1 = error   2 = changes present (DRIFT!)
terraform init -input=false
terraform plan -detailed-exitcode -lock=false -out=drift.tfplan
code=$?
if [ "$code" -eq 2 ]; then
  echo "::warning:: Infrastructure drift detected — reality differs from code"
  terraform show -no-color drift.tfplan | mail -s "TF drift in prod" oncall@acme.io
  exit 1        # fail the scheduled job so it pages / opens a ticket
fi
Close the drift loop
  • Schedule a drift check (nightly cron / scheduled pipeline) per environment.
  • Alert on exit code 2; attach the plan so reviewers see exactly what drifted.
  • Prevent drift at the source: remove human write access to prod consoles (IAM), so the only path to change is a reviewed Terraform PR.
  • Tools like driftctl, Terraform Cloud drift detection, or purpose-built detectors formalize this — but the -detailed-exitcode pattern above works anywhere.

Provision vs configure

Terraform provisions infrastructure (creates the servers, networks, databases). Ansible configures what runs inside (installs packages, sets up services). They're complementary: Terraform builds the house, Ansible furnishes it. In containerized worlds, the "furnishing" often moves into the Docker image instead.

Why the ecosystem matters when choosing. The tools above differ along two axes that determine fit: declarative vs imperative (do you describe the end state or the steps?) and DSL vs general-purpose language (a purpose-built config language like HCL, or real code like Python). Terraform sits at declarative + DSL, which is why it's approachable and safe for the majority — but knowing the trade-offs helps you spot when a different tool genuinely fits better.

How to actually choose

  • Multi-cloud or many SaaS providers, standard team? Terraform/OpenTofu. The widest provider ecosystem and the most examples/hiring pool.
  • Want real loops, unit tests, and abstractions in a language you already use? Pulumi (separate engine) or CDKTF (§30, keeps Terraform's engine). Best when generation logic is complex.
  • All-in on one cloud and want native drift/rollback? That cloud's native tool (CloudFormation/CDK on AWS, Bicep on Azure) integrates deepest, at the cost of portability.
  • GitOps shop already living in Kubernetes? Crossplane models cloud resources as Kubernetes CRDs so your existing K8s reconcilers manage cloud infra too.
  • Configuring inside servers (packages, files, services)? That's config management (Ansible), not provisioning — pair it with Terraform, don't replace one with the other.
Ecosystem gotchas
  • Mixing tools that fight over the same resources. If Terraform and CloudFormation both "own" the same bucket, each will try to undo the other. Draw clear ownership boundaries per resource.
  • Choosing a general-purpose-language tool "because loops." Real languages also invite real complexity (dependency hell, arbitrary logic in infra). Most teams don't need it; start with HCL and graduate only on a concrete need.
  • Assuming Ansible replaces Terraform (or vice versa). They solve different layers. Using Ansible to create cloud resources or Terraform provisioners to configure servers usually leads to fragile setups.
Different vehicles for different roads

Terraform is a reliable all-terrain truck that goes anywhere (any cloud). Cloud-native tools are like a car built for one city's roads — smoother there, useless elsewhere. Pulumi/CDKTF are a truck you can heavily customize with your own engineering. Ansible isn't a vehicle at all — it's the crew that unloads and sets up whatever the truck delivered.

19. Functions & Expressions

HCL is more than key-value pairs — it has a rich expression language with built-in functions, conditionals, and loops. Mastering it is what separates copy-paste Terraform from elegant, DRY configuration.

Expressions = the "smart" part of your config

Without expressions, every value is hardcoded and you repeat yourself endlessly. Expressions let a value be computed: "the bucket name is the environment plus a suffix," "create a rule for each port in this list," "use this value if prod, otherwise that one." Think of them as spreadsheet formulas for infrastructure — one source of truth that derives everything else.

Built-in function categories

Real-world expression patterns
# Conditional (ternary) — pick a value based on environment
instance_type = var.environment == "prod" ? "m5.large" : "t3.micro"

# for expression — transform a list into a map
locals {
  user_roles = { for u in var.users : u.name => u.role }
}

prod_subnets = [for s in var.subnets : s.id if s.env == "prod"]

# Splat — pull one attribute from every resource instance
all_ips = aws_instance.web[*].private_ip

# jsonencode — never hand-write JSON for IAM policies
assume_role_policy = jsonencode({
  Version = "2012-10-17"
  Statement = [{ Action = "sts:AssumeRole", Effect = "Allow",
                 Principal = { Service = "ec2.amazonaws.com" } }]
})

# cidrsubnet — derive subnet CIDRs from a base VPC CIDR

# templatefile — render a script with variables injected
user_data = templatefile("${path.module}/init.sh.tftpl", { app_port = var.port })
Test expressions instantly with terraform console

Run terraform console for an interactive REPL. Type cidrsubnet("10.0.0.0/16", 8, 3) or [for i in range(3) : i * 2] and see the result immediately — the fastest way to learn functions and debug complex expressions without running a plan.

Why expressions matter. The difference between fragile copy-paste Terraform and maintainable Terraform is deriving values instead of repeating them. If your subnet CIDRs, resource names, and tags are all computed from a couple of inputs, then changing an environment name or CIDR base updates everything consistently. Expressions are how you enforce a single source of truth inside a config.

How expressions are evaluated (and why "known after apply" appears)

Terraform evaluates expressions during the plan phase, as part of building the graph. Every expression has a value and a "known-ness." Inputs, locals, and literals are known immediately. But anything derived from a resource attribute that the cloud hasn't assigned yet (an id, an ARN) is known after apply — Terraform tracks it as an unknown placeholder, propagates that unknown-ness through any expression that uses it, and fills in the real value post-apply. This is why an expression like "${aws_instance.web.id}-suffix" shows as (known after apply) in the plan: one unknown input makes the whole result unknown until apply. It's also why for_each keys can't depend on such values — the set of keys must be known to build the graph.

Watching an expression resolve in terraform console
$ terraform console
> cidrsubnet("10.0.0.0/16", 8, 3)
"10.0.3.0/24"
> [for p in [80, 443] : "tcp/${p}"]
[
  "tcp/80",
  "tcp/443",
]
> { for u in ["alice","bob"] : u => upper(u) }
{
  "alice" = "ALICE"
  "bob"   = "BOB"
}
> merge({ env = "prod" }, { team = "payments" })
{
  "env"  = "prod"
  "team" = "payments"
}
Worked example: derive everything from two inputs
variable "environment" { default = "prod" }
variable "vpc_cidr"    { default = "10.2.0.0/16" }

locals {
  # one source of truth -> consistent names, tags, and subnets everywhere
  name_prefix = "${var.environment}-app"
  common_tags = { Environment = var.environment, ManagedBy = "terraform" }
  azs         = ["a", "b", "c"]
  subnets     = { for i, az in local.azs : az => cidrsubnet(var.vpc_cidr, 8, i) }
  #  => { a = "10.2.0.0/24", b = "10.2.1.0/24", c = "10.2.2.0/24" }
}
Expression gotchas
  • Overly clever one-liners. A triple-nested for with conditionals no one can read is a liability. Break complex logic into named locals with comments.
  • lookup/index on a missing key errors at plan time. Use lookup(map, key, default) or try(...) for optional values.
  • Depending on unknown values where they must be known (for_each keys, count) → "Invalid ... argument: value depends on resource attributes that cannot be determined until apply." Key off inputs, not computed ids.
  • Type surprises. "3" + 2-style implicit coercions and list-vs-set confusion cause subtle bugs; test in terraform console.
Expressions = spreadsheet formulas for infrastructure

In a spreadsheet you don't retype a total in ten cells — you write =A1*B1 once and everything updates when A1 changes. Expressions are those formulas for your infra: set the environment name in one cell, and every bucket name, tag, and subnet recomputes itself. "Known after apply" is just a cell whose value is still being fetched — the formula waits for it.

20. Dynamic Blocks & Deep for_each

When a resource needs a variable number of repeated nested blocks (security-group rules, listener rules, tags), dynamic blocks generate them from a collection — eliminating huge amounts of duplication.

Dynamic security-group rules
variable "ingress_ports" { default = [80, 443, 8080] }

resource "aws_security_group" "web" {
  name = "web-sg"
  dynamic "ingress" {
    for_each = var.ingress_ports
    content {
      from_port   = ingress.value
      to_port     = ingress.value
      protocol    = "tcp"
      cidr_blocks = ["0.0.0.0/0"]
    }
  }
}
for_each over a map of objects (the advanced pattern)
variable "buckets" {
  type = map(object({ versioning = bool, acl = string }))
  default = {
    logs    = { versioning = false, acl = "private" }
    backups = { versioning = true,  acl = "private" }
  }
}
resource "aws_s3_bucket" "this" {
  for_each = var.buckets
  bucket   = "myco-${each.key}"        # each.key = "logs"/"backups"
}
resource "aws_s3_bucket_versioning" "this" {
  for_each = { for k, v in var.buckets : k => v if v.versioning }
  bucket   = aws_s3_bucket.this[each.key].id
  versioning_configuration { status = "Enabled" }
}
Don't over-use dynamic blocks

Dynamic blocks hurt readability fast. If a resource always has two or three fixed nested blocks, just write them out. Reserve dynamic for genuinely variable-length, data-driven cases. A config no one can read is a liability, even if it's DRY.

Why dynamic blocks exist. Some resources contain repeated nested blocks — a security group has many ingress blocks, a load balancer many listener rules. You can't put for_each on a nested block the way you do on a resource. Before dynamic, the only option was to hand-write every nested block, so a firewall with 12 rules meant 12 near-identical stanzas. dynamic generates them from a collection instead.

How dynamic blocks and top-level for_each differ under the hood

These operate at two different levels, and confusing them is the top source of bugs here:

  • Top-level for_each creates multiple resource instances, each with its own state key (aws_s3_bucket.this["logs"]). Removing one destroys exactly that one resource.
  • dynamic creates multiple nested blocks inside a single resource instance. The blocks aren't independently addressable in state — they're just the contents of one resource. Changing the collection re-renders all the nested blocks of that one resource in place.

Inside a dynamic "ingress" block, the iterator defaults to the block label: ingress.value is the current element and ingress.key its key. You can rename it with iterator = x. The for_each inside a dynamic block can be a list, set, or map, and you can filter it with a for expression — the pattern that powers conditional and data-driven nested blocks.

Rich dynamic block: rules from a map of objects, with a named iterator
variable "ingress_rules" {
  type = map(object({ port = number, cidr = string, desc = string }))
  default = {
    http  = { port = 80,  cidr = "0.0.0.0/0",   desc = "public web" }
    https = { port = 443, cidr = "0.0.0.0/0",   desc = "public web tls" }
    ssh   = { port = 22,  cidr = "10.0.0.0/8",  desc = "internal admin" }
  }
}
resource "aws_security_group" "web" {
  name = "web-sg"
  dynamic "ingress" {
    for_each = var.ingress_rules
    iterator = rule                       # rename iterator for readability
    content {
      description = rule.value.desc
      from_port   = rule.value.port
      to_port     = rule.value.port
      protocol    = "tcp"
      cidr_blocks = [rule.value.cidr]
    }
  }
}
All rules live inside ONE resource (not separate instances)
$ terraform state list | grep web
aws_security_group.web          # a single instance — the 3 ingress blocks
                                # are nested content, not aws_security_group.web["http"]

# Contrast: top-level for_each over buckets makes SEPARATE instances:
aws_s3_bucket.this["logs"]
aws_s3_bucket.this["backups"]
Dynamic / deep for_each gotchas
  • Reordering a list passed to a dynamic block can churn nested blocks; prefer a map (stable keys) over a list where identity matters.
  • Empty collection = zero blocks. A dynamic over an empty list simply emits nothing — handy for optional blocks, but make sure the resource is valid with none.
  • Nested dynamic blocks (dynamic inside dynamic) become nearly unreadable. If you're there, reconsider the data model or split resources.
  • Confusing each and the dynamic iterator. Top-level for_each exposes each.key/each.value; a dynamic block exposes <label>.key/<label>.value. They're different scopes.
Dynamic block = a mail-merge for one document

Top-level for_each prints many separate letters (many resources). A dynamic block is a mail-merge within a single letter — it fills in a repeating table of rows (the nested blocks) inside that one document. Same iteration idea, but one produces many files, the other fills a section of one file.

21. Lifecycle Meta-Arguments

The lifecycle block changes how Terraform creates, updates, and destroys a resource — essential for zero-downtime changes and protecting critical resources.

Meta-argumentWhat it doesUse when
create_before_destroyMake the replacement before deleting the oldZero-downtime replacement (ASGs, instances)
prevent_destroyHard-fail any plan that would destroy thisDatabases, prod state buckets
ignore_changesIgnore drift on specific attributesValues changed outside TF (autoscaling desired_count)
replace_triggered_byForce replace when another resource changesRecreate instance when its config hash changes

Lifecycle in action
resource "aws_db_instance" "main" {
  # ... config ...
  lifecycle {
    prevent_destroy = true            # never let a plan delete prod DB
    ignore_changes  = [password]      # rotated out-of-band; don't fight it
    precondition {
      condition     = var.multi_az || var.environment != "prod"
      error_message = "Production databases must be multi-AZ."
    }
  }
}
prevent_destroy is a seatbelt, not a lock

It stops terraform destroy and destructive plans — but if you remove the resource block from code, Terraform removes the lifecycle rule too and will destroy it. For true protection also use cloud-side deletion protection (RDS deletion protection, S3 bucket policies) as defense in depth.

Why lifecycle rules exist. Terraform's default create/update/destroy behavior is safe for most resources but wrong for some. The default is destroy-then-create on replacement — fine for a stateless instance, catastrophic for something behind live traffic (a gap of downtime) or holding data (a database). And Terraform's insistence on reconciling every attribute fights you when something is legitimately managed elsewhere (an autoscaler adjusting capacity). lifecycle lets you override these behaviors precisely where the defaults don't fit.

How create_before_destroy reorders the graph

Normally, replacing a resource is two graph nodes in sequence: destroy old → create new. With create_before_destroy = true, Terraform inverts that portion of the graph: it creates the replacement first, updates every dependent to point at the new resource, and only then destroys the old one — eliminating the downtime gap. There's a catch: the new and old must coexist briefly, so any unique constraint (a name, an EIP association) must tolerate two existing at once, or the create fails. That's why create_before_destroy often pairs with computed/random names.

ignore_changes works differently: during plan, Terraform simply excludes the listed attributes from the diff, so drift on those attributes is invisible and never "corrected." prevent_destroy is a plan-time assertion that hard-errors if the planned action for that resource is destroy. precondition/postcondition are custom assertions evaluated during plan/apply.

Zero-downtime replacement with create_before_destroy
resource "aws_launch_template" "web" {
  image_id      = data.aws_ami.web.id
  instance_type = "t3.micro"
  lifecycle {
    create_before_destroy = true      # stand up new template before killing old
  }
}
resource "aws_lb_target_group" "web" {
  name_prefix = "web-"                 # prefix, not fixed name -> two can coexist
  port        = 80
  vpc_id      = var.vpc_id
  lifecycle { create_before_destroy = true }
}
ignore_changes prevents fighting an autoscaler
# Without ignore_changes, every plan tries to reset desired_capacity to code's value,
# undoing the autoscaler's scaling decisions:
  ~ resource "aws_autoscaling_group" "web" {
      ~ desired_capacity = 6 -> 2      # TF wants to shrink what autoscaling grew!
    }
# With lifecycle { ignore_changes = [desired_capacity] } that line disappears —
# Terraform manages the ASG but lets scaling own desired_capacity.
Lifecycle gotchas
  • create_before_destroy + fixed unique names → "already exists" errors because both copies briefly need the same name. Use name_prefix or a random suffix.
  • Over-broad ignore_changes (e.g., ignore_changes = all) hides real drift and makes Terraform nearly useless for that resource. Ignore only the specific attributes managed elsewhere.
  • Relying on prevent_destroy alone. It doesn't survive deleting the resource block, and it blocks legitimate planned replacements too (you must temporarily remove it to intentionally replace). Add cloud-side deletion protection.
  • Lifecycle values must be literal. You can't set prevent_destroy = var.is_prod — these meta-arguments don't accept variables. Structure code so the block is present only where needed.
Lifecycle = the fine print on how to handle a resource

By default, replacing something means "throw out the old, then buy new" — a gap where you have neither. create_before_destroy is "buy the new fridge and move the food over before hauling the old one out." ignore_changes is a sticky note saying "the thermostat is set by someone else, don't touch it." prevent_destroy is a "DO NOT SCRAP" label — but a label peels off if you shred the whole appliance record.

22. Provisioners & the Escape Hatch

Provisioners run scripts on the local machine or a remote resource during create/destroy. They're a last resort — powerful but fragile.

Provisioners are a last resort — here's why

HashiCorp explicitly calls provisioners a last resort. They break Terraform's declarative model: they run imperatively, aren't tracked in state, don't show meaningful plans, and a failure taints the whole resource. Prefer: baked images (Packer), cloud-init/user_data, or configuration management (Ansible). Reach for provisioners only when none of those fit.

The three provisioner types
resource "aws_instance" "web" {
  # ... 
  # 1. local-exec: run on the machine running Terraform
  provisioner "local-exec" {
    command = "echo ${self.private_ip} >> inventory.txt"
  }
  # 2. remote-exec: run ON the created resource (needs connection)
  provisioner "remote-exec" {
    inline = ["sudo apt-get update", "sudo apt-get install -y nginx"]
    connection {
      type        = "ssh"
      host        = self.public_ip
      user        = "ubuntu"
      private_key = file("~/.ssh/id_ed25519")
    }
  }
  # 3. file: copy a file to the resource
  provisioner "file" {
    source      = "app.conf"
    destination = "/etc/app.conf"
  }
}
The modern alternative: cloud-init via user_data

For bootstrapping instances, pass a cloud-init script through user_data (rendered with templatefile). It runs on first boot, is idempotent, needs no SSH connection from Terraform, and doesn't taint the resource on failure. This is the declarative, reliable way to do what most people misuse remote-exec for.

Why provisioners are the "escape hatch." Terraform's model is declarative: it knows the desired state and reconciles toward it idempotently. A provisioner runs an arbitrary imperative command that Terraform can't understand, plan, or reconcile — it's a hole punched through the declarative model for the rare case where no provider resource, image, or config tool can do the job. HashiCorp keeps them because that case exists, and labels them a last resort because they undermine everything that makes Terraform safe.

How provisioners behave under the hood — and why "tainting" hurts

Provisioners run during apply, attached to a resource's creation (or, with when = destroy, its deletion). They produce no plan output — you can't preview what a shell command will do. Their effects aren't recorded in state, so Terraform has no memory that they ran or what they changed. Most importantly, if a provisioner fails, Terraform marks the whole resource tainted: it considers the resource incompletely created and will destroy and recreate it on the next apply — even though the underlying VM booted fine. A flaky apt-get over SSH can thus cause your instance to be torn down and rebuilt. Contrast this with user_data/cloud-init, which the cloud runs on first boot: a failure there doesn't taint the Terraform resource, and no SSH connectivity from the Terraform host is required.

The recommended pattern: cloud-init via user_data (declarative)
# init.sh.tftpl (a template file)
#   #!/bin/bash
#   apt-get update && apt-get install -y nginx
#   echo "listen ${app_port};" > /etc/nginx/conf.d/app.conf
#   systemctl restart nginx

resource "aws_instance" "web" {
  ami           = data.aws_ami.ubuntu.id
  instance_type = "t3.micro"
  user_data = templatefile("${path.module}/init.sh.tftpl", { app_port = var.port })
  # No provisioner, no SSH, no taint-on-failure. Runs on first boot.
}
What a failed provisioner does to your resource
$ terraform apply
aws_instance.web: Creating...
aws_instance.web: Provisioning with 'remote-exec'...
aws_instance.web (remote-exec): Connecting via SSH...
╷
│ Error: remote-exec provisioner error: timeout - SSH not responding
╵
# The instance BOOTED FINE, but the provisioner failed, so:
$ terraform plan
-/+ aws_instance.web is tainted, so must be replaced   # destroy + recreate!
Provisioner gotchas
  • Not idempotent. A provisioner runs once on create; it won't re-run to fix drift. Config management (Ansible) or immutable images handle "keep it configured" far better.
  • Taint-on-failure downtime. A transient network blip during remote-exec can trigger a full instance replacement.
  • SSH/WinRM connectivity coupling. remote-exec needs the Terraform host to reach the instance — security groups, keys, bastions all have to line up, adding fragility.
  • local-exec hides side effects. It runs on the CI runner/laptop, so behavior varies by machine and isn't captured in state or plan.
  • Destroy-time provisioners are especially brittle — if the resource is already gone, they can block destroy.
Provisioners = duct tape

Duct tape fixes anything in a pinch, but you don't build a house with it. Provisioners patch over gaps when nothing else fits — but the sturdy alternatives (baked images with Packer, cloud-init, Ansible) are how you build to last. Reach for the duct tape only when the real tools genuinely can't reach.

23. Provider Aliasing & Multi-Region

A single config often spans multiple regions or accounts — a DR region, a global CloudFront + regional backend, or cross-account roles. Provider aliases make this possible.

Aliased providers for multi-region DR
provider "aws" {
  region = "us-east-1"                 # default
}
provider "aws" {
  alias  = "dr"
  region = "eu-west-1"                 # disaster-recovery region
}

resource "aws_s3_bucket" "primary" { bucket = "app-primary" }

resource "aws_s3_bucket" "dr" {
  provider = aws.dr                    # explicitly use the DR provider
  bucket   = "app-dr"
}

# Passing aliased providers into a module:
module "network_dr" {
  source    = "./modules/vpc"
  providers = { aws = aws.dr }
}

Why aliasing exists. A single provider block configures one endpoint — one region, one account, one set of credentials. But real systems span boundaries: a primary region plus a disaster-recovery region, a global service (CloudFront, ACM certs in us-east-1) alongside regional backends, or a security account plus workload accounts. Aliases let one configuration hold multiple configured instances of the same provider so a single plan/apply can span all of them coherently.

How aliased providers work under the hood

Each provider "aws" block (default plus each alias) becomes a distinct provider instance — Terraform launches and configures a separate plugin process (or configuration) per instance, each with its own region/credentials. Every resource is bound to exactly one provider instance: the default unless you set provider = aws.dr. In the dependency graph, provider configuration nodes are dependencies of the resources that use them, and Terraform can drive them all in one graph walk. Modules don't inherit aliases automatically — you must explicitly pass them via the providers = { ... } map, which is how a reusable module gets pointed at a specific region/account by its caller.

Common real pattern: global cert (us-east-1) + regional app
provider "aws" { region = "us-east-1" }          # default = your app region? no—
provider "aws" {
  alias  = "us_east_1"
  region = "us-east-1"                            # CloudFront/ACM must be here
}
provider "aws" {
  region = "eu-west-1"                            # actually the app's home region
}

# ACM cert for CloudFront MUST live in us-east-1, regardless of app region:
resource "aws_acm_certificate" "cdn" {
  provider          = aws.us_east_1
  domain_name       = "app.example.com"
  validation_method = "DNS"
}
resource "aws_s3_bucket" "app" { bucket = "app-eu" }   # uses default eu-west-1
A module that declares which aliased providers it needs
# Inside modules/replicated/versions.tf — declare provider "slots":
terraform {
  required_providers {
    aws = { source = "hashicorp/aws", configuration_aliases = [aws.primary, aws.dr] }
  }
}
# The caller must then fill both slots:
module "replicated" {
  source    = "./modules/replicated"
  providers = { aws.primary = aws, aws.dr = aws.dr }
}
Aliasing gotchas
  • Forgetting the provider argument silently uses the default provider — so a resource you meant for the DR region lands in primary. Always set provider = explicitly for non-default instances.
  • Modules don't inherit aliases. Pass them via providers = {}; a module using aliased providers must declare configuration_aliases.
  • ACM/CloudFront region trap. Certificates for CloudFront must be created in us-east-1 even if your app is elsewhere — a classic reason people first need aliases.
  • Cross-account assume-role config lives per provider instance; mixing up which alias assumes which role sends resources to the wrong account.
Aliases = multiple phone lines on one desk

One provider block is a single phone line to one office (region/account). Aliases give you several labeled lines on the same desk — "primary," "DR," "us-east-1." Each resource picks up a specific line to place its call. Forget to specify the line and you dial the default office — which is how a DR resource accidentally gets built in the wrong place.

24. Terragrunt & DRY at Scale

As you grow to dozens of environments and components, raw Terraform gets repetitive — the same backend config, provider config, and variable wiring copied everywhere. Terragrunt is a thin wrapper that keeps it DRY.

Terragrunt = don't-repeat-yourself for Terraform

Imagine 4 environments × 6 components = 24 folders, each needing near-identical backend and provider blocks. Copy-paste that 24 times and one change means 24 edits. Terragrunt lets you write the boilerplate once and have each component inherit it, passing only what's different. It also runs commands across many components and manages dependencies between them.

terragrunt.hcl — generate backend + inherit config
# root terragrunt.hcl — written ONCE
remote_state {
  backend = "s3"
  generate = { path = "backend.tf", if_exists = "overwrite" }
  config = {
    bucket = "myco-tfstate"
    key    = "${path_relative_to_include()}/terraform.tfstate"
    region = "us-east-1"
    dynamodb_table = "tf-locks"
    encrypt = true
  }
}

# environments/prod/vpc/terragrunt.hcl — thin, per-component
include "root" { path = find_in_parent_folders() }
terraform { source = "../../../modules//vpc" }
inputs = { cidr_block = "10.2.0.0/16", environment = "prod" }
dependency "iam" { config_path = "../iam" }   # wire cross-component deps
When to adopt Terragrunt

Below ~3 environments, plain Terraform with a modules + environments layout (§12) is simpler — don't add the dependency prematurely. Adopt Terragrunt once backend/provider duplication and cross-component orchestration become real pain. Alternatives: Terraform native stacks (newer), or a CI matrix that loops components.

Why Terragrunt exists. Terraform has two structural weaknesses at scale that it can't solve itself. First, the backend block can't use variables (it's read before variable evaluation), so every one of your dozens of components repeats a nearly identical backend block — with only the state key differing. Second, Terraform has no built-in way to orchestrate multiple root modules: to apply network-then-platform-then-apps in order, or run plan across 20 components at once. Terragrunt is a thin wrapper that generates the boilerplate and orchestrates the components.

How Terragrunt works under the hood

Terragrunt is a separate binary that wraps the terraform CLI. For each component you write a small terragrunt.hcl. When you run terragrunt apply, it: (1) reads your config and any included parent configs, (2) generates real .tf files (like backend.tf) into a scratch .terragrunt-cache directory with the computed values filled in (e.g., a per-component state key derived from the folder path), (3) copies your module source there, then (4) shells out to plain terraform in that directory. dependency blocks pull another component's outputs (by running its state), letting Terragrunt build a dependency graph across separate state files and apply them in order with run-all. So Terraform still does all the real work — Terragrunt just assembles the inputs and sequences the runs.

Orchestrating many components with run-all
$ terragrunt run-all plan          # plan EVERY component, in dependency order
Group 1: environments/prod/iam
Group 2: environments/prod/vpc      (depends on iam)
Group 3: environments/prod/eks      (depends on vpc)
# Terragrunt computes the DAG across components and runs groups in order.

$ terragrunt run-all apply          # apply all, respecting dependencies
The generated backend Terragrunt writes for you
# .terragrunt-cache/.../backend.tf  (GENERATED — you never wrote this)
terraform {
  backend "s3" {
    bucket         = "myco-tfstate"
    key            = "prod/vpc/terraform.tfstate"   # derived from folder path
    region         = "us-east-1"
    dynamodb_table = "tf-locks"
    encrypt        = true
  }
}
# You wrote the S3 details ONCE in the root terragrunt.hcl; every component
# gets a correct, unique key with zero copy-paste.
Terragrunt gotchas
  • Premature adoption. For 1–2 environments it adds a tool, a config language layer, and a learning curve for little gain. Start with plain Terraform (§12).
  • Extra indirection when debugging. Errors surface from generated files in .terragrunt-cache; you must know the generation happened to trace them.
  • dependency outputs at plan time. If a dependency hasn't been applied yet, its outputs don't exist — use mock_outputs for first-time planning or apply dependencies first.
  • Version coupling. Terragrunt tracks Terraform versions; a mismatch can break generation. Pin both.
  • It's third-party. Evaluate against newer native options (Terraform Stacks) before committing an org to it.
Terragrunt = a stencil + a conductor

The stencil: instead of hand-drawing the same backend box on 24 pages, you cut one stencil and trace it everywhere, changing only the label. The conductor: instead of playing each instrument (component) yourself in the right order, one baton (run-all) cues network, then platform, then apps in sequence. Terragrunt is both — it removes the copy-paste and it keeps time.

25. Policy as Code — Sentinel & OPA

At scale you need automated guardrails: "no public S3 buckets," "only approved instance types," "every resource must be tagged." Policy-as-code enforces these on every plan, before apply.

ToolStyleNotes
SentinelHashiCorp's policy languageNative to Terraform Cloud/Enterprise
OPA / ConftestRego language, open sourceWorks anywhere; also used in Kubernetes
Checkov / tfsec / TerrascanPre-built security rulesFastest to adopt; scan plan or code
OPA/Rego — deny public S3 buckets (Conftest)
package terraform.analysis
deny[msg] {
  r := input.resource_changes[_]
  r.type == "aws_s3_bucket_acl"
  r.change.after.acl == "public-read"
  msg := sprintf("S3 bucket %v must not be public-read", [r.address])
}

Why policy-as-code exists. Human review doesn't scale as a guardrail: reviewers miss things, standards live in wiki pages nobody reads, and "please always encrypt volumes" is forgotten under deadline pressure. Policy-as-code turns organizational rules into executable checks that run automatically on every plan and block non-compliant changes before apply — so "no public S3 buckets" or "everything must be tagged with a cost-center" is enforced by a machine, consistently, on every PR, not by hope.

How policy engines inspect a plan under the hood

The key insight: policies don't read your HCL — they read the machine-readable plan. You run terraform plan -out=tfplan then terraform show -json tfplan, which emits a JSON document describing every proposed change: for each resource, its type, address, and the change.after state (what it will look like post-apply). The policy engine (OPA/Conftest, Sentinel, Checkov) loads this JSON and evaluates rules against it. A rule is essentially "find any resource change where X is true, and if found, deny with a message." Because it inspects the computed plan, it catches values that only exist after expression evaluation — not just literals in your source.

Wiring a policy gate into the pipeline
$ terraform plan -out=tfplan
$ terraform show -json tfplan > plan.json      # the machine-readable plan
$ conftest test --policy ./policies plan.json  # evaluate Rego rules

FAIL - plan.json - terraform.analysis - S3 bucket aws_s3_bucket_acl.logs
       must not be public-read
1 test, 0 passed, 1 failure
$ echo $?
1                                              # non-zero -> CI blocks the apply
A tagging-governance rule (deny untagged resources)
package terraform.analysis

required_tags := {"Environment", "Owner", "CostCenter"}

deny[msg] {
  r := input.resource_changes[_]
  r.type == "aws_instance"
  provided := {k | r.change.after.tags[k]}
  missing  := required_tags - provided
  count(missing) > 0
  msg := sprintf("%v is missing required tags: %v", [r.address, missing])
}
Policy-as-code gotchas
  • Analyzing source instead of the plan. Tools that only scan .tf files miss values produced by variables/expressions/modules. Evaluate the plan JSON to see what will actually be created.
  • Advisory vs mandatory confusion. Sentinel has enforcement levels (advisory/soft-mandatory/hard-mandatory); a rule set to "advisory" warns but doesn't block. Know which level each rule is at.
  • Over-strict rules block everything. Roll out new policies in warn-only mode first, measure violations, then flip to blocking — or you'll wedge every pipeline on day one.
  • Policies drift from reality. Rules referencing old resource types/attributes silently pass or error after provider upgrades. Test your policies like code.
  • Pre-built scanners ≠ your policies. Checkov/tfsec catch generic security issues; org-specific rules (naming, cost-center tags, approved regions) you still write yourself.
Policy-as-code = an automatic building inspector

Before a construction crew pours concrete, an inspector checks the plans against code: proper exits, no wiring near water. Policy-as-code is that inspector for your infrastructure plan — it reads exactly what you're about to build and stamps APPROVED or REJECTED automatically, every time, so unsafe designs never get built. No relying on a busy reviewer to remember every rule.

26. State Surgery

Sometimes you must operate on state directly — inspecting it, moving resources, removing items Terraform should forget, or replacing a corrupted resource. These are sharp tools; use them deliberately.

The state subcommands
terraform state list                     # every resource in state
terraform state show aws_instance.web    # full attributes of one resource
terraform state mv aws_instance.a aws_instance.b   # rename/move (prefer 'moved' blocks)
terraform state rm aws_instance.old      # forget a resource (does NOT destroy it)
terraform state pull > backup.tfstate    # download a backup before surgery
terraform taint aws_instance.web         # (older) mark for recreation
terraform apply -replace=aws_instance.web# (modern) force-replace one resource
Always back up state before surgery

terraform state pull > backup.json before any mv/rm. State operations are not automatically reversible, and with remote state you can corrupt the shared source of truth for the whole team. Never edit the state JSON by hand — use the subcommands, which keep it internally consistent.

state rm vs destroy

state rm makes Terraform forget a resource — the real infrastructure keeps running, now unmanaged. Useful when handing a resource to another config/team. destroy actually deletes it. Confusing the two is a classic cause of orphaned resources or accidental deletions.

Why state surgery is sometimes unavoidable. State is a model of reality, and models can get out of sync in ways normal plan/apply can't fix: you split one config into two and need to move resources between their states; a resource in state was deleted out-of-band and Terraform keeps trying to update a ghost; you're migrating from count to for_each and the keys must change; two teams need to divide ownership of existing infra. These require operating directly on the state's bookkeeping — carefully, because you're editing the source of truth for what Terraform believes exists.

How each state command changes the model (not the cloud)

The crucial mental separation: most state commands change Terraform's record, not the real infrastructure. state rm deletes an entry from state — the cloud resource keeps running, now unmanaged (an orphan or a hand-off). state mv renames/relocates an entry's address (within a state, into a module, or with -state-out into a different state file) — again the real resource is untouched, only its label changes. state pull/push download/upload the whole state blob. The one that does touch reality is apply -replace (formerly taint): it marks a resource for destroy-and-recreate on the next apply. Modern Terraform also offers declarative equivalents — the moved block (for renames) and the removed block (to stop managing without destroying) — which are reviewable in Git, unlike ad-hoc CLI surgery.

A safe surgery workflow: back up, act, verify
# 1. ALWAYS back up first
$ terraform state pull > backup-$(date +%s).tfstate

# 2. Example: move a resource into a newly-extracted module
$ terraform state mv aws_vpc.main module.network.aws_vpc.main
Move "aws_vpc.main" to "module.network.aws_vpc.main"
Successfully moved 1 object(s).

# 3. Verify the intent: this should show NO create/destroy, just a clean plan
$ terraform plan
No changes. Your infrastructure matches the configuration.   # surgery succeeded ✓
Declarative alternatives (preferred — reviewable, self-applying)
# Rename without destroy/recreate:
moved {
  from = aws_vpc.main
  to   = module.network.aws_vpc.main
}

# Stop managing a resource WITHOUT destroying it (Terraform 1.7+):
removed {
  from = aws_s3_bucket.handed_off
  lifecycle { destroy = false }     # forget it, don't delete it
}
State surgery gotchas — this is the sharp end
  • No backup = no undo. state rm/mv aren't automatically reversible; on remote state you can corrupt the whole team's source of truth. Always state pull > backup first.
  • state rm then re-add without import → Terraform thinks the resource is new and tries to create a duplicate (name clash) or, if you deleted the block, nothing manages it anymore.
  • Editing state JSON by hand. One wrong bracket or serial number desyncs the lineage/serial and every future operation errors. Use the subcommands only.
  • Surgery while others can apply. Do it with the state locked and teammates paused; a concurrent apply mid-surgery is disaster.
  • taint is deprecated in favor of terraform apply -replace=ADDR — clearer and shown in the plan before it happens.
State surgery = editing the library catalog, not the books

The catalog says which shelf each book is on. state mv updates a catalog card when a book moves shelves — the book itself doesn't change. state rm removes the card, so the library "forgets" it owns that book, but the book stays on the shelf. Only apply -replace actually pulps and reprints a book. And you'd photocopy the whole catalog before rearranging it — because a mangled catalog means nobody can find anything.

27. Large-Scale Architecture

How teams structure Terraform for hundreds of resources across many teams: small blast radius, clear ownership, fast plans.

Reading another layer's outputs
data "terraform_remote_state" "network" {
  backend = "s3"
  config  = { bucket = "myco-tfstate", key = "prod/network/terraform.tfstate", region = "us-east-1" }
}
resource "aws_instance" "app" {
  subnet_id = data.terraform_remote_state.network.outputs.private_subnet_ids[0]
}
Large-scale principles
  • Small state files — split by layer + environment + component; faster plans, smaller blast radius.
  • Explicit outputs as the contract between layers; avoid one giant state.
  • Versioned modules from a private registry; teams consume, don't fork.
  • CODEOWNERS + policy-as-code so each team owns its layer with guardrails.
  • Automated CI (plan on PR, gated apply) — no laptop applies at scale.

Why layering matters at scale. A single giant state for the whole company has three fatal properties: plans get painfully slow (Terraform refreshes every resource), the blast radius is total (one mistake can touch everything), and there's no ownership boundary (every team can break every other team). Layering splits infrastructure into independent states ordered by how fast they change and who owns them — foundation (rarely changes, platform team) at the bottom, applications (change daily, product teams) at the top. Each layer plans in seconds, fails in isolation, and has a clear owner.

How layers communicate under the hood

Layers are separate Terraform configurations with separate state files, so they can't reference each other's resources directly. The contract between them is outputs: a lower layer outputs the facts an upper layer needs (subnet IDs, cluster endpoint, security group IDs), and the upper layer reads them via a terraform_remote_state data source, which literally downloads the lower layer's state file and exposes its outputs map. The dependency is read-only and one-directional — apps read platform, platform reads network, network reads foundation — which is exactly what keeps a mistake in one layer from cascading downward. (An alternative to reading remote state directly is looking resources up by tag with data sources, decoupling layers even from each other's state format.)

The layered directory + state layout
live/
  foundation/  → state key: foundation/terraform.tfstate   (org, IAM, DNS zones)
  network/     → state key: network/terraform.tfstate      (reads foundation)
  platform/    → state key: platform/terraform.tfstate     (reads network)
  apps/
    payments/  → state key: apps/payments/terraform.tfstate (reads platform)
    checkout/  → state key: apps/checkout/terraform.tfstate

# Each has its own backend key → its own state → its own fast, isolated plan.
$ cd live/apps/payments && terraform plan   # refreshes only payments' resources
Producing the contract in the network layer
# live/network/outputs.tf — what higher layers are allowed to depend on
output "private_subnet_ids" { value = aws_subnet.private[*].id }
output "vpc_id"             { value = aws_vpc.this.id }
# These outputs are the STABLE INTERFACE. Change resources freely underneath
# as long as the outputs keep their meaning — just like a function signature.
Large-scale gotchas
  • Over-splitting. Too many tiny layers means dozens of applies to ship one change and painful cross-layer coordination. Split by rate of change and ownership, not arbitrarily.
  • Circular layer dependencies. If apps' outputs feed back into network, you've broken the one-directional contract and created an unresolvable apply order. Keep the flow strictly downward.
  • Tight coupling via terraform_remote_state. Reading another layer's state couples you to its internal output names; renaming an output breaks consumers. Treat outputs as a versioned public API, or decouple via tag-based data-source lookups.
  • Applying layers out of order. Apply a new network change before the app that needs it, or you'll reference an output that doesn't exist yet. Orchestrate order (CI pipeline or Terragrunt run-all).
  • Shared mutable state between teams. Two teams writing one state reintroduces the coupling layering was meant to remove.
Layers = floors of a building

You build the foundation, then floor 1, then floor 2 — each rests on the one below and you never build upward before the lower floor exists. The plumbing coming up through the floor is the "outputs" contract: floor 2 taps into pipes floor 1 exposes. Renovating floor 3 (an app) doesn't require touching the foundation, and a fire on floor 3 doesn't collapse the basement. One giant open warehouse (single state) has none of that safety — a problem anywhere is a problem everywhere.

28. CDKTF & Programmatic IaC

The Cloud Development Kit for Terraform (CDKTF) lets you define infrastructure in TypeScript, Python, Go, Java, or C# instead of HCL — using real loops, classes, and tests while still generating Terraform under the hood.

CDKTF in Python (excerpt)
from cdktf import App, TerraformStack
from imports.aws import AwsProvider, s3

class MyStack(TerraformStack):
    def __init__(self, scope, ns):
        super().__init__(scope, ns)
        AwsProvider(self, "aws", region="us-east-1")
        # real Python loop generating resources
        for env in ["dev", "staging", "prod"]:
            s3.S3Bucket(self, f"bucket-{env}", bucket=f"myco-{env}")

app = App(); MyStack(app, "infra"); app.synth()
HCL vs CDKTF vs Pulumi — choosing

HCL is the standard: simplest, most examples, best for most teams. CDKTF suits teams who want real programming constructs but to keep the Terraform provider ecosystem & state model. Pulumi is a fully separate tool (real languages, own engine). Rule of thumb: start with HCL; reach for CDKTF/Pulumi only when you genuinely need programmatic generation or want infra in your app language. Don't add the complexity without a concrete reason.

Why CDKTF exists. HCL is deliberately limited — it's a configuration language, not a programming language. That's a feature for most infra, but occasionally you hit real walls: you want proper classes and inheritance to model resources, unit tests in a framework your team knows, complex generation logic (build resources from an external API response), or you simply want infrastructure to live in the same TypeScript/Python/Go codebase as the app. CDKTF lets you write infrastructure in a full programming language while keeping Terraform's proven engine, provider ecosystem, and state model underneath.

How CDKTF works under the hood — it's a code generator

CDKTF does not replace Terraform; it generates HCL's JSON form and then hands it to Terraform. The flow: you write code using constructs (App, TerraformStack, resource classes). Running cdktf synth executes your program, and each construct's constructor records a resource into an in-memory tree; CDKTF serializes that tree to cdk.tf.json (valid Terraform JSON). From there, cdktf deploy just runs terraform init/plan/apply on that generated file. The provider classes you import are themselves auto-generated from the same provider schemas Terraform uses (via cdktf get). So your Python loop isn't magic at apply time — it ran during synth to generate static Terraform, which Terraform then plans and applies exactly as if you'd hand-written it. State, locking, and the plan/apply safety net are all identical to normal Terraform.

The CDKTF workflow — synth generates Terraform, then deploy runs it
$ cdktf get            # generate typed provider bindings from schemas
$ cdktf synth          # RUN your program -> emit cdktf.out/stacks/infra/cdk.tf.json
$ cat cdktf.out/stacks/infra/cdk.tf.json   # it's just Terraform JSON!
{ "resource": { "aws_s3_bucket": {
    "bucket-dev":  { "bucket": "myco-dev"  },
    "bucket-prod": { "bucket": "myco-prod" } } } }
$ cdktf deploy         # under the hood: terraform init && apply on that JSON
$ cdktf diff           # under the hood: terraform plan
CDKTF gotchas
  • You now debug two layers. A problem could be in your code, in synth/generation, or in the resulting Terraform. Reading the generated JSON is a routine debugging step — the abstraction leaks.
  • Smaller ecosystem & fewer examples. Most Terraform answers online are HCL; you translate. Provider docs are HCL-first.
  • Real language = real complexity. Loops, inheritance, and dependencies (npm/pip) invite the same over-engineering IaC tried to avoid. Just because you can put arbitrary logic in infra doesn't mean you should.
  • State/refactor still applies. Renaming a construct changes the generated resource address → destroy/recreate. You still need moved-block thinking; the language doesn't save you from Terraform's identity rules.
  • Version skew between CDKTF, the language bindings, and Terraform itself can break synth. Pin all three.
CDKTF = a fancy pasta machine that still makes Terraform pasta

You feed in dough shaped by your favorite tools (TypeScript/Python), and the machine (synth) presses out the same standard pasta Terraform always cooks (HCL/JSON). The kitchen (Terraform engine, state, plan/apply) is unchanged — you just prepared the dough with power tools instead of by hand. Great if you have a lot of dough to shape; overkill if you only need one bowl.

That's the full range a lead engineer uses. The reference sections below stay handy for day-to-day work.

29. Best Practices — the checklist

Production Terraform checklist
  • Remote state with locking + encryption; one state per env+component.
  • Pin provider and module versions.
  • Everything through CI: plan on PR, gated apply on merge, OIDC auth.
  • Security-scan every plan (tfsec/Checkov); never hardcode secrets.
  • Modules for anything used more than once; keep them small and versioned.
  • fmt + validate + tflint in pre-commit hooks.
  • Tag every resource (owner, env, cost-center) for accountability and cost tracking.
  • Prefer for_each and moved/import blocks for safe, reviewable change.

30. Troubleshooting Playbook

"Error acquiring the state lock"

A previous run crashed or someone is applying. Confirm no one else is running, then terraform force-unlock <LOCK_ID>. Never force-unlock during an active apply.

Plan wants to destroy/recreate a resource unexpectedly

A "ForceNew" attribute changed (e.g., an AZ, name). Read which attribute triggers it in the plan. Use create_before_destroy lifecycle to avoid downtime, or reconsider the change.

Drift: plan shows changes on code you didn't touch

Someone changed it in the console. Either revert the console change, or update your code to match and apply. Prevent it by removing console write access in prod.

Provider/version errors after pulling teammate's code

Run terraform init -upgrade. Commit the .terraform.lock.hcl lock file so everyone resolves identical provider versions.
