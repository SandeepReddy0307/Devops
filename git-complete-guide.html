1. What is Git?

Before any commands, understand what Git is and why virtually every software team on earth uses it.

Git is a version control system — a tool that tracks every change to your files over time, lets you return to any earlier version, and lets many people work on the same project safely. It was created in 2005 by Linus Torvalds (who also created Linux) to manage the Linux kernel's code. Today it's the world standard: GitHub, GitLab, and Bitbucket are all built on Git.

Analogy: Git is like an infinite undo button with named save points for an entire folder of files — plus the ability to make parallel "what if" copies and later combine the best parts. Microsoft Word's "track changes" is a distant cousin; Git is that idea made vastly more powerful and built for teams.

Why should a beginner care?

Three everyday problems Git solves that you've probably felt:

  • "I broke it and can't get back to when it worked." Git lets you jump back to any saved version instantly.
  • "report_final_v2_FINAL_reallyfinal.docx" — the mess of copies. Git keeps one folder with a clean, labeled history instead.
  • "We both edited the same file and overwrote each other." Git merges everyone's work and flags any real conflicts.

Why Git specifically (vs older tools)

FeatureWhat it means for you
DistributedEvery person has the full history on their own computer — you can work offline, and there's no single point of failure.
FastMost operations happen locally, so they're instant.
Branching is cheapCreating a parallel line of work takes a millisecond — this enables modern team workflows.
Snapshots, not diffsGit remembers the whole state at each save point, making history reliable and integrity-checked.
UniversalIt's the industry standard — learn it once, use it everywhere, forever.
Git vs GitHub — a crucial distinction

People mix these up constantly. Git is the tool that runs on your computer and tracks versions. GitHub (and GitLab, Bitbucket) is a website/service that hosts Git repositories online so teams can share them. You can use Git with no internet at all; GitHub just adds a shared home for your project in the cloud. This guide teaches Git — those skills work with any host.

WHY Git exists — the problem it was born to solve

In 2005 the Linux kernel team lost free access to the proprietary tool (BitKeeper) they'd been using. Thousands of developers, spread across the planet, needed to collaborate on millions of lines of code — with no central server they all trusted and while frequently offline. Existing tools were slow, required a constant connection to one central server, and made branching painful. Linus Torvalds built Git in about two weeks around three demands: it had to be fast, fully distributed (everyone owns the complete history), and impossible to silently corrupt. Those three goals explain almost every design decision you'll meet in this guide.

HOW Git works under the hood — it's a content database

Most beginners imagine Git stores a list of file changes ("diffs"). It doesn't. Git is really a tiny key–value database of content. Every time you commit, Git takes the full content of each file, runs it through the SHA-1 hash function, and gets back a 40-character fingerprint like e83c516…. That fingerprint is the file's address in the database. Identical content always produces the identical hash, so Git automatically stores each unique version exactly once, no matter how many places it appears.

There are just four kinds of objects in this database, and everything else (branches, tags, history, merges) is built on top of them:

Why a "hash" address is so clever

Imagine every file's contents ran through a machine that spat out a unique fingerprint. Change one character and the fingerprint changes completely. Git uses that fingerprint as the file's filing-cabinet drawer number. Two files with identical contents get the same drawer, so Git never stores a duplicate — and if anything is tampered with, the fingerprint won't match, so corruption is caught automatically.

ObjectWhat it storesEveryday analogy
blobThe raw contents of one file (no name, no date — just bytes)A photocopied page with no title
treeA directory listing: names + permissions pointing to blobs and other treesA folder's table of contents
commitA pointer to one tree (the whole snapshot) + author + message + parent commit(s)A labelled photo with "who/when/why" and a link to the previous photo
tagA permanent, named pointer to a specific commitAn engraved plaque: "v1.0 shipped here"
Peek inside the object database yourself
# The hash of a commit is shown by git log
git log --oneline -1
# a1b2c3d Add login button

# Ask Git what TYPE that hash is, and what's inside it
git cat-file -t a1b2c3d        # → commit
git cat-file -p a1b2c3d        # → shows the tree hash, parent, author, message

# Follow the "tree" hash to see the folder listing (blobs & sub-trees)
git cat-file -p <tree-hash>
# 100644 blob 9daeafb...    README.md
# 040000 tree 2b3c4d5...    src
The mental model: a chain of photo albums

Picture a photo album (a commit). Each page in it is a full snapshot of every folder (trees) and every file (blobs) at that moment. Every album has a paper clip pointing back to the previous album (its parent). To "time travel," Git just follows the paper clips backwards. Because each album is addressed by a fingerprint of its entire contents, changing even one letter anywhere produces a brand-new fingerprint — which is exactly why Git can guarantee your history hasn't been secretly altered.

"Snapshots, not diffs" — the key insight, worked out

When you commit and only README.md changed, Git makes a new commit and a new tree, but for every unchanged file the new tree just re-uses the same blob hash as before — no copying. So a commit is conceptually a full snapshot, yet storage stays tiny because unchanged content is shared by reference. Diffs (what you see in git diff) are computed on demand by comparing two snapshots; they are not how Git stores anything.

Common early misconceptions
  • "Git stores diffs." No — it stores whole-content snapshots and shares unchanged blobs.
  • "Git and GitHub are the same." No — Git is the offline tool; GitHub is one of many hosting sites (covered below).
  • "A commit saves only the files I changed." A commit references the entire project tree, not just edited files.
  • "Deleting a file removes its history." Old blobs stay in the database, so previous versions remain recoverable.

2. Version Control Explained

Let's make the core idea concrete before touching commands.

Version control records the state of your project at points in time you choose. Each saved point (called a commit) is a labeled snapshot with a message describing what changed. The chain of commits is your project's history — a timeline you can travel along.

What's a "commit"?

A commit is simply a saved snapshot with a note. Think of it as clicking "Save" but also writing a one-line diary entry ("added the login button") and getting a permanent bookmark you can return to. Unlike normal Save — which overwrites the old version — every commit is kept forever. You build your project one commit at a time.

WHY version control beats "save-as" copies

Before version control, people versioned by copying folders: project, project-backup, project-final, project-final-2. This fails in three predictable ways: you can't tell what changed between copies, you can't tell why, and when two people edit copies you have no safe way to recombine them. Version control fixes all three: every commit records the exact change, a message says why, and Git can automatically merge separate lines of work.

HOW a commit chain actually works

Each commit stores the hash of its parent commit. That single backward link is what turns a pile of snapshots into a timeline. "The history" is simply the chain you get by following parent links from wherever you are now. A branch is nothing more than a note holding the hash of the newest commit on one line of work; moving forward means updating that note to point at a new commit whose parent is the old one.

Worked example — build a two-commit history and read it
git init diary && cd diary
echo "day one" > log.txt
git add log.txt
git commit -m "Start diary"          # commit C1 (no parent)

echo "day two" >> log.txt
git commit -am "Add day two"         # commit C2 (parent = C1)

git log --oneline
# b7f2a10 Add day two      ← newest, HEAD points here
# 3c1d9e4 Start diary      ← C2's parent
What the chain looks like
C1 (Start diary)  <----parent----  C2 (Add day two)  <--- HEAD / main
Mental model: an unbreakable "undo history" for a whole folder

Your editor's Undo remembers keystrokes but forgets everything when you close it, and only covers one file. Git's history is Undo for your entire project that never forgets, is labelled with human notes, and can be shared with other people. Each commit is a named point you can jump to; the parent links are the "steps" between them.

Gotchas beginners hit here
  • Committing = saving to Git, not saving the file. Saving in your editor only writes to disk; Git doesn't record anything until you add + commit.
  • A commit is permanent by design. You can add new commits that change direction, but a good commit isn't meant to be quietly erased — that's a feature, not a limitation.
  • Empty or meaningless messages waste the whole point. The message is the "why" your future self will read; "update" tells you nothing.

3. Install & First Setup

Getting Git on your machine and doing the one-time configuration everyone needs.

Install Git
# Windows: download from https://git-scm.com  (or: winget install Git.Git)
# macOS:   brew install git     (or it comes with Xcode tools)
# Linux:   sudo apt install git   /   sudo dnf install git

git --version        # verify it's installed
One-time setup (do this once per computer)
# Tell Git who you are — this is stamped on every commit you make
git config --global user.name "Your Name"
git config --global user.email "you@example.com"

# Sensible defaults
git config --global init.defaultBranch main    # name the first branch "main"
git config --global pull.rebase false          # simple merge on pull

git config --list                              # review your settings
What does --global mean?

It means "apply this to all my projects on this computer," so you only set your name/email once. Without --global, a setting applies only to the one project you're currently in. You'll almost always use --global for your identity.

WHY this one-time setup matters, and WHERE it's stored

Every commit is permanently stamped with the name and email from your config — that's how history attributes work to people. If you skip this, Git either refuses to commit or stamps commits with a machine-generated identity that looks wrong in every log and pull request forever. The settings live in plain text files you can read:

Where config actually lives (three levels)
# --system  : /etc/gitconfig            (all users on the machine)
# --global  : ~/.gitconfig              (all YOUR repos)      ← you use this most
# (local)   : <repo>/.git/config        (this one repo only) ← overrides global

git config --list --show-origin        # see every setting AND which file it came from
git config user.email                  # read one value (local wins over global)
Mental model: nested rulebooks

Think of three rulebooks stacked from general to specific: system (whole computer), global (your user), local (this project). When Git needs a setting it reads the most specific one that has an answer. So a project can override your global email (handy when you use a work email in one repo and a personal email elsewhere) without changing anything else.

Worked example — per-project identity override
cd work-project
git config user.email "you@company.com"   # no --global → only this repo
git config user.email                     # → you@company.com
cd ../hobby-project
git config user.email                     # → your global personal email
Setup gotchas
  • Wrong email on early commits. If GitHub shows commits as "unknown," your user.email doesn't match your account email — fix the config; already-made commits keep the old email unless you rewrite history.
  • Line-ending pain across OSes. On Windows set git config --global core.autocrlf true; on macOS/Linux use input. Mismatches cause "every line changed" diffs.
  • Default branch name. Old Git defaults to master; setting init.defaultBranch main keeps you consistent with modern hosts.

4. The Three Areas — the mental model that makes Git click

If you understand one diagram in this whole guide, make it this one. Nearly every Git command moves files between these three areas.

AreaWhat it is
Working DirectoryThe actual files on your disk that you see and edit right now.
Staging Area (a.k.a. "index")A waiting room. You pick which changes go into your next snapshot.
Repository (the hidden .git folder)The permanent history of all your committed snapshots.
Why is there a "staging area"? (the confusing bit)

It feels like an extra step, but it's powerful: it lets you choose exactly what goes into each commit. Say you fixed a bug and changed some wording. You can stage and commit just the bug fix (a clean, focused snapshot), then stage and commit the wording separately. Think of staging as packing a box before you seal and label it — you decide what goes in before it becomes a permanent record.

HOW the three areas map to real things on disk

These aren't abstract ideas — each area is a concrete thing:

Which command moves data between which areas
  • git add — working directory → staging area (index).
  • git commit — staging area → repository (a new snapshot).
  • git restore --staged <file> — pull a change back out of staging (repo/index → working stays).
  • git restore <file> — discard working-directory edits, restoring from the index.
  • git reset — move the branch pointer and (depending on the flag) the index and working directory back to an older snapshot.
AreaWhere it physically isWhat Git compares it to
Working directoryThe normal files in your project foldervs the staging area (git diff)
Staging area / indexA single file: .git/indexvs the last commit (git diff --staged)
RepositoryThe object database in .git/objectsthe permanent record

Here's the mechanical truth that surprises people: git add already writes blob objects into the repository. Adding a file hashes its content and stores the blob immediately; the index just records "this blob is what I plan to commit for this path." git commit then bundles the index into a tree, wraps it in a commit object pointing at the current commit as parent, and moves your branch pointer forward. So staging isn't a "pre-save" — it's the assembly bench where you compose the exact snapshot you want.

Worked example — watch a change move through all three areas
echo "hello" > a.txt
git status         # a.txt is "Untracked" (only in working dir)

git add a.txt
git status         # now "Changes to be committed" (in the index)
git diff           # shows NOTHING — working dir matches the index
git diff --staged  # shows the +hello line — index differs from last commit

echo "world" >> a.txt   # edit again AFTER staging
git status         # a.txt appears TWICE: staged (hello) AND not staged (world)
                   # → the index froze the first version; the file moved on
Mental model: packing a shipping box

Working directory = your messy desk where you work. Staging area = a box you're carefully packing, choosing exactly which items go in. Repository = the shelf of sealed, labelled boxes you keep forever. git add puts an item in the box; if you then change the item on your desk, the box still holds the earlier version until you add again. git commit seals and shelves the box.

The classic staging gotcha

Editing a file after you staged it does not update the stage. As the example shows, the file can be listed as both "staged" and "not staged" — the commit will include the version captured at git add time, not your newest edit. Re-run git add to capture the latest. This one behaviour causes more "why isn't my change in the commit?" confusion than any other.

5. Your First Repository

A repository ("repo") is just a folder that Git is tracking. Turning any folder into a repo takes one command.

Create or clone a repository
# Option A: start tracking a NEW project in the current folder
mkdir myproject && cd myproject
git init                      # creates the hidden .git folder — now it's a repo!

# Option B: copy an EXISTING project from GitHub to your computer
git clone https://github.com/user/project.git
cd project
init vs clone

git init = "start a brand-new photo album for this folder." git clone = "download a copy of someone's existing album (with its full history) to my computer." You'll init for your own new projects and clone to join existing ones.

WHAT git init actually creates

git init makes a single hidden folder — .git — and that folder is the repository. Your files stay ordinary files; the entire history, config, and object database live inside .git. Delete .git and you're left with a plain folder (all history gone); copy .git and you've copied the whole project's history.

Look inside a fresh repo
git init demo && cd demo
ls -a            #  .  ..  .git
ls .git
# HEAD        → a text file that says which branch you're on: "ref: refs/heads/main"
# config      → this repo's settings
# objects/    → the content database (blobs, trees, commits live here)
# refs/       → branch & tag pointers (each is a file holding a commit hash)
cat .git/HEAD          # ref: refs/heads/main
cat .git/refs/heads/main   # (empty until your first commit)
Mental model: .git is the "brain," your files are the "body"

Your visible files are what you edit; .git is the brain that remembers every past state of them. git clone copies both brain and body from someone else; git init grows a fresh, empty brain for the folder you're in. That's the only real difference between the two commands.

First-repository gotchas
  • Nesting repos by accident. Running git init inside a folder that's already in a repo creates a confusing repo-inside-a-repo. Check with git status first.
  • Cloning creates a subfolder. git clone url makes a new folder named after the project; you don't need to mkdir first.
  • Nothing is tracked yet. A fresh init tracks zero files — your existing files are all "untracked" until the first add.

6. Staging & Committing — the core loop

This is the rhythm you'll repeat thousands of times: edit → stage → commit.

add then commit — why two steps?

It feels like one action ("save my work"), so why two commands? Because git add lets you choose what goes into this snapshot. Picture packing a moving box: git add is placing items in the box; git commit is sealing and labelling it. You might fix a bug and tweak some wording, but only want the bug fix in this box — add gives you that control. Beginners can just do git add . (add everything) at first and learn selective staging later.

The everyday cycle
# 1. Edit your files (in your editor)...

# 2. Stage the changes you want to save
git add file.txt              # stage one file
git add .                     # stage ALL changed files in this folder
git add src/                  # stage everything in a folder

# 3. Commit the staged changes as a snapshot, with a message
git commit -m "Add login button"

# Shortcut: stage all tracked files AND commit in one step
git commit -am "Fix typo in header"
Writing good commit messages

A commit message explains why a change was made — future-you and teammates will thank you. Convention: a short summary line (under ~50 chars), in the imperative mood ("Add", "Fix", "Remove", not "Added"/"Fixing").

✅ git commit -m "Fix crash when email field is empty"
❌ git commit -m "stuff"        # useless in 6 months
❌ git commit -m "asdfgh"       # please no
Commit small & often

Beginners tend to make one giant commit at the end of the day. Instead, commit each small, complete change (each bug fix, each feature) separately. Small commits are like save points in a video game — the more you have, the less you lose when something goes wrong, and the easier it is to find exactly where a problem was introduced.

HOW a commit is built, step by step

When you run git commit, Git performs a precise sequence: (1) it turns the current index into a tree object capturing every tracked path; (2) it creates a commit object containing that tree's hash, your name/email/timestamp, your message, and the hash of the current commit as the parent; (3) it computes the new commit's hash; (4) it updates the current branch's ref file to point at that new hash. That's the whole mechanism — a commit is a small object linking a snapshot to the one before it.

Worked example — selective staging in action
# You fixed a bug in app.js AND tweaked wording in README.md
git add app.js                 # stage ONLY the bug fix
git commit -m "Fix crash on empty email"

git add README.md              # now stage the wording change separately
git commit -m "Clarify setup steps in README"
git log --oneline              # two clean, focused commits instead of one mixed blob
Stage only PART of a file (surgical commits)
git add -p app.js
# Git shows each change "hunk" and asks: Stage this hunk? [y,n,s,q,?]
#   y = yes  n = no  s = split into smaller hunks  q = quit
# Lets you commit one logical change even if it shares a file with others.
Mental model: composing the perfect "before/after" photo

A commit is a photo of your project you're taking on purpose. Staging is arranging the scene — deciding exactly what's in frame — before the shutter clicks. git add -p is zooming in to include just the corner you care about. The goal is that anyone reading history later sees one clear story per photo, not a blurry snapshot of ten unrelated things.

Committing gotchas
  • git commit -am skips untracked files. The -a flag stages modified tracked files only — brand-new files still need an explicit git add first.
  • Empty commits and "nothing to commit." If nothing is staged, Git refuses; run git status to see why (you probably forgot to add).
  • Giant end-of-day commits. One huge "did everything" commit is hard to review and impossible to partially undo. Commit each logical change as you finish it.
  • Committing generated/secret files. Stage deliberately (or use .gitignore, §8) so build output and secrets never sneak in via git add ..

7. Checking State — status, log & diff

Three commands to always know where you are. Run git status constantly — it's your compass.

See what's going on
git status                    # what's changed, staged, untracked? (use CONSTANTLY)
git log                       # the history of commits
git log --oneline             # compact one-line-per-commit view
git log --oneline --graph --all   # visual branch/commit graph in the terminal

git diff                      # what changed but is NOT yet staged
git diff --staged             # what IS staged (about to be committed)
Example: git status output, explained
On branch main
Changes to be committed:        ← these are STAGED (green), ready to commit
  modified:   app.js
Changes not staged for commit:  ← these are edited but NOT staged (red)
  modified:   style.css
Untracked files:                ← brand-new files Git isn't tracking yet
  notes.txt
"Tracked" vs "Untracked"

A file Git already knows about (you've committed it before) is tracked. A brand-new file Git has never seen is untracked — Git ignores it until you git add it for the first time. That's why new files show up under "Untracked files."

WHY there are two diffs, and WHAT each one compares

The single most useful thing to internalise: each command compares two specific areas. git diff compares your working directory against the index ("what I've changed but not staged"). git diff --staged compares the index against the last commit ("what I'm about to commit"). Knowing which pair each command looks at removes almost all confusion about "why don't I see my change?"

CommandComparesAnswers
git diffworking dir ↔ indexWhat have I edited but not staged?
git diff --stagedindex ↔ last commitWhat will this commit contain?
git diff HEADworking dir ↔ last commitEverything different since my last commit
git diff main..featuretip of main ↔ tip of featureHow do two branches differ?

HOW to read git log like a pro

Log views for real work
git log --oneline --graph --all --decorate   # the "map" of all branches at once
git log -p app.js                # full patch (what changed) for one file over time
git log --stat                   # per-commit summary of files + lines changed
git log --since="2 weeks ago" --author="Maya"   # filter by time and person
git log -S "getUserToken"        # find commits that added/removed that text ("pickaxe")
git log main..feature            # commits on feature that aren't yet on main
Mental model: status is your GPS, log is the map, diff is the magnifying glass

git status tells you where you are right now (which branch, what's staged, what's messy). git log shows the road you travelled to get here. git diff zooms in on the exact words that changed. Reach for status constantly, log when you need context, and diff right before committing to double-check what you're about to save.

State-checking gotchas
  • Empty git diff after staging. Once staged, changes leave the working-dir↔index comparison; use --staged to see them.
  • Two-dot vs three-dot. a..b = commits in b not in a; a...b = commits in either but not both. Mixing them up gives surprising results.
  • log opens a pager. If output "gets stuck," press q to quit the pager (it's less, not a hang).

8. Ignoring Files — .gitignore

Some files should never be saved in Git: passwords, huge build outputs, temp files, downloaded dependencies. A .gitignore file tells Git to skip them.

.gitignore — a text file in your project root
# Dependencies (can be re-downloaded)
node_modules/
venv/

# Secrets — NEVER commit these
.env
*.key
credentials.json

# Build output & logs
dist/
build/
*.log

# OS / editor junk
.DS_Store
.idea/
Never commit secrets

Passwords, API keys, and .env files must go in .gitignore before you commit. Once a secret is committed and pushed, treat it as compromised — it's in the history forever and bots scan public repos within minutes. If it happens: rotate (change) the secret immediately; deleting it in a new commit is not enough because it stays in history.

Why ignore node_modules / dependencies?

These folders hold code you downloaded (not code you wrote) and can be huge — thousands of files. Since anyone can re-download them with one command, storing them in Git would just bloat the repo. You commit the list of what to download (e.g., package.json), not the downloaded files themselves.

HOW pattern matching works — and the rule that trips everyone

.gitignore patterns are matched top-to-bottom, and a later rule can override an earlier one. A leading / anchors to the repo root; a trailing / means "directory only"; * matches within one path segment; ** matches across segments; and a leading ! un-ignores something a previous line ignored.

Patterns, decoded
*.log            # ignore every .log file, anywhere
!important.log   # ...but DO track this one (negation, must come after)
/build           # ignore build/ only at the repo root (not src/build)
docs/*.pdf       # ignore PDFs directly in docs/, not in docs/sub/
temp/            # ignore the temp directory and everything under it
**/cache         # ignore any folder named cache at any depth
The #1 .gitignore gotcha — it only affects UNtracked files

.gitignore tells Git what to ignore when deciding whether to start tracking a file. If a file is already tracked, adding it to .gitignore does nothing — Git keeps tracking it. You must untrack it first:

echo "secrets.env" >> .gitignore
git rm --cached secrets.env      # stop tracking, keep the file on disk
git commit -m "Stop tracking secrets.env"

Also, a negation (!file) cannot re-include a file if its parent directory is ignored — un-ignore the directory first.

Mental model: a bouncer's guest list at the door

.gitignore is a bouncer standing at the entrance deciding who gets let in (tracked). It only checks people trying to enter for the first time — anyone already inside (already tracked) walks right past it. That's why you must "escort out" (git rm --cached) files that got tracked before you added the rule.

Debug why a file is (not) ignored
git check-ignore -v path/to/file   # prints the exact .gitignore line that matches
git status --ignored               # list ignored files too

9. Undoing Changes — the safety toolkit

Everyone makes mistakes. Git's superpower is that almost anything can be undone — if you know which command fits your situation.

reset vs revert — eraser vs correction note

Both undo a change, but very differently. reset is an eraser: it rubs out recent commits as if they never happened — fine for your own private work, dangerous if teammates already have those commits. revert is a correction note: it leaves the original in place and adds a new entry saying "ignore that last one" — nothing is erased, so it's safe on shared branches. The rule: revert in public, reset in private.

SituationCommand
Discard un-staged edits to a filegit restore file.txt
Un-stage a file (keep the edits)git restore --staged file.txt
Change the last commit's messagegit commit --amend
Undo the last commit, keep the changesgit reset --soft HEAD~1
Undo the last commit, discard the changesgit reset --hard HEAD~1 ⚠️
Safely reverse a commit (new "undo" commit)git revert <commit>
reset vs revert — the key difference

git revert creates a new commit that undoes an old one — the history stays intact (nothing is erased). It's the safe choice, especially for commits you've already shared with others. git reset actually rewinds history, erasing commits — powerful but risky, and dangerous on shared branches. Rule of thumb: revert in public, reset in private.

git reset --hard destroys uncommitted work

--hard throws away your changes with no confirmation and no Recycle Bin. Before running it, make sure you don't need those edits. (Good news: committed work can almost always be recovered via reflog — see §21 — but uncommitted work erased by --hard is usually gone for good.)

HOW reset really works — three areas, three flags

Almost all "undo" confusion melts away once you see that git reset does up to three things in order, and each flag decides where it stops. It (1) moves the branch pointer, (2) optionally updates the index, (3) optionally updates the working directory:

FlagMoves branch?Resets index?Resets working dir?Use it to…
--softYesNoNoUndo the commit, keep changes staged (redo the commit differently)
--mixed (default)YesYesNoUndo commit + unstage, keep edits in working dir
--hardYesYesYes ⚠️Throw everything away back to that commit

git revert, by contrast, never moves the pointer backward — it computes the inverse of a commit's changes and records that as a brand-new commit on top. History grows; nothing is erased. That's why revert is safe on branches others have already pulled.

Worked example — same starting point, three different resets
git log --oneline
# c3 (HEAD) Add feature   ← we want to undo this

git reset --soft HEAD~1    # c3 gone from history; its changes STAGED, ready to re-commit
# ...or...
git reset HEAD~1           # c3 gone; changes kept but UNSTAGED (default --mixed)
# ...or...
git reset --hard HEAD~1    # c3 gone AND its changes wiped from disk ⚠️

# Safe alternative that keeps history intact:
git revert c3              # creates c4 that undoes c3; nothing erased
Mental model: rewind-the-tape vs record-a-correction

reset is rewinding a tape and possibly taping over it — great in private, destructive if someone already copied the tape. revert is leaving the tape untouched and recording a new segment that says "disregard the previous bit." When work is shared, always record a correction (revert); rewind (reset) only your own un-shared tape. And --hard is the one button that also erases what you were working on right now, with no bin to recover from.

Undo gotchas
  • restore vs reset. git restore file touches file contents; git reset touches commits/staging. Use restore --staged just to unstage.
  • --amend makes a NEW commit. It doesn't edit the old one in place — it replaces it with a new hash, so don't amend commits you've already pushed.
  • revert of a merge needs -m. Reverting a merge commit requires telling Git which parent to keep (git revert -m 1 <merge>).
  • Committed work is recoverable via reflog (§21); only uncommitted work destroyed by --hard/clean is truly gone.

10. Branches — parallel universes for your code

Branching is Git's killer feature. A branch is an independent line of work — you can build a new feature without touching the working version, then combine them later.

Branches are cheap sticky notes, not copies

A common misconception: that a branch duplicates all your files. It doesn't! A branch is just a tiny sticky note pointing at one commit — creating one is instant and takes almost no space. HEAD is a second sticky note that says "you are here." When you commit, the note for your current branch simply slides forward to the new commit. That lightness is exactly why Git users branch constantly, even for tiny experiments.

Analogy: A branch is like a "Save As" copy of your whole project that keeps its own history. You experiment freely in the copy; if it works, you fold it back into the original; if it doesn't, you throw the copy away — the original was never at risk. In Git this is instant and free.

Working with branches
git branch                      # list branches (* = current)
git branch feature-login        # create a branch
git switch feature-login        # switch to it (modern command)
git switch -c feature-login     # create AND switch in one step
#   (older equivalent: git checkout -b feature-login)

# ...make commits on the branch...

git switch main                 # go back to main
git branch -d feature-login     # delete a merged branch
What is HEAD?

HEAD is just Git's word for "where you are right now" — a pointer to your current branch/commit. When you switch branches, HEAD moves to point at that branch. If a command mentions HEAD (like HEAD~1 = "one commit before where I am"), it's just referring to your current position.

Use a branch for every new piece of work

Keep main always working. Do each feature or bug fix on its own branch, then merge it in when it's done and reviewed. This means broken/half-finished work never pollutes the stable version, and multiple people can work in parallel without collisions.

WHAT a branch REALLY is — a 41-byte file

This is the fact that makes everything about branching click: a branch is literally a tiny text file under .git/refs/heads/ containing one 40-character commit hash (plus a newline — 41 bytes). Creating a branch just writes a new file with the current commit's hash in it. That's why branching is instant and free no matter how large your project is — Git copies nothing.

Prove it to yourself
git switch -c feature
cat .git/refs/heads/feature     # → the same hash as your current commit
cat .git/refs/heads/main        # → also that hash (they point to the same commit)

# HEAD is a file that names your current branch, not a commit:
cat .git/HEAD                   # → ref: refs/heads/feature

When you commit, Git writes the new commit object and then overwrites just that one ref file with the new hash. "Moving a branch forward" is nothing more than updating 40 characters in a file. HEAD is a second pointer that says which branch ref you're currently on; switching branches rewrites HEAD and swaps your working files to match that branch's snapshot.

Worked example — branches diverge
git switch -c feature        # feature and main both point at C2
echo x > f.txt && git add f.txt && git commit -m "C3 on feature"
git switch main
echo y > g.txt && git add g.txt && git commit -m "C4 on main"

git log --oneline --graph --all
# * C4 (main)      ← main advanced here
# | * C3 (feature) ← feature advanced there
# |/
# * C2             ← the shared point they split from
Mental model: labelled sticky notes on a wall of photos

Imagine your commits as photos pinned in a line on a wall. A branch is a sticky note you place under one photo that reads "main" or "feature." Making a commit pins a new photo and slides the sticky note onto it. HEAD is a little arrow reading "you are here." Creating a branch = adding one more sticky note (instant). Deleting a branch = removing a sticky note; the photos it pointed to stay on the wall until nothing references them.

Branch gotchas
  • Deleting a branch doesn't delete commits—but if no branch/tag points at them and they're unreachable, they eventually get garbage-collected. Reflog (§21) can still rescue them for ~90 days.
  • Uncommitted changes block switching. Git refuses to switch if it would overwrite unsaved edits — commit or stash first.
  • Detached HEAD. Checking out a raw commit hash (not a branch) puts you in "detached HEAD"; new commits there aren't on any branch. Make one with git switch -c name to keep them.
  • -d vs -D. -d refuses to delete an unmerged branch (safety); -D forces it. Prefer -d.

11. Merging — combining branches

Merging takes the work from one branch and integrates it into another (usually a feature branch back into main).

Merge a feature branch into main
git switch main                 # go to the branch you want to merge INTO
git merge feature-login         # bring feature-login's work into main
git branch -d feature-login     # clean up the merged branch

Two kinds of merge

TypeWhen it happensResult
Fast-forwardmain hasn't changed since you branched.Git just moves the pointer forward — no extra commit; perfectly linear history.
Three-way (merge commit)both branches have new commits.Git creates a special merge commit that ties the two histories together.
What actually happens in a merge?

Git looks at the two branches and the point where they split, then combines the changes automatically. If the two branches changed different files or different lines, Git merges them with zero fuss. It only needs your help when both branches changed the same lines — that's a "conflict" (next section).

HOW a three-way merge actually computes the result

The name "three-way" tells you the trick. To merge feature into main, Git finds three commits: the tip of main ("ours"), the tip of feature ("theirs"), and the merge base — the most recent commit both branches share (their common ancestor). Git then compares each side against that base:

  • Changed on only one side? Take that change automatically.
  • Changed the same way on both sides? Keep it once.
  • Changed differently on both sides in the same spot? That's a conflict (next section).

The result becomes a new merge commit — the only kind of commit with two parents (main's tip and feature's tip). A fast-forward is the special case where main hasn't moved since the branch point: there's nothing to combine, so Git just slides main's pointer forward to feature's tip — no merge commit at all.

Worked example — force a real merge commit vs allow fast-forward
git switch main
git merge feature                 # fast-forwards if main didn't move; else 3-way merge
git merge --no-ff feature         # ALWAYS make a merge commit (keeps feature visible)
git merge --ff-only feature       # ONLY fast-forward; refuse if a merge commit is needed

git log --oneline --graph
# *   9f8e7d Merge branch 'feature'   ← two parents
# |\
# | * 1a2b3c work on feature
# * | 4d5e6f work on main
# |/
# * 0a0a0a common ancestor (merge base)
Mental model: three photos and a "spot the difference"

Picture three photos: the original scene (merge base), your edited version, and a teammate's edited version. To combine them, you look at what each of you changed relative to the original. Different areas? Keep both edits. Same area, same edit? Keep it once. Same area, clashing edits? You have to decide — that's a conflict. The finished combined photo is the merge commit, and it remembers it came from both edited versions.

Merge gotchas
  • Fast-forward hides the branch. If you value seeing that a feature existed as its own line, use --no-ff (many teams do this for feature merges).
  • You merge INTO your current branch. git merge feature brings feature into wherever you're standing — switch main first.
  • A merge commit isn't a failure. Some people avoid them for aesthetics, but they honestly record how work came together.

12. Merge Conflicts — don't panic

A merge conflict happens when two branches changed the same lines of the same file. Git can't know which version you want, so it asks you. This is normal and fixable.

A conflict is a question, not an error

Beginners panic at "merge conflict" — but it just means Git found one spot where two people edited the same line and it politely refuses to guess. It's like two editors suggesting different titles for the same paragraph: someone has to decide. You open the file, see both versions marked with <<< / === / >>>, delete the markers, keep the version you want (or combine them), save, then git add + git commit. Modern editors like VS Code even show "Accept Current / Incoming" buttons.

What a conflict looks like in a file
<<<<<<< HEAD
color: blue;              ← the version on YOUR current branch
=======
color: green;             ← the version from the branch you're merging in
>>>>>>> feature-login
Resolving a conflict — the steps
# 1. git tells you which files conflict:
git status

# 2. Open each conflicted file. Delete the <<<, ===, >>> markers and
#    edit it to the final version you want (maybe keep one side, or combine both).

# 3. Mark it resolved by staging it:
git add file.css

# 4. Complete the merge:
git commit               # (message is pre-filled for a merge)

# Escape hatch: abort and go back to before the merge
git merge --abort
Conflicts are not errors — they're questions

A conflict doesn't mean you broke anything. Git is simply saying "two people changed this same line; which one do you want — or a mix?" You just edit the file to the version that's correct, remove the marker lines (<<<, ===, >>>), and save. A visual merge tool or your code editor (VS Code shows nice "Accept" buttons) makes this easy.

HOW to read the conflict markers precisely

When Git can't decide, it writes both versions into the file between three marker lines and leaves the file "unmerged" in the index. Decoding them:

The markers, line by line
<<<<<<< HEAD          ← start of YOUR current branch's version ("ours")
color: blue;
=======                ← divider
color: green;
>>>>>>> feature       ← end; the incoming branch's version ("theirs")

Your job is to make the file say what it should finally say — keep one side, keep the other, or write a blend — then delete all three marker lines. Turning on the zdiff3 style (git config --global merge.conflictStyle zdiff3) adds the original base version in the middle so you can see what each side changed, which makes correct resolution far easier.

Worked example — start-to-finish resolution
git merge feature
# Auto-merging style.css
# CONFLICT (content): Merge conflict in style.css
git status                     # style.css listed under "Unmerged paths"

# 1. Open style.css, edit to the final version, remove <<< === >>> lines.
# 2. Prefer one whole side without hand-editing? Use:
git checkout --ours style.css      # keep MY version entirely
git checkout --theirs style.css    # keep THEIR version entirely

# 3. Mark resolved and finish:
git add style.css
git commit                     # completes the merge (message pre-filled)

# Changed your mind mid-conflict?
git merge --abort              # returns everything to the pre-merge state
Mental model: two editors, one sentence, you're the chief editor

Two colleagues each rewrote the same sentence in a shared document. Git doesn't guess whose is "right" — it puts both suggestions side by side with clear markers and hands you the pen. You decide the final sentence, cross out the markers, and initial it (git add + commit). A conflict is a request for a decision, not a bug you caused.

Conflict gotchas
  • Leftover markers. Forgetting to delete a <<</===/>>> line commits broken code. Search the file for <<<<<<< before staging.
  • "ours/theirs" flips during rebase. In a normal merge "ours" is your branch; during a rebase the sides are swapped because Git replays your commits onto theirs — read the labels, don't assume.
  • Staging isn't finishing. git add only marks a file resolved; you still must git commit (or rebase --continue) to complete.
  • Same conflict, again and again? Enable rerere (§31) so Git remembers and replays your resolution.

13. Rebase vs Merge

Both combine work from two branches, but they produce different-looking histories. This trips up many people — here's the clear version.

MergeRebase
HistoryPreserved exactly (shows the branch)Rewritten into a straight line
Creates a merge commit?Yes (for 3-way)No
ResultTrue but "messier" graphClean, linear, easy to read
Safe on shared branches?YesNo — never rebase commits others already have
Rebasing your feature branch onto the latest main
git switch feature-login
git rebase main        # replay your commits on top of the newest main
# resolve any conflicts, then: git rebase --continue
# escape hatch: git rebase --abort
The golden rule of rebase

Never rebase commits that you've already pushed and shared with others. Rebase rewrites history (gives commits new IDs); if teammates already have the old commits, you'll create a tangled mess for everyone. Safe use: rebase your own local, unshared branch to tidy it up before sharing. When in doubt, merge — it's always safe.

Which should a beginner use?

Start with merge — it's safe and simple. Learn rebase later, once you're comfortable, to keep history tidy on your own branches. Many teams have a convention (e.g., "rebase your feature branch before opening a pull request, then merge it"). Follow your team's convention.

HOW rebase works mechanically — and why hashes change

A rebase does something merge never does: it replays your commits as brand-new commits on a different base. When you run git rebase main from feature, Git: (1) finds the merge base of feature and main; (2) saves each of your feature commits as a patch (a diff); (3) resets feature to point at main's tip; (4) re-applies each saved patch one by one, creating new commits.

Because a commit's hash is computed from its content including its parent, and the parent is now different, every replayed commit gets a new hash. The old commits still exist (reflog can find them) but your branch now points at the new copies. This is the entire reason rebasing shared commits is dangerous — everyone else still references the old hashes, so you've effectively created duplicate divergent history.

Worked example — before and after
# Before: feature branched off an OLD main
# main:    A---B---C
#               \
# feature:       D---E     (D,E have parent B)

git switch feature
git rebase main
# After: D,E are re-created as D',E' on top of C
# main:    A---B---C
#                   \
# feature:           D'---E'   (new hashes; linear on top of C)

git log --oneline --graph      # one straight line, no merge commit
Mental model: transplanting vs stapling

Merge staples two timelines together at a join point and keeps both visible — honest but branchy. Rebase uproots your commits and replants them on top of the latest main, as if you'd started your work today — tidy and linear, but the transplanted commits are new plants (new hashes), not the originals. Merge preserves what happened; rebase rewrites the story to read cleanly.

A practical team convention

Many teams: rebase your own feature branch onto the latest main to stay current, then merge the feature into main with --no-ff. You get a clean, linear feature history and a clear record that the feature was merged. Rebase locally (private) → merge publicly (shared) satisfies the golden rule.

Rebase gotchas
  • Force-push after rebase. Because hashes changed, a rebased branch you already pushed needs git push --force-with-lease (safer than --force — it refuses if someone else pushed meanwhile).
  • Conflicts per commit. Rebase re-applies each commit, so you may resolve conflicts several times (once per replayed commit), not just once as with merge.
  • Never rebase shared history. If teammates already pulled those commits, rebasing creates a painful mess — merge instead.

14. Remotes — connecting to GitHub & friends

So far everything is on your computer. A remote is a copy of your repository hosted elsewhere (like GitHub) that you and your team sync with.

Connecting to a remote
git remote -v                                   # show configured remotes
git remote add origin https://github.com/you/project.git   # link a remote
git branch -M main                              # ensure branch is named main
git push -u origin main                         # first push (sets up tracking)
What is "origin"?

origin is just the default nickname Git gives to the remote you cloned from (usually your GitHub repo). It saves you typing the full URL every time — git push origin main means "send my main to the remote called origin." You can have several remotes with different names, but most projects just have origin.

HOW remote-tracking branches work — the local mirror

A remote isn't just a URL — Git keeps a local read-only mirror of each remote branch, called a remote-tracking branch, named like origin/main. When you fetch, Git updates these origin/* pointers to match the server; it does not touch your own branches. Your local main and the mirror origin/main are separate pointers — which is exactly why Git can tell you "your branch is 2 commits ahead, 1 behind."

See the three pointers involved
git branch -vv
# * main   a1b2c3 [origin/main: ahead 2, behind 1] latest local commit
#   ^your local main   ^tracks    ^comparison to the mirror

cat .git/refs/heads/main             # your local main's hash
cat .git/refs/remotes/origin/main    # the mirror's hash (updated by fetch)
git remote show origin               # full detail: URL, tracked branches, sync state

An upstream (set with push -u) links your local branch to a remote-tracking branch so bare git push/git pull know where to go — that's what the -u in your first push configured.

Mental model: your desk copy vs the office notice board

origin/main is a photograph of the office notice board (the server) that you took the last time you looked (fetched). Your local main is your own working copy on your desk. They drift apart as you and others make changes. Fetching = taking a fresh photo of the board; pushing = pinning your work onto the actual board; the "ahead/behind" count = comparing your desk copy to your latest photo.

Worked example — clone sets everything up automatically
git clone https://github.com/you/project.git
cd project
git remote -v          # origin  https://github.com/you/project.git (fetch & push)
git branch -vv         # * main ... [origin/main]  ← upstream already linked
# clone gives you: the files, full history, a remote named origin, and tracking.
Remote gotchas
  • origin/main is a snapshot, not live. It only reflects the server as of your last fetch/pull — an "up to date" message can be stale until you fetch.
  • HTTPS vs SSH auth. HTTPS uses a token/credential helper; SSH uses your key. "Permission denied (publickey)" means SSH key isn't set up; a password prompt on HTTPS wants a personal access token, not your login password.
  • Renaming/removing remotes. git remote rename origin upstream and git remote remove <name> — the mirror refs move with them.

15. push, pull & fetch

The three commands that move commits between your computer and the remote.

fetch vs pull, the mailbox way

Fetch is like checking your mailbox — you see what arrived, but you haven't opened or filed anything yet. Pull is check the mailbox AND open/file everything into your desk in one motion. Most days you just pull. Use fetch when you want to peek at what changed before mixing it into your own work.

CommandWhat it does
git pushUpload your local commits to the remote (share your work).
git fetchDownload others' commits from the remote, but don't merge them yet (just look).
git pullFetch and merge in one step (get others' work into your branch).
Daily sync
git pull                    # get the latest before you start working
# ...make commits...
git push                    # share your commits

git fetch origin            # just download, review before merging
git log origin/main         # see what's new on the remote
pull = fetch + merge

git fetch is like checking the mailbox — you see what arrived but don't open it. git pull is check the mailbox AND open/file everything. Most days you'll just pull. Use fetch when you want to review incoming changes before combining them with your work.

Pull before you push

Always git pull before starting work and before pushing, so you're building on the latest version. If you push stale work, Git will reject it and ask you to pull first (to merge in what you missed). Pulling frequently means smaller, easier merges.

WHY pull = fetch + integrate, and the merge-vs-rebase choice

git pull is a convenience wrapper. It runs git fetch (update the origin/* mirror) and then integrates the new commits into your current branch — by default with a merge, or with a rebase if you configure pull.rebase true. Understanding this split is what lets you fix the messages people find scary.

Control exactly how pull integrates
git config --global pull.rebase false   # pull = fetch + merge  (default, safe)
git config --global pull.rebase true    # pull = fetch + rebase (linear history)
git config --global pull.ff only        # pull only if it can fast-forward, else stop

git fetch origin                        # just refresh the mirror, integrate nothing
git log HEAD..origin/main --oneline     # exactly what pull would bring in
git merge origin/main                   # integrate manually, on your terms

HOW to read the "rejected — non-fast-forward" push error

The most common push failure means: the server has commits your local branch doesn't, so accepting your push would erase them. Git refuses to protect that work. The fix is not --force — it's to bring the remote's commits into yours first, then push:

The error, decoded
! [rejected]        main -> main (non-fast-forward)
error: failed to push some refs to '...'
hint: Updates were rejected because the remote contains work that you do
hint: not have locally. Integrate the remote changes (e.g. 'git pull') first.
The correct fix
git pull --rebase        # replay your commits on top of the remote's newest
# resolve any conflicts, then:
git push                 # now it's a clean fast-forward
Mental model: a shared whiteboard everyone writes on

The remote is a whiteboard several people write on. push = adding your notes to it. If someone wrote after your last look, the board rejects your overwrite — you must first copy down their new notes (pull), fit yours around them, then post. fetch is photographing the board without editing yours yet; pull is photographing and copying the new notes into your notebook in one motion.

When (not) to force-push

git push --force overwrites the remote branch with yours, discarding commits others may have pushed — on a shared branch this destroys teammates' work. If you genuinely must overwrite (e.g., after rebasing your own feature branch), use git push --force-with-lease: it refuses unless the remote is still where you last saw it, protecting against clobbering someone else's new commits. Never force-push shared branches like main.

16. Pull Requests & the GitHub Flow

A Pull Request (PR) — "Merge Request" on GitLab — is how teams review and discuss changes before merging them. It's a GitHub feature built on top of Git branches.

A Pull Request is "please review my change before it goes in"

Despite the name, a PR isn't really about "pulling." Think of it as submitting your work for approval: you say "here's what I changed on my branch — please look before we add it to the shared version." Teammates read it, leave comments, automated tests run, and once it's approved and green, it gets merged. It's the software equivalent of an editor reviewing your article before it's published — catching problems while they're still easy to fix.

The typical flow
git switch -c fix-login-bug     # 1. branch
# ...edit & commit...
git push -u origin fix-login-bug  # 3. push the branch to GitHub
# 4. On GitHub: click "Compare & pull request", describe it, request review.
#    Teammates comment/approve. Automated checks (CI) run.
# 5. Click "Merge" once approved & green. Then delete the branch.
Why not just push straight to main?

A Pull Request adds a review checkpoint: a teammate reads your change, automated tests run, and problems are caught before they reach the shared, working version. It's like having an editor check your article before it's published. Most teams protect the main branch so changes must go through a PR — this keeps main reliable.

WHAT a PR is under the hood, and the three merge buttons

A Pull Request is a host feature (GitHub/GitLab/Bitbucket), not a Git command. Mechanically it's just: "here are the commits on branch X; propose integrating them into branch Y, with a discussion thread and automated checks attached." When it's approved, the host runs a Git operation on the server. GitHub offers three, and the choice shapes your history:

ButtonWhat it does to historyGood when
Merge commitCreates a real merge commit; keeps every branch commitYou want the full, honest record of how work came in
Squash and mergeCombines all branch commits into ONE new commit on the baseThe branch had messy "wip" commits; you want one clean entry
Rebase and mergeReplays each commit onto the base, linear, no merge commitYou want linear history but keep individual commits
Worked example — the full loop with the GitHub CLI
git switch -c fix-login-bug
# ...edit & commit...
git push -u origin fix-login-bug
gh pr create --title "Fix login crash" --body "Handles empty email field"
# reviewers comment; CI runs; once approved & green:
gh pr merge --squash --delete-branch     # squash, merge, and tidy up the branch
git switch main && git pull              # bring the merged result down locally
Mental model: submitting an article to an editor

Your branch is a draft article. Opening a PR is submitting it to editors: they read it, suggest edits (review comments), and a fact-checker (CI tests) runs automatically. Nothing goes to print (main) until it's approved and passes checks. "Squash" is publishing the polished final draft as one clean piece instead of showing every scribbled revision.

PR gotchas
  • Keep pushing to the same branch. New commits to your branch automatically appear in the open PR — you don't open a new PR per change.
  • Stale branch. If main moved a lot, update your branch (merge main in or rebase) so the PR reflects the real merged result and CI tests the right thing.
  • Squash loses individual commits. After a squash-merge, delete and re-create the branch for new work rather than reusing it, to avoid confusing duplicate history.
  • Protected main. Direct pushes are usually blocked; the PR is the only path in, by design.

WHY teams need a shared workflow at all

Git itself imposes no process — it will happily let ten people push to main at once. A workflow is the social agreement layered on top so that the shared branch stays trustworthy and everyone's work integrates predictably. The core tension every model balances: how long branches live. Long-lived branches drift far from main and produce big, painful merges; short-lived branches integrate constantly and stay easy to merge. Almost every "modern" recommendation is really "make branches shorter-lived."

HOW forking differs from branching (open source)

In a branch-based team everyone has write access to one shared repo and pushes branches to it. In a fork-based model (typical open source) outside contributors can't write to the main repo, so they clone their own server-side copy (a fork), push branches there, and open a PR across repositories. You keep the original repo as a second remote (usually named upstream) to stay in sync.

Worked example — the fork sync dance
# You forked org/project on GitHub, then cloned YOUR fork:
git clone https://github.com/you/project.git
git remote add upstream https://github.com/org/project.git   # the original

# Keep your fork current with the real project:
git fetch upstream
git switch main
git merge upstream/main       # (or rebase) bring in the latest
git push origin main          # update your fork

# Do work on a branch, push to YOUR fork, open a PR to org/project:
git switch -c my-fix
# ...commit...
git push -u origin my-fix
Mental model: choosing a "traffic system" for a shared road

All these workflows are just traffic rules for the shared road that is main. Trunk-based is a busy city with frequent small merges and good signals (tests) keeping flow safe. GitHub Flow adds a quick checkpoint (the PR) before each merge. GitFlow builds dedicated lanes (develop/release/hotfix) for scheduled convoys. Forking is "you drive your own private road and request permission to join the highway." Pick the simplest rules that keep your traffic from crashing.

Collaboration gotchas
  • Long-lived branches rot. A branch open for weeks becomes a merge nightmare — integrate main into it (or rebase) frequently.
  • Everyone force-pushing shared branches. Reserve force-push for your own feature branches; never on main/develop.
  • Forgetting upstream. In forks, pulling from origin only updates your fork, not the real project — sync from upstream.
  • Over-engineering the process. Adopting GitFlow for a small web app adds ceremony without benefit; match the model to your release cadence.

18. Stashing — set work aside temporarily

git stash lets you shelve unfinished changes to get a clean working directory, then bring them back later. Perfect for "I need to quickly switch branches but I'm mid-edit."

Stashing
git stash                    # shelve your uncommitted changes (working dir goes clean)
git stash list               # see stashed items
git stash pop                # bring back the latest stash AND remove it from the list
git stash apply              # bring it back but KEEP it in the list
git stash drop               # delete a stash
git stash -u                 # also stash untracked files
When would I use this?

You're halfway through a feature when an urgent bug comes in. You're not ready to commit your messy half-work, but you need a clean slate to fix the bug. git stash tucks your changes into a drawer, you fix the bug on a clean branch, then git stash pop pulls your half-work back out exactly as it was. Think of it as a clipboard for your entire set of uncommitted changes.

HOW a stash is stored — it's secretly commits

A stash isn't a magic clipboard — Git implements it as real commit objects saved off to the side under refs/stash. Each stash entry bundles up to two hidden commits: one capturing your staged changes and one capturing your working-directory changes, both parented on the commit you were sitting on. That's why a stash survives branch switches and can be inspected, diffed, and even recovered from reflog like any commit.

Inspect and target stashes precisely
git stash list
# stash@{0}: WIP on feature: a1b2c3 last commit
# stash@{1}: WIP on main: 9f8e7d earlier work

git stash show -p stash@{1}     # see the actual diff of a specific stash
git stash apply stash@{1}       # restore a specific one (keeps it in the list)
git stash pop                   # restore newest AND remove it
git stash branch fix stash@{0}  # create a branch FROM a stash (great after conflicts)
Worked example — urgent bug interrupts you
# You're mid-feature, files dirty, and a production bug lands.
git stash push -u -m "half-done login form"   # -u also stashes new untracked files
git switch -c hotfix && # ...fix & commit & push...
git switch feature
git stash pop                                  # your half-done work returns intact
Mental model: sweeping your desk into a labelled tray

Stash is sweeping everything currently on your desk into a tray you slide under the table, leaving a clean surface to handle something urgent. Because the tray is really a mini-snapshot (commits), nothing is lost — pop tips it back out exactly as it was. You can stack several trays and pick which one to tip back.

Stash gotchas
  • Untracked files aren't stashed by default. Use -u (untracked) or -a (also ignored) or they stay behind.
  • pop can conflict. If the branch changed underneath, popping may raise conflicts — resolve them like a merge; the stash isn't dropped until it applies cleanly.
  • Stashes are easy to forget. They're not tied to a branch and don't show in git log; check git stash list so old work isn't stranded.
  • Prefer a WIP commit for long pauses. For anything beyond a quick interruption, a throwaway commit on a branch is safer and clearer than a long-lived stash.

19. Rewriting History — interactive rebase

Before sharing a branch, you can clean up its commits — squash several into one, reword messages, reorder, or drop commits — with interactive rebase.

Interactive rebase
git rebase -i HEAD~3         # edit the last 3 commits
# An editor opens with a list. Change "pick" to:
#   squash (s)  → fold this commit into the one above
#   reword (r)  → change the message
#   edit   (e)  → pause to amend it
#   drop   (d)  → delete the commit
# Save & close; Git replays the commits with your changes.
Why "squash" commits?

While building a feature you might make messy commits: "wip", "fix typo", "actually fix it", "oops". Before sharing, you can squash those into a single clean commit like "Add password reset feature." It's like editing a rough draft into a clean final version — reviewers see one tidy change instead of your scribbles.

Only rewrite history that's still private

Same golden rule as rebase: interactive rebase changes commit IDs. Only do it on commits you haven't pushed/shared yet. Rewriting shared history forces everyone else into a painful cleanup. Clean up locally before the first push.

HOW interactive rebase executes your instructions

Interactive rebase (git rebase -i) opens a to-do script — one line per commit, oldest at the top. You edit the verb at the start of each line, save, and Git replays the commits following your script, creating new commits (new hashes) as it goes. The available verbs:

VerbEffect
pickKeep the commit as-is
rewordKeep changes, edit the message
editPause here so you can amend the snapshot itself
squashMerge into the commit above, combining messages
fixupLike squash but discard this commit's message
dropDelete the commit entirely
(reorder lines)Change the order commits are applied
Worked example — turn four messy commits into one clean one
git log --oneline
# e4 wip
# d3 oops fix
# c2 actually add reset link
# b1 start password reset

git rebase -i HEAD~4
# editor opens:
#   pick b1 start password reset
#   squash c2 actually add reset link
#   squash d3 oops fix
#   squash e4 wip
# save → Git lets you write ONE combined message:
#   "Add password reset feature"
git log --oneline
# a9 Add password reset feature   ← single tidy commit (new hash)
Mental model: editing a rough draft before publishing

Your work-in-progress commits are a messy first draft full of crossings-out ("wip", "oops"). Interactive rebase is the editing pass: you merge scattered paragraphs (squash), fix titles (reword), cut dead sentences (drop), and reorder for flow — before anyone else reads it. Reviewers then see a clean story, not your scribbles.

History-rewriting gotchas
  • New hashes = only for unshared commits. Same golden rule as rebase: never rewrite commits already pushed/shared.
  • Autosquash speeds this up. Commit fixes with git commit --fixup <sha>, then git rebase -i --autosquash pre-arranges the script for you.
  • Stuck mid-rebase? git rebase --abort returns to the exact pre-rebase state; --continue proceeds after resolving; --skip drops the current commit.
  • Editor confusion. If an unfamiliar editor opens, set a comfortable one: git config --global core.editor "code --wait".

20. Cherry-pick & Tags

Two useful targeted tools: grabbing a single commit, and marking release versions.

Tag vs branch — a milestone plaque vs a bookmark

A branch is like a bookmark in a book you're still writing — it moves forward every time you add a page (commit). A tag is like a engraved plaque nailed to one exact spot: "Version 1.0 shipped here." It never moves. You tag the precise commit you released so you can always come back and rebuild exactly that version, even years later. Cherry-pick, meanwhile, is "copy just this one commit over to another branch" — handy for applying a single urgent fix in multiple places.

Cherry-pick — copy one commit

git cherry-pick copies a specific commit from one branch onto your current branch — handy for applying a single bug fix to multiple branches.

cherry-pick
git log --oneline other-branch     # find the commit's ID
git cherry-pick a1b2c3d            # apply just that commit here

Tags — mark releases

A tag is a permanent, human-friendly label on a specific commit — used to mark release versions like v1.2.0.

tags
git tag                            # list tags
git tag -a v1.2.0 -m "Release 1.2.0"   # create an annotated tag
git push origin v1.2.0             # push a tag (tags aren't pushed by default)
git push origin --tags             # push all tags
Tag vs branch

A branch moves forward as you add commits (it's a moving bookmark). A tag is nailed permanently to one specific commit (a fixed milestone). You tag the exact commit you released as "v1.2.0" so you can always find and rebuild that precise version later.

HOW cherry-pick works — it re-applies a change, not the commit

git cherry-pick <sha> takes the diff that one commit introduced (comparing it to its parent) and re-applies that diff on top of your current branch, then records a new commit with a new hash. It is not moving the original commit — it's copying its effect. That's why the same logical fix can exist on two branches with two different hashes.

Worked example — hotfix on main, port it to a release branch
git switch main
git log --oneline -1        # f00dcafe Fix payment rounding bug
git switch release-2.3
git cherry-pick f00dcafe    # re-applies the fix here as a NEW commit
# conflict? resolve, then: git cherry-pick --continue
# range: copy several commits at once
git cherry-pick A^..B       # every commit from A through B

HOW annotated tags differ from lightweight ones (and why it matters for releases)

A lightweight tag is just a name pointing at a commit — like a branch that never moves. An annotated tag (-a) is a full tag object in the database storing the tagger, date, message, and (optionally) a GPG/SSH signature. Release tooling and git describe expect annotated tags — always use -a (or a signed -s) for releases.

Worked example — cut and verify a release
git tag -a v1.2.0 -m "Release 1.2.0"     # annotated (recommended)
git cat-file -t v1.2.0                    # → tag  (a real object, not just a ref)
git show v1.2.0                           # tagger, date, message, then the commit
git describe --tags                       # v1.2.0-3-gab12cd (3 commits past v1.2.0)
git push origin v1.2.0                     # tags are NOT pushed by default
Mental model: photocopy a page vs nail a plaque

Cherry-pick is photocopying one page from another notebook into yours — the content arrives, but it's a fresh copy with its own page number (hash). A tag is nailing a commemorative plaque to one exact spot in your timeline ("v1.2.0 shipped here"): an annotated tag's plaque is engraved with who/when/why, a lightweight tag is just a stick-on label.

Cherry-pick & tag gotchas
  • Cherry-pick duplicates commits. Later merging the source branch can create awkward duplicate changes; prefer merge/rebase for whole-branch integration and reserve cherry-pick for isolated fixes.
  • Tags don't auto-push. Use git push origin <tag> or --tags; teammates won't see a tag until it's pushed.
  • Moving a tag is dangerous. Re-pointing an already-published tag (-f) confuses everyone who fetched it — cut a new version instead.
  • Lightweight tags for releases break tooling. git describe and many CI systems ignore them by default.

21. reflog — Git's ultimate safety net

Think you lost commits after a bad reset or rebase? git reflog can almost always bring them back. This is the command that turns "I destroyed everything" into "phew."

Git quietly records every move HEAD makes — every commit, checkout, reset, rebase — in the reflog, even for commits no longer on any branch. As long as you committed something, the reflog remembers it (for ~90 days).

Recovering "lost" commits
git reflog                    # a list of every recent HEAD position
# find the commit you want to get back, e.g. a1b2c3d, then:
git reset --hard a1b2c3d      # jump back to that state
# or recover it onto a new branch:
git branch recovered a1b2c3d
The most reassuring thing about Git

Once you've committed something, it's extremely hard to truly lose it — even after a scary reset --hard. The reflog is a private journal of everywhere you've been, so you can rewind to any recent point. This is why the #1 rule is commit early and often: committed work is recoverable; uncommitted work is not.

HOW the reflog works — a private diary of pointer moves

Every time a ref (like HEAD or a branch) changes where it points, Git appends a line to a log under .git/logs/ recording the old hash, the new hash, and what caused the move. This log is local and private (it never gets pushed or cloned) and it captures moves that leave no trace in normal history — including commits you "lost" by resetting or rebasing. As long as a commit was ever pointed at, its hash is in the reflog, and the object survives until garbage collection (default ~90 days for reachable-from-reflog objects).

Read the reflog and use its shorthand
git reflog                    # HEAD's history of moves
# a1b2c3 HEAD@{0}: reset: moving to HEAD~3   ← the mistake
# d4e5f6 HEAD@{1}: commit: the work I thought I lost
git reflog show main          # a specific branch's move history

# HEAD@{n} is a usable revision — "where HEAD was n moves ago":
git show HEAD@{1}             # what was there before the last move
git diff HEAD@{2} HEAD        # what changed across the last two moves
Worked example — recover from a catastrophic reset
git reset --hard HEAD~3        # 😱 "I just deleted three commits of work"
git reflog                     # find the hash BEFORE the reset, e.g. d4e5f6
git reset --hard d4e5f6        # jump right back — commits restored
# safer: park it on a new branch first
git branch rescue d4e5f6
Mental model: security-camera footage of your repo

Normal history is the official photo album — curated, shareable. The reflog is the security camera that quietly filmed every move you made in the building, including walking out with commits and then dropping them. When you can't find something in the album, you rewind the camera footage to the moment before it vanished and walk back to that spot. The footage is yours alone and self-erases after a few months.

Reflog gotchas
  • Local only. A freshly cloned repo has an empty reflog — it can't recover a collaborator's lost commits, only your own machine's history.
  • Not forever. Unreachable objects are eventually pruned by git gc; recover promptly.
  • Only rescues committed work. Reflog tracks commits and pointer moves, not uncommitted edits — reset --hard that wipes unsaved changes leaves nothing for reflog to find.

22. bisect & blame — investigation tools

Two commands for answering "when/who introduced this?"

git bisect — find the commit that broke something

git bisect does a binary search through your history to pinpoint exactly which commit introduced a bug — far faster than checking one by one.

bisect
git bisect start
git bisect bad                # current version is broken
git bisect good v1.0          # this old version worked
# Git checks out a commit halfway between. Test it, then tell Git:
git bisect good   # (or) git bisect bad
# Repeat a few times; Git narrows to the exact culprit commit.
git bisect reset              # done — return to normal
How bisect saves hours

If a bug appeared somewhere in the last 1,000 commits, checking each one is hopeless. Bisect uses "binary search": it jumps to the middle, you say better/worse, it halves the range again, and so on. It finds the culprit in about 10 steps instead of 1,000 — like finding a word in a dictionary by opening the middle, not reading every page.

git blame — who last changed each line

blame
git blame file.js             # show who last changed each line, and in which commit
git blame -L 40,60 file.js    # just lines 40–60

Despite the name, it's for understanding why a line exists (find the commit → read its message/PR), not for pointing fingers.

HOW bisect's binary search cuts the range in half each step

Bisect exploits a simple fact: if a version was good at commit A and bad at commit B, the breaking commit is somewhere between them. Instead of testing linearly, it checks out the middle commit; your verdict (good/bad) eliminates half the remaining commits; repeat. That's why 1,000 commits collapse to about 10 tests — each answer halves the search space (2¹⁰ ≈ 1024).

Worked example — fully automate the hunt
git bisect start
git bisect bad                     # now is broken
git bisect good v1.0               # this old tag worked
# Instead of testing by hand each step, hand Git a test script:
git bisect run ./run-tests.sh      # exit 0 = good, non-zero = bad
# Git drives itself to the answer:
# abc1234 is the first bad commit
git bisect reset                   # return to where you started

HOW blame reconstructs authorship line by line

git blame walks history backward for a file, and for each line records the last commit that touched it, following the content as it moved. Options make it a real investigation tool rather than a finger-pointer:

Blame like an investigator
git blame -L 40,60 file.py         # only lines 40–60
git blame -w file.py               # ignore whitespace-only changes
git blame -C file.py               # detect lines COPIED/MOVED from other files
git log -p -S "getUserToken"       # jump to the commit that introduced a string
git show <sha-from-blame>           # read the full change + message for context
Mental model: bisect = guess-the-number, blame = a document's margin notes

Bisect is the "I'm thinking of a number 1–1000, higher/lower?" game — always guess the middle and you win in ~10 tries. Blame is like a document where every line has a margin note saying who wrote it and when; you find a suspicious line, read its note, then open that revision to learn why it was written.

Investigation gotchas
  • Bisect needs a reliable test. A flaky or intermittent bug gives wrong good/bad answers and misleads the search — make the test deterministic first.
  • bisect run exit codes matter. Your script must exit 0 for good and non-zero for bad; use exit code 125 to tell Git "skip this untestable commit."
  • Blame points at reformatting, not authorship. A whitespace or style pass can make one person "own" every line — use -w and -C, and treat blame as a starting point for why, not for assigning fault.

23. Worktrees — Multiple Checkouts, One Repo

Need to fix an urgent bug on main while your feature branch is half-done? Stashing and switching is clumsy. Worktrees let you check out several branches into separate folders simultaneously, all sharing one .git.

Using worktrees
git worktree add ../app-hotfix hotfix/urgent   # new folder on branch hotfix/urgent
git worktree add ../app-review origin/pr-123   # check out a PR to review
git worktree list                              # show all worktrees
git worktree remove ../app-hotfix              # clean up when done
Why lead engineers love worktrees

No more "stash, switch, unstash" dance. Build artifacts stay separate per branch (no recompiling everything after a switch). Perfect for running long tests on one branch while coding on another. Far lighter than a second clone since history isn't duplicated.

HOW worktrees share one object database

A linked worktree gets its own working directory and its own HEAD/index, but it does not get its own .git/objects — it stores a small pointer file back to the main repo's database. So all commits, branches, and blobs live once, in the original repo; each worktree is just another checkout window onto that shared store. This is why adding a worktree is near-instant and cheap compared with a second git clone.

Mental model: several desks, one filing cabinet

The .git object database is a shared filing cabinet. Each worktree is a separate desk where you can lay out a different branch's files. Everyone files into and pulls from the same cabinet, so nothing is duplicated — you just have more surfaces to work on at once.

Worktree gotchas
  • One branch, one worktree. Git refuses to check out the same branch in two worktrees at once (it would create conflicting states).
  • Clean up properly. Deleting a worktree folder by hand leaves a stale entry; use git worktree remove (or git worktree prune).
  • Shared refs. Deleting or moving a branch affects every worktree since they share refs.

24. Submodules & Subtrees — Repos Inside Repos

When your project depends on another Git repo (a shared library, a theme), you have two ways to embed it. They solve the same problem with opposite trade-offs.

How it storesA pointer to a specific commit in another repoActually copies the other repo's files into yours

HistoryStays separateMerged into your repo

Submodules
git submodule add https://github.com/org/shared-lib libs/shared
git clone --recurse-submodules <url>        # clone parent + all submodules
git submodule update --init --recursive     # if you forgot the flag
# Update a submodule to the latest upstream commit:
cd libs/shared && git pull origin main && cd -
git add libs/shared && git commit -m "bump shared-lib"
The #1 submodule gotcha

A submodule points at a commit, not a branch. After pulling, you often land in a "detached HEAD." Forgetting git submodule update after a git pull means your submodule is silently out of date. Add git config submodule.recurse true so pulls update submodules automatically.

HOW a submodule is stored — a pinned commit, not files

Your parent repo does not store the submodule's files at all. It stores two things: a .gitmodules file (the URL and path) and, in its tree, a special gitlink entry recording the exact commit hash the submodule should be at. So checking out the parent gives you a pointer that says "put the shared library at commit abc123." That's why cloning needs --recurse-submodules to actually fetch the referenced content, and why bumping a submodule is a two-step act: pull inside the submodule, then commit the new pinned hash in the parent.

Mental model: a bookmark to a specific edition

A submodule is like citing "Chapter 3 of the 2019 edition" in your book. You don't reprint that chapter — you record precisely which edition and page. A subtree, by contrast, photocopies the whole chapter into your book so readers need nothing else, at the cost of a fatter book that's harder to re-sync with the original.

25. Monorepo Strategies

One giant repository for many projects (Google, Meta style) versus many small repos (polyrepo). Lead engineers must reason about the trade-offs and the tooling that makes monorepos viable.

What makes a monorepo actually work
  • Sparse checkout & partial clone — git clone --filter=blob:none + git sparse-checkout set apps/web so devs only fetch what they touch.
  • Build tooling that understands the graph — Bazel, Nx, Turborepo, or Pants only rebuild/test what a change actually affects.
  • CODEOWNERS — route reviews to the right team per directory.
  • Path-filtered CI — run only the pipelines for changed paths (see the CI/CD guide).

WHY monorepos need special tooling to stay fast

Git was designed around whole-repo operations, so a naïve monorepo with millions of files makes status, clone, and checkout crawl. The fixes attack the two costs — history size and working-tree size. Partial clone (--filter=blob:none) skips downloading old file contents until you actually need them. Sparse-checkout materializes only the directories you work in. fsmonitor and the commit-graph keep status/log instant by caching filesystem and history metadata.

Mental model: a library with on-demand delivery

A polyrepo is many small libraries you visit separately. A monorepo is one enormous central library. To keep it usable you don't carry every book home (partial clone), you only put the shelves you're using on your desk (sparse-checkout), and the librarian keeps a fast index so lookups don't require walking every aisle (commit-graph/fsmonitor).

Monorepo gotchas
  • Unfiltered CI. Running every test on every commit destroys velocity — use path-filtered pipelines and graph-aware tools (Nx/Bazel/Turborepo).
  • Repo bloat from binaries. Large assets committed to history slow everyone's clone forever; route them through Git LFS.
  • Ownership ambiguity. Without CODEOWNERS, reviews land on the wrong people; define ownership per directory.

26. Hooks & Automation

Git can run your scripts at key moments — before a commit, before a push, after a merge. This is how teams enforce quality automatically.

Use the pre-commit framework, not raw hook files

Hand-written hooks in .git/hooks/ aren't versioned or shared. The pre-commit framework (a .pre-commit-config.yaml in your repo) manages hooks declaratively, installs them for everyone, and ships hundreds of ready-made checks (formatters, linters, secret scanners like gitleaks).

.pre-commit-config.yaml
repos:
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v4.6.0
    hooks:
      - id: trailing-whitespace
      - id: end-of-file-fixer
      - id: check-yaml
      - id: detect-private-key      # block committing secrets
  - repo: https://github.com/gitleaks/gitleaks
    rev: v8.18.0
    hooks:
      - id: gitleaks                 # scan for leaked credentials

HOW hooks actually run — scripts in .git/hooks

A hook is simply an executable script with a specific name (e.g. pre-commit) placed in .git/hooks/. At each lifecycle moment Git looks for the matching file and, if it's executable, runs it. A non-zero exit code aborts the operation — that's how a failing linter blocks a commit. Because .git/hooks is not part of the tracked repo, hooks aren't shared or versioned by default, which is exactly the problem the pre-commit framework solves by managing them from a tracked config.

Mental model: quality gates on an assembly line

Hooks are inspection stations along the line. pre-commit checks a part before it's boxed; pre-push checks the crate before it ships; server-side pre-receive is the loading-dock guard nobody can bypass. Any station can pull the cord (non-zero exit) and stop the line until the defect is fixed.

Hook gotchas
  • Client hooks are bypassable. Anyone can --no-verify or delete a local hook — enforce true policy with server-side hooks or required CI checks, not client hooks alone.
  • Not versioned by default. Raw .git/hooks scripts don't travel with a clone; use the pre-commit framework or set core.hooksPath to a tracked folder.
  • Must be executable. A hook without the execute bit is silently ignored.

27. Signed Commits & Supply-Chain Trust

Anyone can set user.name to yours and commit as "you." Signing cryptographically proves a commit really came from you — increasingly required in regulated and open-source projects.

Sign commits with SSH (simplest) or GPG
# Modern & easy: sign with your existing SSH key
git config --global gpg.format ssh
git config --global user.signingkey ~/.ssh/id_ed25519.pub
git config --global commit.gpgsign true      # sign every commit automatically

git commit -m "feat: signed change"          # now signed
git log --show-signature -1                   # verify
# Add the SSH key as a "Signing Key" in GitHub/GitLab to get the "Verified" badge
Why it matters for a lead engineer

Signed commits + branch protection ("require signed commits") close a real attack vector: a compromised account or malicious contributor spoofing trusted authors. Combined with the image signing in the Docker guide, it forms an end-to-end chain of provenance from commit to running container.

WHY the author field is not proof, and HOW signing fixes it

A commit's "author" is just text you set with user.name/user.email — nothing stops anyone from typing your name and committing as "you." Signing attaches a cryptographic signature made with your private key over the commit's exact contents. Anyone with your public key can verify the signature matches, proving two things: the commit really came from your key, and not a byte has changed since. The host shows a "Verified" badge when the signature checks out against a key you registered.

Mental model: a wax seal on a letter

The author line is like typing a name at the bottom of a letter — trivially forged. A signature is a wax seal pressed with a ring only you own: anyone can check the seal's imprint against your known crest, and a broken seal reveals tampering. It doesn't hide the letter; it proves who sealed it and that it wasn't altered.

Signing gotchas
  • Register the right key type. An SSH signing key must be added to the host as a signing key, not (only) an auth key, to earn "Verified."
  • Verification needs the public key. Others only see a valid signature if your public key is known to them or the host.
  • Signing ≠ enforcement. It only helps if branch protection requires signed commits; otherwise unsigned commits still slip in.

28. Advanced Merge & rerere

Big, long-lived branches mean re-resolving the same conflicts repeatedly. Git can remember and replay your resolutions, and offers smarter merge strategies for tricky cases.

rerere — "reuse recorded resolution"
git config --global rerere.enabled true
# Now when you resolve a conflict, Git records it. If the SAME conflict
# reappears (e.g., during repeated rebases of a long-lived branch),
# Git auto-applies your previous resolution. Huge time-saver.

# Merge strategy options for tricky merges:
git merge -X ours feature       # on conflict, prefer our side (keep merge commit)
git merge -X theirs feature     # on conflict, prefer their side
git merge -X ignore-space-change feature   # ignore whitespace-only conflicts

# See a 3-way view (base | ours | theirs) while resolving:
git config --global merge.conflictStyle zdiff3
zdiff3 conflict markers show the common ancestor

The default conflict markers only show "yours" vs "theirs." Setting merge.conflictStyle = zdiff3 adds the original code in the middle, so you can see what each side changed relative to the common base — far easier to resolve correctly.

HOW rerere remembers a resolution

rerere stands for "reuse recorded resolution." When enabled, the first time you resolve a given conflict Git records a fingerprint of the conflicting hunk plus the resolution you chose. If the identical conflict appears again — which happens constantly when repeatedly rebasing a long-lived branch — Git recognizes the fingerprint and re-applies your earlier fix automatically, so you resolve painful conflicts once instead of every rebase.

Mental model: autocorrect for conflicts

The first time you correct a specific "mistake," Git writes it in a personal dictionary. Next time the same conflict shows up, it fills in your answer the way autocorrect fixes a word you've corrected before — you just review and continue.

rerere gotchas
  • Enable it before you need it. rerere only helps conflicts that occur after you turn it on; it can't recall resolutions it never recorded.
  • It replays your exact choice. If your original resolution was wrong, it will confidently re-apply the wrong fix — verify with git rerere diff.
  • Only identical conflicts match. Slightly different surrounding context is treated as a new conflict.

29. Large Repos & Maintenance

Repositories accumulate cruft: giant binaries in history, thousands of stale refs, bloated packs. Keep them fast with maintenance and the right tools.

Health, cleanup & large files
git maintenance start          # enable background gc, commit-graph, prefetch
git count-objects -vH          # repo size / object count
git gc --aggressive --prune=now# manual deep cleanup (careful, slow)

# Big files bloat clones. Use Git LFS for binaries/assets:
git lfs install
git lfs track "*.psd" "*.zip"
git add .gitattributes

# Purge a huge file / secret from ALL history (rewrites history!):
# preferred modern tool: git-filter-repo
git filter-repo --path secrets.env --invert-paths
History rewriting is destructive on shared repos

git filter-repo and filter-branch rewrite every affected commit's hash. Everyone must re-clone, and open PRs break. Only do this for genuine emergencies (leaked secrets, accidental huge blobs), coordinate with the whole team first, and rotate any leaked credential regardless — removing it from history does not un-leak it.

Scaling to very large monorepos

For repos with millions of files, enable partial clone (--filter=blob:none), sparse-checkout, the commit-graph file, and fsmonitor (git config core.fsmonitor true) so status/diff stay instant. Microsoft's Scalar (now built into Git via git maintenance) bundles these optimizations.

HOW Git stores objects — and why gc exists

Each new object starts life "loose" — one file per object in .git/objects, individually zlib-compressed. As these pile up, Git periodically runs garbage collection (git gc): it bundles loose objects into a packfile, stores similar objects as space-saving deltas against one another, builds the commit-graph, and prunes unreachable objects past their grace period. That's why a repo can shrink dramatically after gc, and why old commits linger recoverably until pruning.

Mental model: tidying a garage

Loose objects are groceries dumped on the garage floor after each shopping trip. git gc is the weekend tidy-up: it packs everything neatly into labelled boxes (packfiles), stacks similar items to save space (deltas), and throws out genuine trash whose expiry has passed (prune). Everything still there is easier and faster to find afterward.

30. Branching Strategies

How a team branches and merges shapes its whole delivery flow. There are three dominant models — choosing the right one for your release cadence is a real engineering decision.

StrategyHow it worksBest for
Trunk-BasedCommit small changes to main often, behind feature flags; branches live hoursHigh-performing teams doing continuous deployment (what DORA/Accelerate recommends)
GitHub Flowmain is always deployable; short feature branches → PR → merge → deployMost teams; simple, works great with CI/CD & GitOps
GitFlowLong-lived develop, plus release/* and hotfix/* branchesVersioned software with scheduled releases (desktop apps, libraries)
The research-backed recommendation

The Accelerate / DORA research (see the CI/CD guide) found that trunk-based development with short-lived branches correlates with elite delivery performance. For most teams, GitHub Flow (a lightweight version) is the sweet spot: main always deployable, small PRs merged quickly, deploy on merge. Avoid GitFlow's heavyweight long-lived branches unless you genuinely ship versioned releases — long-lived branches cause painful merges (which is exactly what rerere and frequent integration mitigate).

WHY branch lifetime is the deciding factor

Strip away the names and every strategy is really answering one question: how long may a branch live before it rejoins main? The longer a branch lives, the more main moves underneath it, and the bigger and riskier the eventual merge (this is "merge debt"). Trunk-based development minimizes lifetime to hours; GitHub Flow keeps it to days; GitFlow deliberately runs long-lived develop/release lines for scheduled releases and pays the integration cost in exchange for release structure.

Mental model: merging traffic onto a highway

Short-lived branches are cars joining a highway one at a time at speed — smooth because gaps are small. A long-lived branch is a car that waited on the on-ramp for an hour: now it must merge into completely different traffic, which is exactly when crashes (big conflicts) happen. "Integrate early and often" is just "don't sit on the on-ramp."

Strategy gotchas
  • GitFlow for a simple web app. Its long-lived branches add ceremony and merge pain most continuously-deployed apps don't need.
  • Trunk-based without tests/flags. Committing straight to main only works if strong automated tests and feature flags keep it deployable.
  • Feature branches that never end. The most common real-world failure — rebase/merge main in regularly to avoid a giant final merge.

31. Disaster Recovery with Git

"I think I lost my work" is rarely true in Git — almost everything is recoverable. Knowing these commands turns panic into a two-minute fix.

Recovering from common disasters
# Recover a "lost" commit after a bad reset/rebase — reflog remembers everything
git reflog                            # find the SHA you were at before the mistake
git reset --hard <good-sha>            # or: git checkout -b recovered <good-sha>

# Undo the last commit but KEEP the changes (redo it properly)
git reset --soft HEAD~1

# You committed to the wrong branch
git reset --soft HEAD~1               # undo commit, keep changes staged
git stash && git switch right-branch && git stash pop

# Recover a deleted branch (reflog knows its tip)
git reflog | grep <branch-name>
git branch <branch-name> <sha>

# Find WHO/WHEN a bug was introduced
git bisect start; git bisect bad; git bisect good <old-sha>   # binary search
git blame -L 40,60 file.py            # who last changed these lines

# Restore a single file from another commit
git checkout <sha> -- path/to/file
The reflog is your time machine

Git keeps a private log of everywhere HEAD has been — every commit, checkout, reset, rebase — in the reflog, even "deleted" commits, for ~90 days. So a "catastrophic" git reset --hard that seemed to destroy your work almost never did: git reflog shows the SHA you were on, and you jump right back. Internalize this and you'll never fear experimenting with Git again.

The one truly dangerous case

Uncommitted, unstaged changes are not in Git's history, so git reset --hard or git checkout that discards them is genuinely unrecoverable. Commit or git stash work-in-progress before running destructive commands. Once something is committed (even to a deleted branch), the reflog can bring it back.

WHY almost everything is recoverable — reachability

Git only ever deletes objects that are unreachable (no branch, tag, or reflog entry points to them) and older than the prune grace period. Because the reflog holds a pointer to every commit HEAD ever touched, a "deleted" commit stays reachable — and therefore recoverable — for weeks. The single exception is content you never turned into an object at all: uncommitted, unstaged working-directory edits. Nothing points to them, so a destructive command leaves nothing to recover.

Find truly orphaned commits with fsck
git fsck --lost-found            # list dangling commits/blobs not on any branch
git show <dangling-sha>          # inspect one
git branch recovered <dangling-sha>   # rescue it onto a branch
Mental model: the recycle bin vs the shredder

Committed work goes to a recycle bin (reflog) that keeps items for weeks — you can fish anything back out. Uncommitted work you destroy with reset --hard or clean -f goes straight through the shredder — there's no bin. The lesson every recovery reinforces: commit (or stash) before you experiment, and the shredder can't hurt you.

32. Best Practices

The habits that separate smooth Git users from frustrated ones.

The essential habits
  • Commit small & often — each commit one logical change; easy to understand and undo.
  • Write clear messages — imperative summary line explaining why ("Fix null crash on empty email").
  • Branch per task — never build directly on main; keep main always working.
  • Pull before you start & before you push — build on the latest; avoid big merges.
  • Use .gitignore — keep secrets, dependencies, and build junk out of the repo.
  • Never commit secrets — and if you do, rotate them immediately.
  • Review via Pull Requests — catch problems before they hit main.
  • Only rewrite history that's still private — merge (not rebase) once shared.
  • Run git status constantly — always know where you stand.

33. Troubleshooting Playbook

The scary situations every Git user eventually hits — and the exact way out. Most "disasters" are recoverable.

🔧 "Help!" — common situations & fixes

Made a typo in the last commit messagegit commit --amend -m "Correct message" (only if not pushed).

The universal calming truth

If you have committed your work, you can almost certainly get it back — via git reflog, git revert, or branch recovery. The only work Git can't save is what you never committed and then destroyed with reset --hard, checkout, or clean -f. So when in doubt: commit first, experiment second.
