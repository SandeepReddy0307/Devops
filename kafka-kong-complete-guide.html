Messaging & API Gateways: The Complete Guide

Two pillars of modern distributed systems: Apache Kafka for event streaming that decouples your services, and Kong for the API gateway that fronts them — from core concepts to production operations, with diagrams.

📖 How to read this guide

Part 2 covers Kafka (async communication between services); Part 3 covers Kong (managing the APIs clients call). Both are common in microservice architectures. Each concept: what, why, config, ★ best practice. Builds on the Kubernetes and Observability guides.

1. Why Messaging & Async Communication?

When services call each other directly (synchronously), one slow or down service breaks the chain. Messaging decouples them: producers drop messages, consumers pick them up when ready.

Messaging = a post office, not a phone call

A synchronous API call is a phone call: both parties must be available right now. Messaging is the postal system: you drop a letter in the box and go on with your day; the recipient reads it whenever they're ready. If they're on holiday, the letters wait — nothing breaks. This is why event-driven systems handle spikes and failures so gracefully.

Why async exists — the failure math

In a synchronous chain A → B → C, the availability of the whole request is the product of each link. If each service is up 99.9% of the time, three in series give 0.999³ ≈ 99.7% — and every extra hop makes it worse. Worse, latency adds up and a slow C holds a thread open in B and A, so one slow dependency exhausts connection pools and topples the whole chain (a "retry storm"). Async breaks this coupling: the producer's success no longer depends on the consumer being up at that instant.

How it works under the hood

A broker persists the message to durable storage (disk/replicated log) the moment it is accepted, then acknowledges the producer. The producer's job is done — it doesn't wait for anyone to process the message. The consumer polls (or is pushed) later and processes at its own pace. Between the two sits a buffer: during a traffic spike the broker absorbs the backlog (this is "load leveling" or "peak shaving") and the consumer drains it steadily instead of falling over.

Worked example — smoothing a spike

Suppose checkout emits 5,000 orders/sec during a flash sale but the fulfillment service can only process 800/sec. Synchronously, 4,200 requests/sec fail. With a broker in between, all 5,000/sec are accepted and stored; fulfillment drains the backlog over the next few minutes. No orders lost, no cascading failure — just a temporary, visible lag you can monitor.

Common mistakes with async
  • Assuming async = instant. Messages are eventually consistent; a read right after a write may not see the effect yet. Design UIs and APIs for that lag.
  • No dead-letter path. A message that always fails to process will retry forever and block progress. Route repeated failures to a dead-letter topic/queue.
  • Fire-and-forget everything. Not all calls should be async — a login that must return a token is inherently synchronous. Use async for work that can complete later.

2. Queues vs Streams

Queue (e.g., RabbitMQ, SQS)Stream / Log (e.g., Kafka)
Message lifeDeleted once consumedRetained for a period; many can re-read
ConsumersCompete for messages (one gets each)Independent groups each read all messages
ReplayNoYes — rewind to any offset
Best forTask/work distributionEvent sourcing, analytics, multiple consumers, high throughput

Why two models exist

They answer different questions. A queue answers "who does this piece of work?" — a message is a command that should be handled once, then it's gone. A stream/log answers "what happened?" — a message is a fact that stays on the record so any number of independent readers (now or in the future) can react to it. Confusing the two is the root of most messaging design mistakes.

How each works under the hood

A classic queue tracks per-message state: unacked → delivered → acked → deleted. The broker hands a message to one worker, waits for an ack, and removes it. If the worker dies before acking, the message is redelivered. A log does the opposite: it never mutates or deletes on consumption. Instead, each consumer group stores a single number — its offset (a bookmark). "Consuming" just advances the bookmark; the data stays until a retention policy expires it. That's why a log can serve many groups and support replay, while a queue cannot.

Worked example — the same event, two models

An OrderPlaced event needs to (1) charge the card, (2) update inventory, (3) email the customer, (4) feed analytics. With a queue you'd need four separate queues and the producer must know all four consumers. With a log (Kafka), the producer writes OrderPlaced once to the orders topic and four independent consumer groups each read it — you can add a fifth (fraud scoring) tomorrow without touching the producer.

Common mistakes
  • Using a log as a work queue naively. Kafka distributes work by partition, not per-message, so a single slow message blocks its whole partition (no per-message redelivery like RabbitMQ).
  • Using a queue when you need replay. Once a queue message is acked it's gone; you cannot re-derive state or onboard a new consumer against history.
To-do list vs logbook

A queue is a shared to-do list: whoever grabs a task crosses it off and it's gone. A stream is a logbook: every entry stays written forever, and any number of people can read the whole book from wherever they left their bookmark. Pick a to-do list for dividing up work; pick a logbook for broadcasting facts that many parties care about.

3. What is Kafka?

Apache Kafka is a distributed event streaming platform — think of it as a massive, durable, replayable append-only log that many producers write to and many consumers read from, at enormous scale.

Kafka's superpower: the durable log

Unlike a queue that deletes messages after delivery, Kafka keeps events for a configured retention (hours to forever). New consumers can read history from the start; a buggy consumer can be fixed and replay. This makes Kafka the backbone for event-driven microservices, real-time analytics, and data pipelines.

Why Kafka is fast — the append-only log on disk

People assume disks are slow, but sequential disk writes are extremely fast — often faster than random memory access — because the OS batches them and the disk head never seeks. Kafka exploits this: every write is an append to the end of a segment file, never a random insert or update. Reads are also sequential (consumers read forward from an offset). Kafka further uses the OS page cache (so hot data is served from RAM without a JVM copy) and zero-copy (sendfile) to ship bytes straight from the page cache to the network socket, skipping user space entirely. That's how a single broker handles millions of messages/sec on commodity hardware.

How a partition looks on disk

Inside a partition directory on a broker
$ ls -1 /var/lib/kafka/data/orders-0/
00000000000000000000.log     # segment: the actual appended records
00000000000000000000.index   # offset -> byte position (sparse index)
00000000000000000000.timeindex# timestamp -> offset (for time-based seeks)
00000000000000114820.log     # next segment once the first rolls over
leader-epoch-checkpoint

A partition is a directory of segment files. New records append to the active .log segment; when it hits segment.bytes or segment.ms, it "rolls" to a new one. Old closed segments are deleted (or compacted) by retention — that's just deleting whole files, which is why cleanup is cheap. The .index maps offsets to byte positions so a consumer can seek to any offset in O(log n) without scanning.

Kafka is an ever-growing notebook, not a whiteboard

A queue is a whiteboard — you write a note, someone reads it and wipes it off. Kafka is a bound notebook: you only ever write on the next blank line, never erase, and everyone reading keeps their own bookmark. Old pages get torn out only when the notebook is "full" (retention), and tearing out whole pages is instant. Because nothing is erased on read, ten different readers can all read the same pages independently.

Common misconceptions
  • "Kafka is a message queue." It's a distributed log. Consumption doesn't delete data; retention does.
  • "Retention = how long until delivery." No — retention is how long data lives regardless of whether it's been read. Set it too low and slow/new consumers lose data before reading it.
  • "More brokers = automatically faster." Throughput scales with partitions, not just brokers. A one-partition topic won't go faster on a 10-broker cluster.

4. Topics, Partitions & Offsets

These three concepts are Kafka. Understand them and everything else follows.

TermMeaning
TopicA named stream of events (like a table/category)
PartitionA shard of a topic; the unit of parallelism & ordering
OffsetA message's sequential position within a partition
KeyDetermines the partition → guarantees same-key ordering
BrokerA Kafka server; a cluster has many, holding partition replicas

Why partitions exist

A single ordered log can only be written and read as fast as one machine allows. Partitioning splits a topic into N independent logs so N brokers can accept writes and N consumers can read in parallel — that's the only knob that scales Kafka horizontally. The trade-off: Kafka guarantees order within a partition, never across partitions. So partitioning is really a choice about "what must stay ordered together?"

How keys map to partitions

The producer decides the partition. With no key it round-robins (or sticky-batches) for even spread. With a key it computes partition = murmur2(key) % numPartitions, so the same key always lands on the same partition and therefore stays ordered. This is how you get per-entity ordering: key by customer_id and every event for a customer is processed in order, while different customers spread across partitions for parallelism.

See offsets and where messages land

kafka-console-producer.sh --topic orders --bootstrap-server localhost:9092 \
  --property parse.key=true --property key.separator=:
>cust-42:{"item":"book"}
>cust-42:{"item":"pen"}

# Inspect earliest/latest offsets per partition
kafka-run-class.sh kafka.tools.GetOffsetShell \
  --broker-list localhost:9092 --topic orders
Result — offsets are per-partition
orders:0:0        # partition 0 is empty (latest offset 0)
orders:1:2        # partition 1 has 2 records (both cust-42, in order)
orders:2:0
# Both cust-42 events hashed to partition 1 -> guaranteed ordered
Partitions = checkout lanes; the key = your loyalty card

A topic is a supermarket; partitions are its checkout lanes. More lanes = more shoppers served at once. The key is like a rule that says "customer #42 always uses lane 3" — so all of #42's items are rung up in the exact order they arrived, while other customers use other lanes simultaneously. The offset is simply the receipt line number in that lane.

Common mistakes & gotchas
  • Too few partitions. Partition count caps consumer parallelism forever. You can add partitions later, but that changes key % N so existing keys may move — breaking per-key ordering. Plan for peak up front.
  • Too many partitions. Each partition costs file handles, memory, and leader-election time. Tens of thousands cluster-wide slows failover. Right-size, don't max out.
  • Hot key / skew. If one key (e.g. a single huge tenant) dominates, its partition becomes a bottleneck while others idle. Consider a composite key or salting.
  • Expecting global ordering. Order holds only within a partition. If you truly need total order, you're limited to one partition (and thus one consumer).

5. Producers & Consumers

The key is a "keep these together" label

Imagine sorting mail into a fixed set of pigeonholes. The key is the rule for which hole a letter goes in — all letters for "user-42" always drop in the same hole, so they arrive in the order you sent them. Leave the key blank and the sorter just spreads letters evenly to keep every hole busy. That's why you set a key when per-entity ordering matters (e.g., all events for one account) and skip it when you only care about throughput.

Choosing a partition key

Pick a key with high cardinality and even distribution (e.g., userId, orderId). A low-cardinality key like country creates "hot" partitions where one broker does most of the work. If you change the partition count later, the hash mapping shifts and ordering guarantees only hold for messages sent after the change — plan capacity up front.

Try it with the console tools
# Create a topic with 3 partitions
kafka-topics.sh --create --topic orders --partitions 3 --replication-factor 3 \
  --bootstrap-server localhost:9092

# Produce messages
kafka-console-producer.sh --topic orders --bootstrap-server localhost:9092

# Consume from the beginning
kafka-console-consumer.sh --topic orders --from-beginning \
  --bootstrap-server localhost:9092

Why producers batch and consumers poll

Sending one network request per message would waste most of the bandwidth on protocol overhead. So the producer accumulates records in memory per-partition and flushes a batch when it reaches batch.size or after linger.ms — trading a few milliseconds of latency for a huge throughput win. On the other side, consumers pull (poll) rather than being pushed. Pull lets each consumer read at its own pace (natural backpressure — a slow consumer just polls less) and fetch large batches efficiently, instead of the broker guessing how fast each consumer can go.

How a produce request flows under the hood

Lifecycle of a single send()
1. producer.send(record)   -> serialize key/value, pick partition (key hash)
2. append to in-memory batch for that partition (returns a Future immediately)
3. sender thread groups batches by broker, sends when linger.ms/batch.size hit
4. leader broker appends to its log, waits for replicas per 'acks'
5. broker returns the assigned OFFSET -> Future completes (callback fires)
   on error: retry (safe if enable.idempotence=true), else callback gets error

The consumer side is a loop: poll() returns a batch, you process it, then you commit the offset to say "I've handled up to here." Where you commit relative to processing is exactly what decides your delivery guarantee (§7).

Worked example — tune for throughput

For a high-volume pipeline, set linger.ms=20, batch.size=64KB, and compression.type=lz4. Batching + compression can cut network bytes 5–10× and multiply throughput, at the cost of ~20 ms extra latency — usually a great trade for streaming workloads.

Common mistakes
  • Ignoring the send callback / Future. send() is async; if you never check the result you'll silently drop failed messages.
  • Blocking the poll loop. Long processing between poll() calls exceeds max.poll.interval.ms, so Kafka thinks the consumer died and rebalances — causing duplicate processing and lag.
  • Creating a producer per message. Producers are thread-safe and meant to be long-lived and shared; recreating them destroys batching and hammers connections.
Producer = mailer, consumer = someone checking their mailbox

The producer doesn't hand-deliver each letter; it drops a stack into the post box (batching). The consumer isn't interrupted for every letter — it walks to the mailbox when it's ready and grabs whatever arrived (polling). Committing an offset is like moving a sticky note that says "read up to here," so if you step away and come back you don't reread old mail.

6. Consumer Groups & Scaling

A consumer group lets you scale processing: Kafka distributes a topic's partitions across the group's members so each message is processed once by the group.

Partitions cap your parallelism

You can't have more active consumers in a group than partitions — extras sit idle. Choose partition count with future scale in mind (increasing partitions later changes key→partition mapping and can break ordering). A common starting point is a partition per expected peak consumer.

Why consumer groups exist

A single consumer can't always keep up with a busy topic, and you also want fault tolerance — if a consumer crashes, someone else must pick up its partitions. A consumer group solves both: it's a set of consumers that collectively read a topic, with Kafka guaranteeing each partition is owned by exactly one member at a time. Add members to scale out; lose one and its partitions are reassigned automatically. Different groups (different group.id) are fully independent and each get the whole stream.

How rebalancing & offset commits work under the hood

Each group has a broker acting as its group coordinator. Members send periodic heartbeats. When membership changes (a consumer joins, leaves, or misses heartbeats for session.timeout.ms), the coordinator triggers a rebalance: one member becomes leader, computes a new partition→member assignment, and everyone gets their new set. Committed offsets aren't stored on the consumer — they're written to an internal compacted topic called __consumer_offsets, keyed by (group, topic, partition). So when a partition moves to a new owner, that owner reads the last committed offset and resumes exactly where the previous owner left off.

Inspect a group's assignments and lag
kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --describe --group orders-consumers
CURRENT-OFFSET vs LOG-END-OFFSET = LAG
GROUP            TOPIC   PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG  CONSUMER-ID
orders-consumers orders  0          10520           10540           20   consumer-1
orders-consumers orders  1          9980            9980            0    consumer-1
orders-consumers orders  2          8000            9500            1500 consumer-2  <- falling behind

LAG = how many messages are produced but not yet consumed on that partition. It is the single most important health signal: flat/zero lag is healthy; steadily rising lag means consumers can't keep up.

Rebalance storms & the "stop-the-world" pause

During a classic (eager) rebalance, all members stop consuming while partitions are reassigned — a brief outage. If processing exceeds max.poll.interval.ms, the coordinator evicts that consumer, triggering yet another rebalance, which slows everyone, which causes more evictions — a rebalance storm. Fixes: keep per-batch processing short (or reduce max.poll.records), and enable cooperative-sticky assignment (partition.assignment.strategy=CooperativeStickyAssignor) so only the moving partitions pause, not the whole group.

A group is a delivery team sharing streets

Think of one topic as a city and partitions as its streets. A consumer group is a delivery team; each street is assigned to exactly one driver so no house gets two deliveries. If a driver quits, the dispatcher (coordinator) reshuffles the streets among the rest — that reshuffle is a rebalance. Each driver keeps a note of the last house done on each street (the committed offset) so a replacement resumes from there, not from the start.

7. Delivery Guarantees

GuaranteeMeaningCost
At-most-onceMay lose messages, never duplicatesFastest
At-least-onceNever loses, may duplicateDefault; needs idempotent consumers
Exactly-once (EOS)No loss, no duplicatesSlowest; needs transactions/idempotent producer
Design consumers to be idempotent

Most systems run at-least-once, so duplicates will happen. Make processing idempotent — key on an event ID and skip if already processed (upsert, dedup table). This is simpler and more robust than chasing full exactly-once semantics.

Why the guarantee is decided by commit order, not a setting

The three guarantees aren't a single flag — they emerge from when you commit the offset relative to doing the work. Commit before processing and a crash loses the message (at-most-once). Commit after processing and a crash re-delivers it (at-least-once). Making the process-and-commit a single atomic unit gives exactly-once.

The two orderings that decide everything
# AT-MOST-ONCE  (commit first -> may lose)
records = poll()
commit()                 # <-- crash here: work never done, but offset advanced
process(records)         # message lost

# AT-LEAST-ONCE (process first -> may duplicate)  [DEFAULT, recommended]
records = poll()
process(records)         # <-- crash here: offset NOT advanced, so redelivered
commit()                 # same message processed twice -> must be idempotent
Worked example — an idempotent consumer

Give every event a unique event_id. On the consumer, do an upsert keyed by it:

SQL dedupe on a business key
INSERT INTO processed_orders (event_id, order_id, amount)
VALUES (:event_id, :order_id, :amount)
ON CONFLICT (event_id) DO NOTHING;   -- second delivery is a no-op

Now a duplicate delivery is harmless — you get at-least-once delivery with effectively exactly-once effect, without transactions.

Common mistakes & gotchas
  • Auto-commit + slow processing. enable.auto.commit=true commits on a timer regardless of whether processing finished — silently mixing at-most-once behavior in. For real control, commit manually after processing.
  • Assuming no duplicates. Even with retries disabled, a rebalance right before a commit re-delivers the batch. Duplicates are a when, not an if — always dedupe.
  • Side effects that aren't idempotent. Sending an email or charging a card twice is a real bug. Guard those with an idempotency key / dedupe table.
Crossing off the to-do list too early vs too late

Imagine a chore list where you cross off items as you do them. Cross off before doing the chore and if you get interrupted, it never gets done (at-most-once). Cross off after and if you're interrupted mid-chore, you'll redo it later (at-least-once). Doing the chore and crossing it off in one indivisible motion is exactly-once — harder to arrange, which is why most people just make chores safe to redo.

8. Running Kafka in Production

KRaft replaces ZooKeeper

Older Kafka needed a separate ZooKeeper cluster for coordination. Modern Kafka (3.x+) uses KRaft mode — self-managed metadata, no ZooKeeper — simpler to operate. New clusters should use KRaft.

Production essentials
  • Replication factor 3 and min.insync.replicas=2 so you survive a broker loss without data loss.
  • Spread brokers across AZs.
  • Monitor consumer lag (how far behind consumers are) — the #1 health metric (see Observability).
  • On Kubernetes, use the Strimzi operator; on AWS, consider MSK (managed Kafka) to offload ops.
  • Set retention deliberately (size/time) — it drives storage cost.

Why KRaft replaced ZooKeeper

ZooKeeper was a separate distributed system Kafka depended on to store metadata (which broker leads which partition, ACLs, configs). That meant two clusters to operate, two failure domains, and metadata changes bottlenecked on ZooKeeper writes — limiting how many partitions a cluster could hold. KRaft folds metadata management into Kafka itself: a small quorum of controller brokers runs the Raft consensus protocol and stores metadata in an internal Kafka log. Fewer moving parts, faster failover, and clusters that scale to millions of partitions.

Worked example — a durable topic that survives a broker loss
Create with production-grade durability
kafka-topics.sh --create --topic payments \
  --partitions 12 --replication-factor 3 \
  --config min.insync.replicas=2 \
  --config retention.ms=604800000 \
  --bootstrap-server localhost:9092

# Verify replica placement & ISR
kafka-topics.sh --describe --topic payments --bootstrap-server localhost:9092
Leader + replicas + ISR per partition
Topic: payments  Partition: 0  Leader: 1  Replicas: 1,2,3  Isr: 1,2,3
Topic: payments  Partition: 1  Leader: 2  Replicas: 2,3,1  Isr: 2,3,1
# Isr lists all 3 -> fully replicated; can lose 1 broker with zero data loss
Common production mistakes
  • Replication factor 1. Fine for a laptop, catastrophic in prod — one broker dies and that data is gone forever.
  • All brokers in one AZ/rack. A single rack or AZ failure takes down every replica. Spread replicas with rack awareness.
  • Not monitoring consumer lag / under-replicated partitions. These are your earliest warning signs; without them you learn of trouble from users.
  • Unbounded retention by default. Disks fill up silently; a full disk takes a broker offline. Set retention and alert on disk usage.
Running Kafka = running a warehouse chain, not one shed

Production Kafka is like a chain of warehouses in different neighborhoods (AZs), each keeping copies of the same goods (replicas) so a fire in one doesn't lose inventory. KRaft is the head office that tracks who stores what — modern Kafka keeps that head office in-house instead of outsourcing it to a separate company (ZooKeeper). And you always watch the loading-dock backlog (consumer lag) to know if you're falling behind.

9. Kafka Ecosystem

ToolPurpose
Kafka ConnectNo-code connectors to sync data in/out (databases, S3, Elasticsearch)

Use a Schema Registry from day one

Without schemas, one producer changing a field silently breaks every consumer. A Schema Registry enforces compatibility rules (backward/forward), so message contracts evolve safely — the messaging equivalent of API versioning.

Why the ecosystem exists

Raw Kafka only moves bytes. Real systems also need to get data in and out without hand-writing plumbing (Connect), transform streams (Streams/ksqlDB), keep producers and consumers compatible as messages evolve (Schema Registry), and span regions (MirrorMaker). Each tool exists so you don't reinvent a fragile, bespoke version of it.

How schema compatibility works under the hood

With Avro/Protobuf, the producer registers its schema and the registry returns a numeric schema ID. The message on the wire is just [magic-byte][4-byte schema ID][binary payload] — the schema itself isn't shipped with every message, saving bandwidth. Consumers fetch the schema by ID (and cache it) to deserialize. Before accepting a new schema, the registry checks it against the configured compatibility rule (e.g. backward: new consumers can read old data). If a change would break readers, registration is rejected — the break is caught at deploy time, not at 3am in production.

Worked example — a rejected incompatible change
Adding a required field with no default (backward-incompatible)
{ "type":"record","name":"Order","fields":[
    {"name":"id","type":"int"},
    {"name":"currency","type":"string"}   // NEW, no default -> old data can't fill it
]}
Registry refuses to register it
409 Conflict: Schema being registered is incompatible with an earlier schema
  (reader/writer compatibility: BACKWARD) — field 'currency' has no default
# Fix: give it a default -> {"name":"currency","type":"string","default":"USD"}
Common mistakes
  • No schema governance. JSON with no registry means every field rename is a silent, delayed outage in some downstream consumer.
  • Running Connect workers under-provisioned. Connect is a distributed system too — too few tasks or workers throttles CDC and lets source lag build.
  • Treating MirrorMaker as instant DR. Cross-cluster replication is async; offsets differ between clusters, so failover needs an offset-translation plan.
The ecosystem = the accessories that make the log useful

If Kafka is a conveyor belt, Connect is the loading/unloading robots at each end, Streams/ksqlDB are the workers sorting and combining items as they pass, and the Schema Registry is the quality inspector making sure every box is labelled in a format the next station understands. The belt alone moves things; the accessories make it a factory.

10. What is an API Gateway?

An API gateway is a single front door for all your APIs. Instead of clients calling dozens of microservices directly, they hit the gateway, which routes, authenticates, rate-limits, and observes every request.

API gateway = the reception desk of a building

Visitors don't wander the building looking for the right office. They check in at reception, which verifies their ID (auth), enforces visitor limits (rate limiting), and directs them to the correct floor (routing). The gateway is that reception desk for your APIs — one place that handles security and traffic control so every office (service) doesn't have to.

Why a gateway exists — the alternative is duplication

Every API needs the same cross-cutting concerns: authentication, TLS, rate limiting, CORS, logging, tracing, request size limits. Without a gateway you implement all of that in every microservice, in every language, and it drifts out of sync — one service forgets to check auth and you have a breach. A gateway centralizes these concerns at the edge so services only implement business logic, and security policy is enforced consistently in one place you can audit.

How a gateway processes one request under the hood

The request pipeline (phases run in order)
1. Accept TCP + terminate TLS        (decrypt HTTPS once, at the edge)
2. Match ROUTE                       (host + path + method -> which service?)
3. Run request plugins in order:
     a. auth        -> verify API key / JWT; reject 401 if invalid
     b. rate-limit  -> check & increment this client's counter; 429 if over
     c. transform   -> add/strip headers, rewrite path
4. Load-balance + PROXY to a healthy upstream instance
5. Receive upstream response, run response plugins (CORS, logging, metrics)
6. Return to client + emit trace/metrics

Rate limiting is just a counter per client per window: the gateway keeps requests_this_minute[client] (in memory or in Redis for a shared count across nodes) and rejects with 429 Too Many Requests once it exceeds the limit — protecting your services from being overwhelmed by any single caller.

Common mistakes
  • Business logic in the gateway. The gateway is for cross-cutting concerns. Putting domain logic there creates a fragile, hard-to-test monolith at your edge.
  • Gateway as a single point of failure. If everything flows through it, run it highly available (multiple replicas) or a total outage takes down all APIs.
  • Trusting the gateway as the only security layer. If an attacker reaches a service directly (inside the network), gateway auth is bypassed. Keep service-level checks too (defense in depth).

11. Kong Architecture

Kong is a popular open-source API gateway built on NGINX. Requests flow through Kong, which applies plugins before proxying to your upstream services.

ConceptWhat it is
ServiceAn upstream API Kong proxies to (your microservice)
RouteRules (path, host, method) that map incoming requests to a Service
PluginMiddleware adding behavior (auth, rate-limit, logging, transforms)
ConsumerAn identified API client (for auth & per-client limits)
Upstream / TargetLoad-balancing across backend instances
DB-less & declarative

Kong can run DB-less: its whole config lives in a YAML file (declarative config), version-controlled in Git and applied on deploy — GitOps-friendly and simple. The alternative (Postgres-backed) suits dynamic, admin-API-driven setups. For Kubernetes, config is driven by CRDs (§14).

Why Kong is built on NGINX + Lua

NGINX is already a battle-tested, event-driven proxy that handles tens of thousands of concurrent connections efficiently. Rather than reinvent a proxy, Kong embeds OpenResty (NGINX + LuaJIT) and implements its logic as Lua that runs inside NGINX's request lifecycle. That's why plugins hook into distinct phases (access, header_filter, body_filter, log) — they're literally callbacks NGINX invokes as it processes the request. You inherit NGINX's performance for free and add programmable behavior on top.

12. Services, Routes & Plugins

Service, Route, Plugin — how they fit

A Service is an upstream (where to send traffic). A Route is the match rule (host/path/method) that maps an incoming request to a Service. A Plugin attaches behavior — and can be scoped globally, to a Service, to a Route, or to a Consumer, from broadest to narrowest. When the same plugin is configured at several scopes, the most specific one wins, which is how you set a global default and override it for one noisy route.

DB-less declarative config (kong.yml)
_format_version: "3.0"
services:
  - name: orders-service
    url: http://orders-svc.default.svc:8080
    routes:
      - name: orders-route
        paths: ["/api/orders"]
    plugins:
      - name: rate-limiting
        config: { minute: 100, policy: local }
      - name: key-auth        # require an API key

Why this three-object model

Separating Route (match) from Service (destination) from Plugin (behavior) means each can change independently: point a route at a new service version without touching plugins; attach the same rate-limit plugin to ten routes; or move a plugin from one route to all routes (global) in one edit. It's the same separation-of-concerns that keeps the config understandable as it grows to hundreds of APIs.

How plugin scope resolves

A plugin can be attached at four scopes; when the same plugin type applies at multiple scopes, the most specific wins: Consumer+Route > Route > Service > Global. So you can set a lenient global rate limit and override it with a stricter one on a sensitive route, or a looser one for a trusted consumer.

The gateway's biggest value: enforcing security consistently. Kong ships plugins for the common needs.

Defense in depth

Authenticate at the gateway and keep service-level checks — the gateway is a front door, not the only lock. Rate-limit per consumer to stop one client starving others. Terminate TLS at the gateway and use mTLS (or a service mesh) for internal hops. Emit metrics/traces for every request.

Why enforce security at the edge

Auth and rate limiting must be applied before a request reaches your services — otherwise unauthenticated or abusive traffic already consumed backend resources. The gateway is the earliest, cheapest place to reject bad requests, and doing it in one audited place beats trusting every service to get it right.

How rate limiting actually counts

The simplest algorithm is a fixed window: a counter per (consumer, minute) that resets each minute. It's cheap but allows bursts at window edges (nearly 2× the limit across a boundary). A sliding window smooths this by weighting the previous window. In a multi-node Kong cluster, the counter must be shared — that's why policy: redis stores it centrally so all nodes agree; policy: local keeps a per-node count (faster but the real limit becomes limit × node-count).

Common mistakes & gotchas
  • Rate-limiting by IP behind a load balancer. All traffic appears to come from the LB's IP, so you throttle everyone together. Limit by consumer/API key, and trust X-Forwarded-For only from your own LB.
  • API keys in query strings. They leak into logs and browser history. Prefer headers, and use JWT/OIDC for anything sensitive.
  • Global-only limits. One noisy client can still exhaust the shared budget. Layer per-consumer limits under the global one.
  • Terminating TLS but leaving internal hops plaintext. Anyone inside the network can sniff traffic — use mTLS or a mesh for east-west encryption.
Auth = the ID check; rate limit = the ticket counter

15. Replication, ISR & Durability

Kafka's durability guarantees come from replicating each partition across brokers. Understanding leaders, followers, and the in-sync replica set (ISR) is what lets you configure Kafka to never lose data.

ISR = the "trusted backups" that are fully caught up

Imagine a document with a main author (leader) and copiers (followers) keeping duplicate copies. The in-sync replicas are the copiers whose copy is fully up to date. If the main author vanishes, you promote a fully-caught-up copier — nothing is lost. A copier that's fallen behind is dropped from the trusted set until it catches up. acks=all means "don't confirm my write until all trusted copiers have it" — maximum safety.

Durability configuration that survives a broker loss
# Producer side
acks: all                 # wait for all in-sync replicas to ack (no data loss)
enable.idempotence: true  # no duplicates on producer retries
retries: 2147483647       # retry indefinitely (with idempotence, safe)

# Topic / broker side
replication.factor: 3     # 3 copies of every partition
min.insync.replicas: 2    # require >=2 in-sync; refuse writes if fewer
unclean.leader.election.enable: false  # never promote an out-of-sync replica
The acks + min.insync.replicas contract

With replication.factor=3, min.insync.replicas=2, and producer acks=all: you can lose one broker and still accept writes with zero data loss. Lose two and Kafka correctly refuses writes rather than risk losing data. Set unclean.leader.election=false so a stale replica is never promoted (which would silently lose messages). This trio is the heart of Kafka durability.

How replication works step by step

All reads and writes for a partition go to its leader. Followers are just consumers of the leader: each follower issues fetch requests and appends the records to its own log. The leader tracks each follower's progress via its log-end offset. A follower is "in-sync" (in the ISR) if it has fetched up to the leader within replica.lag.time.max.ms. The leader advances the high-water mark (the highest offset all ISR members have) — and consumers can only read up to the high-water mark. That's the invariant that makes failover safe: anything a consumer has seen is already on every in-sync replica.

How failover picks a new leader

Leader dies — an ISR member is promoted
Before:  P0  Leader=1  Isr=[1,2,3]  HW=10540
Broker 1 crashes
Controller: elect new leader from ISR (must be in [2,3]) -> picks 2
After:   P0  Leader=2  Isr=[2,3]    HW=10540   # no data loss: 2 had everything up to HW
Broker 1 returns -> catches up from leader -> rejoins Isr=[2,3,1]

Because the new leader must come from the ISR, it already holds every acknowledged message — so promotion loses nothing. Allowing out-of-sync replicas to be promoted (unclean election) is the one setting that trades durability for availability and can silently drop data.

Worked example — watch ISR shrink and recover
Find under-replicated partitions
kafka-topics.sh --describe --under-replicated-partitions \
  --bootstrap-server localhost:9092
A shrunk ISR flags a lagging/dead replica
Topic: payments Partition: 3 Leader: 2 Replicas: 2,3,1 Isr: 2,3
# Replica 1 dropped out of the ISR -> still safe (2 in sync >= min.insync.replicas)
# If ISR falls below min.insync.replicas, acks=all producers get NotEnoughReplicas
Common mistakes & gotchas
  • replication.factor = min.insync.replicas. e.g. both 3 — then losing one broker halts writes. Keep RF > min.insync.replicas (3 and 2).
  • Enabling unclean leader election for "availability." It quietly loses committed data on failover. Leave it false unless you truly prefer availability over correctness.
  • acks=1 with RF=3. The leader acks before followers copy the record; if it dies right after, that message is gone despite having 3 replicas configured.

16. Exactly-Once Semantics (EOS)

"Process each message exactly once, even through failures and retries" is famously hard in distributed systems. Kafka provides it via the idempotent producer plus transactions.

How EOS is achieved
1. Idempotent producer  — each message gets a sequence number; the broker
                          dedupes retries, so a retry never creates a duplicate.
2. Transactions         — produce to multiple partitions + commit consumer
                          offsets atomically ("consume-transform-produce").
3. Isolation level      — consumers set isolation.level=read_committed to
                          only see committed messages.
EOS has a cost — often at-least-once + idempotency is enough

Transactions add latency and complexity and only span Kafka (not an external database, unless you use the transactional outbox pattern). For most systems, at-least-once delivery + idempotent consumers (dedupe on a business key) is simpler and robust. Reserve full EOS for Kafka-to-Kafka stream processing where exactly-once is genuinely required.

How the idempotent producer dedupes retries

When you set enable.idempotence=true, the broker assigns the producer a producer ID (PID) and every record carries a per-partition monotonic sequence number. The broker remembers the last sequence it accepted per (PID, partition). If a network hiccup makes the producer retry a record the broker already stored, the sequence number is a duplicate and the broker silently discards it — returning success without writing twice. That's how retries become safe: no duplicates, and order is preserved.

How transactions make consume-transform-produce atomic

The transactional loop (Streams does this for you)
producer.initTransactions()          // register a transactional.id
while (true) {
  records = consumer.poll()
  producer.beginTransaction()
  producer.send(transformed)                        // output records
  producer.sendOffsetsToTransaction(consumedOffsets, groupMetadata) // input offsets
  producer.commitTransaction()       // output + offset commit land ATOMICALLY
}
// On crash mid-transaction, it aborts: outputs are marked aborted and
// read_committed consumers never see them; offsets aren't advanced -> safe replay.

The key trick: the output messages and the input offset commit are written in one transaction. Either both happen or neither does — so there's no window where output exists but the input looks unprocessed (which would duplicate on replay). Downstream consumers set isolation.level=read_committed so they skip aborted/uncommitted records entirely.

Worked example — turn on EOS in Kafka Streams
One line enables the whole machinery
processing.guarantee=exactly_once_v2
# Streams then manages transactional.id, read_committed, and atomic
# offset+output commits for you — no manual transaction code needed.
Common mistakes & gotchas
  • Thinking EOS covers your database. Transactions are Kafka-only. Writing to Postgres and Kafka atomically needs the outbox pattern (write to an outbox table in the DB txn, then CDC it to Kafka).
  • Reusing one transactional.id across instances. It must be stable-per-partition-assignment; sharing it causes producers to fence each other (ProducerFencedException).
  • Forgetting read_committed downstream. Default is read_uncommitted, so consumers would see aborted records — silently breaking the guarantee.
EOS = numbered receipts + an all-or-nothing signature

The idempotent producer is like putting a serial number on every receipt: if you accidentally hand the cashier the same receipt twice, they notice the number and don't ring it up again. Transactions are like signing a whole batch of paperwork at once — either every page is filed or none is, so you never end up with the "money moved but the ledger wasn't updated" situation.

17. Kafka Streams & ksqlDB

Beyond moving messages, you often need to process them — aggregate, join, window. Kafka Streams (a Java library) and ksqlDB (SQL over streams) do this natively.

Stream processing concepts
# ksqlDB — continuous SQL over a stream
CREATE STREAM orders (id INT, amount DOUBLE, region VARCHAR)
  WITH (kafka_topic='orders', value_format='JSON');

# A continuously-updating aggregation (a "materialized view")
CREATE TABLE revenue_by_region AS
  SELECT region, SUM(amount) AS total
  FROM orders WINDOW TUMBLING (SIZE 1 HOUR)
  GROUP BY region;
ConceptMeaning
StreamUnbounded sequence of events (the topic)
TableCurrent state derived from a stream (latest value per key)
WindowingGroup events by time (tumbling, hopping, session)
Stateful opsJoins & aggregations backed by local state + changelog topics
Stream-table duality

A stream is a log of every change ("+£5, +£3, -£2"); a table is the current total ("£6"). They're two views of the same data: replay a stream and you rebuild the table; capture a table's changes and you get a stream. This duality is the core insight behind stream processing — and why Kafka can rebuild state just by replaying the log.

Why a stream processor instead of a database + cron

The old way to aggregate events was: dump them somewhere, run a batch job every N minutes. That's high-latency and reprocesses everything. A stream processor computes incrementally and continuously — each new event updates the result immediately, so your "revenue by region" is always current, not minutes stale.

How stateful operations survive crashes

Aggregations and joins need state (running totals, join buffers). Kafka Streams keeps that state in a local embedded store (RocksDB) for fast access, but also writes every state change to a changelog topic in Kafka. If the instance crashes and its task moves to another node, that node replays the changelog to rebuild the exact state — so local state is fast but never the source of truth. Windowed operations additionally track event time and a grace period for late-arriving data.

Worked example — a materialized view you can query
Push events and read the live aggregate
# Assuming the CREATE TABLE revenue_by_region above is running:
ksql> SELECT region, total FROM revenue_by_region EMIT CHANGES;
Updates stream out as new orders arrive
+------------+---------+
|REGION      |TOTAL    |
+------------+---------+
|EU          |5.00     |   # after order amount=5
|EU          |8.00     |   # +3, updates in place (table semantics)
|US          |12.50    |
# EMIT CHANGES = a continuous query; the view never "finishes"
Common mistakes & gotchas
  • Ignoring event time vs processing time. Windowing on when Kafka received a record (not when the event happened) skews results when producers lag. Set timestamps + a grace period.
  • Deleting changelog topics to "save space." They're how state is rebuilt after a crash — delete them and a restart loses all aggregation state.
  • Under-provisioning RocksDB memory / disk. Large stateful jobs need real local disk; running them on tiny nodes causes constant restore and stalls.

18. Kafka Connect Deep

Most data doesn't originate in Kafka — it's in databases, files, and SaaS apps. Kafka Connect moves data in and out with no code, using pluggable connectors.

Change Data Capture (CDC) with Debezium

Debezium is a source connector that tails a database's transaction log and emits every insert/update/delete as a Kafka event — without polling or changing the app. This is the standard way to stream a database into Kafka for event-driven architectures, cache invalidation, or replicating data to a search index/warehouse.

Why Connect instead of writing your own producer/consumer

Integrations are 80% the same boilerplate: offset tracking, retries, schema conversion, scaling, restart-after-crash. Connect provides all of that as a reusable framework so a connector author only writes the source/sink-specific bit. You get a fleet of hundreds of tested connectors and a uniform way to run and monitor them, instead of a snowflake integration per system.

How Connect scales and tracks progress under the hood

Connect runs as a cluster of workers. A connector is split into tasks (e.g. one task per table or per partition) and the workers balance tasks among themselves — add a worker and tasks rebalance to it. Progress is stored in internal Kafka topics: connect-offsets (source position, e.g. the DB log position), connect-configs, and connect-status. So if a worker dies, another resumes each task from its last committed source offset — no re-reading the whole database.

Worked example — register a Debezium source via REST
Connect is configured over HTTP

  "name": "orders-cdc",
  "config": {
    "connector.class": "io.debezium.connector.postgresql.PostgresConnector",
    "database.hostname": "pg", "database.dbname": "shop",
    "table.include.list": "public.orders",
    "topic.prefix": "cdc" } }'

curl http://connect:8083/connectors/orders-cdc/status

Common mistakes
  • Running Connect in standalone mode in prod. Standalone has no failover; use distributed mode so tasks survive worker loss.
  • Deleting the internal offset topic. A source connector then restarts from the beginning — re-emitting the entire dataset.
  • Debezium without enough DB WAL retention. If the database recycles its transaction log before the connector reads it, you get gaps; size WAL/replication-slot retention accordingly.
Connect = universal adapters for the conveyor belt

You don't rewire a new plug for every appliance — you use a standard adapter. Connect is a set of standard adapters that snap data sources and sinks onto Kafka. Debezium is a special adapter that quietly watches a database's diary (its transaction log) and announces every change to the belt, without the database app even knowing.

Why these levers, and how they trade off

Kafka tuning is mostly a latency vs throughput vs durability triangle. Bigger batches and linger.ms raise throughput but add latency. Compression trades CPU for network/disk. More replicas and acks=all raise durability but add write latency. There's no universal "fast" setting — you pick the corner of the triangle your workload needs and measure.

How consumer lag reveals health under the hood

Lag = log-end-offset − committed-offset per partition. It's the truest health signal because it directly measures "are we falling behind?" A flat non-zero lag means you're keeping pace with a backlog; steadily rising lag means consumers can't keep up and you must add consumers (up to partition count), speed up processing, or add partitions. Pair it with under-replicated partitions (should be 0) and offline partitions (should be 0) for a complete picture.

  • Encryption without authorization. TLS hides traffic but anyone can still connect — add SASL auth and ACLs so only permitted principals read/write each topic.
  • Alerting only on broker CPU. Brokers can look healthy while consumers drown. Lag, under-replicated, and offline partitions are the signals that catch real user-facing problems.
  • Compression mismatch expectations. gzip compresses hard but burns CPU; lz4/zstd are usually the better throughput trade.
Lag is the queue at the checkout

Consumer lag is like the line at a supermarket till: a short, steady line is fine, but a line that keeps growing means you need more cashiers (consumers) or faster ones. Watching CPU alone is like checking if the lights are on — the growing line is what actually tells you customers are unhappy. Security-wise, TLS is the tinted windows (nobody sees in) while ACLs are the door locks (only the right people get in) — you want both.

Why hybrid mode exists

5. DP validates + hot-reloads it; if CP is unreachable, DP keeps serving

Common mistakes
  • Version-skewing CP and DP. The control plane must be the same or newer than data planes; a newer DP against an older CP fails to sync.
  • Expiring the cluster mTLS certs. CP↔DP uses mutual TLS; expired certs silently stop config propagation while old config keeps serving — a confusing "changes don't apply" symptom.
  • Running a single control plane as if it were critical-path. It isn't for traffic, but you still want it HA so you can push changes during an incident.
Head office vs the shops

The control plane is head office where policies are written; data planes are the individual shops serving customers. Head office emails new policies to every shop, but if head office loses power for an afternoon, the shops keep trading on yesterday's rulebook. Customers never notice — that separation is exactly why hybrid mode is resilient at scale.

21. Plugin Categories & Dev Portal

Kong's power is its plugin ecosystem. They fall into clear categories, and you can write your own in Lua or via external plugin servers (Go, Python, JS).

CategoryExample plugins
Authenticationkey-auth, JWT, OAuth2, OIDC, mTLS, LDAP

Developer Portal

Kong's Dev Portal auto-generates API documentation from your specs and lets API consumers self-register and get credentials — turning your gateway into a managed API product. This is the "API management" layer on top of the raw gateway, useful when you expose APIs to external developers.

Why plugins run in a fixed phase order

The categories aren't just organizational — they map to when a plugin runs. Auth must run before rate-limiting (you rate-limit a known consumer), which runs before transformations, which run before proxying. Kong assigns each plugin a priority number and executes higher priorities first within the access phase, so the pipeline is deterministic regardless of the order you configured them.

How a custom plugin hooks in

A minimal Lua plugin adds a header in the access phase
-- handler.lua
local MyPlugin = { PRIORITY = 1000, VERSION = "1.0" }
function MyPlugin:access(conf)
  kong.service.request.set_header("X-Tenant", conf.tenant)
end
return MyPlugin
-- Prefer external plugin servers (Go/Python/JS) if you don't want Lua.

The PRIORITY decides where it sits relative to built-in plugins; the phase method (access, header_filter, log…) decides when in the request lifecycle it fires — the same NGINX phases Kong itself uses (§11).

Common mistakes
  • Assuming config order = execution order. It's the priority number that decides. A rate-limit plugin with a higher priority than auth would meter anonymous traffic wrongly.
  • Heavy work in the access phase. It's on the hot path of every request; do expensive logging in the async log phase instead.
  • Exposing the Dev Portal without RBAC. Self-registration is powerful — gate it and review credential approval, or you hand out API access freely.
Plugins are an assembly line, not a pile

Even though you drop plugins onto a route in any order, Kong runs them in a fixed assembly-line sequence: check ID first, then count visits, then relabel the package, then ship it. The priority number is each station's fixed position on the line — so the outcome is predictable no matter what order you bolted the stations on.

22. Gateway API & the Future

Kubernetes is standardizing ingress around the new Gateway API, which Kong (and Istio, and others) implement. It's the successor to the older Ingress resource.

Gateway API — cleaner separation of concerns
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: { name: orders }
spec:
  parentRefs: [{ name: kong-gateway }]      # infra owned by platform team
  rules:
    - matches: [{ path: { type: PathPrefix, value: /api/orders } }]
      backendRefs: [{ name: orders-svc, port: 8080 }]
Why Gateway API matters

The old Ingress resource crammed everything into annotations and mixed infra and routing concerns. Gateway API cleanly separates the Gateway (owned by platform/infra teams) from HTTPRoutes (owned by app teams), supports more protocols, and is portable across implementations. New clusters should adopt it — see the Kubernetes Ingress section.

Why annotations weren't enough

Ingress standardized only basic host/path routing; everything else (rate limits, rewrites, canary weights) lived in vendor-specific annotations — so an Ingress written for NGINX didn't work on Kong, and there was no schema validation of those magic strings. Gateway API makes these first-class, typed, validated resources, so your routing config is portable and the API server rejects mistakes instead of silently ignoring them.

How the roles split under the hood

Three resources, three owners
GatewayClass  (owned by: infra/vendor)  -> "Kong implements this class"
   ▲ references
Gateway       (owned by: platform team) -> listeners, ports, TLS certs
   ▲ parentRefs
HTTPRoute     (owned by: app team)      -> paths, headers, backends, weights
   -> attaches to a Gateway only if the Gateway's namespace policy ALLOWS it

The Gateway can restrict which namespaces may attach routes, so platform teams delegate routing to app teams safely — app teams can't open ports or change TLS, only add routes to backends they own.

Worked example — canary split with weights
Something Ingress annotations did clumsily, now first-class
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: { name: orders-canary }
spec:
  parentRefs: [{ name: kong-gateway }]
  rules:
    - matches: [{ path: { type: PathPrefix, value: /api/orders } }]
      backendRefs:
        - { name: orders-svc,    port: 8080, weight: 90 }   # 90% stable
        - { name: orders-svc-v2, port: 8080, weight: 10 }   # 10% canary
Common mistakes
  • Mixing Ingress and Gateway API for the same host. Two controllers claiming the same route causes nondeterministic behavior. Migrate a host fully.
  • Forgetting allowedRoutes namespace policy. By default a Gateway may only accept routes from its own namespace; cross-namespace attach needs explicit allowance.
  • Assuming full feature parity across implementations. Core is portable, but some advanced features live in implementation-specific extensions — check your controller's conformance.
Gateway API = a proper org chart for ingress

Old Ingress was one overloaded form where everybody scribbled notes in the margins (annotations) and hoped the vendor read them. Gateway API is a proper org chart: facilities owns the building's doors and locks (Gateway), each team owns the signs directing visitors to their own rooms (HTTPRoute), and there's a clear rule about who may put up signs where. Cleaner ownership, fewer collisions.

23. RabbitMQ, NATS & Pulsar

Kafka is one of several messaging systems. As a lead engineer you choose the right one — they optimize for different things. (Kafka and Kong were examples; the category is what matters.)

SystemModelStrengthsUse when
KafkaDistributed logHigh throughput, replay, streamingEvent streaming, analytics, many consumers
RabbitMQTraditional broker (AMQP)Flexible routing, per-message ack, prioritiesTask queues, complex routing, RPC
NATSLightweight pub/subUltra-low latency, tiny footprintMicroservice signaling, IoT, edge
PulsarLog + queue hybridMulti-tenancy, tiered storage, geo-replicationBoth streaming & queuing at scale
Redis StreamsIn-memory streamSimple, fast, already have RedisLightweight streaming without new infra
Log vs queue — the core distinction

A queue (RabbitMQ) is like a to-do list: workers grab tasks and they're removed once done. A log (Kafka) is like a ship's logbook: entries stay, and many readers can each read the whole history at their own pace. Choose a queue for distributing work to one worker each; choose a log for broadcasting events to many independent consumers and needing replay.

Why not just use Kafka for everything

Kafka is superb at high-throughput ordered logs, but it's a poor fit for some jobs. It has no per-message acknowledgement, no priority queues, no message TTL/delayed delivery, and no easy way to redeliver just one stuck message — a slow message blocks its whole partition. RabbitMQ gives you exactly those queue features; NATS gives you microsecond-latency fire-and-forget signaling with a tiny footprint; Pulsar gives you both models plus multi-tenancy and geo-replication. The right tool depends on whether you need work distribution, low-latency signaling, or durable streaming.

How their routing models differ under the hood

Same "send a message," very different mechanics
RabbitMQ:  producer -> EXCHANGE --(binding rules)--> QUEUE(s) -> consumer ACKs each msg
           (routing by key/headers; unacked msgs redelivered; supports priority/TTL)
NATS core: producer -> SUBJECT -> all current subscribers (fire-and-forget, no storage)
           (JetStream adds persistence + replay on top)
Pulsar:    producer -> TOPIC -> brokers (compute) -> BookKeeper bookies (storage)
           (storage/compute separated -> scale independently; subscriptions pick model)
Kafka:     producer -> PARTITION log -> consumer group advances an OFFSET

Note Pulsar's key architectural difference: it separates compute (brokers) from storage (BookKeeper), so you can scale storage without adding brokers — the opposite of Kafka where a broker owns its partitions' data.

Worked example — a RabbitMQ work queue
Fan work out to competing consumers
# Declare a durable queue and publish a task
rabbitmqadmin declare queue name=tasks durable=true
rabbitmqadmin publish routing_key=tasks payload='resize image 42'

# Two workers compete; each message goes to exactly ONE of them, acked when done
rabbitmqadmin get queue=tasks ackmode=ack_requeue_false count=1
One message, delivered once, then removed
+-------------+----------+---------------+
| routing_key | payload  | message_count |
+-------------+----------+---------------+
| tasks       | resize.. | 0             |   # gone after ack (unlike Kafka)
+-------------+----------+---------------+
Common mistakes when choosing
  • Kafka as a task queue with priorities/TTL. It has none of these natively — you'll fight the tool. Use RabbitMQ/SQS for work queues.
  • NATS core for data you can't lose. Core NATS is at-most-once, in-memory; enable JetStream for persistence and replay.
  • Adopting Pulsar for its features but ignoring its ops cost. Running brokers and a BookKeeper cluster is more moving parts than a single Kafka cluster — worth it only if you need its multi-tenancy/geo features.

Kong is one option. The category also includes cloud-native and mesh-integrated gateways — pick based on your platform.

Why the category has so many players

"API gateway" spans a spectrum: at one end a lightweight reverse proxy (NGINX/Traefik), in the middle a programmable gateway with a plugin ecosystem (Kong, Envoy), and at the far end full API-management platforms with billing, quotas, and developer marketplaces (Apigee, Azure APIM). Cloud vendors also offer managed, serverless gateways (AWS API Gateway) that trade flexibility for zero ops. They coexist because teams sit at different points on the "control vs convenience" and "self-hosted vs managed" axes.

How they differ architecturally

Config model & data path at a glance
NGINX Ingress : file/template config, reload on change   — simple, very fast
Traefik       : auto-discovers services (labels/CRDs)     — great for containers
Envoy/Contour : dynamic config via xDS API (no reloads)   — mesh-aligned, hot updates
AWS API GW    : fully managed, config in AWS, pay-per-call — no servers to run
Kong          : plugins + declarative/CRD config          — feature-rich, portable
Apigee/APIM   : gateway + full lifecycle/monetization      — enterprise API products

Envoy's xDS dynamic-config API is the notable one: control planes push route/cluster updates over gRPC with no reload, which is why service meshes (Istio) build on it.

Common mistakes when picking
  • Choosing an enterprise APM platform for a handful of internal APIs. You pay in cost and complexity for monetization/portal features you won't use.
  • Managed gateway lock-in surprise. AWS API Gateway is great until you need a plugin it doesn't offer or want to move clouds — weigh portability.
  • Running a full gateway where an Ingress would do. If you only need TLS + path routing, a plain NGINX/Traefik Ingress is less to operate than Kong.
From doorman to full concierge service

NGINX/Traefik are a doorman who checks tickets and points the way. Kong/Envoy are a concierge with a toolkit (auth, limits, transforms) you can extend. Apigee/APIM are a whole guest-services department that also bills guests and runs the loyalty program. Pick the level of service the venue actually needs — hiring a concierge team to guard a garden gate is overkill.

25. Choosing the Right Tool

A decision framework
  • Need event streaming, replay, many consumers, analytics? → Kafka (or Pulsar/Kinesis).
  • Need task queues, complex routing, RPC? → RabbitMQ (or SQS on AWS).
  • Need ultra-low-latency service signaling? → NATS.
  • Fronting microservices on Kubernetes? → Kong / Envoy-based gateway, moving to Gateway API.
  • All-in on serverless/AWS? → API Gateway + SQS/SNS/EventBridge.
  • Full API product with external devs? → Kong Enterprise / Apigee / APIM.

The skill isn't memorizing one tool — it's recognizing the pattern (log vs queue, gateway vs mesh) and matching it to requirements.

Why start from requirements, not tools

Every tool in this guide is excellent at what it was designed for and mediocre outside it. Leading with "we'll use Kafka" (because it's popular) instead of "we need replayable, high-throughput events consumed by many independent teams" is how teams end up bending a tool against its grain — fighting Kafka's lack of per-message acks, or fighting RabbitMQ's lack of replay. Nail the requirement first; the tool usually becomes obvious.

How to reason it through

A quick decision tree
Do consumers need to REPLAY history or is the data read by MANY teams?
  ├─ yes -> LOG        (Kafka; Pulsar/Kinesis as alternatives)
  └─ no  -> is it discrete WORK handled once, maybe with priority/retry?
            ├─ yes -> QUEUE   (RabbitMQ; SQS on AWS)
            └─ no  -> just low-latency service-to-service signaling?
                      └─ yes -> NATS (JetStream if it must persist)

Fronting HTTP APIs?
  ├─ on Kubernetes, want plugins/portability -> Kong / Envoy-based + Gateway API
  ├─ all-in on AWS serverless               -> AWS API Gateway + SQS/SNS/EventBridge
  └─ need monetization / external dev portal -> Kong Enterprise / Apigee / APIM
Common decision mistakes
  • Résumé-driven design. Picking the trendiest tool over the fitting one adds ops burden your team pays for forever.
  • One tool to rule them all. Real systems often run both a log and a queue — Kafka for events, RabbitMQ/SQS for tasks. That's healthy, not a failure.
  • Ignoring operational reality. A managed service (MSK, SQS, API Gateway) you can actually run beats a self-hosted best-in-class tool your team can't operate at 3am.
Match the vehicle to the trip

You wouldn't take a sports car to move house or a moving truck to a race. Kafka, RabbitMQ, NATS, Kong, and API Gateway are different vehicles tuned for different trips. The expert move isn't loving one vehicle — it's describing the trip (how far, how much cargo, how fast, who's driving) and letting that pick the vehicle.

27. Troubleshooting Playbook

Kafka: consumer lag growing

Consumers can't keep up. Add consumers (up to partition count), optimize processing, or increase partitions. Check for a stuck/failing consumer causing constant rebalances.

Kafka: messages out of order

Order is only guaranteed within a partition. Ensure related messages share a key so they land in the same partition. Cross-partition ordering isn't a Kafka guarantee.

Kafka: "NotEnoughReplicas" on produce

Fewer in-sync replicas than min.insync.replicas (a broker is down). Restore the broker; producers with acks=all correctly refuse to risk data loss.

Kong: 401/403 on a route

An auth plugin is active but credentials are missing/invalid. Verify the consumer & credential exist and the client sends the right header/key. Check plugin scope (global vs route).

Kong: 502/503 upstream errors

Kong can't reach the backend. Check the Service url/upstream targets, that the pod/service is healthy, and DNS resolves inside the cluster.
