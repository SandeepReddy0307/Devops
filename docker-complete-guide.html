1. What is Docker?

Before any commands, understand what problem Docker solves and why it changed software forever.

Docker is a platform for building, shipping, and running applications inside containers — lightweight, isolated, portable packages that bundle your app together with everything it needs to run (code, runtime, libraries, system tools, config). Docker launched in 2013 and made containers mainstream by making them dead simple to use.

The problem it solves: "it works on my machine"

Before containers, an app that ran perfectly on a developer's laptop would break in testing or production because of subtle differences: a different library version, a missing system package, a different OS, a config mismatch. Docker eliminates this by packaging the app and its entire environment into one artifact that runs identically everywhere Docker runs.

Analogy: Think of shipping containers (the real, physical kind). Before them, cargo was loaded loose — every shape and size, slow and chaotic to move between trucks, ships, and trains. The standardized steel container changed the world: any crane, ship, or truck handles any container the same way, regardless of contents. Docker does this for software — your app is the cargo, the container is the standard box, and any machine with Docker is the crane.

What Docker gives you

BenefitWhat it means in practice
ConsistencySame image runs identically on your laptop, CI, and production. No more environment drift.
IsolationEach container has its own filesystem, processes, and network — apps don't interfere with each other.
PortabilityBuild once, run anywhere Docker runs (Linux, Mac, Windows, cloud).
EfficiencyContainers share the host OS kernel — far lighter than VMs. Start in milliseconds, use MBs not GBs.
SpeedSpin up/tear down environments instantly. Great for testing, CI/CD, and microservices.
VersioningImages are tagged and immutable — roll forward/back to any version reliably.
What Docker is NOT
  • It is not a virtual machine — containers share the host kernel (more on this next).
  • It is not an orchestrator — running hundreds of containers across many servers with self-healing and scaling is the job of Kubernetes/Swarm. Docker runs containers on a host; orchestrators coordinate many hosts.
  • It does not make an insecure app secure — it adds isolation layers, but security still needs thought.

Under the hood: what actually makes a container?

A container is not a special file or a mini-VM — it is simply an ordinary Linux process that the kernel has been told to lie to. The kernel restricts what that process can see and use with three built-in features:

  • Namespaces — control what a process can see. There are separate namespaces for process IDs (PID), the network stack (NET), mount points/filesystem (MNT), hostname (UTS), inter-process communication (IPC), and users (USER). Because of the PID namespace, your app inside a container thinks it is process 1 and cannot even see the host's other processes.
  • cgroups (control groups) — control how much a process can use: CPU, memory, disk I/O, and network bandwidth. This is how --memory=512m is enforced.
  • Union filesystem (overlayfs) — stacks read-only image layers plus a thin writable layer into what looks like one normal filesystem to the process.

Put together: Docker starts your process, wraps it in namespaces so it sees an isolated world, applies cgroup limits so it can't hog the machine, and gives it a layered filesystem. That's the whole trick — no hardware emulation, no second kernel.

Why containers only run Linux binaries natively

Because a container shares the host kernel, a Linux container needs a Linux kernel. On macOS and Windows, Docker Desktop quietly runs a lightweight Linux VM and starts your containers inside it. That is why "containers are lighter than VMs" is true on Linux hosts, and why the same image runs identically once that Linux kernel is present.

A container is a process wearing a blindfold

Imagine an employee in a huge office building. Normally they can wander anywhere. A container puts them in a private room with frosted windows (namespaces — they can only see their own room), and a rule that they may use only one desk and one power outlet (cgroups — limited CPU/RAM). They are still an ordinary employee in the same building (same kernel), just fenced off. That fencing is nearly free, which is why you can run hundreds of them.

Common beginner misconceptions
  • "A container is a tiny VM." No — it is a fenced-off process sharing the host kernel.
  • "Data inside a container is saved." No — the writable layer is deleted when the container is removed. Use volumes for anything you want to keep.
  • "Docker makes my app faster." Not directly — it makes your app portable and consistent. Performance is roughly native because there is no emulation.
  • "One container = one app with a database and a web server inside." Prefer one main process per container — run the DB in its own container.

2. Containers vs Virtual Machines

This is the single most important concept to grasp — it explains why containers are so fast and light.

Houses vs apartments

A virtual machine is like giving each family its own separate house — complete with its own foundation, plumbing, and electricity (a full operating system). Solid, but expensive and slow to build. A container is like an apartment in one building: each has private, lockable space, but they share the building's foundation and utilities (the host's kernel). You fit far more apartments than houses on the same land — which is exactly why containers are so popular.

A Virtual Machine virtualizes hardware. A hypervisor (VMware, VirtualBox, KVM) runs multiple full guest operating systems, each with its own kernel, on top of the host. That's powerful isolation but heavy: each VM carries a whole OS (gigabytes) and takes minutes to boot.

A container virtualizes the operating system. Containers share the host's kernel but run in isolated user-spaces using Linux kernel features (namespaces for isolation, cgroups for resource limits). No guest OS per container — just your app and its dependencies. Result: megabytes, not gigabytes; milliseconds to start, not minutes.

You fit far more apartments than houses on the same plot of land.

Two kernel technologies power containers
  • Namespaces — provide isolation: each container gets its own view of processes (PID), network, mounts, users, and hostname. A process inside can't see the host or other containers.
  • Control groups (cgroups) — provide resource limits: cap how much CPU, memory, and I/O a container can use.

Docker is essentially a friendly toolkit on top of these Linux kernel features.

On Mac & Windows there IS a lightweight VM

Containers need a Linux kernel. On macOS/Windows, Docker Desktop quietly runs a small Linux VM to host containers. On Windows you can also run native Windows containers. It's seamless — but good to know why Docker "just works" on non-Linux machines.

When you should still choose a VM

Containers are not always the right answer. The shared-kernel model is a strength for density and a limitation for isolation. Reach for a VM (or a VM-backed sandbox like Firecracker/Kata) when:

  • You need to run a different kernel or OS (e.g., Windows software on a Linux host, or a specific kernel version).
  • You require hardware-level isolation for strongly untrusted or multi-tenant workloads — the security boundary is thicker than a shared kernel.
  • You need to emulate hardware or run a full desktop OS.

In practice many systems combine both: VMs provide the machines, and containers pack many workloads densely onto each VM.

The isolation trade-off, stated plainly

Because containers share the host kernel, a kernel vulnerability that a container can trigger could, in theory, affect the host and its neighbours — a "container escape." VMs have a thicker boundary (the hypervisor). For most workloads container isolation is more than enough, but this is why you harden containers: run as non-root, drop Linux capabilities, keep the host kernel patched, and never run untrusted images with --privileged.

Boot time, in one picture

Starting a VM is like constructing a new house before anyone can move in — you lay a foundation, run plumbing, wire electricity (boot a whole OS). Starting a container is like handing someone a key to an already-built apartment — they just walk in. The building already exists (the kernel is already running), so "move-in" is instant.

3. Docker Architecture

Docker uses a client–server model. Understanding the pieces demystifies what happens when you type a command.

The restaurant analogy

The Docker CLI is you at the counter placing an order. The daemon is the kitchen that actually cooks (builds images, runs containers) — you never cook directly, you ask the kitchen. The registry (like Docker Hub) is the warehouse of ingredients (pre-made images) the kitchen fetches from. So docker run nginx = "kitchen, please run nginx" → kitchen grabs the nginx image from the warehouse and starts it.

The core components

ComponentRole
Docker CLI (docker)The command-line client you type into. It sends requests to the daemon via a REST API.
Docker daemon (dockerd)The background service that does the real work: builds images, runs/stops containers, manages networks and volumes.
REST APIHow the CLI (or any tool) talks to the daemon — over a Unix socket or TCP.
ImagesRead-only templates used to create containers.

Analogy: The CLI is like a customer at a restaurant counter placing an order. The daemon is the kitchen doing the cooking. The registry is the pantry/warehouse where ingredients (images) are stored. You (client) never cook directly — you ask the kitchen (daemon), which fetches ingredients (images) as needed.

Under the hood: the runtime stack

Modern Docker delegates the low-level work through a layered stack (standardized so tools interoperate):

  • dockerd — the high-level daemon (API, builds, networking, volumes).
  • containerd — the container lifecycle manager (also used by Kubernetes).
  • runc — the low-level runtime that actually creates the container using kernel namespaces & cgroups (implements the OCI standard).
OCI — the standards behind it all

The Open Container Initiative (OCI) defines open standards for image format and runtime. This is why an image built by Docker runs on Kubernetes (containerd/CRI-O) or Podman — they all speak OCI. You are not locked into Docker's runtime.

See the architecture in action
docker version        # client + server (daemon) versions
docker info           # daemon details: containers, images, storage driver, runtime
docker system df      # disk used by images, containers, volumes, cache

What really happens when you run docker run nginx

Tracing a single command through the stack makes the whole architecture concrete. Here is the chain of events, from your keystroke to a running web server:

  1. The CLI parses your command and sends an HTTP request to the daemon over the Unix socket /var/run/docker.sock — something like POST /containers/create then POST /containers/{id}/start.
  2. The daemon (dockerd) checks whether the nginx image exists locally. If not, it pulls each layer from the registry.
  3. dockerd hands the work to containerd, which manages the container's lifecycle.
  4. containerd spawns a containerd-shim and calls runc, which asks the kernel to create the namespaces and cgroups and then executes the container's process (nginx).
  5. runc exits — it is only needed to set things up. The shim stays as the container's parent so the container keeps running even if dockerd restarts.
Why the daemon is split into layers

Early Docker did everything in one big process. Splitting it into dockerd → containerd → runc means each piece follows an open standard and can be swapped or reused. Kubernetes, for example, talks to containerd directly and skips dockerd entirely. The shim is what lets you restart or upgrade the Docker daemon without killing your running containers.

Prove the client/daemon split is over a socket
# The daemon listens on a Unix socket; the CLI is just a client of it
ls -l /var/run/docker.sock
# You can even talk to the daemon's REST API directly with curl:
curl --unix-socket /var/run/docker.sock http://localhost/version
Typical output
srw-rw---- 1 root docker 0 Sep 27 09:10 /var/run/docker.sock
{"Version":"27.1.1","ApiVersion":"1.46","Os":"linux","Arch":"amd64",...}
The socket is the crown jewels

Because the daemon runs as root, anyone who can write to /var/run/docker.sock can start a container that mounts the whole host filesystem and become root on the host. That is why the docker group equals root, and why you should be extremely careful before mounting the socket into a container (e.g., -v /var/run/docker.sock:/var/run/docker.sock).

A remote control, not the TV

The docker command in your terminal is just a remote control. It doesn't build or run anything itself — it sends signals to the daemon (the actual TV doing the work). This is why the daemon can even live on another machine: point the remote at a different address (DOCKER_HOST) and you're controlling a Docker engine across the network.

5. Images & Layers

An image is the blueprint; a container is the running instance. Understanding image layers is the key to fast builds and small images.

Why copy-on-write is clever

All containers read the same underlying layers. The instant a container needs to change a file, that single file is copied up into its private writable layer and edited there — the shared original is untouched. This is why launching many containers from one image is nearly free on disk and starts instantly.

Layers = transparent sheets

Picture drawing on stacked transparent sheets on an overhead projector: the bottom sheet is the base system, each new sheet adds a bit more (dependencies, then your code). Stacked together they form the full picture (the image). The magic: if only the top sheet changes, Docker reuses all the sheets below from cache — that's why the second build is lightning fast. And ten images built on the same base share that bottom sheet instead of storing ten copies.

A Docker image is a read-only, layered filesystem plus metadata (default command, exposed ports, env vars). Each instruction in a Dockerfile creates a layer — a delta representing the filesystem changes from that step. Layers stack on top of each other, and Docker uses a union filesystem to present them as one.

Why layers matter: caching & sharing

  • Build caching: If a layer's inputs haven't changed, Docker reuses the cached layer instead of rebuilding — huge speedups. But if an early layer changes, every layer after it must rebuild.
  • Storage sharing: Layers are content-addressed and shared across images. Ten images built on node:20 store that base once, not ten times.
  • Copy-on-write: When a container runs, Docker adds a thin writable layer on top of the read-only image layers. Changes live only in that layer and vanish when the container is removed (unless you use volumes).

Analogy: Image layers are like transparent sheets stacked on an overhead projector. Each sheet adds some drawing; stacked together they form the full picture. Share the bottom sheets across many drawings, and only redraw the top sheet when something changes.

latest is just a default tag, not "the newest" magic — and it moves. Two machines pulling latest on different days can get different images, breaking reproducibility. Always pin explicit versions (e.g., node:20.11-alpine), and for maximum reproducibility pin by digest (@sha256:...).

Deep dive: what a layer actually is

A layer is nothing more than a tarball of filesystem changes — the files that were added, modified, or deleted by one build step — plus a content hash (a SHA-256 digest) computed from those bytes. Because the name is the hash, layers are "content-addressed": two images that ran the exact same step share the exact same layer on disk, automatically.

The union filesystem (overlay2 on modern Linux) stacks these layers. When the container reads a file, the kernel returns it from the topmost layer that contains it. When the container writes a file, overlayfs first copies it up into the thin writable layer, then edits the copy — the read-only image below is never touched. This "copy-on-write" is why many containers can share one image safely.

See layers as content-addressed digests
docker history --no-trunc nginx:1.27 | head
docker image inspect nginx:1.27 --format '{{json .RootFS.Layers}}'
Typical output (digests are the layer identities)
["sha256:e0b3afb09dc386786d5b6f...","sha256:9e3ea8720c6de96...", ...]

A worked example: watch a cached build vs a busted cache

First build — every layer runs
docker build -t demo:1 .
Second build after changing ONLY source code
 => CACHED [2/5] WORKDIR /app
 => CACHED [3/5] COPY package*.json ./
 => CACHED [4/5] RUN npm ci
 => [5/5] COPY . .            <-- only this and later layers rebuild

The CACHED markers are the layer-sharing mechanism paying off: because the inputs to steps 2–4 were byte-for-byte identical, Docker reused those layers and only re-ran the step whose input (your source) changed.

Deleting a file in a later layer does NOT shrink the image

If layer 3 adds a 500 MB file and layer 6 deletes it, the image still contains ~500 MB — the delete is just a "whiteout" marker in an upper layer; the bytes still live in layer 3 and are downloaded on every pull. To truly remove data it must never be added in the same lineage. This is exactly why secrets and build junk must be handled with multi-stage builds or BuildKit secret mounts, not "add then rm."

Why the second build is instant

Think of a layer's digest as a fingerprint of its contents. Before running a step, Docker asks: "have I seen this exact fingerprint before?" If yes, it reuses the finished result instead of doing the work again — like recognizing you already baked an identical cake yesterday and just taking it out of the freezer. Change the recipe at any step and every step after it needs a fresh bake.

6. The Dockerfile

A Dockerfile is a text file of instructions that Docker executes top-to-bottom to build an image. This is the heart of Docker.

A Dockerfile is a recipe

Think of a Dockerfile as a cooking recipe written down step by step: "start with this base, add these ingredients, run these steps, and here's the dish to serve." Docker follows the recipe from top to bottom to bake an image. Because it's written down, anyone can reproduce the exact same result — no more "but it works on my machine." The three words to remember: Dockerfile (recipe) → image (the frozen prepared dish) → container (a served, running portion).

A well-structured Dockerfile (Node.js example)
# 1. Base image — start from an official, slim base
FROM node:20-alpine

# 2. Metadata (optional but good practice)
LABEL maintainer="you@example.com"

# 3. Set the working directory inside the image
WORKDIR /app

# 4. Copy dependency manifests FIRST (better caching)
COPY package*.json ./

# 5. Install dependencies
RUN npm ci --omit=dev

# 6. Copy the rest of the source
COPY . .

# 7. Document the port the app listens on
EXPOSE 3000

# 8. Set environment variables
ENV NODE_ENV=production

# 9. Run as a non-root user for security
USER node

# 10. The default command when a container starts
CMD ["node", "server.js"]

How Docker reads a Dockerfile, line by line

Each instruction runs in order, and each one that changes the filesystem produces a new layer. Crucially, every instruction runs in a fresh, throwaway container based on the result of the previous layer — so a shell variable or a cd in one RUN does not carry over to the next RUN. State only persists as files on disk and as the metadata Docker explicitly tracks (ENV, WORKDIR, USER, etc.).

A classic gotcha — each RUN is a new shell
# WRONG: the cd does not persist; the second RUN starts back at /
RUN cd /app
RUN npm install     # runs in / , not /app

# RIGHT: set the directory as durable metadata, or chain in one RUN
WORKDIR /app
RUN npm install

ENV vs ARG — build-time vs run-time

This trips up almost everyone. ARG values exist only while building and disappear from the final image; ENV values are baked into the image and are visible to the running container. Use ARG for things that steer the build (a version to install), and ENV for configuration the app reads at runtime.

Combining them
ARG NODE_VERSION=20        # only during build
FROM node:${NODE_VERSION}-alpine
ENV NODE_ENV=production    # persists into running containers
# docker build --build-arg NODE_VERSION=18 .

Common Dockerfile mistakes
  • COPY . . too early — busts the dependency cache on every code change. Copy manifests and install first.
  • Using ADD for plain files — its auto-extract/URL behavior surprises people. Use COPY unless you specifically need those.
  • Forgetting EXPOSE does not publish a port — it is documentation only; you still need -p at run time.
  • Running as root by default — every base image runs as root unless you add USER.
  • Shell-form CMD — swallows signals; prefer the JSON exec form.
Each line is a fresh cook who reads only the pantry

Imagine a relay of cooks: each Dockerfile line is a new cook who walks into the kitchen, sees only the ingredients already on the counter (the files on disk) and the recipe notes pinned to the wall (ENV/WORKDIR), does one step, and leaves. They don't remember what the previous cook was thinking (shell variables, current folder) — only what they left physically on the counter. That's why you write durable state to disk or to metadata.

7. Building & Tagging Images

Turn a Dockerfile into an image with docker build, then tag and share it.

The three words, one more time (they're everything)

Dockerfile = the written recipe. Image = the finished dish, frozen and ready (built once with docker build). Container = a hot, served portion of that dish (started with docker run). You can serve many identical portions (containers) from one frozen dish (image). If those three click, all of Docker clicks.

Build, tag, and inspect
# Build from the Dockerfile in the current directory (. = build context)
docker build -t myapp:1.0 .

# Tag the same image with additional tags
docker tag myapp:1.0 myapp:latest
docker tag myapp:1.0 myuser/myapp:1.0

# Build with a specific Dockerfile and build args
docker build -f Dockerfile.prod --build-arg NODE_ENV=production -t myapp:prod .

# See what you built
docker images myapp
docker history myapp:1.0
The "build context" explained

The . at the end of docker build -t myapp:1.0 . is the build context — the directory whose contents are sent to the daemon and made available to COPY/ADD. A bloated context (e.g., including node_modules or .git) slows every build. Trim it with .dockerignore.

Understanding build cache

Docker caches each layer. On rebuild, it reuses cached layers until it hits an instruction whose inputs changed — then it rebuilds that layer and all following ones. This is why instruction order matters: put things that change rarely (installing dependencies) before things that change often (copying source code).

Cache control
docker build --no-cache -t myapp:1.0 .      # ignore cache entirely
docker build --pull -t myapp:1.0 .          # always pull a fresh base image
Order for optimal caching

Copy dependency manifests and install dependencies before copying your source code. That way, changing a line of app code doesn't invalidate the (expensive) dependency-install layer:

COPY package*.json ./
RUN npm ci            # cached unless package files change
COPY . .              # only this layer rebuilds on code changes

Exactly how the cache decides "hit or miss"

For each instruction, Docker computes a cache key from the instruction text and its inputs, then looks for a matching cached layer built on the same parent layer. The rules differ by instruction:

  • RUN — the key is basically the command string. Docker does not know what the command actually downloads, so RUN apt-get update can serve a stale cache. That is why you chain update and install in one RUN.
  • COPY/ADD — the key includes a checksum of the copied files' contents. Change one byte of a copied file and that layer (and everything after it) rebuilds.
  • Any cache miss invalidates every following instruction, even identical ones — the chain is strictly ordered.

A worked example: the ordering that saves minutes

Cache-hostile order (rebuilds deps on every code edit)
COPY . .
RUN npm ci            # re-runs whenever ANY file changes
Cache-friendly order
COPY package*.json ./
RUN npm ci            # only re-runs when dependencies change
COPY . .              # code edits only invalidate from here down
Rebuild after editing a source file — the good order
 => CACHED [3/5] COPY package*.json ./
 => CACHED [4/5] RUN npm ci          <-- expensive step reused
 => [5/5] COPY . .                   0.1s
Reusing cache across CI machines

A fresh CI runner has an empty local cache, so builds start cold. With BuildKit you can persist and pull cache between runs: docker build --cache-from type=registry,ref=myrepo/app:cache --cache-to type=registry,ref=myrepo/app:cache,mode=max . This uploads the layer cache to a registry so the next runner gets cache hits.

When the cache lies to you

The most common "why is my image stale?" bug is a RUN that fetches something from the internet (a package index, a git clone, a curl of "latest"). Docker sees the same command string, serves the old layer, and you get yesterday's dependency. Fix it by pinning versions, or force a clean build of the affected steps with --no-cache (whole build) or by changing an ARG used just before that step to bust its cache deliberately.

Cache = a stack of sticky notes

Picture the build as a stack of sticky notes, one per step, each stuck to the one below. Docker reuses a note only if it matches and every note beneath it matches. Peel off (change) a note near the bottom and every note above falls off and must be rewritten. So put the notes that rarely change (installing dependencies) at the bottom and the ones you scribble on constantly (your code) at the top.

8. Multi-Stage Builds

The single most impactful technique for small, secure production images. Learn this well.

Multi-stage = cook in a big kitchen, deliver just the meal

To cook a meal you need a whole kitchen — ovens, mixers, raw ingredients, mess. But to deliver it, you just want the finished plate, not the entire kitchen. A multi-stage build does exactly this: one stage has all the heavy build tools and compiles your app; the final stage takes only the finished app into a tiny, clean image. Result: images shrink from hundreds of MB to a few MB, and there are fewer leftover tools for attackers to exploit.

The problem: to build an app you need compilers, dev dependencies, and build tools — but you don't want any of that in the final image (it bloats size and expands the attack surface). A multi-stage build uses multiple FROM stages: build in a fat "builder" stage, then copy only the finished artifacts into a tiny "runtime" stage.

Multi-stage Go example — from ~800MB to ~15MB
# ---- Stage 1: build ----
FROM golang:1.22 AS builder
WORKDIR /src
COPY go.* ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /app/server .

# ---- Stage 2: runtime (tiny) ----
FROM gcr.io/distroless/static-debian12
COPY --from=builder /app/server /server
USER nonroot:nonroot
EXPOSE 8080
ENTRYPOINT ["/server"]
Multi-stage Node example
# ---- build ----
FROM node:20 AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# ---- runtime ----
FROM node:20-alpine
WORKDIR /app
COPY --from=build /app/dist ./dist
COPY --from=build /app/node_modules ./node_modules
USER node
CMD ["node", "dist/server.js"]
Handy multi-stage tricks
  • Build a specific stage: docker build --target build -t myapp:build .
  • Copy from an external image: COPY --from=nginx:latest /etc/nginx/nginx.conf ./
  • Runtime bases, smallest → most compatible: scratch (empty) < distroless < alpine < debian-slim.

Why multi-stage beats the old "builder pattern"

Before multi-stage builds existed, teams used two separate Dockerfiles and a shell script: build in one image, docker cp the artifact out, then copy it into a second image. It was fragile and hard to reproduce. Multi-stage collapses all of that into one Dockerfile the daemon understands natively: COPY --from=<stage> reaches into an earlier stage and lifts out only the files you name. Everything else in that stage — compilers, caches, source, dev dependencies — is simply never copied, so it cannot end up in your shipped image.

Mechanically, what gets shipped

Only the last stage becomes the final image by default. Earlier stages are built (so their layers may be cached) but discarded from the output. The final image's size is the size of its base plus exactly the files you copied in — nothing more.

Prove the size difference for the Go example above
docker build -t go-app:slim .
docker images go-app:slim golang
Typical output — the builder base is huge, the shipped image is tiny
REPOSITORY   TAG       IMAGE ID       SIZE
golang       1.22      d5f...          815MB   <-- build stage base (discarded)
go-app       slim      a1b...          14.7MB  <-- what you actually ship
Name stages and copy between them freely

Stages can be named (FROM ... AS builder) and you can have more than two. A common pattern is deps → build → test → runtime, where the test stage runs your test suite and the runtime stage copies only the built app. You can also stop early for debugging with --target: docker build --target builder -t app:dbg . gives you the full toolchain image to poke around in.

Multi-stage gotchas
  • Forgetting to copy a runtime dependency. A minimal final base may lack shared libraries your binary needs (e.g., glibc, CA certificates, timezone data). Symptoms: "not found" for a binary that exists, or TLS errors. Copy CA certs, or use a base like alpine/distroless:base that includes them.
  • Statically link when targeting scratch/distroless/static. For Go, set CGO_ENABLED=0 so the binary has no dynamic library dependencies.
  • Copying node_modules built for the wrong platform — native modules compiled in the build stage must match the runtime base's libc (glibc vs musl on alpine).
Moving house with movers you send home

Building your app is like packing up a house: you hire a truck full of tools and boxes (the builder stage). But you don't move the movers and their truck into your new home — you keep only the furniture (the finished binary). Multi-stage builds send the movers home and keep just the furniture, so the new place stays clean and small.

9. Image Best Practices

Follow these and your images will be small, fast, secure, and cache-friendly.

The essential checklist
  1. Use small, official base images — alpine, -slim, or distroless. Smaller = faster pulls + smaller attack surface.
  2. Pin versions — never latest in production; pin base image and dependency versions.
  3. Use multi-stage builds — keep build tools out of the final image.
  4. Order instructions for caching — least-changing first, source code last.
  5. Combine RUN commands to reduce layers and clean up in the same layer.
  6. Use .dockerignore — keep the context lean, avoid leaking secrets.
  7. Run as non-root — add a USER; never run app containers as root.
  8. Don't bake in secrets — they persist in layers forever. Use build secrets or runtime env/secret stores.
  9. One process per container — containers are designed for a single main concern.
  10. Add a HEALTHCHECK so orchestrators know when the app is truly ready.

Combining RUN steps & cleaning up

Bad — three layers, leftover apt cache
RUN apt-get update
RUN apt-get install -y curl
RUN rm -rf /var/lib/apt/lists/*   # too late — earlier layers already stored the cache
Good — one layer, clean
RUN apt-get update && apt-get install -y --no-install-recommends \
      curl \
    && rm -rf /var/lib/apt/lists/*
Secrets leak into image layers — permanently

Copying a secret and deleting it later does not remove it — it's preserved in the earlier layer and recoverable with docker history/layer inspection. For build-time secrets use BuildKit secret mounts (RUN --mount=type=secret, see §23). For runtime, inject via environment variables or a secrets manager — never COPY a .env with real credentials.

HEALTHCHECK example
HEALTHCHECK --interval=30s --timeout=3s --start-period=5s --retries=3 \
  CMD curl -f http://localhost:3000/health || exit 1

Then docker ps shows (healthy)/(unhealthy), and orchestrators can act on it.

10. The Container Lifecycle

A container moves through distinct states. Knowing them makes managing and debugging containers intuitive.

Stopped isn't the same as removed

Beginners often think stopping a container deletes it — it doesn't. A stopped container is like a parked car: switched off, but still there, and you can start it again (its files are intact). Removing it (docker rm) is sending the car to the crusher — gone, along with anything written inside it. That's why important data belongs in a volume (an external drive), not inside the container itself.

StateMeaning
CreatedContainer exists (from docker create) but isn't running yet.
RunningThe main process is executing.
PausedProcesses frozen (docker pause) — memory retained, not scheduled.
Stopped / ExitedMain process finished or was stopped. Container remains on disk (can be restarted).
RemovedDeleted (docker rm) — gone, along with its writable layer.
Move a container through its lifecycle
docker create --name c1 nginx     # Created
docker start c1                   # -> Running
docker pause c1                   # -> Paused
docker unpause c1                 # -> Running
docker stop c1                    # graceful stop (SIGTERM, then SIGKILL after grace)
docker start c1                   # restart the same container
docker kill c1                    # immediate stop (SIGKILL)
docker rm c1                      # remove (must be stopped, or use -f)

# docker run = create + start in one step
docker run -d --name web nginx
stop vs kill — signals matter

docker stop sends SIGTERM (please shut down gracefully), waits a grace period (default 10s), then SIGKILL if still running. docker kill sends SIGKILL immediately. Well-behaved apps handle SIGTERM to flush data and close connections cleanly — one reason to use the exec form of CMD/ENTRYPOINT so signals reach your process.

Listing containers
docker ps                 # running containers
docker ps -a              # all, including stopped
docker ps -q              # just IDs (useful for scripting)
docker ps --filter "status=exited"
docker ps --format "table {{.Names}}\t{{.Status}}\t{{.Image}}"

What "exited" really tells you: the exit code

When a container stops, it leaves behind an exit code — the same convention as any Unix process. This is the single most useful clue when debugging "why did it die?" A zero means the main process finished normally; anything non-zero is an error or a signal.

Read a stopped container's exit code
docker run --name flaky alpine sh -c 'exit 7'
docker inspect flaky --format '{{.State.Status}} exit={{.State.ExitCode}}'
docker ps -a --filter name=flaky
Typical output
exited exit=7
CONTAINER ID   IMAGE     STATUS                      NAMES
a1b2c3d4e5f6   alpine    Exited (7) 3 seconds ago    flaky
Exit codeUsual meaning
0Clean exit — the process finished its work.
1–125The app itself errored (application-defined).
137Killed by SIGKILL (128+9) — often an OOM kill or docker kill.
143Terminated by SIGTERM (128+15) — a normal docker stop.
126/127Command not executable / not found — a common Dockerfile CMD typo.
Why "my container exits immediately" is usually not a bug

A container lives exactly as long as its main process (PID 1). If that process finishes — a script that runs and returns, a web server started in the background, or a shell with nothing to do — the container stops. Beginners often run docker run ubuntu and are surprised it exits instantly: bash had no terminal and nothing to do. The fix is to give it a long-running foreground process (a real server) or, for experimentation, -it to attach a terminal. Never "keep it alive" with sleep infinity in production — run the actual service in the foreground.

A container is alive only while its heart beats

Think of PID 1 as the container's heartbeat. As long as that one process keeps running, the container is alive. The moment it finishes — job done, or crashed — the heart stops and the container exits. So to keep a container running, you don't add tricks; you give it a genuine long-running job (a server listening for requests) as its heartbeat.

docker run is the most-used and most-flagged command. Master its options and you master day-to-day Docker.

Realistic examples
# Web app: background, named, port-mapped, env vars, restart policy

Env vars are visible — don't put real secrets in -e casually

Values passed with -e show up in docker inspect and process listings. For sensitive data prefer --env-file (kept out of shell history) or a proper secrets mechanism, and never commit env files with real credentials.

What docker run does behind the scenes

A single docker run is really several steps the daemon performs in sequence. Knowing them explains many error messages:

  1. Resolve the image — found locally? If not, pull it (this is the "Unable to find image ... locally" message).
  2. Create the container — allocate the writable layer, set up namespaces, apply your flags (env, mounts, limits). Errors here are config errors (bad mount, unknown flag).
  3. Create the network endpoint — attach to the chosen network and set up port publishing rules.
  4. Start PID 1 — run the ENTRYPOINT/CMD. Errors here (exec: "foo": not found) mean the command itself is wrong.

So docker run is exactly docker create + docker start fused together, which is why anything you can set at run time maps to a create-time setting.

A worked example: flags map directly to inspectable settings

Run with several flags, then confirm they took effect
docker run -d --name api -p 8080:3000 -e NODE_ENV=production \
  --memory 256m --restart unless-stopped nginx
docker inspect api --format \
  'ports={{.NetworkSettings.Ports}} mem={{.HostConfig.Memory}} restart={{.HostConfig.RestartPolicy.Name}}'
Typical output
ports=map[3000/tcp:[{0.0.0.0 8080}]] mem=268435456 restart=unless-stopped
Flag order matters: image name is a boundary

Everything before the image name is a flag to Docker; everything after it is the command run inside the container. So docker run ubuntu -it passes -it to the container (wrong), while docker run -it ubuntu gives Docker the flag (right). Similarly docker run nginx --help shows nginx's help, not Docker's. When something ignores your flag, check whether it landed on the wrong side of the image name.

The image name is a fence

Reading a docker run line, imagine a fence at the image name. On the left side you're talking to Docker ("run it in the background, map this port"). On the right side you're talking to the program inside ("here are your arguments"). Put a word on the wrong side of the fence and it gets delivered to the wrong listener — the classic reason a flag "does nothing."

12. Inspecting, Logs & Exec

Your core toolkit for observing and interacting with running containers — and your first stop when debugging.

The essential observation commands
# View logs
docker logs web
docker logs -f web                 # follow (stream)
docker logs --tail 100 web         # last 100 lines
docker logs --since 10m web        # last 10 minutes

# Get a shell inside a running container
docker exec -it web bash           # or: sh (for alpine)
docker exec web ls /app            # run a one-off command

# Full low-level details (JSON): IP, mounts, env, state
docker inspect web
docker inspect -f '{{.NetworkSettings.IPAddress}}' web   # extract one field

# Live resource usage
docker stats                       # all containers, live
docker stats web                   # one container

# Processes running inside a container
docker top web

# What changed in the container's filesystem vs its image
docker diff web

# Copy files in/out
docker cp web:/app/log.txt ./log.txt
docker cp ./config.json web:/app/config.json
exec vs attach

docker exec starts a new process in the container (e.g., a debug shell) — this is what you almost always want. docker attach connects to the container's main process's stdio — detaching wrong can kill it. Use exec for debugging.

Log to stdout/stderr

Design containers to write logs to stdout/stderr, not to files inside the container. Docker captures those streams so docker logs (and log drivers shipping to CloudWatch, Loki, etc.) just work. Writing to files inside the container makes logs disappear when the container is removed.

13. Resource Limits (CPU & Memory)

By default a container can consume all host resources. Limits (backed by cgroups) prevent one container from starving the host or its neighbors.

Setting limits
# Memory: hard limit of 512MB (container is OOM-killed if it exceeds)
docker run -d --memory="512m" --name app myapp:1.0

# Memory limit + reservation (soft target)
docker run -d --memory="512m" --memory-reservation="256m" myapp:1.0

# CPU: limit to 1.5 cores
docker run -d --cpus="1.5" myapp:1.0

# Pin to specific CPU cores
docker run -d --cpuset-cpus="0,1" myapp:1.0

# Relative CPU weight (default 1024) — matters under contention
docker run -d --cpu-shares=512 myapp:1.0
FlagEffect
--memory (-m)Hard memory ceiling. Exceed it → container is OOMKilled.
--memory-reservationSoft limit; a target enforced under memory pressure.
--cpusFractional core limit (e.g., 0.5, 2).
--cpuset-cpusWhich physical cores the container may use.
--cpu-sharesRelative weighting when CPUs are contended.
--pids-limitCap the number of processes (guards against fork bombs).
Watch for OOMKilled

If a container mysteriously dies, check docker inspect <c> --format '{{.State.OOMKilled}}'. true means it exceeded its memory limit. Raise the limit or fix the leak. Always set memory limits in production so one container can't take down the host.

14. Restart Policies

Tell Docker what to do when a container exits or the daemon restarts — the foundation of resilience on a single host.

PolicyBehavior
no (default)Never automatically restart.
on-failure[:max]Restart only if it exits with a non-zero code; optional retry cap.
alwaysAlways restart, including after daemon/host reboot.
unless-stoppedLike always, but stays stopped if you stopped it manually.
Applying restart policies
# Recommended for long-running services
docker run -d --restart unless-stopped --name web nginx

# Retry a flaky job up to 5 times on failure
docker run -d --restart on-failure:5 myjob:1.0

# Change the policy on an existing container
docker update --restart=always web
Which policy to use

For services you want up 24/7 on a single host, use unless-stopped — it survives reboots but respects your manual stops. For batch jobs that should retry on error, use on-failure. For anything at scale across multiple hosts, an orchestrator (Kubernetes/Swarm) handles restarts and much more — restart policies are the single-host equivalent.

15. Volumes & Mounts — persistent data

A container's writable layer is ephemeral — remove the container and its data is gone. To persist or share data, you mount storage from outside the container.

Why does data vanish? (and how volumes fix it)

A container is meant to be disposable — like a paper cup. When you throw it away (delete the container), anything written inside goes with it. That's fine for the app itself, but terrible for a database. A volume is like an external hard drive you plug into the container: the data lives on the drive, not the cup, so you can throw away and recreate the container as often as you like and the data stays safe. Rule: anything you need to keep goes in a volume.

The three mount types

TypeWhat it isBest for
VolumeDocker-managed storage (in /var/lib/docker/volumes). Docker owns its lifecycle.Databases & app data — the recommended default for persistence.
Bind mountMaps a specific host path into the container.Local development (live-edit code), mounting config files.
tmpfsIn-memory storage; never written to disk.Sensitive temp data or scratch space that shouldn't persist.

Analogy: A volume is a storage unit the "moving company" (Docker) manages for you — it knows where it is and keeps it safe. A bind mount is you pointing at a specific drawer in your own house (a host path) and saying "use this exact spot." tmpfs is a whiteboard — fast, but wiped clean when you leave.

Working with volumes
# Create and manage named volumes
docker volume create appdata
docker volume ls
docker volume inspect appdata
docker volume rm appdata
docker volume prune               # remove all unused volumes

# Use a named volume (data survives container removal)
docker run -d --name pg \
  -v appdata:/var/lib/postgresql/data \
  -e POSTGRES_PASSWORD=secret \
  postgres:16

# The modern, explicit --mount syntax (recommended)
docker run -d --name pg \
  --mount type=volume,source=appdata,target=/var/lib/postgresql/data \
  postgres:16
Bind mounts for local development
# Live-edit: mount your source code into the container
docker run -d --name dev \
  -v "$(pwd)":/app \
  -w /app \
  -p 3000:3000 \
  node:20-alpine npm run dev

# Mount a config file read-only
docker run -d --name web \
  -v "$(pwd)/nginx.conf":/etc/nginx/nginx.conf:ro \
  nginx
tmpfs (in-memory)
docker run -d --tmpfs /tmp:rw,size=64m myapp:1.0
-v vs --mount

Both work. -v is terse (great for quick commands); --mount is explicit key=value (clearer, less error-prone, preferred in scripts/Compose). A subtle gotcha: with -v, if the source host path doesn't exist Docker creates an empty directory; with --mount it errors — often safer.

Storage best practices
  • Use named volumes for databases and app state — portable and Docker-managed.
  • Use bind mounts for development (live code reload) and config injection, not for production data.
  • Mount config/secrets read-only (:ro).
  • Back up volumes: docker run --rm -v appdata:/data -v $(pwd):/backup alpine tar czf /backup/appdata.tgz -C /data .
  • Prune unused volumes periodically — but carefully, they hold real data.

SymptomCause & fix

Permission denied on mounted filesUID mismatch between host and container user. Align user (-u), fix ownership, or set fsGroup-style permissions.

Under the hood: where the data actually lives

The confusion around volumes evaporates once you see where bytes land. Recall that a container's filesystem is layered, with a thin writable layer on top. A mount bypasses that writable layer entirely — reads and writes at the mount path go straight to storage that lives outside the container's lifecycle:

  • Named volume → a directory Docker manages under /var/lib/docker/volumes/<name>/_data on the host. Delete the container and this directory is untouched.
  • Bind mount → the exact host path you point at. The container and host see the same files live.
  • tmpfs → RAM only; never hits disk, and disappears when the container stops.
Prove data survives container deletion
docker volume create demo
docker run --rm -v demo:/data alpine sh -c 'echo "kept!" > /data/note.txt'
# the container is already gone (--rm); now read it from a brand-new container:
docker run --rm -v demo:/data alpine cat /data/note.txt
Output — the file outlived the container that wrote it
kept!

A worked example: recreate a database, keep the data

Run Postgres on a volume, destroy the container, run a fresh one
docker run -d --name pg -v pgdata:/var/lib/postgresql/data \
  -e POSTGRES_PASSWORD=secret postgres:16
# ... create tables, insert rows ...
docker rm -f pg                       # container gone
docker run -d --name pg -v pgdata:/var/lib/postgresql/data \
  -e POSTGRES_PASSWORD=secret postgres:16
# the new container sees all the old data because it lives on the pgdata volume
The "bind mount shadows the image" gotcha

If you bind-mount a host directory over a path the image already populated, the host directory hides whatever the image put there. The classic case: mounting your source over /app in a Node project also hides the image's /app/node_modules, so the app can't find its dependencies. Fixes: keep node_modules in a separate volume mounted at /app/node_modules, or don't bind-mount over installed dependencies.

A mount is a magic doorway

Think of a mount point as a doorway painted on a wall inside the container. Walk through /data and you're not in the container at all — you're standing in a room that exists outside it (the volume). Everything you leave in that room stays there after the container is demolished, because the room was never part of the container to begin with.

16. Networking

Docker gives containers their own network stack and lets them talk to each other, the host, and the world. Understanding network drivers is key to connecting multi-container apps.

The main network drivers

The most important concept: user-defined bridge networks

On the default bridge network, containers can only reach each other by IP (fragile). On a user-defined bridge network, Docker provides automatic DNS resolution by container name — containers reach each other simply by name. Always create a user-defined network for multi-container apps.

Container-to-container communication done right
# Create a user-defined bridge network
docker network create appnet

# Run a database and an app on the same network
docker run -d --name db --network appnet \
  -e POSTGRES_PASSWORD=secret postgres:16

docker run -d --name api --network appnet \
  -e DATABASE_URL="postgres://postgres:secret@db:5432/postgres" \
  myapp:1.0
# The api reaches the database using the hostname "db" — Docker DNS resolves it.
Network management

Networking best practices
  • Create a user-defined bridge network per application so containers resolve each other by name.
  • Only publish ports (-p) that truly need external access — internal services can talk over the private network without exposing ports to the host.
  • Isolate tiers: put frontend + backend on one network, backend + DB on another, so the frontend can't reach the DB directly.

How bridge networking actually moves a packet

When Docker starts, it creates a virtual switch on the host (the default one is called docker0). Each container gets a virtual ethernet pair (veth): one end lives in the container as its eth0, the other end plugs into the bridge. The container gets a private IP (e.g., 172.17.0.2) from the bridge's subnet. To reach the internet, the container's outbound packets are NAT-ed (masqueraded) behind the host's IP by iptables rules Docker installs. Inbound access requires an explicit port publish, which adds a DNAT rule forwarding a host port to the container's IP:port.

See the bridge, the container IP, and the DNS in action
docker network create appnet
docker run -d --name db --network appnet -e POSTGRES_PASSWORD=secret postgres:16
docker run -d --name api --network appnet alpine sleep 1d

# The api resolves "db" to the database's private IP automatically:
docker exec api getent hosts db
docker network inspect appnet --format '{{range .Containers}}{{.Name}}={{.IPv4Address}} {{end}}'
Typical output
172.18.0.2        db
db=172.18.0.2/16 api=172.18.0.3/16
Why the default bridge feels broken for multi-container apps

On the built-in bridge network there is no name-based DNS between containers — api cannot ping db by name, only by IP, and IPs change on restart. Beginners hit "connection refused" and blame Docker. The fix is almost always: put the containers on a user-defined network (docker network create), where Docker's embedded DNS resolves container names. Compose does this for you automatically.

"localhost inside a container is the container itself"

A very common mistake: an app in container A tries to reach a database at localhost:5432. But localhost means "this container," not the host or the DB container. Use the service/container name (db:5432) on a shared network. To reach a service on the host machine from inside a container, use the special DNS name host.docker.internal (Docker Desktop) or the host's LAN IP.

Containers are phones on the same office network

A user-defined network is like a small office with an internal phone directory. Each container is a phone with an extension (its IP), and the receptionist (Docker's DNS) lets you dial colleagues by name ("get me db") instead of memorizing extension numbers. Publishing a port with -p is like giving one phone a direct outside line so people beyond the office can call in.

17. Ports & DNS

How traffic gets from the outside world into a container, and how containers find each other by name.

Publish is host-facing, DNS is service-facing

A common confusion: you do not need -p for your API to talk to your database. Publishing exposes a container to the host and the outside world. Container-to-container calls on a user-defined network resolve by service/container name via Docker's built-in DNS (127.0.0.11) and work on every port. Only publish what the public actually needs.

Port mapping = a forwarding address

By default a container is sealed off — nothing outside can reach the app inside. -p 8080:80 sets up a forwarding address: "anything that knocks on the host's door number 8080, send it to door 80 inside the container." The number on the left is the door you knock on from outside (the host); the number on the right is the door the app listens on inside. Get them backwards and you'll knock on the wrong door — a super common beginner mix-up.

Port publishing

EXPOSE in a Dockerfile only documents a port. To actually let host/outside traffic in, you publish with -p.

Publishing ports
docker run -d -p 8080:80 nginx           # host 8080 -> container 80
docker run -d -p 127.0.0.1:8080:80 nginx # bind only to localhost (safer)
docker run -d -p 80:80 -p 443:443 nginx  # multiple ports
docker run -d -P nginx                    # publish all EXPOSEd ports to random host ports
docker port web                           # show a container's port mappings
SyntaxMeaning
-p 8080:80Host port 8080 → container port 80 (all host interfaces).
-p 127.0.0.1:8080:80Only reachable from the host itself — good for local-only services.
-p 80Random host port → container 80.
-p 8080:80/udpPublish a UDP port.
Publishing binds to all interfaces by default

-p 8080:80 exposes the service on every host network interface, potentially to your whole network/internet. For services only the host should reach, bind explicitly to 127.0.0.1. Don't expose databases publicly.

Embedded DNS & service discovery

Docker runs an embedded DNS server (at 127.0.0.11 inside containers) on user-defined networks. Containers resolve each other by container name and (in Compose) by service name and network aliases. This is why DATABASE_URL=postgres://...@db:5432 works — db is resolved to the database container's current IP automatically, even if it changes.

Verify name resolution
docker exec api ping -c1 db
docker exec api getent hosts db
docker exec api nslookup db

The most common port confusion, cleared up

The syntax is -p HOST:CONTAINER. The number your browser or curl uses is the left one (host); the number your app listens on inside is the right one (container). They do not have to match. Two containers can both listen on port 80 internally, as long as you map them to different host ports.

Two web servers, same internal port, different doors outside
docker run -d -p 8080:80 --name site-a nginx
docker run -d -p 8081:80 --name site-b nginx
# http://localhost:8080 → site-a's port 80
# http://localhost:8081 → site-b's port 80
docker port site-a
Output
80/tcp -> 0.0.0.0:8080
"It works with curl inside the container but not from my browser"

Nine times out of ten the app is bound to 127.0.0.1 inside the container. From the container's own point of view that works, but Docker's port forwarding delivers traffic to the container's eth0 — so the app must listen on 0.0.0.0 (all interfaces). In Express that's app.listen(3000, '0.0.0.0'); in Flask flask run --host=0.0.0.0; in many frameworks it's a HOST=0.0.0.0 env var.

A worked example: diagnose an unreachable port

Check the mapping, the listen address, and connectivity in order
docker port web                       # 1. is the port actually published?
docker exec web netstat -tlnp 2>/dev/null || docker exec web ss -tlnp
# 2. look for 0.0.0.0:80 (good) vs 127.0.0.1:80 (unreachable from outside)
curl -sSf http://localhost:8080 > /dev/null && echo OK || echo "still failing"
Listening on 0.0.0.0 vs 127.0.0.1

A building has a receptionist who can either answer only the internal phone (127.0.0.1 — calls from inside the same office) or answer every line including the outside one (0.0.0.0). Docker's forwarded calls arrive on the outside line, so if your app only answers the internal phone, those calls ring forever. Tell the app to answer all lines and the calls get through.

18. Docker Compose Basics

Real apps have multiple containers — a web app, a database, a cache, a queue. Running each with long docker run commands is painful. Docker Compose defines your whole multi-container app in one YAML file and manages it with single commands.

Compose = a stage manager for your app

Running a real app by hand means juggling several docker run commands with the right ports, networks, and order — exhausting and error-prone. Compose is like a stage manager with one script: you write down all the actors (web, database, cache) and how they connect in a single compose.yaml, then docker compose up brings the whole show to life at once. Bonus: Compose automatically puts them on a shared network so they can call each other by simple names like db instead of chasing IP addresses.

With Compose you write a compose.yaml file describing your services (containers), networks, and volumes, then bring the entire stack up or down at once. It's declarative: you describe the desired state, Compose makes it happen.

Analogy: If docker run is hiring and instructing one employee at a time, Compose is an org chart plus an onboarding script — it defines the whole team, how they connect, and starts them all with one command. Change the chart, re-run, and Compose reconciles the differences.

The core Compose workflow
docker compose up            # create & start everything (foreground)
docker compose up -d         # detached (background)
docker compose ps            # list this project's containers
docker compose logs -f       # tail logs from all services
docker compose logs -f api   # one service
docker compose down          # stop & remove containers + network
docker compose down -v       # also remove named volumes (deletes data!)
docker compose vs docker-compose

The modern tool is docker compose (v2, a plugin, space not hyphen), included with Docker Desktop and recent Docker Engine. The old standalone docker-compose (v1, Python) is deprecated. Use the space form. The file can be named compose.yaml (current standard) or docker-compose.yml (still supported).

What Compose does that raw docker run can't

Compose is not a different container engine — it is a thin coordinator that translates your YAML into ordinary Docker API calls, but it adds four conveniences that matter enormously in practice:

  • A project namespace. Every resource is prefixed with the project name (the folder name by default), so myapp_db_1, myapp_default network, etc. This lets you run many apps side by side without collisions and tear one down cleanly.
  • Automatic networking. It creates a user-defined bridge network for the project, so services resolve each other by name out of the box.
  • Declarative reconciliation. Run up again after editing the file and Compose recreates only what changed, leaving healthy services alone.
  • Dependency ordering. depends_on controls start order (and with health conditions, readiness).

A worked example: the minimal two-service app

compose.yaml
services:
  web:
    image: nginx:1.27
    ports: ["8080:80"]
  cache:
    image: redis:7-alpine
Bring it up and observe the project namespace + network
docker compose up -d
docker compose ps
docker network ls | grep "$(basename $PWD)"
Typical output
NAME              IMAGE          STATUS         PORTS
myfolder-web-1    nginx:1.27     Up 2 seconds   0.0.0.0:8080->80/tcp
myfolder-cache-1  redis:7-alpine Up 2 seconds   6379/tcp
myfolder_default  bridge  local
down -v deletes your data

docker compose down removes containers and the network but keeps named volumes. Adding -v also deletes the named volumes — which is exactly your database's data. It's the number one "why did my dev database reset?" surprise. Use down (no -v) for a normal stop, and reserve down -v for a deliberate clean slate.

Compose is a recipe for the whole meal

A single Dockerfile is a recipe for one dish. A compose.yaml is the recipe for the whole dinner — it says which dishes to make, in what order, and how they're served together on one table (network). up cooks and plates everything; down clears the table.

19. The Compose File

A complete, real-world example — a web API with a Postgres database and Redis cache — followed by a breakdown of every key.

Compose gives you networking & DNS for free

Building & iterating with Compose
docker compose up -d --build     # rebuild images then start

The depends_on trap — start order is not readiness

The most expensive Compose misunderstanding: plain depends_on: [db] only guarantees the db container is started, not that Postgres has finished initializing and is accepting connections. Your API can race ahead, try to connect, and crash. There are two correct fixes, and you usually want both:

  • Give the dependency a healthcheck, then depend on it with condition: service_healthy (as in the full example above). Compose then waits until the healthcheck passes.
  • Make the app retry its connection with backoff. Networks blip and databases restart in production — an app that assumes its dependency is always instantly available is fragile regardless of Compose.
Healthcheck + condition = the app waits for a truly-ready DB
services:
  db:
    image: postgres:16
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      retries: 10
  api:
    build: .
    depends_on:
      db:
        condition: service_healthy

A worked example: validate before you run

docker compose config resolves variables, merges override files, and prints the final configuration Compose will actually use — invaluable for catching a mistyped indentation or an unset variable before it bites you.

Resolve and sanity-check the merged config
docker compose config            # prints fully-resolved YAML (or errors)
docker compose config --services # just list service names
Example error it catches early
services.api.ports.0: invalid published port: "808O:3000"   (letter O, not zero)
YAML indentation is load-bearing

Compose files are YAML, where indentation defines structure and tabs are illegal — use spaces. A single misaligned key silently changes meaning (e.g., environment nested under the wrong service). When something behaves oddly, run docker compose config first; it re-emits the structure Compose actually parsed so you can see where your indentation went wrong.

"Started" vs "ready" — a kitchen analogy

depends_on without a healthcheck is like telling the waiter "the kitchen light is on, go take orders." But a lit kitchen isn't a ready kitchen — the ovens may still be heating. A healthcheck is the chef shouting "we're open!" Only then should the waiter (your app) start sending orders (queries). Wait for the shout, not the light.

Profiles, variable substitution, multiple files, scaling, and override patterns that make Compose production-capable.

Environment variable substitution

Using variables

Combine base + environment files
# dev: base + override (auto-merged)

Scaling services

Run multiple replicas of a service

#  Compose is single-host — for multi-host scaling use Kubernetes/Swarm)
Compose best practices
  • Pin image versions; don't rely on latest.
  • Keep secrets in .env (git-ignored) or Docker/Compose secrets — never hard-code them in the file.
  • Use healthcheck + depends_on: condition: service_healthy so apps wait for their dependencies (raw depends_on only waits for start, not ready).
  • Use named volumes for stateful data; bind mounts for dev code.
  • Separate frontend and backend networks to isolate tiers.
  • Set resource limits via deploy.resources even in Compose.
Compose vs Kubernetes — when to graduate

Compose is perfect for local development and single-host deployments. When you need to run across many machines with auto-scaling, self-healing, rolling updates, and high availability, that's Kubernetes territory (see my Kubernetes guide). Many teams use Compose for dev and Kubernetes for production — the container images are identical, only the orchestration differs.

How override files actually merge

Compose can layer multiple files, and the merge rules are worth knowing precisely because they cause "why is my prod setting ignored?" confusion. Later files are merged on top of earlier ones: scalars are replaced (a later image: wins), but lists are appended, not replaced (a later ports: adds to the earlier list, it doesn't overwrite it). When you run docker compose up with no -f, Compose implicitly loads compose.yaml then compose.override.yaml if present.

compose.yaml (base — shared everywhere)
services:
  api:
    image: myapp:1.0
    environment:
      LOG_LEVEL: info
compose.prod.yaml (production tweaks)
services:
  api:
    environment:
      LOG_LEVEL: warn        # replaces info
    deploy:
      resources:
        limits:
          cpus: "1.0"
          memory: 512M
Apply base + prod explicitly
docker compose -f compose.yaml -f compose.prod.yaml config   # verify the merge
docker compose -f compose.yaml -f compose.prod.yaml up -d
Scaling a service that publishes a fixed host port fails

docker compose up --scale web=3 asks for three web containers, but if web maps "8080:80", only one can own host port 8080 — the other two fail with "port is already allocated." Either don't publish a fixed host port on scaled services (put a reverse proxy in front and let them talk on the internal network), or use a port range. This is also a reminder that Compose is single-host; real horizontal scaling belongs to an orchestrator.

Override files = sticky notes on the base plan

Think of compose.yaml as the master blueprint and each override file as a stack of sticky notes you press on top: "in production, use less logging and cap the memory." The blueprint stays the same; the notes adjust just the details that differ per environment. That's how one base file serves dev, staging, and prod without copy-pasting.

21. Registries & Docker Hub

A registry stores and distributes images. Pushing to one is how you share images across machines, teams, and deployments.

A registry is an app store for your images

Once you've built an image, how do other machines get it? You push it to a registry — a shared warehouse in the cloud (Docker Hub, or Amazon ECR on AWS). From there, any server or teammate can pull the identical image. It's just like publishing an app to an app store so any phone can download the same version. This is what lets the image you built on your laptop run byte-for-byte identically in production.

The default registry is Docker Hub (docker.io). Others include GitHub Container Registry (ghcr.io), GitLab, Quay, and cloud registries like Amazon ECR, Google Artifact Registry, and Azure ACR. A registry holds repositories, each holding tagged versions of an image.

Push and pull
# Log in
docker login                       # Docker Hub
docker login ghcr.io               # another registry

# Tag your image for the target repository
docker tag myapp:1.0 myuser/myapp:1.0

# Push it
docker push myuser/myapp:1.0

# Pull it (from another machine)
docker pull myuser/myapp:1.0

# Search Docker Hub
docker search postgres

# Log out
docker logout
Official, verified & multi-arch images
  • Official images (e.g., nginx, postgres) are curated by Docker — prefer them as bases.
  • Multi-arch images serve the right build for your CPU (amd64, arm64) automatically via a manifest list — important for Apple Silicon and AWS Graviton.
  • Be wary of random community images — they may be outdated or malicious. Scan before trusting.
Run your own private registry 
docker run -d -p 5000:5000 --name registry registry:2
docker tag myapp:1.0 localhost:5000/myapp:1.0
docker push localhost:5000/myapp:1.0

Good for air-gapped or internal-only image distribution (add TLS + auth for real use).

How a push/pull actually works — and why it's efficient

A registry doesn't store one giant blob per image. It stores each layer separately (content-addressed by digest) plus a small manifest — a JSON document listing the layer digests and the config. When you push, Docker uploads only the layers the registry doesn't already have; when you pull, it downloads only the layers you don't already have locally. This is why pushing a new version of an app whose base image is unchanged is fast — the huge base layers are already there, and only your thin app layer travels the wire.

Watch layer-level deduplication on push
docker push myuser/myapp:1.0
Typical output — shared layers are skipped
The push refers to repository [docker.io/myuser/myapp]
5f70bf18a086: Layer already exists      <-- base layers reused
a1b2c3d4e5f6: Pushed                    <-- only your app layer uploaded
1.0: digest: sha256:9c8e... size: 1786

Tags move; digests don't

A tag (like :1.0) is just a human-friendly pointer that can be re-assigned to a new image at any time. A digest (@sha256:...) is the immutable identity of exact bytes. For reproducible production deploys, pull by digest so you get the exact image you tested, even if someone later re-pushes the tag:

Pin by digest for reproducibility
docker pull nginx:1.27
docker inspect --format '{{index .RepoDigests 0}}' nginx:1.27
# then deploy that exact digest:
docker pull nginx@sha256:1234abcd...   # always the same bytes
Rate limits and login gotchas

Anonymous pulls from Docker Hub are rate-limited — CI pipelines that pull heavily can hit "toomanyrequests" errors. Authenticate (even a free account raises the limit) or mirror images into a private registry. Also remember docker login stores credentials in ~/.docker/config.json, sometimes in base64, not encrypted — use a credential helper on shared machines.

Shipping only the new pages of a book

Imagine mailing updates to a 500-page book. You don't remail the whole book each time — you send only the pages that changed, and the recipient slots them in. Registry push/pull works the same way with layers: the unchanged "pages" (base layers) stay put, and only your new "page" (app layer) is shipped. That's why the second push of an image is so much faster than the first.

23. BuildKit & buildx

BuildKit is Docker's modern build engine (default in current Docker). buildx is the CLI front-end that unlocks its advanced features: parallel builds, better caching, build secrets, and multi-architecture images.

Why BuildKit is better

  • Parallelizes independent build stages — faster builds.
  • Smarter caching, including remote cache import/export for CI.
  • Build secrets that never end up in image layers.
  • Multi-platform images from one command.
Build secrets — safely use a secret at build time
# Dockerfile:
#   RUN --mount=type=secret,id=npmtoken \
#       NPM_TOKEN=$(cat /run/secrets/npmtoken) npm ci
docker build --secret id=npmtoken,src=$HOME/.npmtoken -t myapp:1.0 .
# The token is available during that RUN only and is NOT stored in any layer.
Multi-architecture builds (amd64 + arm64)
# Create a builder that supports multiple platforms
docker buildx create --name multi --use

# Build and push a multi-arch image in one shot
docker buildx build \
  --platform linux/amd64,linux/arm64 \
  -t myuser/myapp:1.0 \
  --push .
Cache in CI for fast builds 
docker buildx build \
  --cache-from type=registry,ref=myuser/myapp:buildcache \
  --cache-to   type=registry,ref=myuser/myapp:buildcache,mode=max \
  -t myuser/myapp:1.0 --push .

Persisting cache to a registry makes CI builds dramatically faster across runs.

How BuildKit differs mechanically from the old builder

The classic (pre-BuildKit) builder executed a Dockerfile strictly top-to-bottom, one instruction at a time, even when steps were independent. BuildKit instead parses the whole Dockerfile into a dependency graph (a DAG) and only runs what's needed, in parallel where possible. Two build stages that don't depend on each other build simultaneously; a stage whose output nobody copies is skipped entirely. This is why enabling BuildKit alone often cuts build times without changing a single line of your Dockerfile.

Confirm BuildKit is active and watch parallel stages
DOCKER_BUILDKIT=1 docker build -t myapp:1.0 .
# (BuildKit is the default in recent Docker; the output shows a clean
#  numbered, parallel step view with per-step timings)
Typical BuildKit output
 => [builder 3/5] RUN go mod download            2.1s
 => [stage-1 2/3] COPY --from=builder /app/server /   0.0s cached
 => exporting to image                            0.3s

Build secrets: the safe way to use a token during build

The dangerous old pattern was COPY .npmrc (with a token) or passing secrets via ARG — both persist in image layers and are recoverable with docker history. BuildKit's --mount=type=secret mounts the secret into a single RUN as a temporary in-memory file that never becomes a layer.

Dockerfile using a mounted secret
# syntax=docker/dockerfile:1
FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN --mount=type=secret,id=npmtoken \
    NPM_TOKEN=$(cat /run/secrets/npmtoken) npm ci
COPY . .
Provide the secret at build time
docker build --secret id=npmtoken,src=$HOME/.npmtoken -t myapp:1.0 .
docker history myapp:1.0    # the token appears NOWHERE in the layers
The syntax line is required for advanced features

Features like --mount=type=secret and --mount=type=cache need a modern Dockerfile frontend. Put # syntax=docker/dockerfile:1 as the very first line so BuildKit fetches the current frontend. Forgetting it produces confusing "unknown flag" errors on the RUN --mount line.

Old builder = one cook; BuildKit = a coordinated kitchen

The old builder was a single cook doing every step in order, even chopping vegetables while the oven sat empty. BuildKit is a head chef who reads the whole recipe first, then runs independent tasks at once (oven preheats while veggies are chopped) and skips any dish nobody ordered. Same ingredients, same result — far less waiting.

24. Security

Containers add isolation, but security is not automatic. These practices meaningfully reduce risk.

Namespaces vs cgroups in one line

Namespaces are the frosted-glass walls of the apartment — you can't see your neighbours. cgroups are the utility meters — you only get so much electricity and water before it's cut off. A container is just a normal Linux process wearing both.

The container security checklist
  1. Run as non-root — add a USER; combine with --user at runtime. Root in a container is closer to root on the host than you'd like.
  2. Use minimal base images — distroless/alpine shrink the attack surface (fewer packages = fewer CVEs).
  3. Scan images for vulnerabilities — Trivy, Docker Scout, ECR scanning. Scan in CI and block on criticals.
  4. Never bake secrets into images — use build secrets and runtime injection.
  5. Drop Linux capabilities — --cap-drop ALL, add back only what's needed.
  6. Read-only root filesystem — --read-only with a writable tmpfs for scratch.
  7. Prevent privilege escalation — --security-opt no-new-privileges.
  8. Never use --privileged for app containers — it grants near-full host access.
  9. Set resource limits — prevent DoS from a runaway container.
  10. Keep Docker & base images updated — patch known CVEs.
A hardened run command
docker run -d \
  --user 1000:1000 \
  --read-only \
  --tmpfs /tmp \
  --cap-drop ALL \
  --security-opt no-new-privileges \
  --memory 512m --cpus 1 \
  --restart unless-stopped \
  myapp:1.0
Scan an image
# Docker Scout (built into Docker)
docker scout cves myapp:1.0

# Trivy (popular open-source scanner)
trivy image myapp:1.0
The two biggest real-world mistakes
  1. Running as root — a container escape then means host root. Add USER.
  2. Secrets in images / committed .env files — they leak via layers and version control. Use secret mounts and managers.

Why "root in a container" is dangerous — the mechanics

By default the process inside a container runs as UID 0 (root), and — unless you use user namespaces — that is the same UID 0 as the host's root. The container's namespaces normally keep that root confined, but the isolation is only as strong as the kernel. If the app is root and an attacker exploits a kernel bug or a misconfigured mount, they can potentially act as root on the host. Running as an unprivileged UID means that even a full container compromise starts from a far weaker position.

See who your container runs as (and fix it)
docker run --rm myapp:1.0 id
# uid=0(root) gid=0(root)   <-- bad default

# With a non-root USER in the Dockerfile, or --user at runtime:
docker run --rm --user 1000:1000 myapp:1.0 id
# uid=1000 gid=1000         <-- much safer

A worked example: scan, then harden

Find vulnerabilities before shipping
docker scout cves myapp:1.0
Typical output — actionable, not just noise
  ✓ Image stored for indexing
  ✗ 2C     1H     4M     high severity: CVE-2024-XXXX in libssl (fixed in 3.0.13)
  Recommendation: bump base image to alpine:3.20

The typical remediation loop is: scan → bump the base image or dependency that carries the CVE → rebuild → rescan. Wiring this into CI (and failing the build on critical findings) stops known-vulnerable images from ever reaching production.

Capabilities and --privileged, demystified

Linux splits root's power into ~40 discrete capabilities (bind low ports, change file ownership, load kernel modules, etc.). Docker grants a limited default set. --cap-drop ALL then --cap-add only what you need shrinks the blast radius. --privileged does the opposite — it hands the container all capabilities plus device access, effectively removing the security boundary. Never use it for application containers; reserve it for rare, trusted cases like Docker-in-Docker.

Defense in depth = locks on every door

Container security isn't one big wall; it's many small locks. Run as a non-root user (don't hand out the master key), use a tiny base image (fewer doors to lock), drop capabilities (take away tools the intruder could use), make the filesystem read-only (nail the windows shut), and scan for known-bad locks (CVEs). No single measure is perfect, but stacked together an attacker who gets past one still faces the next.

Why image size matters more than beginners expect

Image size is not vanity — it compounds across your whole system. Every deploy pulls the image; every new node in an autoscaling group pulls it; every CI job may pull it. A 1.2 GB image versus a 40 MB one is the difference between a 90-second cold start and a 3-second one, multiplied by hundreds of pulls a day. Smaller images also mean fewer installed packages, which means fewer CVEs to patch — size and security move together.

A worked example: measure, then cut

The workflow is always measure first. docker history shows the size each instruction added, so you can target the biggest offenders instead of guessing.

Find the fat layers
docker history myapp:1.0 --format 'table {{.Size}}\t{{.CreatedBy}}' | head
Typical output — the culprit is obvious
SIZE      CREATED BY
0B        CMD ["node" "server.js"]
310MB     RUN npm install                      <-- includes devDependencies!
1.1MB     COPY . .

Here the fix is clear: switch to npm ci --omit=dev (or a multi-stage build) so the 310 MB of dev dependencies never reach the final image, and consider an -alpine base to trim the 78 MB OS layer.

The single highest-leverage change

If you do only one thing, adopt a multi-stage build with a slim runtime base. For compiled languages (Go, Rust, C) the final image can be just the static binary on scratch or distroless — often under 20 MB. For interpreted languages, ship only production dependencies on an -alpine or -slim base. This one pattern usually beats every other micro-optimization combined.

Alpine's hidden cost: musl vs glibc

Alpine is tiny because it uses musl libc instead of the more common glibc. Most software works, but some native extensions and prebuilt binaries expect glibc and will fail or run slowly (Python packages with C extensions are a frequent example, and some report DNS resolution quirks). If you hit strange runtime errors on Alpine, try a -slim (Debian glibc) base before spending hours debugging — the few extra MB are often worth it.

Pack a carry-on, not a moving truck

Shipping a container is like traveling. A bloated image is a moving truck full of furniture you'll never use on the trip — slow to load, slow to unload, expensive to move around. Optimizing is packing a carry-on: only what the app actually needs to run. You get through the airport (deploys and autoscaling) far faster, and there's less stuff for a thief (attacker) to rummage through.

28. Containerizing Node.js / Express

The most common containerized stack. Watch out for node_modules, PID 1 signal handling, and dev-vs-prod dependencies.

Production Node.js — multi-stage, non-root, cache-optimized
# ---- deps: install production dependencies only ----
FROM node:20-alpine AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci --omit=dev

# ---- build: compile TypeScript / bundle (if you have a build step) ----
FROM node:20-alpine AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci                       # full deps incl. dev (tsc, webpack)
COPY . .
RUN npm run build                # -> produces /app/dist

# ---- runtime: tiny, non-root ----
FROM node:20-alpine AS runtime
ENV NODE_ENV=production
WORKDIR /app
# tini gives us a proper init to reap zombies + forward signals
RUN apk add --no-cache tini
COPY --from=deps  /app/node_modules ./node_modules
COPY --from=build /app/dist ./dist
COPY package.json ./
USER node
EXPOSE 3000
HEALTHCHECK --interval=30s --timeout=3s --start-period=20s \
  CMD wget -qO- http://127.0.0.1:3000/health || exit 1
ENTRYPOINT ["/sbin/tini", "--"]
CMD ["node", "dist/server.js"]
The three classic Node.js container mistakes
  • Copying node_modules from your host. Native modules are compiled for your OS/arch and will break in the container. Always npm ci inside the build, and add node_modules to .dockerignore.
  • Using npm install instead of npm ci. ci is faster, reproducible, and respects the lockfile exactly.
  • Running node as PID 1 with no init. Node doesn't reap child zombies or forward SIGTERM well. Use tini (shown above) or docker run --init so graceful shutdown works.
Handle SIGTERM for zero-downtime deploys

Orchestrators send SIGTERM then wait, then SIGKILL. Close the server and drain connections on SIGTERM:

const server = app.listen(3000);
process.on('SIGTERM', () => {
  console.log('SIGTERM received, draining...');
  server.close(() => process.exit(0));
});

29. Containerizing Python & Django / Flask

Python containers hinge on getting the interpreter base right, using virtualenvs across stages, and running WSGI/ASGI apps behind a real server like Gunicorn or Uvicorn.

Production Django — multi-stage venv, non-root, Gunicorn
# ---- build stage: compile wheels ----
FROM python:3.12-slim AS build
ENV PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1
WORKDIR /app
RUN apt-get update && apt-get install -y --no-install-recommends build-essential libpq-dev \
    && rm -rf /var/lib/apt/lists/*
RUN python -m venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# ---- runtime stage: copy the venv, no compilers ----
FROM python:3.12-slim AS runtime
ENV PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1 PATH="/opt/venv/bin:$PATH"
WORKDIR /app

    && rm -rf /var/lib/apt/lists/* \
    && useradd --create-home --uid 1000 appuser

COPY . .
RUN python manage.py collectstatic --noinput

HEALTHCHECK --interval=30s --timeout=3s CMD python -c "import urllib.request;urllib.request.urlopen('http://127.0.0.1:8000/healthz')" || exit 1
CMD ["gunicorn", "myproject.wsgi:application", "--bind", "0.0.0.0:8000", "--workers", "3", "--timeout", "60"]
Migrations: never run them in the image build

manage.py migrate touches the database, which doesn't exist at build time and must run once per deploy — not once per replica. Run it as an init container (Kubernetes), a Compose depends_on one-shot service, or a release command. Only collectstatic (which is DB-free) belongs in the build.

services:

    environment: { POSTGRES_PASSWORD: ${DB_PASSWORD:?set me} }
    volumes: [ "pgdata:/var/lib/postgresql/data" ]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      retries: 5
  migrate:
    build: .
    command: python manage.py migrate --noinput
    depends_on:
      db: { condition: service_healthy }
  web:
    build: .
    ports: ["8000:8000"]
    depends_on:
      migrate: { condition: service_completed_successfully }
volumes: { pgdata: {} }
Flask / FastAPI differences

Same shape. For Flask, use Gunicorn (gunicorn app:app). For FastAPI (async/ASGI), use Uvicorn workers: gunicorn app:app -k uvicorn.workers.UvicornWorker or run uvicorn directly. Choose python:3.12-slim over alpine for Python — alpine uses musl libc, which breaks many pre-built wheels and forces slow source compiles.

30. Containerizing Java / Spring Boot

Java is the poster child for multi-stage builds: a fat build toolchain (JDK + Maven/Gradle) produces a small artifact (a jar) that runs on a lean JRE.

Spring Boot — multi-stage with layered jar for better caching
# ---- build stage ----
FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /src
COPY pom.xml .
RUN mvn -B dependency:go-offline          # cache deps layer
COPY src ./src
RUN mvn -B clean package -DskipTests

# ---- extract Spring Boot layers (deps change rarely, code often) ----
FROM eclipse-temurin:21-jre AS layers
WORKDIR /app
COPY --from=build /src/target/*.jar app.jar
RUN java -Djarmode=layertools -jar app.jar extract

# ---- runtime stage ----
FROM eclipse-temurin:21-jre AS runtime
WORKDIR /app
RUN useradd -r -u 1000 spring
COPY --from=layers /app/dependencies/ ./
COPY --from=layers /app/spring-boot-loader/ ./
COPY --from=layers /app/snapshot-dependencies/ ./
COPY --from=layers /app/application/ ./
USER spring
EXPOSE 8080
# Respect container memory limits (crucial for the JVM!)
ENV JAVA_OPTS="-XX:MaxRAMPercentage=75.0 -XX:+UseG1GC"
HEALTHCHECK --interval=30s --timeout=3s --start-period=40s \
  CMD wget -qO- http://127.0.0.1:8080/actuator/health || exit 1
ENTRYPOINT ["sh","-c","java $JAVA_OPTS org.springframework.boot.loader.launch.JarLauncher"]
The JVM memory trap in containers

Before JDK 10, the JVM read the host's total RAM, not the container's cgroup limit — so it would try to grab far more memory than the container allowed and get OOM-killed. Modern JDKs (11+) are container-aware, but you still must size the heap with -XX:MaxRAMPercentage (e.g. 75%) rather than a fixed -Xmx, so it scales with whatever limit the orchestrator gives the container.

Skip the Dockerfile entirely with build plugins

Spring Boot can build an optimized OCI image with no Dockerfile using Cloud Native Buildpacks: mvn spring-boot:build-image or gradle bootBuildImage. Google's Jib (mvn com.google.cloud.tools:jib-maven-plugin:build) builds reproducible, daemonless, layered images and pushes straight to a registry. Great for teams that don't want to hand-maintain Dockerfiles.

31. Containerizing Go

Go compiles to a single static binary — this yields the smallest, most secure images possible (often under 10 MB on scratch or distroless).

Go — static binary on distroless (≈8 MB image)
# ---- build ----
FROM golang:1.22 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
# CGO off + static build so it runs on scratch/distroless
RUN CGO_ENABLED=0 GOOS=linux go build -ldflags="-s -w" -o /app/server ./cmd/server

32. Containerizing a React / SPA Frontend (Nginx)

Frontends are compiled to static files, then served by a tiny web server — a textbook two-stage build.

33. Healthchecks, Init & Graceful Shutdown

A container that's "running" isn't necessarily "healthy." Healthchecks + proper signal handling are what make deploys safe and self-healing.

Healthcheck = "are you actually okay?"

A process can be running but stuck — deadlocked, out of DB connections, or still booting. A healthcheck is a small command the platform runs periodically to ask "can you really serve traffic?" If it fails repeatedly, the orchestrator stops sending traffic and can restart the container. Two kinds you'll meet in Kubernetes: a liveness probe ("restart me if I'm hung") and a readiness probe ("don't send traffic until I say I'm ready").

Dockerfile HEALTHCHECK anatomy
HEALTHCHECK --interval=30s \    # how often to check
            --timeout=3s \      # fail if the check takes longer
            --start-period=40s \# grace window during startup
            --retries=3 \       # consecutive fails before "unhealthy"
  CMD wget -qO- http://127.0.0.1:8080/healthz || exit 1
Design two endpoints, not one

Expose /livez (cheap — process is up) and /readyz (checks dependencies: DB reachable, caches warm). Liveness should not check the database — otherwise a brief DB blip restarts every replica in a storm. Readiness should, so traffic pauses gracefully instead.

36. Supply Chain Security — SBOM, Scanning & Signing

"What's actually inside my image, and can I prove it wasn't tampered with?" Lead engineers own the answer. This is the fastest-growing area of container security.

SBOM = the ingredients label on your image

A Software Bill of Materials lists every package and version baked into your image — like the ingredients panel on food. When the next big CVE drops (think Log4Shell), you grep your SBOMs to instantly answer "are we affected, and where?" instead of frantically rebuilding to check. Signing is the tamper-proof seal: it proves the image you're about to run is exactly the one your pipeline built.

Generate an SBOM, scan for CVEs, and sign
# 1. SBOM — what's inside (syft)
syft myapp:1.0 -o spdx-json > sbom.spdx.json

# 2. Scan for known vulnerabilities (trivy) — fail the build on HIGH/CRITICAL
trivy image --severity HIGH,CRITICAL --exit-code 1 myapp:1.0

# 3. Sign the image + attach the SBOM as an attestation (cosign, keyless via OIDC)
cosign sign myregistry/myapp:1.0
cosign attest --predicate sbom.spdx.json --type spdxjson myregistry/myapp:1.0

# 4. Later, verify before running
cosign verify myregistry/myapp:1.0 --certificate-identity=... --certificate-oidc-issuer=...
Bake this into CI and pin base images by digest

Run scan + SBOM + sign on every image build; block merges/deploys on CRITICAL CVEs with an allow-list for accepted risks. Pin base images by digest (FROM python:3.12-slim@sha256:...) not just tag, so :slim can't silently change under you. Rebuild regularly to absorb upstream security patches even when your code hasn't changed.

38. BuildKit: Cache Mounts & Build Secrets

BuildKit (the modern Docker builder) unlocks two power features that dramatically speed up builds and keep them secure: cache mounts (persist package caches across builds) and build secrets (use a secret during build without baking it into the image).

Cache mounts = keep the toolbox between jobs

Normally every build re-downloads all your dependencies from scratch — like buying new tools for every job and throwing them away. A cache mount keeps that package cache on the build machine between builds, so npm install or pip install reuses what it already downloaded. Builds go from minutes to seconds. And a build secret lets you use, say, a private-registry token during the build that never gets stored in the final image layers.

Cache mounts — reuse the dependency cache across builds
# syntax=docker/dockerfile:1
FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
# Mount a persistent cache for npm — survives between builds, not stored in the image
RUN --mount=type=cache,target=/root/.npm \
    npm ci
COPY . .
RUN npm run build
Build secrets — use a token at build time, never store it
# syntax=docker/dockerfile:1
FROM python:3.12-slim
# The secret is mounted only for THIS command and never written to a layer
RUN --mount=type=secret,id=pip_token \
    PIP_INDEX_URL="https://$(cat /run/secrets/pip_token)@pypi.acme.io/simple" \
    pip install --no-cache-dir mypackage
Build passing the secret from the host
DOCKER_BUILDKIT=1 docker build --secret id=pip_token,env=PIP_TOKEN -t myapp .
# The token is used during build but does NOT appear in `docker history` or any layer.
Never use build ARGs for secrets

A common mistake: passing a password via --build-arg. Build args are stored in the image history — anyone with the image can run docker history and read them. Always use --mount=type=secret for anything sensitive at build time, or better, fetch secrets at runtime from a secrets manager (see the Security guide).

39. Multi-Architecture Images

Apple Silicon laptops (ARM) and AWS Graviton (ARM) servers are everywhere, alongside traditional x86. A multi-arch image runs natively on all of them from one tag — essential for modern teams.

Build & push multi-arch with buildx
# One-time: create a builder that supports multiple platforms
docker buildx create --name multi --use
docker buildx inspect --bootstrap

# Build for amd64 AND arm64 and push the manifest list in one command
docker buildx build --platform linux/amd64,linux/arm64 \
  -t myregistry/myapp:1.0 --push .

# Verify the manifest lists both architectures
docker buildx imagetools inspect myregistry/myapp:1.0
Why this matters for cost & speed

ARM (Graviton) instances are typically ~20-40% cheaper per performance than x86 (see the Cloud EC2 section). Shipping arm64 images lets you run on them. And developers on Apple Silicon get native-speed local containers instead of slow emulation. Multi-arch is the "build once, run anywhere — including cheaper hardware" win.

40. Compose Profiles & Overrides

One Compose file often needs to behave differently in dev vs CI vs demo. Profiles turn services on/off per scenario, and override files layer environment-specific settings — no duplication.

Profiles: only start what a scenario needs
services:
  app:
    build: .
    ports: ["3000:3000"]
  db:
    image: postgres:16
  # Only started when the 'tools' profile is active
  adminer:
    image: adminer
    profiles: ["tools"]
  # Only for load testing
  k6:
    image: grafana/k6
    profiles: ["loadtest"]

# docker compose up                    -> app + db only
# docker compose --profile tools up     -> app + db + adminer
# docker compose --profile loadtest up  -> app + db + k6
Override files: base + environment-specific layers
# docker-compose.yml (base, committed) + docker-compose.override.yml (auto-applied in dev)
# For prod, layer an explicit file:
#   docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d

# docker-compose.prod.yml (only the differences)
services:
  app:
    restart: always
    environment:
      NODE_ENV: production
    deploy:
      resources:
        limits: { cpus: "1.0", memory: 512M }
One source of truth, many environments

Keep a single base Compose file with the service topology, then layer overrides for dev/prod and use profiles for optional tooling. This mirrors the same "config layering" idea as Kustomize in Kubernetes and Terraform environments — define the shape once, vary only what differs.

41. Debugging Running Containers

When a container misbehaves in production, you need to look inside without rebuilding. Here's the practical debugging toolkit — including for distroless images that have no shell.

The container debugging toolkit
# What's happening right now?
docker stats                          # live CPU/mem/net/IO per container
docker logs -f --tail 100 myctr       # follow recent logs
docker top myctr                      # processes inside the container
docker inspect myctr                  # full config, mounts, network, env, health

# Get a shell inside (if the image has one)
docker exec -it myctr sh              # or bash

# Distroless / no shell? Attach a debug toolbox that shares its namespaces:
docker debug myctr                    # Docker Desktop
# ...or run a sidecar sharing the target's PID + network namespace:
docker run -it --pid=container:myctr --network=container:myctr \
  --cap-add SYS_PTRACE nicolaka/netshoot

# Inspect why a container exited
docker inspect myctr --format '{{.State.ExitCode}} {{.State.Error}}'
docker events &                       # watch lifecycle events live
nicolaka/netshoot — the network debugging Swiss army knife

This image packs dig, curl, tcpdump, ss, iftop, and more. Run it sharing a container's (or pod's) network namespace to debug connectivity from exactly that container's network view — invaluable when a container "can't reach" something. In Kubernetes the equivalent is kubectl debug with ephemeral containers (see the Kubernetes guide).

Debugging distroless without breaking security

Distroless images have no shell by design (smaller attack surface). Don't add one back to production. Instead use docker debug, a namespace-sharing sidecar (above), or in Kubernetes kubectl debug -it <pod> --image=nicolaka/netshoot --target=<container>. You get full tooling temporarily without weakening the actual image.

42. Troubleshooting Playbook

A systematic approach plus a lookup table for the most common Docker problems. When something breaks, follow the flow — don't guess.

The universal debugging flow

  1. What's the state? docker ps -a — is it running, exited, or restarting? Note the exit code.
  2. Read the logs: docker logs <container> (add --tail 100 / -f). Most app failures explain themselves here.
  3. Inspect it: docker inspect <container> — check State, ExitCode, OOMKilled, Mounts, env, and network.
  4. Get inside (if running): docker exec -it <container> sh to poke around.
  5. Reproduce interactively: docker run -it --rm --entrypoint sh <image> to test the image manually.
  6. Check resources & daemon: docker stats, docker system df, docker info.

Container problems

SymptomLikely cause & fix
Container exits immediatelyThe main process finished or errored. Check docker logs. For long-running apps, ensure the CMD/ENTRYPOINT starts a foreground process (containers stop when PID 1 exits). A shell script must not background the app.
Exit code 137Killed by SIGKILL — usually OOMKilled (out of memory) or a forced stop. Check docker inspect -f '{{.State.OOMKilled}}'; raise --memory or fix the leak.
Exit code 139Segmentation fault (SIGSEGV) — a bug in the app/binary or an architecture mismatch (arm64 image on amd64).
Exit code 143Terminated by SIGTERM (graceful stop) — often expected.
Restarting loopApp crashes on start + a restart policy. Read logs; fix config/dependency. Temporarily set --restart no to inspect.
exec format errorWrong CPU architecture. Build/pull the right platform (--platform) or a multi-arch image.
Container can't be removedIt's running — stop first, or docker rm -f.

Image & build problems

SymptomCause & fix
pull access denied / not foundWrong image name, private image without login, or wrong registry. docker login and verify the full reference.
Build fails at a RUN stepRead the error above the failure. Reproduce by running an earlier stage's shell: build with --target or start a shell in the base image and run the command manually.
Changes not taking effectStale build cache or you're running an old image. Rebuild (--no-cache if needed) and confirm the tag you run matches what you built.
Image huge / slow to buildBloated context or no multi-stage. Add .dockerignore, use multi-stage, order layers by change frequency. Inspect with docker history.
COPY failed: no such filePath is outside the build context or excluded by .dockerignore. Paths are relative to the context root.

Networking & storage problems

SymptomCause & fix
Can't reach app on published portApp bound to 127.0.0.1 inside the container (bind to 0.0.0.0), wrong -p mapping, or app not up. Check logs + docker port.
Containers can't talk by nameOn the default bridge (no DNS) or different networks. Put them on the same user-defined network / same Compose project.
port is already allocatedHost port in use. Change host port or stop the conflicting process/container.
Data lost on recreateNo volume used, or wrong mount path. Mount a named volume at the app's data directory.
Permission denied on volumeHost/container UID mismatch. Align users (--user) or fix ownership.
"no space left on device"Disk full. docker system df then prune images/containers/build cache carefully.

Daemon problems

SymptomCause & fix
Cannot connect to the Docker daemonDaemon not running or no permission. Start it (sudo systemctl start docker), ensure you're in the docker group (or use sudo), and check DOCKER_HOST.
Docker Desktop won't startVirtualization/WSL2 issue. Ensure virtualization is enabled in BIOS and WSL2 is installed/updated.
Everything slow / disk fillingAccumulated images, stopped containers, build cache. Regular docker system prune and lifecycle hygiene.
