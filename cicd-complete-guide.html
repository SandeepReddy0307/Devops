1. What is CI/CD?

Let's define the three letters precisely, because people use them loosely.

CI/CD in everyday terms

Imagine a robot assembly line for your software. Every time a developer drops a code change on the belt (a Git push), the line automatically assembles it (build), inspects it (test), and — if it passes — ships it to customers (deploy). CI is the build-and-inspect part; CD is the shipping part. The whole point: no slow, error-prone manual steps, and problems get caught within minutes instead of weeks.

CI/CD stands for Continuous Integration and Continuous Delivery (or Continuous Deployment). It's a set of practices — enabled by automation tools — that let teams deliver code changes more frequently, reliably, and safely.

TermWhat it means
CI — Continuous IntegrationDevelopers merge their code changes into a shared repository frequently (often many times a day). Each merge automatically triggers a build and automated tests, so integration problems are caught within minutes, not weeks.
CD — Continuous DeliveryEvery change that passes CI is automatically prepared for release and can be deployed to production at the push of a button. The final deploy is a manual decision, but everything up to it is automated.
CD — Continuous DeploymentGoes one step further: every change that passes all automated checks is deployed to production automatically, with no human gate. Requires strong testing and confidence.
Delivery vs Deployment — the key distinction

Both are "CD." The only difference is the final step to production:

  • Continuous Delivery = automatically ready to deploy; a human clicks "release."
  • Continuous Deployment = automatically deployed; no human click.

Continuous Deployment requires Continuous Delivery, which requires Continuous Integration. They build on each other.

The pipeline at a glance

Code push→ Build→ Test→ Scan→ Artifact→ Deploy staging→ Deploy prod

Everything left of "Deploy staging" is broadly CI; everything from packaging the artifact through deploying is CD. The whole automated sequence is a pipeline.

Why CI/CD exists at all

The three letters aren't just jargon — each solves a specific, expensive problem. Continuous Integration exists because merging code is exponentially harder the longer you wait: if ten developers each work in isolation for two weeks, the day they combine their work is a nightmare of conflicting changes. Integrating every few hours keeps each merge tiny. Continuous Delivery exists because manual release steps are where humans make mistakes at 6pm on a Friday — automating them makes releases boring and repeatable. Continuous Deployment exists to close the last gap: the time between "code is ready" and "users have it," which is pure waiting with no value added.

How it actually works, mechanically

Under the hood there is no magic — just a piece of software (the CI/CD server) listening for events. When you git push, your Git host (GitHub, GitLab, etc.) fires a webhook: an HTTP POST to the CI system saying "commit abc123 landed on branch main." The CI system reads your pipeline definition file from that commit, allocates a fresh machine (a runner), and executes each step as a shell command on that machine. It streams the output back to you live and records a pass/fail status. If everything is green and the pipeline says "deploy," it runs the deploy commands too. That's the whole loop: event → read config → run commands on a machine → report result.

Worked example — the smallest possible CI/CD loop

This tiny workflow demonstrates the entire event→build→test→deploy loop. On every push to main, GitHub spins up a Linux VM, checks out your code, builds it, tests it, and — only if both succeed — deploys.

.github/workflows/hello-cicd.yml
name: hello-cicd
on:
  push:
    branches: [main]          # the EVENT that triggers everything
jobs:
  ship:
    runs-on: ubuntu-latest    # GitHub allocates a fresh VM (the runner)
    steps:
      - uses: actions/checkout@v4          # clone the repo at this commit
      - run: echo "Building..." && make build   # CI: build
      - run: make test                     # CI: test (fails the job if tests fail)
      - run: ./deploy.sh                   # CD: only runs if the steps above passed
Common mistakes & gotchas
  • Confusing "CI" with "just running tests." CI is the practice of integrating frequently; the automated build/test is what makes that safe. Running tests on a branch nobody merges for a month is not CI.
  • Calling something "Continuous Deployment" when a human still clicks approve. That's Continuous Delivery. The word "deployment" specifically means no human gate.
  • Thinking you need Continuous Deployment to benefit. Most of the value is in solid CI. Adding automated deploy is incremental.
  • Assuming the pipeline "just knows" what to do. It only does exactly what your config file says, in order. There is no hidden intelligence.
Mental model

Picture a vending machine wired to your codebase. Pushing code is inserting a coin. The machine automatically runs a fixed sequence of internal steps (build, test, ship) and either drops out a working release or lights up "error" — every single time, identically, without you reaching inside. CI is the "test the product is good" part; CD is the "drop it into the tray for the customer" part.

2. Why CI/CD Exists — the problems it solves

To appreciate CI/CD, picture software delivery without it.

Life before CI/CD ("integration hell")

Teams worked in isolation for weeks, then tried to merge everyone's code together right before a release. This "big bang" integration surfaced hundreds of conflicts and bugs all at once. Builds were done by hand on someone's machine. Testing was manual and skipped under deadline pressure. Deployments were tense, error-prone, weekend-long rituals documented in fragile runbooks. A bad release meant a frantic manual rollback.

Analogy: Without CI/CD, shipping software is like a group essay where everyone writes their section separately for a month, then frantically tries to staple it all together the night before it's due — discovering the intro contradicts the conclusion and two people wrote the same paragraph. CI/CD is like a shared live document with spell-check and grammar-check running continuously: problems surface the moment they're introduced, while they're small and cheap to fix.

What CI/CD delivers

BenefitWhy it matters
Catch bugs earlyAutomated tests run on every change — a bug found in minutes costs far less than one found in production.
Faster releasesShip multiple times a day instead of once a quarter. Value reaches users sooner.
Consistency & repeatabilityThe same automated steps run every time — no forgotten manual steps, no "works on my machine."
Lower riskSmall, frequent changes are easier to test, review, and roll back than giant releases.
Developer confidenceA green pipeline means "this change is safe." Developers ship without fear.
Faster recoveryAutomated rollbacks and small changes mean incidents are resolved in minutes.
The core principle: automate everything repeatable

If a step is done the same way every release, a machine should do it. Humans are for decisions and creativity, not for copy-pasting deploy commands at midnight. CI/CD is the automation of the boring, error-prone parts of shipping software.

Why the pain was so specific

The problems CI/CD solves aren't vague "it's slow" complaints — they're concrete failure modes. Merge conflicts scale super-linearly: two branches that diverge for a day conflict a little; branches that diverge for a month conflict catastrophically, because both sides refactored the same files. Manual deploys have a non-zero error rate per step: a 12-step runbook done by a tired human at 11pm will eventually skip a step. Untested code accumulates hidden breakage: without automated tests on every change, a bug introduced Monday isn't discovered until the Friday release, by which point twenty more changes are layered on top and nobody knows which one broke it.

How CI/CD mechanically removes each pain

Frequent integration means the "diff" the pipeline has to reason about is tiny, so conflicts and test failures point at one small change. Automation means the deploy runbook is code that runs identically every time — the human error rate on repeated steps drops to zero. And running tests on every commit means a break is caught within minutes of the commit that caused it, while the author still remembers the change and before anything is stacked on top.

Worked example — the cost of finding a bug late vs early

A gate that runs on every pull request turns a "found in production" bug into a "found before merge" bug. This single job is the difference between a 2-minute fix and a 3am incident.

A PR gate that catches bugs before they ever merge
on: [pull_request]           # runs on EVERY proposed change, before merge
jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm test          # a failure here BLOCKS the merge button
# Result: broken code physically cannot reach main. The bug is caught
# minutes after it's written, by the person who wrote it.
Common mistakes & gotchas
  • Adopting CI tools but keeping long-lived feature branches. You get the tool but not the practice — you're back in integration hell, just with fancier logs.
  • Treating "faster releases" as the only goal. The bigger win is lower risk: small, frequently-shipped changes are far easier to debug and reverse.
  • Letting the pipeline stay red. A perpetually-broken pipeline trains everyone to ignore it, which throws away the entire early-detection benefit.
Mental model

CI/CD is like continuous spell-check versus proofreading at the end. Without it, everyone writes their chapter alone and you proofread the whole 300-page book the night before printing — finding contradictions everywhere. With it, the red squiggle appears the instant you type a typo, so the manuscript is always nearly-publishable.

3. Core Vocabulary

These terms appear constantly across every tool. Learn them once and every tool makes sense.

TermMeaning
PipelineThe full automated sequence from code change to deployment. Made of stages/jobs.
Stage / PhaseA logical grouping of work (e.g., "build", "test", "deploy"). Stages usually run in order.
JobA unit of work within a pipeline that runs on a single machine/runner. Jobs can run in parallel.
Step / TaskA single command or action within a job (e.g., "run npm install").
Runner / Agent / ExecutorThe machine (VM, container, or physical) that actually executes the jobs.
Trigger / EventWhat starts a pipeline — a push, a pull request, a schedule, a manual click, a tag.
ArtifactThe output of a build — a compiled binary, a Docker image, a zip. Passed between stages or stored for deploy.
WorkflowGitHub Actions' name for a pipeline (a YAML file defining triggers + jobs).
EnvironmentA deployment target: dev, staging, production, etc.
BuildCompiling/packaging source code into a runnable artifact.
Quality gateA pass/fail check that must succeed for the pipeline to continue (tests, coverage, security scan).
CacheStored dependencies/build outputs reused across runs to speed up pipelines.
SecretSensitive value (token, password, key) injected securely into a pipeline, never hard-coded.
RollbackReverting to a previous working version after a bad deploy.
Tools use different words for the same ideas

A "job's machine" is a runner in GitHub Actions/GitLab, an agent/node in Jenkins, and an executor in CircleCI. A "pipeline" is a workflow in GitHub Actions and a Jenkinsfile pipeline in Jenkins. Once you know the concepts, translating between tools is just vocabulary.

How the pieces nest (this is the whole hierarchy)

The vocabulary looks like a flat glossary, but the terms are actually nested containers, and understanding the nesting is what makes every tool click. A pipeline contains one or more stages; each stage contains one or more jobs; each job runs on exactly one runner and contains an ordered list of steps. A trigger starts the pipeline; artifacts flow between jobs; a cache is restored at the start of a job and saved at the end; secrets are injected into steps as environment variables; a quality gate is just a step whose failure stops everything downstream.

Worked example — every vocabulary term labelled in one file
One pipeline with every core term annotated
on: [push]                    # TRIGGER — the event that starts the PIPELINE
jobs:
  build:                      # a JOB
    runs-on: ubuntu-latest    # the RUNNER (the machine this job executes on)
    steps:                    # ordered list of STEPS
      - uses: actions/checkout@v4
      - uses: actions/cache@v4              # CACHE — reused deps to go faster
        with: { path: ~/.npm, key: npm-${{ hashFiles('package-lock.json') }} }
      - run: npm ci && npm run build        # a STEP (a shell command)
      - run: npm test                       # QUALITY GATE — failure stops the pipeline
      - uses: actions/upload-artifact@v4    # ARTIFACT — the output we keep
        with: { name: dist, path: dist/ }
  deploy:                     # another JOB
    needs: build              # STAGE ordering — waits for build to finish
    environment: production   # ENVIRONMENT — the deployment target
    steps:
      - run: ./deploy.sh
        env: { TOKEN: ${{ secrets.DEPLOY_TOKEN }} }   # SECRET injected securely
Common mistakes & gotchas
  • Confusing "stage" and "job." A stage is a logical phase (test); a job is a concrete unit of execution on one machine. One stage can contain many parallel jobs.
  • Confusing artifact and cache (covered in depth in §9) — an artifact is something you need; a cache is something you'd merely like for speed.
  • Assuming jobs share a disk. Each job usually runs on a different runner with its own clean filesystem — that's why artifacts exist to pass files between them.
Mental model

Think Russian nesting dolls: pipeline ▸ stage ▸ job ▸ step. The outermost doll (pipeline) is opened by a trigger; the innermost doll (step) is a single command. Runners are the tables you set the dolls on; artifacts are notes you pass from one table to the next.

4. Version Control & Pipeline Triggers

CI/CD is built on top of version control (almost always Git). The pipeline reacts to what happens in the repository.

Match the trigger to the cost of the work

Run cheap, fast feedback (lint, unit tests) on every PR and push so developers learn about problems in seconds. Reserve expensive work — full E2E suites, image builds, deploys — for events that warrant it (merge to main, a release tag, or a nightly schedule). Wiring the same pipeline to fire on everything is the most common cause of slow, costly CI.

Git is the foundation

Every CI/CD pipeline watches a Git repository. When code changes in a specific way, the pipeline triggers. So a little Git fluency is essential: commits (saved changes), branches (parallel lines of work), merges / pull requests (PRs) / merge requests (MRs) (proposing to combine branches), and tags (named points, often releases like v1.2.0).

Common triggers

TriggerWhen it firesTypical use
PushCode is pushed to a branch.Run CI on feature branches; deploy on push to main.
Pull/Merge RequestA PR/MR is opened or updated.Validate a change before merging (build + test + review).
TagA version tag is pushed.Trigger a production release build.
Schedule (cron)At set times.Nightly builds, dependency scans, cleanup.
ManualA human clicks "run".Gated production deploys, one-off tasks.
API / webhookExternal event.Triggered by another system or upstream repo.

Branching strategies (how teams organize work)

StrategyIdeaFits
Trunk-based developmentEveryone commits to main frequently behind feature flags; very short-lived branches.High-velocity teams doing true CI/CD.
GitHub FlowBranch off main, open a PR, merge when green. Simple.Most web apps & continuous deployment.
GitFlowLong-lived develop, release, hotfix branches.Versioned/released software with scheduled releases (heavier).
Best practice: protect your main branch

Configure branch protection so that code can only reach main through a PR that: passes all CI checks, has at least one approving review, and is up to date. This makes the pipeline the gatekeeper of quality — broken code literally cannot merge.

How a trigger actually reaches the pipeline

Triggers exist because a pipeline needs to know when to run without a human babysitting the repo. Mechanically, the flow is: you push/tag/open-a-PR → your Git host records the event → it sends a webhook (an HTTP POST containing the event type, branch, commit SHA, and author) to the CI system → the CI system matches that event against the on:/rules:/trigger block in your pipeline file → if it matches, a pipeline run is created and queued for a runner. Filters like branches:, paths:, and tags: are evaluated at this matching step, which is why a well-scoped trigger avoids wasting runner minutes on irrelevant events.

Worked example — different triggers for different intents

Notice how each trigger maps to a purpose: PRs get validated, pushes to main get deployed to staging, tags cut a production release, and a nightly cron runs security scans.

Multiple triggers in one workflow
on:
  pull_request:              # validate proposed changes before merge
    branches: [main]
  push:
    branches: [main]         # deploy to staging on every merge to main
    tags: ['v*']             # cut a production release when a version tag is pushed
  schedule:
    - cron: '0 2 * * *'      # 02:00 UTC nightly — dependency & security scans
  workflow_dispatch:         # a human can also start it manually from the UI
    inputs:
      environment: { type: choice, options: [staging, production] }
The Git actions that fire those triggers
git push origin feature/login    # (via PR) → fires pull_request
git push origin main             # → fires push on main
git tag v1.4.0 && git push --tags # → fires push on tags: v* (release)
Common mistakes & gotchas
  • Trigger loops. A pipeline that commits back to the repo (e.g., bumping a version) can re-trigger itself forever. Guard with [skip ci] in the commit message or path/branch filters.
  • Forgetting pull_request runs against a merge commit, not your branch tip — so it tests "what main would look like after merge," which is usually what you want but surprises people.
  • Long-lived branches with GitFlow but expecting true CI. The branching strategy has to match the goal: trunk-based/GitHub Flow enable frequent integration; heavy GitFlow works against it.
  • No branch protection. Without it, someone can push straight to main and bypass every check — the pipeline stops being a gate.
Mental model

Git is the doorbell and the pipeline is the butler. Different visitors ring differently: a delivery (push) tells the butler to unpack it, a guest at the gate (pull request) gets checked before being let in, and a scheduled milkman (cron) comes every morning regardless. The butler only acts on rings it's been told to listen for.

5. Anatomy of a Pipeline

Every CI/CD pipeline, in every tool, is a variation on the same skeleton. Learn the skeleton and the specific tools become easy.

1. Trigger→ 2. Checkout→ 3. Setup/Install→ 4. Build→ 5. Test→ 6. Scan→ 7. Package→ 8. Publish→ 9. Deploy→ 10. Verify
StageWhat happens
1. TriggerAn event (push/PR/tag) starts the pipeline.
2. CheckoutThe runner clones your repository at the triggering commit.
3. Setup / InstallInstall the language runtime and dependencies (with caching).
4. BuildCompile/transpile/bundle the code into an artifact.
5. TestRun unit, integration, and other automated tests.
6. ScanStatic analysis, linting, security & dependency scanning.
7. PackageBundle into a deployable unit (Docker image, zip, jar).
8. PublishPush the artifact to a registry/repository.
9. DeployRelease to an environment (staging → production).
10. VerifySmoke tests / health checks confirm the deploy is healthy.

Here is that same skeleton expressed in three tools — notice the concepts are identical, only the syntax differs:

GitHub Actions
name: ci
on: [push]
jobs:
  build-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm run build
      - run: npm test
GitLab CI
stages: [build, test]
build:
  stage: build
  script:
    - npm ci
    - npm run build
test:
  stage: test
  script:
    - npm test
Jenkins (declarative Jenkinsfile)
pipeline {
  agent any
  stages {
    stage('Build') { steps { sh 'npm ci && npm run build' } }
    stage('Test')  { steps { sh 'npm test' } }
  }
}
Pipeline-as-code — the golden rule

In all modern tools, the pipeline is defined in a file committed to your repository (.github/workflows/*.yml, .gitlab-ci.yml, Jenkinsfile). This means your pipeline is versioned, reviewed, and rolled back just like code. Never configure pipelines only by clicking in a UI — that's not reproducible.

How a runner actually executes a job (step by step)

The skeleton above is what you declare; here's what the machine does. When a job is scheduled, the CI system finds an idle runner (or boots a fresh VM/container). On that runner it: (1) prepares a clean working directory; (2) runs the checkout step, which git clones your repo and checks out the exact triggering commit SHA — so the job tests precisely the code that triggered it; (3) restores any cache that matches the key; (4) executes each subsequent step in order, as a child shell process, capturing stdout/stderr and the exit code. A non-zero exit code fails the step, which fails the job, which stops downstream jobs. After the last step it optionally saves caches and uploads artifacts, then the runner is released (and, if ephemeral, destroyed).

Worked example — what the runner logs actually show

Reading a real run makes the "commands on a machine" reality concrete: each step is a shell invocation with an exit code.

Common mistakes & gotchas
  • Assuming state persists between jobs. Each job gets a fresh runner — files written in build are gone in deploy unless passed as an artifact.
  • Assuming steps continue after a failure. By default a failed step aborts the rest of the job. Use continue-on-error only deliberately.
  • Skipping the checkout step — a surprising number of "file not found" failures are just a missing actions/checkout.
  • Configuring the pipeline in the UI. It works until someone needs to review, diff, or roll back the change and there's no history.
Mental model

A pipeline is a factory conveyor belt and each runner is a fresh, empty workbench. The raw material (your code at one commit) is placed on the bench, each step is a worker performing one operation, and if any worker drops the part (non-zero exit), the belt stops and the alarm sounds. When the shift ends the bench is wiped clean for the next part.

6. The Build Stage

Continuous Integration starts by turning source code into something runnable — the build. What "build" means depends on your language.

Language / stack"Build" typically meansExample command
JavaScript/TypeScriptInstall deps, transpile, bundlenpm ci && npm run build
JavaCompile + package into a jar/warmvn package / gradle build
GoCompile a binarygo build ./...
PythonInstall deps, build a wheel (often no compile)pip install -r requirements.txt
Docker-based (any language)Build a container imagedocker build -t app:$SHA .
npm ci vs npm install (and why it matters in CI)

In CI, prefer the deterministic install command your ecosystem provides: npm ci (Node), pip install -r with a lockfile, mvn -B, etc. These install exact locked versions, so the build is reproducible. Regular install can silently pull newer versions and make builds non-deterministic ("it built yesterday!").

Build best practices
  • Build once, deploy many. Produce a single artifact and promote that same artifact through environments — never rebuild per environment (rebuilding risks producing a different result).
  • Tag artifacts with the commit SHA so you always know exactly what code an artifact contains.
  • Fail fast — put the quickest checks (lint, compile) first so obvious errors stop the pipeline in seconds.
  • Keep builds reproducible — pin versions, use lockfiles, avoid network calls that can change results.

Why the build stage exists and what it really produces

The build stage exists to turn human-friendly source into a machine-runnable, self-contained artifact — and to do it once, in a controlled environment, so every downstream step and environment gets the identical thing. Even interpreted languages "build" in CI: they resolve and lock dependencies, run code generation, bundle assets, and often produce a container image. The output is the single source of truth that gets tested, scanned, promoted, and deployed.

How a build mechanically works

Take a Docker build, the most common CI build today. docker build reads your Dockerfile top-to-bottom, executing each instruction as a layer. Each layer is content-addressed (hashed), so if the inputs to a layer are unchanged, Docker reuses the cached layer instead of rebuilding it — this is why ordering matters: put rarely-changing steps (installing dependencies) before frequently-changing steps (copying your source). The final image is the stack of layers plus metadata, tagged (ideally with the commit SHA) and pushed to a registry.

Worked example — a layer-ordered Dockerfile + SHA-tagged build

Dependencies are installed before source is copied, so a code-only change reuses the (slow) dependency layer from cache and only rebuilds the fast final layers.

Dockerfile — ordered for cache efficiency
FROM node:20-alpine
WORKDIR /app
COPY package.json package-lock.json ./   # changes rarely →
RUN npm ci                               # this slow layer stays cached
COPY . .                                 # changes often →
RUN npm run build                        # only these last layers rebuild
CMD ["node", "dist/server.js"]
Build once, tag with the commit SHA
SHA=$(git rev-parse --short HEAD)
docker build -t myapp:$SHA .          # deterministic, traceable tag
docker push myregistry/myapp:$SHA     # this exact image is promoted everywhere
Common mistakes & gotchas
  • Using npm install / unpinned versions in CI. Non-deterministic builds mean "it built yesterday" — use npm ci and lockfiles.
  • Tagging images :latest. You lose traceability and can't reliably roll back. Tag with the SHA.
  • Copying source before installing deps in a Dockerfile — busts the dependency cache on every code change, making builds needlessly slow.
  • Rebuilding per environment. Build once; promote the same artifact. Rebuilding for prod ships something never tested.
  • Baking secrets or environment-specific config into the image. Inject those at deploy time so the artifact stays environment-agnostic.
Mental model

Building is baking a cake from a recipe. Source code is the recipe and raw ingredients; the build is the baking; the artifact is the finished cake. You bake one cake and serve slices to every room (environment) — you don't bake a fresh cake in each room hoping they come out identical. Docker layers are like pre-measured, refrigerated prep: if the flour hasn't changed, you reuse yesterday's bowl instead of re-measuring.

7. Testing — the Test Pyramid

Automated testing is the heart of CI — it's what gives you confidence to ship. The test pyramid guides how much of each kind to write.

Why a pyramid?

Think of inspecting a car. Unit tests check each part on the bench ("does this bolt hold?") — cheap and instant, so you do thousands. Integration tests check that assembled parts work together ("does the engine turn the wheels?") — a bit slower, so fewer. End-to-end tests are a full test-drive around the block — realistic but slow and fragile, so just a few for the critical journeys. Lots of cheap checks at the bottom, few expensive ones at the top = fast, reliable confidence.

🔺 E2E tests (few, slow) above Integration tests (some) above Unit tests (many, fast)
Test typeWhat it checksSpeed / quantity
UnitA single function/class in isolation.Milliseconds; write lots (the pyramid's wide base).
IntegrationSeveral components together (e.g., app + database).Seconds; a moderate number.
End-to-end (E2E)The whole system as a user would use it (UI, API, DB).Slow & brittle; write few, only critical paths.
SmokeQuick "is it alive?" checks after deploy.Seconds; run post-deploy.
Performance / loadBehavior under traffic/stress.Slow; run periodically or before big releases.

Analogy: Testing is like inspecting a car. Unit tests check each part on the bench (does this bolt hold torque?). Integration tests check that assembled subsystems work together (does the engine turn the wheels?). E2E tests are a full test drive around the block. You do many cheap bench checks, fewer subsystem checks, and only a couple of full test drives — because test drives are slow and expensive.

Flaky tests will destroy trust in your pipeline

A flaky test passes and fails randomly without code changes (often due to timing, ordering, or shared state). Flaky tests train developers to ignore red pipelines — the worst outcome. Fix or quarantine them aggressively. A test you can't trust is worse than no test.

Running tests in CI (Node example)
- run: npm ci
- run: npm run lint          # fast checks first
- run: npm run test:unit     # then unit
- run: npm run test:integration
# publish results/coverage for visibility

Why the shape is a pyramid (and not a square or ice-cream cone)

The pyramid exists because tests trade off speed and stability against realism. Unit tests are fast, deterministic, and pinpoint the exact broken function — but they don't prove the pieces work together. E2E tests prove the whole system works like a real user's session — but they're slow, flaky (network, timing, browser), and when they fail they tell you "something is broken" without saying where. So you want many of the cheap, precise tests and few of the expensive, vague ones. Inverting this (the "ice-cream cone" anti-pattern: mostly E2E) produces a slow, flaky suite that everyone learns to ignore.

How tests actually gate the pipeline

Mechanically, a test runner executes your test files and exits non-zero if any assertion fails. That exit code is the entire gating mechanism — the CI step fails, the job fails, downstream deploy jobs never run. Test runners also emit machine-readable reports (JUnit XML) and coverage files that the CI system ingests to show pass/fail counts and annotate the PR. Integration tests often spin up real dependencies (a database, a message queue) as sidecar service containers for the duration of the job.

Worked example — layered tests with a real service container

Fast checks run first (fail fast); integration tests get a real Postgres via a service container; results are published as JUnit for PR annotations.

Common mistakes & gotchas
  • Inverting the pyramid. Too many E2E tests = slow, flaky CI. Push logic down into unit tests.
  • Tolerating flaky tests. One test that randomly fails trains the team to re-run red pipelines, destroying trust. Quarantine and fix.
  • Hidden test interdependencies. Tests that share state pass alone but fail when run in a different order/parallel. Isolate each test.
  • Chasing 100% coverage. Coverage is a floor to catch untested code, not proof the tests assert anything meaningful.
  • Not failing the build on test failure. If a misconfigured step swallows the exit code, red tests silently pass the pipeline.
Mental model

Testing is a funnel of inspections on a car: thousands of instant bench checks on individual bolts (unit), a smaller number of "does the assembled engine turn the wheels" checks (integration), and just a couple of full test-drives around the block (E2E). You'd never test-drive the car a thousand times to check a bolt — it's slow and tells you little about which bolt.

Code coverage — a useful signal, not a target to game

Coverage measures how much code your tests execute, not how good the tests are. 100% coverage with weak assertions proves little. Use it as a floor to prevent untested code sneaking in (e.g., "coverage must not drop"), not as the only measure of quality.

A coverage gate that fails the pipeline

Best practice: gate on PRs, not just after merge

Run your quality gates on pull/merge requests so problems are caught before code reaches main. Combined with branch protection, this means the default branch stays always-green and always-deployable.

Why gates exist and how they enforce

Quality gates exist to convert "we should keep quality high" (a hope) into "low-quality code cannot merge" (a rule enforced by machines). Mechanically a gate is just a required status check: the CI job reports a pass/fail status back to the PR, and branch protection is configured to block the merge button until specific checks report success. The gate itself is a step that exits non-zero when a threshold is breached — coverage below the floor, a linter finding, a HIGH-severity CVE. There's no separate "gate engine"; a gate is a failing step wired to a branch-protection rule.

Worked example — a coverage floor that blocks the merge

The test tool is told to fail if coverage drops below 80%. That non-zero exit becomes a failed required check, which disables the merge button.

Coverage-threshold gate wired to branch protection
jobs:

    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm run lint                       # style gate
      - run: npx jest --coverage \
             --coverageThreshold='{"global":{"lines":80}}'  # exits non-zero if < 80%
      - run: npm audit --audit-level=high       # dependency CVE gate
# In repo Settings → Branch protection, mark "quality" as a REQUIRED check.
# Now a PR cannot merge unless this job is green.
Common mistakes & gotchas
  • Gates that report but don't block. If the check isn't marked "required," a red gate is just a decoration people ignore.
  • Coverage as a vanity number. 90% coverage with no assertions proves nothing. Gate on "coverage must not drop," not on a gamed absolute.
  • Too-strict gates create noise. If every PR is blocked by trivial lint nits, people disable the gate. Tune severity thresholds.
  • Gating only after merge. Catching problems after they're in main defeats the purpose — gate on the PR.
Mental model

A quality gate is the metal detector at airport security. It doesn't judge whether you're a nice person — it enforces one clear rule (no metal beyond this point) and physically stops you if you fail. The pipeline's gates stop code that fails a clear, objective bar from reaching production.

9. Artifacts & Caching

Two related but distinct concepts that confuse beginners. Getting them right makes pipelines fast and reliable.

Artifact vs cache — the keeper vs the shortcut

Both store things between pipeline runs, but for opposite reasons. An artifact is the real output you keep — the built app, a Docker image, a test report — passed to the next stage or kept to deploy. A cache is just a speed shortcut: saved copies of downloaded dependencies so the next run doesn't re-download them. Think of baking: the cake is the artifact (the thing you deliver); keeping flour and sugar in the pantry is the cache (so you don't shop again every time). If the cache vanishes, your pipeline still works — just slower. If the artifact vanishes, you have nothing to ship.

Artifacts — the outputs you keep

An artifact is a meaningful output of your pipeline that you want to store or pass to a later stage: a built binary, a Docker image, a test report, a coverage file. Artifacts are how the "build" stage hands its result to the "deploy" stage, and how you keep a record of what was produced.

Producing & consuming an artifact
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci && npm run build
      - uses: actions/upload-artifact@v4
        with:
          name: dist
          path: dist/
  deploy:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - uses: actions/download-artifact@v4
        with:
          name: dist
      - run: ./deploy.sh

Caching — the shortcut you reuse

A cache stores things that are expensive to regenerate but don't change often — mainly downloaded dependencies (node_modules, ~/.m2, pip cache). Restoring a cache turns a 3-minute dependency install into a 10-second restore.

Dependency caching
- uses: actions/setup-node@v4
  with:
    node-version: 20
    cache: 'npm'          # built-in dependency caching
# or manual:
- uses: actions/cache@v4
  with:
    path: ~/.npm
    key: npm-${{ hashFiles('package-lock.json') }}
ArtifactCache
PurposePreserve a real output (deploy it, keep it)Speed up by reusing intermediate work
Correctness impactRequired — it's the thing you shipOptional — a miss just means slower, not wrong
Keyed byA name you chooseA hash of inputs (e.g., lockfile)
Never trust a cache for correctness

A pipeline must produce correct results even if the cache is empty or stale. Key caches on the exact inputs (e.g., the lockfile hash) so a dependency change invalidates the cache. Never cache secrets or build outputs you deploy — cache only regenerable intermediates.

How artifacts actually flow between jobs

Because each job runs on a separate, clean runner, files don't automatically travel from build to deploy. An artifact bridges that gap: the upload step zips the named paths and stores them in the CI system's artifact store (blob storage keyed to the pipeline run); a downstream job's download step fetches that zip and unpacks it into its own workspace. The link between them is (a) the artifact name matching and (b) a needs: dependency so the consumer waits for the producer. Artifacts also have a retention period, after which they're purged.

How a cache actually flows (and why the key matters)

A cache is restore-at-start, save-at-end. At the start of a job the runner computes the cache key (typically a hash of your lockfile) and asks the cache store "do you have an entry for this exact key?" A hit restores the saved directory (e.g., node_modules) instantly; a miss means the job does the slow install, and at the end saves the directory under that key for next time. This is why keying on the lockfile hash is essential: change a dependency → lockfile changes → key changes → cache miss → fresh install. Keep the key static and you'll serve a stale cache forever.

Worked example — artifact hand-off AND correct cache keying together
Producer/consumer artifact + lockfile-keyed cache
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/cache@v4
        with:
          path: ~/.npm
          key: npm-${{ hashFiles('package-lock.json') }}   # invalidates on dep change
          restore-keys: npm-                                # partial fallback
      - run: npm ci && npm run build
      - uses: actions/upload-artifact@v4     # PRODUCE the artifact
        with: { name: dist, path: dist/, retention-days: 7 }
  deploy:
    needs: build                              # wait for build to finish
    runs-on: ubuntu-latest
    steps:
      - uses: actions/download-artifact@v4   # CONSUME the same artifact
        with: { name: dist }
      - run: ./deploy.sh dist/
Common mistakes & gotchas
  • Caching the thing you deploy. A cache miss must never change correctness. Cache regenerable inputs (deps), keep outputs as artifacts.
  • Static cache keys. key: npm never invalidates → stale node_modules → "works in CI with old deps" bugs.
  • Mismatched artifact names. Upload dist, download build → "artifact not found."
  • Forgetting needs:. The consumer may start before the producer finishes and find nothing.
  • Caching secrets. A cache is shared and persisted — never put credentials in it.
Mental model

Baking again: the cake is the artifact — the actual thing you deliver, boxed up and handed to the next room. The pantry of flour and sugar is the cache — keeping it stocked saves a shopping trip, but if the pantry is empty you can still bake (just slower). And you re-stock the pantry keyed to your shopping list (lockfile): change the recipe's ingredients and you restock accordingly.

10. Continuous Delivery vs Continuous Deployment

Now the "CD" half — getting the tested artifact into the hands of users. The distinction between Delivery and Deployment is about who presses the final button.

NeedsSolid CI + automated deployEverything above + very strong automated testing & monitoring

Which should you aim for?

Start with Continuous Delivery (automate everything, keep a human approval for production). As your test suite and monitoring mature and you trust them, drop the manual gate to reach Continuous Deployment. Many excellent teams deliberately keep the approval for production — that's perfectly fine.

Why the distinction is worth caring about

The gap between Delivery and Deployment is exactly one thing: a human approval gate before production. It matters because that gate is where your organization's risk tolerance and confidence in automation live. Continuous Delivery says "we can ship any green build at any moment, but a person decides when." Continuous Deployment says "we trust our tests and monitoring enough that no person needs to decide." The right choice depends on your test coverage, your rollback speed, and your regulatory context — not on which sounds more advanced.

How the approval gate works mechanically

In practice the gate is an environment protection rule. The deploy job is bound to a protected environment (e.g., production); when the pipeline reaches that job, the CI system pauses the run and notifies the designated reviewers. The job stays queued (not failed) until a reviewer clicks approve, at which point the runner picks it up and executes the deploy steps. Remove the required-reviewer rule and the very same pipeline becomes Continuous Deployment — the job runs unattended.

Worked example — one pipeline, toggled between Delivery and Deployment

The only difference is whether the production environment has a required reviewer. Same YAML, different behavior.

Continuous Delivery (human gate) vs Deployment (no gate)
jobs:
  deploy-staging:
    runs-on: ubuntu-latest
    environment: staging          # no protection → deploys automatically
    steps: [ { run: ./deploy.sh staging } ]

  deploy-prod:
    needs: deploy-staging
    runs-on: ubuntu-latest
    environment: production       # DELIVERY: add "required reviewers" in settings
                                  #           → pipeline PAUSES here for approval
                                  # DEPLOYMENT: remove reviewers
                                  #           → this job runs unattended
    steps: [ { run: ./deploy.sh production } ]
Common mistakes & gotchas
  • Calling it Continuous Deployment when a human approves. That's Delivery. The words are precise.
  • Jumping to Continuous Deployment without the safety net. Full automation needs strong tests, monitoring, and fast automated rollback first — otherwise you're auto-shipping bugs.
  • Treating the approval as a rubber stamp. An approver who always clicks yes without checking adds latency but no safety.
  • A "manual" gate that's really a bottleneck. If only one person can approve and they're on vacation, delivery stalls.
Mental model

Continuous Delivery is a loaded dishwasher you still press "start" on; Continuous Deployment is one that runs itself when full. Both did all the loading automatically — the only question is whether a human presses the final button. You upgrade from the first to the second only once you fully trust the machine not to flood the kitchen.

11. Environments & Promotion

Code doesn't jump straight to production. It's promoted through a series of increasingly production-like environments, each a checkpoint.

Environments = rehearsals before opening night

You don't debut a play cold in front of a paying audience. You rehearse in the practice room (dev), do a full dress rehearsal on the real stage (staging), then perform on opening night (production). Crucially, it's the same cast and script that's promoted through each — you never swap in a different version for opening night. In software: build once, test it in staging, and ship that exact build to production. Rebuilding for prod would mean shipping something never rehearsed.

EnvironmentPurpose
Development (dev)Where developers integrate and test early. Unstable by design.
Testing / QADedicated environment for automated + manual testing.
Staging / Pre-prodA near-identical replica of production. Final validation before release.
Production (prod)The live environment real users hit.

Analogy: Environments are like rehearsal stages before opening night. Dev is the rehearsal room (mistakes expected). Staging is the dress rehearsal on the real stage with full costumes and lighting. Production is opening night with a paying audience. You catch problems in dress rehearsal (staging) precisely because it mirrors the real thing.

Promote the same artifact — don't rebuild

The artifact tested in staging must be the exact same bytes deployed to production. If you rebuild for production, you're deploying something that was never tested. Build once, then promote that immutable artifact: dev → staging → prod. Configuration differences (URLs, secrets) are injected at deploy time, not baked in.

Environment gates with manual approval (GitHub Actions)
jobs:
  deploy-prod:
    runs-on: ubuntu-latest
    environment:
      name: production        # configure required reviewers on this environment
      url: https://myapp.com
    steps:
      - run: ./deploy.sh production
# GitHub pauses for approval before running because 'production'
# has protection rules requiring a reviewer.

Why we promote instead of deploying straight to prod

Environments exist to give a new build progressively more realistic scrutiny before it can hurt real users. Each environment is a checkpoint that answers a different question: dev asks "does it run at all?", staging asks "does it behave like production with prod-like data and config?", prod is the real thing. Promotion — moving the same immutable artifact up the chain — exists because the alternative (rebuilding per environment) means production runs bytes that were never tested anywhere.

How promotion works mechanically

The artifact is built once and stored in a registry with an immutable tag (the commit SHA). "Promoting to staging" means deploying that specific tag to the staging environment and injecting staging config/secrets. "Promoting to prod" deploys the identical tag with prod config. Nothing is recompiled — only the target and the injected configuration change. Config lives outside the artifact (environment variables, mounted config maps, a secrets manager) precisely so the same image can run everywhere.

Worked example — same image tag, different injected config per environment
Promote one immutable tag through environments
env:
  IMAGE: myregistry/myapp:${{ github.sha }}   # built ONCE, promoted as-is
jobs:
  staging:
    environment: staging
    steps:
      - run: kubectl set image deploy/myapp myapp=$IMAGE
        env: { APP_ENV: staging, DB_URL: ${{ secrets.STAGING_DB_URL }} }  # config injected
  production:
    needs: staging
    environment: production          # protected: waits for approval
    steps:
      - run: kubectl set image deploy/myapp myapp=$IMAGE   # SAME $IMAGE, no rebuild
        env: { APP_ENV: production, DB_URL: ${{ secrets.PROD_DB_URL }} }
Common mistakes & gotchas
  • Rebuilding per environment. Even the "same" Dockerfile can produce different bytes (new base image, floating dep). Promote the exact tag.
  • Staging that doesn't resemble prod. Different scaling, data volume, or config makes staging a false comfort — bugs slip through.
  • Baking config into the image. If the URL/secret is compiled in, you can't promote the same artifact — inject at deploy time.
  • Skipping staging "just this once." That's exactly the deploy that breaks prod.
Mental model

Environments are rehearsals before opening night with the same cast and script. Dev is the read-through, staging is the full dress rehearsal on the real stage with lights and costumes, prod is opening night. You never swap in different actors for opening night — you promote the exact production that was rehearsed. Costumes and the venue (config) differ; the performance (artifact) does not.

12. Deployment Strategies

How you roll out a new version determines your downtime and risk. These are the strategies every engineer should know.

Deployment strategies as opening a new restaurant kitchen
  • Recreate = close the old kitchen, install the new one, reopen. Simple, but you're shut during the swap (downtime).
  • Rolling = swap the stations one at a time while staying open — customers never notice.
  • Blue-Green = build a whole second kitchen, test it fully, then flip all orders to it at once (and flip back instantly if it's bad).
  • Canary = send just 5% of orders to the new kitchen first; if the food's good, gradually send more; if not, stop early — only a few customers affected.

Recreate (basic)

Stop the old version entirely, then start the new one. Simple but causes downtime. Fine for internal tools or when versions can't coexist.

v1 running→stop all (downtime)→v2 running

Why use it: it's the simplest possible strategy and the only option when v1 and v2 cannot run at the same time (e.g., an exclusive database lock or an incompatible schema). How it works: the orchestrator terminates every v1 instance, waits for them to fully stop, then starts v2 instances — so there's a window where zero instances serve traffic. In Kubernetes this is strategy.type: Recreate.

Rolling update

Gradually replace old instances with new ones, a few at a time. No downtime; both versions briefly coexist. The default in Kubernetes.

v1 v1 v1 v1→v2 v1 v1 v1→v2 v2 v1 v1→v2 v2 v2 v2

How traffic actually shifts: a load balancer / Service sits in front of a pool of instances. Kubernetes brings up a new v2 Pod, waits for its readiness probe to pass, adds it to the Service's endpoint list (so it now receives traffic), then removes and terminates one v1 Pod. It repeats this maxSurge/maxUnavailable at a time until the whole pool is v2. Traffic is never routed to a Pod that isn't "ready," which is what makes it zero-downtime — provided your readiness probe is honest.

Blue-Green

Run two identical environments: "blue" (current) and "green" (new). Deploy to green, test it, then flip all traffic from blue to green instantly. Rollback = flip back. Zero downtime, instant rollback, but needs double the resources temporarily.

Blue (v1) ← 100% trafficdeploy+test greenGreen (v2)flipGreen (v2) ← 100% traffic

How the flip actually happens: the "flip" is a single change to where a router points — a load-balancer target group swap, a Service selector change, or a DNS/weight change. Before the flip, green is fully deployed and smoke-tested while receiving zero production traffic. The flip re-points 100% of traffic to green atomically; if green misbehaves, you re-point back to blue (still running, untouched) in seconds. The cost: you run two full copies of the app during the transition.

Canary

Release the new version to a small subset of users first (say 5%), watch metrics, then gradually increase to 100% if healthy — or roll back if error rates spike. The safest strategy for risky changes.

v2 → 5%healthy?v2 → 25%healthy?v2 → 100%

How the small percentage is achieved: traffic weighting. A service mesh or ingress (Istio, NGINX, ALB weighted target groups) is told "send 5% of requests to the v2 pool, 95% to v1." You then watch v2's error rate and latency for that 5% slice; if it stays healthy you bump the weight to 25%, 50%, 100%; if it degrades you set the weight back to 0%. Because only a small fraction of users ever touch a bad v2, the blast radius of a bad release is tiny.

Choosing a strategy — the decision, mechanically

The choice comes down to three levers: can the two versions coexist? (no → Recreate), do you need instant, whole-fleet rollback? (yes → Blue-Green, at 2× cost), and is the change risky enough to want a small test audience first? (yes → Canary). Rolling is the sensible default for ordinary stateless services because it's zero-downtime, cheap, and built into Kubernetes.

Worked example — a Kubernetes rolling update (the default)

maxSurge/maxUnavailable control how aggressively Pods are swapped; the readiness probe is what guarantees no traffic hits a not-yet-ready Pod.

Deployment with an explicit rolling strategy + readiness gate

  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1          # at most 1 extra Pod above desired count
      maxUnavailable: 0    # never drop below desired capacity (zero-downtime)
  template:
    spec:
      containers:
        - name: myapp
          image: myapp:v2
          readinessProbe:              # traffic only flows once this passes
            httpGet: { path: /healthz, port: 8080 }
            initialDelaySeconds: 5
            periodSeconds: 5

# Bad? Flip back instantly:

Common mistakes & gotchas
  • A lying readiness probe. If the probe returns 200 before the app can actually serve, rolling updates route traffic to broken Pods — instant errors with "zero downtime."
  • Blue-green with a shared database. Both colors hit the same DB; a schema change for green can break blue. Use backward-compatible migrations (§13).
  • Canary without metrics. Sending 5% of traffic to v2 is pointless if nobody watches v2's error rate — you just harm 5% of users slowly.
  • Sticky sessions vs canary. If a user is pinned to v1 by a session cookie, your 5% weighting won't behave as expected.
  • Forgetting the 2× cost of blue-green when capacity-planning.

13. Rollbacks & Release Management

Things will go wrong in production. A mature pipeline makes recovery fast and boring.

Rollback approaches

  • Redeploy the previous artifact — because you kept immutable, versioned artifacts, you can redeploy the last-known-good one instantly.
  • Traffic flip — with blue-green, just point traffic back to the old environment.
  • Roll forward — sometimes fixing forward with a quick patch is safer than rolling back (e.g., after a database migration that can't be reversed).
  • Feature flag off — disable the problematic feature without any deploy.
Database changes make rollbacks hard — plan for it

Code rolls back easily; databases do not. If v2 changed the schema and you roll back to v1, v1 may not understand the new schema. Use backward-compatible migrations (expand-then-contract: add new columns before removing old ones, deploy in stages). Never write a migration that a rollback can't tolerate.

Release management essentials
  • Version everything — semantic versioning (MAJOR.MINOR.PATCH) and tag releases in Git.
  • Keep a changelog — what changed in each release, ideally auto-generated from commits.
  • Make rollback a one-click, tested operation — not an improvised emergency.
  • Deploy small and often — small changes are easier to diagnose and reverse than big-bang releases.
  • Automate a post-deploy smoke test so a broken deploy is detected in seconds, ideally auto-rolling-back.

Why rollbacks must be planned, not improvised

Rollbacks exist because some percentage of deploys will be bad no matter how good your testing is — production is the only environment with real traffic, real data, and real scale. The goal isn't zero bad deploys (impossible); it's making recovery fast and boring. A rollback you've rehearsed and automated turns a potential multi-hour outage into a 60-second non-event. A rollback you improvise under pressure at 2am is how small incidents become big ones.

How rollback works mechanically (and why databases break it)

Because you keep immutable, SHA-tagged artifacts, a code rollback is just "re-point the deployment at the previous known-good tag" — kubectl rollout undo, a blue-green flip back, or reverting the Git commit in a GitOps repo. The orchestrator does another rolling update, this time backwards. The hard part is state: code is immutable and re-deployable, but a database migration that dropped a column or rewrote data can't be un-run by re-pointing an image. That's why schema changes use the expand/contract pattern — add the new column, deploy code that writes both old and new, backfill, and only remove the old column a release later, so any single version can be rolled back safely.

Worked example — instant rollback + safe (expand/contract) migration
Kubernetes rollback to the previous revision
kubectl rollout history deployment/myapp    # list revisions
kubectl rollout undo deployment/myapp       # revert to previous known-good
kubectl rollout status deployment/myapp     # confirm healthy
# GitOps equivalent — revert the commit and let the agent sync:
git revert <bad-deploy-sha> && git push
Expand/contract so v1 and v2 can coexist and roll back
# Release 1 (EXPAND): add the new column, nullable. Old code ignores it.
ALTER TABLE users ADD COLUMN email_verified boolean;
# Release 2: deploy code that WRITES both old & new, READS new. Rollback-safe.
# Release 3 (CONTRACT): only after v2 is proven, drop the old column.
# ALTER TABLE users DROP COLUMN legacy_flag;
Common mistakes & gotchas
  • Irreversible migrations. Dropping a column in the same release that stops using it means a rollback lands on code that expects it. Expand/contract instead.
  • No known-good artifact to roll back to (e.g., you only tag :latest). Keep every release SHA-tagged.
  • Rollback that itself is untested. The first time you run your rollback path should not be during an outage.
  • Rolling back code but not config/feature flags. If the incident was a flag, flip the flag — no deploy needed and far faster.
  • Assuming roll-forward is always worse. After an irreversible data change, a small fix-forward patch is sometimes the only safe path.
Mental model

A rollback is Ctrl+Z for production — but only for the parts that are text. Code is text (undo instantly). A database migration is like having already mailed the letters: you can't un-send them, so you plan changes to be forgiving (expand/contract) rather than counting on undo.

14. GitHub Actions — Fundamentals

GitHub Actions (GHA) is GitHub's built-in CI/CD. It's the most popular choice for projects hosted on GitHub because it needs zero external setup — you just add a YAML file to your repo.

Workflow → Jobs → Steps, like a recipe book

The nesting confuses people, so map it to cooking. A workflow is the whole recipe book for one dish (a .yml file). A job is a course (appetizer, main) — each cooked at its own station, and independent courses can be prepared at the same time. A step is a single instruction in that course ("chop onions," "run the tests"). And an action is a pre-made gadget you grab off the shelf instead of doing a step by hand ("use the food processor"). You trigger the whole book to run whenever code is pushed.

The building blocks (nested inside each other)

ConceptWhat it is
WorkflowAn automated process defined in a YAML file under .github/workflows/. A repo can have many.
EventWhat triggers the workflow (push, pull_request, schedule, workflow_dispatch for manual).
JobA set of steps that run on the same runner. Jobs run in parallel by default; use needs to sequence them.
StepAn individual task in a job — either a shell command (run) or an action (uses).
ActionA reusable, packaged unit of logic (e.g., actions/checkout). Thousands exist in the Marketplace.
RunnerThe machine that runs a job — GitHub-hosted (Ubuntu/Windows/macOS) or self-hosted.

Analogy: A workflow is a recipe book for one dish. Jobs are the courses (appetizer, main). Steps are the individual instructions ("chop onions"). Actions are pre-made kitchen gadgets you grab off the shelf instead of doing it by hand ("use the food processor").

Why GitHub Actions won, and what an "action" really is

GHA exists to remove the friction of standing up a separate CI server: because it's built into GitHub, a workflow file in your repo is all you need — no server to host, patch, or connect. The killer feature is the Marketplace of actions. An action is a packaged, versioned, reusable unit of steps that someone else wrote and you invoke with uses: — actions/checkout clones your repo, aws-actions/configure-aws-credentials handles cloud auth. Instead of scripting these yourself, you compose them like Lego bricks.

How uses: vs run: actually differ

Every step is one of two kinds. run: executes a shell command directly on the runner (e.g., run: npm test). uses: pulls in an action — GHA fetches that action's code (from a repo, at the pinned ref) and runs its defined logic, passing your with: inputs. Jobs run on separate runners in parallel by default; needs: is what serializes them and lets one job depend on another's completion (and artifacts).

Worked example — parallel jobs, a dependency, and both step kinds
Two parallel jobs + a dependent third
on: [push]
jobs:
  lint:                        # these two run IN PARALLEL (no needs between them)
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4      # a "uses" step (an action)
      - run: npm ci && npm run lint     # a "run" step (a shell command)
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci && npm test
  deploy:
    needs: [lint, test]        # waits for BOTH to succeed before starting
    runs-on: ubuntu-latest
    steps:
      - run: ./deploy.sh
Common mistakes & gotchas
  • Expecting jobs to share files. Each job is a separate runner — pass files via artifacts, not by assuming they persist.
  • Wrong file location. Workflows must live in .github/workflows/*.yml; anywhere else and they silently never run.
  • Floating action tags. @v4 is a moving tag; for security-critical actions pin to a full commit SHA.
  • Assuming order without needs:. Jobs are parallel by default — a "deploy" job with no needs can start before tests finish.
Mental model

A workflow is a recipe book, jobs are courses cooked at separate stations (in parallel), steps are the individual instructions, and actions are pre-made gadgets you grab off the shelf. needs: is telling one station "wait until the appetizer's done before you plate the main."

15. Workflows, Jobs & Steps

A complete, annotated workflow — read the comments to understand each part.

.github/workflows/ci.yml — annotated
name: CI                              # workflow name (shown in the UI)

on:                                   # WHAT triggers this workflow
  push:
    branches: [main]
  pull_request:
    branches: [main]
  workflow_dispatch:                  # allow manual runs

env:                                  # workflow-wide environment variables
  NODE_VERSION: 20

jobs:
  test:                               # a job called "test"
    runs-on: ubuntu-latest            # the runner OS
    steps:
      - name: Checkout code
        uses: actions/checkout@v4     # an ACTION (pulls your repo)

      - name: Setup Node
        uses: actions/setup-node@v4
        with:
          node-version: ${{ env.NODE_VERSION }}
          cache: 'npm'

      - name: Install deps
        run: npm ci                   # a shell command

      - name: Lint
        run: npm run lint

      - name: Test
        run: npm test

  build:
    runs-on: ubuntu-latest
    needs: test                       # only runs if "test" job succeeds
    steps:
      - uses: actions/checkout@v4
      - run: npm ci && npm run build
      - uses: actions/upload-artifact@v4
        with: { name: dist, path: dist/ }

Key mechanics

FeatureHow
Run jobs in orderneeds: [jobname] — creates dependencies.
Conditional executionif: github.ref == 'refs/heads/main'
Use action inputswith: block under a uses: step.
Access context data${{ github.sha }}, ${{ github.actor }}, ${{ github.ref }}, etc.
Pin action versionsactions/checkout@v4 (or a full SHA for security).

How data moves between steps and jobs

Within a job, steps share the same runner and workspace, so a file written in one step is visible to the next. To pass a value (not a file) between steps, a step writes to the special $GITHUB_OUTPUT file and later steps read it via ${{ steps.<id>.outputs.<name> }}. Between jobs (different runners) you either use job outputs (declared under outputs: and consumed via needs.<job>.outputs) or pass files via artifacts. Expressions in ${{ }} are evaluated by GHA before the shell runs, letting you branch on context like github.ref.

Worked example — step output, job output, and a conditional deploy
Passing values step→step and job→job, with an if-condition
jobs:
  build:
    runs-on: ubuntu-latest
    outputs:
      tag: ${{ steps.meta.outputs.tag }}       # expose to other jobs
    steps:
      - id: meta
        run: echo "tag=$(git rev-parse --short HEAD)" >> "$GITHUB_OUTPUT"
      - run: echo "Building tag ${{ steps.meta.outputs.tag }}"   # step→step
  deploy:
    needs: build
    if: github.ref == 'refs/heads/main'          # only deploy from main
    runs-on: ubuntu-latest
    steps:
      - run: ./deploy.sh ${{ needs.build.outputs.tag }}   # job→job value
Common mistakes & gotchas
  • Using echo "x=1" >> $GITHUB_ENV vs $GITHUB_OUTPUT confusion. GITHUB_ENV sets env vars for later steps; GITHUB_OUTPUT sets named step outputs. They're different files.
  • Referencing a step output without giving the step an id:. No id → nothing to reference.
  • Expecting job outputs to carry files. Outputs carry strings; use artifacts for files.
  • Mis-scoped if:. An if at job level skips the whole job; at step level it skips one step — pick the right level.
Mental model

Steps in a job are chefs sharing one counter — they can pass a bowl directly. Separate jobs are chefs in different kitchens — to share a value they shout it across (job outputs), and to share a physical dish they courier it over (artifacts).

16. Secrets, Matrix Builds & Reusable Workflows

The features that make GHA production-grade.

Secrets — never hard-code credentials

Store sensitive values in Settings → Secrets and variables → Actions (or environment secrets). Reference them via ${{ secrets.NAME }} — they're masked in logs.

Using secrets
steps:
  - name: Deploy
    env:
      API_TOKEN: ${{ secrets.DEPLOY_TOKEN }}
    run: ./deploy.sh
Use OIDC instead of long-lived cloud keys

For deploying to AWS/GCP/Azure, don't store static cloud credentials as secrets. Use OIDC: the workflow requests a short-lived token and assumes a cloud IAM role. No secrets to leak or rotate.

permissions:
  id-token: write        # required for OIDC
  contents: read
steps:
  - uses: aws-actions/configure-aws-credentials@v4
    with:
      role-to-assume: arn:aws:iam::1111:role/gha-deploy
      aws-region: us-east-1

Matrix builds — test many combinations in parallel

Matrix across versions & OSes
jobs:
  test:
    strategy:
      fail-fast: false
      matrix:
        node: [18, 20, 22]
        os: [ubuntu-latest, windows-latest]
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: ${{ matrix.node }} }
      - run: npm ci && npm test
# This runs 3 x 2 = 6 jobs in parallel.

Reusable workflows — DRY across repos

Define a workflow once and call it from many others, so you don't copy-paste pipeline logic.

Caller referencing a reusable workflow
jobs:
  call-deploy:
    uses: my-org/.github/.github/workflows/deploy.yml@main
    with:
      environment: production
    secrets: inherit
Composite actions vs reusable workflows

Composite actions bundle several steps into one reusable step. Reusable workflows bundle whole jobs. Use composite actions for repeated step sequences (e.g., "setup + install + cache"); use reusable workflows for repeated pipelines (e.g., a standard deploy).

Why these three features make GHA production-grade

Secrets exist so credentials never live in your repo; matrix builds exist so you can prove your code works across many versions/OSes without copy-pasting a job N times; reusable workflows exist so an org defines its standard pipeline once instead of drifting into 50 slightly-different copies.

How each works mechanically

Secrets: GHA stores them encrypted; at runtime it injects the value into the step's environment and scrubs that exact string from logs (so it appears as ***). It only masks values it knows are secrets — if you transform or echo one yourself, masking can fail. Matrix: GHA takes the cartesian product of the matrix axes and fans out one parallel job per combination, substituting ${{ matrix.* }} into each. Reusable workflows: the caller's uses: points at another workflow file; GHA runs that workflow's jobs as if inlined, passing declared inputs and (with secrets: inherit) the caller's secrets.

Worked example — matrix fan-out with a partial exclusion

This declares 3×2 = 6 jobs, then removes one combination — a common real-world need (e.g., an old runtime unsupported on one OS).

Matrix with include/exclude
jobs:
  test:
    strategy:
      fail-fast: false          # let all combos finish even if one fails
      matrix:
        node: [18, 20, 22]
        os: [ubuntu-latest, windows-latest]
        exclude:
          - { node: 18, os: windows-latest }   # skip this one combo (5 jobs total)
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: ${{ matrix.node }} }
      - run: npm ci && npm test
Common mistakes & gotchas
  • Echoing a secret (or piping it through base64) — masking only catches the exact known string, so the transformed value leaks in logs.
  • Expecting secrets on fork PRs. By default secrets aren't shared to workflows triggered from forks — a security feature that surprises people.
  • Huge matrices. 4 axes × several values each can spawn dozens of jobs and blow your runner minutes; constrain with include/exclude.
  • Forgetting secrets: inherit when calling a reusable workflow — the callee then can't see the secrets it needs.
  • Reusable workflow path errors. The uses: must be owner/repo/.github/workflows/file.yml@ref exactly.
Mental model

Secrets are sealed envelopes the runner opens only inside the job and shreds from the transcript. A matrix is a photocopier that runs the same test sheet through once per paper size, all at once. A reusable workflow is a company letterhead template — write the standard pipeline once, and every team imports it instead of redrawing it.

18. Jenkins — Architecture

Jenkins is the veteran open-source automation server — around since 2011, self-hosted, and enormously extensible via plugins. It's still everywhere in enterprises, especially where teams need full control or aren't on a cloud-hosted Git platform.

Controller + agents

ComponentRole
Controller (formerly "master")The brain: schedules jobs, manages configuration, serves the web UI, and coordinates agents. Should not run heavy builds itself.
Agent (formerly "slave" / node)A worker machine that executes the build steps. You can have many, on different OSes, for parallelism and isolation.
ExecutorA slot on an agent that runs one build at a time. An agent with 4 executors runs 4 builds concurrently.
PluginAn add-on extending Jenkins (Git, Docker, Kubernetes, Slack, etc.). Jenkins has 1800+.

Analogy: The controller is a construction site foreman — he doesn't swing the hammer, he assigns work and tracks progress. The agents are the workers on various sites who actually build. Plugins are the specialized tools you bring in for particular jobs.

Jenkins is powerful but high-maintenance

Because it's self-hosted, you own the server, upgrades, security patching, plugin compatibility, and scaling. Plugins are its strength (flexibility) and weakness (version conflicts, security CVEs). Budget for ongoing maintenance — this is the main trade-off vs cloud-hosted tools like GitHub Actions.

Why the controller/agent split exists

Jenkins separates the controller (coordination) from agents (execution) for the same reason a construction site separates the foreman from the workers: the coordinator must stay responsive and secure, so it shouldn't be bogged down running heavy, untrusted build workloads. Offloading builds to agents also gives you parallelism (many agents = many concurrent builds), isolation (a build can't corrupt the controller), and heterogeneity (a Windows agent for .NET, a Linux agent for containers).

How the controller and an agent actually communicate

An agent connects to the controller over a channel (JNLP/WebSocket or SSH). When a build is triggered, the controller's scheduler finds an agent with a free executor that matches the job's label (e.g., linux && docker), sends it the workspace and the build steps, and the agent runs them, streaming logs back. An executor is a single concurrency slot — an agent with 4 executors runs 4 builds at once. Modern setups make agents ephemeral: the controller asks a cloud/Kubernetes plugin to spin up a fresh agent pod per build and destroy it after.

Worked example — pinning a stage to a labelled agent

agent { label '...' } is how a job tells the scheduler which kind of executor it needs. This is the Jenkins equivalent of GHA's runs-on:.

Routing work to specific agents by label
pipeline {
  agent none
  stages {
    stage('Unit tests') {
      agent { label 'linux && nodejs' }     // needs a Linux + Node agent
      steps { sh 'npm ci && npm test' }
    }
    stage('Windows build') {
      agent { label 'windows' }               // routed to a Windows agent
      steps { bat 'msbuild App.sln' }
    }
  }
}
Common mistakes & gotchas
  • Running builds on the controller. It bogs down the UI/scheduler and is a security risk — keep the controller for coordination only.
  • Too few executors → builds queue "waiting for executor." Too many → agents thrash on CPU/RAM.
  • Static, long-lived agents accumulate state (leftover files, drifting tool versions) causing "works on agent A, fails on agent B." Prefer ephemeral container agents.
  • Neglecting patching. An unpatched controller or plugin is a classic breach vector — Jenkins is a high-value target with credentials to everything.
Mental model

The controller is a dispatcher at a taxi company: it takes the jobs and radios them out but never drives. The agents are the drivers; each executor is a seat in a cab (one fare at a time). Labels are the "I need a van, not a sedan" request that routes the job to the right car.

19. The Jenkinsfile

Modern Jenkins uses Pipeline-as-code: a Jenkinsfile committed to your repo. It comes in two flavors — declarative (recommended) and scripted.

Declarative pipeline (recommended)

Structured, opinionated, easier to read. Use this unless you have a strong reason not to.

Jenkinsfile (declarative)
pipeline {
  agent any                              // run on any available agent

  environment {
    IMAGE = "myapp"
    REGISTRY = "111122223333.dkr.ecr.us-east-1.amazonaws.com"
  }

  options {
    timeout(time: 30, unit: 'MINUTES')
    disableConcurrentBuilds()
  }

  stages {
    stage('Checkout') {
      steps { checkout scm }
    }
    stage('Build & Test') {
      steps {
        sh 'npm ci'
        sh 'npm run build'
        sh 'npm test'
      }
    }
    stage('Docker Build & Push') {
      steps {
        sh 'docker build -t $REGISTRY/$IMAGE:$GIT_COMMIT .'
        sh 'docker push $REGISTRY/$IMAGE:$GIT_COMMIT'
      }
    }
    stage('Deploy') {
      when { branch 'main' }             // only deploy from main
      steps {
        sh 'kubectl set image deployment/myapp myapp=$REGISTRY/$IMAGE:$GIT_COMMIT'
      }
    }
  }

  post {                                 // always runs at the end
    success { echo 'Pipeline succeeded' }
    failure { echo 'Pipeline failed — notify team' }
    always  { junit 'reports/**/*.xml' } // publish test results
  }
}

Scripted pipeline (advanced)

Full Groovy programming — maximum flexibility, more complexity. Use only when declarative can't express your logic.

Jenkinsfile (scripted)
node {
  stage('Build') {
    checkout scm
    sh 'npm ci && npm run build'
  }
  stage('Test') {
    sh 'npm test'
  }
  if (env.BRANCH_NAME == 'main') {
    stage('Deploy') {
      sh './deploy.sh'
    }
  }
}
DeclarativeScripted
SyntaxStructured pipeline { } blocksFree-form Groovy node { }
ReadabilityHighLower
FlexibilityGood (with script { } escape hatch)Maximum
Recommended forAlmost everythingComplex custom logic

Why a Jenkinsfile (and why declarative)

The Jenkinsfile exists to make Jenkins pipelines pipeline-as-code — versioned, reviewed, and rolled back with the app, instead of buried in fragile UI job config. Declarative is recommended because its rigid structure (pipeline { agent / stages / post }) is easy to read, validates before running, and gives you post conditions and when guards for free. Scripted (raw Groovy) is an escape hatch for logic declarative can't express — reach for it rarely.

How Jenkins executes a Jenkinsfile

The controller checks out the repo, finds the Jenkinsfile, and interprets it as Groovy. Each stage is scheduled onto an agent; each steps block runs commands (sh on Linux, bat on Windows) on that agent, streaming logs. Crucially the post block runs regardless of outcome — always for cleanup/reporting, success/failure for notifications — which is how you guarantee test results get published and the team gets pinged even when the build fails.

Worked example — parallel stages + post handling

Independent stages run in parallel to save wall-clock time; post guarantees notification and cleanup no matter what.

Parallel stages with guaranteed post actions
pipeline {
  agent any
  stages {
    stage('Verify') {
      parallel {
        stage('Lint') { steps { sh 'npm run lint' } }
        stage('Unit') { steps { sh 'npm test' } }   // runs at the same time as Lint
      }
    }
  }
  post {
    always  { junit 'reports/**/*.xml' }             // publish results even on failure
    failure { slackSend channel: '#ci', message: "Build ${env.BUILD_NUMBER} failed" }
    cleanup { cleanWs() }                            // wipe the workspace
  }
}
Common mistakes & gotchas
  • Putting cleanup/notify in the last stage instead of post. If an earlier stage fails, that stage never runs — post is the only reliable place.
  • Mixing scripted constructs into declarative without a script { } block → MissingProperty/syntax errors.
  • Not setting a timeout — a hung sh can occupy an executor indefinitely.
  • Shell-interpolating Groovy secrets (sh "deploy $TOKEN") leaks them into logs; use withCredentials and single-quote so the shell expands the env var.
Mental model

A declarative Jenkinsfile is a fill-in-the-blanks form: there are fixed boxes (agent, stages, post) and you just fill them. Scripted is a blank sheet of paper — total freedom, but you can also draw yourself into a mess. The post block is the "in case of fire" instructions that run no matter how the show ends.

20. Agents, Plugins & Shared Libraries

The features that scale Jenkins across teams and keep pipelines maintainable.

Dynamic agents (run builds in containers)

Instead of maintaining static agent machines, modern Jenkins spins up ephemeral agents on demand — commonly as Kubernetes pods or Docker containers — giving clean, isolated, scalable builds.

Per-stage container agents
pipeline {
  agent none

}

Credentials & secrets

Jenkins stores secrets in its Credentials store (never in the Jenkinsfile). Reference them with the credentials() helper or withCredentials block.

Using credentials
environment {
  AWS_CRED = credentials('aws-deploy-key')   // injects _USR and _PSW
}
// or scoped:
steps {
  withCredentials([string(credentialsId: 'api-token', variable: 'TOKEN')]) {
    sh './deploy.sh'

}

Shared libraries — DRY across many pipelines

A shared library is a separate Git repo of reusable Groovy pipeline code that many Jenkinsfiles import — so an organization standardizes its build/deploy logic in one place.

Using a shared library
@Library('my-org-pipeline-lib') _
standardPipeline(
  language: 'node',
  deployTo: 'production'
)
// 'standardPipeline' is defined once in the shared library repo.
Jenkins best practices
  • Always use a Jenkinsfile in the repo (pipeline-as-code) — not job config in the UI.
  • Keep the controller lightweight; run all builds on agents (ideally ephemeral containers).
  • Store secrets in the Credentials store, never in the Jenkinsfile or logs.
  • Pin plugin versions and patch regularly — plugins are the top security risk.
  • Use shared libraries to avoid copy-pasting pipeline logic across repos.
  • Set timeouts and clean up workspaces to avoid stuck/space-hogging builds.

How a shared library is resolved and run

@Library('my-org-pipeline-lib') _ tells Jenkins to fetch that library's Git repo (a repo with a vars/ and src/ layout) at the configured version. Functions in vars/ (e.g., standardPipeline.groovy) become callable steps in your Jenkinsfile. At runtime Jenkins loads the Groovy, and calling standardPipeline(...) executes the shared logic with your parameters — so a fix to the library instantly improves every pipeline that imports it.

Worked example — a shared library defining a standard pipeline
vars/standardPipeline.groovy (defined once, org-wide)
// In the shared-library repo: vars/standardPipeline.groovy
def call(Map cfg) {
  pipeline {
    agent { kubernetes { defaultContainer 'build' } }   // ephemeral pod agent
    stages {
      stage('Build') { steps { sh "make build-${cfg.language}" } }
      stage('Test')  { steps { sh 'make test' } }
      stage('Deploy') {
        when { branch 'main' }
        steps {
          withCredentials([string(credentialsId: 'deploy-token', variable: 'TOKEN')]) {
            sh "make deploy ENV=${cfg.deployTo}"
          }
        }
      }
    }
  }
}
Every app's Jenkinsfile shrinks to this
@Library('my-org-pipeline-lib') _

Common mistakes & gotchas
  • Unpinned shared library version. Tracking @main means a library change can break every pipeline at once — pin to a tag per consumer.
  • Secrets in the Jenkinsfile or echoed in sh. Use withCredentials and single-quoted shell so the value never lands in logs.
  • Ephemeral agents without a cache strategy re-download all deps every build — pair them with a shared cache volume or registry mirror.
  • Overstuffing the shared library until it's an unversioned framework nobody dares change. Keep it small and well-tested.
Mental model

Ephemeral agents are disposable rental kitchens — spotless every time, returned after use. The credentials store is the hotel safe (the app borrows the key card, never keeps the master key). A shared library is the franchise operations manual: write "how we make the burger" once, and every branch follows it by reference.

Why GitLab CI feels different, and how stages/jobs relate

GitLab's model is stages contain jobs: you list ordered stages: at the top, and each job declares which stage it belongs to. All jobs in the same stage run in parallel; the next stage starts only when the previous stage fully passes. This is subtly different from GHA, where ordering comes from per-job needs: rather than a global stage list. GitLab also has needs: for a DAG if you want to break the strict stage ordering for speed.

How a GitLab runner executes a job

A runner (shared SaaS or self-managed) picks up a job, pulls the job's image: as a container, clones the repo into it, restores cache:, runs the script: lines, and on success uploads declared artifacts: (which later stages download automatically). rules: decide whether a job is even created for a given pipeline — e.g., only on main, only for merge requests, or only when certain files changed. A when: manual rule turns a job into a click-to-run button (the GitLab way to gate production).

Worked example — DAG needs, rules, and a manual prod gate
Speeding up with needs: and gating prod with rules:
stages: [build, test, deploy]

  stage: build
  script: [make build]
  artifacts: { paths: [dist/] }

test:
  stage: test
  needs: [build]            # start as soon as build is done (DAG, not whole-stage wait)
  script: [make test]

  stage: deploy

Common mistakes & gotchas
  • Confusing stage-parallelism with job-parallelism. Jobs in one stage run together; forgetting this creates accidental races on shared resources.
  • Old only/except vs new rules:. Mixing them is invalid — standardize on rules:.
  • Cache vs artifacts confusion (same as everywhere): artifacts: pass outputs between stages and are always fetched; cache: is a best-effort speedup.
  • Forgetting an image: means the job runs on the runner's default, which may lack your tools.
  • No when: never fallback in rules: can cause jobs to run in pipelines you didn't intend.
Mental model

GitLab CI is an assembly line with numbered stations (stages). Every worker at station 2 works simultaneously, and the belt won't advance to station 3 until all of station 2 finishes. rules: are the sign that says "only assemble this part for orders going to Europe," and when: manual is the big green button a supervisor presses to ship.

A very common modern combo

24. DevSecOps — Security in the Pipeline

DevSecOps means baking security into the pipeline rather than bolting it on at the end. The principle: shift security left — catch vulnerabilities early, when they're cheap to fix.

The types of security scanning

SAST (Static Application Security Testing)Your source code for vulnerable patterns (SQL injection, XSS).CodeQL, SonarQube, Semgrep
SCA (Software Composition Analysis)Your dependencies for known CVEs.Dependabot, Snyk, npm audit, Trivy
Secret scanningAccidentally committed keys/tokens/passwords.Gitleaks, TruffleHog, GitHub secret scanning

Security scanning in a pipeline
jobs:
  security:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Dependency audit (SCA)
        run: npm audit --audit-level=high
      - name: Secret scan
        uses: gitleaks/gitleaks-action@v2
      - name: SAST (CodeQL)
        uses: github/codeql-action/analyze@v3
      - name: Container scan
        run: |
          docker build -t myapp:${{ github.sha }} .
          trivy image --exit-code 1 --severity HIGH,CRITICAL myapp:${{ github.sha }}
DevSecOps best practices
  • Fail the build on high/critical findings — make security a real quality gate, not a report nobody reads.
  • Scan dependencies continuously — new CVEs appear daily; run SCA on a schedule, not just on commits.
  • Generate an SBOM (Software Bill of Materials) so you know exactly what's in every release.
  • Sign your artifacts/images (e.g., Sigstore/cosign) and verify signatures before deploy.
  • Least-privilege pipelines — the pipeline's credentials should only allow what it needs.
  • Balance strictness with noise — too many false-positive failures train people to ignore security.

Why "shift left" is more than a slogan

Fixing a vulnerability gets exponentially more expensive the later it's found: a flaw caught in a PR is a code review comment; the same flaw in production is an incident, a patch release, and possibly a breach. DevSecOps exists to move the discovery point as early as possible — into the pipeline, on every commit — so security becomes a cheap, automatic gate rather than a periodic, expensive audit. The distinct scan types exist because vulnerabilities hide in different places: your code (SAST), your dependencies (SCA), your images (container scan), your infra config (IaC scan), and your running app (DAST).

How a security gate mechanically blocks a bad build

Each scanner is a step that exits non-zero when it finds issues at or above a configured severity. That failing exit code fails the job, which — combined with a required status check — blocks the merge or halts the deploy. The key knob is the severity threshold: --exit-code 1 --severity HIGH,CRITICAL means "only fail on serious findings, report the rest." This is how you keep the gate meaningful without drowning developers in low-severity noise.

Worked example — layered scans, each failing only on serious findings
A security stage that gates on severity
jobs:
  security:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Secret scan (block committed credentials)
        uses: gitleaks/gitleaks-action@v2
      - name: SCA — fail on high-severity CVEs in deps
        run: npm audit --audit-level=high
      - name: IaC scan — fail on misconfig
        run: checkov -d ./infra --hard-fail-on HIGH
      - name: Container scan — fail on HIGH/CRITICAL only
        run: |
          docker build -t app:${{ github.sha }} .
          trivy image --exit-code 1 --severity HIGH,CRITICAL app:${{ github.sha }}
Common mistakes & gotchas
  • Scanners that report but never fail the build. A report nobody reads changes nothing — wire severity to a non-zero exit.
  • Threshold too strict. Failing on every LOW finding floods developers and gets the gate disabled. Start at HIGH/CRITICAL.
  • Only scanning on commit. New CVEs appear daily against code that hasn't changed — run SCA on a schedule too.
  • Ignoring the base image. Most container CVEs come from the OS layer; scan and update your base image, not just your code.
  • Secret scanning as cleanup, not prevention. Once committed, a secret is compromised — rotate it, don't just delete the commit.
Mental model

DevSecOps is airport security throughout the terminal, not just at the gate. Instead of one frantic check right before boarding (a late pen-test), there are quick automated checkpoints as you move through — bag scan (dependencies), ID check (secrets), body scan (code) — each catching problems while they're still cheap to resolve.

Modern teams manage infrastructure — servers, networks, databases — the same way they manage code: as versioned files run through a pipeline. This is Infrastructure as Code.

Instead of clicking in a cloud console, you declare infrastructure in files (Terraform, CloudFormation, Pulumi, etc.) and apply them through CI/CD. Benefits: reproducible environments, peer-reviewed infra changes, version history, and easy disaster recovery.

ToolNotes
Terraform / OpenTofuCloud-agnostic, declarative HCL. The most popular IaC tool.

A Terraform pipeline (plan on PR, apply on merge)
jobs:
  terraform:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
      - run: terraform init
      - run: terraform validate
      - run: terraform plan -out=plan.tfplan     # preview changes on PR
      - name: Apply (only on main)
        if: github.ref == 'refs/heads/main'
        run: terraform apply -auto-approve plan.tfplan
IaC guardrails are non-negotiable

An IaC pipeline can create or destroy real infrastructure. Protect it:

  • Always run terraform plan on PRs and require human review of the plan before apply.
  • Scan IaC for misconfigurations (Checkov/tfsec) as a gate.
  • Store state remotely with locking (e.g., S3 + DynamoDB) so two pipelines can't corrupt it.
  • Never let a pipeline blindly destroy production. Gate destructive actions behind explicit approvals.

Why infrastructure belongs in a pipeline at all

Clicking in a cloud console produces infrastructure nobody can review, reproduce, or audit — and "what's actually deployed" drifts from anyone's understanding. IaC pipelines exist to make infrastructure changes behave like code changes: proposed in a PR, reviewed by a human, applied by automation, and recorded in Git history. The payoff is reproducibility (stand up an identical environment from the files), auditability (every change is a commit), and disaster recovery (rebuild from code).

How the plan/apply model actually protects you

The safety of a Terraform pipeline rests on the plan/apply split. terraform plan computes the diff between your declared state and reality ("will create 1 bucket, will destroy 1 database") without changing anything — this is posted to the PR for a human to scrutinize. Only after merge does terraform apply execute that plan. State is stored remotely (e.g., S3) with a lock (e.g., DynamoDB) so two pipelines can't apply simultaneously and corrupt it. The dangerous line in any plan is destroy — that's what review catches.

Worked example — plan-on-PR, apply-on-merge with a review gate

The plan output is what a reviewer approves; apply runs only from main, using the exact saved plan so nothing changes between review and apply.

Terraform pipeline: preview on PR, apply after merge
jobs:
  plan:
    if: github.event_name == 'pull_request'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
      - run: terraform init          # connects to remote, locked state
      - run: terraform validate
      - run: terraform plan -out=plan.tfplan   # DIFF posted for human review
      - run: checkov -f plan.tfplan --hard-fail-on HIGH   # misconfig gate
  apply:
    if: github.ref == 'refs/heads/main'   # only after the PR is merged
    runs-on: ubuntu-latest
    environment: infra-prod              # protected → requires approval
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
      - run: terraform init
      - run: terraform apply -auto-approve plan.tfplan   # applies the reviewed plan
Common mistakes & gotchas
  • Auto-applying without reviewing the plan. The whole point of plan/apply is the human look at the diff — skipping it is how prod databases get destroyed.
  • Local/unlocked state. Without remote state + locking, two runs (or a run and a human) clobber each other's state file.
  • Manual "just this once" console changes. They create drift so the next plan shows confusing destroys/recreates.
  • No IaC misconfig scanning. A public S3 bucket or open security group sails through if nothing checks the config.
  • Broad pipeline cloud permissions. The IaC pipeline can change everything — scope its role to what it needs and gate destroys.
Mental model

IaC is ordering furniture with a diagram instead of moving it by hand. plan is the preview render — "here's exactly what the room will look like, and note we're throwing out the old couch." You approve the render before the movers (apply) touch anything, so there are no surprises when you walk in.

26. GitOps & Argo CD

GitOps is a modern deployment model where Git is the single source of truth for what should be running, and an automated agent continuously makes reality match Git.

GitOps = Git is the "master copy," a robot keeps reality in sync

Normally a pipeline pushes changes into your servers. GitOps flips it: you only ever edit a Git repo that describes what should be running, and a robot living in the cluster constantly compares "what Git says" to "what's actually running" and fixes any difference. Deploying = merging a commit. Rolling back = reverting a commit. And if someone sneaks in a manual change, the robot undoes it to match Git. It's like a thermostat: you set the target (Git), and it continuously works to keep the room at that temperature.

Instead of your pipeline pushing changes into a cluster (kubectl apply from CI), a GitOps agent running inside the cluster pulls the desired state from a Git repo and reconciles the cluster to match. Deploys become Git commits; rollbacks become git revert.

CI builds image→ CI updates manifest in Git→ Argo CD detects Git change→ Argo CD syncs cluster

Why GitOps is powerful

BenefitWhy

An Argo CD Application (declares what to sync)
apiVersion: argoproj.io/v1alpha1
kind: Application

  name: myapp
  namespace: argocd

  project: default
  source:
    repoURL: https://github.com/my-org/myapp-manifests

  destination:

    namespace: myapp
  syncPolicy:
    automated:
      prune: true          # delete resources removed from Git
      selfHeal: true       # revert manual drift
The clean split: CI vs CD

A leading pattern: CI tool (GitHub Actions/GitLab/Jenkins) handles continuous integration — build, test, scan, push image, and bump the image tag in a manifests repo. Argo CD or Flux handles continuous deployment — watching that repo and syncing to Kubernetes. Each tool does what it's best at. Flux is the other big CNCF GitOps agent alongside Argo CD.

Why GitOps flips the deployment direction

Traditional CD pushes: the pipeline holds cluster credentials and runs kubectl apply from outside. That means your CI system can touch production directly — a big attack surface — and there's no guarantee the cluster still matches what you last deployed (someone can kubectl edit and cause silent drift). GitOps exists to fix both: make Git the declared truth, and put a pull-based agent inside the cluster that continuously reconciles reality to Git. Now deploys are commits (auditable), rollbacks are reverts, drift is auto-corrected, and CI never needs cluster credentials.

How the reconciliation loop actually runs

The Argo CD agent runs in the cluster on a timer (and via webhooks). Each cycle it: (1) fetches the manifests from the Git repo at the target revision — the desired state; (2) queries the Kubernetes API for the live state; (3) diffs them; (4) if they differ and selfHeal is on, applies the desired state to make them match (and with prune, deletes resources removed from Git). Because this loop never stops, a manual kubectl change is detected on the next cycle and reverted — the cluster is always dragged back to what Git says.

Worked example — deploy and roll back purely via Git

With the Argo CD Application shown above (auto-sync + selfHeal), no kubectl is ever run by a human to deploy. You operate the cluster through Git alone.

Deploy = commit; rollback = revert
# Deploy v2: CI (or you) update the image tag in the manifests repo
yq -i '.spec.template.spec.containers[0].image = "myapp:v2"' deploy.yaml
git commit -am "deploy v2" && git push
# → Argo CD detects the change within seconds and syncs v2 to the cluster.

# Roll back: just revert the commit
git revert HEAD && git push
# → Argo CD syncs the cluster back to v1. No kubectl, full audit trail.

# Someone hand-edits the cluster? selfHeal reverts it on the next reconcile.
Common mistakes & gotchas
  • Mixing push and pull. Running kubectl apply from CI and using selfHeal means the agent fights your pipeline — pick one model.
  • Committing plaintext secrets to the manifests repo. Git is the source of truth and readable — use Sealed Secrets / External Secrets, never raw secrets.
  • Enabling prune carelessly. Removing a resource from Git will delete it from the cluster — powerful, and dangerous if unexpected.
  • Storing app code and manifests in the same repo can create trigger loops (a deploy commit re-triggers CI). Many teams separate the manifests repo.
  • Ignoring "OutOfSync" status. It's telling you reality drifted from Git — investigate rather than force-syncing blindly.
Mental model

GitOps is a thermostat. You set the target temperature (the desired state in Git) and a device in the room (the in-cluster agent) constantly compares the actual temperature to the target and works to close the gap. Open a window (a manual change) and it just runs the heater harder to get back to target. You never touch the furnace directly — you only ever change the dial.

27. Secrets Management

Pipelines constantly need credentials — registry logins, cloud keys, deploy tokens. Mishandling secrets is one of the most common and damaging CI/CD security failures.

Where secrets can live (worst → best)

ApproachVerdict
Hard-coded in the pipeline file / repo❌ Never. Leaks to anyone with repo access and lives forever in Git history.
Built-in CI secret store (GHA/GitLab/Jenkins credentials)✅ Good baseline — encrypted, masked in logs, scoped.
External secrets manager (Vault, AWS Secrets Manager, etc.)✅✅ Best for scale — central rotation, audit, fine-grained access.

Secrets best practices
  • Prefer OIDC / workload identity for cloud access — eliminates long-lived keys entirely.
  • Never echo secrets in logs; CI tools mask known secrets but not values you print yourself.
  • Scope secrets tightly — per-environment, per-repo; production secrets shouldn't be reachable from PR builds.
  • Rotate regularly and revoke immediately on suspected exposure.
  • Scan for committed secrets (Gitleaks) as a pipeline gate.
  • Be careful with fork PRs — don't expose secrets to untrusted code.
The classic secret leak

A developer commits an AWS key "temporarily," it gets scraped by bots within minutes, and attackers run up a huge bill or exfiltrate data. Treat every committed secret as compromised — rotate it, don't just delete the commit (it's still in history). Prevention (secret scanning + OIDC) is far cheaper than cleanup.

Why the ladder from "hard-coded" to "OIDC" matters

Every rung up the ladder removes something an attacker can steal. Hard-coded secrets live forever in Git history and leak to anyone with read access. A CI secret store encrypts and masks them but they're still long-lived — if leaked, they work until rotated. An external manager (Vault) adds central rotation and audit. OIDC removes the stored secret entirely: there's nothing durable to steal, because credentials are minted fresh per run and expire in minutes. The goal is to climb as high as your setup allows.

How OIDC eliminates the stored secret (mechanically)

Instead of storing an AWS key, you configure a trust relationship: AWS is told "trust identity tokens issued by GitHub's OIDC provider, but only for repo X on branch main." At runtime the job asks GitHub for a signed OIDC token describing itself (repo, branch, workflow). It hands that token to AWS STS, which verifies the signature and the trust conditions, then returns temporary credentials valid for minutes. Nothing long-lived is ever stored in GitHub — the "secret" is a short-lived token generated on demand and thrown away.

Worked example — masking pitfalls and the OIDC alternative
What leaks, what's masked, and the keyless path
steps:
  # ❌ leaks: transforming a secret defeats masking
  - run: echo "${{ secrets.TOKEN }}" | base64        # base64 value appears in logs!

  # ✅ safe: pass as env, let the tool read it, never echo it
  - run: ./deploy.sh
    env: { TOKEN: ${{ secrets.TOKEN }} }             # value shown as *** in logs

  # ✅✅✅ best: no stored secret at all (OIDC → temporary creds)
  - uses: aws-actions/configure-aws-credentials@v4
    with:
      role-to-assume: arn:aws:iam::123:role/gha-deploy   # trust scoped to this repo
      aws-region: us-east-1
  - run: aws s3 sync ./dist s3://bucket                   # uses temp creds, expire in minutes
Common mistakes & gotchas
  • Echoing/transforming secrets. Masking only catches the exact stored string; base64/substrings slip through.
  • Deleting a leaked commit instead of rotating. It's still in history and likely already scraped — the credential is compromised, rotate it.
  • Over-broad OIDC trust. A trust policy that allows any repo/branch lets other repos assume your role — scope it to repo:org/name:ref:refs/heads/main.
  • Exposing prod secrets to fork PRs. Untrusted code could exfiltrate them; keep prod secrets out of PR-triggered runs.
  • One shared secret everywhere. Scope per environment so a staging leak can't touch production.
Mental model

A stored long-lived key is a house key under the doormat — convenient, but anyone who finds it gets in until you re-key the lock. OIDC is a hotel key card: the front desk issues a fresh one that only works for your room and expires at checkout. Lose it and it's already useless. Always prefer the key card.

28. Observability & DORA Metrics

You can't improve what you don't measure. Mature teams monitor both their pipelines and their delivery performance.

Pipeline observability

  • Build success/failure rates — is the pipeline reliable? A high failure rate erodes trust.
  • Build duration — slow pipelines kill productivity; track and optimize.
  • Flaky test detection — find and fix tests that fail intermittently.
  • Queue times — are jobs waiting for runners? Add capacity.
  • Notifications — pipeline status to Slack/Teams/email so failures are seen fast.

DORA metrics — the industry standard for delivery performance

The DORA (DevOps Research and Assessment) metrics are the widely accepted way to measure how well a team delivers software:

MetricWhat it measuresElite performers
Deployment FrequencyHow often you deploy to production.On-demand (multiple/day)
Lead Time for ChangesTime from commit to running in production.Less than a day
Change Failure Rate% of deploys causing a failure needing remediation.0–15%
Mean Time to Recovery (MTTR)How fast you recover from a failed deploy.Less than an hour
The two axes: speed AND stability

Notice DORA balances speed (frequency, lead time) with stability (failure rate, recovery time). Good CI/CD improves all four together — the myth that "moving fast means breaking things" is wrong. Elite teams deploy more often and fail less, because small automated changes are inherently safer. Use DORA to guide where to invest in your pipeline.

Why measure the pipeline and the delivery, not just the app

Two blind spots sink teams. First, an unreliable pipeline (slow, flaky, often red) quietly taxes every engineer and erodes trust in the gate — you can't fix what you don't track. Second, gut feelings about "are we shipping well?" are usually wrong. DORA metrics exist to replace opinion with four research-backed numbers that correlate with organizational performance, so improvement efforts target the real bottleneck instead of the loudest complaint.

How DORA metrics are actually computed

They're derived from data your tools already emit. Deployment Frequency = count of successful production deploys per period (from deploy job runs). Lead Time for Changes = timestamp of production deploy minus the commit's authored time (join Git history to deploy records). Change Failure Rate = deploys that triggered a rollback/hotfix ÷ total deploys (tag incident-linked deploys). Recovery Time = incident-resolved timestamp minus incident-start (from your alerting/incident tool). Many platforms compute these automatically; otherwise you join CI/CD events with incident data.

Worked example — emit deploy/failure events to compute DORA

Instrumenting the pipeline to record deploy and rollback events gives you the raw data for all four metrics.

Recording the events DORA is derived from
deploy:
  runs-on: ubuntu-latest
  environment: production
  steps:
    - run: ./deploy.sh
    - name: Record a successful deployment (→ frequency, lead time)
      if: success()
      run: |
        curl -X POST "$METRICS_URL/deploy" -d '{
          "sha": "${{ github.sha }}",
          "committed_at": "${{ github.event.head_commit.timestamp }}",
          "deployed_at": "'"$(date -u +%FT%TZ)"'",
          "status": "success"
        }'
    - name: Record a failed deploy (→ change failure rate, recovery)
      if: failure()
      run: curl -X POST "$METRICS_URL/deploy" -d '{"sha":"${{ github.sha }}","status":"failure"}'
Common mistakes & gotchas
  • Turning DORA into targets to game. Optimizing "deploy frequency" by splitting one deploy into ten meaningless ones helps nobody — measure to learn, not to score.
  • Tracking speed but not stability (or vice versa). All four move together; watching only frequency hides a rising failure rate.
  • Ignoring pipeline duration/flakiness. A 40-minute flaky pipeline destroys lead time and trust even if DORA looks okay on paper.
  • Comparing teams' absolute numbers. DORA is best used to track your own trend over time, not to rank teams with different contexts.
Mental model

DORA is a car dashboard with two gauges you must read together: a speedometer (how fast/often you ship) and an engine-temperature light (how often you break and how fast you cool down). Going fast is only good if the engine stays cool — and the research shows well-tuned engines actually go faster and run cooler.

29. Build Caching & Pipeline Speed

Slow pipelines kill developer flow and cost money. The biggest wins come from caching dependencies, caching Docker layers, and only doing work that's actually needed.

Dependency + Docker layer caching in GitHub Actions
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      # Language dependency cache (keyed on the lockfile)
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: 'npm'              # built-in npm cache, keyed on package-lock.json

      - run: npm ci
      - run: npm test

      # Docker layer caching via buildx + GitHub cache backend
      - uses: docker/setup-buildx-action@v3
      - uses: docker/build-push-action@v6
        with:
          push: true
          tags: myapp:${{ github.sha }}
          cache-from: type=gha        # pull layer cache from GitHub
          cache-to: type=gha,mode=max # push layer cache back
Speed tactics that compound
  • Cache on the lockfile hash, not a static key — otherwise you serve stale caches.
  • Shard tests across parallel jobs (--shard=1/4) and fan them out with a matrix.
  • Fail fast: run the cheapest checks (lint, unit) before the expensive ones (e2e, integration).
  • Only build what changed in monorepos (see §37) using path filters or affected-graph tools.
  • Right-size runners: bigger runners for compile-heavy jobs pay for themselves in saved wall-clock time.

Why pipeline speed is a first-class concern

Pipeline latency directly sets your feedback loop. A 3-minute pipeline lets a developer fix-and-retry in the same train of thought; a 30-minute one means they context-switch away, and the fix arrives an hour later. Slow CI also throttles everyone — a shared main branch with a 30-minute merge queue caps how fast the whole team ships. Speed is therefore not a luxury; it's a lever on lead time (a DORA metric) and on morale.

How the two big caches actually work

Dependency cache: keyed on the lockfile hash, it saves/restores node_modules/~/.m2/pip cache so a cache hit skips the slow install entirely. Docker layer cache: BuildKit hashes each layer's inputs; with a remote backend (type=gha, a registry, or type=s3) those layers persist between runs on different runners. On the next build, unchanged layers are pulled from cache instead of rebuilt — which is why a well-ordered Dockerfile (deps before source) turns a 5-minute image build into 30 seconds. Parallelism adds a third lever: sharding tests across a matrix runs quarters of the suite simultaneously.

Worked example — sharded tests fanned out with a matrix

Splitting the suite into 4 shards run in parallel turns a 12-minute test stage into ~3 minutes.

Parallel test sharding
jobs:
  test:
    strategy:
      matrix: { shard: [1, 2, 3, 4] }     # 4 parallel jobs
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: npm }   # dependency cache
      - run: npm ci
      - run: npx jest --shard=${{ matrix.shard }}/4   # each runs 1/4 of tests
Common mistakes & gotchas
  • Static cache keys serve stale deps forever; over-specific keys never hit. Key on the lockfile hash with a restore-keys fallback.
  • Docker cache that never persists. Local layer cache is discarded on a fresh runner — you need a remote backend (cache-to/from).
  • Bad Dockerfile ordering (source copied before deps installed) busts the cache on every code change.
  • Sharding with uneven splits leaves one shard doing most of the work — use a balancer or time-based split.
  • Caching for correctness. A stale cache must never change the result — only the speed.
Mental model

Speeding up CI is meal prep plus extra cooks. Caching is the stocked, pre-chopped pantry so you skip shopping and prep (dependency + layer cache). Sharding is hiring four cooks to each make a quarter of the dishes at once. Do both and a 12-minute dinner rush becomes a calm 2 minutes.

30. Progressive Delivery — Argo Rollouts & Automated Canary

Basic blue-green and canary were covered in §12. Progressive delivery goes further: automatically shift traffic in steps and automatically roll back if metrics degrade — no human watching a dashboard at 2 a.m.

Progressive delivery = a dimmer switch, not an on/off switch

A normal deploy flips everyone to the new version at once — if it's broken, everyone's broken. Progressive delivery is a dimmer: give the new version to 5% of users, watch the error graphs, and only turn it up if they stay healthy. If errors spike, dim it back to zero automatically. The tools (Argo Rollouts, Flagger) automate both the dial and the watching.

Argo Rollouts — canary with automated analysis
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata: { name: myapp }
spec:
  replicas: 5
  strategy:
    canary:
      steps:
        - setWeight: 5
        - pause: { duration: 2m }
        - analysis:                     # gate: check metrics before proceeding
            templates: [{ templateName: success-rate }]
        - setWeight: 25
        - pause: { duration: 5m }
        - setWeight: 50
        - pause: { duration: 5m }
        # implicit final step -> 100%
  selector: { matchLabels: { app: myapp } }
  template: { metadata: { labels: { app: myapp } }, spec: { containers: [ ... ] } }
---
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata: { name: success-rate }
spec:
  metrics:
    - name: success-rate
      interval: 1m
      successCondition: result[0] >= 0.99   # >=99% success or abort
      provider:
        prometheus:
          address: http://prometheus.monitoring:9090
          query: |
            sum(rate(http_requests_total{app="myapp",code!~"5.."}[2m]))
            / sum(rate(http_requests_total{app="myapp"}[2m]))
Argo Rollouts vs Flagger

Both do automated progressive delivery on Kubernetes. Argo Rollouts introduces a Rollout CRD replacing your Deployment and pairs naturally with Argo CD. Flagger keeps your Deployment and drives a service mesh/ingress (Istio, Linkerd, NGINX) to shift traffic. Both query Prometheus for the analysis gate — connecting straight to your Observability stack.

Why automate the canary instead of watching it manually

A manual canary requires an engineer to babysit dashboards, decide when to bump traffic, and react fast at 2am if metrics degrade — slow, error-prone, and unsustainable. Progressive delivery exists to encode that judgment as policy: the traffic steps and the pass/fail thresholds are declared once, and the controller executes them tirelessly, promoting on healthy metrics and rolling back on bad ones without a human in the loop.

How the analysis gate mechanically decides go/no-go

Between traffic steps the controller launches an AnalysisRun: it queries your metrics provider (usually Prometheus) with a promql expression on a schedule, compares the result to a successCondition, and counts consecutive passes/failures. If the metric stays within bounds for the required interval, the rollout advances to the next weight; if it breaches (e.g., success rate drops below 99%), the controller aborts — shifting all traffic back to the stable version automatically. The traffic shifting itself is done via the service mesh/ingress weights, exactly like a manual canary, just driven by the controller.

Worked example — reading the automated canary as a state machine

The Rollout spec above is literally a state machine: set weight → pause → analyze → (pass) advance / (fail) abort. Here's the operator's-eye view of a run.

kubectl argo rollouts get rollout myapp (abridged)
Name:     myapp
Status:   ॥ Paused
Strategy: Canary
  Step:   2/5  (analysis)
  Weight: 5
  SetWeight 5 ✔  Pause 2m ✔  Analysis[success-rate] ⧗ running (0.994 >= 0.99 ✔)
  → advancing to SetWeight 25
# If success-rate had returned 0.97: Analysis ✘ → Rollout Degraded → auto abort to stable
Common mistakes & gotchas
  • Analysis window too short. A 30-second sample is noisy; a bad canary can pass by luck. Give metrics enough traffic/time to be significant.
  • Wrong metric. Gating on CPU instead of user-facing error rate/latency lets a broken-but-idle version promote.
  • No baseline comparison. "99% success" may be normal or a regression from 99.99% — compare canary against the stable version, not an absolute.
  • Canary with a breaking DB migration. Both versions share the DB; progressive delivery doesn't save you from an incompatible schema (use expand/contract, §13).
  • Forgetting Prometheus reachability/auth from the AnalysisRun — a failed query can stall or falsely abort the rollout.
Mental model

Progressive delivery is a self-driving dimmer switch. You tell it "raise the lights 5% → 25% → 50% → 100%, but at each step check the room isn't overheating." It turns the dial and reads the thermometer itself — brightening when safe and snapping back to dark the instant things get too hot, all without you standing at the wall.

31. Runners & Pipeline Scaling

Where does CI actually run? Understanding runners/agents — and scaling them — is what keeps pipelines fast and costs sane as a team grows.

OptionProsConsUse when
Cloud-hosted (GitHub/GitLab SaaS)Zero maintenance, always patchedPer-minute cost, limited specs, no private-network accessMost teams, getting started
Self-hosted staticCustom hardware, private network, cachingYou patch & secure them; idle costSpecial hardware, VPC access
Ephemeral autoscaling (ARC on K8s)Scale to zero, one clean pod per job, cheapMore setup (operator, HPA)High-volume, security-sensitive CI
Ephemeral runners are the gold standard

Run each CI job in a fresh, single-use environment that's destroyed afterward (GitHub's Actions Runner Controller on Kubernetes, GitLab's Kubernetes executor). Benefits: no state leaks between jobs (a security win — a malicious PR can't poison the next build), scale-to-zero saves money, and every job starts clean. Never reuse a self-hosted runner across untrusted PRs.

Self-hosted runners + public repos = danger

If a self-hosted runner serves a public repository, anyone can open a PR whose workflow runs arbitrary code on your runner — potentially reaching your internal network or cloud credentials. Require approval for PRs from first-time/forked contributors, use ephemeral runners, and never put long-lived cloud keys on a runner (use OIDC — next section).

Why runner strategy decides both speed and cost

Runners are where CI actually consumes money and time. Too few and jobs queue (killing lead time); too many idle and you burn budget. Cloud-hosted runners trade per-minute cost for zero maintenance; static self-hosted runners trade idle cost and patching burden for custom hardware and private-network access. The reason ephemeral autoscaling exists is to get the best of both: capacity that scales with demand (down to zero when idle) and a clean environment per job.

How ephemeral autoscaling (ARC) works mechanically

A controller (GitHub's Actions Runner Controller on Kubernetes) watches the queue of pending jobs. When jobs appear, it creates runner pods up to a limit; each pod registers with GitHub, runs exactly one job, then deregisters and is deleted. Because each job gets a fresh pod, no state (files, caches, credentials) leaks to the next job — a security property. When the queue drains, pod count scales back to zero, so you pay only for actual build time.

Worked example — autoscaling ephemeral runners on Kubernetes
A scale set: 0→N one-shot runner pods on demand
apiVersion: actions.github.com/v1alpha1
kind: AutoscalingRunnerSet
metadata: { name: prod-runners }
spec:
  githubConfigUrl: https://github.com/my-org
  minRunners: 0            # scale to ZERO when idle → no idle cost
  maxRunners: 50           # cap concurrency (and spend)
  template:
    spec:
      containers:
        - name: runner
          image: ghcr.io/actions/actions-runner:latest
          resources: { requests: { cpu: "1", memory: 2Gi } }
# Each pod runs ONE job then is destroyed — clean, isolated, no state leak.
Common mistakes & gotchas
  • Reusing a runner across untrusted PRs. A malicious PR can plant a backdoor for the next job — always ephemeral for public/forked work.
  • Long-lived cloud keys on a runner. A compromised runner leaks them; use OIDC so there's nothing durable to steal.
  • Static runners drift. Hand-maintained tool versions cause "works on runner A, fails on B." Bake tools into the image.
  • No maxRunners cap. A flood of jobs can spin up unbounded pods and a surprise bill.
  • Ephemeral runners with no cache. Fresh pods re-download everything — pair with a registry mirror or cache volume.
Mental model

Cloud-hosted runners are ride-share — no car to own, pay per trip. Static self-hosted runners are owning a car — always available, but you insure, fuel, and service it even when parked. Ephemeral autoscaling is a fleet of self-driving taxis that materialize when you call, take exactly one passenger, and vanish — no idle cost, spotless each time.

32. Pipeline Security & Keyless Cloud Auth (OIDC)

Your CI pipeline is a high-value target: it has credentials to your cloud, registry, and production. Hardening it — especially removing long-lived secrets — is core lead-engineer work.

Keyless AWS auth via OIDC — no stored secrets
permissions:
  id-token: write        # allow the job to request an OIDC token
  contents: read
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/github-deploy
          aws-region: us-east-1
      - run: aws s3 sync ./dist s3://my-bucket   # uses temporary creds
Pipeline hardening checklist
  • OIDC everywhere — eliminate long-lived cloud/registry keys.
  • Pin actions by commit SHA, not a mutable tag (uses: actions/checkout@<sha>) — a hijacked tag can run malicious code with your secrets.
  • Least-privilege permissions: — default to read-only, grant write per-job.
  • Protect production with required reviewers/environments and manual approval gates.
  • Scan for leaked secrets (gitleaks) and dependencies (Dependabot/Renovate) in CI.

Why the pipeline itself is a top attack target

Your CI pipeline holds the keys to everything downstream — cloud accounts, registries, production clusters — and it executes code on every push. That makes it a high-value target: compromise the pipeline and you can inject a backdoor into every artifact it builds (the SolarWinds pattern). Hardening exists to shrink two things: the credentials an attacker could steal (remove long-lived secrets via OIDC) and the code an attacker could inject (pin actions, least-privilege permissions, protected environments).

How OIDC trust actually gates who can assume a role

The security of keyless auth lives in the cloud role's trust policy conditions. AWS verifies the OIDC token's signature and that its claims match your conditions: the aud (audience) and the sub (subject, e.g., repo:my-org/my-app:ref:refs/heads/main). A too-broad sub like repo:my-org/* would let any repo in your org assume the role — so the condition scoping is the entire defense. Get it precise and only your specific repo/branch/environment can obtain credentials.

Worked example — the scoped trust policy that makes OIDC safe
IAM role trust policy — scoped to one repo & branch
{
  "Effect": "Allow",
  "Principal": { "Federated": "arn:aws:iam::123:oidc-provider/token.actions.githubusercontent.com" },
  "Action": "sts:AssumeRoleWithWebIdentity",
  "Condition": {
    "StringEquals": {
      "token.actions.githubusercontent.com:aud": "sts.amazonaws.com"
    },
    "StringLike": {
      "token.actions.githubusercontent.com:sub": "repo:my-org/my-app:ref:refs/heads/main"
    }
  }
}
# Only workflows in my-org/my-app on the main branch can assume this role.
Pinning an action to a SHA (defeats tag hijacking)
- uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683   # v4.2.2 pinned
# A mutable @v4 tag could be repointed to malicious code that runs with your secrets.
Common mistakes & gotchas
  • Wildcard OIDC sub. repo:org/* lets any org repo assume the role — scope to the exact repo/branch/environment.
  • Floating action tags. @v4 is mutable; a hijacked tag runs attacker code with your token. Pin the SHA.
  • Default write-all permissions. Set permissions: read-all at the top and grant write per-job only where needed.
  • Untrusted PRs with pull_request_target can access secrets with attacker-controlled code — a classic escalation. Avoid it for fork PRs.
  • Assuming OIDC means "no config." The token is only as safe as the trust conditions you write.
Mental model

OIDC is showing a signed ID badge to a security guard instead of carrying a master key. The guard (the cloud) checks the badge says exactly "my-app team, main entrance" before opening one specific door for a few minutes. Pinning actions by SHA is like only accepting sealed packages you've verified — not whatever arrives labeled "v4," which anyone could relabel.

33. Supply Chain Security & SLSA

After the SolarWinds and Log4Shell incidents, proving how an artifact was built became a hard requirement. SLSA is the industry framework; provenance + signing are how you satisfy it.

SLSA = a tamper-evident receipt for your build

SLSA (pronounced "salsa") is a checklist of build-integrity levels. The core idea: your pipeline emits provenance — a signed statement saying "this exact artifact was built from this commit, by this workflow, at this time." Consumers verify that receipt before trusting the artifact. It's the difference between "trust me" and "here's cryptographic proof."

SLSA levelWhat it guarantees
Level 1Provenance exists (build is documented)
Level 2Provenance is signed by a hosted build service
Level 3Build runs on hardened, isolated infrastructure; provenance is non-forgeable
Generate + verify build provenance and signatures
# Sign the image keylessly (identity from the CI OIDC token) with cosign
cosign sign --yes myregistry/myapp:${GIT_SHA}

# Attach SBOM + SLSA provenance as attestations
cosign attest --yes --type slsaprovenance --predicate provenance.json myregistry/myapp:${GIT_SHA}

# In the deploy step (or an admission controller), verify before running:
cosign verify myregistry/myapp:${GIT_SHA} \
  --certificate-identity-regexp "https://github.com/myorg/.*" \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
Close the loop in the cluster

Signing only helps if something checks the signature. Deploy an admission controller — Kyverno or Sigstore Policy Controller — that refuses to run any image not signed by your pipeline's identity. Now an attacker who pushes a rogue image to your registry still can't get it to run. This ties directly into the security section of the Kubernetes guide.

Why provenance became a hard requirement

SolarWinds and Log4Shell proved that trusting an artifact because "it came from our registry" is insufficient — attackers compromise build systems and dependencies. Supply chain security exists to answer, with cryptographic proof, "was this exact artifact built from the source we think, by the pipeline we trust, and not tampered with since?" SLSA is the leveled framework for that assurance; provenance and signing are the mechanisms that satisfy it.

How signing + verification closes the loop

The flow has two halves that must both exist. Produce: in CI, cosign signs the image — keylessly, using the pipeline's OIDC identity — and attaches attestations (an SBOM listing contents, and SLSA provenance describing the build). The signature and identity are recorded in a transparency log. Enforce: at deploy time an admission controller verifies the signature matches an expected identity (your CI's OIDC issuer + repo) before letting the image run. Without the enforce half, signing is theater — the check is what actually blocks a rogue image.

Worked example — the enforcement policy that rejects unsigned images

A Kyverno policy that only admits images signed by your pipeline identity. Push a rogue image and it's blocked at admission.

Kyverno policy — verify image signature identity
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata: { name: require-signed-images }
spec:
  validationFailureAction: Enforce      # BLOCK, don't just warn
  rules:
    - name: verify-cosign
      match: { any: [{ resources: { kinds: [Pod] } }] }
      verifyImages:
        - imageReferences: ["myregistry/*"]
          attestors:
            - entries:
                - keyless:
                    issuer: "https://token.actions.githubusercontent.com"
                    subject: "https://github.com/myorg/*"   # only OUR pipeline's identity
# Unsigned image, or signed by anyone else → admission denied.
Common mistakes & gotchas
  • Signing without verifying. Signatures nobody checks add zero security — deploy the admission controller.
  • Verifying only that a signature exists, not whose. An attacker can sign their own image; pin the expected issuer + subject.
  • Confusing SBOM with provenance. SBOM = what's inside; provenance = how/where it was built. You want both.
  • Claiming SLSA L3 on shared, non-isolated runners. L3 requires hardened, isolated builds with non-forgeable provenance.
  • Key management pain. Prefer keyless (OIDC identity) signing over managing long-lived signing keys.
Mental model

SLSA is a tamper-evident seal plus a signed delivery receipt on a package. The seal proves nobody opened it after the factory; the receipt says which factory and batch. But it only protects you if the receiving dock actually inspects the seal (the admission controller) and rejects anything unsealed or from an unknown factory.

34. Monorepo & Path-Filtered CI

In a monorepo, running every pipeline on every change is wasteful and slow. Build and test only what a change actually affects.

Path-filtered workflow trigger
# .github/workflows/api.yml — only runs when API code changes
on:
  push:
    paths:
      - 'apps/api/**'
      - 'libs/shared/**'      # also run if a shared lib it depends on changes
      - '.github/workflows/api.yml'
jobs:
  api-ci: { runs-on: ubuntu-latest, steps: [ ... ] }
Graph-aware tools go further

Path filters are simple but coarse. Build systems like Nx (nx affected), Turborepo, and Bazel understand the actual dependency graph — if libs/shared changes, they know precisely which apps are affected and rebuild/test only those, with remote caching so unchanged targets are never rebuilt across the whole team. This is what makes CI on a large monorepo (see the Git guide's monorepo section) stay fast.

Why running everything on every change breaks down

In a monorepo with dozens of apps, a one-line change to one service shouldn't rebuild and re-test the other 40 — that's minutes-to-hours of wasted compute and a slow, discouraging feedback loop. Path-filtered CI exists to make the work proportional to the change: touch the API, only the API pipeline runs. The subtlety is shared code — a change to a shared library legitimately affects every app that imports it, and naive path filters miss that.

How path filters vs graph-aware tools decide what to run

Path filters are purely textual: the CI system compares the changed file paths in the push/PR against your glob patterns and creates the job only if there's a match. Simple, but it can't know that libs/shared feeds into apps/api unless you list that path manually. Graph-aware tools (Nx/Turborepo/Bazel) build a real dependency graph, compute the diff from a base commit, and mark every transitively affected target — then a remote cache lets any unchanged target reuse a previous result instead of rebuilding. That's how huge monorepos keep CI fast and correct.

Worked example — dynamic affected-project matrix with Nx

nx affected computes exactly which projects a change touches (including via shared libs) and feeds them into a matrix, so CI runs only what's needed — no manual path lists to keep in sync.

Build only affected projects (graph-aware)
jobs:
  affected:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }          # need history to diff against base
      - run: npm ci
      - name: Compute & test only affected projects
        run: |
          npx nx affected --target=lint  --base=origin/main
          npx nx affected --target=test  --base=origin/main
          npx nx affected --target=build --base=origin/main
        # nx follows the dependency graph: a change in libs/shared
        # automatically includes every app that imports it.
Common mistakes & gotchas
  • Path filters that miss shared deps. Filtering only apps/api/** skips CI when a shared lib the API uses changes — a real bug reaches prod untested. List dependency paths too, or use a graph tool.
  • Shallow checkout with affected tools. nx/turbo affected needs Git history to compute the diff — use fetch-depth: 0.
  • Wrong --base. Diffing against the wrong ref either runs everything or nothing.
  • No remote cache. Without it, "affected" still rebuilds shared deps on every runner — you lose most of the speedup.
  • Forgetting the workflow file itself in path filters, so changes to the pipeline don't trigger a validating run.
Mental model

A monorepo is an apartment building. If you repaint one flat, you don't re-inspect all 40 — you only check that flat (path filter). But if you replace a shared water pipe (a shared library), you must check every flat it feeds (graph-aware). Smart CI knows the plumbing diagram and inspects exactly the affected flats, no more, no less.

35. DORA Metrics & Delivery Performance

How do you know if your CI/CD is actually good? The DORA metrics (from Google's DevOps Research & Assessment / the Accelerate book) are the research-backed measures of software delivery performance.

MetricMeasuresElite performers
Deployment FrequencyHow often you ship to prodOn-demand (multiple/day)
Lead Time for ChangesCommit → running in prodLess than a day
Change Failure Rate% of deploys causing a failure0–15%
Failed Deployment Recovery TimeTime to recover from a bad deployLess than an hour
How to improve each (concrete levers)
  • Deployment Frequency ↑ — automate the pipeline fully; deploy small changes continuously; use feature flags.
  • Lead Time ↓ — trunk-based dev + small PRs (see branching strategies), fast caching pipelines (§32).
  • Change Failure Rate ↓ — automated tests, quality gates, progressive delivery with automated rollback.
  • Recovery Time ↓ — instant rollback (GitOps git revert), good observability to detect fast.

Measure these (many platforms compute them automatically) and treat them as your delivery scorecard — they connect CI/CD directly to the SRE reliability discipline.

Why these four metrics, and why together

The DORA research (Google's DevOps Research & Assessment, the Accelerate book) found these four measures reliably distinguish high- from low-performing organizations — and, crucially, that speed and stability are not a trade-off. Teams that deploy frequently in small batches also fail less and recover faster, because small changes are easier to test, review, and reverse. The four exist as a set precisely so you can't cheat one at the expense of another — chasing frequency while ignoring failure rate is caught by the stability pair.

How to move each metric, mechanically

Each metric has concrete pipeline levers. Deployment Frequency rises when the pipeline is fully automated and changes are small (feature flags decouple deploy from release). Lead Time falls with trunk-based development, small PRs, and fast cached pipelines. Change Failure Rate falls with automated tests, quality gates, and progressive delivery that catches bad releases at 5% traffic. Recovery Time falls with instant rollback (GitOps git revert) and good observability to detect fast. Notice every lever is something covered earlier in this guide.

Worked example — a bad metric and its pipeline fix
Reading a DORA scorecard and acting on it
Deployment Frequency ...... 1 / week      (Medium)
Lead Time for Changes ..... 9 days        (Medium)   ← bottleneck
Change Failure Rate ....... 8%            (Elite)
Recovery Time ............. 25 min        (Elite)

Diagnosis: stability is great, but lead time is slow.
Fix (not "deploy more"): shrink PRs + trunk-based dev, and cut the
12-min pipeline to 3 min via caching + test sharding (§32).
→ Faster feedback shortens commit→prod without hurting the healthy failure rate.
Common mistakes & gotchas
  • Gaming a single metric. Splitting one real deploy into ten trivial ones inflates frequency but delivers nothing.
  • Optimizing speed while ignoring stability. The two pairs must move together; watch all four.
  • Ranking teams by absolute numbers. Context differs — track each team's trend, not a leaderboard.
  • Measuring without acting. A dashboard nobody uses to pick the next improvement is just decoration.
  • Forgetting pipeline health feeds these. A flaky, slow pipeline silently wrecks lead time and recovery.
Mental model

DORA is a fitness tracker for your delivery process: two "how active" numbers (frequency, lead time) and two "how healthy" numbers (failure rate, recovery). The insight is that the fittest teams score well on both — being fast is a result of being healthy (small, safe, automated changes), not a trade against it.

36. A Complete Real-World Pipeline

Tying every concept together: here's a production-grade GitHub Actions pipeline for a containerized app — test, scan, build multi-arch, sign, and deploy via GitOps. This is the shape you'd actually run.

.github/workflows/deploy.yml (production-shaped)
name: build-and-deploy
on:
  push: { branches: [main] }
permissions:
  contents: read
  id-token: write          # for OIDC keyless auth (no stored cloud/registry keys)
  packages: write

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: npm }   # dependency caching
      - run: npm ci
      - run: npm test -- --coverage              # fail the build on test failure
      - run: npx semgrep ci                       # SAST security scan

  build:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3
      - uses: aws-actions/configure-aws-credentials@v4    # OIDC, no static keys
        with: { role-to-assume: arn:aws:iam::123:role/ci, aws-region: us-east-1 }
      - uses: docker/build-push-action@v6
        with:
          push: true
          platforms: linux/amd64,linux/arm64        # multi-arch (§multiarch in Docker guide)
          tags: myregistry/myapp:${{ github.sha }}
          cache-from: type=gha                       # layer caching
          cache-to: type=gha,mode=max
      - name: Scan image for CVEs
        run: trivy image --severity HIGH,CRITICAL --exit-code 1 myregistry/myapp:${{ github.sha }}
      - name: Sign the image (supply chain)
        run: cosign sign --yes myregistry/myapp:${{ github.sha }}

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment: production          # requires manual approval (protected env)
    steps:
      - uses: actions/checkout@v4
        with: { repository: acme/k8s-manifests, token: ${{ secrets.MANIFEST_TOKEN }} }
      - name: Bump image tag in Git (GitOps — Argo CD deploys it)
        run: |
          yq -i '.spec.template.spec.containers[0].image = "myregistry/myapp:${{ github.sha }}"' \
            overlays/prod/deployment.yaml
          git commit -am "deploy ${{ github.sha }}" && git push
Read the pipeline as a story

It reads top to bottom like a factory line: test (does the code work + is it secure?) → build (package a multi-arch image, scan it for vulnerabilities, cryptographically sign it) → deploy (after a human approves, update the Git manifests so Argo CD rolls it out). Every gate protects production; nothing touches prod directly. This single file combines caching, OIDC security, multi-arch, scanning, signing, and GitOps — the concepts from across this guide, working together.

What makes this "production-grade"
  • Gated stages — build only runs if tests pass; deploy needs approval.
  • OIDC keyless auth — zero long-lived cloud/registry secrets (§35).
  • Security built in — SAST + image CVE scan + signing (§36).
  • Fast — dependency + Docker layer caching (§32).
  • GitOps deploy — the pipeline commits to Git; the cluster pulls. Auditable, revertible.

Why this shape, and how the gates chain

This pipeline is the synthesis of every prior section, arranged so that each stage is a gate the next depends on. build declares needs: test, so a failing test or SAST finding stops everything before an image is ever built. deploy declares needs: build and environment: production, so it can't run until a scanned, signed image exists and a human approves. Nothing touches production directly — the deploy step only writes a Git commit, handing off to GitOps. That chaining is what turns a pile of good practices into a safe, ordered delivery flow.

How to trace one commit through the whole machine

Follow SHA abc123: a push to main fires the workflow → test runs on a fresh runner (deps restored from cache, unit tests + SAST) → on green, build uses OIDC to get temporary registry creds, builds a multi-arch image tagged abc123 (layers pulled from cache), Trivy scans it, cosign signs it keylessly → on green, deploy pauses for approval, then rewrites the image tag to abc123 in the manifests repo and commits. Argo CD sees that commit and rolls it out. Every artifact and log traces back to that one SHA.

Common mistakes & gotchas
  • Dropping a needs: lets a later stage race ahead of its gate — e.g., deploying before the scan finishes.
  • Tagging :latest instead of the SHA breaks traceability and makes rollback ambiguous.
  • Committing to the manifests repo without a loop guard can re-trigger CI endlessly (use a separate repo or skip-ci marker).
  • Signing but not enforcing (no admission controller) means the signature step adds no protection.
  • A missing MANIFEST_TOKEN scope — the deploy job can't push to the manifests repo, silently stalling GitOps.

37. CI/CD Best Practices — the master checklist

Everything the guide taught, distilled into one actionable checklist. If you follow these, you have a genuinely good pipeline.

Pipeline design
  • Pipeline-as-code — define it in a versioned file in the repo, never only in a UI.
  • Fail fast — run the quickest checks (lint, compile, unit tests) first.
  • Keep pipelines fast — parallelize jobs, cache dependencies; aim for CI under ~10 minutes.
  • Build once, promote the same artifact through every environment.
  • Make every run reproducible — pin versions, use lockfiles, avoid hidden state.
  • Idempotent & reliable — same inputs → same result; eliminate flaky steps.
Quality & testing
  • Run automated tests on every change, gated on pull requests.
  • Follow the test pyramid — many fast unit tests, few slow E2E tests.
  • Enforce quality gates (tests, coverage floor, linting, security) that block merges.
  • Protect the main branch — no direct pushes; require green checks + review.
  • Hunt down flaky tests relentlessly — they destroy trust.
Deployment & safety
  • Deploy small and often — smaller changes are safer and easier to debug.
  • Use a progressive strategy (rolling/canary/blue-green) — avoid downtime.
  • Make rollback one-click and tested; use backward-compatible DB migrations.
  • Run post-deploy smoke tests and monitor; auto-rollback on failure where possible.
  • Gate production behind approvals until your automation earns full trust.
Security & secrets
  • Shift security left — SAST, SCA, secret & container scanning in the pipeline.
  • Never hard-code secrets; prefer OIDC/short-lived tokens over stored keys.
  • Least-privilege pipeline credentials, scoped per environment.
  • Generate an SBOM and sign artifacts; verify before deploy.
Culture & measurement
  • Treat a broken pipeline as the top priority — a red main branch blocks everyone.
  • Notify fast on failures (chat integration).
  • Track DORA metrics and optimize for both speed and stability.
  • Continuously refine — the pipeline is a product that needs maintenance.

38. Troubleshooting Playbook

A systematic approach plus a lookup table for the most common CI/CD problems.

The universal debugging flow

  1. Read the pipeline logs top-to-bottom — find the first error, not the last (later errors are often consequences).
  2. Identify the failing stage/step — was it checkout, install, build, test, or deploy?
  3. Reproduce locally — run the exact failing command on your machine or in the same container image.
  4. Check what changed — code, dependencies, the pipeline file, the runner image, or an external service?
  5. Isolate — re-run with more logging/verbosity; add a debug step; disable caching to rule it out.

🔧 Common CI/CD problems

SymptomLikely cause & fix
"Works locally, fails in CI"Environment difference: missing dependency, different language/tool version, missing env var, or you rely on uncommitted local files. Pin versions; match the CI image; check .gitignored files aren't needed.
Pipeline doesn't triggerWrong file path/name, YAML syntax error, or the trigger config doesn't match the event/branch. Validate the YAML and trigger rules.
Flaky/intermittent failuresTiming/race conditions, test ordering, shared state, or an unreliable external service. Add retries only for genuinely transient ops; fix root causes for tests.
Dependency install failsRegistry down, version yanked, or lockfile out of sync. Use lockfiles + caching; pin a registry mirror if needed.
Build passes, deploy failsCredentials/permissions, wrong environment config, or the target changed. Check deploy logs and that the pipeline identity has the right access.
Secret is empty / auth deniedSecret not set at the right scope, fork PR restriction, or OIDC role/trust misconfigured.
Pipeline suddenly slowCache stopped hitting, runner contention, or added tests. Check cache keys and runner capacity; profile stage durations.
Timeout / hung jobWaiting on input, a process that never exits, or no available runner. Set timeouts; ensure commands are non-interactive.
Deploy succeeds but app is brokenConfig/secret mismatch per environment, or a bad migration. Add post-deploy smoke tests; verify env-specific config.
"Permission denied" running a scriptScript isn't executable. chmod +x and commit, or run via the interpreter (bash script.sh).
The single best debugging habit

Make your pipeline steps reproducible locally. If npm ci && npm test is what CI runs, you should be able to run the exact same thing in the same container image on your laptop. Pipelines that can only be tested by pushing commits are painful; ones you can reproduce locally are debugged in minutes.

Why "works locally, fails in CI" is the signature symptom

Almost every CI mystery reduces to one root cause: the CI environment differs from your laptop in some invisible way — a different tool version, a missing env var, a file you have locally but never committed, or a clean filesystem where you assumed leftover state. The debugging flow above works because it systematically closes that gap: reproduce in the same image, and the difference reveals itself.

How to reproduce CI locally (the fastest fix)

Run the exact failing command inside the exact image CI uses. Because CI checks out a clean tree and runs deterministic installs, doing the same locally surfaces the discrepancy immediately — a missing file (not committed), a version mismatch (unpinned dependency), or reliance on local state.

Worked example — reproduce a CI failure in the CI image
Run the failing job's commands in CI's own container
# Use the SAME image the CI job used (e.g., node:20), on a CLEAN checkout
git clone --depth 1 <repo> /tmp/repro && cd /tmp/repro
docker run --rm -it -v "$PWD":/app -w /app node:20 bash -lc '
  npm ci &&              # deterministic install, like CI
  npm test              # the step that failed
'
# If it now fails locally too → it was env drift or an uncommitted file.
# If it passes → suspect a CI-only secret/env var or a service dependency.
Common mistakes & gotchas
  • Reading the last error, not the first. Later errors are usually consequences — scroll up to the first failure.
  • Blaming flakiness prematurely. Re-running until green hides a real race condition; reproduce it instead.
  • Debugging on a dirty local tree. An uncommitted file makes it "work locally" — test on a fresh clone.
  • Ignoring the runner image version. ubuntu-latest changing under you can break a pipeline with no code change.
  • Adding blanket retries. Retry genuinely transient network ops, never flaky tests — fix the test.
Mental model

Debugging CI is reproducing a crime scene in identical conditions. "Works on my machine" is an alibi that only holds because your machine differs from the scene. Rebuild the exact environment (same image, clean checkout) and the culprit — a missing file, a wrong version — steps into the light.
