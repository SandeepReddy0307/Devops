A single, end-to-end reference to take you from "what is a container?" all the way to running production workloads on Amazon EKS — with plain-English explanations, real examples, both imperative and declarative commands, and troubleshooting for every concept.

📖 How to read this guide

This document is built so a complete beginner can start at the top and become genuinely skilled. Each concept follows the same rhythm:

  • What it is — a plain-English explanation, often with an analogy.
  • Why it exists — the problem it solves.
  • Imperative commands — quick kubectl commands you type directly (great for learning and debugging).
  • Declarative YAML — the "real" way to run production (files you version-control and apply).
  • Examples — copy-paste-ready.
  • Troubleshooting — common errors and how to fix them.
  • ☁ EKS focus — how the concept behaves specifically on Amazon EKS.
Imperative vs Declarative — read this first

Imperative = you tell Kubernetes exactly what to do, step by step ("create this pod now"). Fast for learning and debugging.

Declarative = you describe the desired end state in a YAML file and let Kubernetes figure out how to get there ("I want 3 replicas of this app"). This is how real teams operate because files can be reviewed, versioned in Git, and re-applied safely.

Golden rule: learn imperatively, operate declaratively.

1. What is Kubernetes?

Before any commands, understand what problem Kubernetes solves and why it exists.

Kubernetes in one idea

Say you have an app packaged in containers (see the Docker guide). Running one container on your laptop is easy. But in production you need many copies, spread across many servers, that automatically restart when they crash, scale up when busy, and get replaced when a server dies at 3 AM. Doing that by hand is impossible. Kubernetes is the automated manager that does all of it for you — you tell it "keep 5 copies of my app running," and it makes that true and keeps it true, no matter what breaks.

Kubernetes (often written "K8s" — K, then 8 letters, then s) is an open-source system for automatically deploying, scaling, and managing containerized applications. Google originally built it based on their internal system "Borg", and donated it to the Cloud Native Computing Foundation (CNCF) in 2014.

Analogy: Imagine you run a shipping company. Each application is a shipping container (standardized, self-contained). Kubernetes is the port authority + crane operator + logistics manager combined — it decides which ship (server) each container goes on, restarts containers that fall off, adds more containers when demand rises, and reroutes traffic if a ship sinks. You just declare "I need 100 of these containers running" and Kubernetes makes it happen and keeps it that way.

The core idea: desired state

The single most important concept in Kubernetes is the reconciliation loop. You tell Kubernetes your desired state ("I want 3 copies of my web app running"). Kubernetes constantly compares the actual state to the desired state and takes action to close any gap. If a copy crashes, actual state (2) < desired state (3), so it starts a new one automatically. You do not script "if crash then restart" — the platform does it for you.

Reconciliation loop = a self-adjusting thermostat

This is the big idea in Kubernetes, so make it stick. A thermostat doesn't need you to manage the heater — you set the target temperature (say 21°C), and it constantly checks the actual temperature and turns heating on/off to match. Kubernetes works identically: you declare "I want 3 copies running" (the target), and it constantly checks reality and fixes any gap — a Pod dies, it starts a new one; you ask for more, it adds them. You describe the goal, not the steps. That's why it "self-heals" without you writing any restart scripts.

What Kubernetes is NOT
  • It is not a PaaS like Heroku — it doesn't build your code or dictate a language. You bring container images.
  • It does not provide databases, message queues, or logging as built-ins (you run or connect them).
  • It is not a replacement for thinking about architecture — it's a powerful tool that rewards good design and punishes bad design at scale.
EKS focus

Amazon EKS (Elastic Kubernetes Service) is AWS's managed Kubernetes. AWS runs and scales the control plane (the "brain" — API server, etcd, scheduler) for you across multiple Availability Zones, patches it, and backs it with an SLA. You focus on your worker nodes and workloads. The Kubernetes API you interact with is the same standard Kubernetes — everything in this guide's core sections applies directly to EKS.

How the reconciliation loop actually works under the hood

The "loop" isn't a metaphor — it's real code. Every Kubernetes object type has one or more controllers running inside the kube-controller-manager. Each controller opens a long-lived watch against the API server for the objects it cares about. When anything changes (a Pod dies, a spec is edited, a node goes away), the API server streams that event to the controller, which places the affected object's key into a work queue. A worker goroutine then runs the reconcile function: it reads current state, compares it to the desired spec, and issues create/update/delete calls to close the gap. Crucially, reconciliation is level-triggered, not edge-triggered — the controller acts on the current observed state, not on the specific event, so it self-corrects even if it missed an event or restarted. This is why Kubernetes is so robust: a controller crashing and restarting simply re-lists everything and reconciles again from scratch.

Worked example — watch self-healing happen

Run these against any cluster to see desired-state enforcement with your own eyes:

See the loop react in real time
kubectl create deployment demo --image=nginx --replicas=3
kubectl get pods -l app=demo -w        # leave this watching in one terminal

# In a second terminal, delete one pod:
kubectl delete pod <one-demo-pod>
what the watch shows
demo-6f9c... 1/1  Running       0     40s
demo-6f9c... 1/1  Terminating   0     55s   <- you deleted it
demo-a12b... 0/1  Pending       0     0s    <- controller already made a replacement
demo-a12b... 0/1  ContainerCreating 0 1s
demo-a12b... 1/1  Running       0     3s    <- back to 3, no human involved

You never told it "if a pod dies, make a new one." You declared replicas: 3, and the ReplicaSet controller keeps that true forever.

Common beginner mistakes about "desired state"
  • Editing a live Pod expecting it to persist. If a controller owns the Pod, your manual edits get reverted on the next reconcile. Edit the controller (Deployment), not the Pod.
  • Deleting Pods to "fix" things. Deleting a Deployment-managed Pod just triggers a replacement — it won't reduce your replica count. To scale down, change replicas.
  • Thinking kubectl apply is a command that "runs once." It records desired state; controllers then converge toward it continuously.

2. Containers & Why We Need Kubernetes

Kubernetes orchestrates containers, so you must understand containers first.

From physical servers to containers

  • Physical servers: One app per box (or messy shared boxes). Wasteful, slow to provision.
  • Virtual Machines (VMs): Multiple isolated OSes on one physical machine. Better utilization, but each VM carries a full OS — heavy (GBs), slow to boot (minutes).
  • Containers: Package just your app + its dependencies, sharing the host's OS kernel. Lightweight (MBs), start in milliseconds, portable across any machine that runs a container runtime.

Analogy: A VM is like renting a whole house (own plumbing, own foundation). A container is like renting an apartment in a building — you get your own private space, but share the building's core infrastructure (the kernel). You fit far more apartments than houses on the same land.

What is a container image?

An image is an immutable, layered snapshot of a filesystem plus metadata (what command to run, which ports, env vars). A container is a running instance of an image. Images are stored in registries (Docker Hub, Amazon ECR, GitHub Container Registry).

Dockerfile — how an image is built
FROM node:20-alpine          # base layer
WORKDIR /app
COPY package*.json ./
RUN npm ci --production       # install deps (cached layer)
COPY . .                      # your code
EXPOSE 3000
CMD ["node", "server.js"]     # default command when container starts
Build, run, and push an image (Docker)
# Build an image and tag it
docker build -t myapp:1.0 .

# Run it locally
docker run -d -p 3000:3000 --name myapp myapp:1.0

# Push to a registry (example: Amazon ECR)
docker tag myapp:1.0 111122223333.dkr.ecr.us-east-1.amazonaws.com/myapp:1.0
docker push 111122223333.dkr.ecr.us-east-1.amazonaws.com/myapp:1.0

Why containers alone aren't enough — enter orchestration

Running one container is easy. But production needs: dozens/hundreds of containers, restart-on-crash, spreading them across many servers, rolling updates with zero downtime, networking between them, secrets, scaling under load, and recovery when a server dies at 3 AM. Doing this by hand is impossible. That coordination problem is exactly what Kubernetes solves.

Container runtimes

Kubernetes doesn't run containers itself — it delegates to a container runtime via the Container Runtime Interface (CRI). Modern clusters use containerd or CRI-O. (Docker as a runtime was deprecated in K8s 1.20 and removed in 1.24 — but images built with Docker still work fine; they follow the OCI standard.)

EKS focus

EKS worker nodes use containerd as the runtime. Store your images in Amazon ECR — it integrates with IAM for authentication, so nodes can pull images securely without embedding registry passwords. The EKS-optimized AMI comes preconfigured to pull from ECR.

What actually makes a container "isolated" — namespaces & cgroups

A container is not a lightweight VM; it is just a normal Linux process with two kernel features wrapped around it. Namespaces give it its own view of the world — a PID namespace so it sees only its own processes, a network namespace so it gets its own interfaces and IP, a mount namespace so it sees only its own filesystem, plus UTS, IPC, and user namespaces. cgroups (control groups) limit and account for what it can consume — CPU shares, memory ceilings, I/O. When Kubernetes sets a memory limit, it is writing to that container's cgroup; when the process exceeds it, the kernel's OOM killer terminates it (that's the OOMKilled status). Understanding this demystifies a lot: "why did my container see the node's total memory?" (because tools read /proc which isn't namespaced the way you'd expect), "why is my CPU throttled?" (cgroup CPU quota), and so on.

Worked example — layers are cached, order matters

Each Dockerfile instruction creates a layer. Layers are cached and reused if nothing above them changed. This is why you copy package.json and install dependencies before copying your source: your code changes constantly, but your dependencies rarely do, so the expensive npm ci layer stays cached.

rebuild after changing only source code
=> CACHED [2/6] WORKDIR /app
=> CACHED [3/6] COPY package*.json ./
=> CACHED [4/6] RUN npm ci --production   <- reused, saved 40s
=> [5/6] COPY . .                         <- only this and below re-run
=> [6/6] ...
=> exporting to image

Flip the order (copy all code first, then install) and every source change busts the dependency cache — builds crawl.

Image vs container, in one sentence

An image is like a class in programming (a blueprint on disk); a container is like an object (a running instance created from that blueprint). One image → many identical containers.

Container gotchas that bite beginners
  • latest is not a version. It's just a tag that moves. Two nodes pulling myapp:latest a day apart may run different code. Always pin explicit tags or, better, digests in production.
  • Writing to the container filesystem is temporary. It vanishes when the container is recreated. Persist data via volumes.
  • One process per container. Containers are designed around a single foreground process. Cramming a whole init system + multiple daemons in one container fights the model — use multiple containers in a Pod or sidecars instead.

3. Cluster Architecture

A Kubernetes cluster = a control plane (the brain) + worker nodes (the muscle). Understanding these components makes everything else click.

Like a thermostat

You set a thermostat to 21°C (desired state). It constantly reads the room temperature (actual state) and turns heating on/off to close the gap. Kubernetes controllers do exactly this for Pods, replicas, load balancers, and storage — forever.

Think of an airport

The control plane is the control tower — it doesn't fly planes, it makes all the decisions (which runway, which gate, scheduling). The worker nodes are the runways and ground crew that do the physical work of handling planes (your containers). You (a pilot) file a flight plan with the tower (submit YAML to the API server); the tower coordinates everything to make it happen and keep it running smoothly.

Analogy: Think of an airport. The control tower (control plane) makes all decisions — which runway, which gate, scheduling flights. The runways, gates, and ground crew (worker nodes) do the physical work of handling planes (your containers). Pilots submit flight plans (you submit YAML); the tower reconciles everything to keep the airport running.

Control Plane components (the brain)

ComponentRole
kube-apiserverThe front door. Every command, every component talks through the REST API server. It validates requests and is the only thing that reads/writes etcd. When you run kubectl, you're calling the API server.
etcdThe cluster's database — a distributed, consistent key-value store holding the entire cluster state (all objects). If etcd is lost and unbacked, the cluster's memory is gone. Guard it.
kube-schedulerDecides which node a new Pod runs on, based on resource requests, affinity rules, taints, and available capacity. It only decides placement; it doesn't start the Pod.
kube-controller-managerRuns the reconciliation loops (controllers): the Deployment controller, ReplicaSet controller, Node controller, etc. Each watches desired vs actual state and acts.
cloud-controller-managerIntegrates with the cloud provider (creating load balancers, attaching disks, managing routes). On EKS this is how a Service of type LoadBalancer becomes a real AWS load balancer.

Worker Node components (the muscle)

ComponentRole
kubeletThe node agent. Talks to the API server, receives Pod specs, and instructs the container runtime to start/stop containers. Reports node & pod health back.
kube-proxyMaintains network rules on each node so that Services work — routing traffic to the right Pods (via iptables/IPVS).
container runtimeActually runs containers (containerd/CRI-O).
Inspect your cluster's architecture
# See all nodes and their status
kubectl get nodes -o wide

# See control plane & system components (self-managed clusters)
kubectl get pods -n kube-system

# Check overall cluster health / endpoints
kubectl cluster-info
kubectl get componentstatuses   # (deprecated but illustrative)

# Describe a node — capacity, conditions, allocated resources
kubectl describe node <node-name>

The flow: what happens when you create a Deployment

  1. You run kubectl apply -f deploy.yaml. kubectl sends it to the API server.
  2. API server validates it and stores the object in etcd.
  3. The Deployment controller notices a new Deployment and creates a ReplicaSet.
  4. The ReplicaSet controller creates the required Pods (initially unscheduled).
  5. The scheduler picks the best node for each Pod and updates the Pod object.
  6. The kubelet on that node sees the assignment and tells the runtime to pull the image and start containers.
  7. kube-proxy wires up networking so the Pods are reachable.
EKS focus — the managed control plane

On EKS, AWS fully manages the control plane: the API server and etcd run in an AWS-owned account, spread across at least two Availability Zones, auto-scaled and patched by AWS. You never SSH into it or see those Pods in kube-system. You pay a flat hourly fee per cluster for it. What you manage: worker nodes (EC2/Fargate), add-ons, and workloads. The API server is reached via a managed endpoint (public and/or private). cloud-controller-manager functionality is provided by AWS-integrated controllers (e.g., the AWS Load Balancer Controller, EBS/EFS CSI drivers) that you install as add-ons.

Deeper: the API server is the only source of truth, and everything is a controller

A mental model that unlocks all of Kubernetes: every component is a client of the API server, and no component talks to any other component directly. The scheduler doesn't call the kubelet; it just writes spec.nodeName onto the Pod object. The kubelet doesn't ask the scheduler anything; it watches for Pods where nodeName equals its own node and acts. Controllers don't coordinate with each other; they each independently watch and write objects. etcd is the single database; the API server is the only process allowed to touch it, and it enforces validation, authentication, authorization, and admission on every write. This "hub and spoke through a shared datastore" design is why the system is so extensible — you add behavior simply by writing another controller that watches objects.

The whiteboard-and-workers mental model

Imagine a shared whiteboard (etcd, guarded by one receptionist = the API server). You write on it: "I want 3 web pods." Various specialists keep glancing at the whiteboard: the scheduler sees unassigned pods and writes which machine each should run on; each machine's foreman (kubelet) sees "pods assigned to me" and starts them; the ReplicaSet clerk keeps counting and re-writes if the number is wrong. Nobody phones anybody — they all just read and update the same whiteboard. Remove any specialist and the others keep working; bring it back and it catches up by re-reading the board.

Worked example — trace a Pod's journey through the components
create something, then follow the trail
kubectl create deployment trace --image=nginx
kubectl get events --sort-by=.lastTimestamp | tail -n 12
events reveal each component doing its job

Created pod: trace-7d...-abcde                (replicaset controller)
Successfully assigned default/trace-... to ip-10-0-1-42   (scheduler)
Pulling image "nginx"                        (kubelet)

Started container nginx                      (kubelet)

Read top to bottom: Deployment controller → ReplicaSet controller → scheduler → kubelet. The Events feed is a live narration of the architecture.

Operational gotchas around the control plane
  • etcd is the crown jewels. On self-managed clusters, if etcd is lost without a backup, the entire cluster state is gone. Back it up (etcdctl snapshot save). On EKS, AWS handles this for you.
  • A Pod stuck in Pending forever usually means the scheduler found no suitable node — not a kubelet problem. Read kubectl describe pod Events for the scheduler's reason.
  • A node showing NotReady usually means its kubelet stopped reporting (crashed, network partition, disk pressure) — a node-agent problem, distinct from Pod issues.

kubectl reads ~/.kube/config (the kubeconfig). It contains clusters (API server addresses + certs), users (credentials), and contexts (a named combination of cluster + user + namespace). You switch environments by switching context.

EKS focus — connecting to an EKS cluster

You don't hand-edit kubeconfig for EKS. The AWS CLI generates it for you and wires in IAM-based authentication:

aws eks update-kubeconfig --name my-cluster --region us-east-1
kubectl get nodes   # now works, authenticated via your IAM identity

Under the hood, kubectl calls aws eks get-token to obtain a short-lived token. Authorization (what you can do) is controlled by Kubernetes RBAC mapped to IAM principals via EKS access entries (modern) or the legacy aws-auth ConfigMap. You'll also want eksctl — a popular CLI for creating and managing EKS clusters declaratively.

What kubectl really does when you press Enter

kubectl is a thin HTTPS client. When you run kubectl get pods, it: (1) reads your kubeconfig to find the API server URL and your credentials; (2) issues an authenticated GET https://<apiserver>/api/v1/namespaces/<ns>/pods; (3) the server returns JSON; (4) kubectl formats it as the table you see. Every action is just a REST call — get=GET, apply=PATCH/PUT, delete=DELETE. Prove it to yourself with -v=8, which prints the raw HTTP:

see the actual API calls
kubectl get pods -v=8 2>&1 | grep -E 'GET|Response Status'
GET https://ABC123.gr7.us-east-1.eks.amazonaws.com/api/v1/namespaces/default/pods
Response Status: 200 OK

This is why anything kubectl can do, your CI pipeline or a script can do too — it's all one documented REST API.

The single most useful learning command: kubectl explain

You never need to memorize YAML fields. kubectl explain is the entire API schema, offline, live from your cluster's version:

kubectl explain pod.spec.containers.resources
kubectl explain deployment.spec.strategy.rollingUpdate
kubectl explain pod --recursive | less   # the whole tree

When you forget "is it livenessProbe or livenessCheck?", explain answers authoritatively for your exact cluster version.

Context & namespace mistakes cost people hours
  • Running a command against the wrong cluster. kubectl config current-context before anything destructive. Prod and dev contexts look similar in a hurry.
  • "My resource disappeared!" — you're probably in the wrong namespace. Objects are namespaced; kubectl get pods only shows the current namespace. Use -A to see all.
  • Version skew. A very old kubectl against a new cluster (or vice versa) can misbehave. Keep kubectl within one minor version of the cluster.

5. Pods — the atom of Kubernetes

A Pod is the smallest deployable unit in Kubernetes. You almost never run bare containers — you run Pods.

What's a Pod (and why not just "a container")?

A Pod is a thin wrapper around one container (occasionally a few that must live together). Kubernetes wraps containers in Pods so it has a consistent "unit" to schedule, network, and heal — Pods get an IP, can share storage, and always run together on one node. For a beginner: Pod ≈ "one running instance of your app." You'll rarely think about the wrapper; you'll think "I have 3 Pods of my web app running." Important: Pods are disposable — Kubernetes freely deletes and recreates them, which is why you never store important data inside one (use volumes) or rely on a Pod's address (use a Service).

A Pod wraps one or more containers that are tightly coupled: they share the same network namespace (same IP address and port space, so they reach each other over localhost) and can share storage volumes. Containers in a Pod are always scheduled together on the same node and live and die together.

Analogy: A Pod is like a pod of peas — usually one pea (container), but sometimes a few peas that must travel together in the same shell. They share the same house (node), the same phone line (network), and the same fridge (volumes).

Why "one or more"? The sidecar pattern

Most Pods have exactly one container. But sometimes a helper container assists the main one — this is the sidecar pattern. Examples: a logging agent shipping logs, a service-mesh proxy (Envoy), or a container that syncs files. They belong together, so they share a Pod.

Init containers

An initContainer runs to completion before the main containers start. Use it for setup tasks: waiting for a database, running migrations, or fetching config. If it fails, the Pod restarts it until it succeeds.

Create and inspect a Pod
# Quickest way to run a pod
kubectl run nginx --image=nginx:1.27

# Generate YAML without creating (great for learning!)
kubectl run nginx --image=nginx:1.27 --dry-run=client -o yaml

kubectl get pods
kubectl describe pod nginx        # events + full state
kubectl logs nginx
kubectl exec -it nginx -- bash
kubectl delete pod nginx
pod.yaml — declarative, with a sidecar & init container
apiVersion: v1
kind: Pod
metadata:
  name: web
  labels:
    app: web
spec:
  initContainers:
    - name: wait-for-db
      image: busybox:1.36
      command: ['sh', '-c', 'until nc -z db 5432; do sleep 2; done']
  containers:
    - name: app                       # main container
      image: myapp:1.0
      ports:
        - containerPort: 8080
    - name: log-shipper               # sidecar
      image: fluent/fluent-bit:3.0
  restartPolicy: Always               # Always | OnFailure | Never
Apply it
kubectl apply -f pod.yaml
kubectl get pod web -o wide

Pods are mortal & cattle, not pets

Pods are ephemeral. They get a new IP each time, and when a Pod dies it is not resurrected — a controller creates a brand-new Pod. Never store important data inside a Pod's container filesystem, and never rely on a Pod's IP. This is why we use higher-level controllers (Deployments) and Services.

EKS focus

On EKS with the default VPC CNI, each Pod gets a real VPC IP address from your subnet (not an overlay). This is powerful (Pods are first-class in your VPC) but means subnet IP exhaustion is a real concern at scale — size your subnets generously. A Pod stuck in Pending with "insufficient IPs" or failing to get an IP often points to CNI/subnet issues.

Under the hood: the pause container and shared namespaces

How do multiple containers in a Pod share one IP and reach each other over localhost? Kubernetes starts a tiny, almost-invisible "pause" container first. Its only job is to hold the network namespace (and IPC namespace) open. Your real containers then join that same namespace rather than creating their own. The pause container does nothing but sleep — but because it owns the namespace, containers can die and restart without the Pod losing its IP. That's the secret behind "containers in a Pod share networking." You can even see these pause containers on a node with crictl ps | grep pause.

Worked example — prove containers in a Pod share localhost & a volume
shared-pod.yaml
apiVersion: v1
kind: Pod
metadata: { name: shared }
spec:
  volumes:
    - name: data
      emptyDir: {}
  containers:
    - name: writer
      image: busybox:1.36
      command: ['sh','-c','echo hello > /shared/msg && sleep 3600']
      volumeMounts: [{ name: data, mountPath: /shared }]
    - name: reader
      image: busybox:1.36
      command: ['sh','-c','sleep 3600']
      volumeMounts: [{ name: data, mountPath: /shared }]
verify the shared volume
kubectl apply -f shared-pod.yaml
kubectl exec shared -c reader -- cat /shared/msg
hello

The writer wrote it; the reader — a different container — reads it, because they share the same emptyDir volume and the same node.

Init containers vs sidecars, simply

Init containers run before and finish — like doing prep work (waiting for the DB, running a migration) before the shop opens. Sidecars run alongside the main container for its whole life — like a shop assistant who's there the entire day (shipping logs, proxying traffic). Init = "do this first, then get out of the way." Sidecar = "stay and help the whole time."

Pod gotchas
  • Bare Pods don't self-heal across node failure. A Pod you create directly (not via a controller) is gone for good if its node dies. Always run workloads via a Deployment/StatefulSet/DaemonSet so a controller recreates them.
  • Two containers can't bind the same port inside one Pod — they share the network namespace, so port 8080 can only be used once.
  • restartPolicy: Always restarts containers, not the Pod. A crashing container is restarted in place (that's CrashLoopBackOff); the Pod object stays. Only a controller replaces the whole Pod.

6. ReplicaSets

A ReplicaSet ensures a specified number of identical Pod replicas are running at all times.

If you want 3 copies of a Pod, the ReplicaSet controller watches: if one dies, it creates a replacement; if there are too many, it deletes extras. It identifies "its" Pods using a label selector.

You rarely create ReplicaSets directly

In practice you use a Deployment (next section), which manages ReplicaSets for you and adds rolling updates and rollbacks. Understand ReplicaSets because Deployments create them under the hood — but author Deployments.

replicaset.yaml
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: web-rs
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web          # MUST match template labels below
  template:             # the Pod template — a Pod spec
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: nginx:1.27
Observe self-healing
kubectl apply -f replicaset.yaml
kubectl get rs
kubectl get pods -l app=web
kubectl delete pod <one-of-the-pods>   # watch a replacement appear instantly
kubectl scale rs web-rs --replicas=5   # scale up
How the selector actually claims Pods — and why it's dangerous

A ReplicaSet doesn't "own" Pods by a hidden link — it adopts any Pod matching its selector.matchLabels that lacks a controller owner. Each reconcile it lists Pods matching the selector, counts them, and creates or deletes to hit replicas. This label-based ownership is elegant but sharp: if two ReplicaSets share a selector, they fight over the same Pods; if you hand-label a random Pod to match, the ReplicaSet may delete it as a surplus. The link back is recorded in each Pod's metadata.ownerReferences — that's what garbage-collects Pods when you delete the ReplicaSet.

see the ownership chain
kubectl get pod <pod> -o jsonpath='{.metadata.ownerReferences[0].kind}/{.metadata.ownerReferences[0].name}{"\n"}'
ReplicaSet/web-rs
ReplicaSet = a headcount enforcer

Picture a shift manager whose only rule is "there must always be exactly 3 people at the counter." Someone leaves? Call in one more. Someone extra wanders in wearing the uniform (matching label)? Send one home. It doesn't care which people — only the count and the uniform (label). That single-minded counting is all a ReplicaSet does; everything smarter (versioned rollouts) lives in the Deployment above it.

Why you should not manage ReplicaSets by hand
  • No rollout/rollback. Changing a ReplicaSet's Pod template does not update existing Pods — it only affects Pods created afterward. Deployments solve this by creating a new ReplicaSet and shifting Pods over.
  • Immutable selector. You cannot change a ReplicaSet's selector after creation; you'd have to delete and recreate.
  • Orphaning. kubectl delete rs web-rs --cascade=orphan deletes the ReplicaSet but leaves its Pods running with no owner — occasionally useful, usually a footgun.

7. Deployments — how you actually run stateless apps

The Deployment is the workhorse of Kubernetes. It manages ReplicaSets to give you declarative updates, rolling deployments, and instant rollbacks.

Deployment = a fleet manager for your app

You don't babysit individual copies of your app. You tell the Deployment "keep 3 copies of version 2 running," and it handles the rest through a ReplicaSet (whose only job is "always keep exactly N alive"). If a copy crashes, a new one appears automatically. When you ship a new version, the Deployment swaps copies out a few at a time so users never see downtime — and if the new version misbehaves, it rolls back. It's like a fleet manager for taxis: you say "keep 3 cars on the road," they handle breakdowns and upgrades.

You describe the desired state (image, replicas, config). The Deployment creates a ReplicaSet. When you change the image, it creates a new ReplicaSet and gradually shifts Pods from old to new — a rolling update with zero downtime. If something breaks, you roll back to the previous ReplicaSet.

Analogy: A Deployment is like a fleet manager for taxis. You say "keep 10 taxis on the road." To upgrade the fleet, it brings in new cars a few at a time while retiring old ones — passengers never wait. If the new cars turn out faulty, it recalls them and brings back the old fleet.

Deployments the quick way
kubectl create deployment web --image=nginx:1.27 --replicas=3
kubectl scale deployment web --replicas=5
kubectl set image deployment/web nginx=nginx:1.28   # trigger rolling update
kubectl rollout status deployment/web               # watch progress
kubectl rollout history deployment/web              # revision history
kubectl rollout undo deployment/web                 # roll back to previous
kubectl rollout undo deployment/web --to-revision=2 # roll back to specific
deployment.yaml — the real-world way
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  labels: { app: web }
spec:
  replicas: 3
  selector:
    matchLabels: { app: web }
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1      # at most 1 pod down during update
      maxSurge: 1            # at most 1 extra pod created during update
  template:
    metadata:
      labels: { app: web }
    spec:
      containers:
        - name: web
          image: nginx:1.27
          ports:
            - containerPort: 80
          resources:
            requests: { cpu: "100m", memory: "128Mi" }
            limits:   { cpu: "500m", memory: "256Mi" }
          readinessProbe:
            httpGet: { path: /, port: 80 }
            initialDelaySeconds: 5
          livenessProbe:
            httpGet: { path: /, port: 80 }
            initialDelaySeconds: 10
Deploy & manage
kubectl apply -f deployment.yaml
kubectl get deploy,rs,pods -l app=web
# Edit and re-apply to update — Kubernetes computes the diff
kubectl apply -f deployment.yaml

Deployment strategies

StrategyBehavior
RollingUpdate (default)Gradually replace old Pods with new ones. Zero downtime. Controlled by maxSurge/maxUnavailable.
RecreateKill all old Pods, then create new ones. Causes downtime but ensures no two versions run at once (useful for incompatible DB schema changes).
Blue/Green (pattern)Run two full environments; switch traffic at the Service/Ingress. Not built-in — achieved with labels or tools like Argo Rollouts.
Canary (pattern)Send a small % of traffic to the new version first. Achieved with multiple Deployments, service mesh, or Argo Rollouts/Flagger.

🔧 Troubleshooting Deployments

Update didn't triggerYou changed something Kubernetes considers identical, or only changed a ConfigMap (Deployments don't auto-restart on ConfigMap changes). Use kubectl rollout restart deployment/web.

Force a restart without changing the image 
kubectl rollout restart deployment/web

This is the clean way to pick up new ConfigMap/Secret values or just cycle Pods.

Under the hood: how a rolling update really moves Pods

When you change the Pod template (e.g., a new image), the Deployment controller computes a hash of the template and creates a new ReplicaSet named with that hash (you'll see it in the Pod names, e.g. web-6f9c7d8b). It then plays a careful dance governed by maxSurge and maxUnavailable: scale the new ReplicaSet up by maxSurge, wait for those Pods to become Ready (this is where readiness probes are critical), scale the old ReplicaSet down, and repeat until the new one is at full size and the old one is at zero. The old ReplicaSet is kept (scaled to 0) so a rollback is instant — it just scales the old one back up. This is why "rollback" is nearly free and why revisionHistoryLimit controls how many old ReplicaSets linger.

Worked example — watch a rollout and roll it back 
kubectl create deployment web --image=nginx:1.25 --replicas=4
kubectl set image deployment/web nginx=nginx:1.27
kubectl rollout status deployment/web
kubectl get rs -l app=web
two ReplicaSets — old kept at 0 for instant rollback
NAME             DESIRED   CURRENT   READY   AGE
web-5c8f7d9b6b   0         0         0       3m    # old (nginx:1.25)
web-7f6c4b8d5d   4         4         4       40s   # new (nginx:1.27)
simulate a bad deploy and undo it
kubectl set image deployment/web nginx=nginx:doesnotexist
kubectl rollout status deployment/web   # hangs — new pods never become Ready
kubectl rollout undo deployment/web     # instantly scales the good RS back up
The #1 rolling-update trap: no readiness probe

Without a readiness probe, Kubernetes considers a Pod "Ready" the instant its container process starts — before your app has loaded config, warmed caches, or connected to its database. During a rollout it will happily send traffic to Pods that return errors, and scale down the old (healthy) Pods because the new ones "look" Ready. A rolling update is only zero-downtime if readiness probes actually reflect readiness to serve. Also beware: changing a referenced ConfigMap/Secret does not trigger a rollout — the Pod template hash is unchanged. Use kubectl rollout restart or a config-hash annotation to force it.

maxSurge and maxUnavailable in plain English

Imagine swapping the tires on a moving car with 4 wheels. maxUnavailable=1 means "never remove more than 1 wheel at a time" (never drop below 3 serving). maxSurge=1 means "you may temporarily bolt on a 5th wheel" to speed the swap. Together they let the car keep rolling (serving traffic) while every wheel gets replaced.

8. StatefulSets — for stateful apps

Deployments treat Pods as interchangeable. But databases, queues, and clustered apps need stable identity and stable storage. That's what a StatefulSet provides.

A StatefulSet gives each Pod:

  • A stable, ordered name: web-0, web-1, web-2 (not random suffixes).
  • Stable network identity: a predictable DNS name via a headless Service (e.g., web-0.mysvc).
  • Stable, dedicated storage: each Pod gets its own PersistentVolumeClaim that follows it across restarts/reschedules.
  • Ordered, graceful operations: Pods are created/scaled/updated one at a time in order (0, then 1, then 2).

Analogy: A Deployment's Pods are like identical rental bikes — grab any one. A StatefulSet's Pods are like assigned employee desks — desk 0 is always yours, with your stuff in the drawer (its own volume), and there's a defined order to onboarding.

statefulset.yaml (with per-Pod storage)
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: pg
spec:
  serviceName: pg          # headless Service for stable DNS
  replicas: 3
  selector:
    matchLabels: { app: pg }
  template:
    metadata:
      labels: { app: pg }
    spec:
      containers:
        - name: postgres
          image: postgres:16
          ports:
            - containerPort: 5432
          volumeMounts:
            - name: data
              mountPath: /var/lib/postgresql/data
  volumeClaimTemplates:    # each Pod gets its OWN PVC
    - metadata:
        name: data
      spec:
        accessModes: ["ReadWriteOnce"]
        storageClassName: gp3
        resources:
          requests:
            storage: 20Gi
StatefulSets are not magic

They give identity and storage plumbing, but they do not make an app clustered or replicated at the data layer. Your app (or an Operator) must handle data replication, leader election, and backups. For databases, prefer a purpose-built Operator or a managed service.

EKS focus

StatefulSet volumes on EKS typically use the EBS CSI driver (block storage, ReadWriteOnce — one node at a time). Note EBS volumes are AZ-bound: a Pod with an EBS volume can only reschedule to a node in the same AZ. For shared/multi-AZ access use EFS CSI (ReadWriteMany). For real databases, seriously consider Amazon RDS/Aurora instead of self-hosting on K8s.

Under the hood: stable identity, ordered rollout, and the headless Service

Three mechanisms make a StatefulSet "stateful." (1) Ordinal identity: Pods are named <set>-0..N-1 and created strictly in order — pg-1 is not started until pg-0 is Running and Ready. Scale-down happens in reverse (highest ordinal first). This lets clustered apps rely on "0 is the seed/primary." (2) Sticky storage: each ordinal gets a PVC from volumeClaimTemplates named data-pg-0, data-pg-1, etc. If pg-1 is rescheduled to another node, Kubernetes reattaches that same PVC — the data follows the identity, not the node. (3) Stable DNS via a headless Service (clusterIP: None): instead of one virtual IP, DNS returns per-Pod records like pg-0.pg.default.svc.cluster.local, so peers can address specific members. Rolling updates also proceed one ordinal at a time, highest-to-lowest.

Worked example — sticky names and PVCs survive deletion 
kubectl get pods -l app=pg
kubectl get pvc
notice PVC names are bound to ordinals
NAME   READY   STATUS    AGE
pg-0   1/1     Running   5m
pg-1   1/1     Running   4m
pg-2   1/1     Running   3m

NAME        STATUS   VOLUME       CAPACITY   STORAGECLASS
data-pg-0   Bound    pvc-a1..     20Gi       gp3
data-pg-1   Bound    pvc-b2..     20Gi       gp3
data-pg-2   Bound    pvc-c3..     20Gi       gp3
delete pg-1 — it returns with the SAME name and SAME data
kubectl delete pod pg-1
kubectl get pod pg-1 -w    # comes back as pg-1, reattached to data-pg-1
StatefulSet gotchas
  • Deleting the StatefulSet does not delete the PVCs (by default). This protects data — but orphaned PVCs (and their EBS volumes) keep costing money. Clean them up deliberately.
  • Scaling down leaves PVCs behind too, so scaling back up reuses the old data. Intentional, but surprising.
  • You must create the headless Service (serviceName) yourself — the StatefulSet does not create it. No headless Service = no stable per-Pod DNS.
  • Ordered startup can wedge a rollout: if pg-0 never becomes Ready, pg-1 and pg-2 never start. A bad probe on ordinal 0 stalls the whole set.

9. DaemonSets — one Pod per node

A DaemonSet ensures that a copy of a Pod runs on every node (or a selected subset). When a new node joins, it automatically gets the Pod; when a node leaves, its Pod is removed.

Perfect for node-level agents: log collectors (Fluent Bit), monitoring agents (node-exporter, CloudWatch agent), storage daemons, and network plugins.

daemonset.yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: log-agent
spec:
  selector:
    matchLabels: { app: log-agent }
  template:
    metadata:
      labels: { app: log-agent }
    spec:
      tolerations:                 # so it also runs on tainted/control nodes
        - operator: Exists
      containers:
        - name: fluent-bit
          image: fluent/fluent-bit:3.0
          volumeMounts:
            - name: varlog
              mountPath: /var/log
      volumes:
        - name: varlog
          hostPath: { path: /var/log }
Inspect
kubectl get ds -A
kubectl get pods -o wide -l app=log-agent   # note: one per node
EKS focus

Several EKS components run as DaemonSets: the VPC CNI (aws-node), kube-proxy, and optionally the CloudWatch/Fluent Bit logging agents. When you use Fargate, DaemonSets don't run (there are no nodes you manage), so logging/monitoring must be configured differently (e.g., Fargate log routing).

Why DaemonSets exist and how they bypass the scheduler

The problem: some software is infrastructure, not an application — it must run exactly once per node because it works with that node's kernel, disk, or network (a log tailer reading /var/log, a CNI plugin wiring up interfaces, a metrics agent reading /proc). A Deployment can't express "one per node." The DaemonSet controller watches the list of Nodes (not a replica count) and ensures each matching node has exactly one of its Pods. Historically it even bypassed the default scheduler; today it still effectively pins each Pod to a specific node by setting nodeAffinity/nodeName, but respects taints via tolerations. That's why DaemonSet Pods often carry broad tolerations — they need to land on control-plane and specially-tainted nodes that ordinary workloads avoid.

Worked example — one Pod per node, automatically 
kubectl get nodes
kubectl get pods -o wide -l app=log-agent
exactly one agent Pod per node, each on its own node
NODE            NAME               STATUS
ip-10-0-1-10    log-agent-4xk2p    Running
ip-10-0-2-20    log-agent-9dfz7    Running
ip-10-0-3-30    log-agent-pm8qt    Running

Add a node (or the cluster autoscaler adds one), and a fourth agent Pod appears on it within seconds — no config change needed.

DaemonSet gotchas
  • They ignore replicas. You never set a count — the count is the number of matching nodes. To run on a subset, use nodeSelector/affinity.
  • Missing tolerations = missing coverage. If nodes are tainted (e.g., a GPU pool or control-plane nodes) and your DaemonSet lacks matching tolerations, those nodes silently get no agent — a common monitoring blind spot.
  • Rolling updates one node at a time (via updateStrategy: RollingUpdate) — a big fleet updates slowly; tune maxUnavailable.
  • hostPath volumes couple you to the node; treat them as read-mostly and be mindful of security (a Pod reading host paths is powerful).

10. Jobs & CronJobs — batch and scheduled work

Deployments keep Pods running forever. But some work should run once and finish (a migration, a report) or run on a schedule (nightly backup). That's Jobs and CronJobs.

Job — run to completion

A Job creates one or more Pods and ensures a specified number of them successfully complete. If a Pod fails, the Job retries (up to backoffLimit).

job.yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: db-migrate
spec:
  completions: 1          # how many successful pods needed
  parallelism: 1          # how many run at once
  backoffLimit: 4         # retries before marking Failed
  ttlSecondsAfterFinished: 300   # auto-clean 5 min after finishing
  template:
    spec:
      restartPolicy: OnFailure
      containers:
        - name: migrate
          image: myapp:1.0
          command: ["python", "manage.py", "migrate"]
Run a one-off Job
kubectl create job db-migrate --image=myapp:1.0 -- python manage.py migrate
kubectl get jobs
kubectl logs job/db-migrate

CronJob — Jobs on a schedule

A CronJob creates Jobs on a time schedule using standard cron syntax.

cronjob.yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: nightly-backup
spec:
  schedule: "0 2 * * *"          # 02:00 every day (min hr dom mon dow)
  concurrencyPolicy: Forbid      # don't overlap runs
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 1
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: backup
              image: backup-tool:2.1
              args: ["--target", "s3://my-bucket/backups"]
Manage & test
kubectl get cronjobs
kubectl create job --from=cronjob/nightly-backup manual-run-1   # trigger now for testing
kubectl get jobs --watch

🔧 Troubleshooting Jobs/CronJobs

Job never completesContainer doesn't exit 0. Check logs; ensure the command actually terminates and returns success.
CronJob never firesCheck timezone (older K8s used controller's UTC; newer supports spec.timeZone). Verify schedule syntax and that suspend isn't true.
Too many leftover Pods/JobsSet ttlSecondsAfterFinished and history limits.
Under the hood: how the Job controller counts success, and how CronJob spawns Jobs

A Job is not "a Pod that runs once" — it's a controller tracking completions. It creates Pods and watches their terminal phase. A Pod that exits 0 counts toward completions; one that fails is retried until backoffLimit is hit (with exponential backoff: 10s, 20s, 40s…), after which the whole Job is marked Failed. With parallelism > 1 it runs several Pods at once until enough succeed. A CronJob is a controller on top of Jobs: every reconcile it checks the schedule against "now" and, when due, stamps out a brand-new Job object from jobTemplate. So the chain is CronJob → Job → Pod. concurrencyPolicy decides what happens if the previous Job is still running when the next fires: Allow (overlap), Forbid (skip), or Replace (kill the old one).

Worked example — a failing Job and its retries 
kubectl create job flaky --image=busybox -- sh -c 'exit 1'
kubectl get pods -l job-name=flaky -w
the controller retries with backoff, then gives up
flaky-abcde   0/1   Error       0   2s
flaky-fghij   0/1   Error       0   14s   # retry 1 (~10s later)
flaky-klmno   0/1   Error       0   36s   # retry 2 (~20s later)
...
kubectl get job flaky
NAME    COMPLETIONS   DURATION   AGE
flaky   0/1           2m         2m       # never completed → Failed after backoffLimit
Job/CronJob gotchas
  • restartPolicy: Always is invalid for Jobs — use OnFailure or Never. Always is only for long-running Pods.
  • Missed schedules. If the CronJob controller is down past startingDeadlineSeconds, a run is skipped entirely — not queued. Long outages silently drop backups.
  • Overlapping runs. Default concurrencyPolicy: Allow can pile up slow jobs. Use Forbid for backups/migrations that must not overlap.
  • Clutter. Without ttlSecondsAfterFinished and history limits, finished Pods accumulate and clog kubectl get pods.
  • Migrations that aren't idempotent are dangerous with retries — a retried migration Job may run twice.

11. Namespaces, Labels & Annotations

These are the organizing primitives that keep a cluster sane as it grows.

Namespaces = floors in one office building

A namespace divides a single cluster into separate areas — like floors in an office building. The Sales floor and Engineering floor can each have a "meeting room A" without clashing, they don't trip over each other, and you can control who badges into each floor and how much space they get. In Kubernetes you'll commonly have dev, staging, and prod namespaces (or one per team) — same building (cluster), tidy separate areas.

Namespaces — virtual clusters

A Namespace partitions a cluster into virtual sub-clusters. Use them to separate teams, environments (dev/staging), or applications. Names must be unique within a namespace, not across. Resource quotas and RBAC are often scoped per namespace.

Namespace commands
kubectl get namespaces
kubectl create namespace dev
kubectl get pods -n dev
kubectl get pods -A                    # all namespaces
kubectl config set-context --current --namespace=dev   # default ns
Built-in namespaces
  • default — where objects go if you don't specify one.
  • kube-system — control-plane & system components.
  • kube-public — readable by all, rarely used.
  • kube-node-lease — node heartbeat leases.

Note: not everything is namespaced. Nodes, PersistentVolumes, and Namespaces themselves are cluster-scoped. Check with kubectl api-resources --namespaced=false.

Labels — the glue of Kubernetes

Labels are key/value tags attached to objects (e.g., app=web, env=prod, tier=frontend). They are how Kubernetes objects find each other: a Service selects Pods by label; a Deployment manages Pods by label. Selectors query by label.

Working with labels
kubectl get pods --show-labels
kubectl get pods -l app=web,env=prod        # AND
kubectl get pods -l 'env in (dev,staging)'  # set-based
kubectl label pod web tier=frontend         # add a label
kubectl label pod web tier-                 # remove a label

Annotations — non-identifying metadata

Annotations also store key/value data, but are not used for selection. They hold metadata for tools and humans: build info, config for controllers (e.g., ingress/LB settings), change-cause, etc.

EKS focus

On EKS, annotations drive AWS integrations. For example, a Service uses annotations like service.beta.kubernetes.io/aws-load-balancer-type: "external" to control how the AWS Load Balancer Controller provisions an NLB/ALB. IRSA (IAM Roles for Service Accounts) uses the annotation eks.amazonaws.com/role-arn on a ServiceAccount. You'll see annotations everywhere in EKS configuration.

Deeper: labels are queryable indexes; annotations are opaque payloads

The distinction is not stylistic — it's architectural. Labels are indexed by the API server and drive selection: Services find Pods, ReplicaSets adopt Pods, and kubectl get -l filters, all via label selectors evaluated server-side. Keep them short and low-cardinality (app, tier, env, version). Annotations are not indexed and can't be selected on; they're a place to stash arbitrary data (up to ~256KB total) that tools and controllers read: the ingress controller reads annotations to configure the ALB, kubectl.kubernetes.io/last-applied-configuration stores the last-applied manifest for 3-way merges, and kubectl.kubernetes.io/change-cause feeds rollout history. Rule of thumb: if something needs to select it, it's a label; if it's just data for a tool, it's an annotation.

Worked example — quotas make a namespace a real boundary

Namespaces alone don't limit resources; add a ResourceQuota and LimitRange:

quota.yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-quota
  namespace: dev

Namespace & label gotchas
  • Namespaces are weak isolation. They separate names and scope RBAC/quotas, but by default Pods in different namespaces can still reach each other over the network — you need NetworkPolicies for real isolation.
  • Deleting a namespace deletes everything in it — Pods, Services, Secrets, PVCs. It's a big hammer; a namespace stuck Terminating usually has a finalizer waiting on a resource.
  • Selector/template label mismatch is the classic Deployment bug: spec.selector.matchLabels must be a subset of spec.template.metadata.labels, or the object is rejected.
  • Changing a selector on a live Service can silently orphan traffic — endpoints recompute against the new selector.

12. Services — stable networking for Pods

Pods are ephemeral and get new IPs constantly. A Service gives a stable address and load-balances traffic to a dynamic set of Pods selected by label.

Why do we need a Service? (the reception desk)

Pods are disposable — they're created and destroyed constantly, and each gets a new address every time. If clients tried to talk to a Pod directly, they'd constantly lose the connection. A Service is like a company's main reception phone number: it never changes, and it forwards your call to whichever employee (Pod) is available. Staff come and go, desks change — you always dial the one reception number and reach someone. That stable front door is what makes a shifting set of Pods usable.

A Service watches for Pods matching its selector and maintains the list of their IPs (the Endpoints). Clients talk to the Service's stable virtual IP (ClusterIP) or DNS name, and traffic is distributed to healthy Pods behind it. When Pods come and go, the Service transparently updates — clients never notice.

Analogy: A Service is like a company phone reception number. Employees (Pods) change desks and extensions constantly, but you always dial the one reception number; reception routes your call to an available person. You never need to know individual extensions.

Under the hood: ClusterIP is a virtual IP nothing actually listens on

The surprising truth: a ClusterIP address has no server behind it and answers no ping. It's a fiction maintained by kube-proxy on every node. When you create a Service, the endpoints controller watches Pods matching the selector and writes their IPs into an EndpointSlice. kube-proxy watches Services and EndpointSlices and programs kernel rules (iptables DNAT chains, or IPVS) so that any packet destined for the ClusterIP is transparently rewritten to a randomly chosen backend Pod IP. There's no proxy process in the data path — it's the Linux kernel doing the load balancing. This is why a Service "just works" from any Pod on any node, and why an empty EndpointSlice means "no rules programmed" → connection refused.

Service gotchas beyond the basics
  • Empty endpoints = failing readiness. A Pod is only added to the Service when it's Ready. If your readiness probe is missing or wrong, either dead Pods get traffic or healthy ones are excluded.
  • Session affinity is off by default. Each connection may hit a different Pod. Set sessionAffinity: ClientIP if you truly need stickiness (but prefer stateless apps).
  • ClusterIP is immutable. You can't change it after creation; delete and recreate.
  • NodePort range is 30000–32767 — asking for port 80 as a NodePort fails.
  • Source IP is often lost through NAT. Use externalTrafficPolicy: Local (with awareness of its load-balancing tradeoffs) to preserve client IP on NodePort/LoadBalancer.

13. Ingress — HTTP routing & TLS

Creating a LoadBalancer per service gets expensive and doesn't do smart HTTP routing. Ingress is a single entry point that routes HTTP/HTTPS traffic to many services based on host and path, and terminates TLS.

Ingress = the building's front desk & directory

Without Ingress, each service would need its own expensive public entrance (LoadBalancer). Ingress is one shared front door with a receptionist and directory: everyone enters through the same lobby, and the receptionist reads the request ("floor 3 for /api, the shop wing for /shop") and sends it to the right place. One entrance, smart routing, and it handles the HTTPS lock on the door too — far cheaper and tidier than a separate door per department.

An Ingress is just a set of routing rules. It does nothing on its own — you need an Ingress Controller (NGINX Ingress, AWS Load Balancer Controller, Traefik, etc.) running in the cluster that reads Ingress objects and configures a real load balancer/proxy.

Analogy: Ingress is the building directory + receptionist at a single front door. "Floor 3 for /api, Floor 5 for /shop, and shop.example.com goes to the retail wing." One door, smart routing, instead of a separate entrance per department.

ingress.yaml — host & path routing with TLS
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx
  tls:
    - hosts: [shop.example.com]
      secretName: shop-tls        # a Secret holding the cert
  rules:
    - host: shop.example.com
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: api-svc
                port: { number: 80 }
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web-svc
                port: { number: 80 }

EKS focus — Ingress = ALB

On EKS, the AWS Load Balancer Controller turns an Ingress into an Application Load Balancer (ALB). Use ingressClassName: alb and annotations such as:

alb.ingress.kubernetes.io/scheme: internet-facing
alb.ingress.kubernetes.io/target-type: ip
alb.ingress.kubernetes.io/certificate-arn: arn:aws:acm:...   # TLS via ACM
alb.ingress.kubernetes.io/group.name: shared                 # share one ALB across ingresses

Using group.name lets multiple Ingress resources share a single ALB — a big cost saver. TLS certs come from AWS Certificate Manager (ACM), not Kubernetes Secrets.

The future: Gateway API

The Gateway API is the modern successor to Ingress — more expressive, role-oriented (infra vs app teams), and supports more than HTTP. It uses GatewayClass, Gateway, and HTTPRoute resources. Learn Ingress first (still ubiquitous), but expect Gateway API adoption to grow. AWS supports it via the Gateway API controller / VPC Lattice.

Under the hood: the Ingress object is inert; the controller does the work

An Ingress resource is pure configuration — a declaration of intent stored in etcd. Nothing routes traffic until an Ingress Controller (a Pod running NGINX, or the AWS Load Balancer Controller, etc.) is watching. The controller watches all Ingress objects matching its ingressClassName, then translates them into real proxy config: for NGINX it rewrites nginx.conf and reloads; for AWS it makes API calls to create/modify an ALB, listeners, target groups, and rules. Traffic then flows: client → cloud LB / controller Pod → Service (ClusterIP) → Pod. Notice the Ingress still relies on Services underneath — it routes to a Service, which load-balances to Pods. That's why a healthy Ingress with a broken Service still fails.

Ingress gotchas that cost real time
  • No controller installed = Ingress does nothing. The object shows no ADDRESS and traffic never routes. Always confirm an ingress controller is running.
  • pathType matters. Prefix vs Exact vs ImplementationSpecific change matching. A missing/wrong pathType is a top cause of 404s.
  • Annotations are controller-specific. NGINX annotations (nginx.ingress.kubernetes.io/*) do nothing on an ALB controller and vice-versa. Copy-pasting between clusters silently breaks.
  • TLS Secret must be in the same namespace as the Ingress (for controllers that read K8s Secrets). On EKS/ALB, the cert comes from ACM instead.
  • Cross-namespace backends aren't allowed — an Ingress can only route to Services in its own namespace.

14. DNS & Service Discovery

Kubernetes runs an internal DNS server (CoreDNS) so Pods can find Services by name instead of IP.

Every Service gets a DNS record. The fully qualified name is:

<service>.<namespace>.svc.cluster.local

From within the same namespace, you can just use <service>. From another namespace, use <service>.<namespace>. This is how microservices talk: an app calls http://payments or http://payments.billing.svc.cluster.local.

EKS focus

CoreDNS runs as an EKS managed add-on — keep it updated via the add-on mechanism. At scale, CoreDNS can become a bottleneck; scale its replicas and consider NodeLocal DNSCache. For resolving AWS resources (RDS endpoints, etc.), Pods use the VPC's Route 53 resolver by default.

Under the hood: how a name becomes an IP, and the search-domain trick

When a Pod is created, the kubelet writes its /etc/resolv.conf pointing at the CoreDNS Service's ClusterIP as the nameserver, plus a set of search domains like default.svc.cluster.local svc.cluster.local cluster.local and ndots:5. This is why web resolves to web.default.svc.cluster.local: the resolver tries each search domain in turn. CoreDNS itself is a small DNS server whose kubernetes plugin watches Services and EndpointSlices from the API server and answers queries from that live data — a normal Service returns its ClusterIP (an A record), while a headless Service returns each Pod's IP. So DNS in Kubernetes is just another controller-driven view of the same object store.

Worked example — see the resolver config and resolve names 
kubectl run tmp --rm -it --image=busybox:1.36 -- sh

resolve short and fully-qualified names

The famous ndots:5 latency trap

Because ndots:5 means "any name with fewer than 5 dots gets the search domains appended first," a lookup of an external host like api.stripe.com (3 dots) first tries api.stripe.com.default.svc.cluster.local, api.stripe.com.svc.cluster.local, etc. — several failing queries before the real one. Under load this hammers CoreDNS and adds latency. Mitigations: use a fully-qualified name with a trailing dot (api.stripe.com.) to skip the search list, deploy NodeLocal DNSCache, or tune dnsConfig.options. Other classic issues: CoreDNS Pods crash-looping (whole cluster "can't resolve anything"), and forgetting the namespace on cross-namespace calls.

15. Network Policies — the Pod firewall

By default, every Pod can talk to every other Pod — the network is flat and open. NetworkPolicies let you restrict traffic, implementing zero-trust segmentation.

A NetworkPolicy selects Pods (by label) and defines allowed ingress (incoming) and egress (outgoing) traffic. The moment a Pod is selected by any policy, it switches from "allow all" to "deny all except what's explicitly allowed" for that direction.

Policies need a supporting CNI

NetworkPolicy objects are inert unless your CNI plugin enforces them. Calico, Cilium, and Weave do. The default EKS VPC CNI historically did NOT — see the EKS box below.

Default-deny all ingress, then allow specific traffic
# 1) Deny all incoming traffic to pods in this namespace
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
spec:
  podSelector: {}          # empty = all pods in namespace
  policyTypes: [Ingress]
---
# 2) Allow only the frontend to reach the API on port 8080
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend-to-api
spec:
  podSelector:
    matchLabels: { app: api }
  policyTypes: [Ingress]
  ingress:
    - from:
        - podSelector:
            matchLabels: { app: frontend }
      ports:
        - protocol: TCP
          port: 8080
EKS focus

Since 2023, the Amazon VPC CNI supports Kubernetes NetworkPolicies natively — enable it via the add-on config (enableNetworkPolicy: true). Alternatively, many teams run Cilium or Calico for richer policy features (L7 rules, DNS-based egress). NetworkPolicies control Pod-to-Pod traffic; Security Groups still guard node/ENI-level traffic, and Security Groups for Pods can attach SGs directly to Pods.

Under the hood: additive allow-lists, and the "selected = default deny" flip

NetworkPolicies are subtle because they are allow-only and additive — there is no "deny" rule. The logic: (1) A Pod not selected by any policy is fully open (legacy default). (2) The instant any policy selects a Pod for a direction (Ingress or Egress), that direction flips to default-deny, and only traffic matching some policy's allow rule is permitted. (3) Multiple policies are OR-ed together — traffic is allowed if it matches any of them. The CNI's agent (Calico Felix, Cilium agent, or the VPC CNI's node agent) watches policies and Pod IPs and compiles them into per-node enforcement (iptables/ipset or eBPF programs) applied at the Pod's network interface. This is why an empty podSelector: {} with policyTypes: [Ingress] and no ingress rules is the idiomatic "default-deny everything inbound."

Worked example — prove isolation before and after
before any policy — open network
kubectl run api --image=nginx --labels=app=api --port=80
kubectl expose pod api --port=80
kubectl run tester --rm -it --image=busybox:1.36 -- wget -qO- --timeout=3 http://api
# → returns the nginx welcome page (allowed)
apply default-deny + frontend-only allow, then retry
kubectl apply -f netpol.yaml
kubectl run tester --rm -it --image=busybox:1.36 -- wget -qO- --timeout=3 http://api
# → wget: download timed out  (tester has no app=frontend label → blocked)

kubectl run tester --rm -it --image=busybox:1.36 --labels=app=frontend -- wget -qO- --timeout=3 http://api
# → nginx page again (now matches the allow rule)
NetworkPolicy gotchas
  • No enforcing CNI = silent no-op. The object applies cleanly but does nothing. Always confirm your CNI enforces policies before relying on them for security.
  • Forgetting egress DNS. A default-deny egress policy blocks DNS (UDP/53 to CoreDNS) too — suddenly nothing resolves names. Explicitly allow egress to kube-dns.
  • namespaceSelector vs podSelector. To allow from another namespace you need namespaceSelector (and often both combined). A lone podSelector only matches Pods in the policy's own namespace.
  • Policies are namespaced — they don't protect Pods in other namespaces. Segment each namespace.

16. CNI — the Container Network Interface

The CNI is the plugin standard that gives Pods their network connectivity. Kubernetes delegates all Pod networking to a CNI plugin.

The Kubernetes networking model has three hard rules:

  • Every Pod gets its own unique IP address.
  • Pods can communicate with all other Pods without NAT.
  • Agents on a node (kubelet) can reach all Pods on that node.

The CNI plugin implements this. Approaches differ:

CNIApproach
Overlay (Flannel, Calico VXLAN)Pods get IPs from a virtual network layered on top of the real network (encapsulation). Simple, works anywhere.
Native / routed (Calico BGP)Pod IPs are routed directly by the underlying network — faster, no encapsulation overhead.
Cloud-native (AWS VPC CNI)Pods get real IPs from the cloud VPC — first-class network citizens.
eBPF-based (Cilium)Uses eBPF in the kernel for high-performance networking, security, and observability.
EKS focus — the VPC CNI in depth

EKS's default Amazon VPC CNI (aws-node DaemonSet) assigns each Pod a real IP from your VPC subnets by attaching secondary IPs to the node's Elastic Network Interfaces (ENIs). Implications:

  • Pod density is limited by instance type — max Pods depends on how many ENIs/IPs the EC2 type supports (e.g., a t3.medium supports far fewer Pods than an m5.4xlarge). Check the max-pods formula/AMI defaults.
  • Prefix delegation (assigning /28 prefixes instead of single IPs) dramatically increases Pod density and reduces IP churn — enable it for large clusters.
  • Subnet IP exhaustion is the most common scaling pain — plan CIDR sizing, or use a secondary CIDR / custom networking for Pods.
  • Alternatives like Cilium can run on EKS for eBPF features or to decouple Pod IPs from the VPC.
Under the hood: how the kubelet calls the CNI when a Pod starts

CNI is a beautifully simple contract. When the kubelet needs to start a Pod, it (via the container runtime) creates the Pod's network namespace, then invokes the CNI plugin binary on the node (found in /opt/cni/bin, configured by files in /etc/cni/net.d) with a verb (ADD) and the namespace path. The plugin's job: allocate an IP, create a virtual interface (veth pair) into the Pod's namespace, wire up routes, and print JSON describing the result. On Pod deletion, the kubelet calls the plugin with DEL to release the IP and tear down the interface. That's the whole interface — which is why so many plugins exist. On EKS, the VPC CNI's ADD hands the Pod a secondary IP from an ENI it manages; an overlay CNI's ADD instead assigns an IP from a virtual subnet and sets up encapsulation.

Worked example — see which CNI you're running and the max-pods limit 
kubectl get pods -n kube-system -o wide | grep -Ei 'aws-node|calico|cilium|flannel'
kubectl get node <node> -o jsonpath='{.status.allocatable.pods}{"\n"}'
on EKS, the aws-node DaemonSet is the VPC CNI; max pods is instance-bound
kube-system   aws-node-abcde   2/2   Running   0   3h   10.0.1.42   ip-10-0-1-42
kube-system   kube-proxy-fghij 1/1   Running   0   3h   10.0.1.42   ip-10-0-1-42
29        # allocatable pods on this instance type (before prefix delegation)
CNI, simply

Kubernetes doesn't know how to give a Pod a network — it just says "hey plugin, please connect this Pod." The CNI plugin is that hired electrician: it runs the wiring (IP + virtual cable) so the Pod can talk to everything else, then unwires it when the Pod leaves. Different electricians (Calico, Cilium, VPC CNI) do the wiring differently, but they all satisfy the same three rules: every Pod gets its own IP, and all Pods can reach each other without address translation.

CNI gotchas
  • Pods stuck ContainerCreating with "failed to set up sandbox" usually means the CNI plugin is broken/misconfigured — not your app.
  • IP exhaustion on the VPC CNI shows as Pods pending for an IP; enable prefix delegation or size subnets bigger.
  • You can't casually swap CNIs on a live cluster — it's a disruptive, cluster-wide change.
  • Not every CNI enforces NetworkPolicy (see previous section) — feature sets differ widely.

17. ConfigMaps — externalize configuration

Never bake environment-specific config into your container image. ConfigMaps store non-sensitive configuration separately, so the same image runs in dev, staging, and prod with different settings.

ConfigMaps & Secrets = settings you slot in from outside

You want one app image that behaves differently in each environment (test database vs real database, debug logging vs quiet). Instead of building a separate image per environment, you keep the settings outside the image and hand them in when it runs. A ConfigMap holds ordinary settings; a Secret holds sensitive ones (passwords, keys) and is handled more carefully. It's like a game console (the image) that plays different game cartridges (config) — same machine, different behaviour, no rebuild needed.

A ConfigMap is a key/value store for config data: environment variables, config files, command-line args. You inject them into Pods as env vars or mounted files.

Create ConfigMaps various ways
# From literal values
kubectl create configmap app-config \
  --from-literal=LOG_LEVEL=info \
  --from-literal=MAX_CONN=100

# From a file (whole file becomes one key)
kubectl create configmap nginx-conf --from-file=./nginx.conf

# From an env file
kubectl create configmap app-env --from-env-file=./app.env

kubectl get configmap app-config -o yaml
configmap.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  LOG_LEVEL: "info"
  MAX_CONN: "100"
  app.properties: |
    server.port=8080
    feature.flag=true
Consuming a ConfigMap in a Pod (env vars & mounted file)
spec:
  containers:
    - name: app
      image: myapp:1.0
      envFrom:
        - configMapRef:
            name: app-config          # inject ALL keys as env vars
      env:
        - name: LOG_LEVEL             # or inject one specific key
          valueFrom:
            configMapKeyRef:
              name: app-config
              key: LOG_LEVEL
      volumeMounts:
        - name: config-vol
          mountPath: /etc/config      # each key becomes a file here
  volumes:
    - name: config-vol
      configMap:
        name: app-config
ConfigMap changes don't auto-restart Pods

Env-var-injected values are fixed at Pod start — changing the ConfigMap won't update running Pods. Mounted-file values do update (eventually), but most apps don't re-read files. Trigger a rollout to pick up changes: kubectl rollout restart deployment/web. (Tools like Reloader can automate this.)

Under the hood: two very different injection paths

ConfigMap consumption splits into two mechanisms with different behavior. As env vars (envFrom/configMapKeyRef): the kubelet reads the ConfigMap once when it starts the container and bakes the values into the process environment. A process's environment can't be changed from outside, so these are frozen for the container's life — full stop. As a mounted volume: the kubelet mounts a special tmpfs and projects each key as a file via a symlink to a hidden versioned directory. When the ConfigMap changes, the kubelet's sync loop (roughly once a minute) atomically swaps the symlink, so the files update in place — but only if your app watches/re-reads them. Neither path restarts your process; that's why config changes so often "don't take effect."

Worked example — inject and verify both ways 
kubectl create configmap app-config --from-literal=LOG_LEVEL=debug
kubectl run demo --image=busybox:1.36 --restart=Never \
  --overrides='{"spec":{"containers":[{"name":"demo","image":"busybox:1.36","command":["env"],"envFrom":[{"configMapRef":{"name":"app-config"}}]}]}}'
kubectl logs demo | grep LOG_LEVEL
LOG_LEVEL=debug
change the value — a running pod does NOT pick it up as an env var
kubectl create configmap app-config --from-literal=LOG_LEVEL=info \
  --dry-run=client -o yaml | kubectl apply -f -
# existing pods still show debug until restarted; rollout restart to refresh
ConfigMap gotchas
  • Everything is a string. MAX_CONN: 100 without quotes can trip YAML type parsing; quote values and let the app parse. Booleans like true can become the string "true" — expected, but surprising.
  • 1 MiB size limit. ConfigMaps (and Secrets) max out at ~1 MiB because they live in etcd. Don't stuff large files/binaries in them.
  • Missing referenced key ⇒ Pod stuck in CreateContainerConfigError. Create the ConfigMap first, or mark the reference optional: true.
  • Subpath mounts don't auto-update. Using subPath to mount a single file breaks the live-update behavior — the file is copied, not symlinked.

18. Secrets — sensitive data

Secrets are like ConfigMaps but for sensitive data: passwords, tokens, TLS certs, API keys. They're handled with extra care by the system.

Important: base64 is NOT encryption

Secret values are stored base64-encoded, which is just encoding — anyone with read access can decode them. By default they're stored unencrypted in etcd. Real security requires: (1) encryption at rest for etcd, (2) tight RBAC on Secrets, and (3) ideally an external secrets manager.

Create Secrets
kubectl create secret generic db-cred \
  --from-literal=username=admin \

EKS focus — do Secrets properly
  • Enable envelope encryption for etcd Secrets using AWS KMS (EKS supports KMS-backed encryption of Secrets).
  • Use the External Secrets Operator or the Secrets Store CSI Driver (AWS provider) to sync secrets from AWS Secrets Manager or SSM Parameter Store into Pods — so secrets live in a managed store, not in Git.
  • Combine with IRSA/Pod Identity so Pods fetch secrets using IAM, no long-lived credentials.
  • Lock down get/list on Secrets with RBAC.
Under the hood: why base64, and how Secrets differ from ConfigMaps at runtime

Secrets are base64-encoded for a mundane reason: the value field must be valid in JSON/YAML even for binary data (certs, keystores), and base64 guarantees that. It is encoding, not encryption — echo <value> | base64 -d reveals it instantly. At runtime, Secrets get a few safety touches ConfigMaps don't: when mounted as volumes they're backed by tmpfs (in-memory, never written to the node's disk), the kubelet only distributes a Secret to nodes that actually run a Pod needing it, and the API server can encrypt them at rest via an EncryptionConfiguration (envelope encryption with a KMS provider). But anyone with RBAC to get the Secret, or to exec into a Pod using it, can read the plaintext — so RBAC is the real security boundary.

Worked example — decode is trivial (which is the whole point) 
kubectl create secret generic db-cred --from-literal=password='S3cr3t!'
kubectl get secret db-cred -o jsonpath='{.data.password}' | base64 -d; echo
S3cr3t!

No password required beyond read access to the Secret — which is exactly why you (1) restrict that access with RBAC, (2) enable etcd encryption, and (3) prefer an external secrets store for anything truly sensitive.

Secret mistakes that cause real breaches
  • Committing Secret YAML to Git. base64 is not protection — a public repo leaks the plaintext. Use SealedSecrets, SOPS, or an external store; never commit raw Secrets.
  • Over-broad RBAC. A ServiceAccount with secrets: list at cluster scope can read every credential in the cluster. Scope tightly.
  • Logging env vars. Apps that dump their environment on startup print your secrets to logs (and then to your log aggregator).
  • Forgetting etcd encryption at rest — without it, a node/etcd backup leak exposes all Secrets in plaintext.

19. Volumes — storage inside Pods

A container's filesystem is ephemeral — wiped when the container restarts. Volumes provide storage that outlives a container (and can be shared between containers in a Pod).

Common volume types

TypeLifetime / use
emptyDirEmpty scratch space created with the Pod, deleted when the Pod dies. Great for temp files or sharing between a container and its sidecar.
hostPathMounts a file/dir from the node's filesystem. Powerful but risky (ties Pod to a node, security concerns). Used by node agents.
configMap / secretMount config/secret data as files.
persistentVolumeClaimThe real-world way to get durable storage — see next section.
projectedCombine several sources (secrets, configmaps, tokens) into one directory.
emptyDir shared between two containers
spec:
  containers:
    - name: writer
      image: busybox:1.36
      command: ['sh','-c','while true; do date >> /data/log; sleep 5; done']
      volumeMounts: [{ name: shared, mountPath: /data }]
    - name: reader
      image: busybox:1.36
      command: ['sh','-c','tail -f /data/log']
      volumeMounts: [{ name: shared, mountPath: /data }]
  volumes:
    - name: shared
      emptyDir: {}
Under the hood: a volume is a shared mount, and lifetime is the whole story

The key mental shift: a container's writable layer is thrown away on restart, but a Pod's volume can outlive individual container restarts. When the kubelet starts a Pod, it prepares each volume (allocates scratch space for emptyDir, attaches/mounts a disk for a PVC, projects files for configMap/secret) and then bind-mounts it into each container at the requested mountPath. Because the mount lives at the Pod level, two containers mounting the same volume see the same files (how sidecars share data), and a container that crashes and restarts finds its emptyDir data intact — it's only wiped when the whole Pod is removed. emptyDir is backed by the node's disk by default, or by RAM with medium: Memory (fast, but counts against the Pod's memory).

The three lifetimes, simply

Think of three kinds of storage by how long they last: the container's own filesystem is a whiteboard wiped every restart; an emptyDir is a notepad that lasts as long as the Pod lives (survives container restarts, dies with the Pod); a PVC-backed volume is a filing cabinet in the building that stays even after the Pod (and its data) is gone. Match the tool to how long you need the data to survive.

Volume gotchas
  • emptyDir is NOT durable. It's gone the moment the Pod is deleted or rescheduled to another node. Never use it for data you can't lose — use a PVC.
  • hostPath ties a Pod to a node and is a security risk — a Pod mounting / or the container socket can effectively own the node. Avoid it for apps; it's for node agents only.
  • Memory-backed emptyDir counts against the Pod's memory limit — filling it can trigger OOMKilled.
  • Mount path collisions: mounting a volume over a directory that had image content hides the original files.

20. PersistentVolumes, PVCs & StorageClasses

This is how Kubernetes provides durable storage that survives Pod deletion — decoupling what storage an app needs from how that storage is provided.

PV / PVC / StorageClass = booking a hotel room

These three names confuse everyone. Use a hotel: a PVC is your booking request ("I'd like a room, 2 nights, king bed"). A StorageClass is the room category ("Deluxe" vs "Suite" — i.e., which kind of disk). The PV is the actual room you're given. Dynamic provisioning means the hotel builds your room on demand the moment you book, instead of relying on pre-built rooms. The point of all this: your app just says "I need 20Gi" and doesn't care what disk it lands on — and the data survives even when the Pod is destroyed.

Under the hood: the binding dance and why WaitForFirstConsumer exists

Provisioning is a multi-controller relay. You create a PVC referencing a StorageClass. The PV controller sees an unbound PVC and, because the StorageClass names an external CSI provisioner, asks that provisioner (running as a Pod, e.g. the EBS CSI controller) to create real storage — it calls the cloud API (CreateVolume), creates a matching PV object, and binds the PVC to it. Later, when a Pod using the PVC is scheduled to a node, the CSI node plugin on that node runs attach then mount to make the disk available inside the container. The subtlety: EBS volumes are AZ-locked, so if the volume were created before the Pod is scheduled, the Pod might get placed in a different AZ and never be able to attach it. volumeBindingMode: WaitForFirstConsumer fixes this by delaying volume creation until the scheduler picks the node — then the volume is created in the right AZ.

Delete vs Retain, in one line

reclaimPolicy: Delete = "when I return the room key (delete the PVC), demolish the room and everything in it (delete the disk + data)." Retain = "keep the room and its contents locked for later" — safer for anything you'd cry about losing.

Storage gotchas that lose data or money
  • reclaimPolicy: Delete means deleting the PVC destroys the EBS volume and its data — irreversibly. Use Retain for anything important.
  • Orphaned PVs cost money. With Retain, or leftover StatefulSet PVCs, the underlying EBS volumes keep billing after you think you've cleaned up.
  • RWO ≠ shared. You cannot mount one EBS volume on two nodes — that's the "Multi-Attach error." For shared read-write use EFS (RWX).
  • Resizing is one-way. Most drivers allow growing a volume but never shrinking it.
  • Missing CSI driver/IRSA ⇒ PVCs hang Pending forever with no obvious error except in the provisioner's logs.

21. Resource Requests, Limits & QoS

Telling Kubernetes how much CPU and memory each container needs is one of the highest-impact things you can do for stability and cost.

  • requests = the amount guaranteed to the container. The scheduler uses requests to decide which node has room. This is what you're "reserving".
  • limits = the maximum the container may use. Exceeding a CPU limit gets it throttled; exceeding a memory limit gets it OOMKilled.

Units: CPU is measured in cores; 500m = 0.5 core ("millicores"). Memory is bytes; use Mi (mebibytes) / Gi (gibibytes).

Setting requests & limits
resources:
  requests:
    cpu: "250m"
    memory: "256Mi"
  limits:
    cpu: "1"
    memory: "512Mi"

Quality of Service (QoS) classes

Kubernetes assigns each Pod a QoS class that determines eviction priority under node pressure:

QoS classConditionBehavior
Guaranteedrequests == limits for all containers (both CPU & mem set).Highest priority, evicted last. Use for critical workloads.
BurstableAt least one request set, but not equal to limits.Medium priority.
BestEffortNo requests or limits set.First to be evicted under pressure. Avoid in prod.
Practical guidance
  • Always set memory requests = limits (memory is incompressible — better to guarantee it).
  • Set a CPU request but often omit CPU limits to avoid needless throttling (debated, but common at scale).
  • Use LimitRange to enforce defaults per namespace and ResourceQuota to cap total namespace usage.
Namespace guardrails
apiVersion: v1
kind: ResourceQuota
metadata: { name: team-quota, namespace: dev }
spec:
  hard:
    requests.cpu: "10"
    requests.memory: 20Gi
    limits.cpu: "20"
    pods: "50"
---
apiVersion: v1
kind: LimitRange
metadata: { name: defaults, namespace: dev }
spec:
  limits:
    - default: { cpu: 500m, memory: 256Mi }
      defaultRequest: { cpu: 100m, memory: 128Mi }
      type: Container
EKS focus

Right-sizing requests directly controls cost on EKS: over-requesting wastes EC2 capacity; under-requesting causes contention and OOMKills. Use metrics-server + tools like Goldilocks/VPA-in-recommend-mode to right-size. Requests also drive Karpenter/Cluster Autoscaler node provisioning decisions — accurate requests = efficient scaling.

Under the hood: requests are scheduling math; limits are kernel cgroups

Requests and limits do completely different jobs. Requests are used only by the scheduler: it sums the requests of all Pods already on a node and only places a new Pod where sum(requests) + newRequest ≤ allocatable. Requests reserve nothing at the kernel level — a Pod can use more than it requested if the node has spare capacity. Limits are enforced by the kernel via cgroups on the node. CPU is compressible: exceeding the CPU limit doesn't kill anything, the kernel just throttles the process (CFS quota) so it runs slower. Memory is incompressible: there's no way to "run with less RAM," so exceeding the memory limit triggers the kernel OOM killer, which terminates the container — the OOMKilled status. This asymmetry is exactly why the practical advice is "set memory request = limit, but be cautious with CPU limits."

Worked example — see QoS class and catch an OOMKill 
kubectl run stress --image=polinux/stress --restart=Never \
  --limits='memory=64Mi' --requests='memory=64Mi' \
  -- stress --vm 1 --vm-bytes 150M --vm-hang 0
kubectl get pod stress -o jsonpath='{.status.qosClass}{"\n"}'
kubectl get pod stress
requests==limits → Guaranteed; but it exceeds memory → killed

confirm the reason
kubectl describe pod stress | grep -A2 'Last State'

  Reason:    OOMKilled
  Exit Code: 137
Requests vs limits, plainly

Request = the seat you reserve on a train — you're guaranteed that much room and the scheduler won't overbook the car. Limit = the maximum space you're allowed to spread into. Spread past your CPU limit and the conductor makes you slow down (throttle); spread past your memory limit and you get thrown off the train (OOMKilled). QoS is who gets kicked off first when the train is overcrowded: BestEffort passengers (no reservation) go first, Guaranteed (exact reservation) go last.

Resource gotchas
  • No requests = BestEffort = first evicted. Unset resources feel convenient in dev and cause outages in prod under node pressure.
  • CPU limits cause surprise latency. A too-low CPU limit throttles bursty apps (GC pauses, cold starts) even when the node is idle. Many teams set CPU requests only.
  • Memory limit too low ⇒ constant OOMKills that look like app bugs. Check kubectl describe for exit code 137.
  • Requests, not usage, drive scheduling and autoscaling. A Pod requesting 2 CPU but using 0.1 still "fills" 2 CPU of node capacity — over-requesting silently wastes money.

22. Scheduling: nodeSelector, Affinity & Topology Spread

By default the scheduler places Pods wherever they fit. These tools let you influence placement for performance, availability, and cost.

nodeSelector — the simplest

Run only on nodes with a matching label
spec:
  nodeSelector:
    disktype: ssd
    # e.g. on EKS: eks.amazonaws.com/nodegroup: gpu-nodes

Node Affinity — richer rules

More expressive than nodeSelector, with "hard" (required) and "soft" (preferred) rules.

Node affinity
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:   # hard rule
        nodeSelectorTerms:
          - matchExpressions:
              - key: topology.kubernetes.io/zone
                operator: In
                values: ["us-east-1a", "us-east-1b"]
      preferredDuringSchedulingIgnoredDuringExecution:  # soft preference
        - weight: 80
          preference:
            matchExpressions:
              - key: node.kubernetes.io/instance-type
                operator: In
                values: ["m5.large"]

Pod Affinity / Anti-Affinity

Place Pods near (affinity) or away from (anti-affinity) other Pods. Anti-affinity is key for HA — spread replicas across nodes/zones so one failure doesn't take them all.

Spread replicas across nodes (anti-affinity)
spec:
  affinity:
    podAntiAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        - labelSelector:
            matchLabels: { app: web }
          topologyKey: kubernetes.io/hostname   # one per node

Topology Spread Constraints — the modern way to spread

Evenly spread across AZs
spec:
  topologySpreadConstraints:
    - maxSkew: 1
      topologyKey: topology.kubernetes.io/zone
      whenUnsatisfiable: DoNotSchedule
      labelSelector:
        matchLabels: { app: web }
EKS focus

Use topology spread across topology.kubernetes.io/zone so replicas survive an AZ outage. Common node labels on EKS: eks.amazonaws.com/nodegroup, node.kubernetes.io/instance-type, karpenter.sh/capacity-type (on/spot). Use affinity/nodeSelector to pin GPU or Spot workloads to the right nodes.

Under the hood: the scheduler's two-phase Filter → Score algorithm

The scheduler runs a loop for each unscheduled Pod (any Pod with empty spec.nodeName). It works in two phases. Filter (predicates): eliminate every node that can't run the Pod — not enough allocatable CPU/memory for the Pod's requests, taints the Pod doesn't tolerate, unsatisfied required node/pod affinity, no matching volume topology (the EBS-AZ case), ports in use. If zero nodes survive, the Pod stays Pending with an event like 0/5 nodes are available: 3 Insufficient cpu, 2 node(s) had untolerated taint. Score (priorities): rank the surviving nodes — spreading Pods of the same Service, honoring preferred affinities, balancing resource utilization, topology spread. The highest-scoring node wins; the scheduler binds the Pod by writing nodeName. Note it schedules on requests, not live usage, and it never moves already-running Pods — placement decisions are made once, at schedule time.

Worked example — read the scheduler's decision 
kubectl create deployment web --image=nginx --replicas=6
kubectl get pods -l app=web -o wide --sort-by=.spec.nodeName
kubectl describe pod <a-pending-pod> | grep -A3 Events
when it can't fit, the event tells you exactly why
Warning  FailedScheduling  0/3 nodes are available:
  1 node(s) had untolerated taint {gpu: true},
  2 Insufficient cpu.  preemption: 0/3 nodes are available.
nodeSelector vs affinity vs spread, plainly

nodeSelector = "only sit at tables with this exact label" (rigid). Node affinity = the same idea but with "must" and "prefer" options and richer matching. Pod anti-affinity = "don't seat my copies at the same table" (spread for resilience). Topology spread = the modern, gentle way to say "spread my copies evenly across the rooms (zones), and here's how uneven I'll tolerate (maxSkew)."

Scheduling gotchas
  • Over-strict required rules cause permanent Pending. If no node can satisfy a hard affinity/anti-affinity, the Pod never schedules. Prefer preferred unless you truly mean "must."
  • IgnoredDuringExecution is literal: affinity is evaluated only at scheduling time. Relabel a node later and running Pods are not moved.
  • Anti-affinity + not enough nodes = stuck replicas. "One per node" with 3 replicas but 2 nodes leaves one Pod Pending.
  • whenUnsatisfiable: DoNotSchedule in topology spread can block scheduling; use ScheduleAnyway if best-effort spreading is acceptable.

23. Taints & Tolerations

Affinity is a Pod saying "I want that node." Taints are the reverse — a node repelling Pods unless they explicitly tolerate it.

A taint on a node says "keep Pods away unless they tolerate me." A toleration on a Pod says "I can handle that taint." Together they reserve nodes for specific workloads (GPU nodes, dedicated tenants).

EffectMeaning
NoScheduleDon't schedule new Pods here unless they tolerate the taint.
PreferNoScheduleTry to avoid, but not strict.
NoExecuteAlso evict already-running Pods that don't tolerate it.
Taint a node & tolerate it
kubectl taint nodes node1 dedicated=gpu:NoSchedule
kubectl taint nodes node1 dedicated=gpu:NoSchedule-   # remove (trailing -)
Toleration on a Pod
spec:
  tolerations:
    - key: "dedicated"
      operator: "Equal"
      value: "gpu"
      effect: "NoSchedule"
EKS focus

EKS managed node groups let you set taints declaratively. Common pattern: taint GPU or Spot node groups so only tolerating workloads land there. Karpenter also supports taints on provisioned nodes. Note: some system DaemonSets tolerate everything so they still run on tainted nodes.

Under the hood: taints are the mirror image of affinity, and NoExecute has a timer

Affinity is Pod-driven attraction; taints are node-driven repulsion — and both are evaluated by the scheduler's filter phase. A taint is a key=value:effect triple stamped on a Node object. During scheduling, the scheduler checks each node's taints against the Pod's tolerations and filters out nodes with an untolerated NoSchedule/NoExecute taint. NoExecute is special: it's also enforced after scheduling by the node lifecycle controller — an already-running Pod that doesn't tolerate a newly-added NoExecute taint is evicted. This is exactly how Kubernetes drains a broken node: when a node goes NotReady, the controller adds node.kubernetes.io/not-ready:NoExecute, and Pods (respecting their tolerationSeconds, default 300s) get evicted and rescheduled elsewhere. So taints power both intentional reservations and automatic failure handling.

Worked example — reserve a node, watch Pods avoid it 
kubectl taint nodes ip-10-0-1-42 dedicated=gpu:NoSchedule
kubectl create deployment plain --image=nginx --replicas=5
kubectl get pods -l app=plain -o wide | awk '{print $7}' | sort | uniq -c
no plain pods land on the tainted node
   5 ip-10-0-2-20   # all replicas avoided the tainted node
   0 ip-10-0-1-42
a Pod that tolerates it CAN be placed there
kubectl run gpu-job --image=nginx --overrides='{"spec":{"tolerations":[{"key":"dedicated","operator":"Equal","value":"gpu","effect":"NoSchedule"}]}}'
Taints vs affinity, one sentence

Affinity is a guest asking to sit at a certain table; a taint is a table with a "reserved" sign, and a toleration is the reservation card that lets you sit there anyway. A toleration doesn't force a Pod onto a tainted node — it only allows it; pair with affinity/nodeSelector if you also want to attract it there.

Taint/toleration gotchas
  • A toleration permits, it doesn't attract. Tolerating a GPU taint doesn't send your Pod to the GPU node — it just makes the Pod eligible. Add nodeSelector/affinity to actually target it, or the Pod may land on a cheap node instead.
  • Forgetting DaemonSet tolerations means agents skip your tainted nodes (monitoring/logging blind spots).
  • Built-in taints surprise people: node.kubernetes.io/not-ready, unreachable, disk-pressure, and control-plane taints are added automatically and drive evictions.
  • The trailing - removes a taint (kubectl taint nodes n1 key=val:NoSchedule-) — easy to forget.

24. Autoscaling — HPA, VPA & Cluster/Node Autoscaling

Three different autoscalers operate at different layers. Know which does what.

Three autoscalers = staff, desk size, and building size

Kubernetes can scale at three levels, and people mix them up. HPA (Horizontal Pod Autoscaler) adds more copies of your app when it's busy — like calling in extra cashiers at rush hour. VPA (Vertical) gives each copy a bigger desk (more CPU/memory) instead of adding people. Cluster Autoscaler / Karpenter adds more servers (a bigger building) when there's no room left for new Pods. Most beginners only need HPA: "get busy → add copies; quiet down → remove them."

AutoscalerScalesBased on
HPA (Horizontal Pod Autoscaler)Number of Pod replicasCPU/memory/custom metrics
VPA (Vertical Pod Autoscaler)CPU/memory requests of PodsObserved usage
Cluster Autoscaler / KarpenterNumber of nodesPending (unschedulable) Pods

HPA — add/remove replicas

The HPA watches metrics and adjusts a Deployment's replica count to hit a target (e.g., keep average CPU at 60%). Requires metrics-server installed.

Create an HPA
kubectl autoscale deployment web --cpu-percent=60 --min=2 --max=10
kubectl get hpa
kubectl describe hpa web
hpa.yaml (v2 — supports multiple/custom metrics)
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 60
HPA needs requests set

CPU-based HPA computes utilization relative to the CPU request. If you don't set requests, HPA can't compute a percentage and won't scale. Always set resource requests when using HPA.

VPA — right-size requests

VPA recommends (and can auto-apply) better CPU/memory requests based on real usage. Don't run VPA in auto mode on the same target as HPA for CPU — they conflict. Common practice: VPA in "recommend" mode for guidance, HPA for scaling.

Cluster/Node autoscaling

When Pods can't be scheduled (no room), a node autoscaler adds nodes; when nodes are underused, it removes them. Two main options: the classic Cluster Autoscaler (scales node groups) and Karpenter (provisions right-sized nodes directly, faster and more flexible — AWS-born).

EKS focus — Karpenter vs Cluster Autoscaler
  • Cluster Autoscaler scales EKS managed node groups (Auto Scaling Groups) up/down. Nodes come in the instance types you predefine.
  • Karpenter (recommended for most new EKS clusters) watches pending Pods and launches optimally-sized EC2 instances directly — picking instance types/AZs/Spot to fit exactly, and consolidating/replacing nodes to cut cost. Configured via NodePool and EC2NodeClass CRDs.
  • For metric-driven Pod scaling on AWS metrics (SQS depth, etc.), use KEDA.
  • Combine: HPA for Pods + Karpenter for nodes + right-sized requests = elastic, cost-efficient clusters.
Under the hood: the HPA control loop and its scaling formula

The HPA is a controller that wakes on a timer (default every 15s). Each cycle it reads the current metric for the target's Pods from the metrics.k8s.io API (served by metrics-server for CPU/memory, or a custom/external metrics adapter). It then applies a simple ratio: desiredReplicas = ceil(currentReplicas × currentMetric / targetMetric). So if 4 Pods average 90% CPU against a 60% target: ceil(4 × 90 / 60) = 6 — scale to 6. A tolerance band (~10%) prevents flapping around the target. To avoid thrashing when load is spiky, a stabilization window (default 5 minutes for scale-down) makes the HPA use the highest recent recommendation before shrinking. This is also why HPA needs resource requests: "utilization %" is defined as usage ÷ request, so no request means no percentage to compute.

Why you need BOTH pod and node autoscaling

HPA can shout "I need 4 more Pods!" — but if the cluster has no spare room, those Pods sit Pending forever. That's where Karpenter/Cluster Autoscaler comes in: it notices unschedulable Pods and adds servers so the new Pods have somewhere to live. HPA scales demand for space; the node autoscaler scales the space itself. Run them together or the pod autoscaler eventually hits a wall.

Autoscaling gotchas
  • No metrics-server = HPA shows <unknown> targets and never scales. Install it first.
  • HPA + VPA fighting over CPU. Don't run both against the same target for the same resource — they oscillate. Use VPA in recommend-only mode alongside HPA.
  • Slow scale-up feels like an outage. Node provisioning takes minutes; pre-scale or use headroom/overprovisioning Pods for spiky traffic.
  • Scaling to zero isn't native HPA behavior (min is ≥1); use KEDA for event-driven scale-to-zero.
  • PodDisruptionBudgets can block scale-down — the node autoscaler won't evict Pods it isn't allowed to, leaving underused nodes running.

25. Health Probes — liveness, readiness, startup

Probes let Kubernetes know whether a container is alive and ready. Getting them right is essential for zero-downtime and self-healing.

ProbeQuestion it answersAction on failure
livenessProbe"Is the app alive (not deadlocked)?"Restart the container.
readinessProbe"Is the app ready to serve traffic?"Remove Pod from Service endpoints (no restart).
startupProbe"Has a slow-starting app finished booting?"Hold off liveness/readiness until it passes.
All three probes
containers:
  - name: app
    image: myapp:1.0
    startupProbe:                # for slow starters; gives up to 5min
      httpGet: { path: /healthz, port: 8080 }
      failureThreshold: 30
      periodSeconds: 10
    readinessProbe:
      httpGet: { path: /ready, port: 8080 }
      initialDelaySeconds: 5
      periodSeconds: 10
    livenessProbe:
      httpGet: { path: /healthz, port: 8080 }
      initialDelaySeconds: 15
      periodSeconds: 20
      failureThreshold: 3

Probe types: httpGet (HTTP 200–399 = success), tcpSocket (port open?), and exec (command exit 0?).

Common probe mistakes
  • Liveness too aggressive → healthy-but-busy Pods get killed, causing restart loops. Keep liveness simple and forgiving.
  • No readiness probe → traffic hits Pods before they're ready → errors during rollouts.
  • Slow start without startupProbe → liveness kills the app before it finishes booting → CrashLoop.
  • Liveness endpoint checks dependencies (like the DB) → a brief DB blip restarts all your Pods. Liveness should test the process itself, not downstreams.
PodDisruptionBudgets (PDB)

A PDB limits how many Pods of an app can be voluntarily disrupted at once (during node drains/upgrades), protecting availability. Example: "always keep at least 2 replicas available."

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: web-pdb }
spec:
  minAvailable: 2
  selector:
    matchLabels: { app: web }

On EKS this matters during node group upgrades and Karpenter consolidation — a good PDB prevents taking down too many replicas simultaneously.

Under the hood: who runs probes, and how the three interact

Probes are executed by the kubelet on the node — not the control plane, not a central health checker. Each period the kubelet hits the endpoint/port/command locally and tracks consecutive successes/failures against your thresholds. The three probes feed different machinery: a failed liveness probe makes the kubelet kill and restart the container in place (incrementing RESTARTS, applying CrashLoopBackOff backoff); a failed readiness probe flips the Pod's Ready condition to false, which the endpoints controller sees and removes the Pod's IP from all Service EndpointSlices — so traffic stops, but the container keeps running. The startup probe is a gate: while it's still running, liveness and readiness are suspended, so a slow-booting app isn't killed prematurely. Understanding "readiness = traffic gate, liveness = restart trigger, startup = grace period" prevents most probe disasters.

Worked example — a failing readiness probe pulls a Pod from the Service 
kubectl get endpointslices -l kubernetes.io/service-name=web -o jsonpath='{.items[*].endpoints[*].conditions.ready}{"\n"}'
# make one pod "unready" by breaking its readiness endpoint, then re-check:
kubectl get pod <pod> -o jsonpath='{.status.conditions[?(@.type=="Ready")].status}{"\n"}'
an unready pod is dropped from endpoints but NOT restarted
true true false           # third pod not ready → excluded from Service
RESTARTS still 0          # readiness failure does not restart; liveness would
The three probes as a new employee's first day

Startup probe = orientation: "don't judge them until onboarding finishes." Readiness probe = "are they ready to take customers right now?" — if not, stop routing customers to them (but don't fire them). Liveness probe = "are they still conscious?" — if they've passed out (deadlocked), replace them (restart). Keep liveness lenient (only checks a pulse) and readiness honest (checks they can actually serve).

26. ServiceAccounts — identity for Pods

Humans authenticate to the cluster with user credentials. Pods authenticate with a ServiceAccount — an in-cluster identity used when a Pod calls the Kubernetes API or (with cloud integration) cloud APIs.

Every Pod runs as a ServiceAccount. If you don't specify one, it uses the namespace's default SA. A token for that SA is mounted into the Pod so it can authenticate to the API server. RBAC then decides what that SA is allowed to do.

Create & assign a ServiceAccount
kubectl create serviceaccount app-sa
kubectl get sa
# Assign in a Pod/Deployment spec:
#   spec.serviceAccountName: app-sa
Use a ServiceAccount in a Deployment
spec:
  template:
    spec:
      serviceAccountName: app-sa
      automountServiceAccountToken: true   # set false if the pod doesn't call the API
Least privilege

If a Pod doesn't need to talk to the Kubernetes API, set automountServiceAccountToken: false so no token is exposed. Give each app its own SA with only the permissions it needs — never share the powerful default.

EKS focus — IRSA & Pod Identity (this is huge)

The killer feature: map a Kubernetes ServiceAccount to an AWS IAM Role, so Pods get scoped AWS permissions without storing AWS keys. Two mechanisms:

  • IRSA (IAM Roles for Service Accounts): uses an OIDC provider; annotate the SA with eks.amazonaws.com/role-arn: arn:aws:iam::...:role/my-role. The Pod then assumes that role via the AWS SDK automatically.
  • EKS Pod Identity (newer, simpler): an agent + association API; no OIDC/annotation juggling, easier at scale.

Example: a Pod that reads from S3 gets an SA linked to an IAM role with just s3:GetObject on one bucket. This is the correct way to grant AWS access on EKS.

Under the hood: projected tokens and how IRSA actually works

A modern ServiceAccount token isn't a static secret — the kubelet requests a short-lived, audience-scoped projected token (a signed JWT) from the API server and mounts it at /var/run/secrets/kubernetes.io/serviceaccount/token, rotating it before expiry. When the Pod calls the API server, it sends this JWT; the server validates the signature and maps it to system:serviceaccount:<ns>:<name>, then RBAC decides what's allowed. IRSA cleverly reuses this: EKS runs an OIDC identity provider for the cluster, and the SA's projected token has an AWS audience (sts.amazonaws.com). The AWS SDK in your Pod finds that token file, calls sts:AssumeRoleWithWebIdentity with it, and AWS — trusting the cluster's OIDC provider and the role's trust policy — returns temporary AWS credentials. No long-lived keys ever exist. That's why it's the recommended pattern.

Worked example — a Pod's identity and permissions 
kubectl create serviceaccount app-sa
kubectl run id-check --image=nginx --overrides='{"spec":{"serviceAccountName":"app-sa"}}'
kubectl auth can-i list pods --as=system:serviceaccount:default:app-sa
a fresh SA has almost no permissions by default
no
confirm the mounted token audience (inside the pod)
kubectl exec id-check -- ls /var/run/secrets/kubernetes.io/serviceaccount/
# ca.crt  namespace  token
ServiceAccount gotchas
  • The default SA is a trap. Every Pod uses it if you don't specify one; granting it permissions accidentally empowers every Pod in the namespace. Give apps their own SA.
  • Auto-mounted tokens are an attack surface. If a Pod never calls the K8s API, set automountServiceAccountToken: false so a compromised container can't use the token.
  • IRSA silently fails without SDK support. Very old AWS SDKs don't do AssumeRoleWithWebIdentity; you'll see "unable to locate credentials" despite a correct annotation.
  • Trust-policy mismatch (wrong OIDC issuer, namespace, or SA name) is the #1 IRSA failure — the role exists but STS refuses to assume it.

27. RBAC — Role-Based Access Control

RBAC governs who can do what in the cluster. It's built from four object types.

ObjectScopePurpose
RoleNamespaceA set of permissions (verbs on resources) within one namespace.
ClusterRoleCluster-widePermissions across all namespaces or on cluster-scoped resources (nodes, PVs).
RoleBindingNamespaceGrants a Role (or ClusterRole) to subjects in a namespace.
ClusterRoleBindingCluster-wideGrants a ClusterRole cluster-wide.

Subjects = users, groups, or ServiceAccounts. Verbs = get, list, watch, create, update, patch, delete. RBAC is additive — there are no "deny" rules; you only grant.

Role + RoleBinding: let app-sa read pods in "dev"
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: dev
  name: pod-reader
rules:
  - apiGroups: [""]           # "" = core API group
    resources: ["pods", "pods/log"]
    verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods
  namespace: dev
subjects:
  - kind: ServiceAccount
    name: app-sa
    namespace: dev
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
Create RBAC & test permissions
kubectl create role pod-reader --verb=get,list,watch --resource=pods -n dev
kubectl create rolebinding read-pods --role=pod-reader --serviceaccount=dev:app-sa -n dev

# The "can I?" superpower — test any permission:
kubectl auth can-i list pods -n dev --as=system:serviceaccount:dev:app-sa
kubectl auth can-i '*' '*' --as=someuser         # am I admin?
kubectl auth can-i is your best RBAC debugging tool

Before blaming the app, check whether the identity actually has permission. It answers yes/no instantly and impersonates any user/SA with --as.

EKS focus — mapping IAM to Kubernetes RBAC

On EKS, cluster authentication is via AWS IAM, but authorization is still Kubernetes RBAC. You link them with EKS access entries (modern, API-managed) or the legacy aws-auth ConfigMap. Example: map an IAM role to the Kubernetes group system:masters (admin) or to a custom group bound to a limited ClusterRole. Principle of least privilege applies to both IAM and RBAC.

Under the hood: additive-only, and the Role vs Binding scope matrix

RBAC is evaluated by an admission/authorization stage in the API server on every request. It is purely additive with no deny rules: a request is allowed if any RoleBinding/ClusterRoleBinding grants a matching verb+resource to the requester's identity or groups; otherwise it's denied by default. Two axes matter — where the permissions are defined (Role = one namespace; ClusterRole = cluster-wide or cluster-scoped resources like nodes/PVs) and where they're granted (RoleBinding = within a namespace; ClusterRoleBinding = everywhere). A powerful combo people miss: a RoleBinding can reference a ClusterRole, which lets you define a permission set once (e.g., the built-in view ClusterRole) and grant it namespace-by-namespace. Requests are matched on apiGroups + resources + verbs, so getting the API group right ("" for core, apps, batch, etc.) is essential.

Worked example — grant, then prove with auth can-i 
kubectl create serviceaccount app-sa -n dev
kubectl create role pod-reader --verb=get,list,watch --resource=pods -n dev
kubectl create rolebinding read-pods --role=pod-reader --serviceaccount=dev:app-sa -n dev

kubectl auth can-i list pods   -n dev  --as=system:serviceaccount:dev:app-sa
kubectl auth can-i delete pods -n dev  --as=system:serviceaccount:dev:app-sa
kubectl auth can-i list pods   -n prod --as=system:serviceaccount:dev:app-sa
exactly the granted verb, in exactly the granted namespace
yes     # list pods in dev — granted
no      # delete pods — not in the role
no      # list pods in prod — RoleBinding is namespaced to dev
RBAC as building keys

A Role/ClusterRole is a key design ("opens the supply closets"). A Binding is handing that key to a specific person. A Role's keys only work on one floor (namespace); a ClusterRole's keys can work building-wide. There are no "anti-keys" (no deny) — if you can't open a door, it's simply because no one gave you a key that fits it.

RBAC gotchas
  • Wrong apiGroups. Deployments live in apps, Jobs in batch, Pods in "". A Role listing resources: ["deployments"] under the core group grants nothing.
  • ClusterRoleBinding when you meant RoleBinding. This accidentally grants cluster-wide access — a common privilege-escalation bug.
  • system:masters bypasses RBAC entirely. Members are superusers regardless of bindings; grant it to almost no one.
  • Subresources are separate. Reading logs needs pods/log; exec needs pods/exec — granting pods alone isn't enough.
  • "It's an app bug" that's really RBAC. Always run kubectl auth can-i ... --as=... before deep-diving app code.

28. SecurityContext & Pod Security Standards

A securityContext hardens how containers run: which user, whether root is allowed, filesystem writability, and Linux capabilities.

A hardened securityContext
spec:
  securityContext:              # pod-level
    runAsNonRoot: true
    runAsUser: 1000
    fsGroup: 2000
    seccompProfile:
      type: RuntimeDefault
  containers:
    - name: app
      image: myapp:1.0
      securityContext:          # container-level (overrides pod-level)
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        privileged: false
        capabilities:
          drop: ["ALL"]         # drop all Linux capabilities

Pod Security Standards (PSS) & Pod Security Admission (PSA)

PodSecurityPolicy (PSP) is removed. The replacement is Pod Security Admission, a built-in admission controller enforcing three levels per namespace via labels:

LevelMeaning
privilegedUnrestricted (only for trusted system workloads).
baselineBlocks known privilege escalations; minimally restrictive.
restrictedHeavily hardened best-practice (non-root, drop caps, etc.).
Enforce "restricted" on a namespace
kubectl label namespace dev \
  pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/warn=restricted
Security fundamentals
  • Never run as root unless truly required (runAsNonRoot: true).
  • Drop all capabilities, add back only what's needed.
  • Read-only root filesystem where possible.
  • Never use privileged: true for app containers.
  • Scan images for CVEs (Trivy, ECR scanning) and use minimal base images (distroless/alpine).
EKS focus

Enable Amazon ECR image scanning and admission tools like Kyverno/OPA Gatekeeper to block non-compliant images. GuardDuty EKS Protection monitors audit logs and runtime for threats. Use Bottlerocket (a minimal, security-focused OS) for nodes. Enable EKS control-plane audit logging to CloudWatch for forensics.

Under the hood: securityContext maps to kernel primitives; PSA is an admission gate

A securityContext isn't advisory — each field configures a real Linux kernel control the runtime applies to the container. runAsUser/runAsNonRoot set the process UID (and refuse to start if the image would run as root). capabilities.drop: ["ALL"] strips Linux capabilities so even a "root" process can't do privileged operations like raw sockets or mounting. readOnlyRootFilesystem mounts the container's / read-only (writes must go to explicit volumes). allowPrivilegeEscalation: false sets the no_new_privs bit so setuid binaries can't gain rights. seccompProfile: RuntimeDefault filters dangerous syscalls. Pod Security Admission is the enforcement layer on top: it's a built-in validating admission plugin that, based on the namespace's pod-security.kubernetes.io/enforce=<level> label, inspects each incoming Pod spec and rejects (or warns/audits) any that violates the baseline or restricted profile. PSA doesn't fix Pods — it blocks non-conforming ones at creation.

Worked example — the restricted profile rejects a root Pod 
kubectl create namespace locked
kubectl label namespace locked pod-security.kubernetes.io/enforce=restricted
kubectl run bad --image=nginx -n locked
nginx runs as root and lacks hardening → rejected at admission

The error is the checklist — set those fields and it's admitted.

securityContext vs PSA, simply

securityContext is how you lock down a single container (the settings you write on the Pod). Pod Security Admission is the bouncer at the door for a whole namespace, checking every Pod against a rulebook (privileged / baseline / restricted) and turning away anyone who isn't dressed to code. One is your own seatbelt; the other is a policy that refuses to let unbuckled cars leave the lot.

SecurityContext / PSS gotchas
  • readOnlyRootFilesystem: true breaks apps that write to /tmp or their working dir — add an emptyDir volume for writable paths.
  • fsGroup on large volumes is slow: Kubernetes may recursively chown the whole volume on mount; use fsGroupChangePolicy: OnRootMismatch.
  • Enforcing restricted on existing namespaces breaks running deployments on next rollout. Roll out warn/audit first, fix specs, then enforce.
  • Container-level securityContext overrides Pod-level — a hardened Pod default can be silently undone by a lax container setting.

29. Admission Control & Policy

When a request reaches the API server, after authentication & authorization it passes through admission controllers that can validate or mutate it before it's persisted. This is where policy enforcement lives.

  • Mutating admission — modifies objects (e.g., inject a sidecar, add default labels, set resource defaults).
  • Validating admission — accepts or rejects (e.g., "reject Pods without resource limits", "require an owner label").

You extend this with webhooks or policy engines:

ToolWhat it does
KyvernoPolicy-as-YAML (no new language). Popular, easy. Validate/mutate/generate resources.
OPA GatekeeperPolicies in Rego (OPA). Powerful, more complex.
ValidatingAdmissionPolicyBuilt-in (CEL-based) policy, no external webhook needed — the emerging native option.
Kyverno example — require a "team" label on all Pods
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata: { name: require-team-label }
spec:
  validationFailureAction: Enforce
  rules:
    - name: check-team
      match:
        any:
          - resources: { kinds: [Pod] }
      validate:
        message: "Every Pod must have a 'team' label."
        pattern:
          metadata:
            labels:
              team: "?*"
Where admission fits in the request flow

kubectl apply → Authentication (who are you?) → Authorization/RBAC (are you allowed?) → Mutating admission (tweak it) → schema validation → Validating admission (approve/reject) → persist to etcd. Understanding this order explains many "why was my object modified/rejected?" mysteries.

Under the hood: webhooks, ordering, and the fail-open/fail-closed choice

External policy engines plug in as admission webhooks: you register a MutatingWebhookConfiguration or ValidatingWebhookConfiguration that tells the API server "for objects matching these rules, POST them to my HTTPS endpoint and honor the response." Mutating webhooks run first (and can run several times, so they must be idempotent) — this is how a service mesh injects an Envoy sidecar or how defaults get added. Then the object is schema-validated, then all validating webhooks run and any single rejection fails the request. The critical operational knob is failurePolicy: Fail (fail-closed) means if your webhook is down, matching requests are rejected — safe for security, but a crashed webhook can freeze all Pod creation cluster-wide; Ignore (fail-open) lets requests through when the webhook is unreachable — available, but a policy gap. The newer built-in ValidatingAdmissionPolicy uses in-process CEL expressions, avoiding the webhook network hop and its availability risk.

with the require-team-label policy in Enforce mode
kubectl run noteam --image=nginx
kubectl run good --image=nginx --labels=team=payments
the first is blocked at admission, the second is admitted

Admission control as airport security

Authentication is checking your passport (who are you?). Authorization/RBAC is checking your boarding pass (are you allowed on this flight?). Admission control is the security checkpoint: a mutating step that tidies your bag (adds defaults, injects a sidecar) and a validating step that refuses anything against the rules (no liquids over 100ml = "no Pods without resource limits"). Only after passing all of it do you (the object) get to board — i.e., get written to etcd.

Admission gotchas
  • A dead failurePolicy: Fail webhook can brick the cluster — nothing can be created. Scope webhooks narrowly (namespaceSelector) and exclude kube-system.
  • Mutating webhooks must be idempotent — they can run multiple times; non-idempotent mutations corrupt objects.
  • Order matters: policies validate the object after other mutations, so what you wrote isn't necessarily what's checked.
  • Enforce vs Audit/Warn. Roll new policies out in audit/warn mode first; flipping straight to Enforce can block legitimate deploys.

30. Helm — the Kubernetes package manager

Managing dozens of YAML files across environments is painful. Helm packages them into reusable, parameterized, versioned units called charts.

Analogy: Helm is like apt/npm for Kubernetes. A chart is a package (templated manifests + defaults). Values customize it per environment. A release is an installed instance of a chart in your cluster.

Key concepts

TermMeaning
ChartA bundle of templated Kubernetes manifests + metadata + default values.
Valuesvalues.yaml parameters that fill the templates; override per env.
ReleaseA named, versioned installation of a chart. Upgradeable and rollback-able.
RepositoryA place charts are hosted (e.g., Bitnami, or an OCI registry like ECR).
Everyday Helm
helm repo add bitnami https://charts.bitnami.com/bitnami
helm repo update

# Install with custom values

A templated manifest (templates/deployment.yaml)

EKS focus

Most EKS add-ons ship as Helm charts: AWS Load Balancer Controller, Karpenter, metrics-server, External DNS, Cluster Autoscaler, External Secrets. You can host private charts in ECR (OCI). Pin chart versions and manage installs via GitOps (next sections) for reproducibility.

Under the hood: Helm renders templates client-side, then tracks a release in-cluster

Helm is fundamentally a templating + release-tracking tool, not a runtime agent. On helm install, the client (Helm 3, no server-side Tiller) merges values.yaml with your --set/-f overrides, runs Go templating over everything in templates/ to produce plain Kubernetes YAML, and sends that YAML to the API server — exactly as if you'd kubectl apply'd it. It then records the rendered manifest and metadata as a release secret (in the release's namespace, type helm.sh/release.v1). On helm upgrade it renders the new version, diffs against that stored manifest, and applies the changes; the previous revision's manifest is kept so helm rollback can re-apply it. This is why helm template (render locally, apply nothing) is the perfect debugging tool, and why a release "exists" only as those tracked secrets — delete them and Helm forgets, even though the objects still run.

Worked example — render before you install, then track revisions
see exactly what will be applied — no cluster changes
helm template my-app ./mychart -f values-prod.yaml | head -40
helm install my-app ./mychart -f values-prod.yaml
helm upgrade my-app ./mychart --set replicaCount=5
helm history my-app
every install/upgrade is a numbered, rollback-able revision
REVISION  UPDATED   STATUS      CHART        APP VERSION  DESCRIPTION
1         ...       superseded  mychart-1.0  1.0          Install complete
2         ...       deployed    mychart-1.0  1.0          Upgrade complete
# oops — revert instantly:
# helm rollback my-app 1
Chart vs values vs release, plainly

A chart is a cake recipe with blanks ("bake at {{oven temp}} for {{minutes}}"). values fill the blanks for your kitchen (350°F, 30 min). A release is an actual cake you baked from that recipe with those values — and Helm keeps every version you've baked so you can go back to yesterday's cake if today's flops.

Helm gotchas
  • Templating produces text, so indentation bugs are common. A misplaced nindent yields invalid YAML that only fails at apply time. helm template + --dry-run catch these.
  • Editing objects with kubectl edit causes drift. The next helm upgrade overwrites your manual change — manage everything through values.
  • CRDs are special. Helm installs CRDs from the crds/ dir but does not upgrade or delete them, to avoid data loss — plan CRD upgrades manually.
  • A failed upgrade can leave a release pending-upgrade; you may need helm rollback or --force to recover.
  • Unpinned chart versions make deployments non-reproducible — always pin --version.

31. Operators & Custom Resources (CRDs)

Kubernetes is extensible. Custom Resource Definitions (CRDs) let you add your own object types to the API. Operators add controllers that manage those objects — encoding human operational knowledge into software.

A CRD teaches the API server a new kind (e.g., kind: PostgresCluster). An Operator is a custom controller that watches those resources and reconciles reality to match — handling day-2 tasks like backups, failover, and upgrades automatically.

Analogy: A CRD is a new noun in Kubernetes' vocabulary; an Operator is the expert employee who knows what to do whenever one of those nouns appears or changes. Instead of a human DBA running runbooks, the Operator does it.

Explore CRDs in a cluster

spec: { size: 3 }
EKS focus

You use Operators/CRDs constantly on EKS: Karpenter (NodePool, EC2NodeClass), AWS Load Balancer Controller (TargetGroupBinding), ACK — AWS Controllers for Kubernetes (manage AWS services like S3, RDS, DynamoDB as Kubernetes objects), and database operators. ACK lets you provision AWS infra with kubectl apply.

Under the hood: a CRD extends the API; an Operator is just another reconcile loop

This ties the whole guide together. When you apply a CRD, the API server dynamically registers a new REST endpoint (e.g., /apis/example.com/v1/widgets), validates objects against the CRD's OpenAPI schema, and stores them in etcd — exactly like built-in kinds. But a custom object alone does nothing; it's inert data. An Operator supplies the missing behavior: it's a controller (often built with controller-runtime/Kubebuilder or the Operator SDK) that watches your custom resource and runs the same level-triggered reconcile loop as every built-in controller — observe desired state (the CR's spec), compare to actual, and drive reality toward it, writing progress back to the CR's status. So "a PostgresCluster Operator" is literally a program that, on seeing kind: PostgresCluster, replicas: 3, creates StatefulSets, Services, Secrets, sets up replication, and handles failover — encoding a human DBA's runbook as a reconcile function. The genius of Kubernetes is that your controllers are first-class citizens using the same machinery as the core ones.

Worked example — a CRD gives you a new kubectl-native type 
kubectl apply -f widget-crd.yaml
kubectl api-resources | grep widgets
kubectl apply -f my-widget.yaml
kubectl get widgets
kubectl explain widget.spec
your custom kind now behaves like any built-in resource
widgets   example.com/v1   true   Widget
NAME        AGE
my-widget   10s
# explain shows the schema you defined:
FIELD: size <integer>

Without an Operator watching widgets, my-widget just sits in etcd — proof that the CRD adds the noun and the Operator adds the verb.

CRD + Operator, simply

A CRD teaches Kubernetes a new word — say "Database" — so you can write it down and kubectl get databases. But a word with no one who understands it does nothing. The Operator is the specialist who reads that word and actually does the work: sets up the database, backs it up nightly, fails over if it breaks — all the things a human expert would do, automated. New noun (CRD) + expert who acts on it (Operator) = self-driving software.

Operator / CRD gotchas
  • Deleting a CRD deletes every custom object of that kind — cascading, irreversible. Removing a database Operator's CRD can wipe your Database objects (and what they manage).
  • No Operator = inert CRs. If the controller Pod is down/crashlooping, your custom resources simply stop reconciling — check the Operator's own logs first.
  • CRD version upgrades need conversion. Moving v1beta1→v1 may require a conversion webhook; skipping it breaks stored objects.
  • Finalizers can wedge deletion. An Operator adds a finalizer to clean up external resources; if the Operator is gone, the CR hangs in Terminating until you remove the finalizer manually.
  • Operators need RBAC. They fail silently (permission denied in their logs) if their ServiceAccount lacks rights to the resources they manage.

33. Upgrades, Maintenance & Reliability

Clusters need regular upgrades (K8s releases ~3 minor versions/year, each supported ~1 year) and safe maintenance procedures.

Draining nodes safely

Cordon & drain for maintenance
kubectl cordon <node>      # mark unschedulable (no new pods)
kubectl drain <node> --ignore-daemonsets --delete-emptydir-data   # evict pods gracefully
# ... do maintenance ...
kubectl uncordon <node>    # allow scheduling again

Drain respects PodDisruptionBudgets, so it won't evict more than allowed — this is why PDBs matter.

Upgrade order (general rule)

  1. Upgrade the control plane first.
  2. Then upgrade worker nodes (one minor version at a time — don't skip).
  3. Then update add-ons (CNI, CoreDNS, kube-proxy) to compatible versions.
  4. Check API deprecations before upgrading — removed APIs break manifests.
Watch for deprecated APIs

Each release removes old API versions. Use tools like kubent (kube-no-trouble) or pluto to detect manifests using soon-to-be-removed APIs before upgrading.

Backups & DR

Back up etcd (or use a managed control plane) and use Velero to back up cluster objects and PV data to object storage (S3). Test restores regularly — an untested backup is a hope, not a plan.

EKS focus — upgrades made easier
  • AWS manages control-plane upgrades — you click/CLI to bump the version; AWS handles etcd/HA.
  • Upgrade managed node groups with rolling replacement (respects PDBs), or let Karpenter drift-replace nodes onto the new AMI.
  • Keep EKS add-ons (VPC CNI, CoreDNS, kube-proxy, EBS CSI) updated via the add-on API — AWS validates compatibility.
  • Use EKS upgrade insights to catch deprecated API usage before upgrading.
  • Consider EKS Auto Mode for AWS to manage compute, scaling, and upgrades largely for you.

42. Nodes, Fargate & Karpenter

Choosing and scaling compute well is where EKS cost and performance are won or lost.

Managed Node Groups

The straightforward option: define instance types, min/max/desired counts, AMI type (Amazon Linux 2023, Bottlerocket), and let EKS manage the ASG, AMI updates, and graceful draining on upgrades. Scale with the Cluster Autoscaler.

Fargate — serverless Pods

With Fargate profiles, matching Pods (by namespace/labels) run without any nodes you manage — each Pod gets its own right-sized micro-VM. No node patching, strong isolation.

Fargate limitations
  • No DaemonSets (logging/monitoring configured differently — Fargate log router).
  • No privileged containers, no hostPath, GPU not supported.
  • EBS support is limited (use EFS for shared storage).
  • Can be pricier per-Pod for steady heavy workloads vs EC2.

Karpenter — the modern node autoscaler

Karpenter watches for unschedulable Pods and launches exactly the right EC2 instances in seconds — choosing types, sizes, AZs, and Spot vs On-Demand to fit the pending Pods. It also consolidates underutilized nodes to cut cost.

Karpenter NodePool (v1)
apiVersion: karpenter.sh/v1
kind: NodePool
metadata: { name: default }
spec:
  template:
    spec:
      requirements:
        - key: karpenter.sh/capacity-type
          operator: In
          values: ["spot", "on-demand"]
        - key: node.kubernetes.io/instance-type
          operator: In
          values: ["m5.large", "m5.xlarge", "c5.large"]
      nodeClassRef:
        group: karpenter.k8s.aws
        kind: EC2NodeClass
        name: default
  disruption:
    consolidationPolicy: WhenEmptyOrUnderutilized
    consolidateAfter: 30s
  limits:
    cpu: "1000"
Cost optimization on EKS
  • Use Spot for fault-tolerant/stateless workloads (big savings) with On-Demand fallback.
  • Let Karpenter consolidate to remove waste.
  • Right-size requests — they drive both scheduling and node provisioning.
  • Use Graviton (arm64) instances for better price/performance where images support it.
  • Share one ALB across Ingresses (group.name) and prefer gp3 over gp2.

35. Service Mesh — Istio & Linkerd

Once you have dozens of services, you need consistent mTLS, retries, traffic splitting, and per-request telemetry — without changing every app. A service mesh adds this at the platform layer via sidecar proxies.

Service mesh = a smart post office for your services

Instead of every service learning how to encrypt mail, retry lost letters, and log every delivery, you put a little post-office clerk (a sidecar proxy) next to each one. The clerks handle all the hard networking — encryption, retries, routing, metrics — identically everywhere. Your app just hands its letter to the local clerk and forgets about it. The control plane is head office, telling every clerk the current rules.

CapabilityWhat the mesh gives you
mTLS everywhereAutomatic mutual TLS between services — zero-trust networking with no app changes
Traffic managementCanary/weighted routing, retries, timeouts, circuit breaking, fault injection
ObservabilityGolden-signal metrics, distributed traces, and a service map for free
PolicyAuthorization rules (who may call whom) enforced at the proxy
Istio traffic split — 90/10 canary without touching the app
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata: { name: reviews }
spec:
  hosts: [reviews]
  http:
    - route:
        - destination: { host: reviews, subset: v1 }
          weight: 90
        - destination: { host: reviews, subset: v2 }
          weight: 10
      retries: { attempts: 3, perTryTimeout: 2s }   # automatic retries
Istio vs Linkerd — which to choose

Linkerd is lightweight, opinionated, and easy — a purpose-built Rust micro-proxy, minimal config, great default mTLS. Istio is powerful and feature-rich (Envoy-based) but heavier and more complex. Rule of thumb: choose Linkerd for simplicity and low overhead; choose Istio when you need its advanced routing, extensibility, or multi-cluster features. Also watch Istio ambient mode, which removes per-Pod sidecars to cut overhead.

A mesh is not free

Sidecars add latency (an extra network hop each way), memory/CPU per Pod, and operational complexity. Don't add a mesh for three services — plain Kubernetes Services and NetworkPolicies are enough. Reach for a mesh when mTLS, fine-grained traffic control, and uniform telemetry across many services become real needs.

36. Scheduler Internals & Disruption Budgets

You've seen affinity and taints (§22–23). Now understand how the scheduler decides, and how to protect availability during voluntary disruptions like node drains and upgrades.

PodDisruptionBudget — keep enough replicas during drains
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: web-pdb }
spec:
  minAvailable: 2            # (or maxUnavailable: 1)
  selector:
    matchLabels: { app: web }
# During a node drain / cluster upgrade, Kubernetes won't evict Pods if it would
# drop below minAvailable — protecting availability during voluntary disruptions.
PriorityClass — protect critical workloads
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata: { name: high-priority }
value: 1000000
globalDefault: false
description: "Critical services; may preempt lower-priority Pods."
# Reference it in a Pod spec: priorityClassName: high-priority
The reliability trio every production workload needs
  • PodDisruptionBudget — survive node drains/upgrades without dropping below N replicas.
  • topologySpreadConstraints — spread replicas across zones/nodes so one failure ≠ outage.
  • Anti-affinity — keep replicas of the same app off the same node.

Together these turn "we have 3 replicas" into "we actually stay up when a node dies or is upgraded."

37. Multi-Tenancy & Multi-Cluster

As adoption grows, you must safely share clusters between teams (multi-tenancy) and operate across several clusters (multi-cluster). Lead engineers own these architecture decisions.

Soft vs hard multi-tenancy

Soft (namespaces + quotas + RBAC + policies) suits internal teams that broadly trust each other. Hard (separate clusters, or sandboxed runtimes like gVisor/Kata Containers, or virtual clusters with vcluster) is required when tenants are untrusted, since a container escape in soft tenancy could cross the boundary. Choose based on your threat model, not convenience.

Multi-cluster patterns
  • Why multi-cluster: blast-radius isolation, regional latency, compliance/data residency, and clean prod/nonprod separation.
  • Fleet management: Argo CD (app-of-apps across clusters), Cluster API for cluster lifecycle, and a common policy baseline (Kyverno/OPA) applied everywhere.
  • Cross-cluster networking: service mesh multi-cluster (Istio), Submariner, or a global load balancer routing to the nearest healthy cluster.
  • Config sanity: keep one Git repo of desired state per environment; never click-configure clusters by hand (see the GitOps section).

38. Autoscaling Deep Dive & KEDA

§24 introduced HPA/VPA/Cluster Autoscaler. Here's how they interact, their pitfalls, and event-driven autoscaling for queues and custom metrics.

KEDA — scale a worker on SQS queue depth (even to zero)
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata: { name: worker-scaler }
spec:
  scaleTargetRef: { name: worker }
  minReplicaCount: 0            # scale to ZERO when the queue is empty
  maxReplicaCount: 50
  triggers:
    - type: aws-sqs-queue
      metadata:
        queueURL: https://sqs.us-east-1.amazonaws.com/123/jobs
        queueLength: "5"          # target ~5 messages per replica
        awsRegion: us-east-1
KEDA = autoscaling driven by events, not just CPU

Plain HPA scales on CPU/memory — but a queue worker might be idle on CPU while 10,000 messages pile up. KEDA (Kubernetes Event-Driven Autoscaling) scales on the thing that actually matters: queue depth, Kafka consumer lag, cron schedule, database rows, or any of 60+ sources. Its superpower is scale-to-zero — when there's no work, it runs zero pods (you pay nothing); when a message arrives, it activates pods in seconds. HPA can't go below 1.

KEDA scalerScales onGreat for
aws-sqs-queue / azure-servicebus / gcp-pubsubQueue message countAsync workers, job processors
kafkaConsumer group lagStream consumers (see Messaging guide)
prometheusAny PromQL query resultCustom business metrics (requests/sec, etc.)
cronTime schedulePre-scale before known daily peaks
postgresql / redisQuery result / list lengthDB-backed job tables, Redis queues

When to reach for KEDA over plain HPA

Use plain HPA for classic web services that scale on CPU/latency. Reach for KEDA when the load signal is an event source (a queue, a stream, a schedule) or when you want scale-to-zero for spiky/batch workloads to cut cost. KEDA actually creates an HPA under the hood — it's an extension, not a replacement, so everything you know about HPA still applies.

Autoscaling pitfalls that page you at night
  • HPA + VPA on the same metric — they oscillate. Use VPA in "recommend" mode, or split the metrics.
  • No resource requests — HPA can't compute utilization and won't scale.
  • Slow scale-up — cold starts + node provisioning add minutes. Pre-scale for known spikes or keep warm headroom.
  • Thrashing — tune stabilizationWindowSeconds so it doesn't flap up and down.

The #1 cause of a scary K8s bill

Over-requesting resources. If every Pod requests 1 CPU but uses 0.1, the scheduler reserves 10× the compute you need and you pay for nodes sitting mostly idle. 44. Helm Charts in Practice

§30 introduced Helm. Here's how you actually use it day-to-day — installing charts, templating your own, managing values per environment, and safe upgrades/rollbacks.

Helm = a package manager + templating for Kubernetes

Deploying an app means many YAML files (Deployment, Service, Ingress, ConfigMap…). Copying them per environment is error-prone. Helm bundles them into a chart with variables (values.yaml), so you install a whole app with one command and override just what differs per environment — like apt install but for Kubernetes apps, with knobs.

Using existing charts
# Add a repo and install a real app (e.g. ingress-nginx) with custom values
helm repo add ingress-nginx https://kubernetes.github.io/ingress-nginx
helm repo update
helm install ingress ingress-nginx/ingress-nginx \
  --namespace ingress --create-namespace \
  --set controller.replicaCount=2

helm list -A                          # what's installed
helm upgrade ingress ingress-nginx/ingress-nginx --set controller.replicaCount=3
helm rollback ingress 1               # instantly revert to revision 1
helm uninstall ingress
Your own chart's template (values-driven)
# templates/deployment.yaml — values are injected from values.yaml / --set
apiVersion: apps/v1
kind: Deployment
metadata: { name: {{ .Release.Name }}-web }
spec:
  replicas: {{ .Values.replicaCount }}
  template:
    spec:
      containers:
        - name: web
          image: "{{ .Values.image.repo }}:{{ .Values.image.tag }}"
          resources: {{- toYaml .Values.resources | nindent 12 }}
Environment values & safe upgrades
  • Keep a base values.yaml + per-env files: helm upgrade --install app ./chart -f values-prod.yaml.
  • Always helm upgrade --install (idempotent) and preview with helm diff upgrade (diff plugin).
  • helm rollback is your instant safety net — every release is versioned.
  • Lint & template-render in CI: helm lint and helm template to catch errors before deploy.

45. Kustomize & Config Layering

Kustomize (built into kubectl) takes a different approach from Helm: instead of templating, you keep plain YAML "bases" and layer environment-specific "overlays" that patch them. No templating language to learn.

An overlay that patches the base
# overlays/prod/kustomization.yaml
resources: [ ../../base ]
replicas: [ { name: web, count: 6 } ]
images: [ { name: myapp, newTag: "1.4.2" } ]
patches:
  - path: resources-patch.yaml        # add CPU/mem limits for prod
# apply: kubectl apply -k overlays/prod
# preview: kubectl kustomize overlays/prod
Helm vs Kustomize — which?

Helm shines for packaging apps to distribute (variables, dependencies, versioned releases, rollback) — use it to consume third-party apps and ship your own. Kustomize shines for your own manifests across environments with no templating (plain YAML stays valid YAML). Many teams use both: Helm for off-the-shelf components, Kustomize for their app overlays. Both integrate with GitOps (next).

47. Debugging Pods & Clusters

A systematic toolkit for the question every Kubernetes user faces: "why isn't my pod working?" Work from the object state outward.

The debugging workflow (in order)
# 1. What state is it in, and why?
kubectl get pods -o wide                      # Running? Pending? CrashLoopBackOff?
kubectl describe pod <pod>                     # Events at the bottom explain scheduling/pull/probe failures

# 2. What do the logs say?
kubectl logs <pod> --previous                 # logs from the CRASHED container (key for CrashLoopBackOff)
kubectl logs <pod> -c <container> -f           # follow a specific container

# 3. Get inside / attach a debug container (works for distroless too)
kubectl exec -it <pod> -- sh
kubectl debug -it <pod> --image=nicolaka/netshoot --target=<container>

# 4. Is it a networking / service problem?
kubectl get endpoints <svc>                   # empty = selector matches no pods (common bug!)
kubectl run tmp --rm -it --image=nicolaka/netshoot -- curl http://<svc>:<port>

# 5. Cluster-level
kubectl get events --sort-by=.lastTimestamp  # recent cluster events
kubectl top pods; kubectl top nodes          # resource pressure (needs metrics-server)
The two most common "it's broken" causes

1) Empty Service endpoints — your Service's selector labels don't match the pod's labels, so traffic goes nowhere. kubectl get endpoints <svc> shows empty. 2) Readiness probe failing — the pod is "Running" but not "Ready", so the Service excludes it. kubectl describe pod shows the probe failures. Check these two first for connectivity issues.

48. Troubleshooting Playbook

A systematic approach plus a lookup table for the most common Kubernetes problems. When something's wrong, follow the flow — don't guess.

The universal debugging flow

  1. Get the big picture: kubectl get pods -A — what's not Running/Ready?
  2. Describe the object: kubectl describe pod <pod> — read the Events at the bottom (this solves ~70% of issues).
  3. Read the logs: kubectl logs <pod> (add --previous for a crashed container, -c <name> for multi-container).
  4. Check events cluster-wide: kubectl get events --sort-by=.lastTimestamp.
  5. Exec in to poke around: kubectl exec -it <pod> -- sh (or use kubectl debug for distroless).
  6. Check resources: kubectl top pods/nodes, node conditions via kubectl describe node.

EKS-specific troubleshooting
  • Can't connect (kubectl): re-run aws eks update-kubeconfig; verify IAM identity has an access entry / is in aws-auth; check the endpoint is reachable (public vs private).
  • Pods Pending, "insufficient IPs": subnet IP exhaustion — enable prefix delegation or add subnet CIDR.
  • Pod can't reach AWS API / AccessDenied: IRSA/Pod Identity misconfigured — check SA annotation/association and the IAM role trust policy.
  • PVC Pending: EBS CSI add-on not installed or its IAM role missing; or AZ mismatch.
  • ALB not created: AWS Load Balancer Controller not installed / lacks IAM perms / subnets not tagged.
  • Use CloudWatch control-plane audit logs to see denied API calls and who made them.
